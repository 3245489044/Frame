## 二、错误逻辑（潜在 Bug 与风险）

### 2.1 InMemoryGraphStorage 线程安全漏洞 ⚠️ P0 严重

**位置**：`GraphFoundation/Storage/InMemoryGraphStorage.cs` L68-L69, L178-L185

```csharp
private readonly ConcurrentDictionary<TKey, HashSet<string>> _outgoingEdges = new();
private readonly ConcurrentDictionary<TKey, HashSet<string>> _incomingEdges = new();
```

**问题**：

- `HashSet<string>` 本身**不是线程安全**的
- `AddOrUpdate` 返回同一个 HashSet 实例，多个线程并发 `set.Add(edgeId)` 会导致：
  - 数据损坏（丢失条目）
  - 死循环（HashSet 内部桶链表被破坏）
  - 异常（InvalidOperationException: Collection was modified）

**复现场景**：并发添加多条同源边时触发。

**建议**：
- 方案 A：改用 `ConcurrentDictionary<TKey, ConcurrentDictionary<string, byte>>`
- 方案 B：保留 HashSet，但在所有访问点加细粒度锁
- 方案 C：使用 `ConcurrentBag<string>`（不保证去重，需评估业务）

### 2.2 CoreGraph 事务锁与读锁混用风险 ⚠️ P0 严重

**位置**：`GraphFoundation/Graph/CoreGraph.cs`

**问题 1 — 可重入锁与读锁降级混乱**：

```csharp
private readonly ReaderWriterLockSlim _lock = new(LockRecursionPolicy.SupportsRecursion);

public ITransaction BeginTransaction()
{
    _lock.EnterWriteLock();  // L226 获取写锁
    return new LockedTransaction(this, ErrorHandler);
}
```

- 命令执行时若调用 `ReadLock()`（L297），由于 `SupportsRecursion`，会进入读锁嵌套
- 写锁中获取读锁是合法的（"读锁降级"模式），但 `LockedTransaction.Commit` 在 L389 才释放写锁，期间 `ReadLock().Dispose()` 会先释放读锁，导致锁计数不一致
- `LockRecursionPolicy.SupportsRecursion` 性能开销大，应尽量避免

**问题 2 — Dispose 不等待事务**：

```csharp
public void Dispose()  // L498
{
    if (_disposed) return;
    // 没有检查事务是否进行中
    _lock.Dispose();  // 若有事务持有写锁，会抛 SynchronizationLockException
}
```

**建议**：
1. 移除 `SupportsRecursion`，明确锁层级（写锁内不获取读锁，或显式降级）
2. Dispose 时检查 `_lock.IsWriteLockHeld` 并先回滚事务
3. 实现 `IAsyncDisposable` 异步释放

### 2.4 CacheTransformer 缓存键依赖 TInput.GetHashCode ⚠️ P1

**位置**：`Transformers/CacheTransformer.cs` L27, L44

```csharp
private readonly ConcurrentDictionary<TInput, Lazy<TOutput>> _cache = new();
// where TInput : notnull
```

**问题**：

- `notnull` 约束不保证 `GetHashCode` / `Equals` 被正确重写
- 若 TInput 是可变对象（如 `List<T>`、`Dictionary`、自定义类未重写），用作字典键会：
  - 在对象被修改后找不到缓存
  - 不同实例但值相同的对象重复计算
  - HashSet/Dictionary 内部结构损坏（极少数情况）

**建议**：
- 添加 `where TInput : IEquatable<TInput>` 约束
- 或在构造时校验 `typeof(TInput).IsValueType || typeof(IEquatable<TInput>).IsAssignableFrom(typeof(TInput))`

### 2.5 ConditionalStateMachine.Reset 覆盖原始 StartTime ⚠️ P2

**位置**：`StateMachine/ConditionalStateMachine.cs` L124-L135

```csharp
public void Reset(TState initialState)
{
    lock (_lock)
    {
        var oldState = _currentState;
        _currentState = initialState;
        StartTime = DateTime.UtcNow;  // ⚠️ 覆盖原 StartTime
        EndTime = null;
        StateChanged?.Invoke(this, new StateChangedEventArgs<TState>(oldState, initialState));
```

**问题**：`ExecutionStateMachineBase.Duration` 依赖 StartTime 计算持续时间：

```csharp

{

    {
        if (_stateMachine.EndTime.HasValue)
            return _stateMachine.EndTime.Value - _stateMachine.StartTime;  // ⚠️ StartTime 已被重置

            return DateTime.UtcNow - _stateMachine.StartTime;

```

**影响**：重试场景下，Reset 后 Duration 仅反映"重置后到现在"的时间，丢失了原始启动时间，导致总执行时间统计偏低。

**建议**：
- 增加 `OriginalStartTime` 字段保留首次启动时间
- 或提供 `TotalDuration` 属性累加多次执行时长

### 2.6 AsyncEventStateMachine 虚方法在锁外调用仍有风险 ⚠️ P2

**位置**：`StateMachine/AsyncEventStateMachine.cs` L130-L135

```csharp
{
```

### 2.7 ExecutionPipeline.RunAsync 覆盖 context.CancellationToken ⚠️ P2

**位置**：`Block/ExecutionPipeline.cs` L127-L128

### 2.11 CoreGraph.PublishEvent 锁外调用 OnNext ⚠️ P2

**位置**：`GraphFoundation/Graph/CoreGraph.cs` L272-L279

```csharp
internal void PublishEvent(GraphEvent evt)
{
    lock (_eventSubject)
    {
        if (_eventCompleted) return;
    }
    _eventSubject.OnNext(evt);  // ⚠️ 锁外调用
}
```

**问题**：

- 检查 `_eventCompleted` 与 `OnNext` 之间有竞态窗口
- 另一线程可能在 `lock` 释放后、`OnNext` 调用前调用 `Dispose` 并 `OnCompleted`
- `Subject.OnNext` 在 `OnCompleted` 后调用会抛 `ObjectDisposedException`

**建议**：将 `OnNext` 移入锁内，或使用 `Interlocked.Exchange` 标志位检查。

## 五、关键发现与重构建议

### 5.1 关键发现

**Map 模块的"分层抽象"过度**：同一关注点在多处独立实现：

| 关注点 | Block | Container.Behaviors | Container.Decorators | Transformers |
|---|---|---|---|---|
| 重试 | RetryBlockBase | RetryBehavior | RetryDecorator | — |
| 超时 | TimeoutBlock | TimeoutBehavior | TimeoutDecorator | — |
| 熔断 | — | CircuitBreakerBehavior | CircuitBreakerDecorator | — |
| 日志 | LogBlock | LoggingBehavior | LoggingDecorator | — |
| 条件 | ConditionalBlock | — | — | ConditionalTransformer |
| 容错 | — | — | — | TryTransformer |

### 5.2 优先重构项

1. **统一 PolicyFactory**：将四套 Polly 策略构建集中到 `Container.PolicyFactory`，Block 与 Decorator/Behavior 共用
2. **抽取 StateChangeEmitter**：将 StateMachine 的 5 处事件触发模式统一为辅助类
3. **抽取 NamedItemList**：统一 Block/Queue 的 FindIndexByName/InsertBefore/InsertAfter/Remove
4. **修复 InMemoryGraphStorage 并发**：将 `HashSet<string>` 替换为线程安全结构
5. **修复 CoreGraph 锁管理**：移除 `SupportsRecursion`，明确锁层级，Dispose 时回滚事务
6. **补全 Queue 错误传播**：ConsumeLoopAsync 引入日志、错误回调、最大失败次数

### 5.3 重构顺序建议

```

```
