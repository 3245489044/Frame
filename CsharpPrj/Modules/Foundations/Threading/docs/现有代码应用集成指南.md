# 现有代码应用指南 — 统一异步执行框架（AEF）集成与迁移

> 版本：1.1（实施状态更新）｜ 前置：先完成《AsyncExecutionFramework-扩展设计.md》中 P1–P3

> **实施状态（2026-08）**：函数调用内核（`InvocationKernel`）已落地——见 `Share/EventBindingOrchestrator/Invocation/`。
> - ✅ opId 关联贯穿（click ↔ ECS 分发 ↔ 内核终结事件）
> - ✅ 单一权威计时（`InvocationBudget`：绝对预算内核裁决；空闲看门狗默认关闭，根治误杀慢函数）
> - ✅ 失败分类裁决（`InvocationOutcome`：FunctionFault=函数错 / FrameworkTimedOut·IdleHung=框架错 / SignalLost=框架缺陷）
> - ✅ 命令层归因：`click ... 失败 [Kind] (opId=...)`
> - ✅ `ClineClient.RunNodeAsync` 任何取消/超时 kill 整棵进程树（杜绝孤儿进程）
> - ✅ `CancellationTokenInjector`（`ExecutionFramework.Engine`）：委托声明 CancellationToken 即自动注入调用方 ct（其余零影响）
> - ✅ 取消链贯通：`FunctionSystem` 转发 ct → `FunctionExecutor` 单一时钟（有框架 ct 时不再叠加内层 30s）→ `FunctionDescriptor` 过滤 ct 参数 + 注入器 → Cline 函数声明 ct → `ClineClient` 预算点 kill node 进程树
> - ✅ click 等待预算 = 函数预算 + 宽限，读到归因分类而非竞速超时
> - ⏳ 真机验证：Cline CLI 下预算即杀 node 需端到端回归；入口全量收敛到内核
> 目标：把散落在五处的异步生命周期收编到 `Modules.Threading` 的 AEF，消除孤儿进程、级联、死锁与延迟日志。

## 1. 迁移总览（收编映射）

| 现有调用点 | 现状（碎片） | AEF 落地方式 |
|---|---|---|
| `EcsEventBus.DispatchFunctionAsync` | 手建 `TaskCompletionSource<bool>` `completion` | 改为提交 `AsyncOperation`；`TrySetResult` → `op.Complete` |
| `ClickSystem`（`ClickSetGetSystems.cs`） | `ack.Completion.Wait(timeout)` 阻塞 | `await op.WaitAsync()`；`timeout<=0` = 无固定上限，靠空闲看门狗 |
| `AwaitValueSystem` | 手建 TCS + `tcs.Task.Wait()` | 订阅 `AsyncOp` 状态/发布事件，非阻塞 |
| `FunctionCallFacade` | `Task.WhenAny` 竞速 + `ContinueWith` 只打日志 | 变薄适配器：提交 AsyncOp，`TimeoutMs<=0`=无上限，取消贯穿 |
| `ClineClient.RunNodeAsync` | 自管进程 + 自身 20min/空闲逻辑 | 实现 `IProcessHandle` + 心跳；取消→`process.Kill` |
| `FunctionCallFacadeResult`/`ExecutionResult`/`FunctionCallResult` | 三套结果类型 | 统一为 `AsyncOperationResult` |
| 日志（`FrontEndDrivenLog` 延迟 60s） | 散落 `BeginInvoke` | 经 `ThreadContext.Post` 单一调度 |

## 2. 第一步：装配 AEF（应用启动处）

```csharp
using Modules.Threading;

// 应用初始化（MainForm / FrameworkInitializer）处：
ThreadingBridge.Initialize();                       // 既有：SetMainThread

var scheduler = new AsyncOperationScheduler(
    maxConcurrency: 4,
    idleWindow: TimeSpan.FromSeconds(30));          // 空闲兜底 30s
var watchdog = new WatchdogService();
watchdog.Start(TimeSpan.FromSeconds(2), TimeSpan.FromSeconds(30));

ThreadingBridge.InitializeAEF(scheduler, watchdog);
```

> `idleWindow=30s` 满足"快速失败"；需要"不设固定时限"时，单个操作用 `IdleTimeout<=0` 覆盖。

## 3. 迁移 `ClineClient`（实现 `IProcessHandle` + 心跳 + 取消贯穿）

这是取消链的末端，是"真正终止孤儿进程"的关键。

```csharp
// 改造后：ClineClient 暴露 IProcessHandle，并向 AsyncOp 报告心跳
private async Task<string> RunNodeAsync(
    IReadOnlyList<string> args,
    CancellationToken cancellationToken)
{
    using var process = new Process();
    /* ... StartInfo 配置同现状 ... */

    if (!process.Start()) throw new InvalidOperationException(...);
    process.BeginOutputReadLine();
    process.BeginErrorReadLine();

    // 心跳：每行输出即 op.ReportProgress → 看门狗重置空闲窗口
    process.OutputDataReceived += (_, e) => { if (e.Data is not null) { stdout.AppendLine(e.Data); _heartbeat?.Invoke(); } };
    process.ErrorDataReceived  += (_, e) => { if (e.Data is not null) { stderr.AppendLine(e.Data);  _heartbeat?.Invoke(); } };

    try
    {
        await process.WaitForExitAsync(cancellationToken);   // 取消贯穿→框架/调用方取消即终止等待
    }
    catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested)
    {
        try { process.Kill(entireProcessTree: true); } catch { /* 忽略 */ }
        throw new TimeoutException("ClineApi 调用空闲挂起/超时");
    }
    /* ... 后续 ExitCode 校验同现状 ... */
}
```

要点：
- **`CancellationToken` 必须来自 `AsyncOp.Cts`**（由 FunctionCallFacade/调度器传入），不再用自身 20min 计时兜底。
- **心跳源**：node stdout/stderr 每行（真实 AI 调用配 `cli.ts --stream` 才有持续输出）。
- 被取消时 `WaitForExitAsync(token)` 抛 `OperationCanceledException` → `process.Kill` → 无孤儿进程。

## 4. 迁移 `FunctionCallFacade`（变薄适配器）

```csharp
// 改造后：ExecuteAsync 提交 AsyncOp，取消贯穿 + 无固定上限
public static async Task<AsyncOperationResult> ExecuteAsync(FunctionCallRequest request)
{
    var scheduler = ThreadingBridge.AefScheduler;
    return await scheduler.RunAsync(
        request.FunctionName,
        async (ct, progress) =>
        {
            var svc = ResolveExecutionService();
            // 关键：ct 贯穿到执行服务 → ClineClient.RunNodeAsync
            return await svc.ExecuteFunctionAsync(request.FunctionName,
                request.Parameters ?? new(), ct);          // 签名增加 CancellationToken
        },
        new AsyncOperationOptions
        {
            IdleTimeout    = request.TimeoutMs <= 0 ? null : TimeSpan.FromMilliseconds(request.TimeoutMs),
            AbsoluteTimeout= null,                          // 默认不设绝对上限
            ReentryKey     = request.FunctionName,          // 防重复真实调用
            Process        = request.ProcessHandle,         // 可杀对象
        });
}
```

要点：
- 删除 `ExecuteWithTimeout` 的 `Task.WhenAny` 竞速与 `BuildTimeoutResult` 的 `ContinueWith`。
- `request.TimeoutMs<=0` → 无绝对上限（交给空闲看门狗）；`>0` → 仅作为**空闲窗口**语义，而非"绝对竞速"。
- 结果统一为 `AsyncOperationResult`，三套旧结果类型删除。

## 5. 迁移 `EcsEventBus.DispatchFunctionAsync`

```csharp
// 改造前：var completion = new TaskCompletionSource<bool>(...);  completionTask = completion.Task; ...
//         dispatch 后 completion?.TrySetResult(true/false)

// 改造后：Dispatch 返回 AsyncOp（替代 EventDispatchResult.Completion）
var op = new AsyncOperation<bool>(name: binding.FunctionName);
_ = DispatchAsync(binding, parameters, evt, op, evt.FunctionTimeoutMs);
return new EventDispatchResult(EventDispatchOutcome.Dispatched, matchedFunction, Operation: op);

private async Task DispatchAsync(..., AsyncOperation<bool> op, int? functionTimeoutMs)
{
    try
    {
        var result = await FunctionCallFacade.ExecuteAsync(new FunctionCallRequest
        { FunctionName = binding.FunctionName, Parameters = parameters, ... });

        if (result.IsSuccess && binding.OutputTarget is not null && result.Output != null)
            _stateAccessor.SetValue(binding.OutputTarget, result.Output.ToString());

        op.Complete(result.IsSuccess);   // 取代 completion.TrySetResult
    }
    catch (Exception ex) { op.Fail(ex); }
}
```

要点：`AsyncOperation<bool>.Completion` 即原来的 `completionTask`，由框架统一终结（Complete/Fail/Cancel）。

## 6. 迁移 `ClickSystem`（非阻塞等待 + 无固定上限）

```csharp
// 改造前（阻塞）：if (!ack.Completion.Wait(waitTimeoutMs)) { ...timeout... }
// 改造后（非阻塞）：命令系统改为 async，或经 op.Completion.WaitAsync
if (wait)
{
    // 阻塞式命令线程仍可用 Task.WaitAsync 有限等待；首选把命令处理器改为 async
    var ok = await op.Completion.WaitAsync(
        waitTimeoutMs > 0 ? TimeSpan.FromMilliseconds(waitTimeoutMs) : Timeout.InfiniteTimeSpan);
    // waitTimeoutMs<=0 → 无限等待，靠 AsyncOp 自身空闲看门狗自终止后 Completion 落定
    if (!ok) { BackEndLog.Log("Command_Await_Timeout", ...); SetFailure(...); return; }
    /* 后续取 op.Result / 回读 outputTarget 同现状 */
}
```

要点：
- 用 `WaitAsync`（非阻塞）替代 `Task.Wait()`；若命令系统为同步循环，至少用 `op.Completion.WaitAsync(TimeSpan)` 带可空上限。
- `timeout<=0` 语义保持"不设固定上限"，由空闲看门狗兜底。

## 7. 迁移 `AwaitValueSystem`

```csharp
// 改造前：手建 tcs + 订阅 DataChanged + tcs.Task.Wait(timeout)
// 改造后：订阅控制键发布事件 → 把"等待值"建模为 AsyncOp
public override async Task ExecuteAsync(Entity entity, CommandMetaComponent meta)
{
    var target = meta.Target;
    var op = new AsyncOperation<string>(name: $"await:{target}");
    var key = ControlKeyPrefix + target;

    using var sub = EntityManager.GetComponentDataStore()
        .DataChanged
        .Where(e => string.Equals(e.Key, key, StringComparison.Ordinal)
                    && !string.IsNullOrWhiteSpace(e.NewValue?.ToString()))
        .Subscribe(_ => op.Complete(target));

    var timeout = ResolveTimeout(meta);            // <=0 → 无固定上限
    var ok = await op.Completion.WaitAsync(
        timeout > 0 ? TimeSpan.FromMilliseconds(timeout) : Timeout.InfiniteTimeSpan);
    /* 成功/超时处理同现状 */
}
```

要点：`AwaitValueSystem` 与 `ClickSystem` 收敛为同一 `AsyncOp.WaitAsync` 范式。

## 9. 传输层修复（AEF 之外的独立问题）

AEF 保证挂起的 `ClineCore.create` 在 idle 窗口内被终止且不阻塞其他操作。**但要真正让 plan/ask/history 完成，仍需处理 `ClineCore.create({backendMode:"local"})` 在本机 headless 卡死**：

- 诊断结论（已实测）：`version`/`config` 直接跑秒回，`history`（创建 ClineCore）>25s 卡死 → 问题在 ClineCore 本地后端初始化。
- 修复方向（择一）：
  1. 将 `SdkTransport` 的 `backendMode:"local"` 改为走真实 `cline` CLI（headless `--json`），或使用可用的 provider 通道。
  2. 若为 data-dir/锁竞争，给每次调用独立 `--data-dir`（对应 `AsyncOperationOptions.IsolationKey`）。
- 这一步与 AEF 正交：AEF 治理"如何跑"，传输修复治理"跑什么"。
