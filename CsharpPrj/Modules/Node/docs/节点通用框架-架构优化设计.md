## §0 诊断结论

### 0.1 三个结构性缺失 + 一个定位漂移

| # | 缺失 | 一句话 | 批量生成的症状 |
|---|---|---|---|
| **S1** | **校验有件、无裁决权** | 框架齐备实现了校验代数（声明面 + 链面 + 对账），但**声明面校验没有任何装配期调用点**，也没有"Error ⇒ 拒绝产出实例"的语义 | 声明缺陷一律拖到运行期以**崩溃/静默**暴露（`task-node` 整域物化抛异常、`ParseEnum` 静默回退） |
| **S2** | **键代数只闭合一半** | 只有正向半映射（identity values → 位置键）；**无反向**（位置键 → identity values）。闭包约束**已实现但未执行**（见 §0.2） | 无法"由某位置的键寻址同一节点的其它位置" ⇒ B1 per-frame 键、C1「同 Key 多位置」缺同一座桥 |
| **S3** | **能力面无必需性/生命周期** | `NodeFramework` 把 23 个端口平铺为 `get` 属性（`NodeFramework.cs:98-147`），无任何"写路径/读路径/治理各需要哪几件"的声明 | `Compensation` / `Reconciler` / `Validator` / `ChainComposer` 可"永久缺席或零读取而不被察觉"（影子能力）；B0 之前 `NodeFramework` 自身零调用点亦无人察觉 |
| **S4** | **两套"节点"语义共用一个装配根（定位漂移）** | Usharp/Chain 世界（`NodeConfig`/`NodeChainDocument`/`NodeDirectiveSet`/`NodeChainComposer`/`NodePortBinding`）与 Agent/ur_nodes 世界（`NodeExecutionRecord`/`NodeMaterializer`/`NodeReadProjection`）共用同一个 `NodeFramework` 与**同一份 identity/placements 声明** | Agent 侧只消费 4 件；`C1 待评估是否触 Frame` 反复卡住（两世界的"节点"不是同一个东西）；而框架 ModuleRule 自述"位置层纯净、不引上层契约"——`NodeChainComposer`/`NodeDirectiveSet` 恰为上层 Chain 服务，**已与自述定位漂移** |

### 0.2 决定性证据：校验代数齐备，缺的是"裁决权"（全仓实测）

| 校验件 | 定义 | 生产调用点 | 结论 |

`Placeholders(placement.KeyTemplate) ⊆ Placeholders(Identity.Template)`，违例码 `spec.placement-template-unknown-field`（Error）。

> ⇒ 因此本设计的形态是「**把既有校验代数接成裁决点**（O1）+「**补唯一真新增：反向寻址**」（O2），而非"引入新代数"。
> ⇒ 这一结论同时解释了 S1：**同一族校验、同一族装配入口，链判据接了一半、声明判据没接**。

## §1 设计原则（约束本设计的四条）

| # | 原则 | 含义 |
|---|---|---|
| P1 | **裁决优于诊断** | 判定"声明不可用"时，框架**不得产出实例**（⊥ 不产生对象）；诊断是裁决的副产物，不是替代品。对齐 `[CR: axioms:AX-FRAME.CriterionWellFormedness@consume]`「¬wellformed → 判定 ⊥，不作放行依据」 |
| P2 | **单源不改写，只收口** | 既有校验件（Validator/Reconciler/TemplatesDistinguishable/Codec）**不复制、不重写**，只把它们接进单一裁决序（`Strategy.SingleImplementation`） |
| P3 | **新增仅限"代数闭合"** | 允许新增的只有几何/代数上缺失的东西（反向解析、`ViewParams`、能力必需性、读侧声明）；其余一律接线 |
| P4 | **不越层、不泛滥** | 不把 Agent 业务语义（task/history/会话/轮次治理）搬进框架；不做表达式语言；不把 `Error/Warning/Info` 抹平成全阻断（N9 只要求"不静默"） |

## §2 O1 装配期裁决点（Assembly Gateway）

### 2.1 不变式

```
INV-1  ∀spec, ports:  Assemble(spec, ports) ≠ ⊥  →  WellFormed(spec) ∧ Validator.Validate(spec).IsValid
INV-1b ∀spec:  ¬WellFormed(spec) ∨ Validator.Validate(spec) 含 Error  →  Assemble(spec) = ⊥（拒绝产出实例）
INV-1c 裁决序固定： Load → WellFormed → Validator.Validate → Reconciler.ValidateTemplates → SelfCheck(O4) → 裁决
INV-1d 装载期枚举非法 ⇒ 诊断（spec.enum-invalid），不回退默认值
```

### 2.2 接口形状（设计，非实现）

```
NodeFramework.Assemble(spec, ports, policy) → NodeAssemblyOutcome
  NodeAssemblyOutcome = { Framework: NodeFramework?, Validation: NodeSpecValidationReport,
                          Reconciliation: ReconciliationReport, Diagnostics: [NodeDiagnostic] }
  policy = Strict | WarnOnLegacy   // Strict = Error 即拒装配；WarnOnLegacy 仅供存量迁移期降级观测
  FromSpec(...) 保留为兼容入口：= Assemble(policy=WarnOnLegacy)（存量不炸；新宿主一律 Strict）
```

**关键纪律**：`Framework = null` 时**不提供**任何可用端口；调用方按"未装配 + 可见化"处理（与 `NodeFrameworkHosting.TryAttach` 现有口径一致，见 `Agent应用篇-实施步骤.md` §15.1）。

### 2.3 判据

| 判据 | 命令 / 断言 |
|---|---|
| 枚举非法 ⇒ 装载期 Error | 新用例：`form/retention/state` 写非法值 → `spec.enum-invalid` 出现，且 `Assemble` 返回 ⊥ |
| 声明面裁决被调用 | 新用例：违例声明 → `Assemble` 返回 ⊥ 且 `Validation.Errors ≠ ∅` |
| 兼容入口不炸存量 | `FromSpec` 对现有 fixture 仍非 null（`Modules.Node.Tests` 既有 **100 例**零回归） |
| 门禁 | `Check-NodeFramework.ps1` 增项：`Assemble` 为唯一装配入口（禁 `new NodeFramework(...)` 旁路） |
| 命令 | `dotnet build Frame\CsharpPrj\Modules\Node\Modules.Node.csproj` → `& Frame\PowerShellScript\Modules\Node\Check-NodeFramework.ps1 -ShowDetail` → `& Environment\CentralTest\Run-CSharpTests.ps1 -Test node` |

### 2.4 迁移影响

- `FromSpec` 语义变更（新增裁决）⇒ 需 §10.3 的 **M1/M2 声明迁移先行**，否则 Agent 侧拒装配（§0.3 的 3 Error）。
- B0 的 `NodeFrameworkHosting.TryAttach` 改用 `Assemble(Strict)`，并把 `Validation.Errors` 计数并入装配日志（现仅统计 `Diagnostics`）。

## §3 O2 键代数闭合（Address Algebra）

### 3.1 不变式

```
INV-2  ∀p ∈ Placements:  Placeholders(p.KeyTemplate) ⊆ Placeholders(Identity.Template) ∪ ViewParams(p)   // 已实现，仅需执行（§0.2）
INV-3  ∀p, ∀a ∈ Address:  TryParse(p, KeysFor(p, a)) = a            // 往返恒等（位置 → 地址）
INV-3b ∀p, ∀k ∈ Keys(p):  ∃! a : KeysFor(p, a) = k                  // 键 → 地址唯一（消除 ambiguous 多解）
INV-4  ∀p: placementKey 占位符取值来源必须可枚举声明（Context / Sequence / ViewParam / 字面量），无可隐式来源
```

### 3.2 唯一真新增：**反向解析**

现状（实测）：`NodeMaterializer:86` → `values = TryParseValues(identity.Template, request.Key)`；`:175` → `placementKey = Evaluate(spec.KeyTemplate, values)`。**只有这一条正向链。**

设计新增（**唯一**新增代数件）：

```
AddressSpace(identity, placements)
  Evaluate(p, values) → placementKey                 // 复用 KeyTemplateEvaluator（单源，不改写）
  TryParse(p, placementKey) → values                 // ★新增：按位置模板反解（与正向同一占位符词法）
  KeysFor(address) → { p → placementKey }            // ★新增：同一地址在全部位置上的键（C1 的基础）
  AddressOf(placementKey) → address | ⊥              // ★新增：由任一位置的键回到身份（B1 per-frame 的基础）
```

**为什么这是"代数闭合"而不是补丁**：
- 反向**不引入第二套键逻辑** —— 与正向共用 `KeyTemplateEvaluator.PlaceholderRegex`（`:15`）与 `TryParseValues`（`:77`），是同一函数的对偶。
- 它把「键即地址」（N1）从**声明**变成**可计算**：由此可回答"同一逻辑节点有哪些键" —— 这是 C1「同 Key 多位置」与 D1′「读侧按位置枚举」的共同前置。
- 它顺带把 `RefHeadContext.KeyOrder` / `SessionMessageKeys.OrderComparer` 这类"各层自定的键序/寻址口径"收敛到框架一处（此后只需一个 `IComparer<string>` 适配）。

### 3.3 `ViewParams`（位置额外值的显式声明）

`task-node`（`{storage}.{node}`）在代数上**不是错误**，而是"该位置需要 identity 之外的额外值"。设计上**允许**，但必须**显式声明来源**：

```
placement: { id, carrier, key, form, retention, selection, writer,
             viewParams: [ { name: "storage", from: "caller" | "declared" } ] }
```

- `from=caller`：调用方在 `NodeMaterializeRequest` 中显式给出（如 B1 的 `frameSeq`）。
- `from=declared`：位置声明常量（如固定 `storage="task"`）。
- `from=env`：**禁止**（进程环境不可复现，违 K5/P14）。

**约束**：`ViewParams` 只允许枚举式来源，**不做表达式语言**（P4）。

### 3.4 判据

| 判据 | 断言 |
|---|---|
| 往返恒等 | 新用例：∀fixture 位置 × ∀样本地址：`TryParse(p, Evaluate(p, a)) = a` |
| 键→地址唯一 | 新用例：同域任意两位置键空间交集为 ∅ ⇒ `AddressOf` 单值（消 `ambiguous` 对账发现） |
| 缺值不再抛 | `KeyTemplateEvaluator.Evaluate` 缺值 → 归 `Assemble` 期 Error（INV-1b），**运行期不再抛 `InvalidOperationException`** |
| 门禁 | `Check-NodeFramework.ps1` 增项：框架内**唯一**键求值入口 = `KeyTemplateEvaluator`（禁第二处手拼/反解） |
| 命令 | `Modules.Node.Tests` 增"代数往返"用例组 → `Run-CSharpTests.ps1 -Test node` |

### 3.5 迁移影响

- `PlacementSpec` 增 `ViewParams`（可选，缺省空 ⇒ 存量声明零影响）。
- **`task-node` 必须裁决**：或 `storage`/`node` 由 `from: caller|declared` 显式给，或移出本域声明（见 §9 路线）。
- `NodeMaterializer` 的键求值改为经 `AddressSpace`（行为等价，仅入口收敛）。

## §4 O3 能力契约（Capability Contract）

### 4.1 不变式

```
INV-5  ∀kind ∈ {Write, Read, Govern}:  Capable(kind) → Required(kind) ⊆ Bound
INV-5b  ∀p ∈ 框架公开面:  p 的（生产）读取点 ≠ ∅  ∨  p 显式标记 inactive
INV-5c 装配日志必须逐项列出 {required, bound, unbound, inactive}
```

### 4.2 设计（治 S3）

实测面：`NodeFramework` 暴露 23 个 `get` 属性（`NodeFramework.cs:98-147`），其中**已证零读取**者：`Validator`（暴露但无人调 `Validate`）、`Compensation`、`Reconciler`（仅测试）、`ChainComposer`（仅测试）、`ReferenceIndexImpl`、`PortBinding`、`Directives`（Agent 侧零消费）。

```
NodeCapabilities:
  Write  ← { Identity, Placements, Carriers, FormCodec, Defaults, WriteGate, Materializer, AddressSpace(O2) }
  Read   ← { Identity, Placements, Carriers, Selections, FormCodec, Projection, AddressSpace(O2) }
  Govern ← { Validator, Reconciler, Compensation, Diagnostics }

Framework.EnsureCapable(kind) → 缺失即抛/诊断（fail-fast，二次防线）
Framework.Capabilities → 只读清单（供装配日志与门禁）
```

**与 S4 的关系**：`ChainComposer` / `Directives` / `PortBinding` 属 Usharp/Chain 世界 —— 在 Agent 宿主下应登记为 `inactive`（而非沉默）。这正是 §9 路线 A 的落点。

### 4.3 判据

| 判据 | 断言 |
|---|---|
| 必需面齐 | 新用例：`EnsureCapable(Write/Read)` 在缺端口时抛/诊断；装配齐全时通过 |
| 零读取面可见 | 装配日志含 `inactive: [...]`；门禁断"公开面无 `inactive` 标记且零读取" ⇒ 违规 |
| 命令 | `Check-NodeFramework.ps1` 增项（E 类同族：公开面可达性审计）+ `Modules.Node.Tests` |

## §5 O4 读写对称自证（Round-trip SelfCheck）

### 5.1 不变式

```
INV-6  ∀p ∈ Placements:  SelfCheck(p) 通过  ⟺
       Decode(p.Form, Encode(p.Form, sampleJson)) 语义等价（raw 恒等；view/digest 按形态规约）
       ∧ TryParse(p, Evaluate(p, a)) = a                     // 即 INV-3
       ∧ WriterId 与声明一致 ∧ Selection 表达式可解析
```

### 5.2 设计（治 S1 的"运行期才发现"）

- `SelfCheck` 在 `Assemble` 期执行（INV-1c 的倒数第二步），用**内存载体**做 dry-run，**不触真库**。
- 把既有影子件接成 SelfCheck 的**执行体**（P2 单源）：
  - `NodeCompensation`：进入"提交前快照 → 失败回滚"的自证切片（`SyncProtocolTriple` 的 Compensate 段在装配期即被证明可用）。
  - `NodeReconciler.ValidateTemplates`：直接作为 drift 判据。
- 对齐 `[CR: axioms:AX-CORE.SyncProtocolTriple@consume]`：Commit→Compensate→Observe 的 Observe 段在装配期成立，而非留到运行期。

### 5.3 判据

| 判据 | 断言 |
|---|---|
| 逐位置自证 | 新用例：∀fixture 位置 `SelfCheck = pass`；注入坏 `Form`/不可解析 `Selection` → fail 且 `Assemble` 返回 ⊥ |
| raw 恒等 | raw 形态载荷**逐字节**恒等（N11） |
| 命令 | `Modules.Node.Tests` 增"SelfCheck"用例组 + `Run-CSharpTests.ps1 -Test node` |

## §7 O6 静态面边界 + 作用域注册表

### 7.1 不变式

```
INV-8   框架内允许的静态面 = { static readonly 不可变实例 | 纯函数 }；禁：可变静态字段/属性、进程级 handler 单值
INV-8b  多作用域状态（run state / 序列 / sink）经 NodeScopeRegistry 按作用域键持有 ⇒ 多会话不串味为结构保证
```

### 7.2 依据（实测）

- `ClineDaemonPool.PersistSink` 为进程级单 handler（经 root slot）⇒ 多会话共享一个 persist 接收器（B1 前置障碍）。
- `ClineClientDiagnostics.Emit` / `ClineDaemonPool.Diagnostics` / `AttachTraceProjection` 均为静态挂钩；`ClineDiagnosticsHosting` 原为 `static` + `Interlocked`（E6）。
- `KeyProcessor.HierarchyFormat` / `Mapper` 为类型级 static 单值 ⇒ 键层次格式全局唯一（多工作流差异只能靠传参覆盖）。
- 门禁 E 类**只扫 `Modules.Node`（29 文件）** ⇒ Agent 侧同类静态面不在覆盖内（B0 用 `RootSlot` 属人工纪律）。

### 7.3 判据

| 判据 | 断言 |

## §8 O7 读侧消费者声明（反向声明制度化）

### 8.1 不变式

```
INV-9  ∀p ∈ Placements:  IsReadable(p) → readBy(p) ≠ ∅  ∨  writeOnly(p) = true
INV-9b readBy 是**声明面**字段（与 writer 对称），装配期可校验 ⇒ "写了没人读"在装配期即被拒
```

### 8.2 依据（实测）

- 声明面只描述写侧（`level/carrier/key/form/retention/selection/writer`），**不描述读侧** ⇒ `round_sequence`（三写者、零生产读者）成为结构性必然（已退役，见 `Agent应用篇-实施步骤.md` §14.2）。
- 文档 §11 已把该问题理论化为"编译器本该提供、被降级掉的依赖清单"；O7 是该结论的**唯一系统性落地手段**。

### 8.3 判据

| 判据 | 断言 |
|---|---|
| 读侧声明齐 | 新用例：缺 `readBy` 且非 `writeOnly` 的位置 ⇒ `spec.placement-readside-missing`（Error） |
| 反例已消除 | 对存量声明做一次全量审计，输出"写了没人读"清单（预期暴露 `ur_histories` 灰度面等） |
| 命令 | `Modules.Node.Tests` + `AgentNodeSpecDeclarationTests`（声明级） |

> **问题**：框架的"节点"是**几个**语义？这决定 O3/O7 的门能做多严，也决定 C1 是否触 Frame。
