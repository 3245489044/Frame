# 引用图库物理删除与墓碑治理 —— Frame 通用框架重构方案

> 状态：方案定稿（待施工）
> 范围：**优先在 `Frame\CsharpPrj\Operation\DataStoreDriven` 构建通用能力**；`Projects\Plug\Agent` 仅做消费面适配。
> 关联：`ReferenceGraphCoordinator.cs`、`ReferenceGrounding.cs`、`ReferenceGraphQuery.cs`、`GraphRowWritePort.cs`、`ReferenceGraphReadPort.cs`
> 实测基线：`Projects\Information\State\graph.db`（只读打开）
> 日期：2026-10-17

## 0. 摘要（结论先行）

### 0.1 现象

数据库页删除 LiteDB 图数据后：

1. 立即刷新 → 数据确实消失；
2. 重启 / 开始对话（触发完整装配）→ 被删除的声明、边、端点全部恢复。

### 0.2 根因

不是 LiteDB 删除失败，而是**图库当前被当作“每次装配从 `.ushar` 重新生成的派生投影”**：

`AgentAssemblySegments.DStepRelationsAsync`（`AgentAssemblySegments.cs:295`）
→ `ReferenceGrounding.SeedDeclarationsFromAsync`
→ 无条件把每条声明写回 `Status="active"`、重新 Ensure 端点、重新 Add 边。

对应代码：

- `ReferenceGrounding.cs:646-657`：seed 无条件写 `Status="active"`；
- `ReferenceGrounding.cs:662-664`：重新 Ensure 端点 + Add 边；
- `ReferenceGraphCoordinator.cs:622-635`：`UpsertRelationDeclarationAsync` 是“先删再插”，会覆盖 `revoked`；
- `ReferenceGrounding.cs:709-729` / `:747-770`：`RebuildAllAsync` / `ReconcileAsync` 会从 active 声明重新生成边。

因此当前端到端**没有“删除 LiteDB 引用关系且跨装配持久”的语义**：

| 数据 | 角色 | 删除后的实际结果 |
|---|---|---|
| `ur_relations` | 声明 | UI 删除 = status flip；下次 seed 覆盖回 active |
| `ur_references` | 派生边 | 硬删边；下次 seed / reconcile / rebuild 从声明重建 |
| `ur_endpoints` | 端点缓存 | 删文档；下次 seed 为静态边重新 Ensure |

### 0.3 定案

采用 **B 方案：物理删除 + tombstone（墓碑）**，并把能力上移为 Frame 通用框架：

```
删除 = 先写 tombstone → 再物理删除
seed = 只补缺失，不覆盖 tombstone
reconcile / rebuild = 只从 active 且未 tombstone 的声明重建
SQLite 节点/实体永远不参与图库删除
```

### 0.4 附带结论：边不应被当作节点

- 当前通用存储读适配器把 `ur_references` 的每一行都投影成 `NodeProjectionItem` / `NodePanelRow`，导致“每条边一个节点”。
- 这是**框架层读模型缺失 edge 类型**，不是“应该把多条边合并成一个节点”。
- 正确方向：Frame 提供独立的节点 / 边 / 声明读面；视图可按端点聚合边，但存储层必须保持一条边一个可寻址关系。

## 2. 目标与非目标

### 2.1 目标

| # | 目标 |
|---|---|
| G1 | 图库删除具备**跨重启、跨完整装配、跨 reconcile/rebuild 的持久性** |
| G2 | tombstone 机制位于 **Frame 通用层**，不包含 Agent 业务语义 |
| G3 | 明确权威边界：`.ushar` 是 seed 源；LiteDB 声明是运行时权威；边是派生索引；tombstone 是删除意图 |
| G4 | 删除只影响 LiteDB 图库，不删除 SQLite 节点/任务/历史实体 |
| G5 | 提供稳定的内容身份，不依赖 index-based `RelationId` |
| G6 | 读面具备分页、总数、稳定排序、可见化错误 |
| G7 | 显式重新声明可以清除 tombstone 并恢复关系 |
| G8 | 现有图算法（邻接/路径/依赖/环检测）行为保持不变 |

### 2.2 非目标

- 不把多条边合并为一个节点；
- 不修改 SQLite 节点库的删除语义；
- 不在 Frame 中引入 Agent 的 UI 文案、域键、页面布局；
- 不在本批解决所有 UI 交互细节（分页 UI 可分批）；
- 不强制迁移历史 NodeKey（index-based `RelationId` 可保留，身份由指纹承担）。

### 3.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│ 消费方（Agent / 其他产品）                                   │
│  - UI 行端口 / 域适配 / SQLite 实体                          │
└───────────────────────┬─────────────────────────────────────┘
                        │ 只消费 Frame 通用契约
┌───────────────────────▼─────────────────────────────────────┐
│ Frame：Operation.DataStoreDriven（通用图持久化框架）         │
│                                                             │
│  GraphIdentityKeys        内容身份 / 指纹 / tombstone key    │
│  GraphTombstoneDoc        墓碑文档                           │
│  IGraphTombstoneStore     墓碑读写契约                       │
│  IGraphSeedSource         装配期 seed 源契约（已有扩展）     │
│  IGraphMaintenanceStore   删除 / seed / reconcile / rebuild  │
│  IGraphCatalogReader      节点 / 边 / 声明分页读面           │
│  ReferenceGraphCoordinator 唯一 LiteDB owner 实现            │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│ LiteDB graph.db                                             │
│  ur_endpoints | ur_references | ur_relations | tombstones   │
└─────────────────────────────────────────────────────────────┘

SQLite（ur_nodes / ur_tasks / ur_histories）—— 实体真源，不参与图库删除
.ushar 声明 —— 仅作为 seed 源，不覆盖运行时删除意图
```

### 3.2 权威与职责

| 数据 | 权威 | 写入者 | 删除语义 |
|---|---|---|---|
| SQLite 实体 | SQLite | 各域 Store | 不归图库管 |
| `.ushar` 声明 | 配置源 | 人工/配置系统 | 不直接删除图库 |
| `ur_relations` | 运行时声明权威 | seed / 显式声明 | **物理删除 + tombstone** |
| `ur_references` | 派生边索引 | 声明推导 / 运行时写边 | 声明边随声明删除；运行时边可硬删 |
| `ur_endpoints` | 端点投影 | seed / Ensure | 物理删除 + endpoint tombstone |
| `ur_graph_tombstones` | 删除意图 | 删除路径 | 只由显式重新声明/维护命令清除 |

### 3.3 核心不变量

| ID | 不变量 |
|---|---|
| I1 | 删除必须先写 tombstone，再物理删除；tombstone 写失败则删除失败（fail-closed） |
| I2 | seed **永不**清除 tombstone，**永不**把已删除（不存在或 revoked）的声明恢复为 active |
| I3 | reconcile / rebuild 只处理 `active` 且未 tombstone 的声明 |
| I4 | 声明边必须由声明推导；无声明时不得凭 seed 凭空建边 |
| I5 | 运行时边与声明边分离，运行时边删除不受 seed 影响 |
| I6 | 图库删除绝不触碰 SQLite 实体 |
| I7 | tombstone 身份必须基于内容指纹，不能基于 index-based `RelationId` |
| I8 | tombstone 集合不出现在图库 UI 集合列表与业务读面 |
| I9 | 关系行身份必须是全局唯一 `_id`，不得以 `RelationId` 作为可删除身份 |
| I10 | 读面必须返回总数/分页信息，禁止静默截断 |

## 4. 数据模型

### 4.1 集合

| 集合 | 文档形态 | 主键 | 索引 |
|---|---|---|---|
| `ur_endpoints` | `{ _id, Doc }` | `{type}:{id}` | `_id` |
| `ur_references` | `{ _id, Doc }` | `{sourceKey}::{targetKey}::{refType}` | `_id`；**新增** `SourceId/TargetId/RefType` 顶层字段后建索引 |
| `ur_relations` | `{ _id, Doc }` | `relations.{workflowId}.{relationId}` | `_id`；**新增** `RelationId/WorkflowId/Status` 顶层字段后建索引 |
| `ur_graph_tombstones` | `{ _id, Doc }` | 见 §4.3 | `_id` |

> 顶层字段策略：保留 `Doc` 作为 USharp 文本真源；为查询/级联/分页新增只读投影字段。旧文档缺字段时由 codec 解码兜底，迁移批次回填。若不做顶层字段，则所有查询必须改为 `_id` 前缀或内存解析，帧库必须明确二选一。

### 4.3 身份与指纹

新增 `Frame\CsharpPrj\Operation\DataStoreDriven\Graph\GraphIdentityKeys.cs`：

```csharp
public static class GraphIdentityKeys
{
    public static string DeclarationFingerprint(RelationDoc doc);
    public static string DeclarationTombstoneKey(RelationDoc doc);
    public static string EdgeTombstoneKey(string sourceKey, string targetKey, string refType);
    public static string EndpointTombstoneKey(string resourceType, string id);
```

指纹内容：

```

SourceType + Source + SourcePort
TargetType + Target + TargetPort
RefType
KeyMappingRef
```

统一使用**长度前缀 + U+001F 分隔 + SHA-256**，避免字段拼接歧义。

tombstone key 示例：

```
decl:9f2c...       // 声明墓碑
edge:4a71...       // 边墓碑
endpoint:node:wf.a // 端点墓碑（可读键）
```

### 4.4 边/端点身份限制

- 当前边 `_id` = `{sourceKey}::{targetKey}::{refType}`，**不包含端口**；
- 同端点/同 refType 但不同端口的声明会共享同一个边 `_id`；
- B 方案下，删除边按 `(source,target,refType)` 批量删除匹配声明并写 tombstone；
- P2 可扩展 `EdgeIdKeys` 加入端口/KeyMappingRef，并迁移旧边。

## 5. 删除设计（Frame 通用）

### 5.1 删除模式

新增通用枚举：

```csharp
public enum GraphDeleteMode
{
    /// <summary>物理删除 + tombstone（配置声明/端点/声明边）。</summary>
    PhysicalWithTombstone = 0,

    /// <summary>仅删除派生数据，不写 tombstone（维护/对账路径）。</summary>
    DerivedOnly = 1,
}
```

消费方（Agent UI）默认使用 `PhysicalWithTombstone`；`Reconcile` 等维护路径使用 `DerivedOnly`。

### 5.2 删除声明

```
GraphRowWritePort.Delete(ur_relations:<NodeKey>)
  → coordinator.DeleteDeclarationDurablyAsync(nodeKey, reason)
      ① 读 RelationDoc（不存在 → NotFound）
      ② 计算 DeclarationTombstoneKey(doc)
      ③ AddTombstone（幂等；写失败 → 整个删除失败）
      ④ 删派生边 RemoveReferenceAsync(doc.Source, doc.Target, doc.RefType)
      ⑤ 物理删除 _relationDocs.Delete(nodeKey)
      ⑥ 返回 GraphDeleteOutcome(Ok, TombstoneKey)
```

顺序要求：**先墓碑后删除**。如果第 ④/⑤ 步失败，墓碑已存在，seed 不会恢复；重试可继续清理。

### 5.3 删除边

```
GraphRowWritePort.Delete(ur_references:<EdgeId>)
  → coordinator.DeleteEdgeDurablyAsync(edgeId, reason)
      ① 反解 edgeId → (sourceKey, targetKey, refType)
      ② 扫描声明：匹配 (SourceType/Source/TargetType/Target/RefType) 的全部声明
           → 逐条 DeleteDeclarationDurablyAsync（墓碑 + 删声明 + 删边）
      ③ 若没有匹配声明：
           → Add EdgeTombstone（防御/审计）
           → RemoveReferenceAsync(source, target, refType)
      ④ 返回逐项结果
```

说明：
- 由于边 `_id` 不包含端口，删除边会**批量删除该 endpoints/refType 下的全部端口变体声明**；
- 运行时边（无声明）直接硬删，seed 不会恢复；
- 如果消费方需要“端口级精确删除”，必须等 P2 扩展 EdgeId 文法。

### 5.4 删除端点

```
GraphRowWritePort.Delete(ur_endpoints:<type:id>)
  → coordinator.DeleteEndpointDurablyAsync(id, reason)
      ① 收集所有 ReferencesResource(doc, id) 的声明
      ② 逐条 DeleteDeclarationDurablyAsync（墓碑 + 删声明 + 删派生边）
      ③ 清全部 incident 边：
           - 内存邻接 GetReferencesAsync
           - 防御性按 _id 前缀/顶层 SourceId/TargetId 扫描孤儿边
      ④ 物理删除 _endpointDocs.Delete(uniqueKey)
      ⑤ Add EndpointTombstone
      ⑥ 返回 GraphDeleteOutcome
```

端点删除只删 LiteDB 端点与关系，不触碰 SQLite 实体。

### 5.5 显式撤销 / 重新声明

| 操作 | 语义 |
|---|---|
| `UndeclareRelationsAsync` | 改为物理删除 + tombstone（不再是 status flip） |
| `DeclareRelationsAsync` | 显式声明：清除声明/边/端点 tombstone → active upsert → 建边 |
| `SeedDeclarationsFromAsync` | seed：**不清 tombstone**；只补缺失；已 tombstone 直接跳过 |
| `ClearTombstonesAsync` | 维护命令：清除墓碑（之后下一次 seed 会按配置恢复） |

### 5.6 运行时边与声明边

为目标“删除持久”且不误伤运行时关系，边需要来源标记：

- `EdgeDoc.Origin`：`Declared | Runtime | Unknown`（新增可选字段，旧文档默认 `Unknown`）；
- `Declared` 边：由声明推导，删除必须走声明墓碑；
- `Runtime` 边：任务/历史/会话等运行时写边，seed 不管理，硬删即持久；
- `Unknown`：按“有匹配声明则走声明删除，否则硬删”处理。

该字段同时服务于 UI 读面：区分“配置声明边”与“运行时边”，避免把两者混为同一类节点。

## 6. Seed / Reconcile / Rebuild 设计

### 6.1 Seed 算法

`ReferenceGrounding.SeedDeclarationsFromAsync` 改造为“tombstone-aware、create-only”：

```csharp
foreach (var s in source.GetStaticEdges(workflowId))
{
    var doc = BuildActiveRelationDoc(workflowId, relationId, s);
    if (await _graph.IsTombstonedAsync(GraphIdentityKeys.DeclarationTombstoneKey(doc), ct))
        continue; // 用户已永久删除

    var effective = await _graph.SeedRelationDeclarationAsync(nodeKey, doc, ct);
    if (effective is null || !effective.IsActive)
        continue; // 旧 revoked / 被墓碑抑制

    await _graph.ClearEndpointTombstoneAsync(effective.SourceType, effective.Source, ct);
    await _graph.ClearEndpointTombstoneAsync(effective.TargetType, effective.Target, ct);
    await _graph.EnsureResourceAsync(src, ...);
    await _graph.EnsureResourceAsync(tgt, ...);
    await _graph.AddReferenceAsync(src, tgt, s.RefType, ...);
}
```

`SeedRelationDeclarationAsync` 语义：

| 现有状态 | 行为 |
|---|---|
| 无记录 + 有墓碑 | 返回 `null`，不插入 |
| 无记录 + 无墓碑 | Insert `active`，返回 doc |
| 有记录 active | 更新非状态字段，保持 active，返回 doc |
| 有记录 revoked（旧数据） | 转写墓碑 + 物理删除，返回 `null` |
| 有记录但声明指纹不匹配 | 视为不同关系，按无记录处理（可选：记录诊断） |

node 关系部分不能直接复用显式 `DeclareRelationsAsync`，新增 seed 模式：

```csharp
public Task DeclareRelationsAsync(
    string workflowId,
    IReadOnlyCollection<RelationDeclarationEntry> declarations,
    CancellationToken ct = default); // 显式：清墓碑 + active

internal Task SeedNodeRelationsAsync(
    string workflowId,
    IReadOnlyCollection<RelationDeclarationEntry> declarations,
    CancellationToken ct = default); // seed：respect tombstones / preserve status
```

### 6.2 Reconcile

`ReferenceGrounding.ReconcileAsync` 保持“从声明重建边”，但增加：

```csharp
if (!d.IsActive) continue;
if (await _graph.IsTombstonedAsync(GraphIdentityKeys.DeclarationTombstoneKey(d), ct)) continue;
```

由于 B 方案会物理删除被删声明，正常情况下不会命中；该检查用于防御旧数据/异常恢复。

### 6.3 RebuildAll

```csharp
public async Task RebuildAllAsync(CancellationToken ct = default)
{
    await _graph.ClearAllAsync(ct);          // 只清 endpoints/references，不清 tombstones
    await RebuildDeclarationsAsync(ct);      // 只重建 active 且未 tombstone 的声明
}
```

明确：
- `ClearAllAsync` **不删除** `ur_graph_tombstones`；
- 新增 `ClearAllIncludingTombstonesAsync` 仅用于“完全重置图库”的显式维护命令；
- `RebuildAllAsync` 不得恢复被删除声明。

### 6.4 配置漂移策略

| 场景 | 行为 |
|---|---|
| 配置新增关系 | 新指纹无墓碑 → seed 插入 active + 建边 |
| 配置删除关系 | 图库不自动删除；由 UI/维护命令删除并写墓碑（或后续增加配置 diff 清理批次） |
| 配置顺序变化 | 指纹不变；旧 NodeKey 可能残留（index-based `RelationId`），但删除/墓碑仍按内容匹配 |
| 配置修改端点/端口 | 视为新关系（指纹变化）；旧关系保留，需显式清理 |
| 用户删除后配置仍存在 | tombstone 抑制，直到显式重新声明/清墓碑 |

### 6.5 显式重新同步（维护命令）

新增 Frame 维护端口（供 Agent/宿主调用）：

## 7. 读模型：节点 / 边 / 声明分离

### 7.1 问题定性

当前调用链：

```
ReferenceGraphReadPort.ReadRows(limit)
  → 每个集合展开为 StoreTableRow
  → StoreReadAdapter 每行投影成 NodeProjectionItem
  → NodePanelRow（只有 Key/Badge/Title/Summary）
```

结果：
- `ur_endpoints` 每行 = 一个节点（合理）；
- `ur_references` 每行 = 一个“节点行”（不合理，边是关系）；
- `ur_relations` 每行 = 又一个“节点行”（同一关系可能被计两次）。

这是**框架读模型缺少 edge 维度**，不是“多个边应该合并成一个节点”。

### 7.2 目标读面

Frame 提供三类独立读面，消费方按需组合：

```csharp
public sealed record GraphPage<T>(
    IReadOnlyList<T> Items,
    int Total,
    int Offset,
    int Limit)
{
    public bool HasMore => Offset + Items.Count < Total;
}

public sealed record GraphEndpointRow(
    string Key, string ResourceType, string Id, string? Symbol,
    int OutDegree, int InDegree, string? UpdatedAt);

public sealed record GraphEdgeRow(
    string Key, string SourceKey, string TargetKey, string RefType,
    double Strength, string Origin, string? UpdatedAt);

public sealed record GraphDeclarationRow(
    string Key, string RelationId, string WorkflowId,
    string Source, string Target, string RefType, string Status,
    bool Tombstoned);

public interface IGraphCatalogReader
{
    GraphPage<GraphEndpointRow> ReadEndpoints(int offset, int limit, CancellationToken ct = default);
    GraphPage<GraphEdgeRow> ReadEdges(int offset, int limit, CancellationToken ct = default);
    GraphPage<GraphDeclarationRow> ReadDeclarations(
        int offset, int limit, bool includeDeleted, CancellationToken ct = default);
}
```

### 7.3 稳定行身份

| 行类型 | 显示键 | 删除/详情真键 |
|---|---|---|
| 端点 | `{type}:{id}` | `_id`（同显示键） |
| 边 | `_id` | `_id` |
| 声明 | `_id`（`relations.{wf}.{rid}`） | `_id` |
| 墓碑（维护面） | `_id` | `_id` |

禁止：
- 用 `RelationId` 作为声明行主键；
- 用 `RelationId → NodeKey` 的 `TryAdd` 别名映射；
- 用 `NodeReadNormalizer` 按 `RelationId` 去重（可在读适配器内部按 `_id` 去重）。

### 7.4 视图建议

- 图库页分组：**端点 / 边 / 声明**（可加“已删除墓碑”维护组，默认隐藏）；
- 端点行可展开出边/入边列表，实现“多个边挂在同一个节点下”；
- 边行按 `source -[refType]-> target` 展示，不再作为节点参与节点计数；
- 声明行显示 `active/revoked`、是否 tombstoned；
- 删除动作按类型给出明确语义：
  - 端点：物理删除端点 + incident 声明/边；
  - 边：物理删除边 + 匹配声明；
  - 声明：物理删除声明 + 派生边；
  - 墓碑：默认只读，维护面可清墓碑。

### 7.5 “边合并为节点”结论

| 方案 | 结论 |
|---|---|
| 多条边合并为一个节点 | ❌ 丢失 refType/strength/方向/端口，破坏逐边删除与级联 |
| 按端点聚合展示（节点 + 邻接边列表） | ✅ 推荐的视图聚合，不合并存储 |
| 节点/边/声明三读面分离 | ✅ Frame 目标模型 |
| 继续把每条边投影成节点行 | ❌ 当前缺陷来源 |

## 13. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 配置仍声明已删除关系 | 用户删除后配置仍在，tombstone 永久抑制 | 显式 `Resync`/清 tombstone 命令 + UI 文案；或改配置 |
| index-based `RelationId` | 配置顺序变化导致 NodeKey 漂移、旧声明残留 | 指纹与 NodeKey 解耦；P2 改内容哈希 relationId |
| 边 `_id` 不含端口 | 边删除批量影响端口变体 | 文档化；P2 扩展 EdgeId |
| tombstone 增长 | 集合缓慢膨胀 | 维护命令列出/清理；不做自动 GC |
| 顶层字段迁移 | 旧文档缺字段 | codec 解码兜底；P1 回填批次 |
| 并发删除/seed | 删除与 seed 竞争 | 墓碑检查 + 插入在同一 `_gate` 临界区；失败可见化 |
| 5 秒门超时 | UI 偶发 Rejected | 删除操作重试/批量端点级操作；后续可调 |
| 跨进程打开 | 无跨进程事务/乐观锁 | 明确单写进程；或引入版本号（后续） |

|---|---|---|
| 删除语义 | B：物理删除 + tombstone | 用户要求“重启不恢复”，且数据库页删除应持久 |
| tombstone 归属 | Frame 通用层 | 图库持久化是通用能力，Agent 只消费 |
| 权威模型 | `.ushar` 仅 seed；LiteDB 声明运行时权威 | 与现有 `IDeclaredReferenceSource` 文档一致 |
| 边是否合并为节点 | 否 | 边是关系，合并丢失语义；视图按端点聚合即可 |
| 关系行身份 | 全局 `_id` | `RelationId` 非全局唯一，导致不可达/误删 |
| 分页 | Frame 分页读契约 | 200 硬截断导致“删不干净” |
| 运行时边 | `Origin=Runtime`，seed 不管理 | 避免误伤任务/历史关系 |
| 显式重新声明 | 清 tombstone + 恢复 | 提供可控的“撤销删除”入口 |
| 兼容策略 | 旧 API 保留，seed 换新原语 | 降低 Agent/测试改动面 |
