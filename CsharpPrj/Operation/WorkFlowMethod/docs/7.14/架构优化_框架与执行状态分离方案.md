## 2. 核心问题

### 问题 1：图框架与执行引擎深度耦合

`NodeProcess` 管线中的执行步骤直接操作 `UniversalNode`，而 `UniversalNode` 包含了图配置（GetConfig）、执行配置（ExeConfig）、添加配置（AddConfig）、连接配置（ConnectConfig）——这些本质上是**图框架的节点定义**，但执行引擎直接依赖它们。

**后果**：
- 图框架的任何变更都会波及执行引擎
- 无法独立测试图框架或执行引擎
- 难以支持不同的图框架实现

### 问题 2：执行状态与图框架状态混在一起

- `GraphUnit.dic`（全局字典）被执行引擎直接读写
- `WorkflowRuntimeContext` 同时承载图框架状态和执行状态
- `AICallFrame.CallNode` 既作为图框架的调用记录，又作为执行过程的追踪
- `FunctionExecutionFramework` 的 `DebugLogger` 与执行过程深度绑定

**后果**：
- 无法支持同一工作流的**多重并发执行**
- 状态管理混乱，难以追踪问题
- 全局状态导致测试困难

### 问题 3：动态更新逻辑散落在各层

- `WorkFlowUpdate` 在编排层
- `WorkflowChainUpdater` 在执行引擎层
- `GraphWorkflowUpdater` 在图框架层
- `LegacyUpdateAdapter` / `HybridUpdateManager` 作为桥接

**后果**：
- 更新逻辑重复且不一致
- 执行过程中的图更新可能影响正在执行的会话
- 难以控制更新的原子性和一致性

### 问题 4：重构不彻底

- `RefactoredNodeProcess` 使用了新的 `PipelineExecutor<TContext>` 和 `TypedExecutionContext`，但仍然直接依赖 `UniversalNode`
- `RefactoredWorkflowExecutor` 引入了 `ExecutionStateManager`，但执行逻辑仍然委托给旧的 `WorkflowProcessor`

**后果**：
- 新旧代码并存，维护成本高
- 重构收益未完全体现
- 开发者需要在两套体系间切换

### 问题 5：SkeletonFlow 已存在但未集成

SkeletonFlow 是项目中已有的管线组合框架，已在多处使用但未与 GraphFramework 和 Execution 统一集成：

| 位置 | 使用情况 | 说明 |
|------|----------|------|
| `BasicMethod/FrameMethod/SkeletonFlow.cs` | 核心框架定义 | ISkeleton, SkeletonBase, SkeletonContext, Flow, Branch, Loop, Parallel 等 |
| `WorkFlowMethod/WrokFlow_Script.cs` | 已有 Skeleton 使用 | AddNodeSkeleton, GeneratePromptSkeleton, BuildRecordsAndStorageSkeleton |
| `WorkFlowMethod/ExecutionEngine/ExecutionEngine.cs` | 已有 Skeleton 使用 | GetConfigSkeleton, ExecuteFuncSkeleton, AddNodeSkeleton, NextNodeSkeleton |
| `WdUI/Layout/Skeletons/` | 大量 Skeleton | ApplyLayoutSkeleton, CreateLayoutPanelSkeleton 等 |

**后果**：
- SkeletonFlow 的 Flow 管线能力未被 GraphFramework 和 Execution 利用
- 新旧代码结构混乱，存在多个并行的管线体系
- 巨型文件（ExecutionEngine.cs 1301行、WrokFlow_Script.cs 1691行）难以维护

## 3. 设计目标

### 3.1 核心目标

| 目标 | 描述 | 优先级 |
|------|------|--------|
| **中央集成管道** | 以 SkeletonFlow 为核心构建统一管道，所有逻辑以 Skeleton 形式动态注册 | P0 |
| **框架与执行分离** | 图框架只负责拓扑结构定义，执行引擎只负责执行逻辑 | P0 |
| **状态独立管理** | 执行状态完全封装在执行会话中，与图框架无关 | P0 |
| **支持多重执行** | 同一工作流图可同时启动多个执行会话，状态完全隔离 | P0 |
| **动态管道** | Skeleton 可随时 Insert/Replace/Remove，无需重启 | P1 |
| **执行凭证机制** | 图快照作为不可变的执行凭证，执行过程不受图变更影响 | P1 |
| **渐进式迁移** | 不破坏现有代码，逐步替换 | P1 |

### 3.2 非目标

- 不改变现有的函数注册机制（IWorkflowRegistry）
- 不改变现有的图更新指令体系（GraphUpdateDirective）
- 不改变 SkeletonFlow 核心框架本身

## 4. 总体架构：SkeletonFlow 中央集成管道

### 4.1 核心理念

**以 SkeletonFlow 为核心构建中央集成管道**，所有工作流逻辑——图定义、执行、更新、热重载——都在这个管道的基础上以 Skeleton 的形式动态注册、动态修改。管道本身是动态的，Skeleton 可随时插入、替换、移除，管道自动重建。

```
┌═════════════════════════════════════════════════════════════════════╗
║               SkeletonFlow Central Pipeline (中央集成管道)             ║
║                                                                     ║
║  管道本身是动态的：Skeleton 可随时 Insert/Replace/Remove              ║
║  管道状态由 WorkflowContext 统一管理                                  ║
║  所有子系统都是管道的"插件"                                           ║
╚═════════════════════════════════════════════════════════════════════╝
         │                    │                    │
         ▼                    ▼                    ▼
┌─────────────────┐  ┌────────────────┐  ┌────────────────┐
│  GraphFramework  │  │   Execution    │  │  动态更新       │
│  (图定义Skeleton) │  │ (执行Skeleton)  │  │ (更新Skeleton)  │
│                  │  │                │  │                │
│ 可动态替换图定义   │  │ 可动态替换执行   │  │ 可动态注入更新   │
│ 可动态添加节点    │  │ 可动态修改管线   │  │ 可动态切换快照   │
└─────────────────┘  └────────────────┘  └────────────────┘
```

### 4.2 管道架构

中央集成管道由三个核心组件构成：

```
┌═════════════════════════════════════════════════════════════════════╗
║               WorkflowCentralPipeline (中央集成管道)                  ║
║                                                                     ║
║  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────┐  ║
║  │ 图定义    │  │ 输入解析  │  │ 函数执行  │  │ 调用帧   │  │下一  │  ║
║  │ Skeleton │→│ Skeleton │→│ Skeleton │→│ Skeleton │→│节点  │  ║
║  └──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────┘  ║
║       │              │              │              │         │       ║
║       ▼              ▼              ▼              ▼         ▼       ║
║  ┌─────────────────────────────────────────────────────────────┐    ║
║  │                  WorkflowContext (统一上下文)                  │    ║
║  │  GraphSnapshot | ExecutionSession | DataContext | DebugLog  │    ║
║  └─────────────────────────────────────────────────────────────┘    ║
║                                                                     ║
║  ┌─────────────────────────────────────────────────────────────┐    ║
║  │              SkeletonRegistry (动态注册表)                     │    ║
║  │  运行时 Insert / Replace / Remove → 自动 RebuildPipeline()    │    ║
║  └─────────────────────────────────────────────────────────────┘    ║
╚═════════════════════════════════════════════════════════════════════╝
```

### 4.3 管道核心组件

#### 4.3.1 中央管道（WorkflowCentralPipeline）

中央管道是整个工作流系统的单一入口。它持有 Skeleton 注册表，按阶段组织所有已注册的 Skeleton，并在注册表发生变化时自动重建 Flow 管线。

**核心职责**：
- 管理 Skeleton 注册表（按阶段分类）
- 支持运行时动态注册、替换、移除 Skeleton
- 注册表变化时自动重建管道
- 提供统一的执行入口

**管道阶段定义**：

| 阶段 | 说明 | 典型 Skeleton |
|------|------|--------------|
| 图定义阶段 | 加载和准备工作流图定义 | 图定义加载、图快照创建 |
| 输入解析阶段 | 解析当前节点的输入配置 | 输入配置读取、数据获取 |
| 函数执行阶段 | 执行当前节点对应的函数 | 函数查找、函数调用、结果处理 |
| 调用帧记录阶段 | 记录执行过程和结果 | 调用帧创建、执行记录 |
| 下一节点阶段 | 确定下一个要执行的节点 | 后继节点查找、路由决策 |
| 后处理阶段 | 执行完成后的处理 | 指标收集、日志导出 |
| 更新检查阶段 | 检查图是否已更新 | 图更新检测、热重载触发 |

#### 4.3.2 管道上下文（WorkflowContext）

管道上下文是统一的状态容器，替代了原有的 `ExecutionContext`、`SkeletonContext`、`GraphUnit.dic` 等多个分散的状态载体。

**核心职责**：
- 承载图快照（执行凭证）
- 承载执行会话（状态容器）
- 承载数据上下文（替代全局字典）
- 承载调试日志
- 提供管道级共享数据存储

#### 4.3.3 动态注册表（SkeletonRegistry）

动态注册表是管道的"插件系统"，所有 Skeleton 都通过注册表管理。

**核心职责**：
- 按阶段组织 Skeleton
- 支持 Insert（插入新 Skeleton）
- 支持 Replace（替换已有 Skeleton）
- 支持 Remove（移除 Skeleton）
- 变更后自动触发管道重建

### 4.5 动态修改管道的典型场景

#### 场景1：运行时动态添加处理逻辑

在管道运行过程中，动态注册一个新的 Skeleton 到指定阶段。管道自动重建，下次执行时新逻辑生效。例如在输入解析阶段动态添加一个数据预处理步骤。

#### 场景2：运行时动态替换执行逻辑

在管道运行过程中，替换某个阶段的 Skeleton。例如将标准函数执行 Skeleton 替换为调试模式的执行 Skeleton，实现运行时切换执行模式。

#### 场景3：运行时动态注入更新检查

在管道运行过程中，动态注入图更新检查 Skeleton。每次节点执行后自动检查图是否已更新，如果检测到更新则自动创建新快照并触发热重载。

#### 场景4：基于配置动态构建管道

根据工作流配置文件动态构建管道。遍历配置中的阶段和 Skeleton 定义，通过 Skeleton 工厂创建对应的 Skeleton 实例并注册到管道。管道完全由配置驱动，无需硬编码。

### 5.2 模块0：CentralPipeline（中央集成管道）

#### 5.2.1 职责

中央集成管道是整个工作流系统的核心枢纽。它基于 SkeletonFlow 构建，所有工作流逻辑都以 Skeleton 的形式注册到管道中，支持运行时动态修改。

#### 5.2.2 核心类型

| 类型 | 职责 | 关键行为 |
|------|------|----------|
| **WorkflowCentralPipeline** | 中央管道，工作流系统的单一入口 | 管理 Skeleton 注册表；支持动态注册/替换/移除；注册表变化时自动重建 Flow 管线；提供统一执行入口 |
| **WorkflowContext** | 管道上下文，统一状态容器 | 承载 GraphSnapshot、ExecutionSession、DataContext、DebugLog；提供管道级共享数据存储 |
| **SkeletonRegistry** | 动态注册表，按阶段管理 Skeleton | 按阶段组织 Skeleton；支持 Insert/Replace/Remove；变更后自动触发管道重建 |
| **PipelineStages** | 管道阶段定义 | 定义固定顺序的阶段：图定义 → 输入解析 → 函数执行 → 调用帧 → 下一节点 → 后处理 → 更新检查 |
| **SkeletonFactory** | Skeleton 工厂，基于配置创建 Skeleton | 根据类型名和参数动态创建 Skeleton 实例；支持自定义 Skeleton 注册 |

#### 5.2.3 模块间契约

中央管道对外输出的核心契约是 `WorkflowContext`，所有 Skeleton 都消费和产出 `WorkflowContext`。管道不直接依赖任何子系统，所有子系统都通过 Skeleton 适配后注册到管道。

### 5.3 模块1：GraphFramework（图框架层）

#### 5.3.1 职责

图框架层只负责工作流的**拓扑结构定义**和**版本管理**，不包含任何执行状态。它是整个系统的"蓝图"提供者。

#### 5.3.2 核心模型

| 类型 | 职责 | 关键属性/行为 |
|------|------|---------------|
| **WorkflowGraph** | 工作流图定义，可变，用于构建和更新 | GraphId, Nodes 字典, Edges 列表；提供 CreateSnapshot() 和 ApplyUpdate() 方法 |
| **NodeDefinition** | 节点定义，纯配置，无状态 | NodeKey, Symbol, Label；持有原始 NodeConfig 的只读引用 |
| **EdgeDefinition** | 边定义，描述节点间连接关系 | EdgeId, SourceNodeKey, TargetNodeKey, IsDirected |
| **GraphSnapshot** | 图快照，不可变，作为执行凭证 | SnapshotId, CreatedAt；提供 GetEntryNode()、GetNextNodes()、GetPreviousNodes()、Validate() 方法 |
| **GraphDiff** | 图差异，记录两个快照间的变更集 | OldSnapshotId, NewSnapshotId；包含 Added/Removed/Modified 的节点和边列表 |

**关键设计说明**：
- `GraphSnapshot.GetNextNodes(nodeDef)` 返回多个后继节点，以支持分支/条件路由
- `GraphSnapshot` 是值语义的不可变对象，创建后其内容不会改变
- `WorkflowGraph.ApplyUpdate()` 返回新的 `WorkflowGraph` 实例，旧实例不受影响

#### 5.3.3 图操作服务

| 服务 | 职责 | 关键方法 |
|------|------|----------|
| **GraphBuilder** | 从各种来源构建 WorkflowGraph | BuildFromChain(ChainInfo), BuildFromNodes(IEnumerable<NodeDefinition>), BuildFromJson(string) |
| **GraphValidator** | 验证图的拓扑完整性 | Validate(WorkflowGraph), ValidateSnapshot(GraphSnapshot) |
| **GraphUpdateService** | 处理图的动态更新，每次更新产生新图 | ApplyUpdate(graph, directive), ApplyBatchUpdate(graph, directives), CalculateDiff(oldSnapshot, newSnapshot) |
| **GraphAdapter** | 兼容旧系统的适配层 | FromChainInfo(ChainInfo), ToChainInfo(WorkflowGraph), FromUniversalNode(UniversalNode) |

#### 5.3.4 在中央管道中的角色

GraphFramework 通过 `GraphDefinitionSkeleton` 适配到中央管道，注册到"图定义阶段"。该 Skeleton 负责从 WorkflowGraph 创建 GraphSnapshot 并注入到 WorkflowContext 中。

### 5.4 模块2：Execution.Session（执行会话 - 状态容器）

#### 5.4.1 职责

执行会话封装一次执行的所有状态，是"状态"的唯一载体。每个执行会话完全独立，互不干扰。

#### 5.4.2 核心类型

| 类型 | 职责 | 关键属性/行为 |
|------|------|---------------|
| **ExecutionSession** | 执行会话，状态容器，实现 IDisposable | SessionId, GraphSnapshot(凭证), CreatedAt；持有 State、Data、CallFrame、DebugLog 等子组件 |
| **ExecutionStateMachine** | 执行状态机，管理会话生命周期 | Status(枚举), StartTime, EndTime, Duration；提供 TryTransitionTo(newStatus) 方法 |
| **NodeExecutionState** | 单个节点的执行状态 | NodeKey, Status(枚举), StartedAt, CompletedAt, ErrorMessage |
| **DataContext** | 数据上下文，替代全局 GraphUnit.dic | 线程安全的键值存储；支持点号分隔的路径访问 |
| **DebugLog** | 调试日志，每个会话独立 | 提供 AddSection()、AddError()、AddWarning() 方法 |

#### 5.4.3 状态枚举

```
ExecutionStatus: NotStarted → Running ↔ Paused → Completed / Faulted / Cancelled

NodeStatus: Pending → Running → Completed / Failed / Skipped
```

**状态转换规则**：
- `NotStarted` → `Running`：执行开始时
- `Running` ↔ `Paused`：暂停/恢复
- `Running` → `Completed`：所有节点执行成功
- `Running` → `Faulted`：节点执行失败
- `Running` → `Cancelled`：外部取消
- 终态（Completed/Faulted/Cancelled）不可转换到其他状态

#### 5.4.4 在中央管道中的角色

Execution.Session 通过 `SessionInitSkeleton` 适配到中央管道，在管道开始时初始化会话。DataContext 作为 WorkflowContext 的一部分，替代全局 GraphUnit.dic。

### 5.5 模块3：Execution.Engine（执行引擎 - 无状态层）

#### 5.5.1 职责

执行引擎只负责执行逻辑，不持有任何状态。所有状态都在 `ExecutionSession` 中。引擎可复用，支持同时处理多个会话。

#### 5.5.2 核心类型

| 类型 | 职责 | 关键行为 |
|------|------|----------|
| **WorkflowExecutionEngine** | 执行引擎入口，无状态，可复用 | 依赖 IWorkflowRegistry；提供 CreateSession(snapshot)、ExecuteNodeAsync(session, nodeKey) 等方法 |
| **ExecutionManager** | 执行会话管理器 | 提供 Register/GetSession/CancelSession/RemoveSession 方法 |
| **NodeExecutor** | 节点执行器，执行单个节点的完整管线 | 依赖 IWorkflowRegistry；执行四步管线 |
| **ExecutionOrchestrator** | 执行编排器，编排完整工作流的执行 | 从入口节点开始，按拓扑顺序依次执行节点 |
| **HotReloadService** | 热重载服务，支持执行中的图变更 | 提供 ShouldReload() 和 ReloadSession() 方法 |
| **SessionFactory** | 会话工厂，创建和恢复执行会话 | 提供 CreateSession() 和 RestoreSession() 方法 |

#### 5.5.3 在中央管道中的角色

Execution.Engine 的各个能力被拆分为多个 Skeleton 注册到中央管道的不同阶段：

| 引擎能力 | 对应 Skeleton | 注册阶段 |
|---------|--------------|---------|
| 节点输入解析 | InputResolveSkeleton | 输入解析阶段 |
| 函数执行 | FunctionExecSkeleton | 函数执行阶段 |
| 调用帧记录 | CallFrameRecordSkeleton | 调用帧记录阶段 |
| 下一节点路由 | NextNodeResolveSkeleton | 下一节点阶段 |
| 热重载检查 | HotReloadSkeleton | 更新检查阶段 |

### 5.6 模块4：Skeletons（Skeleton 实现）

#### 5.6.1 职责

Skeleton 实现模块包含所有可注册到中央管道的 Skeleton 实现。每个 Skeleton 职责单一，可独立测试和维护。

#### 5.6.2 Skeleton 分类

| 分类 | 典型 Skeleton | 说明 |
|------|--------------|------|
| **图定义 Skeleton** | GraphDefinitionSkeleton | 从 WorkflowGraph 创建 GraphSnapshot 并注入上下文 |
| **输入解析 Skeleton** | InputResolveSkeleton | 从 NodeDefinition 读取输入配置，从 DataContext 获取输入值 |
| **函数执行 Skeleton** | FunctionExecSkeleton | 通过 IWorkflowRegistry 查找并执行对应的函数 |
| **调用帧 Skeleton** | CallFrameRecordSkeleton | 将执行结果记录到会话的 CallFrame 中 |
| **下一节点 Skeleton** | NextNodeResolveSkeleton | 从 GraphSnapshot 获取后继节点列表，根据执行结果决定路由 |
| **后处理 Skeleton** | MetricsCollectSkeleton, LogExportSkeleton | 执行完成后的指标收集、日志导出等 |
| **更新检查 Skeleton** | GraphUpdateCheckSkeleton, HotReloadSkeleton | 检查图是否已更新，触发热重载 |

#### 5.6.3 Skeleton 设计原则

- **单一职责**：每个 Skeleton 只做一件事
- **无状态**：Skeleton 本身不持有状态，所有状态在 WorkflowContext 中
- **可组合**：Skeleton 可通过 Flow 的 Then/Branch/Loop/Parallel 组合
- **可替换**：同一阶段的 Skeleton 可被替换为不同实现
- **可测试**：每个 Skeleton 可独立测试

## 7. 关键收益

### 7.1 架构层面

| 收益 | 描述 |
|------|------|
| **中央集成管道** | 所有工作流逻辑以 Skeleton 形式注册到统一管道，单一入口、统一管理 |
| **框架与执行彻底分离** | 图框架只负责拓扑结构定义，执行引擎只负责执行逻辑，通过 `GraphSnapshot` 契约交互 |
| **清晰的职责边界** | 每层只关注自己的职责：中央管道管编排、图框架管定义、执行引擎管执行、会话管状态 |
| **可替换的图框架** | 只要实现 `GraphSnapshot` 契约，可以替换不同的图框架实现 |
| **可测试性提升** | 各层可独立测试，每个 Skeleton 可独立测试 |

### 7.2 动态管道层面

| 收益 | 描述 |
|------|------|
| **完全动态的管道** | Skeleton 可随时 Insert/Replace/Remove，无需重启 |
| **统一上下文** | `WorkflowContext` 替代 `ExecutionContext` + `SkeletonContext` + `GraphUnit.dic` |
| **配置驱动** | 管道可由配置文件动态构建，无需硬编码 |
| **可观测性** | 管道可插拔 Metrics/Logging/Tracing Skeleton |
| **渐进式迁移** | 旧 Skeleton 可逐步迁移到新管道，新旧并存 |

### 7.3 执行层面

| 收益 | 描述 |
|------|------|
| **支持多重执行** | 同一个工作流图可以同时启动多个执行会话，状态完全隔离 |
| **执行凭证机制** | `GraphSnapshot` 作为不可变的执行凭证，确保执行过程不受图变更影响 |
| **状态独立管理** | `ExecutionSession` 封装所有执行状态，可序列化、可恢复、可追踪 |
| **并发安全** | 每个会话独立加锁，无全局竞争 |

### 7.4 动态更新层面

| 收益 | 描述 |
|------|------|
| **更新不影响执行** | 图更新产生新快照，正在执行的会话继续使用旧快照 |
| **版本化图定义** | 每次更新产生新版本的 WorkflowGraph，支持回滚和审计 |
| **热重载支持** | `HotReloadService` 可安全地将执行中的会话切换到新快照 |
| **变更追踪** | `GraphDiff` 精确记录每次变更，支持增量同步 |

### 7.5 维护层面

| 收益 | 描述 |
|------|------|
| **代码复杂度降低** | 每层职责单一，代码量减少，易于理解和维护 |
| **消除巨型文件** | `ExecutionEngine.cs`（1301行）和 `WrokFlow_Script.cs`（1691行）拆分为独立 Skeleton 文件 |
| **统一异常处理** | 各层使用统一的异常类型和处理策略 |
| **更好的扩展性** | 新功能可以在不修改现有代码的情况下添加，只需注册新的 Skeleton |
| **测试友好** | 每个 Skeleton 可独立测试，管道可 mock |
