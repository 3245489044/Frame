# 代码分析报告：重复逻辑、冗余逻辑与错误逻辑

> 分析日期: 2026-05-25
> 分析范围: RoslynMethod 项目全部核心模块

## 一、重复逻辑 (Duplicate Logic)

### 1.1 AnalysisContextExtensions 与 QuerySkeleton 功能重叠

**AnalysisContextExtensions.cs** 中的 `GetClasses()`, `GetMethods()`, `GetProperties()`, `GetFields()`, `GetInterfaces()`, `GetStructs()`, `GetEnums()`, `GetDelegates()` 方法与 **QuerySkeleton.cs** 中的 `FindTopLevelDeclarations<T>()`, `FindMembersInClass<T>()`, `FindAllNodes<T>()` 方法功能完全重叠。

- `AnalysisContextExtensions.GetClasses(className)` → 等价于 `QuerySkeleton.FindTopLevelDeclarations<ClassDeclarationSyntax>(root, className)`
- `AnalysisContextExtensions.GetMethods(className, methodName)` → 等价于 `QuerySkeleton.FindMembersInClass<MethodDeclarationSyntax>(root, className, methodName)`
- 其他所有 GetXxx 方法同理

**影响**: 两套 API 做同一件事，维护成本翻倍，且容易产生行为不一致。

### 1.2 TypeQueryExecutor / MemberQueryExecutor 与 QuerySkeleton 完全重复

**TypeQueryExecutor.cs** 和 **MemberQueryExecutor.cs** 的每个方法都只是简单委托给 `QuerySkeleton`，是纯粹的"转发层"：

```csharp
// TypeQueryExecutor.cs
public static IEnumerable<ClassDeclarationSyntax> FindClasses(SyntaxNode root, string className, bool includeNested)
    => QuerySkeleton.FindTopLevelDeclarations<ClassDeclarationSyntax>(root, className);
```

**影响**: 这些类没有任何额外逻辑，完全是冗余的中间层。

### 1.3 StaticTupleStore 与 StringTupleStore 的重复包装

**StaticStore.cs** 中：
- `StaticTupleStore<TKey, TValue>` 是核心实现
- `StringTupleStore` 只是 `StaticTupleStore<string, string>` 的简单包装
- `StaticTupleStore`（非泛型）又是 `StringTupleStore` 的简单包装

三层包装链：`StaticTupleStore` → `StringTupleStore` → `StaticTupleStore<string, string>`

### 1.4 重复的"自定义提取器不支持"异常方法

`StaticTupleStore<TKey, TValue>` 中有 **6个方法** 都抛出相同的 `NotSupportedException("自定义提取器重载当前不支持...")`：
- `ParseTuples(code, fieldName, keyExtractor, valueExtractor)` 
- `ParseTuples(code, className, fieldName, keyExtractor, valueExtractor)`
- `FindValueByKey(code, key, fieldName, keyExtractor, valueExtractor)`
- `FindValueByKey(code, key, className, fieldName, keyExtractor, valueExtractor)`
- `AddTuple(code, key, value, fieldName, keyGenerator, valueGenerator)`
- `AddTuple(code, key, value, className, fieldName, keyGenerator, valueGenerator)`

这些方法从未被使用，且抛出同样的异常，属于死代码。

### 1.5 重复的 null 检查模式

**AnalysisContextExtensions.cs** 中每个方法都重复相同的 null 检查：
```csharp
if (context == null) throw new ArgumentNullException(nameof(context));
```
而 **Guard.cs** 中已有 `Guard.AnalysisContext(context)` 方法，但只有 `SyntaxHierarchy.cs` 使用了它。

## 二、冗余逻辑 (Redundant Logic)

### 2.1 RoslynBasic.cs 空壳文件

**RoslynBasic.cs** 只包含空的 `#region` 注释块，没有任何实际代码。注释说"已迁移至 Models/ 目录"和"已迁移至 Utilities/ 目录"，但文件本身未被删除。

### 2.2 CompilationReferenceHelper 中的冗余缓存

- `_referenceMap` 使用 `Lazy<>` 初始化，但内部又调用了 `DiscoverLoadedAssemblies(map)` 来动态发现程序集
- `_namespaceMatchCache` 和 `_referenceCache` 两个缓存可以合并
- `_namespaceAliasMap` 只包含 3 个条目，且与 `_referenceMap` 的查找逻辑重叠

### 2.3 SyntaxHierarchy.cs 中的冗余循环检测

`FunctionHierarchyAnalyzer` 中有 **两套独立的循环依赖检测**：
1. `HasCircularDependency()` - 在 `CalculateFunctionHierarchy()` 中被调用
2. `FindCycles()` / `FindCyclesDFS()` - 在 `FindCircularDependencies()` 扩展方法中被调用

两者使用不同的算法（DFS vs Tarjan-like），但目的相同。

### 2.4 MethodMergeEngine 中的冗余合并策略

`MergeConservative()` 只是 `ExecuteBasicMerge(original, modified, true)` 的简单包装，而 `ExecuteBasicMerge` 只有一个调用者。

### 2.5 冗余的 FindMovedStatement 方法

`FindMovedStatement()` 方法（第737行）从未被任何代码调用，是死代码。`FindMovedStatementWithContext()` 才是实际使用的方法。

### 2.6 StorageFramework 中的 MemoryManager

`MemoryManager` 类与 **Mathematics/Core/MemoryManager.cs** 同名且功能重叠，但位于不同的命名空间和项目中。

## 三、错误逻辑 (Erroneous Logic)

### 3.1 QuerySkeleton.FindTopLevelDeclarations 逻辑错误

```csharp
public static IEnumerable<T> FindTopLevelDeclarations<T>(SyntaxNode root, string name = null)
{
    var nodes = root.DescendantNodes().OfType<T>().Take(MaxNodeSize);
    return FilterByName(nodes, name);
}
```

**问题**: 该方法名为"查找顶级声明"，但实际使用了 `DescendantNodes()`（递归遍历所有后代），而不是只查找直接子节点。这意味着嵌套在类内部的类也会被返回，与"顶级"的语义矛盾。

**对比**: `AnalysisContextExtensions.GetClasses()` 有 `includeNested` 参数来控制此行为，但 `QuerySkeleton` 忽略了这一点。

### 3.2 QuerySkeleton.Query 方法中 IncludeNested 逻辑错误

```csharp
if (criteria.IncludeNested && typeof(T) == typeof(ClassDeclarationSyntax))
    return nodes; // FindTopLevelDeclarations 已包含所有嵌套
```

**问题**: 注释说"FindTopLevelDeclarations 已包含所有嵌套"，但 `FindTopLevelDeclarations` 始终返回所有嵌套节点（因为使用了 `DescendantNodes()`），所以 `IncludeNested` 参数实际上没有任何效果——无论 true/false，结果都一样。

### 3.3 SyntaxHierarchy 中 CalculateDepth 的循环检测缺陷

```csharp
private static int CalculateDepth(string signature, ..., HashSet<string> visited)
{
    if (visited.Contains(signature))
        return 0; // 检测到循环，返回0
    visited.Add(signature);
    // ... 递归调用 ...
    visited.Remove(signature);  // 回溯时移除
}
```

**问题**: 使用 `visited.Remove(signature)` 回溯移除，这会导致在 DAG（有向无环图）中重复计算。例如 A→B, A→C, B→D, C→D 的情况下，D 会被计算两次。应该使用 memoization（已通过 `levelMap` 实现）来避免重复计算，但 `visited.Remove` 破坏了缓存效果。

### 3.4 CompilationReferenceHelper 中 GetHashCode 的潜在错误

```csharp
var hashCode = sourceCode.GetHashCode();
```

**问题**: `string.GetHashCode()` 在 .NET 中不保证跨进程/AppDomain 一致，且不同版本的 .NET 实现可能不同。更严重的是，不同字符串可能产生相同的哈希值（哈希冲突），导致返回错误的缓存结果。应该使用确定性哈希或直接使用字符串本身作为键。

### 3.5 CodeRemovalService.RemoveByName 的容器过滤逻辑

```csharp
if (!string.IsNullOrWhiteSpace(containerName))
    nodes = nodes.Where(n => containerSelector(n) == containerName);
nodes = nodes.Where(n => nameSelector(n) == name);
```

**问题**: 当 `containerName` 为空时，`containerSelector` 仍然会被调用（在 `Where` 子句中），但结果不会被使用。这虽然不会导致错误，但会造成不必要的性能开销。更严重的是，`containerSelector` 在 `RemoveMethod` 等调用中返回的是简单类名，而嵌套类中的方法可能无法被正确匹配。

### 3.6 StaticStore.cs 中 GetTypeSyntax 的潜在 StackOverflow

```csharp
private static string GetTypeFullName(Type type)
{
    if (type.IsNested)
    {
        var parentFullName = GetTypeFullName(type.DeclaringType);
        return parentFullName + "." + GetTypeNameWithoutGenericArity(type);
    }
    // ...
}
```

**问题**: 对于某些特殊类型（如泛型参数、数组类型的 DeclaringType），可能存在循环引用导致无限递归。虽然当前代码有 `IsNested` 检查，但某些边界情况可能绕过此检查。

### 3.7 MethodMergeEngine 中 BuildFinalCode 的方法替换逻辑

```csharp
private static ClassDeclarationSyntax ReplaceMethodsInClass(ClassDeclarationSyntax classDecl, List<MethodDeclarationSyntax> newMethods)
{
    var updatedMembers = classDecl.Members.Where(m => !(m is MethodDeclarationSyntax)).ToList();
    var existingMethodNames = new HashSet<string>(updatedMembers.OfType<MethodDeclarationSyntax>()
        .Select(m => m.Identifier.Text));
    foreach (var method in newMethods)
        if (!existingMethodNames.Contains(method.Identifier.Text))
            updatedMembers.Add(method);
    return classDecl.WithMembers(SyntaxFactory.List(updatedMembers));
}
```

**问题**: 
1. `updatedMembers` 中已经过滤掉了所有 `MethodDeclarationSyntax`，所以 `existingMethodNames` 始终为空集
2. 这意味着所有新方法都会被添加，但旧方法不会被替换——这是"追加"而非"替换"
3. 方法重载（同名不同参数）会被错误地跳过

### 3.8 RefactoringFramework 中 AddNullChecksRule 的潜在 NullReferenceException

```csharp
root = root.ReplaceNode(method.Body, newBody);
```

**问题**: 当 `method.Body` 为 null（例如表达式体方法）时，`AddParameterNullChecks` 返回 null，但调用处没有 null 检查，`ReplaceNode` 会抛出异常。

## 四、总结

| 类别 | 数量 | 严重程度 |
|------|------|---------|
| 重复逻辑 | 5 处 | 中-高 |
| 冗余逻辑 | 6 处 | 低-中 |
| 错误逻辑 | 8 处 | 中-高 |

**最需要优先修复的问题**:
1. **QuerySkeleton 的"顶级声明"语义错误**（3.1, 3.2）- 影响所有使用该方法的模块
2. **MethodMergeEngine 的 BuildFinalCode 替换逻辑错误**（3.7）- 导致合并结果不正确
3. **CompilationReferenceHelper 的哈希冲突风险**（3.4）- 可能导致缓存返回错误结果
4. **RefactoringFramework 的 NullReferenceException**（3.8）- 运行时崩溃风险

**最需要消除的重复**:
1. **AnalysisContextExtensions 与 QuerySkeleton** - 应统一为单一查询 API
2. **TypeQueryExecutor/MemberQueryExecutor** - 应直接删除，改为直接调用 QuerySkeleton
3. **StaticTupleStore 的三层包装** - 应简化为一层
