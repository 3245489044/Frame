2. BackEndDriven — 后端驱动执行框架

ECS 内核StaticPipelineFacade BuilderIoC/DI

2.1 核心执行闭环

BackEndDriven 的核心职责是将文本命令脚本解析为可执行的命令实体，经 StaticPipeline 管线编排后分发到各命令系统执行。整个执行闭环为：

FrameworkExecutor.Run(args) │ ├─ ParseArguments (命令行参数解析) ├─ SetupLogging (日志初始化) ├─ InitializeFramework (框架初始化) │ ▼ CommandInputPort.LoadCommandLines(lines) // 文本 → 命令实体 │ ▼ CommandSystemCoordinator.Update() // 中枢调度 │ ├─ CommandPipelineFactory.Create(entities) // 构建 StaticPipeline │ │ │ └─ 每条命令 = 1个 Step │ Execute: 设置 CurrentIndex → processEntity │ CanExecute: !StopRequested && !IsCancelled // halt/取消短路 │ IsFatal: false // 单命令失败不中断后续 │ ▼ ProcessEntity → system.Execute(entity) // 按 Action 路由 │ ├─ "click" → ClickSystem → IInteractionEventPort.Enqueue(target, eventName) ├─ "set" → SetSystem → IEcsStateAccessor.SetValue(target, value) ├─ "get" → GetSystem → IEcsStateAccessor.GetValue(target) ├─ "exec" → ExecSystem → EventPlatformExecutor.Invoke(functionName, params) ├─ "parse" → ParseCommandSystem → CommandParser.Parse ├─ "sleep" → SleepSystem → Thread.Sleep(ms) ├─ "assert" → AssertSystem → 5种子断言 (event-bound/openforms/text-empty/container) └─ ... (共16个命令系统)

2.2 关键组件分析

BackEndDrivenBuilder（Facade 门面）

Fluent Builder Facade，封装 CommandFrameworkOptions 的完整装配过程。核心方法：

  • WithWorkflowMethodExecution() — 从 Options 读取 ControlValueAccessor 和 ControlFinder，构造 WorkflowMethodExecutionWorkflow 并注入
  • WithUnifiedConfig(configPath, registry) — 实例化 UnifiedConfigLoader，将 JSON 配置中的函数注册到 ITrConfigRegistry
  • Apply() — 返回装配好的 CommandFrameworkOptions

CommandSystemCoordinator（中枢调度器）

持有 Dictionary<string, ICommandSystem> 按 action 名映射。注册了 16 个命令系统（Parse/Echo/Sleep/Close/Sideload/List/Load/Exec/Exit/Show/Look/Discover/Assert/Validate/ValidateMount/Click/Set/Get）。

Halt 语义：执行后检测 ExitRequestComponent 或 CloseRequestComponent，设置 ctx.StopRequested = true，管线后续 Step 的 CanExecute 自动短路。

M3 事件与命令收编设计

核心设计决策：Click/Set/Get 命令不再直接操作 WinForms 物理控件，而是经 ECS 事件/状态链路解耦：

  • ClickSystem → IInteractionEventPort.Enqueue(target, eventName) 发送事件到 ECS 队列
  • SetSystem → IEcsStateAccessor.SetValue(target, value) 写入 ECS 状态（ControlValueComponent），由渲染管线投影到物理控件
  • GetSystem → IEcsStateAccessor.GetValue(target) 读取，策略为"ECS 真源优先 + 物理兜底"

这消除了命令与 GUI 的直接耦合，使 CLI 模式（VirtualStore）和 GUI 模式（真实控件）共用同一执行路径。

EventPlatformExecutor（统一执行入口）

静态门面，聚拢所有 IEventPlatform 调用：

public static EventPlatformInvocation Invoke(string functionName, Dictionary<string, object?>? parameters)
{
    var platform = AppServiceProvider.Resolve<IEventPlatform>();
    return platform.InvokeFunction(name, params, "ExecCommand", 30000);
}

返回 EventPlatformInvocation（含 Result 和 PlatformAvailable 布尔值），消除多处的超时+来源重复代码。

UnifiedConfigLoader（配置加载器）

从 JSON 反序列化 UnifiedConfig，遍历 Functions 按 Type 分流：

  • delegate 类型 — 反射创建委托（method.CreateDelegate），经 ITrConfigRegistry.Register 注册
  • workflow 类型 — 创建 TrConfigRecord 注册

使用 Expression.GetActionType/GetFuncType 构造委托类型，参数名/类型校验并输出 Trace 警告。

CommandInputPort（双路径执行策略）

ExecuteSingle(commandText) 实现双路径执行：

  1. 优先通过 EventPlatformExecutor.InvokeAsync 走事件平台 workflow（含 middleware 管道）
  2. 失败则回退到本地命令系统（ParseAndCreateEntity + Coordinator.Update(entity)）
  3. 最终补挂 ExecutionResultComponent 统一产出形态

ValidateSystem（验证系统）

引入"挂载可见"判据（FindForm() != null），消除"对象存在但不可见"的假阳性。支持 scope 作用域参数，经 IContainerAccessPort.ResolveHost(scope) 解析容器宿主。

3. FrontEndDriven — 前端 ECS 驱动框架

ECS 架构渲染事务快照投影WinForms

3.1 核心设计理念

状态真源单向化：ECS 世界为唯一状态真源（single source of truth），物理控件仅为投影产物。数据流单向流动：配置驱动 → ECS 实体化 → 系统处理 → 快照投影 → 物理控件渲染。

3.2 Gate 层（入口与编排）

EcsGate（统一入口门面）

采用 Command 模式 + 拦截器链。核心方法 ExecuteAsync 在 try 块内依次执行拦截器的 OnBefore → DispatchAsync → OnAfter，异常时调 OnError。

唯一的操作类型是 LoadAndRenderOperation（原子 Load+Render），流程为：

校验宿主控件
  → 销毁旧 scope (经 ICompositionLifecycle.ScopeDestroyed 单一路径)
  → 开启 RenderTransaction 事务
  → _composition.Execute 加载配置
  → ExecuteRenderStage 渲染
  → Commit 落定

RenderTransaction（渲染事务）

实现 IDisposable，提供事务语义：using 作用域内执行渲染体，显式 Commit() 跳过回滚；未 Commit 即 Dispose 时触发 Rollback——仅销毁该 scope 残留实体，绝不 Dispose composition。

3.3 ControlRender 层（创建与布局）

ConfigDrivenControlFactory（配置→实体转换）

将 UIConfiguration 转换为 ECS 实体树。核心流程：

Convert → CreateRootEntity (root:{scope}, 类型 panel, 不建物理控件)
        → ConvertChildren (递归 ConvertControl)

每个控件实体挂载:
  ├─ ControlInfoComponent (Name/Text/Enabled/Visible)
  ├─ ParentEntityComponent (父实体引用)
  ├─ PendingCapabilityComponent (待创建标记)
  ├─ PendingLayoutComponent (待布局标记)
  ├─ PendingStyleComponent (待样式标记)
  ├─ EventBindingStateComponent (事件绑定状态机)
  └─ ScopeComponent (作用域)

SplitContainer 额外:
  ├─ SplitterRatioComponent (分割比例)
  └─ 2个 SplitterPanelComponent 子实体

LayoutSystem（核心布局引擎）

Update 收集 PendingLayoutComponent 实体，按树深度排序后逐层计算。布局策略：

  • 比例布局：按 ProportionalLayoutComponent 的比例乘父尺寸
  • dock=Fill：取父客户区全尺寸
  • SplitterPanel：按 SplitterRatioComponent 分割

最多 16 轮收敛循环，确保嵌套布局收敛。

标记-处理模式（Pending → Applied）

ECS 组件通过标记-处理模式驱动系统执行：System 查询 Pending 标记的实体 → 处理 → 移除 Pending + 添加 Applied，形成数据驱动的处理流水线。

PendingCapabilityComponent → ControlCreateSystem 处理 → 移除 Pending → 物理控件创建
PendingLayoutComponent    → LayoutSystem 处理       → 移除 Pending → ComputedLayoutComponent
PendingStyleComponent     → StyleSystem 处理        → 移除 Pending → MergedStyleComponent + StyleAppliedComponent

3.4 ControlInteraction 层（事件与状态）

EventBindingSystem（物理事件挂接）

Update 遍历 Pending 状态且含 EventBindingsComponent 的实体：

  1. 校验控件存在
  2. 校验函数注册（IFunctionHub.HasFunction）
  3. 经 EventSubscriptionHelper.TrySubscribe 物理 += 挂接 handler
  4. handler 调 _eventPort.Enqueue 转发 ECS 事件链

状态收敛：Pending → Bound / Failed。

EcsEventBus（事件分发）

实现 IInteractionEventPort，用 ConcurrentQueue 缓冲事件。Enqueue 后立即 DispatchPending（同步语义，重入保护）。

Dispatch 流程：按控件名查实体 → 匹配 EventBindingsComponent → BuildParameters 求值 → FunctionCallFacade.ExecuteAsync → 结果回写 OutputTarget

参数求值策略：literal 原义 / control 读 ECS 状态 / property 路径兜底物理反射。

EcsStateAccessor（状态读写器）

真源方向为写 ECS（ControlValueComponent）→ 契约投影物理。

  • GetValue：优先读 ECS，无则契约读物理，兜底 ControlInfo.Text
  • SetValue：写 ECS 后投影物理，写后规范值回写保证一致性

InputCapturePort（防循环机制）

仅采集"值变更信号"（不采集 Click）。防循环：物理值 == ECS 值则跳过，仅用户操作回灌 ECS。经 ValueContractRegistry 契约声明语义→事件名映射。

3.5 WinForms 层（投影与适配）

WinFormApplier（核心投影器）

采用两阶段投影方案：

ApplyStructure (结构投影)
  ├─ 创建/更新控件引用
  ├─ ApplyRelations 建父链 (不设属性)
  └─ SplitContainer 面板经 SplitterPanelRegistry 注册

ApplyProperties (属性投影)
  ├─ 父先子后排序
  ├─ 快照差异判定 GetSnapshotChanged (纯数据对比，零物理读取)
  ├─ 一次 SetBounds 到位
  └─ 回写 AppliedSnapshot

投影策略分派

  • DockProjector：对 dock 控件移除坐标键（坐标由原生 Dock 接管）
  • PixelProjector：默认策略，尺寸无效时移除坐标键
  • PlatformConstrainedProjector：平台约束投影

4. WorkFlowMethod — 工作流方法引擎

RGE 编排器CSG 三投影ReAct 循环热重载

4.1 统一入口 — WorkFlowMethodUsage

1300+ 行的静态 Facade 门面，将 13 个子系统的 API 聚合到一个类中。每个工厂方法都是简单的 "new" 加配置注入。依赖注入的核心是 UnifiedRegistryCenter.Instance，承载 Workflows、Functions、Pipeline、Executor 四大注册表。

4.2 执行引擎层

WorkflowEngine（核心引擎）

ExecuteCoreAsync(workflow, context, cancellationToken) │ ├─ _sessionManager.CreateSession(workflow, context.ExecutionId) │ session.MarkRunning() │ ├─ _ctsManager.Register(session.SessionId, cancellationToken) │ ├─ context.SetData("ExecutionPlan", workflow) [关键: 将plan放入上下文] ├─ using pipelineSession = _pipeline.CreateSession() [CentralPipeline] ├─ pipelineSession.ExecuteAsync(workflow, context, cts.Token) │ │ │ ├─ 成功: session.MarkCompleted() │ └─ 失败: session.MarkFailed() │ ├─ OperationCanceledException: session.MarkCancelled() └─ finally: _ctsManager.TryRemove()

支持完整的生命周期控制：CancelAsync、PauseAsync、ResumeAsync、GetStatus——通过 CancellationTokenSourceManager 实现取消/暂停/恢复。

HotReloadService（热重载）

Snapshot/State Transfer 模式——在不中断业务的情况下切换工作流定义版本：

ReloadSession(oldSession, newSnapshot)
  │
  ├─ dataSnapshot = oldSession.Data.CreateSnapshot()     [保存数据快照]
  ├─ oldStatus = oldSession.Status
  │
  ├─ newSession = _sessionFactory.CreateSession(newSnapshot) [基于新快照创建会话]
  ├─ newSession.Data.RestoreFromSnapshot(dataSnapshot)        [恢复数据]
  │
  ├─ 迁移节点状态:
  │    Completed → newNodeState.Complete()
  │    Failed    → newNodeState.Fail()
  │    Skipped   → newNodeState.Skip()
  │    Running   → newNodeState.Reset()  [重置为待执行]
  │    Pending   → 保持
  │
  ├─ oldSession.MarkCancelled()
  └─ _executionManager.RemoveSession(oldSessionId)

PipelineSession（状态机驱动的顺序执行）

ExecuteAsync(workflow, context, cancellationToken)
  │
  ├─ StateMachine: Pending → Running
  │

  │    ├─ cancellationToken.ThrowIfCancellationRequested()

  │    ├─ if !result.IsSuccess:
  │    │    StateMachine: Running → Failed

4.4 FunctionExecutionFramework（FEF 核心）

函数执行框架的入口。维护 Lazy 初始化单例 DefaultWorkflowRegistry 和 PipelineExecutor。三种执行路径：

  • ExecuteAsync(functionName, parameters, context) → 创建 FunctionExecutor 调用
  • ExecuteAsync(delegate, parameters, context) → 包装为单步 Pipeline 执行
  • ExecuteAsync(IFunctionUnit, input, context) → 包装为单步 Pipeline 执行

FuncCallRun（递归函数调用）

递归深度限制 32 层防止循环引用；子管线结果自动注入为父调用的最后一个参数。

PipelineRunAsync(funcPipeline, registry, context, depth=0)
  │
  ├─ [Guard] depth > 32 → 抛出循环引用异常
  │
  └─ foreach call in funcPipeline.Calls:
       ├─ if call.PipelineGroup != null:
       │    parameter = PipelineRunAsync(call.PipelineGroup, ..., depth+1)
       │    [递归: 子管线先执行，结果作为参数传给当前调用]
       │
       ├─ callContext = CreateCallContext(call, context, recursiveResult)
       └─ if registry.HasFunction(call.FuncName):
            parameter = registry.Call(call.FuncName, callContext)

4.5 LoopFramework（ReAct 循环核心）

这是整个框架中最具创新性的部分——实现了 Reasoning + Acting 的 AI Agent 循环。

LoopEngine 核心循环

ExecuteAsync(initialContext, cancellationToken) │ ├─ Status = Running ├─ _controller.OnLoopStart() │ └─ while _controller.ShouldContinue(): [循环控制] │ ├─ decision = ExecuteWithMiddleware( [推理阶段: "我应该做什么?"] │ _stateMachine.DecideAsync(context, ct)) │ │ │ ├─ NotifyObservers: OnStateChanged │ └─ NotifyObservers: OnDecisionMade │ ├─ if decision.IsCompleted: │ Status = Completed, break [任务完成则退出] │ ├─ actionResult = ExecuteWithMiddleware( [动作执行阶段] │ _actionExecutor.ExecuteAsync( │ decision.ActionName, params, ct)) │ │ │ └─ NotifyObservers: OnActionExecuted │ ├─ _contextManager.UpdateAsync(actionResult) [更新上下文] ├─ result.RecordIteration(decision, actionResult) │ └─ if !actionResult.Success: Status = Completed, Result.Failed, break

中间件机制（洋葱模型）

ExecuteWithMiddleware(coreAction):
  逆序遍历 _middlewares，构建洋葱模型调用链:
  middleware1(call) → middleware2(call) → ... → coreAction()

HybridStateMachine（规则+LLM 混合决策）

DecideAsync(context, ct)
  │
  ├─ ruleResult = _ruleMachine.DecideAsync()    [规则引擎优先]
  │
  ├─ if !ruleResult.IsCompleted:                [规则引擎仍在执行中]
  │    return ruleResult                        [直接使用规则引擎结果]
  │
  ├─ if !_fallbackToLLM:
  │    return ruleResult
  │
  ├─ llmResult = _llmMachine.DecideAsync()      [LLM 兜底决策]
  ├─ llmResult.Reasoning += "规则不匹配，LLM 兜底决策: ..."
  ├─ if !llmResult.IsCompleted:
  │    _ruleMachine.SetCurrentState(llmResult.NextState)
  └─ return llmResult

LLMStateMachine（LLM 驱动决策）

构建包含"当前状态"、"上下文数据"、"允许的动作"的提示词，调用 LLM 服务，解析响应：

  • "COMPLETE" → LoopState.Completed, IsCompleted=true
  • 精确匹配 allowedActions → LoopState.Running, ActionName=action
  • 模糊匹配 (Contains) → LoopState.Running, ActionName=action
  • 都不匹配 → LoopState.Completed（视为完成）

4.6 CSG 三投影变换

CSG = C(配置投影) + S(状态投影) + G(图投影)——三位一体的工作流一致性验证框架。

投影适配器来源目标接口
C 投影PipelineContextConfigAdapterPipelineContextIConfiguration
S 投影PipelineContextStateMachineAdapterPipelineContextIStateMachine
G 投影GraphSnapshotGraphAdapterGraphSnapshotIGraph

三投影一致性校验规则：

  • C 投影的 Action 节点 ID 集合 ≠ S 投影的节点 ID 集合 → Warning (缺失)
  • S 投影的 currentState 不在 G 投影的节点 ID 中 → Warning (状态孤立)
  • G 投影的每条边必须在 S 投影中存在对应 Transition → Warning (边缺失)
  • C 投影和 S 投影的 ContextId 不一致 → Error

还支持 csg://node/xxx、csg://edge/xxx、csg://context/xxx、csg://snapshot/xxx 的 URI 解析。

5.2 StateCenter（全量状态唯一权威门面）

sealed class StateCenter : IStateCenter，聚合四类职责：

职责实现
存储分区 持有根 IStorageCell，通过 GetOrCreateScope(scope) 用 ConcurrentDictionary.GetOrAdd 原子创建子 StorageCell（parent 链回退），消除并发覆盖
事务 BeginTransaction(scope?) 将事务定向到对应 scope 的分区 cell（无 scope 落根 cell），返回 StateTransaction
订阅 内含 StateSubscriptionHub，Write 后递增版本号并 Publish
生命周期 Provider 三个可空字段 IScopeLifecycle/ICompositionLifecycle/IContainerLifecycle，未注册时访问属性抛 InvalidOperationException（fail-fast 暴露装配顺序错误）

5.3 StateStore（统一后端存储）

基于 IStorageCell 的统一后端存储。关键设计：

  • 双命名空间隔离：对象态 KV（Get<T>/Set<T>）键加 "_obj:" 前缀，与字符串态 KV 同落 Session 层但互不覆盖
  • 事件转发：订阅 cell.DataChanged，转发为 StateChanged 事件——底层唯一物理事件源
  • Reset vs Clear：Reset() 仅清对象态（_obj: 前缀键），保留字符串 KV；Clear() 则 ClearLayer(Session) 全清
  • GetOrAdd 修复：用 Contains 判定而非 null 判定，修复了"已存 null 值被覆盖"的 bug

5.4 StateTransaction（工作单元模式）

StateTransaction (IStateTransaction)
  │
  ├─ Set/Remove → 写入内存缓冲 _buffer/_removals
  │
  ├─ Commit():
  │    ├─ 按序落 cell Session 层
  │    ├─ 逐 key 经订阅中枢发布 (版本单调递增 = GetLastVersion + 1)
  │    └─ 标记 Committed
  │
  └─ Dispose():
       └─ 若未 Commit → Rollback (清空缓冲，不产生任何事件)

5.5 StateSubscriptionHub（发布-订阅）

  • 按 namespace 维护订阅列表（List<SubscriptionEntry>，加锁保护增删）
  • 按 (namespace, scope) 维护版本表
  • 版本去重：Publish 时若 version <= lastSeen 直接丢弃
  • 异常隔离：handler 异常 try-catch 隔离，单 handler 失败不影响其余
  • 订阅返回 Subscription : IDisposable，Dispose 时移除条目

5.6 ScopeLifecycleStateMachine（作用域生命周期状态机）

状态转移路径: Empty → Declared → Loading → Loaded │ └→ Failed (终态) Failed → Loading (重试) Loaded → Destroying → Destroyed → 移除

关键修复（E1）：LoadAsync 的幂等短路仅当 State==Loaded && ConfigVersion>0 && 同 ConfigPath && !forceReload 才直接返回成功；Loading/Failed 状态一律走完整事务——失败不得被短路吞掉。

5.7 初始化管线（StatePipelineBuilder）

三种管线模板：

管线Block 顺序
Default Registry → FunctionStorage → FileDriven → Executor → AppService → StateCenterBlock（末尾追加）
Minimal 仅 Registry
Custom 传入 Action<StatePipeline> 自定义

5.8 FunctionStorage 框架

FunctionStorageRegistry（函数注册表静态门面）

  • Register(IFunctionUnit) — 将 unit 包装为 Func<object?,Task<ExecutionResult>> 注册到 registry 并缓存
  • ExecuteBatchAsync — 并行执行多函数，30s 超时 + 取消处理
  • 修复了原实现"把函数名当参数传入"的 bug

NonEventCommandCenter（非事件命令中心）

懒初始化注册 echo/sleep/close/sideload/list/exit/load/show/look/discover/assert/validate/exec/exec-system 等命令处理器。其中 sideload 支持加载 JSON 配置并自动注册函数；exec-system 支持执行系统命令（cmd.exe）。

MathFunctionRegistrar（数学函数注册器）

启动期自检：ValidateManifest 对照 math-register-manifest.json 期望清单校验，缺失即抛 InvalidOperationException 并附带 Mathematics.dll 路径/时间戳诊断信息——将"执行期未找到"提前到启动期。

8. 关键发现与观察

8.1 架构亮点

① ECS 架构贯穿前后端

BackEndDriven 用 ECS 作为命令执行内核（实体承载命令状态，系统处理逻辑），FrontEndDriven 用 ECS 作为UI 渲染内核（实体承载控件状态，系统处理创建/布局/样式/事件）。两者通过 IEcsStateAccessor 和 IInteractionEventPort 统一交互，消除了命令与 GUI 的直接耦合。

② M3 事件与命令收编

Click/Set/Get 命令不再直接操作 WinForms 控件，而是经 ECS 事件/状态链路。这使得 CLI 模式（VirtualStore）和 GUI 模式（真实控件）共用同一执行路径——这是整个项目最关键的设计决策之一。

③ CSG 三投影一致性验证

将工作流的三种视图（配置/状态/图）统一为可交叉验证的投影体系，能在运行时发现配置遗漏、状态孤立、边缺失等问题。这在工业级工作流引擎中很少见，是本项目的独创设计。

④ ReAct 循环 + 规则/LLM 混合决策

LoopFramework 实现了完整的 AI Agent ReAct 循环（推理→行动→更新上下文→循环），支持规则引擎优先 + LLM 兜底的混合决策模式，且通过洋葱模型中间件支持横切关注点。这使框架具备了 AI Agent 编排能力。

⑤ 热重载与状态迁移

HotReloadService 通过 Snapshot/State Transfer 模式，在不中断业务的情况下切换工作流定义版本，并精确迁移节点状态（Completed 保持、Running 重置、Pending 保持）。

8.2 工程实践亮点

  • 启动期自检：MathFunctionRegistrar 在启动期对照 manifest 校验函数注册完整性，将"执行期未找到"提前到启动期
  • 递归深度保护：FuncCallRun 限制 32 层递归，防止循环引用导致栈溢出
  • 循环保护：NodeLoop 的 maxIterations=10000，防止无限循环
  • 并发安全：StateCenter 用 ConcurrentDictionary.GetOrAdd 原子创建子分区，消除并发覆盖
  • 版本去重：StateSubscriptionHub 按 version 去重，防止重复事件处理
  • 防循环写入：InputCapturePort 在物理值 == ECS 值时跳过，防止回写循环
  • Fail-fast 设计：StateCenter 的生命周期 Provider 未注册时抛异常，暴露装配顺序错误
  • 布局收敛：LayoutSystem 最多 16 轮收敛循环，确保嵌套布局收敛

8.3 值得关注的改进点

  • WorkFlowMethodUsage 体量过大：1300+ 行的静态门面类承载 13 个子系统的工厂方法，虽然作为统一入口有其价值，但可考虑按子系统拆分为多个 partial 类或接口
  • CentralPipeline 的 Init/Finalize 阶段为空实现：预留了扩展点但尚未使用，可能增加理解成本
  • ParameterExecutionWorkflow 已废弃：README 明确标注废弃，但相关注释和文档仍存在，需清理
  • 16 轮布局收敛：固定上限可能对极深嵌套场景不够，建议增加收敛失败的诊断输出

报告总结

Operation 项目是一个高度模块化、设计模式密集型的 .NET 10 企业级框架。其最突出的技术贡献是：

  1. ECS 架构统一前后端——命令执行和 UI 渲染共用同一数据驱动模型
  2. M3 事件与命令收编——消除 CLI/GUI 双路径，统一经 ECS 事件链
  3. CSG 三投影验证——工作流一致性的运行时保证
  4. ReAct + 混合决策——AI Agent 编排能力内建于工作流引擎
  5. 热重载 + 状态迁移——不中断业务的版本切换

整个项目展现了成熟的工程实践：递归保护、并发安全、版本去重、防循环、fail-fast 设计、启动期自检等。代码结构清晰，设计模式运用得当，是一个具有很高技术含量的 .NET 框架项目。
