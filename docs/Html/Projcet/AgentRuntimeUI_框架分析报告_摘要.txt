【核心结论（两大论点）】

1) 本框架的 LLM 循环是以「数据库 + 任务快照状态」为基础构建的。
   - 循环不是上下文窗口的对话循环，而是"数据库 / 任务快照状态机"。
   - 每个任务本身就是运行中的快照（AgentTaskItem 同时实现
     ITaskPoolItem + ILoopState + IAgentLoopState），整份快照以单条
     PayloadJson 持久化在 SQLite 的 ur_tasks 表中 —— 「任务=快照，快照=任务」，
     是唯一权威的状态根。
   - 每轮流程：写 ur_tasks（EnqueueAsync，写入即激活，唤醒消费循环）
     → TaskPool 条目式状态机 → TaskRouter 路由（Hybrid→需LLM /
       Config·Deterministic→零LLM）
     → SnapshotDrivenLoopEngine（每轮 读快照 → execute 五步骨架 →
       next[LLM+计算变更整体状态] → 回写 PayloadJson）。
   - 关键代码：AgentRunner.PersistRuntimeAsync 在每个轮次边界把整个
     PayloadJson 写回 ur_tasks（AgentTaskItem 实现 ILoopState）。
   - 因此循环天然可恢复、可审计、崩溃安全；状态在数据库而非模型上下文窗口。

2) Cline / Claude 编排调用作为「子智能体」被本循环调度。
   - 框架是编排者（主智能体），Cline/Claude 是循环内每轮派发的子智能体执行后端。
   - 调用链：execute 阶段 → cline_execute 函数 → IAgentExecutor 端口
     → ClineAgentExecutor（name 参数可命名 cline / claude / sk）。
   - ClineAgentExecutor 把分层提示词组装为 Cline 单次编码代理任务，
     经 ClineClient（daemon 池 → Node 桥）执行；同一 IAgentExecutor 端口
     支持 claude/sk 等 provider 语义命名。
   - LLM 调用门（CheckLlmGateAsync）在真实 LLM 调用前合作式挂起（Running⇄Paused）。
   - 与 Claude Code / CLine 的对比因此被重构：它们首先是被本框架 DB 驱动循环
     内嵌的子智能体执行后端，其次才是行业基准参照。

【一、框架定位】
────────────────────────────────────────────────────────────────
WorkFlowPrj 的 Agent 子系统是一个「配置为中心、完全自研的桌面级 Agent 运行时」：
前端渲染（JSON UI）、命令执行（ECS）、函数注册（注册表）、调度执行（AxiomLoop/任务池）、
存储（三库收敛）、LLM 路由（热可配置）全部自研，统一经声明式 AgentRuntimeUI.json
控制台暴露。两层栈：
  · Agent 框架层（Projects/Agent）：Agent.Core（运行引擎）+ Agent.Launcher
    （装配与暴露，组合根 + 5 个库 62 个 AgentUi_* 函数），拥有业务能力。
  · 架构框架层（FileDriven + Share + Operation）：JSON UI 渲染管线、ECS、
    事件绑定编排、函数注册表、InvocationKernel 调用内核、任务池框架、图框架、
    状态管理，拥有通用执行底座。

KPI 概览：17 个函数库；67 个已注册函数（5 Ui_* + 62 AgentUi_*）；
9 大 Agent 功能域；14 个 RunJson 顶层 action 分支；2 种调度模式 + 双执行器；
6 层调用链。

【二、Agent 框架层（Projects/Agent）】
────────────────────────────────────────────────────────────────
2.1 项目组成
  · Agent.Core：引擎核心（无 UI 依赖）—— Loops(AxiomLoop)、TaskPool(任务池+双执行器)、
    Boundaries(边界框架)、DataStream(事件流)、Orchestration(编排器)、Prompts(提示词)、
    Workflow/DynamicWorkflow(动态合并)。
  · Agent.Launcher：装配与外部暴露（WinForms 宿主）—— 组合根(12 个 Hosting/Assembler)、
    入口(AgentHost/AgentLauncher/AxiomAgentLauncher)、5 个函数库。
  · Agent.Axioms + Generator：公理系统（L0/L1/L2 分层，源码生成器把声明编译为代码）。
  · Agent.Guardrails：护栏/安全（规则拦截，与 Core.Boundaries 协同）。
  · Agent.Contract / Agent.Calculate：契约与计算。

2.2 核心域（引擎层）
  · Loops 运行引擎：AgentRunner（PreRound→RunRound→PostRound 生命周期）；
    双调度 Hybrid(LLM 导演) / Config(ConfigStateDirector 热读 ur_config)；
    状态根=任务快照（每轮边界回写 PayloadJson 到 ur_tasks）。
  · TaskPool 任务池：AgentTaskPoolAdapter(门面，兼 IConversationStore)；
    双执行器 LlmTaskExecutor(LLM 路径) / RuleTaskExecutor(零 LLM，WirePauseGate 协作挂起)；
    TaskRouter 路由决策(:107/:119-120) 需 LLM→Llm / 零LLM→Rule。
  · Orchestration 编排器：RegisterModule / RegisterAgentExecutor / RunAsync；
    P3「配置即数据行」每轮热读 ur_config，改行即生效。
  · Boundaries 边界框架：DefaultBoundaryFramework / LogicalBoundaryEvaluator，
    前后轮钩子（PreRound/PostRound）。
  · DataStream 事件流：EventSink / ReactiveTrigger 反应式数据桥。
  · Prompts 提示词：IPromptComposer / PromptRequestComposer。

2.3 Agent.Launcher（装配、入口、暴露）
  · 组合根 12 组件按生命周期装配运行时：AgentFramework(门面)、LlmHosting(LLM 网关：
    :46 按 provider 注册客户端，:70 组装统一路由代理 LlmRoutingClient，:89 LlmMode.LocalOnly
    运行时开关)、TaskPoolHosting、DataStoreHosting、ConversationHosting、DatabaseBootstrapper 等。
  · 67 个函数分 5 库：Runtime(20)/Data(23)/TaskPool(10)/Db(3)/Conversation(5)。
  · 入口：AgentHost.RunAsync(静态) → AxiomLoopResult。

【三、架构框架层（FileDriven + Share + Operation）】
────────────────────────────────────────────────────────────────
3.1 六层调用链
  L0 JSON UI 配置 → L1 进程入口(FrameworkInitializer, FailFast, 显式加载 17 库)
  → L2 渲染管线(ScopeLifecycleAdapter: EcsGate 原子渲染+三重校验+initCommands)
  → L3 统一函数门面(EventPlatform.InvokeFunctionAsync → FunctionCallFacade)
  → L4 调用内核(InvocationKernel: 预算/取消/失败分类/阶段快照 Dispatch→Start→End)
  → L5 注册委托 → 实现库(Ui_* → FrontEndDriven / AgentUi_* → Agent.Launcher)
  → L6 结果回写(WriteInitOutput / 输出绑定 → 物理控件, UI 线程调度)。

3.2 关键组件
  · ECS 架构：命令=实体、状态=组件、系统处理；快照-差异投影。
  · 事件绑定编排：WinFormsEventBus + EventBindingOrchestrator 映射物理事件到函数门面。
  · 函数注册表：function-libraries.json 单一清单，autoDiscover=false 显式加载 + FailFast。
  · 调用内核：InvocationKernel 唯一持有 预算/超时/取消/失败分类/可观测性，阶段快照。
  · 任务池框架：通用 TaskPool<TItem,TResult>，写 ur_tasks + 唤醒消费循环 + TaskStateChanged。
  · 图框架：LiteDB 图库（端点+纯边），引用语义。
  · 状态管理：StateCenter 门面 + StorageCell + 事务 + 订阅。

【四、功能分析】
────────────────────────────────────────────────────────────────
4.1 九大功能域（67 函数）：
  1) 任务池系统（enqueue/status/delete/pause/resume/cancel 等，写透守卫自动建引用）
  2) 对话系统（任务即对话，AgentTaskPoolAdapter : IConversationStore）
  3) 运行引擎双调度（Hybrid LLM 导演 / Config 规则导演零 LLM）
  4) LLM 路由与热重配（LlmHosting 统一网关 + LlmMode.LocalOnly 一键本地化 + 运行时热切换）
  5) 本地集成测试（LocalOnly + CallLog 回放 + AgentUi_GetFunctions 内省，确定性后端）
  6) 节点数据读写（output/input/resource/config/event/checkpoint… 幂等 upsert）
  7) 引用图系统（写透守卫 + 可重建投影，graph.rebuild/diff）
  8) 统一只读查询（outputs/inputs/events/sessions/config/checkpoints/resources/snapshot/taskList）
  9) 模板与任务作用域（文件夹=分类零硬编码；TaskScope 自动展开多步 JSON）

4.2 关键设计亮点：
  · 任务池「需 LLM vs 零 LLM」路由 + mode=Config 规则导演：后台任务可完全跑规则
    不接 LLM，成本可控；改一行配置即生效。
  · 对话系统：一次会话消息作为任务入队推进对话；任务=对话、对话=任务，无重复状态。
  · 引用图：门面只编排不写边，ReferenceGraphCoordinator 为唯一写边者；可空守卫自动跳过；
    写透守卫在任意入队路径自动镜像任务图端点（不建边避免高频状态抖动）。
4.3 工作流（Workflow）逻辑 —— 声明式骨架，循环体不是 LLM 即兴发挥：
  · 骨架模型 RoundSpec：一轮 = 有序步骤列表（声明式数据，非散落硬编码）。
    无状态容器，仅保留 步骤 + 端口契约(InputPorts/OutputPorts) + 全局键映射
    (GlobalKeyMapping)；运行时状态全部外置 StateCenter。成功准则可声明：
    DecisionWord（须产出决策词）或 RunToEnd（无异常跑完即成功）。
  · 内置默认骨架 DefaultRoundSpec（agent-round）：
    guard_input → provide_prompt(分层装配 L0/L1/L2) → cline_execute →
    rule_match(零 LLM 决策路由)；stop 终态附 guard_output（安全输出过滤）。
    默认会话模板 DefaultConversationSpec（collect-analyze-act）：
    cline_execute(收集) → answer(分析) → cline_execute(执行)。
  · 骨架加载 RoundSpecLoader：从 Config/workflows/agent-loop.json 沿
    start→on_success 提取主路径线性链；未找到/解析失败回退内置默认；旧 Schema
    (<5.0.0) 零异常迁移。换模板文件即换循环体，引擎零改动。
  · 一轮执行 WorkflowRunner：按声明式步骤顺序调用已注册工作流函数执行"一轮"，
    经 IWorkflowRunner 端口与公理引擎解耦；构建 StaticAsyncPipeline 供各轮复用；
    控制流一次性静态化到引用图；终态信封"补漏"写（消除 R1 双写）；终答来源由
    工作流结构决定（逆序扫最后一个产出可读值的步骤）。
  · 步骤执行 RoundStepInvoker：「一切逻辑以 workflow 节点为主」。每个步骤构建为
    AgentNode（存储+执行单元），经 KeyMapping 从数据空间 + 其他节点输出端口解析入参、
    调用注册函数、结果作为节点输出端口持久化（ur_nodes NodeType=output）；
    KeyMapping 分类写 SQL；节点关系经 ReferenceGrounding 自动落地（不手写建边）。
  · 跨轮状态映射 RoundStateMapper：Seed（HFSM 租约切片 → 数据空间，含 LastResult/
    SessionId/Cwd/DataDir/执行器实例）⇄ Harvest（数据空间 → AxiomContext.Data，
    即任务快照/ur_tasks）；会话工作流种子键（system/l1/l2/prompt/question）显式透传。
  · 动态工作流 DynamicWorkflowMerger：把任意运行期片段（FragmentNode 节点类型
    process/condition/loop/parallel + FuncName + ParameterKeys/ResultKeys +
    InputMapping/OutputMapping + NextNodeConfig）解析/合并/执行，产出
    DynamicWorkflowResult；旧 key_mapping 自动迁移为 GlobalKeyMapping 的 Exact 规则。
  · 与 LLM 循环的关系：骨架固定（五步管道），LLM 仅在 provide_prompt 和 cline_execute
    两个步骤被调用；决策路由（rule_match：Done/Error/Retry → Terminate/SwitchAgent/
    Retry/Continue）完全确定性零 LLM；工作流节点即存储单元，产出回写 ur_nodes。
  · 平台侧工作流目录：FileDriven/DrivenConfig/WorkFlow/*.json（AgentRuntimeWorkflow、
    CodeReviewWorkflow、BatchRefactorWorkflow、DeepSeekChatWorkflow、McpToolWorkflow、
    NLToCodeWorkflow、MathWorkflows/* 等），配置驱动平台的声明式工作流库。
  · 底层图引擎 WorkFlowMethod（Operation 层）：WorkflowContext 统一状态容器
    （GraphSnapshot 不可变执行凭证 + CurrentNodeKey + ExecutionSession + SharedData）；
    IGraph → GraphSnapshot → WorkflowContext → ExecutionSession → DataContext 管线；
    PipelineBuilder 注册 GraphDefinitionSkeleton(图→快照) / NodeProcessSkeleton(节点
    处理 GetConfig→Execute→Record→Resolve) 等骨架。

【六、存储：三库收敛模型】
────────────────────────────────────────────────────────────────
  · SQLite ur_nodes：基础节点库（节点=存储单元，NodeType 判别 output/input/resource/config…）。
  · SQLite ur_tasks：任务状态集合（任务=状态根，enqueue/status/delete，PayloadJson）。
  · LiteDB graph：关系投影（ur_endpoints + ur_references 纯引用边），可整体重建(rebuild)，
    diff 报告漂移；权威在 SQL。
  · 内存热邻接 CoreGraph：会话内图视图，供 UI/编排器读取。
  架构亮点：图库是"可重建投影"，权威在 SQL；AttachReferenceGrounding 单一图属主断言
  防止双协调器读写分裂存储。

【七、客观评估】
────────────────────────────────────────────────────────────────
优势：
  1) 彻底配置驱动、约定优于配置（UI/注册/LLM/测试脚本全部 JSON 化，零硬编码发现）。
  2) 引擎层与暴露层干净分离（Agent.Core 无 UI 依赖；67 函数分 5 库）。
  3) 失败可诊断、永不静默（FailFast + 失败分类 + 超时阶段快照 + 显式诊断文本）。
  4) 成本敏感设计（双执行器 + 双调度；需LLM/零LLM 路由；本地确定性测试体系）。

劣势：
  1) 复杂性是最大成本（一次点击 9+ 跳；六层机制叠加导致上手极贵）。
  2) 并行路径与历史兼容并存（双路命令执行、initCommands→onAfterLoad 双支持，
     行为存在非确定性；冗余代码仍存在）。
  3) 字符串耦合、无编译期保护（函数名/控件名/action/op 大量字符串，重命名/拼写
     仅运行时暴露）。
  4) 依赖面与可观测性（17 库跨 5+ 程序集；日志散落为松散的字符串 ID，无统一结构化采集）。

【八、行业对比：Claude Code 与 CLine（既是子智能体也是基准）】
────────────────────────────────────────────────────────────────
Cline/Claude 双重角色：
  ① 子智能体执行后端 —— 被本框架的数据库/任务快照驱动循环内嵌，经 cline_execute →
     IAgentExecutor 每轮派发编码子任务；
  ② 行业基准 —— 与本框架（配置驱动平台学派）逐维度对比，定位异同与借鉴方向。

对比矩阵要点：
  · 循环形态：本框架 = 数据库/任务快照状态机（每轮读 ur_tasks 快照→execute→next→写回
    PayloadJson）；Claude Code = 终端极简学派（上下文窗口循环）；CLine = IDE 审批学派。
  · 子智能体/任务分解：本框架把 Cline/Claude 作为子智能体内嵌（cline_execute →
    IAgentExecutor）；Claude Code 用 Task 工具派生子智能体(depth=1)；CLine 用 new_task
    层级分解 + 子智能体(v3.58 独立上下文)。
  · 状态存储：本框架 SQLite 权威(ur_nodes/ur_tasks) + LiteDB 图投影(可重建) ——
    任务快照即循环状态根；Claude Code 追加式 JSONL 会话文件(--continue/--resume)；
    CLine SQLite + git 隐藏分支检查点。
  · 失败恢复/可观测：本框架分类失败 + 阶段快照 + 未知 action 诊断；Claude Code
    Hook 审计 + 会话回放 + fork_session；CLine 检查点恢复(文件回滚、对话保留) + 实时成本追踪。
  · 扩展机制：本框架函数注册表(JSON 声明) + 模板树零硬编码；Claude Code MCP+插件+技能+Hook
    四通道(MCP 懒加载省 85% token)；CLine MCP 多传输 + 插件。

三方共识与借鉴方向：
  · 简单循环 + 强大外围是共识（复杂度在权限/上下文/扩展/恢复）。
  · 标准协议扩展(MCP)成为行业方向。
  · 状态持久化与会话可恢复三方殊途同归；本框架的 SQLite 任务状态根是三者的最完整设计。

【九、结论与评分】
────────────────────────────────────────────────────────────────
· 能力全景：任务池(双执行器)、对话(任务即对话)、AxiomLoop(双调度)、LLM 热重配、
  本地集成测试、节点数据、引用图、统一查询、模板系统 —— 9 大功能域 67 函数，
  全部声明式 JSON 暴露、可组合可复用。
· 成本：多层抽象 + 多路收敛执行路径带来的复杂度，更适合作为长期演进的平台核心，
  而非快速上手的小团队方案；"星形收敛"保证行为统一，但任何中层的缺陷
  （如信号丢失）会表现为"无报错无日志的挂起"。
· 行业定位：循环是数据库/任务快照状态机，状态根是持久化的 ur_tasks 快照
  (PayloadJson)；Cline/Claude 是它编排的子智能体执行后端(cline_execute→IAgentExecutor)。
  作为行业原型走"配置驱动平台学派"，与 Claude Code 的"极简模型学派"
  (while 循环 + 模型全权决策) 和 CLine 的"审批增强学派"(逐步 diff 审批 + 检查点恢复)
  构成三原型。差异化能力：零 LLM 双执行器 + 可重建引用图；相对短板：上下文压缩管线、
  MCP 开放生态、diff 审批交互。
· 加权总分：7.2 / 10 —— 架构值得长期投资。建议优先级：
  ① 上下文压缩管线（借鉴 Claude Code 五阶段压缩）
  ② MCP 生态桥接（复用社区 150+ 工具）
  ③ 任务检查点恢复（借鉴 CLine "文件回滚、对话保留"）
  ④ 调用链追踪可视化
  ⑤ 函数名/action 的编译期校验。
