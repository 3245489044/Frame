## 第一部分：核心抽象——从 UI 布局到空间排布

### 0.0 前置思考：为什么这个架构"什么都能编排"？

在深入技术细节之前，先回答一个根本性问题。

#### 根本原因：这个架构捕获了"解决问题的最通用模式"

WdUI 的架构之所以能适配如此广泛的领域，不是因为它的代码写得有多好，而是因为它恰好捕获了**人类解决排布问题的通用思维模式**：

```
┌─────────────────────────────────────────────────────────┐
│  人类解决"排布问题"的通用思维模式：                       │
│                                                         │
│  1. 我有一个有限的空间/资源（容器）                       │
│  2. 我有一堆东西要放进去（元素）                          │
│  3. 每个东西有它自己的规则（配置）                        │
│  4. 我按某种顺序依次处理（管线）                          │
│  5. 不同类型的东西用不同方法处理（策略）                   │
│  6. 放完后检查有没有冲突（重叠检测）                      │
│  7. 如果有冲突就调整（约束/修复）                         │
│  8. 如果东西太多就递归处理（递归）                        │
└─────────────────────────────────────────────────────────┘
```

这个思维模式与"UI"无关，与"编程"无关——它是人类面对"有限资源分配问题"时的自然思考方式。

#### 三个层次的抽象，层层递进

```
层次1: 具象层 — "我在排布 UI 控件"
        ↓ 剥离 UI 细节
层次2: 抽象层 — "我在 2D 空间内排布矩形元素"
        ↓ 剥离空间维度
层次3: 元抽象层 — "我在有限资源内分配元素"
```

- **层次1** 只能做 UI 布局
- **层次2** 可以做地图、PDF、建筑排布
- **层次3** 可以做动画、频谱分配、内存管理、项目排期...

WdUI 的架构恰好站在了**层次2和层次3之间**——它的接口是层次2（2D 空间），但它的机制是层次3（资源分配）。这就是它"什么都能编排"的根本原因。

#### 具体来说，五个数学体系为什么如此通用

| 数学体系 | 它解决的本质问题 | 为什么通用 |
|---------|----------------|-----------|
| **ProportionalMath** | "按比例分配" | 任何资源分配问题都需要按比例分配——时间、空间、频率、预算 |
| **StackMath** | "按顺序排列" | 任何排布问题都需要排列顺序——串行、并行、网格 |
| **ClampMath** | "设定边界约束" | 任何现实问题都有边界——不能为负、不能超限 |
| **OverlapMath** | "检测冲突" | 任何分配问题都需要检测冲突——空间重叠、时间冲突、资源争用 |
| **MergeMath** | "合并配置" | 任何复杂系统都需要配置合并——默认值 + 覆盖值 |

这五个数学体系不是 UI 布局特有的，它们是**资源分配问题的五个基本操作**。就像加减乘除是数学的基本操作一样，这五个操作是"排布问题"的基本操作。

#### 三个编排机制为什么如此通用

| 机制 | 它解决的本质问题 | 为什么通用 |
|-----|----------------|-----------|
| **Pipeline** | "分阶段处理" | 任何复杂任务都需要分解为多个阶段——这是"分治"思想的体现 |
| **Strategy** | "按类型分发" | 任何多类型系统都需要多态处理——这是"多态"思想的体现 |
| **Recursion** | "递归分解" | 任何层级结构都需要递归处理——这是"递归"思想的体现 |

分治、多态、递归——这是计算机科学中最核心的三个思想，不是 UI 布局特有的。

#### 一个思想实验

```
问题: 如何用 WdUI 的架构编排一场音乐会？

容器:      音乐厅（有限空间）+ 时间轴（有限时间）
元素:      各个乐手、乐器、曲目
配置:      每个乐手的位置、每个曲目的时长、音量
策略:      弦乐组策略、管乐组策略、打击乐策略
管线阶段:  阶段1: 舞台布局 → 阶段2: 乐手定位 → 阶段3: 声学检测 → 阶段4: 曲目排期
重叠检测:  两个乐手是否位置重叠？两个曲目是否时间重叠？
约束:      乐手不能超出舞台、曲目不能超时
递归:      每个乐器组内部递归安排具体乐手位置
```

这个思想实验说明：**只要问题可以抽象为"在有限资源内分配元素"，WdUI 的架构就能适配。**

#### 总结

这个架构"什么都能编排"不是因为巧合，而是因为：

1. **五个数学体系** = 资源分配问题的五个基本操作
2. **三个编排机制** = 计算机科学的三个核心思想（分治、多态、递归）
3. **泛型化设计** = 将具体类型延迟到使用时确定

它不是一个"UI 布局框架"，它是一个**用计算机科学核心思想实现的通用资源分配引擎**，恰好最初被用于 UI 布局而已。

### 1.1 本质抽象

WdUI 的布局排布逻辑，剥离掉 WinForms 的 UI 特定细节后，其本质是一个 **"2D 矩形元素空间排布引擎"**：

```
输入: 容器(尺寸) + 元素列表(配置) + 策略(排布规则)
处理: Pipeline 管线(多阶段编排) + Strategy 策略(类型分发)
输出: 每个元素的最终位置和尺寸
约束: 比例定位 / 堆叠排列 / 尺寸夹持 / 重叠检测
```

这个抽象与"UI 布局"无关，与"空间排布"有关。任何需要在有限 2D 空间内排布矩形元素的问题，都可以映射到这个引擎上。

### 1.2 五大数学体系

| 编号 | 体系 | 核心公式 | 领域无关性 |
|------|------|---------|-----------|
| M1 | **比例定位 (ProportionalMath)** | `x = containerSize × ratio` | ★★★★★ 纯数学 |
| M2 | **堆叠排列 (StackMath)** | 垂直/水平/Grid 三种排列 | ★★★★☆ 排列逻辑通用 |
| M3 | **尺寸约束 (ClampMath)** | `Clamp(value, min, max)` | ★★★★★ 纯数学 |
| M4 | **重叠检测 (OverlapMath)** | AABB 碰撞检测 + 分级报告 | ★★★★★ 纯数学 |
| M5 | **配置合并 (MergeMath)** | 深度合并算法 | ★★★★★ 纯数据操作 |

### 1.3 三大编排机制

| 编号 | 机制 | 说明 | 领域无关性 |
|------|------|------|-----------|
| E1 | **Pipeline 管线** | 多阶段顺序编排，支持跳过/分支 | ★★★★☆ 通用编排模式 |
| E2 | **Strategy 策略** | 按类型注册/分发排布策略 | ★★★★★ 通用策略模式 |
| E3 | **Recursion 递归** | 可配置深度/范围的递归遍历 | ★★★★★ 通用树遍历 |

### 1.4 当前架构的泛型化程度

WdUI.Core 已经完成了关键的泛型化工作，核心泛型接口包括：

- `ILayoutContext<TElement>` —— TElement 可以是任何元素类型
- `ILayoutStrategy<TElement>` —— 策略接口
- `IPipelineStage<TElement, TConfig>` —— 管线阶段
- `IControlFinder<TElement>` —— 元素查找（可重命名为 IElementFinder）
- `LayoutStrategyRegistry<TElement>` —— 策略注册表
- `Pipeline<TElement, TConfig>` —— 管线执行器
- `RecursionPolicy` —— 递归策略（完全通用）

**核心结论：** 替换泛型参数 `TElement`，即可将整个引擎适配到不同领域。


## 第三部分：领域一——地图生成

### 3.1 领域映射

| WdUI 概念 | 地图生成映射 | 说明 |
|-----------|------------|------|
| Control (控件) | MapElement (地图元素) | 建筑、道路、树木、资源点等 |
| ControlConfig (控件配置) | MapElementConfig (元素配置) | 类型、位置、尺寸、属性 |
| LayoutPosition (比例位置) | GeoPosition (地理坐标) | 经纬度或地图比例坐标 |
| Container (容器) | MapRegion (地图区域) | 城市、区块、地块 |
| ProportionalMath | 元素在地图上的比例定位 | **直接复用** |
| StackMath.Grid | 建筑群网格排列 | **直接复用** |
| OverlapMath | 建筑碰撞检测 | **直接复用** |
| Pipeline | 地图生成管线 | 重新定义阶段 |
| Strategy | 不同类型元素的布局策略 | 重新实现 |

### 3.2 数据模型规划

需要定义的地图生成领域模型：

- **MapElementType 枚举**：Terrain(地形)、Road(道路)、Building(建筑)、GreenSpace(绿化带)、Water(水域)、ResourcePoint(资源点)、Decoration(装饰物)
- **MapElement 类**：Name、ElementType、X/Y/Width/Height、Rotation、ZOrder、Properties
- **MapElementConfig 类**：继承 ElementConfig，增加 MapType、Rotation、ZOrder、Color、Icon、IsCollidable、MinSpacing
- **MapRegionConfig 类**：Name、Width、Height、Elements、Rules
- **MapGenerationRules 类**：BuildingCoverage、GreenSpaceRatio、RoadWidth、GridSize、EnableOverlapDetection、OverlapMode

### 3.3 需要实现的策略

| 策略 | 用途 | 执行顺序 |
|------|------|---------|
| RoadLayoutStrategy | 生成网格状道路网络 | 先执行（StageOrder: 10） |
| BuildingLayoutStrategy | 按比例定位排布建筑 | 中间执行（StageOrder: 20） |
| GreenSpaceStrategy | 在建筑空隙中放置绿化带 | 后执行（StageOrder: 30） |

### 3.4 地图生成管线阶段

```
阶段1: GenerateTerrainStage        — 生成基础地形（高度图、噪声等）
阶段2: GenerateRoadNetworkStage    — 生成道路网络（网格状）
阶段3: DivideIntoBlocksStage       — 根据道路网格划分地块
阶段4: LayoutBuildingsStage        — 按策略排布建筑
阶段5: LayoutGreenSpacesStage      — 排布绿化带
阶段6: DetectAndResolveOverlapsStage — 重叠检测与自动修复
阶段7: AddDecorationsStage         — 添加装饰元素
```

### 3.5 可行性评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 数学复用度 | ★★★★★ | ProportionalMath、StackMath、OverlapMath 全部直接可用 |
| 架构适配度 | ★★★★★ | Pipeline + Strategy 模式天然适合地图生成流程 |
| 实现工作量 | 小 | 只需实现 3 个策略 + 7 个管线阶段 |
| 核心价值 | 高 | 一套配置驱动的地图生成方案，支持 JSON 定义城市布局 |

## 第四部分：领域二——PDF 排版

### 4.1 领域映射

| WdUI 概念 | PDF 排版映射 | 说明 |
|-----------|------------|------|
| Control (控件) | PageElement (页面元素) | 文本块、图片、表格、页眉页脚 |
| ControlConfig | PageElementConfig | 字体、颜色、边距、对齐 |
| LayoutPosition | PagePosition | 页面比例坐标 (0-1) |
| Container | PageSection (页面区域) | 页眉区、正文区、页脚区 |
| ProportionalMath | 元素在页面上的比例定位 | **直接复用** |
| StackMath.Vertical | 文本流式排版 | **直接复用** |
| StackMath.Grid | 表格布局 | **直接复用** |
| ClampMath | 元素尺寸约束 | **直接复用** |
| OverlapMath | 元素碰撞检测 | **直接复用** |
| Pipeline | PDF 生成管线 | 重新定义阶段 |

### 4.2 数据模型规划

需要定义的 PDF 排版领域模型：

- **PageElementType 枚举**：TextBlock(文本块)、Image(图片)、Table(表格)、Line(分割线)、Header(页眉)、Footer(页脚)、PageNumber(页码)、Shape(形状)
- **PageElement 类**：Name、ElementType、X/Y/Width/Height、Content、ImageData、Style
- **PageElementStyle 类**：FontName、FontSize、Bold、Italic、Color、BackgroundColor、Alignment、Padding
- **PageConfig 类**：Width/Height（默认 A4: 595.28x841.89）、Margin、Elements
- **PageElementConfig 类**：继承 ElementConfig，增加 PageType、Content、Style、IsFlowContent

### 4.3 需要实现的策略

| 策略 | 用途 | 说明 |
|------|------|------|
| TextBlockStrategy | 文本块排版 | 支持流式（自动换行）和固定位置两种模式 |
| TableLayoutStrategy | 表格排版 | 使用 StackMath.Grid 计算单元格位置 |

### 4.4 PDF 排版管线阶段

```
阶段1: CalculatePageMarginsStage   — 计算可用区域
阶段2: LayoutHeaderFooterStage     — 排布页眉页脚
阶段3: LayoutFlowContentStage      — 流式内容排版（文本自动换行）
阶段4: LayoutFixedElementsStage    — 固定元素排版（图片、标题等）
阶段5: DetectPageBreaksStage       — 分页检测与自动分页
阶段6: DetectOverlapsStage         — 重叠检测
阶段7: RenderToPdfStage            — 调用第三方 PDF 库渲染输出
```

### 4.5 可行性评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 数学复用度 | ★★★★★ | ProportionalMath、StackMath、ClampMath、OverlapMath 全部直接可用 |
| 架构适配度 | ★★★★★ | Pipeline 管线天然适合"布局→渲染"的 PDF 生成流程 |
| 实现工作量 | 中 | 需要集成第三方 PDF 渲染库（推荐 QuestPDF） |
| 核心价值 | 高 | JSON 驱动的 PDF 模板引擎，支持动态报表生成 |

## 第五部分：领域三——游戏建筑建模排布

### 5.1 领域映射

| WdUI 概念 | 建筑排布映射 | 说明 |
|-----------|------------|------|
| Control (控件) | BuildingElement (建筑元素) | 建筑、道路、装饰物、地形块 |
| ControlConfig | BuildingElementConfig | 建筑类型、尺寸、旋转、材质 |
| LayoutPosition | ScenePosition | 场景坐标（2D 俯视图） |
| Container | SceneZone (场景区域) | 城区、街区、地块 |
| ProportionalMath | 建筑在场景中的比例定位 | **直接复用** |
| StackMath.Grid | 建筑群网格排列 | **直接复用** |
| OverlapMath | 建筑碰撞检测（2D 俯视图） | **直接复用** |
| Pipeline | 场景生成管线 | 重新定义阶段 |
| Strategy | 不同建筑类型的布局策略 | 重新实现 |

### 5.2 数据模型规划

需要定义的建筑排布领域模型：

- **BuildingElementType 枚举**：Foundation(地基)、Wall(墙壁)、Floor(楼层)、Roof(屋顶)、Column(柱子)、Stair(楼梯)、Door(门)、Window(窗)、Decoration(装饰)、Road(道路)、GreenSpace(绿化)
- **BuildingElement 类**：Name、ElementType、X/Y/Width/Height、Rotation、FloorLevel、Material、Properties
- **BuildingElementConfig 类**：继承 ElementConfig，增加 BuildingType、Rotation、FloorLevel、Material、IsLoadBearing、MinDistance
- **SceneZoneConfig 类**：Name、Width、Height、MaxFloors、Elements、Rules
- **BuildingRules 类**：BuildingCoverage、MinBuildingSize、MaxBuildingSize、RoadWidth、EnableCollisionDetection、EnforceSetback、SetbackDistance

### 5.3 需要实现的策略

| 策略 | 用途 | 说明 |
|------|------|------|
| StreetLayoutStrategy | 生成网格状道路系统 | 先执行（StageOrder: 10） |
| ResidentialBuildingStrategy | 住宅建筑布局 | 中间执行，支持内部房间划分 |
| CommercialBuildingStrategy | 商业建筑布局（高层） | 中间执行，支持多楼层生成 |

### 5.4 场景生成管线阶段

```
阶段1: GenerateTerrainStage           — 生成地形
阶段2: GenerateStreetNetworkStage     — 生成道路网络
阶段3: DivideIntoPlotsStage           — 划分地块
阶段4: LayoutBuildingsStage           — 排布建筑（调用策略）
阶段5: GenerateInteriorLayoutStage    — 生成建筑内部布局
阶段6: DetectCollisionsStage          — 碰撞检测与自动修复
阶段7: AddDecorationsStage            — 添加装饰元素
```

### 5.5 3D 扩展方案

对于需要 3D 空间排布的场景，可以在 2D 引擎基础上扩展：

- **Rect3D 结构体**：在 2D Rect 基础上增加 Z 轴和 Depth（深度）
- **OverlapMath3D 静态类**：3D AABB 碰撞检测算法
- **BuildingElement3D 类**：在 BuildingElement 基础上增加 Z、Depth、RotationY、ModelPath

### 5.6 可行性评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 数学复用度 | ★★★★☆ | 2D 数学全部可用，3D 碰撞需扩展 |

## 第六部分：领域四——动画编排（抽象资源排布）

### 6.1 核心洞察：从空间到时间的维度跃迁

动画的本质是 **"在时间轴上，对对象的属性进行插值和编排"**。这与 WdUI 的布局排布逻辑在数学上是**同构的**：

```
WdUI 布局: 容器(2D空间) + 元素(控件) + 策略(排布规则) → 位置/尺寸
动画编排: 时间轴(1D时间) + 关键帧(动画片段) + 策略(插值规则) → 时间点/持续时间
```

这个映射证明了 WdUI 的排布逻辑不仅适用于"空间"这种具象资源，也适用于"时间"这种抽象资源。**"空间排布"和"时间排布"在数学上是同构的。**

### 6.2 领域映射

| WdUI 概念 | 动画编排映射 | 说明 |
|-----------|------------|------|
| Container (容器) | Timeline (时间轴) | 有限的时间区间 [0, T] |
| Control (控件) | AnimationClip (动画片段) | 在时间轴上占据一段区间 |
| ControlConfig | ClipConfig | 开始时间、持续时间、插值方式 |
| LayoutPosition (比例位置) | TimePoint (时间点) | 元素在时间轴上的比例位置 |
| Width/Height (尺寸) | Duration (持续时间) | 动画片段的时间长度 |
| ProportionalMath | 时间比例定位 | `t = timelineDuration × ratio` **直接复用** |
| StackMath.Horizontal | 时间序列编排 | 动画片段在时间轴上串行排列 **直接复用** |
| StackMath.Vertical | 并行动画编排 | 多个动画同时播放 **直接复用** |
| StackMath.Grid | 时间网格编排 | 多轨道时间轴（类似视频编辑软件） **直接复用** |
| OverlapMath | 时间冲突检测 | 两个动画片段是否时间重叠 **直接复用** |
| ClampMath | 时间/速度约束 | 动画时长/帧率约束 **直接复用** |
| Pipeline | 动画合成管线 | 多个动画阶段的顺序执行 |
| Strategy | 插值策略 | 不同属性使用不同插值方式 |
| Recursion | 嵌套动画 | 子动画在父动画时间轴内递归 |

### 6.3 数据模型规划

需要定义的动画编排领域模型：

- **AnimationClipType 枚举**：PositionX(水平位移)、PositionY(垂直位移)、Rotation(旋转)、Scale(缩放)、Opacity(透明度)、Color(颜色变化)、Path(路径动画)、Custom(自定义属性)
- **AnimationClip 类**：Name、ClipType、StartTime、Duration、FromValue、ToValue、EasingFunction、LoopCount
- **EasingType 枚举**：Linear(线性)、EaseIn(缓入)、EaseOut(缓出)、EaseInOut(缓入缓出)、Bounce(弹跳)、Elastic(弹性)、Back(回退)
- **TimelineConfig 类**：TotalDuration、AutoReverse、Loop、Clips、ParallelTracks
- **AnimationState 类**：CurrentTime、IsPlaying、IsPaused、Progress(0-1)、CurrentFrame

### 6.4 需要实现的策略

| 策略 | 用途 | 说明 |
|------|------|------|
| TimelineAllocationStrategy | 时间轴分配 | 使用 ProportionalMath 将动画片段分配到时间轴上 |
| InterpolationStrategy | 插值策略 | 按 EasingType 分发到不同的插值算法 |
| ParallelTrackStrategy | 并行轨道编排 | 使用 StackMath.Vertical 管理多轨道并行动画 |

### 6.5 动画编排管线阶段

```
阶段1: TimelineAllocationStage      — 使用 ProportionalMath 分配时间轴上的时间段
阶段2: ClipSequenceLayoutStage      — 使用 StackMath 排列动画片段的执行顺序
阶段3: InterpolationStrategyStage   — 为每个片段选择插值策略
阶段4: TimeConflictDetectionStage   — 使用 OverlapMath 检测时间冲突
阶段5: EasingFunctionStage          — 应用缓动函数
阶段6: AnimationCompositionStage    — 合成输出最终动画帧
```

### 6.6 具体场景分析

#### 场景1：UI 控件动画编排（与现有 WdUI 最接近）

```
UI 控件 = 容器
动画效果 = 元素

策略注册：
- FadeInStrategy: 透明度 0→1
- SlideInStrategy: 位置从屏幕外滑入
- ScaleStrategy: 缩放动画
- RotateStrategy: 旋转动画

管线：
阶段1: 动画触发条件检测
阶段2: 动画参数计算（ProportionalMath 计算关键帧时间点）
阶段3: 动画执行（插值）
阶段4: 动画完成回调
```

#### 场景2：粒子系统（Pipeline 的天然应用）

```
粒子系统 = 容器
粒子 = 元素

Pipeline 管线：
阶段1: 粒子生成 (EmitStage) — 决定粒子数量、初始位置
阶段2: 生命周期分配 (LifetimeStage) — 使用 ProportionalMath 分配
阶段3: 运动轨迹 (TrajectoryStage) — 使用 StackMath 排列运动路径

阶段5: 颜色/透明度渐变 (ColorStage) — 属性插值
阶段6: 粒子消亡 (DeathStage) — 回收
```

#### 场景3：多属性动画编排（最抽象的映射）

```
每个动画属性（位置X、位置Y、旋转、透明度、缩放）可以看作一个"维度"
每个维度有自己的"时间轴容器"

Pipeline 管线阶段可以定义为：
阶段1: 时间轴分配 (TimelineAllocationStage)
阶段2: 关键帧布局 (KeyframeLayoutStage) 
阶段3: 插值策略选择 (InterpolationStrategyStage)
阶段4: 时间冲突检测 (TimeConflictDetectionStage)
阶段5: 缓动函数应用 (EasingFunctionStage)
阶段6: 动画合成输出 (AnimationCompositionStage)
```

## 第七部分：领域五——WorkFlowMethod 图编排（大规模动态工作流引擎的数学基础层）

### 7.1 背景：WorkFlowMethod 架构全景

WorkFlowMethod 是一个基于 ECS + 图框架 + LLM 决策的大规模动态工作流引擎。其核心架构为：

### 7.3 四个融合层面

#### 层面1：Pipeline 统一——WdUI.Core.Pipeline 作为 GraphPipeline 的基类

WorkFlowMethod 已经实现了 `GraphWorkflowConnector` 和 `IGraphPipelineStep`：

```csharp
// 当前 WorkFlowMethod 的实现
public interface IGraphPipelineStep<TKey, TNodeData, TEdgeData> {
    string Name { get; }
    Task ExecuteAsync(IGraph<TKey, TNodeData, TEdgeData> graph, IGraphPipelineContext context);
}

public class GraphWorkflowConnector {
    public async Task ConnectAsync(IReadOnlyList<ChainInfo> inputChains, ...) {
        foreach (var step in _steps) {
            await step.ExecuteAsync(graph, pipelineContext);
        }
    }
}
```

WdUI 的 Pipeline 是泛型的、领域无关的：

```csharp
// WdUI.Core 的实现
public class Pipeline<TElement, TConfig> {
    public async Task<PipelineResult> ExecuteAsync(ILayoutContext<TElement> context) {
        foreach (var stage in _stages) {
            await stage.ExecuteAsync(context, cancellationToken);
        }
    }
}
```

**统一方案**：让 `IGraphPipelineStep` 继承或包装 WdUI.Core 的 `IPipelineStage`：

```csharp
// 统一后：GraphPipelineStep 复用 WdUI.Core 的 Pipeline 机制
public interface IGraphPipelineStep<TKey, TNodeData, TEdgeData> 
    : IPipelineStage<IGraph<TKey, TNodeData, TEdgeData>, GraphPipelineConfig> 
{
    // Name 和 ExecuteAsync 由 IPipelineStage 提供
}
```

**价值**：WorkFlowMethod 不需要维护自己的 Pipeline 实现，直接复用 WdUI.Core 的 Pipeline 机制（中间件、观察者、跳过/分支、事务支持）。

```csharp
public class GraphAnalyzeStep : IGraphPipelineStep<...> {
```

### A. 术语对照表

| 术语 | 说明 |
|------|------|
| TElement | 泛型元素类型，在不同领域替换为具体类型 |

| ProportionalMath | 比例定位数学，将比例值转换为绝对坐标 |
| StackMath | 堆叠排列数学，支持垂直/水平/Grid 三种排列 |
| OverlapMath | 重叠检测数学，AABB 碰撞检测 |
| ClampMath | 尺寸约束数学，将值限制在指定范围内 |
| MergeMath | 配置合并数学，深度合并配置对象 |
| LayoutContext | 布局上下文，提供布局过程中需要的服务和状态 |
| RecursionPolicy | 递归策略，控制递归遍历的深度和范围 |

> **文档结束**
>
> 本文档论证了 WdUI 的布局排布逻辑可以提取为通用的"资源分配引擎"，
> 并且该引擎可以无缝适配到地图生成、PDF 排版、游戏建筑建模排布、动画编排、WorkFlowMethod 图编排五个领域。
>
> 五个领域代表了三个层次的抽象跃迁：
> - **具象空间层**：地图生成、PDF 排版、游戏建筑排布（2D/3D 空间资源）
> - **抽象时间层**：动画编排（时间资源）
> - **AI 决策层**：WorkFlowMethod 图编排（LLM 做定性推理，WdUI 做定量分析）
>
> 核心价值在于：**一套数学体系 + 一套编排模式 = 无限领域适配可能**。
> **维度跃迁**：从"空间排布"到"资源分配"，从具象到抽象，从 UI 框架到通用引擎。
