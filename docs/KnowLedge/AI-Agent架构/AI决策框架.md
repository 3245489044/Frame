## 引言：告别"模式拜物教"

技术社区长期存在一种**"脚本原教旨主义"**，仿佛将任何命令写入 `.sh` 文件就能自动降本增效；同时也存在**"实时万能论"**，认为 ReAct 架构是解决一切模糊需求的银弹。

事实是：在工程领域，不存在绝对更优的模式，只存在**"在特定执行频率（N）与任务耗时（T）下，谁的含权综合成本更低"**。本文将重构四个关键数学模型，彻底终结这场无意义的争论。

## 第一章 诚实的 Token 账簿

> 修复"调试期望值"与"回显对称性"

V1.0 最大的逻辑欺诈在于：计算脚本成本时只算了"完美跑通"的理想值（800 Tokens），而计算实时模式时却强行塞入了高额回显（5000 Tokens）。这是典型的控制变量失衡。

### 1.1 含错期望成本

**现实工程中，一次写对脚本的概率 `P_ok` 通常不超过 0.4**（取决于任务复杂度）。当脚本报错时，AI 必须将 StdErr 塞回上下文才能修复代码。

**真实期望推演**（以中等复杂度任务 `jq + sed` 批处理为例）：

| 步骤 | Token 消耗 | 说明 |
|------|-----------|------|
| 初版生成 | 800 Out | 首次生成脚本 |
| 首次报错（概率 60%） | 1500 In + 600 Out | 读取错误回显 + 修复重生成 |
| 二次报错（概率 20%） | 1000 In + 400 Out | 再次读取错误 + 二次修复 |

**脚本模式的期望 Token 成本：**

```
E[Tokens] = 800 + 0.6 × (1500 + 600) + 0.2 × (1000 + 400)
         = 800 + 0.6 × 2100 + 0.2 × 1400
         = 800 + 1260 + 280
         = 2,340 Tokens
```

### 1.2 实时模式的对称性成本

实时模式每一步必须读取 Stdout/Stderr 作为观测依据，且携带历史上下文：

| 步骤 | Token 消耗 | 说明 |
|------|-----------|------|
| 生成动作 | 800 Out | 生成指令 |
| 环境回显（npm build / ls -la） | ~2000 In | 读取执行结果 |
| 历史累积摊销 | ~500 In | 上下文窗口增长 |

**实时模式单次期望成本：**

```
E[Tokens] = 800 + 2000 + 500 = 3,300 Tokens
```

**纯算力结论**（尚未引入人力）：脚本模式的期望 Token 成本确实比实时模式低约 **29%**。这验证了"写脚本省 Token"的直觉，但远远未触及工程决策的核心。

## 第二章 颠覆性变量：认知重启税

> 被 99% 技术文章忽视的"Context Switching Penalty"

V2.0 的核心谬误在于宣称"脚本提交后台 → 人去开会 → 零阻塞"，这无视了人类认知科学的基本定律。

### 2.1 异步带来的隐性成本

当工程师将脚本提交后台运行并切去做其他事（如回邮件、开会），6 分钟后回来时，他必须重新回答三个问题：

1. 我刚才写的这个脚本逻辑是什么来着？
2. 我预期它的输出应该长什么样？
3. 如果报错，这个报错是因为权限还是因为数据格式变了？

根据认知心理学中的**"注意力残留（Attention Residue）"**理论，从干扰中恢复复杂工程心流的平均耗时为 **6~12 分钟**。我们取极保守下界：**60 秒**。

以工程师时薪 $100/小时（$0.027/秒）计算：

```
单次异步重启税 = 60 秒 × $0.027/秒 = $1.62
```

### 2.2 单次任务的真实总成本对比

**场景：N=1（单次任务）**

| 成本维度 | 实时串行模式 | 脚本异步模式 |
|---------|-------------|-------------|
| AI Token 算力成本 | 3300 Tokens ≈ $0.021 | 2340 Tokens（含期望调试）≈ $0.015 |
| 人类阻塞等待（盯屏/提交） | 7 秒 ≈ $0.19 | 4 秒 ≈ $0.11 |
| 认知重启恢复成本 | $0（从未离开任务） | **$1.62**（开会回来重新理解逻辑） |
| **总综合成本** | **≈ $0.211** | **≈ $1.745** |

> **颠覆性洞见**：在 **N=1（单次任务）** 的场景下，实时模式的总成本仅为脚本模式的 **1/8**。

结论显而易见：只要任务不是高频重复的，强迫自己写脚本并后台运行，实际上是在用 **$1.62 的人力浪费** 去省 **$0.006 的 Token 差价**——这是极其愚蠢的工程决策。

## 第三章 恢复"重复性"的经济学正统地位

V1.0 曾宣称"脚本化的第一性原理是逻辑闭合，重复性只是表现形式"，并称此为"因果倒置"。这属于用哲学修辞替代经济学常识。

### 3.1 脚本化收益的严格数学摊销公式

设：
- **R** = 确定性任务单次实时成本
- **S** = 单次脚本边际执行成本（近似为 0）
- **F** = 脚本的固定编写与调试沉没成本（含期望调试与重启税）
- **N** = 执行次数

```
脚本化净收益 = N × (R - S) - F
```

其中 **F** 不仅包含 Token 调试成本（2340 Tokens ≈ $0.015），更包含首次编写与调试所占用的人力阻塞 + 潜在的异步重启税。

### 3.2 为什么"重复性"才是第一生产力

- 当 **N = 1** 时，即使逻辑完美闭合，**F** 的绝对值远大于 **R**，净收益必为负。
- 只有当 **N** 足够大（例如 **N ≥ 5**），固定沉没成本 **F** 被充分摊销，脚本化才真正开始盈利。

**修正后的逻辑归因：**

| 条件 | 角色 | 说明 |
|------|------|------|
| 逻辑闭合 | 必要非充分条件 | 没有闭合，绝对写不了脚本 |
| 重复性（高 N 值） | 经济杠杆 | 有了重复，才值得写脚本 |

## 第四章 修正"计算量分配"的架构常识

原 V1.0 声称"最高效 Agent 应将 80% 算力花在路由决策"，这违背了 Transformer 的数学铁律。

### 4.1 算力消耗的客观公式

在 Decoder-only 架构中：

```
单次前向推理计算量（FLOPs）≈ 2 × 模型参数量 × 生成 Token 数
```

| 操作类型 | Token 生成量 | 相对计算量 |
|---------|-------------|-----------|
| 路由决策（选择工具） | 1~3 个特殊 Token | **低**（基准） |
| 生成具体指令（如 `grep -r "error" ./logs`） | 30~50 个连续 Token | **10~15 倍**于路由 |

因此，**把"减少长文本生成"作为优化目标，其效率远高于"优化路由逻辑"**。

### 4.2 Agent 架构的正确进化方向

最高效的 Agent 框架应将任务拆解为**两层**：

```
┌─────────────────────────────────────────────────┐
│  意图路由层（高调用频次，低生成长度）              │
│  判断："是否需要调用本地工具"                      │
├─────────────────────────────────────────────────┤
│  确定性编译层（低调用频次，高生成长度）              │
│  一旦判断为确定性任务，一次性生成长脚本，            │
│  后续执行绝不消耗 LLM 算力                         │
└─────────────────────────────────────────────────┘
```

这才是在 Transformer 计算量公式下的最优解——**用路由频次换生成长度**。

## 第五章 最终的工程决策矩阵

基于以上四个修复模型，唯一可被验证的决策树如下：

| 任务场景 | 执行次数 N | 机器运行耗时 | 推荐模式 | 核心算账逻辑 |
|---------|-----------|-------------|---------|-------------|
| 临时探索（查 API 字段） | 任意 | 任意 | **强制实时 ReAct** | 逻辑不闭合，脚本无法预生成，物理上不可行 |
| 简单别名（如 `ll`） | N=1 | < 1 秒 | **实时终端** | 写文件的 IO 耗时 > 直接敲命令，脚本收益为负 |
| 确定脚本，单次运行 | N=1 | < 10 分钟 | **实时 Agent（串行）** | 认知重启税（$1.62）远大于节省的 Token（$0.006），盯屏最划算 |
| 确定脚本，多次运行 | N ≥ 5 | 任意 | **离线脚本/编译** | 高额沉没成本（含调试期望）被充分摊销 |
| 确定脚本，单次但极耗时 | N=1 | > 1 小时 | **强制离线脚本（异步）** | 人类阻塞成本（$100/小时）远超 $1.62 的重启税，必须释放人力 |

## 终章：工程学的归途

以上所有数学推导，均可被 **AWS 账单与 Jira 工时记录** 交叉验证。

AI Agent 的工程真相不是"实时干翻脚本"，也不是"脚本拯救世界"，而是：

1. **Token 不是成本的大头，人的注意力碎片化才是。**
2. **异步解耦不是免费午餐，它必须支付高昂的上下文切换税费。**
3. **只有面对高频重复（N ≥ 5）或极长耗时（T > 1h）的任务，才值得动用脚本这把"重剑"。**

> 告别概念炒作，尊重数学常识——这才是工程师对技术应有的敬畏。
