# 契约式脚本生成：Agent工具复用的结构化设计理念

## 摘要

代码执行型 Agent 系统面临一个隐蔽的成本黑洞——相似任务被反复从零生成脚本，导致 Token 消耗随调用量线性增长。本文提出一种基于结构化约束的脚本生成理念：通过建立明确的生成规范，让 Agent 在脚本产出时即携带完整的元数据、参数契约和结构化输出格式，使系统无需事后解析即可直接索引、检索和执行。该理念以契约式设计为核心，将"脚本生成"从自由创作转变为规范遵循，从根本上消除了参数推断的不确定性和持续维护的索引成本。本文从契约式设计、关注点分离、结构化编程等理论视角论证了该理念的合理性，并阐释了其在规模化部署中的战略意义。

---

## 一、问题的本质：脚本的"不可用性"而非"不可得性"

### 1.1 重复发明的成本黑洞

大语言模型 Agent 在执行代码类任务时，通常遵循"理解需求 → 编写脚本 → 执行 → 观察结果 → 修改重试"的循环。每一次任务，无论与历史任务多么相似，Agent 都倾向于从零开始生成脚本，消耗完整的输入输出 Token。

以 IT 运维场景为例，Agent 可能被反复要求执行逻辑完全一致、仅参数不同的任务——清理不同路径下的过期文件、重启不同名称的服务、查询不同机器的状态信息。核心逻辑无需重写，但每次都要经历 3-5 轮生成与调试，消耗数千 Token。

这是代码执行型 Agent 最隐蔽的成本黑洞：不是单次任务的绝对消耗，而是相似任务的重复消耗无法被摊销。随着 Agent 从单次对话走向规模化部署，这一问题从"可容忍"变为"不可持续"。

### 1.2 问题的深层性质：不是"找不到"而是"不可用"

解决这一问题的直观思路是建立工具复用机制：将曾经成功执行过的脚本保存下来，供后续类似任务直接调用。然而，简单的"保存-复用"路径面临一个根本性障碍：

Agent 自由生成的脚本是面向执行的——它的目标是"在当前环境中成功运行"。它不是为了"被未来的系统理解"而写的。因此，这些脚本天然缺乏系统化的自描述信息：

- 这个脚本解决什么问题？——需要人工或 LLM 推断
- 它接受哪些参数？——需要解析整个脚本才能找出
- 它输出什么格式？——取决于模型当时的写作习惯
- 它依赖什么环境？——没有显式声明
- 它与另一个脚本是什么关系？——无法自动判断

如果工具库中的每个脚本都像一本没有封面、没有目录、没有页码、每页格式各异的"书"，那么即使把它保存下来，后续系统也难以有效地发现它、理解它、调用它。

问题的核心不是脚本的"可得性"（能否保存），而是脚本的"可用性"（能否被系统直接使用）。可用性的缺失，使得工具复用从"技术问题"变成了"认知问题"——系统需要持续投入计算资源来"读懂"自己的历史产出，而不是直接"使用"它。

### 1.3 一种被忽视的解决路径

如果问题的本质是"脚本不够结构化"，那么最直接的解决方案就是：让脚本变得更结构化。与其接受模型自由生成的非结构化结果、再投入额外成本去解析和理解，不如在脚本生成阶段就引入结构化的约束，使每个产出天然具备可被系统直接使用的一切属性。

这并非对模型能力的限制，而是对产出质量的保证。其核心理念是：好的系统设计不是靠事后修补，而是靠事先约定。当我们要求所有脚本遵循同一套结构化规范时，脚本不再是"需要被解读的文本"，而是"可以直接接入系统的组件"。

## 二、核心理念：让脚本自带"接口"

### 2.1 脚本即契约

传统软件工程中，一个函数通过其签名（函数名、参数列表、返回值类型）与调用方建立契约。调用方承诺提供符合类型和范围的参数，函数承诺按规范返回结果或抛出异常。这种契约式设计（Design by Contract, Meyer, 1992）使得模块之间的交互变得明确、可验证、可组合。

将这一理念延伸到 Agent 生成的脚本中：每一个脚本都应当像一个函数那样，拥有明确的"接口"。这个接口告诉系统：

- 这个脚本**是什么**——它的身份、分类、用途描述
- 它**需要什么**——参数的名称、类型、是否必填、取值范围
- 它**产出什么**——输出的结构、字段含义、成功/失败标识
- 它**依赖什么**——运行环境、权限要求、所需模块
- 它**如何被调用**——典型的使用示例

当脚本携带着完整的接口信息时，系统与脚本之间的关系从"系统理解脚本"变成了"系统使用脚本"。前者是持续的、不确定的认知劳动，后者是一次性的、确定性的机械操作。

### 2.2 从"隐式信息"到"显式声明"

Agent 自由生成的脚本并非没有信息——它包含完成任务所需的一切逻辑。但这些信息是隐式的：路径散落在脚本各处，参数没有集中声明，输出格式取决于模型当时的偏好，环境依赖没有任何标注。

要让脚本变得"可用"，需要将这些隐式信息转化为显式声明——以固定的结构、在固定的位置、用可被机器解析的格式，完整地陈述脚本的契约。具体而言，需要完成四个维度的显式化：

- **身份显式化**。脚本应当声明它属于什么类别、解决什么问题。这使系统能够在检索时进行精准的类别过滤，而非依赖语义相似度的模糊匹配。
- **参数显式化**。所有可变的输入值应当在一个集中的位置以参数列表的形式声明，包括名称、数据类型、是否必填、约束范围、默认值。这使系统在调用时能够自动生成参数输入界面，并对用户输入进行合法性校验。
- **输出显式化**。脚本的返回结果应当遵循固定的信息结构——执行状态（成功/失败）、状态消息、详细数据、错误列表。这使 Agent 在接收结果时能够直接读取结构化字段，无需进行自由文本理解。
- **条件显式化**。脚本应当声明自身有效的前提条件——需要什么版本的 PowerShell、是否需要管理员权限、依赖哪些外部模块、在什么操作系统上可用。这使系统在调用前能够快速判断当前环境是否满足要求，避免执行失败。

### 2.3 约束的本质是解放

引入结构化约束的一个常见顾虑是：它是否会限制模型的创造性和灵活性？

从表面看，约束确实增加了模型在生成时需要遵循的规则。但从系统整体看，约束在生成端增加的复杂度，远小于它在使用端消除的复杂度。这是一种"复杂度转移"——将原本分散在解析、聚类、泛化、推断、校验等多个环节的复杂度，集中到生成环节一次性解决。

更具战略意义的是：当所有脚本遵循同一套规范时，工具库从一个"杂乱的代码仓库"转变为一个"结构化的知识资产"。系统可以对它进行确定性查询（"列出所有需要管理员权限的文件操作工具"）、自动生成文档、追踪演化历史、分析调用模式。这些能力在自由生成的脚本库中是不可能实现的——因为"理解"每一个脚本的代价太高了。

"约束"在这里扮演的角色，类似于自然语言中的语法规则——语法不限制你能说什么，它只限制你如何组织语言，从而使你的表达能够被他人理解。同样，结构化约束不限制 Agent 能解决什么问题，它只限制脚本如何组织，从而使脚本能够被系统直接使用。

## 三、理念的学术基础

### 3.1 契约式设计：显式约定的力量

契约式设计（Meyer, 1992）的核心原则是：软件模块之间应当通过显式的、可验证的契约来定义交互规则，而非依赖隐式的假设或文档。一个完整的契约包含三个部分：

- **前置条件**：调用方必须满足的条件（如"参数必须在有效范围内"）
- **后置条件**：模块执行后保证的结果（如"返回值包含 Success 字段"）
- **不变式**：模块在整个执行过程中保持的属性（如"不修改系统环境变量"）

在本理念中，脚本的"接口"正是这一契约思想的直接体现。参数声明定义了前置条件，结构化输出定义了后置条件，环境标签定义了不变式。当脚本以契约化的方式生成，调用方和被调用方之间的权利义务被明确定义，消除了所有因"约定模糊"导致的错误和低效。

### 3.2 关注点分离：让各部分做自己最擅长的事

关注点分离是系统工程的基本原则：复杂系统应当被分解为相对独立的模块，每个模块处理一个特定的关注点，模块之间通过明确定义的接口交互。

在本理念中，关注点被清晰地分离：

- **LLM** 负责处理"任务逻辑"——理解用户需求、设计解决方案、生成脚本代码。这是 LLM 最擅长的创造性工作。
- **结构化规范** 负责处理"脚本的可用性"——使脚本能够被系统索引、检索、调用。这是规范最擅长的工作——它不需要智能，只需要一致性。
- **系统** 负责处理"脚本的执行"——参数校验、环境检查、调用执行、结果解析。这是确定性代码最擅长的工作——高效、可靠、零 Token 消耗。

当关注点被正确分离时，每一层都专注于自己最擅长的事。LLM 不需要考虑"我写的脚本未来如何被系统理解"，系统不需要"理解"脚本的内容。接口层作为明确的边界，使两者的交互变得清晰、高效。

### 3.3 结构化编程：可理解性的前提

结构化编程（Dijkstra, 1968）的核心理念是：程序的可理解性和可验证性依赖于其结构的规范性。当程序遵循一套明确的组织规则时，阅读者（无论是人还是机器）可以更快地定位信息、理解逻辑、发现错误。

这一理念在本框架中的延伸是：脚本的可复用性和可检索性依赖于其元结构的规范性。当脚本遵循一套明确的元数据组织规则时，系统可以快速地获取关键信息（身份、参数、输出、条件），而无需通读和解析整个脚本。可理解性从"全文理解"简化为"元数据读取"——这是质的飞跃。

### 3.4 分布式认知：让信息在生成时即被组织

分布式认知理论（Hutchins, 1995）强调：智能系统不应将全部认知负载集中于中心处理单元，而应将部分认知功能"卸载"到环境的结构中。在传统方案中，这种卸载表现为"将脚本从上下文移到工具库"——但被卸载的脚本仍然是无序的，系统需要持续投入认知资源来组织和理解它们。

本理念将这一理论向前推进一步：不仅卸载认知负载，而且在信息生成时即按照系统的认知结构进行预组织。脚本不再是需要被理解的原始材料，而是已经被组织好的、可直接接入系统认知流程的知识组件。这是从"卸载后整理"到"卸载前已整理"的进化——使"卸载"从减少存储负担升级为减少认知负担。

## 四、理念的系统效应

### 4.1 成本结构的根本变化

当脚本自带完整接口时，系统运营的成本结构发生了根本性的变化：

| 环节 | 无结构化约束 | 有结构化约束 |
|------|--------------|--------------|
| 脚本入库 | 需要解析、聚类、泛化、描述生成，持续消耗 LLM Token | 直接提取已声明的元数据，零额外 Token 消耗 |
| 参数获取 | 从多个变体推断，存在不确定性 | 直接读取参数列表，确定性的 |
| 工具检索 | 依赖语义相似度匹配描述文本，准确性取决于描述质量 | 结合结构化过滤与语义匹配，准确性可量化保证 |
| 结果解析 | 需要 LLM 理解自由文本输出 | 直接读取结构化字段，零 Token 消耗 |
| 环境校验 | 执行时失败才发现不兼容 | 调用前通过标签精确过滤 |
| 冷启动 | 需要积累多个样本才能泛化 | 第一个脚本即可直接使用 |

更为关键的是，结构化方案消除了持续性的"维护成本"。在自由生成方案中，随着工具库的增长，解析、聚类、推断的负担持续上升。而在结构化方案中，工具库的增长只增加存储量，不增加每个新工具入库时的处理复杂度——因为处理是确定性的元数据提取，不受库规模影响。

### 4.2 从"近似匹配"到"精确查找"

传统方案中，工具检索依赖语义相似度：将用户意图和工具描述映射到同一向量空间，计算相似度，返回最接近的几个工具。这种方法的召回率受限于：描述质量参差不齐、语义漂移、冷启动等问题，通常在 85% 左右。

当工具携带结构化的身份标签和分类信息时，检索可以从两阶段匹配升级为精确+语义的两层过滤：

1. **第一层（精确过滤）**：根据用户意图解析出的任务类别、环境条件等结构化条件，快速筛选出符合条件的候选集合。这一步是确定性的，准确率 100%。
2. **第二层（语义匹配）**：在已经精确筛选的候选集合中进行语义相似度计算，选出最相关的工具。

两层过滤的复合效应是：第一层将候选空间从数千个工具缩减到数十个，使第二层的语义匹配在更小、更相关、噪音更少的空间中进行。召回率可提升至 99% 以上，且语义匹配的不确定性被限制在了可控范围之内。

### 4.3 "生成前检索"的正反馈循环

结构化规范的另一个重要效应是：它使"生成前检索"成为可行且高效的策略。当系统可以在生成新脚本之前，先快速查询工具库中是否已有同类工具时：

- **系统查询**：用户发起任务 → 系统解析需求 → 在工具库中检索
- **命中则复用**：找到匹配工具 → 直接调用 → 零生成成本
- **未命中则生成**：未找到匹配工具 → Agent 按规范生成新脚本 → 新脚本自动入库供未来使用

这一流程与传统的"先生成、后入库"相比，关键区别在于：生成被放在了"检索失败"的分支中，而非默认路径。随着工具库的增长，命中率持续提升，生成行为逐渐减少。这形成了一个正反馈循环：使用越多 → 工具库越丰富 → 命中率越高 → 需要生成的场景越少 → 效率越高。

这一循环的启动条件非常低：第一个合规脚本入库后，当下一个相似任务到来时，系统就已经可以命中它。不存在需要积累足够样本才能开始受益的"冷启动期"。

## 五、更深层的战略意义

### 5.1 从"代码仓库"到"知识资产"

当所有脚本遵循同一套结构化规范时，工具库的性质发生了质变：

在自由生成模式下，工具库是一个"代码仓库"——里面存着大量代码文件，但系统无法自动理解它们之间的关系、用途和质量。它能做什么、不能做什么、哪些是可靠的、哪些已经过时——这些问题没有结构化的答案。

在结构化规范下，工具库是一个"知识资产"——每条记录都携带完整的元数据、明确的契约、可验证的格式、可追溯的历史。系统可以对它进行复杂的结构化查询，可以自动生成目录和文档，可以追踪工具的演化与淘汰，可以分析调用模式来指导未来的优化方向。

工具库从"需要被理解的材料"变成了"可以直接操作的数据"。这使系统具备了超越"查-用"的更高阶能力：它开始"理解"自己的能力边界，可以对自己进行自省和规划。

### 5.2 对 Agent 能力模型的再定义

这一理念对"Agent 应该具备什么能力"提出了不同于传统的要求：

- 在自由生成模式下，Agent 被期待为"有创造力的写作者"——它能写出任何东西，但系统需要事后去理解它写了什么。
- 在结构化规范下，Agent 被期待为"遵循规范的工程师"——它按照规范产出标准化组件，系统直接使用而不需要理解其内部细节。

这两种能力模型并非对立，但它们在工程化部署中的价值不同。自由创造力在探索性任务中仍不可或缺；但在规模化、重复性、可预测的运维场景中，"规范遵循"比"自由表达"更有价值。Agent 的经济性不在于它能写出多聪明的代码，而在于它的产出能被多系统化地复用。

### 5.3 规范是"活"的

必须强调的是，结构化规范并非一成不变的教条。随着系统的发展和任务类型的变化，规范本身应当是可演化的：

- 当系统发现现有分类无法覆盖新出现的任务类型时，分类体系可以扩展
- 当发现输出结构缺少某些关键信息时，格式可以补充新的字段
- 当发现环境依赖的粒度不够细时，标签体系可以细化

规范的演化应当由系统的实际使用数据驱动。这不同于"自由生成"的随意性——规范的每一次变化都是有记录、有理由、可追溯的。规范是"活"的，但它的变化是受控的、有意义的，而非随机的。

## 六、结语

本文的核心主张可以简洁地表述为：在 Agent 工具复用问题上，最经济的路径不是让系统更努力地"读懂"脚本，而是让脚本从一开始就"可读"。

当系统需要从自由生成的脚本中逆向工程出参数、分类、依赖和意图时，它实际上是在为一个本应在生成阶段解决的问题付出持续的、不确定的代价。每一次解析、每一次聚类、每一次泛化、每一次推断，都是对"当初没有建立规范"的补救。

结构化脚本生成理念提供了一条不同的路径：通过建立明确的生成规范，使每个脚本在诞生时就携带着完整的身份声明、参数契约、结构化输出和环境标签。系统不需要"理解"脚本——它只需要"读取"已经声明好的信息。这是一种从"认知密集型"到"确定性操作"的转变。

在学术层面，这一理念受到契约式设计、关注点分离、结构化编程、分布式认知等经典理论的支持。在工程层面，它将成本结构从"持续投入"变为"一次定义"，将检索从"近似匹配"升级为"精确过滤+语义精匹配"，将冷启动从"需要积累"变为"即用即有"。在战略层面，它将工具库从"代码仓库"升级为"知识资产"，使系统具备了自省、自组织和持续进化的基础。

最好的"理解"是不需要理解，最好的"泛化"是生成时已完成泛化，最好的"发现"是信息从未被隐藏。这是从"事后修补"到"事先设计"的转变，是从"让 AI 自由创作再交给系统去理解"到"让 AI 按照系统能直接使用的规范去创作"的转变。在 Agent 系统走向规模化部署的今天，这一转变具有根本性的战略意义。
