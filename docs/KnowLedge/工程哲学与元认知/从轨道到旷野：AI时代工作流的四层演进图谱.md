## 引言：一个被滥用的词

在AI应用开发领域，**工作流**大概是继**智能体**之后被滥用得最严重的词汇。

从一段简单的 `if-else` 条件判断，到 LangGraph 中错综复杂的图状态机，再到 AutoGen 里自由奔放的多 Agent 群聊——这些天差地别的东西，在无数技术文章里都被统称为"工作流"。开发者面对这些概念时，往往陷入"拿着锤子找钉子"的困境，选错范式，轻则事倍功半，重则项目翻车。

本文试图建立一个清晰的分级框架，帮你穿透"工作流"的迷雾。需要提前说明的是，这四层并非严格的"代际更替"，而是一个**控制权光谱**——从左端的"绝对刚性"到右端的"高度自治"，每一层都在前一层的基础上释放了更多运行时灵活性，但也相应付出了可控性的代价。

---

## 一、先厘清两个基本概念

在深入分级之前，有必要区分两个经常被混为一谈的概念：**工作流（Workflow）** 与 **流程引擎（Process Engine）**。

> **工作流**是业务过程的抽象模型，表现为任务序列、规则与角色的组合（如"提交→审核→归档"）。
>
> **流程引擎**是执行工作流模型的运行时环境，负责状态跟踪、事务管理与异常处理（如 Activiti、Camunda）。

工作流是"图纸"，流程引擎是"施工队"。理解这一层，我们就能更精准地讨论：不同层级的"工作流"，究竟是在"图纸设计期"还是"运行时执行期"做文章。

## 二、四层分级：从绝对控制到完全自主

### 第一层：硬编码管道（Hard-coded Pipeline）

最原始、最确定的工作流形态。

- **核心特征**：步骤顺序在代码中写死，路径 100% 确定。`Step A → Step B → Step C`，不存在运行时变量。
- **控制权归属**：设计时绑定。程序员在编译期穷尽了所有可能性。
- **典型代表**：普通函数调用链、简单的 API 串接。
- **适用场景**：逻辑极度稳定且永不变化的基础设施层（如"读取配置→连接数据库→执行查询"）。
- **局限性**：任何流程变动都需要改代码、重新部署。

### 第二层：声明式管道（Declarative Pipeline）

将步骤定义从代码中剥离，放入配置文件。

- **核心特征**：步骤顺序依然 100% 确定，但流程定义变成了声明式配置（`YAML`/`JSON` 或可视化拖拽）。LLM 在这里只是一个"被调用的黑盒节点"，输入由上游提供，输出交给下游。
- **控制权归属**：运行时解析。虽然路径固定，但参数调整无需重新编译，只需修改配置文件。
- **典型代表**：LangChain 的旧版 `LLMChain`、Coze/Dify 等平台的基础工作流。
- **适用场景**：步骤固定但需要频繁调整 Prompt 或参数的业务流程（如"检索→生成→格式化"）。
- **关键认知**：这一层的进步是"代码与配置分离"，但路径依然是预先画好的单行道。第一层与第二层在决策逻辑上毫无区别，区别仅在于"流程定义"是以二进制代码还是以纯文本配置的形式存在。

### 第三层：预置图状态机（Pre-defined Graph State Machine）

当前 AI 生产环境中最具工程价值的核心层级。

- **核心特征**：流程不再是线性管道，而是开发者预先绘制的有向图（`Node + Edge + State`）。运行时具体走哪条边，可能由 LLM 的输出动态决定。路径不再是 100% 确定，而是在开发者预设的有限备选集合中动态选择。
- **控制权归属**：拓扑由人定，路由由模型选。开发者划定"赛道"边界，模型在边界内做选择题。
- **典型代表**：LangGraph、Semantic Kernel Process Framework。
- **适用场景**：多步推理、ReAct 工具调用循环、需要质量评估与重试的复杂任务（如"检索→评估相关性→若不佳则重写查询→生成→评估生成质量→迭代修正"）。
- **关键认知**：这是传统确定性流程与 AI Agent 之间的分水岭。它既保留了工程的可控性（图结构由人定义），又引入了 AI 的灵活性（条件分支由模型推理决定）。

### 第四层：动态图生成（Dynamic Graph Generation / Autonomous Swarm）

最前沿、最激进的研究探索层级。

- **核心特征**：开发者提供的不是预定义的图，而是目标、环境约束和工具集。智能体在运行时根据任务目标，自主规划并动态实例化执行拓扑——调用哪些工具、分几个步骤、是否需要新建子任务，均由模型在运行时生成。
- **控制权归属**：拓扑由 AI 生成。开发者从"画图者"退化为"规则制定者"，只负责划定边界（安全护栏、记忆机制、人工确认点）。
- **典型代表**：AutoGen、CrewAI，以及具备自主规划能力的 Agent Orchestration 模块。
- **适用场景**：高度开放、无法预判所有分支的探索性任务（如"分析上季度销售异常原因并生成汇报 PPT"）。
- **关键认知**：数学上，第四层的"动态图生成"可以视为第三层的超集（只要允许 LLM 动态修改图结构）。但在工程实践中，两者代表了截然不同的风险偏好——第三层追求"确定性产出"，第四层容忍"不可预知性"以换取更高的上限。

## 四、穿透本质：三个关键维度的重构

### 1. 路径 vs 拓扑：分清楚"选择"与"生成"

原文常将"路径"混为一谈，这里必须精确区分：

- **第一、二层**：路径集合在设计时已穷举。
- **第三层**：路径集合由开发者预置（图结构），模型仅做选择。
- **第四层**：路径集合本身由模型生成，开发者事先不知道图的完整形状。

> **一句话判断**：关掉 LLM 后，如果代码能画出所有可能的箭头，那就是前三层；如果关掉 LLM 就无法预知箭头从哪来、到哪去，那就是第四层。

### 2. 状态管理：事务状态 vs 语义记忆

传统流程引擎（Camunda 等）与 AI 框架（LangGraph 等）管理的对象性质完全不同，不存在"谁追赶谁"的问题：

- **传统 BPM**：持久化的是结构化业务数据（表单字段、审批意见），追求 ACID 事务特性。
- **AI 框架**：持久化的是高维语义上下文（对话记忆、Token 向量、嵌入索引），追求最终一致性。

两者在工程实践中往往嵌套共存：外层事务由传统引擎负责（保证断点续跑），内层语义修正由 AI 循环负责。

### 3. 失败处理：抛错与迭代并非对立

传统工作流出错就抛异常、回滚事务；AI 工作流出错则反馈给 LLM，让它自我修正（重试、换策略）。

但两者是**垂直嵌套关系**，而非水平对立关系。一个稳健的生产级系统，通常是：

> 外层由传统流程引擎监控超时与重试（事务级容错），内层由 LLM 循环进行内容修正（语义级容错）。

将两者割裂对立，是工程视角的典型误判。

## 五、框架映射：LangGraph与AutoGen在第几层？

基于上述精确定义：

- **LangGraph**：**第三层**（预置图）。开发者显式定义 `StateGraph`，LLM 在预设边之间跳转。虽然它具备很强的状态持久化能力，但其核心价值在于"可控的图执行"。
- **Semantic Kernel Process**：**第三层**。事件驱动的 Step 编排，思路更贴近微服务开发者的习惯。
- **Semantic Kernel Agent Orchestration**：**第三层向第四层的过渡地带**。提供顺序/并发/交接等预制模式，但在部分高阶场景中允许 Agent 动态协商。
- **AutoGen / CrewAI**：**第四层**（动态图）。原生支持多 Agent 自主协商、任务动态拆解，不依赖预定义的全量拓扑图。

## 六、选型指南：打破"混合悖论"

原文在选型部分存在一个逻辑矛盾：声称最优解是"第一层与第四层混合"，但按定义，一旦固定了关键路径，系统就自动退化回了第三层。

修正后的决策框架如下：

> **一个成熟的生产级系统，从来不是"选一层"，而是分层架构：**

1. **基础设施层**：用第一层/第二层的刚性管道处理数据库读写、API 鉴权、日志落盘——这些不需要 AI 参与，图灵完备的代码是最优解。
2. **业务逻辑主干**：用**第三层（预置图）** 定义核心业务 SOP（如客服工单处理、合同审核流程）。这一步保证了流程的下限（不跑偏），开发者对核心路径拥有绝对掌控力。
3. **边缘探索节点**：在图中特定的"复杂决策节点"内部，引入**第四层（动态生成）** 的 Agent 子群，负责处理长尾边缘案例。

> 这才是真正的"混合"——它不是将第一层与第四层强行缝合，而是利用第三层的"图结构"作为容器，将第四层的动态性封装在有限的局部节点内。

| 你的核心痛点 | 推荐落点 | 理由 |
|-------------|---------|------|
| 步骤固定，追求极致性能和确定性 | **第一/二层** | 杀鸡不用牛刀，代码是最可靠的工程实体。 |
| 步骤固定，但需要业务人员频繁调参 | **第二层** | 配置热加载，降低运维成本。 |
| 流程复杂，存在多条件分支，但边界清晰 | **第三层** | 图状态机提供可控性与灵活性的最佳平衡。 |
| 任务目标模糊，处理大量未知边缘案例 | **第三层为主 + 第四层封装在节点内** | 用图兜底保证不出圈，用 Agent 提升上限。 |
| 纯研究探索，容忍不可预知性 | **第四层** | 追求极限灵活性，换取实验空间。 |

## 七、结语：没有优劣，只有视点

回到文章开头：为什么"工作流"被滥用？

因为这四层在数学上存在包含关系（第四层能做第三层的事，第三层能做第二层的事），它们本是一条连续的控制权光谱。但为了工程决策，我们必须人为切分刻度。

> **传统工作流（一、二层）** 是为了消除不确定性，**预置图工作流（三层）** 是为了管理不确定性，而**动态生成（四层）** 是为了拥抱不确定性。

在真实的工程实践中，最稳妥的策略不是激进地"All in 第四层"，也不是保守地"死守第一层"。正确的做法是：

> 用第三层的图结构搭建刚性骨架，在骨架上预留柔性接口，将第四层的自主智能体作为"特种兵"空降到局部复杂战场。

理解这四层分级，不是为了给技术贴标签，而是为了让你在"绝对控制"与"绝对灵活"之间，找到属于你业务场景的黄金分割点。当你下次听到"AI 工作流"时，请先问一句：**你说的这条路，是工程师铺好的，还是 AI 自己现踩出来的？**
