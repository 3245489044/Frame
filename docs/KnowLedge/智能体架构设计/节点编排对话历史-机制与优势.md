# 基于节点编排的对话历史：LLM 历史与节点的双向转换机制与优势

> **定位**：抓住「节点」这一核心抽象，追问它的第三种身份——**LLM 对话历史与工作流之间的转换介质**。围绕「一条用户消息如何以节点为轴、在『对话历史』与『节点产出』两个真源之间来回转换」，做两个横切分析：**读侧组装**（对话历史 + 节点产出 → LLM 上下文）与**写侧组装**（节点处理完成 → 再组装为新的对话历史）。
> **依据**：Agent 工程源码（角色分工见文末「参考定位」）。凡结论标注证据来源，凡推演标注「设计意图 vs 未证」。

***

## 零、一句话模型

**一个** **`AgentNode`** **同时是执行单元、存储单元与「历史 ⇄ 工作流」的转换介质**。LLM 看到的「对话历史」并非单一存储，而是由两个真源经节点拼装而来：

| 真源                            | 承载什么                  | 角色           | 锚点               |
| ----------------------------- | --------------------- | ------------ | ---------------- |
| `ur_histories`                | user / assistant 累积对话 | 「对话」本体，只进历史  | `history.{seq}`  |
| `ur_nodes`（`NodeType=output`） | 节点处理产出（Tool）          | 「节点」成果，只进节点库 | `wf.{wf}.{node}` |

> **核心设计**：**节点产出（Tool 消息）不写进** **`ur_histories`，其唯一真源是** **`ur_nodes`**。读侧由读侧组装器从 `ur_nodes` 按需合成 Tool 消息，写侧由生命周期管线只把 user/assistant 落历史——这条「不重复投影」原则构成本文所有方向的地基，也是「无重复对话节点」的直接来源。

***

## 一、基础：节点的双身份与历史的三层归属

### 1.1 节点双身份（执行 + 存储）

| 身份   | 载体                                                    | 对历史 ⇄ 节点的意义                           |
| ---- | ----------------------------------------------------- | ------------------------------------- |
| 执行单元 | `FuncName` + 输入端口 `ParameterKeys` / 输出端口 `ResultKeys` | 节点是「工序」：input 喂 LLM，output 构成 Tool 消息 |
| 存储单元 | 输出写 `ur_nodes`（`NodeType=output`）+ 双写数据空间             | 节点是「成果」：产出持久可再生，读侧据此合成历史              |

### 1.2 历史的三层归属链

历史经 **history → task → node** 三家引层层归属：一个历史（会话）含多个任务，一个任务含本轮多个节点产出。归属关系由会话层建边（`cross_db_link` / `round_sequence`）。**三粒度上下文（Node / Task / History）共享同一组装点**，保证单实现、无分叉。

***

## 二、转换方向 ①：历史 + 节点产出 → LLM 上下文（读侧组装）

目标：把「用户这条消息要延续什么」喂给 LLM 执行端（answer / cline / MCP）。这一方向把两个真源拼装为一条规范消息序列。

### 2.1 组装点：`StandardContextBuilder.BuildTaskAsync`

对单任务（一次会话工作流运行），组装顺序：

1. **任务对话**：`ur_histories` 读回，仅 user/assistant，经 `MessageBinding`（`history.{seq}`，seq 单次 Build 内全局递增）投影。
2. **节点产出**：经 `cross_db_link` 拿 `GetTaskNodeKeysAsync` → 逐节点 `TryGetNodeOutputAsync` → `NodeOutputToMessages` 把每个输出端口合成一条 **Tool 消息**（`Stage=SubAgent=nodeKey`），锚点 `wf.{wf}.{node}`。

> 关键点：**节点产出的唯一来源是** **`ur_nodes`，从不二读 history**。因此同一批节点不会重复投影 → 主对话框右侧无重复对话节点（对应「写↔读闭环」）。
>
> `BuildHistoryAsync` 依任务键升序对每个 task 调用同一组装点，构成「历史=全部任务并集」的标准上下文。

### 2.2 如何进入 LLM：`PriorWire` 与种子键

组装好的规范消息序列经 wire 注册表渲染为 `conversation_context`，作为 LLM 的续聊上下文：

* `RenderPriorWireAsync`：注入 `StandardContextBuilder` 时取 **canonical**（`BuildTaskAsync`，含 `ur_nodes` output，与 UI 同源）；否则回退 `RenderWire(log.Messages)`（零回归路径）。

* `SeedWorkflow` 种子键：`system`（系统提示）/ `l1`（本轮用户文本）/ `l2`= `window`（最近窗口 `log.ToPromptText(_window)`，默认 3 条）/ `conversation_context`（canonical 全景 wire）/ `session_id | round`。

LLM 主流程不感知 collect/analyze/act——执行的哪一步由工作流 spec 决定，读侧组装照常。

***

## 三、转换方向 ②：节点处理完成 → 再组装为新的对话历史（写侧组装）

目标：一次工作流运行跑完，把「节点做了哪些事、最终答了什么」回写为可持续的对话历史。分「分层提取 → 规范映射 → 落库建边」三步。

### 3.1 分层提取：节点执行快照 → `ConversationStageInfo`

`ProcessAsync` 沿工作流链跑一次，拿到 `WorkflowRoundResult`（含 `Nodes: NodeExecutionRecord[]` + 终答 `Text`），再 `ExtractStages` 把**每个有产出端口的节点**提取为一个可折叠气泡 `ConversationStageInfo(nodeKey, subAgent, text)`。

### 3.2 规范映射：`ConversationNodeMapper.MapToConversation`

`SaveAsync` 调通用映射器把「分层气泡 + 终答」组装为规范消息序列：

```
user(round) → tool(Stage/SubAgent/round, 每个节点) → assistant(最终答)
```

### 3.3 落库建边：真源分流

`SaveAsync` 生效的关键分流：

* **仅非-Tool（user/assistant）追加进** **`ctx.Log`**（→ `ur_histories`）。

* **Tool 消息不入历史**，其真源交给 `NodeWritePipeline.PersistAsync(..., nodes)`：节点输出落 `ur_nodes`（`NodeType=output`）+ `SyncRelationsBlock` 建 `cross_db_link` / `round_sequence` 边。

* 下一轮读侧（§2）再把二者拼回同一消息序列进 LLM → **写侧只存各归其位，读侧才拼装**。

> 好处：历史只存「对话」，节点库只存「成果」；某一轮节点产出若被替换/裁剪，读侧随之变化而不污染对话时间线，实现「节点产出可被下游/跨轮复用」的前提（衔接 §六）。

***
## 四、反向投影：历史 → 节点结构（回放 / resume / 再材料化）

方向 ② 的逆：把已存消息序列（或规范消息序列）**反向重建为工作流分层节点结构**：

* `ToStages(log)` / `ToStages(messages)` → 经 `ConversationNodeMapper.ToContributions` 提取 **Tool 消息**为节点贡献（保留 `Stage/SubAgent/Round`），非 Tool / 空文本跳过。

* 两个重载走**同一条反向映射**（历史与规范消息序列单实现），供历史回放 / resume 恢复 / 再材料化为分层节点。

> **边界（设计意图 vs 未证）**：反向投影是**读重建**，不构造新的持久节点，也不驱动新执行——它服务于「把已发生的对话视为一组节点结构来理解」。真正驱动下一轮执行的仍是 `ur_nodes` 真源，而非反向投影本身。声明式「跨轮组节点」（spec 级复用）目前未接线（衔接 §六）。

***

## 五、双向闭环与设计优势

把 §2 读侧、§3 写侧、§4 反向打通，得到以节点为轴的闭环：

```
用户消息 ─► 读侧组装(ur_histories+ur_nodes) ─► LLM 工作流 ─► 节点执行快照
                                                     │
        ur_nodes(成果) ◄──落库建边── ┐          ┌──┼─ 分层提取+规范映射
        ur_histories(对话)◄─非Tool───┘          └──► SaveAsync ─► 写侧组装
                                                     │
        下一轮读侧再次拼装（复用产物、延续对话）      ▼
```

由此带来的优势：

1. **单一真相源**：节点产出只落 `ur_nodes`，`MessageBinding` 让「UI ≡ LLM」绑定同一份锚点（`history.{seq}` / `wf.{wf}.{node}`），杜绝双写分叉导致的重复/漂移。
2. **无重复投影**：读侧从不二读 history，避免同一批节点重复进入 LLM 上下文 → 上下文干净、token 受控。
3. **对话 / 成果解耦**：历史管对话延续，节点管成果复用。改节点不影响历史时间线，读侧再拼装即获新上下文。
4. **模型 / 执行中立**：编写侧走规范 `ConversationNodeMapper`，执行走 `FoldConversationRunner` 包装的 runner 端口——换 LLM / 换工作流，历史↔节点编排零改动。

## 六、衔接：与复用性 / 原子性分析的关系

本条把原文档「节点复用性与处理原子性」的核心结论压缩至此，作为节点转换的支撑（详参旧版）：

* **复用性**：存储层可复用充分成立（端口契约 + 持久存储）、运行态上下文跨轮透传成立（`conversation_context` 经 canonical `BuildTaskAsync` 含 `ur_nodes` output 喂下一轮）；**主动声明式复用在任务作用域内闭环**（跨 task 被 `cross_db_link` 隔离、跨轮声明式组节点未实现）。

* **原子性**：节点处理**数据面单库原子**（`ur_nodes` 输出 + SQL KeyMapping 同 SQLite 事务）；**关系面 / 双写面刻意放弃单事务**，转幂等写透 + 最终一致 + 对账兜底（真源 `ur_nodes` 单库原子，派生关系逐条幂等可对账）。

* **耦合**：转换越展开（历史 ↔ 节点越频繁双向），越依赖「写侧分流正确 + 读侧合成唯一」，越依赖关系面幂等对账高频正确——这是后续演进（尤其声明式跨轮复用 + 历史回放重建）必须先校验的权衡主链。
