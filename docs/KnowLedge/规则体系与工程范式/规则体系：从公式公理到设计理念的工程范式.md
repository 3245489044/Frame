## 引言：为什么需要规则体系

在 AI 辅助编程的实践中，一个根本性的矛盾始终存在：AI 需要精确、可执行的规则来约束行为，但自然语言描述的规则天然带有歧义和不确定性。当规则分散在多个文件中、以不同表述重复定义时，AI 的执行一致性就更加难以保证。

WorkFlowPrj 的 `rules/` 目录正是为解决这一矛盾而设计。它不是一份简单的"开发规范文档集"，而是一套**以公式为最小逻辑单元、以分层引用为组织方式、以可计算性为设计目标的规则工程体系**。

> **本文档是 AI 的系统提示词（System Prompt）**。AI 首次接触 WorkFlowPrj 项目时，应首先阅读本文档以理解规则体系的整体架构。本文档第六部分提供全部公式的索引（名称、类型、参数签名、用途），精确逻辑定义统一在 `rules/formulas.md` 中维护。场景化说明在各引用层文件中。

这套体系的核心信念是：**好的规则是可计算、可组合、可验证的**。当规则从自然语言进化为公式，从分散定义收敛为单一事实来源，AI 的执行就从"猜意图"变成了"算结果"。

# 第一部分：设计哲学

## 1.1 万物皆公式

规则体系的基石是 `rules/formulas.md`——它是所有规则的**唯一逻辑本体**。其他 8 个规则文件不重复定义规则逻辑，仅做引用和场景化说明。

```
┌─────────────────────────────────────────────────┐
│              formulas.md（唯一事实来源）            │
├─────────────────────────────────────────────────┤
│  §一 项目规范  → project-rules.md                │
│  §二 场景模式  → scenarios.md                    │
│  §三 性能优化  → performance-optimization.md     │
│  §四 零容忍规范 → zero-tolerance.md              │
│  §五 聚合架构  → aggregation-architecture.md     │
│  §六 文件读取  → file-reading-strategy.md        │
│  §七 上下文管理 → context-lifecycle-management.md │
│  §八 输出精简  → file-writing-strategy.md        │
└─────────────────────────────────────────────────┘
```

这种设计的直接好处是：**修改规则只需改一处**。当 `formulas.md` 中的公式更新时，所有引用它的文件自动获得最新语义，不存在"改了 A 文件忘了改 B 文件"的同步问题。

## 1.2 分层引用架构

规则体系分为三个层次，每个层次服务于不同的使用场景：

- **本体层**（`rules/formulas.md`）：所有规则的精确逻辑定义。这是唯一需要修改的地方。公式以参数→条件→输出的形式表达，消除自然语言的歧义。
- **引用层**（`rules/` 下其他 8 个 `.md` 文件）：面向场景的快速查阅。每个文件聚焦一个主题领域，列出该领域的公式名称和用途，但不重复公式逻辑。AI 可以快速了解"有哪些规则"，需要精确逻辑时再到 `formulas.md` 查阅。
- **知识层**（`docs/KnowLedge/`）：完整背景文档和设计讨论。这些文件解释规则背后的设计决策、演进历程和理论依据，帮助理解"为什么这样设计"。

三层之间的关系是：知识层解释设计动机，本体层定义精确逻辑，引用层提供快速导航。三者互补，不重复。

## 1.3 信噪比优先

规则体系自身也遵循它所定义的输出精简三定律（`WellFormed(output)` — `rules/formulas.md` §八）：

- **语义自足**：命名表达意图，结构揭示关系。公式的参数名和条件分支本身就是文档，不需要额外注释来解释"这个参数是什么意思"。
- **结构正交**：每段有且仅有一个职责。每个公式只做一件事，每个规则文件只覆盖一个主题领域。没有"万能公式"或"大而全的规则文件"。
- **表达克制**：不写入可有可无的内容。引用层文件不重复公式逻辑，只列出公式名称和用途。需要精确逻辑时，去 `formulas.md` 查阅。

# 第二部分：公式公理体系

## 2.1 公式的六种类型

`rules/formulas.md` 中的每个公式都有一个类型标签，标识其逻辑性质：

| 类型 | 标签 | 含义 | 示例 |
|------|------|------|------|
| 阈值决策 | `[TD]` | 基于阈值做二元或多元判断 | `ReadMode(S): S<50KB→direct` |
| 分类映射 | `[CM]` | 输入到输出的分类映射 | `ToolSelect(taskType): file_read→MCP_Script` |
| 条件决策 | `[CD]` | 多条件组合的决策树 | `CompactDecision(phaseChanged, moduleDone, ctx)` |
| 序列映射 | `[SM]` | 有序步骤的流程映射 | `LogAddFlow(step): 1→identify_layer` |
| 质量评估 | `[QA]` | 质量合规性检查 | `CodeQualityCheck(code): ¬emptyCatch∧...→pass` |
| 成本计算 | `[CC]` | 成本或复杂度计算 | `CalculateCost(N, R): Cost_batch(N)≈max(T_i)+R` |

这六种类型覆盖了规则工程的全部需求：判断做什么（TD/CD）、选择怎么做（CM）、按什么顺序做（SM）、做得怎么样（QA）、值不值得做（CC）。

## 2.2 公式的调用契约

每个公式遵循统一的调用契约，包含三个部分：

```
公式名(参数...) [类型]
逻辑体：条件分支 → 输出结果
参数说明：参数名=含义(类型)
```

以 `DataProcessMode` 为例（参考：`rules/formulas.md` §一）：

```
DataProcessMode(S, Ctx) [CD]
S<50KB∧Ctx≤0.7→direct · S<50KB∧Ctx>0.7→sandbox ·
S≥50KB∧Ctx≤0.7→sandbox · S≥50KB∧Ctx>0.7→sandbox_then_dump
```

这个公式接受两个参数（文件大小 S 和上下文使用率 Ctx），通过四个条件分支输出不同的数据处理模式。调用者不需要理解"为什么这样设计"，只需要按参数传入值，按输出执行即可。

## 2.3 公式间的组合关系

公式不是孤立的。它们通过输入输出相互衔接，形成可组合的决策链：

```
场景检测链（参考：rules/formulas.md §二 + rules/scenarios.md）：
  ScenarioDetect(taskDescription) → 场景类型
    → Toolchain(scene) → 工具链列表
      → 执行完毕后自动附加 [reason, record]

上下文压缩链（参考：rules/formulas.md §七 + rules/context-lifecycle-management.md）：
  CompactDecision(phaseChanged, moduleDone, ctx) → 压缩类型
    → CA(action) → 具体压缩动作

废弃处理链（参考：rules/formulas.md §一 + rules/project-rules.md）：
  HFC(projectType, hasReference) → 废弃处理动作
    → 文件标记为 D=true
      → HandleDeprecated(D, hasReference, ...) → 后续处理
```

这种组合关系的设计原则是：**每个公式的输出恰好是下一个公式的输入**。不需要额外的"胶水逻辑"来衔接，公式链本身就是可执行的流程定义。

# 第三部分：文件架构总览

## 3.1 九文件的定位与职责

| 文件 | 定位 | 引用 formulas.md | 核心内容 |
|------|------|-----------------|---------|
| `rules/formulas.md` | **唯一逻辑本体** | — | 全部公式的精确定义（8 章 30+ 公式） |
| `rules/aggregation-architecture.md` | 聚合架构设计规范 | §五 | 边界+契约+实现，三种拓扑结构 |
| `rules/context-lifecycle-management.md` | 上下文生命周期管理 | §七 | 阶段压缩/模块压缩/紧急转储 |
| `rules/file-reading-strategy.md` | 文件读取策略 | §六 | 三阶段模型（scan→preview→deep） |
| `rules/file-writing-strategy.md` | 输出精简策略 | §八 | 精简三定律 + 三问检查 |
| `rules/performance-optimization.md` | 性能优化策略 | §三 | 上下文预算控制 |
| `rules/scenarios.md` | 常用场景模式 | §二 | 场景→工具链映射 |
| `rules/zero-tolerance.md` | 零容忍规范 | §四 | 编译错误/代码质量/异常处理 |
| `rules/project-rules.md` | 项目规范 | §一 | 绝对路径/废弃文件/构建 |

每个文件只覆盖一个主题领域，职责边界清晰。AI 在遇到具体任务时，应按以下方式定位文件：

- 需要做**代码分析/重构/审查** → 先查 `rules/scenarios.md` 确定场景和工具链
- 需要**读取文件** → 查 `rules/file-reading-strategy.md`
- 需要**写入/修改代码** → 查 `rules/file-writing-strategy.md`
- 需要**管理上下文/压缩会话** → 查 `rules/context-lifecycle-management.md`
- 需要**优化性能/控制预算** → 查 `rules/performance-optimization.md`
- 需要**设计模块架构** → 查 `rules/aggregation-architecture.md`
- 需要**处理编译错误/代码质量** → 查 `rules/zero-tolerance.md`
- 需要**处理文件冲突/废弃代码** → 查 `rules/project-rules.md`
- 需要**精确的公式逻辑** → 查 `rules/formulas.md` 对应章节

## 3.2 核心规则速览

### 聚合架构

参考：`rules/aggregation-architecture.md` → `rules/formulas.md` §五

聚合的本质是 `边界 + 契约 + 实现`。三种拓扑结构可嵌套组合：

- **点聚合**：分散同类操作收敛到单一入口，适用于外部依赖和数据流边界收敛
- **线聚合**：有序步骤编排为管线，适用于流程编排和阶段式处理
- **面聚合**：模块公开能力收敛到入口面，适用于模块能力出口收敛

检测公式包括 `SCA`（创建判断）、`VB`（边界验证）、`GodAggregation`（上帝聚合检测）、`ScatteredAggregation`（分散检测）、`ImplicitAggregation`（隐式检测）、`CyclicAggregation`（循环检测）。

### 上下文生命周期

参考：`rules/context-lifecycle-management.md` → `rules/formulas.md` §七

三种压缩场景由 `CompactDecision` 统一决策：

| 触发条件 | 压缩类型 | 动作 |
|---------|---------|------|
| 阶段切换 | 阶段压缩 | 记录→更新进度→清理→（新会话）恢复 |
| 模块完成 | 模块压缩 | 记录摘要→记录注意事项→更新进度→清理 |
| Ctx > 0.9 | 紧急转储 | 直接 `attempt_completion` 清空 |

反模式包括阶段粘连、模块膨胀、过度压缩、压缩替代转储、恢复路径丢失。

### 文件读取策略

参考：`rules/file-reading-strategy.md` → `rules/formulas.md` §六

三阶段模型：`scan → preview → deep`。每个阶段只读取对应信息层次的内容：

- `scan`：只读 meta 信息（路径、大小、语言），不读内容
- `preview`：读 meta + structural 信息（类签名、函数签名），一次批量调用
- `deep`：读全部三层，但只在确认需要后执行

### 输出精简策略

参考：`rules/file-writing-strategy.md` → `rules/formulas.md` §八

精简三定律：
1. **语义自足**：命名表达意图，结构揭示关系，数据格式自描述
2. **结构正交**：每段有且仅有一个职责，职责间无重叠
3. **表达克制**：不写入可有可无的内容，不预留抽象

三问检查（`ShouldWrite`）：移除是否损失信息？是否有更简洁表达？维护成本是否超过价值？三者皆否才写入。

### 性能优化

参考：`rules/performance-optimization.md` → `rules/formulas.md` §三

上下文预算按操作类型分配：文件读取用 `partial_read`，代码执行用 `summary_only`，批量操作用 `batch_with_queries`，文档网页用 `index_no_content`。

预算按阶段分配：规划阶段较多，准备阶段中等，核心阶段最大，验证阶段少量，完成阶段不分配。

### 零容忍规范

参考：`rules/zero-tolerance.md` → `rules/formulas.md` §四

| 优先级 | 类型 | 处理方式 |
|-------|------|---------|
| P0 | 编译错误 | 立即修复，修复后必须编译通过 |
| P1 | 运行时异常 | 按失败模式选择 FailFast/FailSafe/FailGraceful |
| P2 | 代码质量警告 | 禁止空 catch、console.log、魔法数字、未使用导入、硬编码路径、TODO/FIXME |

### 场景模式

参考：`rules/scenarios.md` → `rules/formulas.md` §二

任务描述通过 `ScenarioDetect` 映射到场景类型，再通过 `Toolchain` 获取工具链，执行完毕后自动附加推理和记录知识步骤。

6 种预定义场景：代码分析、知识构建、问题解决、代码审查、性能优化、重构。

### 项目规范

参考：`rules/project-rules.md` → `rules/formulas.md` §一

路径必须使用绝对路径，禁止 `cd` 切换目录。废弃文件移至 `_deprecated/` 目录并编译排除。项目为 C# (.NET) + PowerShell + Python 混合项目。

# 第四部分：设计理念详解

## 4.1 为什么用公式而非自然语言

| 维度 | 公式 | 自然语言 |
|------|------|---------|
| **精确性** | 条件分支明确，无歧义 | 容易产生多种解读 |
| **可组合性** | 公式输出可作为另一公式输入 | 需要人工理解衔接 |
| **可验证性** | 可逐条检查条件是否满足 | 依赖主观判断 |
| **可维护性** | 修改一处公式，所有引用同步 | 多处文本需同步修改 |

公式的本质是将"意图"转化为"计算"。当 AI 面对一个决策点时，公式告诉它"输入这些参数，按这些条件判断，得到这个结果"——而不是"根据你的理解，酌情处理"。

## 4.2 为什么分层

单一事实来源（`rules/formulas.md`）确保规则的一致性，但纯公式的形式对快速查阅不友好。引用层文件的存在解决了这个问题：

- **面向场景的导航**：按主题快速定位。想知道"文件读取有什么规则"？去 `rules/file-reading-strategy.md`。
- **示例和反模式**：补充公式无法表达的上下文。公式告诉"怎么做"，示例和反模式告诉"什么情况下这么做"和"什么情况下不要这么做"。
- **降低认知负荷**：不需要每次查阅都理解全部公式。大多数时候只需要知道"有哪些规则"，不需要知道"规则的精确逻辑是什么"。

## 4.3 反模式清单

规则体系自身也需要避免以下问题：

| 反模式 | 表现 | 后果 |
|-------|------|------|
| **阶段粘连** | 不压缩直接进入下一阶段 | 上下文持续膨胀 |
| **模块膨胀** | 一个文件包含多个无关规则 | 破坏结构正交性 |
| **过度压缩** | 每步都压缩，频繁 `attempt_completion` | 反而降低效率 |
| **重复表达** | 同一规则在 formulas.md 和引用文件中重复定义 | 修改时必须同步两处 |
| **注释替代命名** | 用注释解释本应自描述的公式 | 说明公式命名不够好 |
| **预留抽象** | 为不存在的未来写入抽象层 | 增加不必要的复杂度 |

# 第五部分：使用指南

## 5.1 如何查找规则

AI 在遇到任务时，按以下流程查找规则：

1. **确定任务类型**：分析 / 构建 / 修复 / 审查 / 优化 / 重构
2. **定位场景**：在 `rules/scenarios.md` 中找到对应场景
3. **获取工具链**：通过 `Toolchain(scene)` 获取工具链列表
4. **查阅细节**：如需规则精确逻辑，到 `rules/formulas.md` 对应章节查阅公式

## 5.2 如何修改规则

1. **修改本体**：只修改 `rules/formulas.md` 中的公式定义（唯一事实来源）
2. **同步引用**：检查引用层文件是否需要同步更新
3. **验证关系**：确保公式间的组合关系仍然成立
4. **更新速览**：更新本文档中的核心规则速览部分（如涉及）

## 5.3 如何新增规则

1. **添加公式**：在 `rules/formulas.md` 对应章节添加新公式
2. **选择类型**：选择正确的公式类型标签 `[TD]` / `[CM]` / `[CD]` / `[SM]` / `[QA]` / `[CC]`
3. **定义逻辑**：定义清晰的参数和条件分支
4. **补充引用**：在对应的引用层文件中添加引用和场景化说明
5. **更新索引**：在本文档第六部分（公式索引）中添加新公式的索引条目
