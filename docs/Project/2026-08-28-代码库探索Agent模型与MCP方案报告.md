# 代码库探索 Agent：小模型方案、MCP 包装与成本报告

> 日期：2026-08-28
> 范围：ZhiLianStorage Agent —— 节点（ur_nodes）层面引入分类/小模型替代 LLM、代码库信息收集生成节点、包装为 MCP、成本与本地硬件测算
> 说明：云端单价为 2026-08 各厂商公开报价（来源见 §9）；本地占用为理论估算，实际以量化与运行环境为准。成本测算基准为「约 1000 文件的中型仓库一次全量扫描」。

---

## 1. 背景与目标

现有 Agent 的核心耗点是「LLM 主动翻阅代码库」：每轮把对话历史解析为工作流节点、由大模型决定读哪个文件、抽什么信息，token 消耗大且路径不可控。

目标：**在节点（ur_nodes）层面用小模型 + 确定性逻辑替代部分 LLM 功能**，实现与「LLM 主动翻代码库」等价的能力，但成本降到近零、路径确定可控，并将整条链路包装为可复用的 MCP。

三层目标：
1. **节点处理增强**：对已有节点（guard_input / provide_prompt / rule_match 等）用分类/嵌入/重排模型增强，不碰框架主循环。
2. **代码库 → 节点生成**：不用 RAG，用「目标驱动的探索工作流」主动收集代码库信息、解析为语义节点与引用边。
3. **MCP 化 + 成本可控**：包装为 MCP 服务器，给出云端/本地两条部署路径的成本与硬件测算。

---

## 2. 现有 Agent 调用路径与节点层

调用路径：外部宿主 → 入口 Shell → 组合根 → 任务池/编排器 → 循环引擎 → 单轮骨架 → LLM 执行端。

节点两种形态：

| 形态 | 说明 |
|---|---|
| 工作流节点 | `guard_input` / `provide_prompt` / `cline_execute` / `rule_match` / `guard_output`，由 `WorkflowRunner` + `RoundStepInvoker` 按 FuncName 分发执行 |
| SQL 节点 | `ur_nodes` 表，`NodeKey / NodeType / PayloadJson`，由 `NodeStore` 门面幂等写入，引用边落 LiteDB 图 |

关键落点：
- [NodeStore.cs](file:///workspace/ZhiLianStorage/Projects/Agent/src/Agent.Core/Nodes/NodeStore.cs) —— 节点单一门面（BuildNode → ResolveInputs → Execute → Persist）。
- [RoundStepInvoker.cs](file:///workspace/ZhiLianStorage/Projects/Agent/src/Agent.Core/Nodes/RoundStepInvoker.cs) —— 按 FuncName 分发步骤，新函数在此注册。
- [NodeTaskLinker.cs](file:///workspace/ZhiLianStorage/CsharpPrj/Operation/HierarchyMethod/Nodes/Linkage/NodeTaskLinker.cs) —— task → node 建边，LLM-free。

## 3. 节点层可引入的模型与映射

按「节点步骤 → 可替代模型 → 部署位置」映射（不引入框架改动）：

| 节点步骤 | 可引入模型 | 用途 | 部署 |
|---|---|---|---|
| guard_input（意图识别） | nli-MiniLM2-L6-H768 等蕴含/分类模型 | 输入意图分类、护栏判定 | 本地 CPU |
| rule_match（决策） | DecisionWordClassifier（确定性规则） | 决策词 → continue/stop/error | 无模型 |
| provide_prompt（上下文供给） | BAAI/bge-* 嵌入 + bge-reranker-v2-m3 重排 | 语义检索、候选裁剪 | 本地/GPU |
| 节点摘要/描述 | qwen2.5:0.5b / llama3.2:1b/3b | 代码块→一句话摘要 | 本地 CPU/GPU |
| 节点关系/图 | node2vec / MetaPath2Vec / GraphSAGE | 图嵌入、关系强度 | CPU |

要点：
- **分类与决策词**替代「每轮都问大模型」的判定，确定性、零成本。
- **嵌入 + 重排**只在需要语义召回时启用，替代 LLM 通读全库。
- **小生成模型**只做「有界摘要」，不承担推理与规划。

## 4. 代码库探索 Agent（explore-loop 工作流）

非 RAG，是「LLM 主动翻代码库」的结构化平替。复用 `WorkflowRunner` 与主循环（决策词驱动 continue/stop），以自定义 RoundSpec 循环工作流承载：

```
locate_entry（找入口）→ read_unit（读单元/文件）→ collect_node（生成节点）
    → coverage_check（覆盖率检查）→ follow_edges（沿引用边扩散）→ loop
```

- `locate_entry` / `read_unit`：确定性 AST/符号解析，零成本。
- `collect_node`：写入 ur_nodes，复用 NodeStore 幂等 upsert + NodeTaskLinker 建边。
- `coverage_check` / `follow_edges`：图遍历 + 覆盖率判定（决策词/分类模型控制是否继续）。
- 语义增强：对节点内容做 embedding，查询时 rerank 精排。

## 5. MCP 包装方案

仓库已有 [节点发现精炼MCP设计.md](file:///workspace/ZhiLianStorage/docs/analysis/2026/8/8.23/节点发现精炼MCP设计.md)（`node-discovery`，挂 `TypeScriptPrj/TsWorkspace/MCPBridge`）。本方案新增 `codex-explore` MCP，同一桥接、同一注册方式（见 [mcp-servers.json](file:///workspace/ZhiLianStorage/Projects/Agent/Config/mcp-servers.json)）。

| 工具 | 对应工作流步骤 | 模型/逻辑 |
|---|---|---|
| `explore_scan` | locate_entry → read_unit → collect_node | 确定性解析（AST/符号提取），0 成本 |
| `explore_embed` | collect_node 后节点向量化 | bge-small-zh / text-embedding-v4 |
| `explore_query` | provide_prompt 语义召回 | embedding + bge-reranker 重排 |
| `explore_summarize` | 节点描述生成 | qwen2.5:0.5b / qwen-turbo |
| `explore_route` | guard_input / rule_match | 分类模型 + DecisionWordClassifier |
| `explore_edge` | follow_edges / coverage_check | node2vec 图嵌入 + NodeTaskLinker 建边 |

接入原则：**不改框架主循环**。复用 `RoundStepInvoker` 注册新 FuncName，写入走 `NodeStore` 门面；与既有 `node-discovery` MCP 平级注册、可独立开关。

## 6. 成本测算

### 6.1 云端单价（2026-08 公开报价）

| 用途 | 模型 | 单价 |
|---|---|---|
| 嵌入 | text-embedding-v4 | 0.5 元/百万 tok（批量 0.25）；qwen3.7-text-embedding-flash 0.125 元/百万 |
| 重排 | qwen3-rerank | 0.5 元/百万 tok |
| 摘要小 LLM | qwen-turbo | 0.3 元/百万输入 / 0.6 元/百万输出 |
| 主 LLM 兜底（可选） | deepseek-v4-flash | 输入（缓存未命中）1.5–3 元/百万；缓存命中 0.05–0.1 元/百万；输出 4.5–9 元/百万（高峰价，空闲半价） |

### 6.2 一次全量扫描（≈1000 文件）成本拆解

| 阶段 | token 量 | 云端 API | 本地 |
|---|---|---|---|
| 解析 / AST 遍历 | 无模型 | 0 元 | 0 元 |
| 节点向量化 | ≈0.5M | 0.25 元（v4，批量 0.125） | 0 元 |
| 语义检索 + 重排 | ≈1M | 0.5 元 | 0 元 |
| 节点摘要 · 小 LLM | ≈0.5M | 0.17 元（qwen-turbo） | 0 元 |
| 主 LLM 兜底（可选） | ≈0.5M | ≈1 元（flash 空闲） | 0 元 |
| **合计** | — | **≈2 元**（核心组合 ≈1 元） | **0 元** |

- 核心组合（向量化 + 重排 + 小模型摘要）≈ **1 元/次**；含主 LLM 兜底 ≈ **2 元/次**。
- 日常增量 / 单次问答：云端 **0.01–0.05 元/次**。
- 分类 / 决策词 / 图嵌入均为确定性或本地推理，API 成本为 0。

## 7. 本地部署硬件需求（同时运行）

### 7.1 各模型占用（fp16 / Q4 量化估算）

| 模型 | 参数 | 占用 | 运行位置 |
|---|---|---|---|
| nli-MiniLM2-L6-H768（分类） | 22M | ~0.05GB | CPU |
| DecisionWordClassifier（决策词） | 规则 | 0 | 无模型 |
| BAAI/bge-small-zh-v1.5（嵌入） | 24M | ~0.1GB | CPU |
| BAAI/bge-base-zh-v1.5 | 102M | ~0.2GB | CPU |
| GTE-Chinese-Large | ~326M | ~0.7GB | CPU/GPU |
| BAAI/bge-m3（嵌入·强） | 568M | ~1.2GB | GPU 推荐 |
| BAAI/bge-reranker-v2-m3（重排） | 568M | ~1.2GB | GPU 推荐 |
| qwen2.5:0.5b（摘要） | 0.5B | ~0.5GB | CPU/GPU |
| llama3.2:3b（摘要/兜底） | 3B | ~2.0GB | GPU 推荐 |
| node2vec/GraphSAGE（图嵌入） | — | ~0.3GB（1000 节点） | CPU |

全套常驻 ≈ **5GB 显存**（bge-m3 + reranker + 3B + 0.5B + 小模型）。

### 7.2 三档硬件配置

| 档位 | 硬件 | 常驻模型 | 占用 | 全量扫描 | 单次查询 | 定位 |
|---|---|---|---|---|---|---|
| 纯 CPU 入门 | 8 核 CPU + 16G 内存 | bge-small + 0.5B + 分类 | ≈1G | 30–60 分钟 | 1–3 秒 | 旧机起步 |
| GPU 中配（推荐） | RTX 3060 12G + 16G 内存 | bge-m3 + reranker + 3B + 0.5B | ≈5G | 5–10 分钟 | <1 秒 | 体验/成本最佳平衡 |
| GPU 高配 | RTX 3090/4090 24G | 全部 + 7B–14B 兜底余量 | ≈6G+ | 分钟级 | 亚秒·高并发 | 大仓库/团队 |

### 7.3 实现与注意事项

- 常驻方式：Ollama（`OLLAMA_KEEP_ALIVE`）常驻小 LLM；embedding/rerank 用 `sentence-transformers` 或 vLLM 起服务；分类/图嵌入为普通 Python 进程。总量 ≤ 显存/内存即全常驻，超出按需换载。
- 纯 CPU 档建议跳过 bge-m3 与 reranker-v2-m3（1.2GB×2 最重），改用 bge-small 检索、必要时 bge-reranker-base。
- 图嵌入开销被高估：1000 节点、128 维仅 ~0.5MB 参数，CPU 秒级训练；真正吃内存的是引用图与库本身。
- 系统内存建议 ≥16GB（GPU 推理也要同时跑 SQLite ur_nodes + LiteDB 引用图 + 代码解析）。

## 8. 结论与建议

1. **成本**：全本地部署 API 成本为 0（仅一次性硬件）；云端全量扫描约 1–2 元/次，日常近 0。小模型组合使「主动翻代码库」从按 token 计费变成确定性 + 本地推理。
2. **部署**：单仓库探索用「纯 CPU + 常驻 bge-small/0.5B」即可 0 成本运转；追求交互体验（<1s）上 8–12GB 显存 GPU 中配（推荐档）。
3. **架构**：MCP 化不改框架，`codex-explore` 与既有 `node-discovery` 平级注册；语义检索仅在需要召回时启用，其余步骤走确定性逻辑。
4. **建议下一步**：落地 `codex-explore` 的 `tools-definitions/*.json` 工具定义与 `explore-loop.json` 工作流骨架（本报告仅设计，未落代码）。
