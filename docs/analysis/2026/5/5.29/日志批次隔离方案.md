# 日志批次隔离方案

## 一、问题分析

### 1.1 当前问题
日志长期存储在数据库中，但不同批次的日志完全混在一起，无法区分：
- 多次运行的日志条目在同一个表中混杂
- 无法按运行批次查询、对比
- 无法追溯某次特定运行的完整日志

### 1.2 根本原因
日志系统（`Common.Diagnostics`）在设计时没有"批次"概念：
- `LogEntry` 没有批次标识字段
- `LogRepository` 没有按批次隔离的存储机制
- 数据库存储将所有日志写入同一张表

## 二、解决方案架构

### 2.1 总体设计

```
┌─────────────────────────────────────────────────────────────────┐
│                        交互启动.bat / CLI启动.bat                 │
│  (启动时生成 BatchId → 设置环境变量 LOG_BATCH_ID)                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  BatchRouter (Common.Diagnostics)                               │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  BatchSelector: 从环境变量/参数获取当前 BatchId            │  │
│  │  SqliteIsolatedStorage: 按 BatchId 分表存储               │  │
│  │  BatchMetadata: 批次元数据管理                             │  │
│  └───────────────────────────────────────────────────────────┘  │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  UniversalReference (BatchIntegration)                          │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  BatchRegistry: 将批次注册为 Resource                      │  │
│  │  BatchChangeTracker: 利用 ReferenceTrackingCore 对比差异   │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 核心组件

#### 2.2.1 BatchRouter（日志层 - 已实现）
- **位置**: `BasicMethod/Logging/BatchRouter.cs`
- **职责**: 在数据层面按批次隔离日志存储
- **核心机制**:
  - `BatchSelector`: 从环境变量 `LOG_BATCH_ID` 获取当前批次 ID
  - `SqliteIsolatedStorage`: 按 `BatchId` 分表存储（表名格式: `logs_{BatchId}`）
  - `BatchMetadata`: 记录批次元数据（开始时间、来源、状态等）
- **使用方式**: 单例模式 `BatchRouter.Instance`

#### 2.2.2 BatchRegistry（集成层 - 已实现）
- **位置**: `BasicMethod/UniversalReference/BatchIntegration/BatchRegistry.cs`
- **职责**: 将批次注册为 UniversalReference 资源
- **核心功能**:
  - `RegisterBatchAsync()`: 将批次注册为 Resource（类型: "Batch"）
  - `UpdateBatchAsync()`: 更新批次元数据
  - `LinkBatchesAsync()`: 建立批次间引用关系
  - `GetBatchDependenciesAsync()`: 获取批次依赖链
  - `GetAllBatchMetadataAsync()`: 获取所有批次元数据

#### 2.2.3 BatchChangeTracker（分析层 - 已实现）
- **位置**: `BasicMethod/UniversalReference/BatchIntegration/BatchChangeTracker.cs`
- **职责**: 利用 ReferenceTrackingCore 对比两个批次的日志差异
- **核心功能**:
  - `CompareBatches()`: 完整变更报告
  - `CompareBatchesSummary()`: 简化差异统计（按级别/类别分组）
  - `CompareBatchesById()`: 从 BatchRouter 获取数据后对比

### 2.3 数据流

```
启动批次:
  交互启动.bat → 设置 LOG_BATCH_ID=guid → 启动 Launcher
  → Logger 写入 → BatchRouter 拦截 → SqliteIsolatedStorage 按 BatchId 分表
  → 批次结束时 → BatchRegistry.RegisterBatchAsync() 注册到 UniversalReference

查询批次:
  LogViewer.ps1 → 读取 logs_{BatchId} 表 → 按批次展示

对比批次:
  BatchChangeTracker.CompareBatches(batchA, batchB)
  → DiscreteChangeCalculator 计算差异
  → 返回 ChangeReport<LogEntry>
```

## 三、使用方式

### 3.1 启动时指定批次
```batch
:: 自动生成 BatchId
set LOG_BATCH_ID=auto
启动程序.exe

:: 手动指定 BatchId（用于关联上下游）
set LOG_BATCH_ID=workflow-run-2026-05-24-001
启动程序.exe
```

### 3.2 代码中使用
```csharp
// 获取当前批次的所有日志
var logs = BatchRouter.Instance.GetAllFromBatch(currentBatchId);

// 注册批次到 UniversalReference
var registry = new BatchRegistry(refManager);
await registry.RegisterBatchAsync(metadata);

// 对比两个批次
var tracker = new BatchChangeTracker();
var diff = tracker.CompareBatchesById("batch-001", "batch-002");
Console.WriteLine(diff.ToString());
```

### 3.3 日志查看
```powershell
# 进入交互式日志查看器（支持按批次筛选）
.\运行测试GUI模式.ps1 --log

# 直接查看指定批次的 ERROR 日志
.\运行测试GUI模式.ps1 --log "batch batch-001 level ERROR"
```

## 四、与 UniversalReference 的集成

### 4.1 资源模型
每个批次作为 UniversalReference 的一个 Resource：
- `ResourceType = "Batch"`
- `Id = BatchId`
- `Name = 批次名称`
- `Metadata`: 包含开始时间、结束时间、来源、状态、日志统计等

### 4.2 引用关系
批次间可以建立引用关系：
- `Dependency`: 批次 A 依赖批次 B（如：测试批次依赖构建批次）
- `Sequence`: 批次 A 在批次 B 之后运行
- `Derived`: 批次 A 由批次 B 派生

### 4.3 查询能力
- 按时间范围查询批次
- 按来源查询批次
- 查询批次依赖链
- 查询批次变更差异

## 六、设计原则

1. **最小侵入**: 底层 `LogEntry`/`LogRepository`/`Logger` 完全不需要改动
2. **向后兼容**: 不设置 `LOG_BATCH_ID` 时，行为与原来完全一致
3. **渐进增强**: 批次功能按需启用，不影响现有功能
4. **可追溯**: 每个批次都有完整元数据，支持溯源
5. **可对比**: 利用 ReferenceTrackingCore 的离散变化计算能力
