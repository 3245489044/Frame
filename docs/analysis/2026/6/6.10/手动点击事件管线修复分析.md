# 手动点击事件管线修复分析

## 问题现象

用户在 GUI 模式下点击 `addButton` 按钮时，日志显示 `[OK] addButton.click`，但计算结果始终为 `0`（默认值），而非正确的两数之和。

## 根因分析

### 直接原因：`IEventPipelineExecutor.Execute` 未设置 `CurrentCommand`

**文件：** `FileDriven/FileDriven.Pipeline/PipelineEntry.cs`（第343-354行）

```csharp
var context = new FileDrivenPipelineContext
{
    // ★★★ 缺少：CurrentCommand = ???
    ParsedTarget = controlName,       // "addButton"
    ParsedAction = eventType,         // "click"
    ...
};
```

`ParseCommandStage.CanExecute` 检查的是：

```csharp
return !string.IsNullOrWhiteSpace(context.CurrentCommand);
```

由于 `CurrentCommand` 为 `null`，`CanExecute` 返回 `false`。

### 问题链路

```
IEventPipelineExecutor.Execute("addButton", "click")
  → context.CurrentCommand = null
  → pipeline.Execute(context)
    → StagePipeline.ExecuteAsync 遍历各阶段：
      → ParseCommandStage.CanExecute = false
        → 标记为成功（跳过） ← StagePipeline 对 CanExecute=false 的处理
      → FindBindingStage.CanExecute = false（IsEventCommand 检查 ParsedCommand）
        → 标记为成功（跳过）
      → ExtractValuesStage.CanExecute = false
        → 标记为成功（跳过）
      → ExecuteFunctionStage.CanExecute = false
        → 标记为成功（跳过）
      → WriteResultStage.CanExecute = false
        → 标记为成功（跳过）
  → TryGetError 检查所有阶段 → 全部成功 → 输出 [OK]
  → 返回 true（但函数从未执行，结果始终为 0）
```

### 关键机制：`StagePipeline` 对 `CanExecute=false` 的处理

**文件：** `Share/Pipeline/Core.cs`（第1231-1236行）

```csharp
if (!stage.CanExecute(context))
{
    // 条件不满足时标记为跳过（视为成功）
    context.SetStageResult(stage.Name, true);
    continue;
}
```

当 `CanExecute` 返回 `false` 时，阶段被标记为**成功**（视为跳过）。这是合理的设计（允许阶段条件性跳过），但在此场景中掩盖了 `CurrentCommand` 未设置的问题——所有阶段都被静默跳过，没有任何错误提示。

### 间接原因：`ExtractValuesStage` 对 click 的特殊处理

**文件：** `Share/CommandFramework/Pipeline/Stages/ExtractValuesStage.cs`（第48-73行）

旧代码中 click 命令直接返回空字典：

```csharp
if (action == "click")
{
    context.ExtractedValues = new Dictionary<string, string?>();
    context.SetStageResult(Name, true);
    return Task.CompletedTask;
}
```

这导致即使管线正常执行，click 命令也不会从绑定的 `inputs`（`num1TextBox`、`num2TextBox`）中提取值，函数执行时参数为空。

**但此问题被直接原因掩盖**——即使修复了 `ExtractValuesStage`，由于管线根本不执行，问题依然存在。

## 修复方案

### 修复1（关键）：设置 `CurrentCommand`

**文件：** `FileDriven/FileDriven.Pipeline/PipelineEntry.cs`

```csharp
var context = new FileDrivenPipelineContext
{
    // ★ 修复：设置 CurrentCommand，让 ParseCommandStage 能正常解析命令
    CurrentCommand = $"{controlName}.{eventType}",
    BindingResolver = _bindingResolver,
    FunctionExecutor = _functionExecutor,
    LoadedConfigs = new Dictionary<string, object>(_loadedConfigs, StringComparer.OrdinalIgnoreCase),
    TargetForm = targetForm,
    Mode = targetForm != null ? "GUI" : "Unknown"
};
```

同时移除了冗余的便捷属性设置（`ParsedTarget`、`ParsedAction`、`IsNonEventCommand`、`ParseSuccess`），因为这些值会在 `ParseCommandStage` 执行后被正确填充。

### 修复2（辅助）：`ExtractValuesStage` 删除 click 早期返回

**文件：** `Share/CommandFramework/Pipeline/Stages/ExtractValuesStage.cs`（第70-73行）

已删除 click 命令的早期返回逻辑，click 命令走通用的值提取逻辑——从 `context.BoundInputs` 中读取控件名称列表，通过 `ExecuteForMode` 从真实控件（GUI 模式）或虚拟存储（CLI 模式）中提取值。

## 修复后的完整链路

```
IEventPipelineExecutor.Execute("addButton", "click")
  → CurrentCommand = "addButton.click"
  → pipeline.Execute(context)
    → ParseCommandStage:
      CanExecute = true（CurrentCommand 不为空）
      ExecuteCoreAsync: 解析 "addButton.click"
      → ParsedCommand = { Target="addButton", Action="click" }
    → FindBindingStage:
      CanExecute = true（IsEventCommand 通过）
      ExecuteCoreAsync: 查找 addButton.click 的绑定
      → BoundFunctionName = "MathLibrary.Plus"
      → BoundInputs = ["num1TextBox", "num2TextBox"]
      → BoundOutputTarget = "outputTextBox"
    → ExtractValuesStage:
      CanExecute = true
      ExecuteCoreAsync: GUI 模式，action="click" → 走通用逻辑
      → 从 TargetForm 的 num1TextBox 读取值 "10"
      → 从 TargetForm 的 num2TextBox 读取值 "20"
      → ExtractedValues = { "num1TextBox"="10", "num2TextBox"="20" }
    → ExecuteFunctionStage:
      CanExecute = true
      ExecuteCoreAsync: 调用 MathLibrary.Plus({a=10, b=20})
      → FunctionResultValue = 30
    → WriteResultStage:
      CanExecute = true
      ExecuteCoreAsync: 将 30 写入 outputTextBox
  → TryGetError 检查 → 无错误
  → 输出 [OK] addButton.click
  → 返回 true
```

## 经验教训

1. **`StagePipeline` 的 `CanExecute` 跳过机制**：当阶段被条件性跳过时，会被标记为成功。这是合理的设计，但调试时容易被忽略——"成功"不等于"已执行"。

2. **日志误导**：`[OK] addButton.click` 日志仅表示 `TryGetError` 检查通过，不代表函数已执行。需要结合阶段级调试日志（`CommandLoopSkeleton_ExecuteCore_stage_debug`）综合判断。

3. **两层问题的叠加效应**：`ExtractValuesStage` 的 click 特殊处理是框架层的缺陷，`CurrentCommand` 未设置是应用层的缺陷。两个缺陷叠加导致问题难以定位——修复任何一个都无法单独解决问题。
