# 日志系统优化方案

## 问题背景

加载 `MathFunctions.json` 时出现错误：

```
[ERROR] Failed to load config: ...MathFunctions.json - JsonConfigService.LoadConfigAsync returned null
[DIAG] 可能原因: 1) 模板预处理失败(检查 TempletConfig 目录) 2) 反序列化失败(检查 UIConfiguration 模型匹配)
```

但控制台没有输出任何预处理失败的具体原因，导致无法定位问题。

## 根因分析

### 日志链路

```
FileDrivenLogPlaceholderHandler.Log("msgId", params)
  → LogPlaceholderHandlerBase.Log(msgId, moduleName, keyPrefix, params)
    → PlaceholderLogHelper.Log(level, category, module, message)
      → LogRepository.Write(logEntry)
```

### `LogRepository.Write` 的行为

```csharp
public static void Write(LogEntry entry)
{
    if (OutputMode == LogOutputMode.Console)
    {
        // Console 模式：通过 LogCollapser 折叠打印到控制台
        var formatted = $"[{entry.Timestamp:HH:mm:ss.fff}] [{entry.Level}] [{entry.Module}] {entry.Message}";
        LogCollapser.Write(formatted);
        return;
    }

    // Database 模式（默认）：只写入内存仓库，不打印到控制台
    // ...
}
```

### 根本原因

**`CliOptions.LogOutputMode` 的默认值是 `LogOutputMode.Database`。**

```csharp
// FileDriven/FileDriven.Utilities/CLI/CliOptions.cs
public LogOutputMode LogOutputMode { get; set; } = LogOutputMode.Database;
```

当 `OutputMode == Database` 时，`LogRepository.Write` 只将日志写入内存仓库（后续刷入 SQLite），**不打印到控制台**。

所以 `PreprocessConfig`、`JsonTemplateProcessor.Process`、`CreateReferencePreprocessor` 中的 `FileDrivenLogPlaceholderHandler.Log` 调用虽然正常执行了，但日志只进入了内存仓库，控制台看不到。

### 为什么 `[DIAG]` 前缀的日志能打印？

`[DIAG]` 前缀的日志是通过 `Console.WriteLine` 直接输出的，不经过 `LogRepository`，所以不受 `OutputMode` 影响。

## 优化方案

### 方案一：修改默认 OutputMode（推荐）

将 `CliOptions.LogOutputMode` 的默认值从 `Database` 改为 `Console`，使日志系统默认打印到控制台。

**修改文件：** `FileDriven/FileDriven.Utilities/CLI/CliOptions.cs`

```csharp
// 修改前
public LogOutputMode LogOutputMode { get; set; } = LogOutputMode.Database;

// 修改后
public LogOutputMode LogOutputMode { get; set; } = LogOutputMode.Console;
```

**优点：**
- 改动最小，只改一行
- 所有 `FileDrivenLogPlaceholderHandler.Log` 的日志都会自动打印到控制台
- 不需要在每处调用点加 `Console.Error.WriteLine`

**缺点：**
- 默认不再写入内存仓库，`Shutdown` 时不会刷入 SQLite
- 但可以通过 `--log-mode database` 命令行参数切换回 Database 模式

### 方案二：在 SetupLogging 中根据模式设置 OutputMode

如果 GUI 模式需要 Database 模式（刷入 SQLite），CLI 模式需要 Console 模式，可以在 `SetupLogging` 中根据运行模式设置。

**修改文件：** `FileDriven/FileDriven.Launcher/FileDrivenBootstrapper.cs`

```csharp
private static void SetupLogging(CliOptions options)
{
    // ★ 如果用户没有显式指定 --log-mode，则根据运行模式自动选择
    if (!options.IsLogModeExplicitlySet)
    {
        options.LogOutputMode = options.ShouldRunGuiMode() 
            ? LogOutputMode.Database   // GUI 模式：刷入 SQLite
            : LogOutputMode.Console;   // CLI 模式：打印到控制台
    }
    
    LoggingManager.Setup(options);
}
```

**优点：**
- CLI 模式默认打印到控制台，方便调试
- GUI 模式默认刷入 SQLite，保持数据持久化
- 用户仍可通过 `--log-mode` 参数覆盖

**缺点：**
- 需要修改 `CliOptions` 类，添加 `IsLogModeExplicitlySet` 标志

### 方案三：提升关键日志级别 + 保持 Database 模式

如果希望保持 Database 模式（所有日志都刷入 SQLite），同时让关键错误日志也能打印到控制台，可以在 `LogRepository.Write` 中增加逻辑：**Error 级别的日志无论什么模式都打印到控制台**。

**修改文件：** `BasicMethod/Logging/LogRepository.cs`

```csharp
public static void Write(LogEntry entry)
{
    if (!Enabled) return;

    if (OutputMode == LogOutputMode.Console)
    {
        var formatted = $"[{entry.Timestamp:HH:mm:ss.fff}] [{entry.Level}] [{entry.Module}] {entry.Message}";
        LogCollapser.Write(formatted);
        return;
    }

    // ★ Database 模式下，Error 级别的日志也打印到控制台
    if (entry.Level is "ERROR" or "Error")
    {
        var formatted = $"[{entry.Timestamp:HH:mm:ss.fff}] [{entry.Level}] [{entry.Module}] {entry.Message}";
        LogCollapser.Write(formatted);
        // 继续写入内存仓库，不 return
    }

    // Database 模式：写入内存仓库
    // ...
}
```

**优点：**
- 保持 Database 模式不变
- Error 级别的日志自动打印到控制台
- 不需要修改调用方代码

**缺点：**
- 修改了底层日志仓库，影响范围较大

## 推荐方案

**方案一**（修改默认 OutputMode）最简单直接，改动最小。

如果担心 Database 模式的持久化需求，可以采用**方案二**（根据运行模式自动选择）。

## 实施记录

### 第一阶段：方案一 + 方案二（组合优化）

| 步骤 | 修改文件 | 修改内容 | 状态 |
|------|----------|----------|------|
| 1 | `FileDriven/FileDriven.Utilities/CLI/CliOptions.cs` | 添加 `IsLogModeExplicitlySet` 属性，在 `--log-mode` 解析时标记 | ✅ |
| 2 | `FileDriven/FileDriven.Launcher/FileDrivenBootstrapper.cs` | `SetupLogging` 中根据运行模式自动选择：GUI→Database，CLI→Console | ✅ |
| 3 | `BasicMethod/Logging/LogRepository.cs` | 统一 `OutputMode` 默认值为 `Console`，与 `CliOptions` 保持一致 | ✅ |

### 第二阶段：统一输出通道（LogWritten 事件）

**问题：** 结构化日志（通过 `FileDrivenLogPlaceholderHandler.Log` 调用）只输出到 Console，**不会显示在 UI 的 `_outputTextBox` 中**。UI 控制台只能显示通过 `logAction` 委托传递的日志。

**方案：** 在 `LogRepository.Write()` 中增加 `LogWritten` 静态事件，让 `MainForm` 订阅后将结构化日志也显示到 UI 控制台。

| 步骤 | 修改文件 | 修改内容 | 状态 |
|------|----------|----------|------|
| 1 | `BasicMethod/Logging/LogRepository.cs` | 添加 `LogWritten` 静态事件，在 `Write()` 中触发 | ✅ |
| 2 | `FileDriven/FileDriven.UI/Core/MainForm.cs` | 在 `OnRootContainerLoaded` 中订阅 `LogWritten` 事件，添加 `OnLogWritten` 处理方法 | ✅ |
| 3 | `FileDriven/FileDriven.UI/Core/MainForm.cs` | 在 `Dispose` 中取消订阅 `LogWritten` 事件，防止事件泄漏 | ✅ |

**效果：** 所有通过 `FileDrivenLogPlaceholderHandler.Log` 调用的结构化日志，现在都会实时显示到 UI 控制台。

### 行为变更

| 场景 | 旧行为 | 新行为 |
|------|--------|--------|
| CLI 模式（默认） | 日志写入内存仓库，控制台不可见 | 日志打印到控制台，方便调试 |
| GUI 模式（默认） | 日志写入内存仓库，控制台不可见 | 日志写入内存仓库，刷入 SQLite |
| `--log-mode console` | 强制 Console 模式 | 强制 Console 模式（不变） |
| `--log-mode database` | 强制 Database 模式 | 强制 Database 模式（不变） |
| **结构化日志在 UI 控制台** | ❌ 不显示 | ✅ 通过 `LogWritten` 事件实时显示 |

## 预期效果

采用方案一后，控制台将输出类似以下内容：

```
[23:03:52.000] [INFO] [FileDriven] [JsonConfigService] PreprocessConfig 开始: configPath=...MathFunctions.json, fileExists=True
[23:03:52.001] [INFO] [FileDriven] [PreprocessConfig] baseDir=...TempletConfig, stylesExists=True, compositesExists=True
[23:03:52.002] [INFO] [FileDriven] [PreprocessConfig] 即将调用 JsonTemplateProcessor.Process, configPath=...MathFunctions.json
[23:03:52.003] [ERROR] [FileDriven] [JsonTemplateProcessor] 预处理委托返回 null: path=...MathFunctions.json
[23:03:52.004] [ERROR] [FileDriven] [PreprocessConfig] 预处理失败: configPath=...MathFunctions.json, reason=JsonTemplateProcessor.Process 返回 null
[23:03:52.005] [ERROR] [FileDriven] 配置文件预处理失败: ...MathFunctions.json
```

这样用户可以直接从控制台看到**具体在哪一步失败**以及**失败原因**，无需再猜测。
