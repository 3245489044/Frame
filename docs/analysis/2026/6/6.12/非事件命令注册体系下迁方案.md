# 非事件命令注册体系下迁方案

> 分析 CommandFramework（Share 层）与 FileDriven（FileDriven 层）中两套平行的非事件命令注册逻辑，制定下迁方案消除重复。

---

## 1. 现状分析

### 1.1 两套注册体系总览

```
┌─────────────────────────────────────────────────────────────────┐
│                   体系 A：CommandFramework (Share 层)              │
│                                                                   │
│  Registration/Registries.cs                                       │
│  ├── CommandRegistry         工厂模式，延迟创建 ICommand 实例      │
│  ├── EngineCommandRegistry   键值映射，管理 CommandEngine 注册     │
│  └── HandlerRegistry         处理器注册表，命令名→处理函数映射     │
│                                                                   │
│  Execution/                                                    │
│  ├── CommandEngine.cs         持有 EngineCommandRegistry           │
│  └── NonEventCommandHandler   持有 HandlerRegistry                │
│                                                                   │
│  CommandParser.cs                                                 │
│  └── DefaultNonEventCommands  静态 HashSet<string>                │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│             体系 B：FileDriven (FileDriven 层)                     │
│                                                                   │
│  FileDriven.Pipeline/Core/                                        │
│  ├── NonEventCommandRegistry.cs  单例注册中心                      │
│  │   └── BindingRegistration     绑定注册来源记录                  │
│  ├── NonEventCommands.cs         命令名称集中定义                  │
│  └── SideloadRetryPolicy         级联失败重试策略                  │
│                                                                   │
│  FileDriven.Execution/Command/                                    │
│  ├── Skeletons/NonEventCommandHandler.cs  实际处理逻辑             │
│  └── PipelineFactory.cs                  注册所有内置命令          │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 重复点详细对比

#### 重复 1：非事件命令名称列表（三处维护同一份数据）

| 位置 | 定义方式 | 内容 |
|------|----------|------|
| `CommandParser.DefaultNonEventCommands` | `static readonly HashSet<string>` | load, close, echo, sleep, show, look, wait, assert, discover, list, validate, exit, sideload |
| `NonEventCommands._commands` | `static readonly HashSet<string>` | 同上（完全一致） |
| `NonEventCommandRegistry._handlers` | `ConcurrentDictionary` | 同上（通过 Register() 动态添加） |

**问题**：`CommandParser.DefaultNonEventCommands` 和 `NonEventCommands._commands` 没有任何强制同步机制。虽然 `NonEventCommandRegistry.Register()` 会同时同步到两者，但直接修改 `CommandParser.DefaultNonEventCommands` 时 `NonEventCommands` 不会感知。

#### 重复 2：非事件命令处理器（两个独立的 Handler 类）

| 类 | 项目 | 注册表 | 处理函数签名 |
|----|------|--------|-------------|
| `CommandFramework.Execution.NonEventCommandHandler` | Share.CommandFramework | `HandlerRegistry` | `Func<ParsedCommand, Task<CommandExecutionResult<object?>>>` |
| `FileDriven.Execution.Command.Skeletons.NonEventCommandHandler` | FileDriven.Execution | `NonEventCommandRegistry` | `Action<object?>`（运行时转型为 FileDrivenPipelineContext） |

**问题**：两个 Handler 处理相同的命令集（load/echo/sleep 等），但使用完全不同的注册表和函数签名。Share 层的 Handler 实际上在 FileDriven 场景中**未被使用**——FileDriven 管线直接调用 FileDriven 层的 Handler。

#### 重复 3：注册表基类继承体系

```
Share.Registry (Registry.csproj)
├── FactoryRegistryBase<TKey, TValue>     ← CommandRegistry 继承
├── MapRegistryBase<TKey, TValue>         ← EngineCommandRegistry 继承
└── HandlerRegistry<TKey, THandler>       ← HandlerRegistry 继承

FileDriven.Pipeline.Core
└── NonEventCommandRegistry               ← 独立实现，未继承任何基类
    └── 内部使用 ConcurrentDictionary     ← 与 MapRegistryBase 功能重叠
```

**问题**：`NonEventCommandRegistry` 没有复用 `Share.Registry` 的基类，而是自己用 `ConcurrentDictionary` 重新实现了一遍注册逻辑。

### 1.3 数据流分析

```
命令字符串
    │
    ▼
ParseCommandStage (CommandFramework.Pipeline)
    │
    ├── 判断是否为非事件命令
    │   └── CommandParser.DefaultNonEventCommands.Contains(action)
    │
    ├── 是 → NonEventCommandHandler.Handle() (FileDriven 层)
    │       └── NonEventCommandRegistry.Instance.TryGetHandler(action)
    │           └── 执行注册的 Action<object?> 处理函数
    │
    └── 否 → FindBindingStage → ExecuteFunctionStage (事件命令路径)
```

**关键发现**：实际运行时，Share 层的 `NonEventCommandHandler`（使用 `HandlerRegistry`）**从未被 FileDriven 管线调用**。FileDriven 管线直接使用自己的 `NonEventCommandHandler`（使用 `NonEventCommandRegistry`）。

## 2. 下迁方案（方案一：精简下迁 — 推荐）

### 2.1 核心思路

```
迁移前：
  Share.CommandFramework
    ├── HandlerRegistry          ← 实际未被 FileDriven 使用
    ├── NonEventCommandHandler   ← 实际未被 FileDriven 使用
    └── CommandParser.DefaultNonEventCommands  ← 与 NonEventCommands 重复

  FileDriven.Pipeline
    ├── NonEventCommandRegistry  ← 实际使用的注册中心
    └── NonEventCommands         ← 命令名称定义

迁移后：
  Share.CommandFramework.Abstractions
    └── INonEventCommandRegistry  ← 新增接口

  FileDriven.Execution (下迁目标)
    ├── NonEventCommandRegistry   ← 从 Pipeline 迁入，实现 INonEventCommandRegistry
    └── NonEventCommands          ← 从 Pipeline 迁入

  Share.CommandFramework
    ├── HandlerRegistry           ← 删除
    ├── NonEventCommandHandler    ← 改为接受 INonEventCommandRegistry 注入
    └── CommandParser.DefaultNonEventCommands  ← 改为通过接口查询
```

### 2.2 步骤详解

#### 步骤 1：在 `CommandFramework.Abstractions` 中定义接口

```csharp
// Share/CommandFramework/Abstractions/INonEventCommandRegistry.cs
namespace CommandFramework.Abstractions;

/// <summary>
/// 非事件命令注册表接口
/// <para>允许 CommandFramework 通过接口引用注册表，而不依赖具体实现。</para>
/// <para>FileDriven 的 NonEventCommandRegistry 将实现此接口。</para>
/// </summary>
public interface INonEventCommandRegistry
{
    /// <summary>注册非事件命令处理函数</summary>
    void Register(string commandName, Action<object?> handler,
        CommandCriticality criticality = CommandCriticality.Important,
        string? description = null);

    /// <summary>尝试获取处理函数</summary>
    bool TryGetHandler(string commandName, out Action<object?>? handler);

    /// <summary>判断命令是否已注册</summary>
    bool IsRegistered(string commandName);

    /// <summary>获取所有已注册的命令名称</summary>
    IReadOnlyCollection<string> RegisteredCommandNames { get; }
}
```

#### 步骤 2：将 `NonEventCommandRegistry` 和 `NonEventCommands` 从 `FileDriven.Pipeline` 下迁到 `FileDriven.Execution`

- 移动文件：`FileDriven.Pipeline/Core/NonEventCommandRegistry.cs` → `FileDriven.Execution/Command/NonEventCommandRegistry.cs`
- 移动文件：`FileDriven.Pipeline/Core/NonEventCommands.cs` → `FileDriven.Execution/Command/NonEventCommands.cs`
- 更新命名空间：`FileDriven.Pipeline.Core` → `FileDriven.Execution.Command`
- `NonEventCommandRegistry` 实现 `INonEventCommandRegistry` 接口
- 更新所有引用方（`PipelineFactory.cs`、`NonEventCommandHandler.cs`、`FileDrivenPipelineContext.cs` 等）

#### 步骤 3：修改 `CommandFramework.Execution.NonEventCommandHandler`

```csharp
// 改造前：内部创建 HandlerRegistry
public class NonEventCommandHandler
{
    private readonly HandlerRegistry _handlerRegistry;

    public NonEventCommandHandler(HandlerRegistry? handlerRegistry = null)
    {
        _handlerRegistry = handlerRegistry ?? new HandlerRegistry();
        RegisterDefaultHandlers();
    }
}

// 改造后：接受 INonEventCommandRegistry 注入
public class NonEventCommandHandler
{
    private readonly INonEventCommandRegistry? _registry;

    public NonEventCommandHandler(INonEventCommandRegistry? registry = null)
    {
        _registry = registry;
        // 不再注册默认处理器，由外部通过 INonEventCommandRegistry 注册
    }

    public async Task<CommandExecutionResult<object?>> HandleAsync(ParsedCommand command)
    {
        if (_registry == null)
            return CommandExecutionResult<object?>.Failure(
                "Non-event command registry is not available");

        var action = command.Action?.ToLowerInvariant() ?? command.Verb?.ToLowerInvariant();
        if (string.IsNullOrEmpty(action))
            return CommandExecutionResult<object?>.Failure("Action is required");

        if (_registry.TryGetHandler(action, out var handler) && handler != null)
        {
            try
            {
                // 将 ParsedCommand 包装为 object? 传入
                handler(command);
                return CommandExecutionResult<object?>.Success(null);
            }
            catch (Exception ex)
            {
                return CommandExecutionResult<object?>.Failure(
                    $"'{action}' execution error: {ex.Message}");
            }
        }

        return CommandExecutionResult<object?>.Failure($"Unknown non-event command: {action}");
    }
}
```

#### 步骤 4：删除 `HandlerRegistry`

- 从 `Registration/Registries.cs` 中删除 `HandlerRegistry` 类
- 如果 `HandlerRegistry` 在其他地方有引用，改为使用 `INonEventCommandRegistry`

#### 步骤 5：改造 `CommandParser.DefaultNonEventCommands`

```csharp
// 改造前：静态 HashSet
public static readonly HashSet<string> DefaultNonEventCommands = new(...);

// 改造后：通过 INonEventCommandRegistry 查询
// 保留 DefaultNonEventCommands 作为缓存，但由 NonEventCommandRegistry 同步更新
// 或者完全移除，改为方法调用
public bool IsNonEventCommand(string action)
{
    return _nonEventRegistry?.IsRegistered(action) ?? false;
}
```

#### 步骤 6：更新 `CommandFrameworkHost` 初始化

```csharp
// CommandFrameworkHost.Initialize() 中
// 不再创建 HandlerRegistry
// NonEventCommandHandler 接受 INonEventCommandRegistry 注入
// 由 FileDrivenExecutor 在初始化时通过 RegisterServices() 传入
```

#### 步骤 7：更新 `FileDrivenExecutor.InitializeFramework()`

```csharp
// 在 RegisterBuiltInCommands() 之后
// 将 NonEventCommandRegistry 注入到 CommandFrameworkHost
var host = CommandFrameworkUsage.Instance;
host.RegisterServices(
    nonEventRegistry: NonEventCommandRegistry.Instance  // 新增参数
);
```

## 3. 依赖关系分析

### 3.1 当前依赖关系

```
FileDriven.Execution
  ├── 引用 → Share.CommandFramework
  ├── 引用 → FileDriven.Pipeline
  └── 引用 → FileDriven.UI

FileDriven.Pipeline
  ├── 引用 → Share.CommandFramework
  └── 引用 → Share.Pipeline

Share.CommandFramework
  └── 引用 → Share.Registry
```

### 3.2 迁移后的依赖关系

```
FileDriven.Execution
  ├── 引用 → Share.CommandFramework
  ├── 引用 → FileDriven.Pipeline  (NonEventCommandRegistry 迁出后，此引用可移除)
  └── 引用 → FileDriven.UI

FileDriven.Pipeline
  └── 引用 → Share.Pipeline
      (不再依赖 Share.CommandFramework，如果其他部分也不依赖的话)

Share.CommandFramework
  └── 引用 → Share.Registry
      (HandlerRegistry 删除后，可能不再需要 Share.Registry)
```

### 3.3 循环依赖风险

```
风险场景：
  FileDriven.Execution → Share.CommandFramework
  Share.CommandFramework → FileDriven.Execution  ← 不允许！

解决方案：
  Share.CommandFramework 只引用 INonEventCommandRegistry 接口（在 Abstractions 中）
  FileDriven.Execution 中的 NonEventCommandRegistry 实现此接口
  通过依赖注入（RegisterServices）将实现传入 Share.CommandFramework
```

## 5. 风险与注意事项

### 5.1 兼容性风险
- `CommandFramework.Execution.NonEventCommandHandler` 的 `RegisterHandler()` 和 `RegisterServiceCommands()` 方法被外部调用时需要适配
- `CommandParser.DefaultNonEventCommands` 是 `public static` 字段，被外部直接引用的地方需要修改

### 5.2 测试验证
1. 编译验证：`dotnet build` 整个解决方案
2. 功能验证：CLI 模式下执行命令文件，验证所有非事件命令（load/echo/sleep 等）正常工作
3. 注册验证：`NonEventCommandRegistry.ValidateAll()` 校验通过
4. 级联保护验证：sideload 失败后的重试和降级机制正常

### 5.3 回退方案
如果迁移后出现问题，可以：
1. 保留 `HandlerRegistry` 但标记为 `[Obsolete]`
2. `CommandParser.DefaultNonEventCommands` 保留但改为从接口同步
3. 逐步迁移而非一次性完成
