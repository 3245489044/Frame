# 事件绑定架构分析与修复方案

## 1. 问题现象

日志中 `funcListView` 数据为空：

```
[WARN] [WinFormsWriter] ListView 'funcListView' 数据为空，跳过填充
```

同时大量出现 `ControlRegistryAwareFinder` Registry 未命中的警告：

```
[WARNING] [ControlRegistryAwareFinder] Registry 未命中: controlName=searchTextBox, registryCount=0
```

## 2. 架构分析

### 2.1 当前事件绑定链路

```
用户点击 domainListView
  → WinFormsEventBinderAdapter.BindSingleEvent() 创建 EventHandler
    → handler 内部调用 _eventPipelineExecutor.Execute()
      → ExecutionPipelineEntry.Execute()
        → GetOrCreateSingleCommandPipeline()（缓存，只构建一次）
          → ParseCommandStage → FindBindingStage → ExecuteCommandStage → ResultCollectStage
```

### 2.2 两条执行路径的对比

| 特性 | 路径 A：脚本/initCommands | 路径 B：手动点击事件 |
|------|--------------------------|---------------------|
| 入口 | `RunPipeline()` | `WinFormsEventBinderAdapter` 事件处理器 |
| 命令来源 | 脚本文件/配置中的 `initCommands` | 事件触发时动态构建 |
| bindings 来源 | `FindBindingStage` 从配置查找 | 事件处理器已通过 `GetBindingsForEvent` 获取 |
| 结果写入 | `ResultCollectStage` 处理 | `ExecuteCommandStage.HandleClick` 内部完成 |

### 2.3 核心问题：bindings 信息在事件处理器处丢失

**问题不在于"层数多"，而在于"信息没传下去"。**

`ExecuteCommandStage.HandleClick()` 的实际逻辑（`Share/CommandFramework/Pipeline/Stages/ExecuteCommandStage.cs`）已经是 read→exec→write 的工作流模式：

```
HandleClick:
  1. FindBinding(target, eventType)       ← 从 SharedData 读取 _originalEventType 重新查找
  2. 从控件读取输入值（ParameterResolver）  ← read
  3. executor.ExecuteAsync(functionName)  ← exec
  4. WriteResult(context, target, value)  ← write
```

命令管道在这里扮演的正是工作流引擎的角色。**问题不是"用错了引擎"，而是"函数执行器可以换成工作流引擎来获得更多能力"**。

数据丢失只发生在一个地方：

```
WinFormsEventBinderAdapter.BindSingleEvent()
  ├── 获取了 eventOutput / eventInputs（bindings 信息） ← ✅ 已获取
  └── 调用 _eventPipelineExecutor.Execute()
       └── 只传了 ctrl.Name 和 value ← ❌ bindings 没传下去
```

### 2.4 具体问题

**问题 1：bindings 信息丢失（唯一的数据丢失点）**

`WinFormsEventBinderAdapter.BindSingleEvent()` 第 122-147 行：

```csharp
private void BindSingleEvent(Control control, string eventName, string functionName, EventConfig eventsConfig)
{
    var (eventOutput, eventInputs) = GetBindingsForEvent(eventsConfig, eventName);

    EventHandler handler = (sender, args) =>
    {
        if (IsScriptExecutionMode) return;
        if (sender is not Control ctrl || string.IsNullOrEmpty(ctrl.Name)) return;

        // ★ 问题：只传了 ctrl.Name 和 value，bindings 信息丢失了
        _eventPipelineExecutor.Execute(ctrl.Name, eventName.ToLowerInvariant(),
            _controlService.GetValue(ctrl)?.ToString() ?? string.Empty);
    };
    // ...
}
```

事件处理器获取了 `eventOutput` 和 `eventInputs`，但没有传递给执行层。执行层内部的 `ExecuteCommandStage.HandleClick` 通过 `_originalEventType` 从 SharedData 重新查找绑定，但查找路径与 `GetBindingsForEvent` 可能不一致，导致结果没有写回正确的 output 控件。

**问题 2：ControlRegistryAwareFinder 注册缺失**

`ControlRegistryAwareFinder` 的 `_registry` 字典为空，所有控件查找都回退到 `Controls.Find` 路径。这表明控件创建后没有正确注册到查找器的注册表中。

## 3. 根因定位：函数执行器可以替换为工作流引擎

| 场景 | 当前处理方式 | 优化方向 |
|------|-------------|---------|
| 脚本命令（initCommands、脚本文件） | 命令管道 | ✅ 正确 |
| UI 事件动态触发（点击、选中变化） | 命令管道（HandleClick 已是 read→exec→write 模式） | 将 `IFunctionExecutor.ExecuteAsync` 替换为 `WorkflowRuntime.ExecuteAsync`，获得状态追踪、暂停恢复等能力 |

`ExecuteCommandStage.HandleClick()` 对 click 事件的处理本身就是工作流模式（read→exec→write），只是它调用的函数执行器是 `IFunctionExecutor` 而不是 `WorkflowRuntime`。因此**不需要改变整体架构**，只需要替换函数执行器。


## 4. 工作流方案：复用 Operation/WorkFlowMethod 引擎

### 4.1 为什么使用工作流引擎

工作流引擎的核心思想是：**事件只负责触发，不负责传递数据**。数据在工作流内部通过变量流动，不依赖调用链传递。

```
事件触发 → 工作流引擎匹配工作流
         → 工作流内部：
           步骤1: read domainListView → $selectedDomain（平级）
           步骤2: exec Math_GetFunctionsInDomain($selectedDomain) → $functions（平级）
           步骤3: write funcListView ← $functions（平级）
```

数据不再穿透多层，而是在工作流引擎内部通过变量名直接引用。每层之间没有嵌套关系，都是平级的步骤。

### 4.2 项目已有工作流引擎：Operation/WorkFlowMethod

项目 `Operation/WorkFlowMethod` 中已经存在完整的工作流引擎，无需新建。其核心组件包括：

| 组件 | 位置 | 说明 |
|------|------|------|
| `WorkflowRuntime` | `Orchestration/WorkflowRuntime.cs` | 工作流运行时，支持 ExecuteAsync/Pause/Resume/Cancel |
| `WorkflowBuilder` | `Orchestration/WorkflowBuilder.cs` | 工作流构建器，支持从 JSON 反序列化 |
| `NodeConfig` | `Orchestration/Models.cs` | 工作流节点配置模型 |
| `NodeProcess` | `ExecutionEngine/NodeProcess.cs` | 四步管线：GetConfig → ExecuteFunc → AddNode → NextNode |
| `WorkflowUseage` | `WorkFlowMethod/WorkflowUseage.cs` | 前台使用模块，统一函数注册和执行 |
| `IWorkflowRegistry` | `BasicMethod/FunctionExecution/WorkflowFunctions/` | 工作流函数注册表 |
| `PipelineExecutor` | `BasicMethod/FunctionExecution/` | 管线执行引擎 |

### 4.3 事件配置 → NodeConfig 映射（需要转换层）

`MathFunctionBrowser.json` 中的 events+bindings 配置不能直接作为 `NodeConfig` 使用，需要经过一个转换层：

```json
{
  "events": {
    "selectedIndexChanged": "Math_GetFunctionsInDomain",
    "bindings": { "inputs": ["domainListView"], "output": "funcListView" }
  }
}
```

`NodeConfig` 需要更详细的信息，转换层负责补充：

```csharp
// 转换层：events+bindings → NodeConfig
var node = new NodeConfig
{
    Symbol = eventName,                                    // 来自 events 键名
    Label = controlName,                                   // 来自触发事件的控件名
    getStrConfig = new GetStrConfig 
    { 
        GetConfigGetstring = $"{inputControl}.Value"       // 转换层推断：从 input 控件读取值
    },
    funcPipelineConfig = new FuncPipelineConfig
    {
        FuncName = functionName,                           // 来自 events 值
        ParameterKeys = string.Join(",", inputControls)    // 转换层拼接：来自 bindings.inputs
    },
    addNodeConfig = new AddNodeConfig
    {
        AddConfigAddKey = outputControl                    // 来自 bindings.output
    }
};
```

### 4.4 执行流程

通过 `NodeProcess` 执行单个节点配置，引擎自动完成四步管线：

```
NodeConfig
  → GetConfig:   从 domainListView 读取选中值（对应 read 步骤）
  → ExecuteFunc: 调用 Math_GetFunctionsInDomain（对应 exec 步骤）
  → AddNode:     将结果写入 funcListView（对应 write 步骤）
  → NextNode:    后续处理（可选）
```

注意：`WorkflowRuntime.ExecuteAsync` 执行的是整个工作流（多个节点），单个节点应使用 `NodeProcess` 的管线方法。

### 4.5 与现有系统的集成

| 集成点 | 说明 |
|--------|------|
| **函数注册表** | `Math_GetFunctionsInDomain` 等函数通过 `BuiltInFunctionRegistrar` 注册到 `IWorkflowRegistry` |
| **控件服务** | read/write 步骤通过 `IControlService` 读写控件值 |
| **控件查找器** | 通过 `IControlFinder` 按名称查找控件（支持容器范围限定） |
| **日志集成** | 工作流执行过程输出日志，与现有 `FileDrivenLogPlaceholderHandler` 兼容 |
| **配置驱动** | 工作流定义可从 JSON 加载，与 `MathFunctionBrowser.json` 的配置风格一致 |

### 4.6 工作流 vs 现有方案对比

| 维度 | 当前架构（命令管道） | 事件处理器直连 | 事件总线 | 工作流方案（复用 WorkFlowMethod） |
|------|-------------------|--------------|---------|-------------------------------|
| 耦合度 | 中（命令管道） | 中（代码硬编码） | 低（发布订阅） | 低（配置驱动） |
| 可配置性 | 中 | 低 | 中 | 高 |
| 可扩展性 | 中 | 低 | 高 | 高 |
| 实现成本 | - | 中 | 高 | **低**（引擎已存在） |
| 与现有架构兼容 | - | 中 | 低 | **高**（复用现有引擎和注册表） |
| 维护成本 | 中 | 中 | 高 | **低**（统一执行模型） |

### 4.7 为什么不是"新建"工作流引擎

项目 `Operation/WorkFlowMethod` 中已经存在完整的工作流引擎基础设施：

1. **执行引擎**：`WorkflowRuntime` + `NodeProcess` 已实现四步管线执行
2. **函数注册**：`IWorkflowRegistry` + `BuiltInFunctionRegistrar` 已支持函数注册和调用
3. **配置驱动**：`WorkflowBuilder` + `WorkflowDeserializer` 已支持从 JSON 加载工作流
4. **管线编排**：`PipelineExecutor` + `WorkflowUseage` 已支持管线化执行

因此不需要新建工作流引擎，只需要在 `ExecuteCommandStage` 中将 `IFunctionExecutor.ExecuteAsync` 替换为 `WorkflowRuntime.ExecuteAsync`。



## 5. 替换范围：仅将 GUI 点击触发的函数执行替换为工作流引擎

### 5.1 核心思路

**触发前的一切不变**，只替换 GUI 点击事件触发后、实际调用函数的那一步。

```
GUI 点击触发 → 事件绑定 → 命令管道 → 查找 bindings → 准备参数
                                                      ↓
                                              调用函数  ← 只替换这一步
                                                      ↓
                                              结果收集 → 写入控件
```

具体来说，`ExecuteCommandStage` 中原本通过 `IFunctionExecutor` 直接调用函数的逻辑，改为通过 `WorkflowRuntime.ExecuteAsync` 调用，让工作流引擎管理函数的执行过程。

### 5.2 替换细节

**替换前**：`ExecuteCommandStage` 中直接调用函数

```csharp
// 当前逻辑（简化）
var functionName = bindingInfo.FunctionName;
var result = _functionExecutor.Execute(functionName, parameters);
context.SetResult(result);
```

**替换后**：`ExecuteCommandStage` 中将函数调用委托给工作流引擎

```csharp
// 替换后的逻辑（简化）
var functionName = bindingInfo.FunctionName;
var nodeConfig = new NodeConfig
{
    funcPipelineConfig = new FuncPipelineConfig
    {
        FuncName = functionName,
        ParameterKeys = string.Join(",", parameters.Keys),
        Params = JsonSerializer.Serialize(parameters)
    }
};
var result = await _workflowRuntime.ExecuteAsync(nodeConfig);
context.SetResult(result);
```

### 5.3 替换对照表

| 当前 | 替换为 | 说明 |
|------|--------|------|
| `IFunctionExecutor.Execute(functionName, params)` | `WorkflowRuntime.ExecuteAsync(nodeConfig)` | 函数调用由工作流引擎管理，获得状态追踪、暂停恢复、历史记录等能力 |

### 5.4 保持不变的部分（触发前的一切）

| 组件 | 说明 |
|------|------|
| `WinFormsEventBinderAdapter` | 事件绑定逻辑不变 |
| `IEventPipelineExecutor` / `ExecutionPipelineEntry.Execute()` | 事件管线执行器不变 |
| `BuildEventCommand()` | 事件→命令映射不变 |
| `CreateMinimalContext()` | 上下文创建不变 |
| `GetOrCreateSingleCommandPipeline()` | 命令管线构建不变 |
| `ParseCommandStage` | 命令解析不变 |
| `FindBindingStage` | bindings 查找不变 |
| `ResultCollectStage` | 结果收集不变 |
| `IControlService` | 控件服务不变 |
| `IWorkflowRegistry` | 函数注册表不变 |
| `IsScriptExecutionMode` | 脚本执行模式不变 |


## 6. 推荐演进路径

### 阶段一：短期修复

最小改动，修复当前 `funcListView` 数据为空的问题：

1. 扩展 `IEventPipelineExecutor.Execute` 接口，增加 `sharedData` 参数
2. 修改 `WinFormsEventBinderAdapter.BindSingleEvent`，将 bindings 信息传递给执行层
3. 修改 `ExecutionPipelineEntry.Execute`，将 sharedData 合并到上下文
4. 确保 `ResultCollectStage` 从 `SharedData["_eventOutput"]` 读取输出目标

### 阶段二：将 ExecuteCommandStage 的函数调用替换为工作流引擎

在保持整体架构不变的前提下，只替换 `ExecuteCommandStage` 中调用函数的部分：

1. **ExecuteCommandStage 改造**：将 `IFunctionExecutor.Execute(functionName, params)` 替换为 `WorkflowRuntime.ExecuteAsync(nodeConfig)`
2. **NodeConfig 构建**：在 `ExecuteCommandStage` 中将函数名和参数映射为 `NodeConfig`
3. **工作流引擎集成**：`ExecuteCommandStage` 持有 `IWorkflowRuntime` 引用，通过它执行函数
4. **结果回传**：工作流引擎执行完成后，将结果写回 `FileDrivenPipelineContext`，后续 `ResultCollectStage` 照常处理

### 阶段三：统一执行模型（可选）

逐步将脚本命令、initCommands 中的函数调用也迁移到工作流引擎，统一执行模型。
