## 2. 根本原因

`MathFunctions.json` 中使用了模板引用的控件（如 `title-bar-with-text`、`action-button`、`status-bar`），这些控件在 JSON 中**只有 `"template": "..."` 而没有 `"type": "..."`**：

```json
{
  "template": "title-bar-with-text",
  "name": "titleLabel",
  "text": "Built-in Math Functions"
}
```

模板展开系统（`TemplatePreprocessor` → `ProcessJsonWithTemplate` → `JsonPipelineRegistry.Process`）应该将这些 template 引用展开为完整的控件定义（包含 `type` 字段）。

查看 `composites.json` 中的模板定义：
- **`title-bar-with-text`**：`"type": "label"` ✓ 有 type
- **`action-button`**：`"type": "button"` ✓ 有 type
- **`status-bar`**：`"type": "label"` ✓ 有 type

**所以模板定义中是有 `type` 字段的。** 问题出在模板展开后的 JSON 中 `type` 字段没有被正确合并到最终的 `ControlConfig` 对象中。

## 3. 关键线索：`MainLayout.json` 加载成功

从日志看，`MainLayout.json` 的加载是成功的（`OnRootContainerLoaded: success=true`），说明 `_rootContainer` 的 `TemplatePreprocessor` 被正确设置了。

但 `MathFunctions.json` 是通过 `LoadSideContainerAsync` 加载到 `_sideContainer` 的。

## 6. 最可能的根因分析

### 6.1 假设 A：`_sideContainer.TemplatePreprocessor` 为 null

**分析**：从时序链看，`_rootContainer.TemplatePreprocessor` 在 `GuiModeRunner.Run()` 中设置（第 74 行），此时 `_rootContainer` 刚创建，还没有子控件。当 `MainLayout.json` 加载后，`sideContainer` 被创建并通过 `RegisterSubContainer` 注册，此时 `_templatePreprocessor` 已经不为 null，所以 `sideContainer` 应该能继承 `TemplatePreprocessor`。

**结论**：在正常时序下，`_sideContainer.TemplatePreprocessor` **不应该为 null**。

### 6.2 假设 B：模板展开后的 JSON 中 `type` 字段缺失

**分析**：`ProcessJsonWithTemplate`（`FrameworkInitializer.cs:470-518`）的流程：
1. 读取 JSON 文件
2. 解析为 `JsonNode`
3. 执行 `FileDrivenAdapter.ConvertBareNamesToPrefixed(doc)` — 裸名转 @前缀
4. 序列化为字符串
5. 调用 `JsonPipelineRegistry.Process(serialized, path)` — 模板展开
6. 返回展开后的 JSON

`JsonPipeline.Execute(string json, string? sourcePath)`（`JsonPipeline.cs:100`）直接使用传入的 `json` 字符串，**不会重新读取文件**。`sourcePath` 仅用于日志上下文。

**结论**：`ConvertBareNamesToPrefixed` 的修改是有效的，`JsonPipelineRegistry.Process` 使用的是已转换的 JSON。

### 6.3 假设 C：`ConfigurationLoader.LoadConfigAsync` 的缓存问题

**分析**：`ConfigurationLoader.LoadConfigAsync`（`WdUI.Configuration.cs:44-64`）有缓存机制：
```csharp
if (_configCache.TryGet(configPath, out var cached))
    return cached;
```

如果 `MathFunctions.json` 之前被加载过（例如通过 `WdUIComposer.LoadConfigAsync` 直接加载，未经过模板展开），缓存中存储的是未展开的配置。后续通过 `_sideContainer.LoadConfigAsync` 加载时，虽然 `TemplatePreprocessor` 生成了临时文件（`loadPath` 指向临时文件），但 `ConfigurationLoader.LoadConfigAsync` 收到的是临时文件路径，缓存中可能没有这个路径。

**结论**：缓存问题可能性较低，因为临时文件路径每次不同（包含 `Guid`）。

### 6.4 假设 D：`WdUIComposer.LoadConfigAsync` 内部也做了模板处理

**分析**：`WdUIComposer.LoadConfigAsync`（`WdUIComposer.cs:215-216`）委托到 `Config.LoadConfigAsync`，即 `ConfigurationLoader.LoadConfigAsync`。这个方法是纯反序列化，**不做模板处理**。

**结论**：模板处理只在 `ConfigContainer.LoadConfigAsync` 中通过 `TemplatePreprocessor` 完成，`WdUIComposer.LoadConfigAsync` 不重复处理。

### 6.5 假设 E：`ConfigLoaderAdapter.LoadConfigAsync` 的路径解析问题

**分析**：`ConfigLoaderAdapter.LoadConfigAsync<T>`（`Infrastructure.cs`）读取文件并反序列化。如果 `loadPath` 指向的临时文件内容正确（包含展开后的 `type` 字段），则反序列化后的 `ControlConfig.Type` 应该有值。

**结论**：需要验证临时文件的内容是否正确。

- `_rootContainer.TemplatePreprocessor` 是否为 null

### 8.2 单元测试

2. 加载包含 `sideContainer` 的布局
3. 通过 `FindSubContainer` 获取 `_sideContainer`
4. 验证 `_sideContainer.TemplatePreprocessor` 不为 null
5. 调用 `_sideContainer.LoadConfigAsync` 加载包含 template 引用的 JSON

### 8.3 日志检查

检查运行时日志中以下关键日志点：

- `ConfigContainer_RegisterSubContainer_propagate_template` — TemplatePreprocessor 传播
- `MainForm_OnRootContainerLoaded` — 主布局加载完成

## 9. 结论

最可能的根因是 **`_sideContainer.TemplatePreprocessor` 为 null**，导致 `MathFunctions.json` 中的 `template` 引用未被展开，`ControlConfig.Type` 保持为空字符串。

虽然从代码时序分析看，在正常流程下 `_sideContainer` 应该能继承 `TemplatePreprocessor`，但以下场景可能导致传播失败：

1. **异常时序**：如果 `RegisterSubContainer` 在 `_rootContainer.TemplatePreprocessor` 设置之前被调用（例如 `MainLayout.json` 的渲染过程中有异步操作导致时序错乱）
2. **控件树断裂**：如果 `sideContainer` 不是通过 `RegisterSubContainer` 注册，而是通过其他方式添加到控件树
3. **TemplatePreprocessor 被重置**：如果在某个环节 `TemplatePreprocessor` 被设置为 null

已实施的三层防御性修复（MainForm 同步 + LoadConfigAsync fallback + 控件树传播增强）覆盖了以上所有场景，确保 `TemplatePreprocessor` 在任何情况下都能正确传播。
