# 工作流参数处理缺陷分析

> 本文档分析工作流框架中参数传递与返回值处理的框架级缺陷，并提出修复方案。
> 编写日期：2026-07-15

---

## 1. 问题现象

`Add` 函数执行后返回 `0`，但预期应为 `a + b` 的计算结果。同时 `SetValue` 函数的返回值输出到控件时格式错误（显示为键值对列表而非单个值）。

## 2. 当前调用链

```
EventBindingStageBase (事件触发)
  → ParameterBuilder.Build()                    # 构建参数字典 {a, b, value}
    → ForEachParameterBindingStage              # 从控件取值：a="123", b="456"
    → SenderValueAddStage                       # 多余：添加 value="加法 (Add)"
  → WorkflowMethodExecutionService              # 包装为单节点工作流
    → ExecuteWorkflowAsync                      # 复制 Dictionary → {a, b, value}
      → NodeExecutor.ExecuteFunctionNodeAsync   # 包装为 object?[] → [{a, b, value}]
        → FunctionExecutor.ExecuteAsync(string, object?[])
          → 检测 Dictionary，委托给 Dictionary 重载
            → FunctionExecutor.ExecuteAsync(string, Dictionary)
              → ParameterTransformer.Transform  # FillFromDict 按名匹配
                → InvokeDelegateAsync            # Add(a=123.0, b=456.0) = 579.0
  → HandleExecutionResult                       # 处理返回值
    → result.Value = 579.0 (double) 或 {"value": 123} (Dictionary)
    → 写入 resultTextBox
```

## 3. 框架级缺陷

### 缺陷1：参数构建层不知道函数签名

**所在位置**：`ParameterBuilder.cs` + `ParameterBuilderStages.cs`

**问题描述**：
- `ParameterBuilder.Build()` 只管从控件取值拼成 `Dictionary<string, object>`
- `SenderValueAddStage` 盲目添加 `value` 键（触发控件的当前值）
- 对于 `Add(a, b)`，构建出 `{a: "123", b: "456", value: "加法 (Add)"}` 三个键
- 其中 `value` 键是多余的，虽然 `FillFromDict` 按名匹配能正确忽略它，但增加了数据污染和调试难度

**根因**：
- `ParameterBuilder` 没有从 `IFunctionRegistry` 获取目标函数的参数列表
- 不知道函数需要哪些参数，所以无法过滤多余的键

**影响范围**：
- 所有通过事件绑定触发的多参数函数
- 当前侥幸正确（因为 `FillFromDict` 按名匹配），但增加了混淆和潜在风险

### 缺陷2：工作流执行层返回值格式不统一

**所在位置**：`WorkflowMethodExecutionService.ExecuteWorkflowAsync()`

**问题描述**：
- `type: "workflow"` 的函数（如 `SetValue`）返回 `Dictionary<string, object>`
- `type: "delegate"` 的函数（如 `Add`）返回原始值（`double`）
- `ExecuteWorkflowAsync` 直接将 `lastResult` 原样返回：

```csharp
return ExecutionResult.Success(lastResult ?? new object());
```

- 导致 `HandleExecutionResult` 需要同时兼容 `double` 和 `Dictionary` 两种格式

**根因**：
- 工作流执行层没有统一返回值格式
- 单节点工作流（由 delegate 自动包装）的返回值没有被包装为 Dictionary

**影响范围**：
- `HandleExecutionResult` 第 462-470 行的 Dictionary 检测逻辑是补丁式修复
- 所有 delegate 类型函数的事件绑定都需要特殊处理

### 缺陷3：NodeExecutor 中多余的参数包装

**所在位置**：`NodeExecutor.ExecuteFunctionNodeAsync()` 第 231 行

**问题描述**：
- `node.Parameters` 已经是 `Dictionary<string, object>`
- 又被包装为 `object?[]` 传入 `FunctionExecutor`
- `FunctionExecutor` 第 48 行又检测 Dictionary 并拆包
- 导致 `Dictionary → object?[] → Dictionary` 的冗余转换

```csharp
// NodeExecutor 第 231 行
result = await _executor.ExecuteAsync(functionName, new object?[] { namedParams }, basicContext);

// FunctionExecutor 第 48 行
if (parameters is { Length: 1 } && parameters[0] is Dictionary<string, object> namedParams)
    return await ExecuteAsync(functionName, namedParams, context);
```

**根因**：
- `IFunctionExecutor` 接口只有 `ExecuteAsync(string, object?[], context)` 重载
- 没有提供 `ExecuteAsync(string, Dictionary<string, object>, context)` 重载
- NodeExecutor 不得不把 Dictionary 包装为 `object?[]`

### 缺陷4：FunctionExecutor 中 object?[] → Dictionary 的拆包逻辑

**所在位置**：`FunctionExecutor.cs` 第 48 行

**问题描述**：
- 因为上层传入了 `object?[]`，所以这里需要检测并拆包
- 这个拆包逻辑的存在，恰恰证明了上层传错了格式
- 如果上层直接传 Dictionary，这个逻辑就不需要了

```csharp
// FunctionExecutor 第 48 行 — 这是"补丁式"代码
if (parameters is { Length: 1 } && parameters[0] is Dictionary<string, object> namedParams)
    return await ExecuteAsync(functionName, namedParams, context);
```

**根因**：
- 与缺陷3相同：接口设计不完整，导致包装-拆包的冗余循环

## 4. 消除多余包装的分析

### 4.1 核心原则

**以工作流运行为基础**：所有函数都走工作流路径，不跳过 `WorkflowMethodExecutionService` 和 `NodeExecutor`。

### 4.2 工作流内部的数据契约

工作流内部传递参数的自然格式是 `Dictionary<string, object>`（键值对），这是工作流的数据契约。所有层都应遵守这个契约：

| 层 | 当前格式 | 目标格式 |
|----|---------|---------|
| ParameterBuilder → WorkflowMethodExecutionService | `Dictionary<string, object>` | `Dictionary<string, object>` ✅ |
| WorkflowMethodExecutionService → NodeExecutor | `Dictionary<string, object>` | `Dictionary<string, object>` ✅ |
| NodeExecutor → FunctionExecutor | `object?[]` | `Dictionary<string, object>` ← 修复 |
| FunctionExecutor → ParameterTransformer | `Dictionary<string, object>` | `Dictionary<string, object>` ✅ |
| ExecuteWorkflowAsync → 调用方 | `double` / `Dictionary` | `Dictionary<string, object>` ← 修复 |

### 4.3 四层多余包装的消除方案

#### 包装1：ParameterBuilder 构建了多余的 value 键

**消除方案**：ParameterBuilder 感知函数签名

```csharp
// 修改前
public Dictionary<string, object> Build(object sender, List<ParameterBinding>? parameterBindings)

// 修改后
public Dictionary<string, object> Build(
    object sender,
    List<ParameterBinding>? parameterBindings,
    string? functionName = null,
    IFunctionRegistry? registry = null)
```

**逻辑**：
1. 从 `parameterBindings` 构建参数字典（不变）
2. 如果提供了 `functionName` 和 `registry`，获取目标函数的参数名列表
3. 只保留函数声明中存在的参数键
4. `SenderValueAddStage` 改为：仅当函数有名为 `value` 的参数时才添加 sender 值

**改动文件**：
- `ParameterBuilder.cs` — 修改 `Build` 方法签名和实现
- `ParameterBuilderStages.cs` — 修改 `SenderValueAddStage` 的条件判断
- `EventBindingStageBase.cs` — 调用 `Build` 时传入 `functionName` 和 `registry`

#### 包装2：NodeExecutor 把 Dictionary 包装为 object?[]

**消除方案**：`IFunctionExecutor` 接口增加 Dictionary 重载

```csharp
// IFunctionExecutor.cs — 新增重载
Task<ExecutionResult> ExecuteAsync(
    string functionName,
    Dictionary<string, object> namedParameters,
    EXContext? context = null);
```

```csharp
// NodeExecutor.cs — 直接调用 Dictionary 重载
if (node.Parameters is Dictionary<string, object> namedParams)
{
    result = await _executor.ExecuteAsync(functionName, namedParams, basicContext);
    // 不再需要 new object?[] { namedParams }
}
```

**改动文件**：
- `IFunctionExecutor.cs` — 新增 Dictionary 重载
- `FunctionExecutor.cs` — 实现 Dictionary 重载（将现有逻辑从 `object?[]` 重载中提取出来）
- `NodeExecutor.cs` — 调用 Dictionary 重载

#### 包装3：FunctionExecutor 中 object?[] → Dictionary 的拆包逻辑

**消除方案**：有了 Dictionary 重载后，`object?[]` 重载中的拆包检测逻辑不再需要。

```csharp
// FunctionExecutor.cs — 修改前
public async Task<ExecutionResult> ExecuteAsync(
    string functionName,
    object?[] parameters,
    EXContext? context = null)
{
    // 第 48 行：检测 Dictionary 并委托
    if (parameters is { Length: 1 } && parameters[0] is Dictionary<string, object> namedParams)
        return await ExecuteAsync(functionName, namedParams, context);

    // ... 原有逻辑（处理非 Dictionary 参数）
}

// 修改后
public async Task<ExecutionResult> ExecuteAsync(
    string functionName,
    object?[] parameters,
    EXContext? context = null)
{
    // 不再检测 Dictionary，直接处理 object?[] 参数
    // ... 原有逻辑
}
```

**注意**：`object?[]` 重载仍然保留，供其他调用方使用（非工作流路径）。

**改动文件**：
- `FunctionExecutor.cs` — 移除第 48 行的 Dictionary 检测逻辑

#### 包装4：ExecuteWorkflowAsync 返回原始值而非 Dictionary

**消除方案**：工作流执行完成后，统一将结果包装为 `Dictionary<string, object>`

```csharp
// WorkflowMethodExecutionService.cs — 修改前
return ExecutionResult.Success(lastResult ?? new object());

// 修改后
// 将 lastResult 统一包装为 Dictionary<string, object>
// 键名由函数定义的 OutputKey 指定，默认为 "value"
var resultDict = new Dictionary<string, object>();
var outputKey = workflowDef.Nodes?.LastOrDefault()?.OutputKey ?? "value";
resultDict[outputKey] = lastResult ?? new object();
return ExecutionResult.Success(resultDict);
```

**配套改动**：`MathFunctions.unified.json` 中为 delegate 函数添加 `outputKey`

```json
{
  "name": "Add",
  "type": "delegate",
  "outputKey": "value",
  "parameters": [
    { "name": "a", "type": "System.Double" },
    { "name": "b", "type": "System.Double" }
  ]
}
```

**改动文件**：
- `WorkflowMethodExecutionService.cs` — 修改返回值包装逻辑
- `MathFunctions.unified.json` — 为 delegate 函数添加 `outputKey`

### 4.4 消除后的调用链

```
EventBindingStageBase (事件触发)
  → ParameterBuilder.Build(sender, bindings, registry)  # 感知签名，只构建 {a, b}
  → WorkflowMethodExecutionService                      # 包装为单节点工作流
    → ExecuteWorkflowAsync                              # 复制 Dictionary → {a, b}
      → NodeExecutor.ExecuteFunctionNodeAsync           # 直接调用 Dictionary 重载
        → FunctionExecutor.ExecuteAsync(string, Dict)   # 直接执行，无需拆包
          → ParameterTransformer.Transform              # FillFromDict 按名匹配
            → InvokeDelegateAsync                        # Add(a=123.0, b=456.0) = 579.0
  → HandleExecutionResult                               # 处理返回值
    → result.Value = {"value": 579.0} (统一 Dictionary)
    → 根据 outputMapping 提取 "value" → 579.0
    → 写入 resultTextBox
```

**消除的冗余步骤**：
1. ~~`SenderValueAddStage` 添加多余的 `value` 键~~ → 不再添加
2. ~~`NodeExecutor` 包装为 `object?[]`~~ → 直接传 Dictionary
3. ~~`FunctionExecutor` 检测 Dictionary 并拆包~~ → 不再需要
4. ~~`ExecuteWorkflowAsync` 返回原始值~~ → 统一返回 Dictionary

## 5. 基于 Functor 的框架级重构方案

### 5.1 Functor 框架简介

`BasicMethod.Functor` 是一个基于**函子理论**的通用跨层值传递框架，位于 `CsharpPrj/BasicMethod/Map/Functor/`。

**核心能力**：
- **隐式传播**：通过 `AsyncLocal` 实现，中间层零修改
- **键值存储**：支持按类型（`Type.FullName`）和按键（`string`）存取
- **嵌套作用域**：支持父子作用域，子作用域可覆盖父作用域的值
- **快照**：`Snapshot()` 返回当前作用域的所有值

**核心接口**：

```csharp
public interface IFunctor
{
    string Name { get; }
    T? Get<T>() where T : class;           // 按类型获取
    void Set<T>(T value) where T : class;  // 按类型设置
    object? Get(string key);               // 按键获取
    void Set(string key, object? value);   // 按键设置
    bool Has(string key);                  // 按键检查
}

public interface IFunctorScope : IFunctor, IDisposable
{
    IFunctorScope? Parent { get; }
    IFunctorScope CreateScope();
    IReadOnlyDictionary<string, object?> Snapshot();
}
```

**使用方式**：

```csharp
// Source 端：创建作用域并设置值
using (var scope = Functor.Begin("FileDriven"))
{
    scope.Set(mainForm);           // 按类型
    scope.Set("config", config);   // 按键
    // 调用链中的任意代码都可以获取
}

// Sink 端：获取值
var form = Functor.Current?.Get<Form>();
var cfg = Functor.Current?.Get("config");
```

### 5.2 Functor 优化工作流参数传递

#### 核心思路

Functor 作为工作流的**数据总线（Data Bus）**，参数和结果通过 Functor 隐式传播，而不是显式传递 Dictionary。

```
当前方式（显式传递 Dictionary）：
EventBindingStageBase → [Dictionary] → WorkflowMethodExecutionService → [Dictionary] → NodeExecutor → [object?[]] → FunctionExecutor

Functor 方式（隐式传播）：
EventBindingStageBase → Functor.Set("a", 123).Set("b", 456) → 调用工作流
  → WorkflowMethodExecutionService（无需参数）
    → NodeExecutor（无需参数）
      → FunctionExecutor → Functor.Get("a"), Functor.Get("b") → Add(a, b) → Functor.Set("result", 579)
  → HandleExecutionResult → Functor.Get("result") → 写入控件
```

#### 方案对比

| 方案 | 描述 | 改动量 | 风险 | 收益 |
|------|------|--------|------|------|
| **方案A：Functor 统一返回值** | 仅用 Functor 传递返回值 | 小 | 低 | 消除返回值格式不统一 |
| **方案B：Functor 完整数据总线** | 参数和返回值都通过 Functor | 大 | 高 | 彻底消除显式 Dictionary 传递 |

**推荐方案A**（轻量级），原因：
1. 改动最小，只影响返回值处理
2. 不改变现有的参数传递方式
3. 解决了核心问题（返回值格式不统一）
4. 为将来扩展到方案B留下空间

### 5.3 方案A：Functor 统一返回值（推荐）

#### 改动1：WorkflowMethodExecutionService 将结果存入 Functor

```csharp
// WorkflowMethodExecutionService.cs
// 执行完成后，将结果存入 Functor
var outputKey = workflowDef.Nodes?.LastOrDefault()?.OutputKey ?? "value";

// 存入 Functor（如果当前有 Functor 作用域）
Functor.Current?.Set(outputKey, lastResult);

// 同时保留原有的返回值（向后兼容）
return ExecutionResult.Success(lastResult ?? new object());
```

#### 改动2：EventBindingStageBase 从 Functor 获取结果

```csharp
// EventBindingStageBase.cs — HandleExecutionResult 中
protected async Task HandleExecutionResult(
    ExecutionResult result,
    string functionName,
    string? output,
    object sender,
    Action<string, string, object?>? onResult,
    string eventName)
{
    if (result.IsSuccess)
    {
        object? resolvedValue = result.Value;

        // ★ 优先从 Functor 获取结果（如果存在 Functor 作用域）
        if (Functor.Current != null && !string.IsNullOrEmpty(output))
        {
            var functorValue = Functor.Current.Get(output);
            if (functorValue != null)
                resolvedValue = functorValue;
        }

        // ★ 回退：当 result.Value 是 Dictionary 时，提取指定键的值
        if (resolvedValue is System.Collections.IDictionary dict &&
            !string.IsNullOrEmpty(output) &&
            dict.Contains(output))
        {
            resolvedValue = dict[output];
        }

        // ... 写入控件
    }
}
```

#### 改动3：EventBindingStageBase 创建 Functor 作用域

```csharp
// EventBindingStageBase.cs — 事件处理方法中
// 创建 Functor 作用域，用于传递工作流参数和结果
using var scope = Functor.Begin("EventBinding");

// 将输出目标存入 Functor
scope.Set("output", output);

// 执行工作流
var result = await _executionService.ExecuteFunctionAsync(functionName, parameters);

// HandleExecutionResult 从 Functor 获取结果
```

#### 改动4：配置中添加 outputKey

```json
{
  "name": "Add",
  "type": "delegate",
  "outputKey": "value",
  "parameters": [
    { "name": "a", "type": "System.Double" },
    { "name": "b", "type": "System.Double" }
  ]
}
```

### 5.4 方案B：Functor 完整数据总线（远期目标）

#### 完整调用链

```
EventBindingStageBase:
  → 创建 Functor 作用域: Functor.Begin("EventBinding")
  → 将参数存入 Functor: scope.Set("a", 123).Set("b", 456)
  → 调用工作流（无需传递 Dictionary）

WorkflowMethodExecutionService:
  → 从 Functor 获取参数: Functor.Current?.Get("a")
  → 执行工作流节点

NodeExecutor:
  → 从 Functor 获取参数
  → 调用 FunctionExecutor

FunctionExecutor:
  → 从 Functor 获取参数
  → 执行函数
  → 将结果存入 Functor: Functor.Current?.Set("result", 579)

HandleExecutionResult:
  → 从 Functor 获取结果: Functor.Current?.Get("result")
  → 写入控件
  → 释放 Functor 作用域
```

#### 优势

1. **中间层零修改**：WorkflowMethodExecutionService 和 NodeExecutor 不需要显式传递 Dictionary
2. **返回值格式统一**：所有函数的结果都通过 Functor 传递，不需要区分 delegate 和 workflow
3. **消除包装-拆包循环**：不再需要 `Dictionary → object?[] → Dictionary` 的冗余转换
4. **类型安全**：Functor 支持按类型存取，编译时检查

#### 劣势

1. **隐式数据流**：参数从哪里来不直观，降低代码可读性
2. **调试困难**：隐式传播的数据在调试时不易追踪
3. **作用域管理**：需要确保 Functor 作用域的正确创建和释放

### 5.5 推荐实施路径

| 阶段 | 内容 | 优先级 | 时间 |
|------|------|--------|------|
| **阶段1** | 修复4：ExecuteWorkflowAsync 统一返回值格式 | P0 | 立即 |
| **阶段2** | 修复1：ParameterBuilder 感知函数签名 | P1 | 阶段1后 |
| **阶段3** | 方案A：Functor 统一返回值 | P1 | 阶段2后 |
| **阶段4** | 修复2+3：消除包装-拆包循环 | P2 | 阶段3后 |
| **阶段5** | 方案B：Functor 完整数据总线 | P3 | 远期 |

## 6. 修复方案汇总

| 修复 | 缺陷 | 改动文件 | 改动类型 |
|------|------|---------|----------|
| 修复1 | 缺陷1：参数构建多余 | `ParameterBuilder.cs`, `ParameterBuilderStages.cs`, `EventBindingStageBase.cs` | 代码修改 |
| 修复2 | 缺陷3：接口缺少 Dictionary 重载 | `IFunctionExecutor.cs`, `FunctionExecutor.cs`, `NodeExecutor.cs` | 接口扩展 + 代码修改 |
| 修复3 | 缺陷4：拆包逻辑 | `FunctionExecutor.cs` | 代码删除 |
| 修复4 | 缺陷2：返回值不统一 | `WorkflowMethodExecutionService.cs`, `MathFunctions.unified.json` | 代码修改 + 配置修改 |
| 方案A | Functor 统一返回值 | `EventBindingStageBase.cs`, `WorkflowMethodExecutionService.cs` | Functor 集成 |

### 6.1 修复优先级

| 优先级 | 修复 | 理由 |
|--------|------|------|
| P0 | 修复4：返回值统一 | 直接影响所有函数的输出结果 |
| P1 | 修复1：参数构建精简 | 消除数据污染，提高可调试性 |
| P1 | 方案A：Functor 统一返回值 | 框架级优化，统一返回值处理 |
| P2 | 修复2+3：消除包装-拆包循环 | 性能优化，代码简洁 |

### 6.2 向后兼容性

- `IFunctionExecutor` 新增 Dictionary 重载是**非破坏性变更**（新增方法，不影响现有实现）
- `ParameterBuilder.Build()` 新增可选参数是**非破坏性变更**（默认值 `null`，不影响现有调用）
- `FunctionExecutor` 移除 Dictionary 检测逻辑是**潜在破坏性变更**（如果其他调用方依赖 `object?[]` 重载的自动拆包功能）
- Functor 集成是**非破坏性变更**（新增逻辑，不影响现有路径）
