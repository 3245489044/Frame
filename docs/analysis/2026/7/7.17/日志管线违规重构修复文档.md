## 1. 问题概述

项目中存在大量绕过日志管线的**直接打印调用**（`Debug.WriteLine` / `Console.WriteLine` / `Trace.WriteLine`），违反了 `Architecture.md` 定义的日志架构规范。

**直接后果**：以 `MathFunctions.unified.json` 按钮点击无日志触发为例——`EventBindingDiagnosticContext.Record()` 使用 `Debug.WriteLine` 输出，在 Release 构建下完全不可见，在 Debug 构建下也只能通过调试器查看，导致事件绑定管线的可观测性为零。

## 2. 架构规范回顾

### 2.1 分层职责与日志 API

| 层 | 角色 | 应使用的日志 API | 说明 |
|----|------|-----------------|------|
| **Operation** | 日志消费者 | **各自模块的专用日志类**：`BackEndLog.Log` / `WdUILog.Log` / `WorkFlowMethodLog.Log` / `EventTriggerLog.Log` / `FsLog.Log` / `IocLog.Log` / `ExecutionLog.Log` | 通过 `LogPlaceholderHandlerBase.Log` 统一入口，但调用方应使用模块封装后的 `XxxLog.Log`，而非直接调用底层 API |
| **Share** | 插桩生产者 | **`EventBindingDiagnosticContext.Record`**（插桩事件） / **`ModuleLog.Log`**（模块日志） | 只负责记录结构化事件，不关心日志如何输出。禁止使用 Operation 层的 `XxxLog.Log` |
| **Share.Diagnostics** | 基础设施 | `LogRepository.Write` | 日志管线编排、内存仓库、SQLite 持久化 |
| **Modules** | 纯逻辑层 | **无日志代码** | 正确性通过单元测试和集成测试维护，不依赖运行时日志 |
| **Modules.DiagnosticContext** | 插桩框架 | 框架内部可保留合理的 Debug 降级 | AsyncLocal 传播、作用域管理、事件存储 |
| **BasicMethod** | 工具/基础设施 | **日志框架类保留**，非日志工具类**禁止日志** | 如 `LogRepository` / `LogCollapser` / `LogFilterLoader` 等日志框架自身可保留；其他工具类应删除日志或改为抛异常 |

### 2.2 作用域专属日志 API 对照

#### Operation 层 — 各模块专用日志入口

| 模块 | 日志类 | 命名空间 | KeyPrefix | 调用示例 |
|------|--------|----------|-----------|---------|
| BackEndDriven | `BackEndLog.Log` | `BackEndDriven.Diagnostics` | `backend:` | `BackEndLog.Log("MethodName_desc", new { key, value })` |
| EventTrigger | `EventTriggerLog.Log` | `EventTriggerFramework.Diagnostics` | `eventtrigger:` | `EventTriggerLog.Log("EventName_desc", data)` |
| WdUI | `WdUILog.Log` | `WdUI.Diagnostics` | `wdui:` | `WdUILog.Log("MethodName_desc", new { key })` |
| WorkFlowMethod | `WorkFlowMethodLog.Log` | `WorkFlowMethod.Diagnostics` | `workflowmethod:` | `WorkFlowMethodLog.Log("MethodName_desc", data)` |
| FileDriven.Execution | `ExecutionLog.Log` | `FileDriven.Execution.Diagnostics` | `exec:` | `ExecutionLog.Log("MethodName_desc", data)` |
| FileDriven.Business | `FsLog.Log` | `FileDriven.Business.Diagnostics` | `fs:` | `FsLog.Log("MethodName_desc", data)` |
| BackEndDriven.IoC | `IocLog.Log` | `BackEndDriven.Diagnostics` | `ioc:` | `IocLog.Log("MethodName_desc", data)` |

#### Share 层 — 插桩与模块日志

| 场景 | API | 调用示例 |
|------|-----|---------|
| 记录插桩事件 | `EventBindingDiagnosticContext.Record` | `Record("eventbinder.event.triggered", new { controlName })` |
| 创建诊断作用域 | `EventBindingDiagnosticContext.BeginScope()` | `using var scope = BeginScope();` |
| 模块通用日志 | `ModuleLog.Log(msgId, data, moduleName, keyPrefix)` | `ModuleLog.Log("pipeline_step_start", data, "GraphFramework", "graph:")` |

### 2.3 禁止事项

| # | ❌ 禁止 | 原因 |
|---|---------|------|
| 1 | Share 层使用 `BackEndLog.Log` / `WdUILog.Log` 等 Operation 层日志 | 依赖消息字典注册，属于 Operation 层控制范畴 |
| 2 | Operation 层直接调用 `DiagnosticContext.Record` | 应通过 `EventBindingDiagnosticContext` 封装调用 |
| 3 | **任何层使用 `System.Diagnostics.Debug.WriteLine` / `Console.WriteLine` / `Trace.WriteLine` 等直接打印方式** | 直接打印绕过框架日志管线，无法被日志系统统一管理和持久化 |
| 4 | **Modules 层包含任何日志代码** | Modules 层是纯逻辑层，正确性通过测试维护 |
| 5 | **BasicMethod 层非日志框架代码包含日志** | 工具类不应有日志行为，错误应通过异常向上传播 |
| 6 | **Share 层在 catch 块中静默吞掉异常（仅 Record 不重新抛出）** | 事件触发时无活跃 DiagnosticContext，Record 降级到 Debug.WriteLine 不可见，错误被静默吞掉 |

**设计规范（供后续新增模块参考）：**

```csharp
// 每个 Share 子项目创建一个 XxxDiagnosticContext 静态类
namespace Xxx.Diagnostics;

public static class XxxDiagnosticContext
{
    public static void Record(string eventName, object? data = null)
    {
        var context = Modules.DiagnosticContext.Core.DiagnosticContext.Current;
        context?.Record(eventName, data);
    }
}
```

**关键约束：**
- ❌ 不包含 `Debug.WriteLine` / `Console.WriteLine` / `Trace.WriteLine`
- ❌ 不包含 `#if DEBUG` 条件编译
- ❌ 不引用 `LogPlaceholderHandlerBase` / `ModuleLog` 等日志输出 API
- ✅ 只通过 `DiagnosticContext.Current?.Record()` 记录事件
- ✅ 方法签名统一为 `Record(string eventName, object? data = null)`

```csharp
throw new JsonException($"序列化失败: {ex.Message}", ex);
```

> **保留的日志框架类：** `LogRepository`、`LogCollapser`、`LogFilterLoader`、`Printer`（打印工具类设计如此）

## 7. Operation 层应用 Share 的逻辑

### 7.1 架构关系

Operation 层是**日志消费者**，Share 层是**插桩生产者**。两者通过 Share 层的 `LogPlaceholderHandlerBase.Log` 统一入口汇合：

```
┌─────────────────────────────────────────────────────────────┐
│                      Operation 层（日志消费者）                │
│                                                             │
│  BackEndLog.Log  WdUILog.Log  WorkFlowMethodLog.Log  ...    │
│       │              │                │                      │
│       └──────────────┼────────────────┘                      │
│                      ▼                                       │
│              LogBase.Log()                                    │
└──────────────────────┼──────────────────────────────────────┘
                       │ 委托
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                   Share 层（日志管线入口）                     │
│                                                             │
│  LogPlaceholderHandlerBase.Log(msgId, module, keyPrefix,     │
│       data)                                                  │
│       │                                                      │
│       ▼                                                      │
│  LogRepository.Write(entry) → 内存仓库 → SQLite 持久化       │
│                                                             │
│  ─── 插桩通道（职责分离）───                                   │
│  XxxDiagnosticContext.Record(eventName, data)                │
│       │                                                      │
│       ▼                                                      │
│  DiagnosticContext.Current?.Record(eventName, data)          │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 调用链说明

Operation 层的日志调用链：

```
XxxLog.Log(msgId, data)
  → LogBase.Log(moduleName, keyPrefix, msgId, data)      // Operation/BackEndDriven/Diagnostics/LogBase.cs
    → LogPlaceholderHandlerBase.Log(msgId, module, keyPrefix, data)  // Share/PlaceholderFramework
      → ConvertParameters(data) → FormatTemplate(msgId, parameters)  // 模板填充
        → LogRepository.Write(logEntry)                              // 写入内存仓库
          → 控制台输出 / SQLite 持久化                                // 由日志框架配置决定
```

### 7.3 Operation 日志类 vs Share 插桩类

| 维度 | Operation 日志类（XxxLog.Log） | Share 插桩类（XxxDiagnosticContext.Record） |
|------|-------------------------------|-------------------------------------------|
| **角色** | 日志消费者 | 插桩生产者 |
| **输出方式** | 通过 `LogPlaceholderHandlerBase.Log` 进入日志管线 | 通过 `DiagnosticContext.Current?.Record` 记录结构化事件 |
| **依赖** | 依赖消息字典注册（`xxx_log_messages.json`） | 不依赖消息字典，事件名直接作为字符串 |
| **调用方** | Operation 层各模块的业务代码 | Share 层各模块的内部逻辑 |
| **典型场景** | 记录业务操作（"工作流开始"、"按钮点击"） | 记录架构事件（"管线步骤执行"、"命令解析失败"） |
| **是否可观测** | 是，通过日志框架配置输出到控制台/文件/SQLite | 是，通过 DiagnosticContext 框架传播，由日志框架消费 |

### 7.4 Operation 层修复指引

Operation 层的违规代码（`Debug.WriteLine` / `Trace.WriteLine`）应替换为对应模块的 `XxxLog.Log`：

| 模块 | 日志类 | 命名空间 | 调用示例 |
|------|--------|----------|---------|
| WorkFlowMethod | `WorkFlowMethodLog.Log` | `WorkFlowMethod.Diagnostics` | `WorkFlowMethodLog.Log("WorkflowLogger_LogExecutionStart", new { planId })` |
| WdUI | `WdUILog.Log` | `WdUI.Diagnostics` | `WdUILog.Log("RenderPipeline_Render_start", new { })` |
| BackEndDriven | `BackEndLog.Log` | `BackEndDriven.Diagnostics` | `BackEndLog.Log("MethodName_desc", new { key })` |
| EventTrigger | `EventTriggerLog.Log` | `EventTriggerFramework.Diagnostics` | `EventTriggerLog.Log("EventName_desc", data)` |
| IoC | `IocLog.Log` | `BackEndDriven.Diagnostics` | `IocLog.Log("MethodName_desc", data)` |

**替换规则：**

```csharp
// ❌ 错误：直接 Debug.WriteLine
Debug.WriteLine($"[INFO] 工作流开始: PlanId={planId}");

// ✅ 正确：使用模块专用日志 API
WorkFlowMethodLog.Log("WorkflowLogger_LogExecutionStart", new { planId, planName });

// ❌ 错误：直接 Trace.WriteLine
Trace.WriteLine($"[Execution] 执行完成: {result}");

// ✅ 正确：使用模块专用日志 API
WorkFlowMethodLog.Log("RefactoredExecution_ExecuteAsync_completed", new { result });
```

> **注意：** Operation 层的 `XxxLog.Log` 依赖 `xxx_log_messages.json` 消息字典注册。替换前需确保对应的消息 ID 已在 JSON 文件中定义。如果消息 ID 不存在，需要先在 JSON 文件中添加对应的模板条目。
>
> **消息字典文件位置：**
> - `CsharpPrj/Operation/BackEndDriven/backend_log_messages.json`
> - `CsharpPrj/Operation/BackEndDriven/ioc_log_messages.json`
> - `CsharpPrj/Operation/WdUI/wdui_log_messages.json`
> - `CsharpPrj/Operation/WorkFlowMethod/workflowmethod_log_messages.json`
> - `FileDriven/filedriven_log_messages.json`
