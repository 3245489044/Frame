### 2.2 复杂度根源分析

#### 根源 1：演进式架构的"层叠抽象"

从代码注释中的日期标记可以看到演进历史：

```
07-06: 从 EventTriggerFramework 迁移到 Share 层 → 加一层适配
07-07: 新增 GenericEventBindingPipeline → 加一条新管线
07-08: WinFormsEventBus 基于 DefaultEventBus → 加一层委托
07-10: IEventBus 为主重构 → 加 DynamicMethod 包装
07-13: Modules.Pipeline 替代手动 foreach → 加管线抽象
07-15: 迁移到 TConfig → 加接口抽象
07-16: IEventBindingIoC 新增 → 加 IoC 容器
07-17: StaticPipeline 替代 StagePipeline → 换管线实现
```

**每次重构都在"加一层"而不是"减一层"**。每次新增需求时，自然反应是加接口、加适配器、加管线步骤，而不是重新审视整体架构。

#### 根源 2：三个变化维度揉进一个管线

真正的变化维度有三个，但被揉进了一个管线：

| 维度 | 变化来源 | 当前处理方式 |
|------|---------|------------|
| A：事件源类型 | WinForms / WPF / 自定义 | 全部走 WinFormsEventBus |
| B：函数执行策略 | Delegate / Workflow / Script | 全部包装为工作流 |
| C：参数绑定策略 | ControlBinding / Literal / Expression | 全部走 ParameterTransformer |

管线步骤数量 ≈ A × B × C 的笛卡尔积。每个步骤都要处理所有维度的组合。

#### 根源 3：管线步骤冗余

当前 10 步管线中存在不必要的步骤拆分：

| 冗余点 | 说明 |
|-------|------|
| ValidateInput + ControlFinder 分离 | 两个步骤都操作控件，可合并 |
| DiagnosticsScope + EmptyViewGuard + StatisticsCollect 分离 | 三个编排器步骤可合并为一个 |
| EventNameNormalization + EventInfoResolution + BindOrWrap 分离 | 三个事件总线步骤可内联 |
| ConfigBinding + DeclarationBinding 分离 | 已内联为静态方法，但管线结构仍保留 |

**10 步中有 5 步是多余的步骤拆分，合并后应为 5 步。**

#### 根源 4：IEventBindingIoC 违反 ISP ✅ 第一阶段已解决

> **当前状态**：`IEventBindingIoC` 已拆分为 3 个子接口（`IFunctionResolver`/`IParameterBinder`/`IEventBinder`），每个子接口 2-4 个方法。旧 `IEventBindingIoC` 接口定义已移动到 `Dispose/` 目录。

`IEventBindingIoC` 原来把 5 个不同职责塞进一个接口：

```
IEventBindingIoC（20+ 成员）
├── 函数注册查询（ResolveWorkflow, ResolveDelegate）
├── 参数绑定（PrecomputeParameterSources, CreatePreResolvedHandler）
├── 事件绑定（TryBindEvent, RecordBoundControl）
├── 诊断（RecordDiagnostic, BeginDiagnosticScope 等 4 个）
└── 生命周期（Validate, Reset）
```

#### 根源 5：重构只做加法不做减法 ✅ 部分已解决

> **当前状态**：双轨注册路径已合并为单轨（`ITrConfigRegistry`，阶段7），`IEventBindingIoC` 已拆分为 3 个子接口（阶段5），8 个 Stage 类已内联为静态方法（阶段4）。剩余废弃抽象待阶段6清理。

每次重构都在增加新的抽象层，从未系统地清理旧代码。导致：
- 6+ 个废弃/未使用的抽象仍然存在于代码中
- ~~双轨注册路径（IFunctionRegistry + ITrConfigRegistry）共存~~ ✅ 已合并为单轨
- 旧接口的 95 处引用阻碍了直接删除

#### 根源 6：3 个 StaticPipeline 实例分散而非 1 个统一管线

EventBindingOrchestrator 已在 2026-07-17 的重构中从 StagePipeline 迁移到 `Modules.Pipeline.StaticPipeline`，但管线仍然分散在 3 个不同的 StaticPipeline 实例中：

| StaticPipeline 实例 | 所在类 | 步骤数 |
|-------------------|--------|-------|
| 编排器管线 | `EventBindingOrchestrator.cs` | 4 步 |
| 事件触发管线 | `EventBindingPipelineFactory.cs` | 3 步 |
| 绑定管线 | `WinFormsEventBus.cs` | 3 步 |

**问题**：
- 10 步管线分散在 3 个 StaticPipeline 实例中，步骤间通过可变上下文传递数据
- 3 个管线实例串联执行，但每个管线内部是内联 Step，整体仍然是线性链
- 没有利用 Pipeline 模块的 `Pipeline.RegisterStage()` 编排器模式（当前使用 StaticPipeline 而非 Pipeline）

**改进方向**：合并 3 个 StaticPipeline 为 1 个统一管线（5 步），步骤间通过不可变 record 传递数据。

## 第三部分：修改步骤

### 核心原则

> **统一管线 + 条件分支**
>
> 所有场景走同一条管线，管线内部通过条件分支处理不同场景的差异。
> 保持管线的统一性，避免多路径带来的维护成本。

### 实施路线图

```
时间线 →
├── 3.1 引入新能力 ────────┤ 先打好基础，为后续重构提供能力支撑
│   ├── 阶段1：引入标准 DI（Microsoft.Extensions.DependencyInjection）
│   ├── 阶段2：引入 FluentValidation
│   └── 阶段3：诊断剥离（新建 DiagnosticsMiddleware）
│
├── 3.2 重构阶段 ──────────┤ 在已有新能力的基础上改造现有代码
│   ├── 阶段4：安全清理（删除废弃代码）
│   ├── 阶段5：接口拆分（IEventBindingIoC → 3 个子接口）
│   ├── 阶段6：管线扁平化（10 步 → 5 步）
│   └── 阶段7：统一注册路径（IFunctionRegistry → ITrConfigRegistry）
```

#### 阶段 2：引入 FluentValidation

**当前问题**：`ValidateInput` 步骤是自研的 if-else 验证逻辑，没有复用项目中已有的 `FluentValidation`（v12.1.1）。

**借鉴来源**：CommandFramework 模块和 UniversalMiddleware 模块已正确使用 FluentValidation 的验证器模式。

**具体步骤**：

1. **定义验证器**
   ```csharp
   public class EventBindingContextValidator : AbstractValidator<EventBindingContext>
   {
       public EventBindingContextValidator()
       {
           RuleFor(x => x.Form).NotNull().WithMessage("Form 不能为空");
           RuleFor(x => x.UiConfig).NotNull().WithMessage("UiConfig 不能为空");
           RuleFor(x => x.UiConfig.Events)
               .NotNull()
               .Must(events => events.Count > 0)
               .WithMessage("Events 配置不能为空");
       }
   }
   ```

2. **替换 `ValidateInput` 步骤**
   ```csharp
   // 当前：自研 if-else 验证
   private static void ValidateInput(EventBindingContext context)
   {
       if (context.Form == null) throw ...;
       if (context.UiConfig?.Events == null) throw ...;
   }
   
   // 目标：FluentValidation
   private static void ValidateInput(EventBindingContext context)
   {
       var validator = new EventBindingContextValidator();
       var result = validator.Validate(context);
       if (!result.IsValid)
           throw new ValidationException(result.Errors);
   }
   ```

3. **验证方法**
   - ✅ 编译通过
   - ✅ 验证器单元测试（覆盖 null Form、null UiConfig、空 Events 等边界）
   - ✅ 集成测试（验证通过和验证失败的场景）
   - ✅ 验证错误信息比自研 if-else 更详细

**风险与回退**：
- 风险：低（仅替换 1 个步骤，不影响其他步骤）
- 回退：保留旧 ValidateInput 实现，通过配置切换

**风险与回退**：
- 风险：低（增量进行，逐个步骤迁移）

#### 阶段 6：管线扁平化（高风险，需全面测试）

**当前问题**：10 步管线分散在 3 个 StaticPipeline 实例中，步骤间通过可变上下文传递数据。

**借鉴来源**：Container 模块的不可变 record + 统一管线模式。

**具体步骤**：

1. **将管线步骤的输入/输出改为不可变 record**
   ```csharp

   {
       public Form? Form { get; set; }
       public UnifiedUiConfig? UiConfig { get; set; }
       public bool SkipPipeline { get; set; }
   }
   
   // 目标：不可变 record（步骤间传递新 record，而非修改旧 record）
   public record EventBindingInput(Form Form, UnifiedUiConfig UiConfig);
   public record BindingMetadata(Control Control, EventConfig EventConfig);
   public record BoundHandler(Delegate Handler, string EventName);
   ```

2. **合并 3 个 StaticPipeline 为 1 个统一管线（5 步）**
   ```

     编排器：ValidateInput → DiagnosticsScope → EmptyViewGuard → StatisticsCollect
     绑定管线：ControlFinder → BindingMetadata → ConfigBinding/DeclarationBinding
     事件总线：EventNameNormalization → EventInfoResolution → BindOrWrap
   
   合并后 5 步（统一管线）：
     Step 1: 参数验证 + 控件查找（合并 ValidateInput + ControlFinder）
     Step 2: 绑定元数据解析（合并 BindingMetadata + EventNameNormalization + EventInfoResolution）
     Step 3: 参数绑定（支持 ControlBinding / Literal / Expression）
     Step 4: 函数执行（支持 Delegate / Workflow / Script）
     Step 5: 结果处理（写回控件 / 回调 / 诊断）
   ```

3. **统一管线示意图**
   ```
   请求入口
       │
       └─ 统一管线（5 步）
           ├─ Step 1: 参数验证 + 控件查找
           │   ├─ 验证输入参数合法性（FluentValidation，阶段 2）
           │   └─ 根据控件名查找真实 WinForms 控件
           │
           ├─ Step 2: 绑定元数据解析
           │   ├─ 从 Events 配置提取绑定元数据
           │   ├─ 事件名标准化（EventNameNormalization）
           │   └─ 事件信息解析（EventInfoResolution）
           │
           ├─ Step 3: 参数绑定
           │   ├─ [ControlBinding] 从控件读取值
           │   ├─ [Literal] 使用字面量
           │   └─ [Expression] 表达式求值
           │
           ├─ Step 4: 函数执行
           │   ├─ [Delegate] 直接调用 Delegate
           │   ├─ [Workflow] 执行工作流编排
           │   └─ [Script] 执行脚本
           │
           └─ Step 5: 结果处理
               ├─ 写入输出目标控件
               ├─ 触发回调
               └─ 记录诊断事件（DiagnosticsMiddleware，阶段 3）
   ```

### A. 术语表

| 术语 | 定义 |
|------|------|
| **统一管线** | 所有场景走同一条 5 步管线，内部通过条件分支处理差异 |

| **AOP（面向切面编程）** | 将横切关注点（如诊断）从业务逻辑中分离的技术，本文中指 DiagnosticsMiddleware |
| **ISP（接口隔离原则）** | SOLID 原则之一，不应强迫客户端依赖它们不使用的接口 |
| **DiagnosticsMiddleware** | AOP 中间件，自动记录管线步骤的进入/离开/异常，替代内联诊断代码 |
| **FunctionRegistryAdapter** | 适配器类，包装 ITrConfigRegistry 以实现 IFunctionRegistry 接口，用于双轨统一 |
| **StaticPipeline** | 内联 Step 的管线实现，替代了旧的 StagePipeline（5 个 Stage 类） |
| **标杆模块** | 项目中设计良好的模块（Container、StateBlockDriven、FileDriven.Execution、WorkFlowMethod），其设计框架可被其他模块借鉴 |
| **设计框架借鉴** | 分析已有优秀模块的设计模式，将其核心架构（如不可变 record、Actor 模型、三层嵌套）应用到当前问题模块的渐进式改进中 |
| **Actor 模型** | 将每个职责封装为独立的 Actor（实例化、私有状态、消息驱动），借鉴自 StateBlockDriven 模块 |
| **MediatR** | 第三方 NuGet 包，提供进程内消息中介（命令/查询/事件），核心抽象为 IRequest/IRequestHandler/IPipelineBehavior。项目中 Container 模块使用 MediatR 作为执行容器的基础设施 |
| **Pipeline 模块** | 项目自研的通用管线编排框架（`CsharpPrj/Modules/Pipeline`），提供三体系管线抽象：A) 链式传参 IPipeline<TIn,TOut>；B) 共享配置 IStage；C) 编排器 Pipeline.RegisterStage() |
| **MediatR vs Pipeline 模块** | 两者是互补关系而非替代关系：MediatR 解决消息分发问题（发消息→找处理器→执行），Pipeline 模块解决流程编排问题（定义阶段→编排顺序→执行流程）。项目中 Container 模块同时使用两者 |

### B. 决策日志

| 日期 | 决策 | 选项 | 选择理由 |
|------|------|------|---------|
| 2026-07-17 | 三层路径 vs 统一管线 | ① 三层路径 ② 统一管线 + 条件分支 | 统一管线更简洁，避免多路径维护成本；所有场景走同一路径，内部通过条件分支处理差异 |
| 2026-07-17 | Facade 模式 vs 直接删除旧接口 | ① Facade ② 直接删除 | Facade 允许逐步迁移，降低风险；直接删除会导致大规模编译错误 |
| 2026-07-17 | 诊断中间件 vs 保留内联 | ① 中间件 ② 内联 | 中间件集中管理诊断逻辑，业务代码减少 30-50%，且提供 Fallback 模式 |
| 2026-07-17 | 适配器模式 vs 直接替换注册路径 | ① 适配器 ② 直接替换 | 95 处引用需要逐步迁移，适配器允许新旧共存直到验证完成 |
| 2026-07-17 | MediatR 替换 Pipeline vs 保留两者互补 | ① MediatR 替换 ② 保留互补 | 两者定位不同（消息中介 vs 管线编排），项目中 Container 模块已正确同时使用两者。EventBindingOrchestrator 已使用 StaticPipeline，无需引入 MediatR |
| 2026-07-17 | 合并 3 个 StaticPipeline 为 1 个统一管线 vs 保留 3 个分散管线 | ① 合并统一 ② 保留分散 | EventBindingOrchestrator 已在 2026-07-17 重构中从 StagePipeline 迁移到 StaticPipeline，但管线仍分散在 3 个实例中（编排器 4 步 + 事件触发 3 步 + 绑定 3 步）。合并为 1 个统一管线可消除步骤间可变上下文耦合，合并冗余步骤（10 步 → 5 步） |
