## 一、🔴 严重 Bug（可能导致数据损坏或崩溃）

### 1.1 ArchetypeManager.AddComponent 的回滚逻辑在并发下可能导致数据不一致

**文件**：`Archetype/ArchetypeManager.cs` 第 141-157 行

```csharp
catch
{
    try
    {
        if (_entityArchetype.TryGetValue(entity, out var current) && current == targetArchetype)
        {
            targetArchetype.MoveEntity(entity, currentArchetype, _componentTypeId);
            _entityArchetype[entity] = currentArchetype;
        }
    }
    catch (Exception rollbackEx)
    {
        System.Diagnostics.Debug.WriteLine(
            $"ArchetypeManager.AddComponent: Rollback failed for {entity} on {typeof(T).Name}: {rollbackEx.Message}");
    }
    throw;
}
```

**问题分析**：
- `MoveEntity` 成功后，`currentArchetype` 中已经没有该 entity 的记录，但回滚时假设 `currentArchetype` 还是原来的状态
- 如果 `MoveEntity` 成功但 `SetComponent` 失败，entity 已经在 `targetArchetype` 中，回滚时再次 `MoveEntity` 回到 `currentArchetype`，但 `currentArchetype` 可能已被其他线程修改
- 回滚失败只记录 Debug.WriteLine，不抛出异常，导致调用方以为操作失败但实际部分数据已修改
- 没有使用锁保护整个操作，多线程环境下 Archetype 字典可能被并发修改

**修复建议**：
- 将 AddComponent 的整个操作（MoveEntity + SetComponent）放在一个事务性范围内
- 使用写锁保护整个操作
- 回滚失败时应抛出异常，而非静默忽略

### 1.2 RelationManager.RemoveAllRelations 在读锁中调用会导致死锁

**文件**：`Relations/RelationComponent.cs` 第 358-371 行

```csharp
public void RemoveAllRelations(Entity e)
{
    if (_globalLock.IsWriteLockHeld)
    {
        RemoveAllRelationsCore(e);
    }
    else
    {
        using (var globalWrite = Locking.Lock.Write(_globalLock))
        {
            RemoveAllRelationsCore(e);
        }
    }
}
```

**问题分析**：
- 只检查了是否持有**写锁**，没有检查是否持有**读锁**
- 如果在读锁中调用 `RemoveAllRelations`，会尝试获取写锁 → **读锁升级写锁导致死锁**
- `OnEntityDestroyed` 事件处理器中调用 `RemoveAllRelations`，而 `DestroyEntity` 可能在读锁或写锁中被调用
- `ReaderWriterLockSlim` 不支持读锁升级到写锁（除非使用 `LockRecursionPolicy.SupportsRecursion`，但即使如此也需要先释放读锁）

**修复建议**：
- 添加 `IsReadLockHeld` 检查，如果持有读锁则先释放再获取写锁
- 或者在调用 `RemoveAllRelations` 前确保不持有读锁
- 考虑使用独立的锁而非与 `_worldLock` 共享

### 1.3 Chunk.GetComponentSpan 的潜在类型转换异常

**文件**：`Archetype/Chunk.cs` 第 90-96 行

```csharp
public Span<T> GetComponentSpan<T>(ComponentTypeId componentTypeId) where T : struct, IComponent
{
    int typeId = componentTypeId.GetId(typeof(T));
    if (!_componentColumns.TryGetValue(typeId, out var column))
        return Span<T>.Empty;
    return new Span<T>((T[])column, 0, _count);
}
```

**问题分析**：
- `column` 通过 `Array.CreateInstance(component.GetType(), Capacity)` 创建，运行时类型是 `Array` 而非 `T[]`
- `(T[])column` 强制转换在运行时如果类型不匹配会抛出 `InvalidCastException`
- 虽然逻辑上 typeId 对应的列类型应该匹配 T，但没有运行时验证
- 如果 `ComponentTypeId.GetId` 返回的 ID 与预期类型不匹配（例如由于缓存或并发问题），会导致崩溃

**修复建议**：
- 在调试模式下添加类型检查
- 使用 `column.GetType().GetElementType()` 验证类型匹配
- 或者将 `_componentColumns` 改为 `Dictionary<int, Array>` 并添加类型安全的访问方法

## 二、🟠 中等 Bug（逻辑错误或设计缺陷）

### 2.1 ArchetypeManager.AddComponent 的签名检查可读性差

**文件**：`Archetype/ArchetypeManager.cs` 第 122 行

```csharp
int typeId = _componentTypeId.GetId(typeof(T));
if (typeId < currentSig.Components.Length && currentSig.Components[typeId])
```

**问题分析**：
- 当 `typeId >= currentSig.Components.Length` 时条件为 false，不会抛出异常
- 逻辑上正确（越界意味着该 Component 不存在），但可读性差

```csharp
bool alreadyHas = typeId < currentSig.Components.Length && currentSig.Components[typeId];
if (alreadyHas)
    throw new InvalidOperationException($"Entity {entity} already has component {typeof(T).Name}");
```

### 2.2 EntityManager.GetComponent/SetComponent 缺少 HasComponent 检查

**文件**：`ECSFrame.cs` 第 183-207 行

```csharp
public T GetComponent<T>(Entity entity) where T : struct, IComponent

    ThrowIfDisposed();

        if (!_archetypeManager.HasComponent<T>(entity))  // 这里检查了

    }
```

**问题分析**：
- `GetComponent<T>` 没有检查 Entity 是否拥有该 Component
- 如果 Entity 没有该 Component，`chunk.GetComponent<T>` 会抛出 "not in this chunk" 异常，但错误信息不够友好
- `SetComponent` 却检查了 `HasComponent`，策略不一致

**修复建议**：
- 在 `GetComponent<T>` 中添加 `HasComponent` 检查，抛出更友好的错误信息
- 或者在 `ArchetypeManager.GetComponent<T>` 中添加检查

### 2.3 ArchetypeManager.DestroyEntity 在移除前触发 ComponentRemoved 事件

**文件**：`Archetype/ArchetypeManager.cs` 第 83-113 行

```csharp
public void DestroyEntity(Entity entity)
{
    ...

    try
    {
```

**修复建议**：
- 先 `RemoveEntity` 再触发事件
- 或者明确文档说明事件触发时 entity 的状态

### 2.4 RelationManager 的 _pendingDestroy 时序问题

**文件**：`Relations/RelationComponent.cs` 第 240/271/410 行

```csharp
private readonly ConcurrentDictionary<Entity, byte> _pendingDestroy = new();

// HandleRelationComponentRemoved 中：
if (_pendingDestroy.ContainsKey(entity))
    return;

// RemoveAllRelationsCore 中：
foreach (var ent in visited)
    _pendingDestroy.TryAdd(ent, 0);

// 注释说明：释放写锁后再销毁 Entity，避免死锁
```

**问题分析**：
- `_pendingDestroy` 在 `RemoveAllRelationsCore` 的写锁内设置
- 但实际销毁 Entity 在写锁外（第 414 行注释说明）
- 写锁释放后、实际销毁前，其他操作可能看到不一致的状态
- `HandleRelationComponentRemoved` 检查 `_pendingDestroy` 来避免重复处理，但时序窗口存在

**修复建议**：
- 将实际销毁操作移到写锁内，或者使用两阶段提交模式
- 考虑使用不可变快照来避免时序问题

### 2.5 IndexManager.RegisterIndex 回滚不完整

**文件**：`Relations/RelationComponent.cs` 第 546-563 行

```csharp
try
{
    using (var globalWrite = Locking.Lock.Write(_globalLock))
    {
        index.Rebuild(_em);
    }
}
catch
{
    // 回滚：先移除 _idx 中的条目
    using (var writeLock = Locking.Lock.Write(_indexLock))
    {
        _idx.Remove(typeof(T));
    }
```

**问题分析**：
- 如果 `Rebuild` 失败，回滚只移除了 `_idx` 条目并尝试取消注册 handler

**修复建议**：

- 或者在 `Rebuild` 失败时调用 index 的清理方法

## 五、⚪ 未重构完全的储存逻辑

### 5.1 IECSStorage 只管理 ID，不管理数据持久化

**问题**：
- `IECSStorage` 当前只用于 Entity ID 管理（版本号、回收池、Archetype ID）
- 从使用方式看，接口包含：`GetEntityVersion`, `SetEntityVersion`, `AddFreeEntityId`, `TakeFreeEntityId`, `GetAllEntityArchetypeIds`
- 没有看到将 Archetype/Chunk/Component 数据持久化的接口
- 说明"储存重构"只完成了 ID 管理部分，数据存储部分还未重构

**涉及文件**：`Archetype/ArchetypeManager.cs`（多处引用 `_ecsStorage`）

### 5.2 ArchetypeManager 完全在内存中操作

**问题**：
- 所有 Archetype、Chunk、Entity 数据都在内存的 `Dictionary` 中
- `IECSStorage` 只用于 ID 管理，不存储实际数据
- 程序重启后所有数据丢失
- 没有快照/序列化/恢复机制

**涉及文件**：`Archetype/ArchetypeManager.cs`

### 5.3 ComponentTypeId 和 RelationType 的模式重复

**文件**：`ComponentTypeId.cs` 和 `Relations/RelationComponent.cs`

**问题**：
- 两者都使用 `IStorageRegistry` 做 ID 注册
- 都使用类似的 key 前缀模式（`name_to_id`, `id_to_name`）
- 都使用 `NextId`/`CounterName` 分配 ID
- 可以抽象出一个通用的 `IdRegistry<T>` 基类

**重复模式**：
```
ComponentTypeId:  comp_type_to_id: / comp_id_to_type: / ComponentTypeId
RelationType:     rel_name_to_id: / rel_id_to_name: / RelationTypeId
```
