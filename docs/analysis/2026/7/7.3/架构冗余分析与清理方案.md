# 架构冗余分析与清理方案

> 分析日期：2026-07-02
> 背景：按钮点击事件链路涉及 6 个项目、20+ 文件，接口继承链 3-4 层，核心问题在于持续重构叠加未清理。

---

## 一、根本原因

### 1. 多次架构迁移，旧层未清理

| 迁移方向 | 旧 | 新 | 状态 |
|---------|-----|-----|------|
| GUI 初始化 | `FileDrivenGuiInitializer` | `FileDrivenGuiInitializerOrchestrator`（继承 `InitializationOrchestrator`） | 新旧并存 |
| 函数执行 | `IFunctionExecutionService` | `IFunctionRegistry` | 旧接口已删，但包装层残留 |
| 事件执行 | `Func` 委托 | `IEventExecutionService` 接口 | 接口与 `IFunctionRegistry` 功能重叠 |
| 事件管线 | `BackEndEventPipelineExecutor` | `EventExecutionService`（直接实现 Share 接口） | 旧类已标记但未删除 |

### 2. "Share" 层抽象过度

`EventBindingOrchestrator` 放在 `Share` 层，定义了：
- `IEventExecutionService` — 事件执行服务接口
- `IWinFormsEventBinder` — WinForms 事件绑定器接口
- `IEventBindingService` — 事件绑定服务接口

然后 `FileDriven` 和 `BackEndDriven` 各自实现这些接口，中间还要通过 `ComponentRegistry` 做服务定位。

### 3. 模板系统与事件系统耦合

`action-button` 模板的 `buildEvents: true` 逻辑和运行时事件绑定逻辑混在一起，模板展开结果直接影响事件绑定能否成功。

### 4. ComponentRegistry 作为全局服务定位器

本来 DI 容器能解决的问题，硬是手写了一个 `ComponentRegistry`，而且经常忘记注册服务。

### 5. 没有回归测试

每次重构都没有自动化测试验证"按钮点击→函数执行"这条核心链路。

---

## 二、冗余代码清单（可直接删除的）

### 2.1 `ComponentRegistry.cs` — 手写服务定位器，与 DI 容器重复

**文件**：`CsharpPrj/Share/FrameworkAbstractions/ComponentRegistry/ComponentRegistry.cs`

**问题**：项目已经用了 `Microsoft.Extensions.DependencyInjection`（见 `FrameworkInitializer.cs`），但又手写了一个全局单例 `ComponentRegistry`。两套服务注册机制并存。

**引用分布**（7 个文件，20+ 处调用）：

| 文件 | 用途 |
|------|------|
| `FileDrivenGuiInitializerOrchestrator.cs` | 获取 `IFunctionRegistry`、`IEventPipelineExecutor` |
| `WinFormsEventBinder.cs` | 获取 `IControlService` |
| `MainForm.cs` | 注册 `IControlRegistry` |
| `CommandLayer.cs` | 获取 `IControlValueWriter` |
| `UICommandManager.cs` | 获取 `IControlValueWriter` |
| `UnifiedControlService.cs` | 获取 `IControlFinder`、`IControlValueWriter`、`IControlRegistry` |
| `ControlServiceCollectionTests.cs` | 测试中注册/解析服务 |

**删除条件**：所有 `ComponentRegistry.Instance.Resolve<T>()` 替换为 `IServiceProvider.GetRequiredService<T>()` 后，整个文件可删。

---

### 2.2 `EventExecutionService` 的双重职责 — 旧方法未清理

**文件**：`CsharpPrj/Operation/BackEndDriven/Execution/EventExecutionService.cs`

这个类有 **两套方法**：

| 方法 | 用途 | 状态 |
|------|------|------|
| `Execute(controlName, eventType, value)` | 旧的事件→管线路径 | **冗余**，仅被 `EventPipelineExecutor.Execute()` 调用 |
| `BuildEventCommand(controlName, eventType)` | 构建命令字符串 | **冗余**，仅被 `Execute` 调用 |
| `CreateContext(command)` | 创建管线上下文 | **冗余**，虚方法但从未被重写 |
| `ExecuteFunctionAsync(functionName, parameters)` | 新接口，直接执行函数 | **核心路径** |
| `HasFunction(functionName)` | 检查函数是否存在 | **核心路径** |

**删除条件**：确认 `EventPipelineExecutor.Execute()` 不再调用 `_eventExecutionService.Execute()` 后，这 3 个方法可删。

---

### 2.3 `EventPipelineExecutor` — 整层包装，职责重复

**文件**：`FileDriven/FileDriven.Execution/EventPipeline/EventPipelineExecutor.cs`

调用链：
```
EventPipelineExecutor.Execute(controlName, eventType, value)
  → _eventExecutionService.Execute(controlName, eventType, value)
    → EventExecutionService.Execute(controlName, eventType, value)
      → BuildEventCommand → CreateContext → ExecutePipelineInternal
        → GetOrCreateSingleCommandPipeline().Execute(pipelineContext)
```

**5 层委托才执行一条命令**。而且 `EventPipelineExecutor` 自己创建了一个 `EventExecutionService` 实例，`FileDrivenGuiInitializerOrchestrator` 又创建了另一个，**同一个类被实例化了两次**。

**删除条件**：将管线执行逻辑合并到 `EventExecutionService` 或直接内联到调用处后，整个文件可删。

---

### 2.4 `FileDrivenGuiInitializerOrchestrator` — 过度设计的编排层

**文件**：`FileDriven/FileDriven.Execution/Gui/FileDrivenGuiInitializerOrchestrator.cs`

继承 `InitializationOrchestrator<MainForm>`，重写了 6 个虚方法，但核心逻辑只有：
1. 创建 `MainForm`（10 行代码）
2. 从 `ComponentRegistry` 获取服务并创建 `EventExecutionService`
3. 创建 `WinFormsEventBinder`（4 行代码）
4. 从 `WdUIUsage.RenderPipeline.EventBinder` 获取 `IEventBindingService`

为了这 4 件事，搞了一个完整的"编排器"继承体系（`InitializationOrchestrator` + 4 个策略类 + 6 个重写方法）。

---

### 2.5 `IEventExecutionService` 接口 — 与 `IFunctionRegistry` 功能重叠

**文件**：`CsharpPrj/Share/EventBindingOrchestrator/Abstractions/IEventExecutionService.cs`

```csharp
public interface IEventExecutionService
{
    Task<ExecutionResult> ExecuteFunctionAsync(string functionName, object?[]? parameters);
    bool HasFunction(string functionName);
}
```

`IFunctionRegistry` 接口：
```csharp
public interface IFunctionRegistry
{
    bool Contains(string name);
    bool TryGetDelegate(string name, out Delegate? function);
    void Register(string name, Delegate function, string? description = null);
}
```

`IEventExecutionService.ExecuteFunctionAsync` = `IFunctionRegistry.TryGetDelegate` + `DynamicInvoke`
`IEventExecutionService.HasFunction` = `IFunctionRegistry.Contains`

**两个接口功能完全重叠**。

**删除条件**：让调用方直接依赖 `IFunctionRegistry` 后，`IEventExecutionService` 接口和 `ExecutionResult` 结构体可删。

---

### 2.6 `BackEndEventPipelineExecutor` — 已被替代的旧实现

**文件**：`CsharpPrj/Operation/BackEndDriven/Execution/BackEndEventPipelineExecutor.cs`

已被 `EventExecutionService` 替代（`EventExecutionService` 直接实现 `Share.IEventExecutionService`），但文件仍然存在。

## 三、问题区域（需要重构的）

### 3.1 `EventBindingTransformers.cs` — 职责过重

**文件**：`CsharpPrj/Operation/EventTriggerFramework/EventBinding/EventBindingTransformers.cs`（630 行）

一个文件包含 4 个 Transformer，其中 `EventBinderTransformer` 同时做两件事：
- **遍历事件**：遍历标准事件和自定义事件
- **创建 handler 并绑定**：`CreateEventHandler` 方法 83 行

而且 `CreateEventHandler` 内部又包含了：
- 参数构建（`BuildParametersFromBindings`）
- 结果写入（`WriteOutputToControl`）
- 值获取（`GetControlValueStatic`）

**建议**：拆分为 `EventTraversalTransformer`（遍历事件）+ `EventHandlerBinder`（创建 handler 并绑定）。

### 3.2 `FrameworkInitializer.cs` — 初始化流程散乱

**文件**：`FileDriven/FileDriven.Execution/Lifecycle/FrameworkInitializer.cs`

初始化流程散落在多个地方：
- `FrameworkInitializer.Initialize()` — 初始化 6 个组件
- `FileDrivenGuiInitializerOrchestrator` — 创建 MainForm 和 EventExecutionService
- `FileDrivenExecutor.Run()` — 9 步骨架
- `MainForm.OnInitializeAsync()` — UI 加载流程

一个"按钮点击→函数执行"的链路，初始化代码分布在 **4 个文件** 中。

## 四、清理方案（三阶段）

### Phase 1：止血 — 统一服务注册，消除 ComponentRegistry（1-2天）

| 步骤 | 操作 | 影响范围 |
|------|------|----------|
| 1.1 | 将 `ComponentRegistry` 标记为 `[Obsolete]`，所有新代码禁止使用 | 全局 |
| 1.2 | 在 `FrameworkInitializer` 中创建统一的 `IServiceProvider`，将所有服务注册到 DI | `FrameworkInitializer.cs` |
| 1.3 | 将 `ComponentRegistry.Instance.Resolve<T>()` 调用替换为 `IServiceProvider.GetRequiredService<T>()` | 7 个文件 |
| 1.4 | 删除 `ComponentRegistry.cs`（或移到 `_Obsolete` 目录） | `Share/FrameworkAbstractions/` |

### Phase 2：清理 — 简化事件绑定链路（2-3天）

| 步骤 | 操作 | 影响范围 |
|------|------|----------|
| 2.1 | 合并 `IEventExecutionService` 与 `IFunctionRegistry`，让调用方直接依赖 `IFunctionRegistry` | `Share/EventBindingOrchestrator/` |
| 2.2 | 删除 `EventExecutionService` 的 `Execute`/`BuildEventCommand`/`CreateContext` 方法 | `BackEndDriven/Execution/EventExecutionService.cs` |
| 2.3 | 删除 `EventPipelineExecutor.cs` | `FileDriven/FileDriven.Execution/EventPipeline/` |
| 2.4 | 简化 `FileDrivenGuiInitializerOrchestrator` 为顺序调用 | `FileDriven/FileDriven.Execution/Gui/` |
| 2.5 | 删除 `BackEndEventPipelineExecutor.cs` | `CsharpPrj/Operation/BackEndDriven/Execution/` |

### Phase 3：治本 — 解耦模板与事件，建立测试体系（3-5天）

| 步骤 | 操作 | 影响范围 |
|------|------|----------|
| 3.1 | 模板系统只输出数据，不参与事件绑定 | `JsonTemplateProcessor` |
| 3.2 | 为 `IFunctionRegistry` 建立单元测试 | `CentralTest/CSharpTest/` |
| 3.3 | 为 `EventBindingService` 建立集成测试 | `CentralTest/CSharpTest/` |
| 3.4 | 建立"按钮点击→函数执行"端到端测试 | `CentralTest/CSharpTest/` |

## 五、架构原则（后续开发必须遵守）

1. **禁止新增 `ComponentRegistry` 使用**：所有服务通过 DI 容器（`IServiceProvider`）获取
2. **接口层数 ≤ 2**：调用方 → 接口 → 实现，禁止超过 2 层接口继承
3. **每个类一个职责**：如果看到"同时做 A 和 B"的方法，立即拆分
4. **核心链路必须有测试**：涉及"配置加载→UI渲染→事件绑定→函数执行"的修改，必须附带测试
5. **重构必须清理旧代码**：加新层的同时删除旧层，不允许"先留着后面删"

---

## 六、理想目标

按钮点击事件的理想路径：

```
按钮点击 → EventHandler(从IFunctionRegistry获取委托) → DynamicInvoke
```

而不是现在的：

```
按钮点击 → EventBinderTransformer.CreateEventHandler 
  → IEventExecutionService.ExecuteFunctionAsync 
    → EventExecutionService(检查IFunctionRegistry) 
      → IFunctionRegistry.TryGetDelegate 
        → DynamicInvoke
```

**4 层接口调用 → 1 层直接调用**，这就是最根本的简化方向。
