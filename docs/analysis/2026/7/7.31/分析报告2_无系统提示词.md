# `FrontEndDriven` 代码分析报告

经过对 `CsharpPrj/Operation/FrontEndDriven` 目录下核心文件的详细审查，以下是发现的**重复逻辑、冗余逻辑、错误逻辑**分析：

---

## 一、重复逻辑 (Duplicate Logic)

### 1.1 Entity 名称获取逻辑重复 —— 两处独立实现 `GetEntityName`

| 文件 | 位置 |
|---|---|
| `ControlLookup/EcsEntityTreeWalker.cs` | Line 184-195 |
| `Validation/EntityValidationHelper.cs` | Line 30-37 |

两处代码功能完全相同：读取 `ControlTypeComponent.Name` → 回退到 `Entity#{Id}`。虽然一个是实例方法（`EcsEntityTreeWalker`），一个是静态方法（`ValidationHelper`），但本质是同一业务逻辑的重复编码。

**建议**：提取到单一公共辅助类中，例如 `Shared/Abstractions/` 下的静态方法。

### 1.2 ControlData → CanonicalProps 与 ControlData → ControlDescriptor 适配结构重复

**文件**：`Ports.cs`

- `ToCanonicalProps()` (L279-333) 和 `ToControlDescriptor()` (L343-399)
- 两个方法的判断结构完全一致：`if(data.HasLayout) → 写布局字段` / `if(data.HasStyle) → 写样式字段` / `if(data.EventBindings) → 写事件绑定`
- 虽然输出目标不同（`Dictionary<string,object?>` vs `ControlDescriptor`），但字段映射关系多次重复书写

**建议**：定义一个 `ControlData → T` 的映射器模式或使用 Mapper（如 Mapster/AutoMapper）消除手动映射。

### 1.3 `ControlTypeRegistry` 与 `ContractRegistry` 角色重叠

**文件**：
- `Shared/ControlTypeRegistry.cs` — 管理控件类型注册表（工厂+Schema工厂+容器标记）
- `Shared/ContractRegistry.cs` — 契约注册中心，但底层完全遍历 `ControlTypeRegistry.SchemaFactories`

`ContractRegistry.RegisterAll()` (L40-44) 遍历 SchemaFactories 重新注册一遍，相当于对同一数据源的二次包装。新增控件类型只需在 `ControlTypeRegistry` 加一行，`ContractRegistry` 的循环注册带来的间接层无明显收益。

**建议**：考虑将 `ContractRegistry` 降级为对 `ControlTypeRegistry.SchemaFactories` 的直接委托查询，消除注册循环。

### 1.4 `EventBindingSystem` 和 `IEventBindingService` 两个事件绑定体系并存

**文件**：
- `ControlInteraction/EventBinding/EventBindingSystem.cs` — ECS System 版，只实现了 `click`
- `ControlInteraction/EventBinding/IEventBindingService.cs` — 独立接口体系，包含 `BindEvent`/`UnbindEvent`/UI线程调度

两者都处理"事件→函数"的绑定，但路径完全不同。`EventBindingSystem` 通过 `EventBindingsComponent` → switch(click) → 注册 EventHandler；`IEventBindingService` 通过 `BindEvent(control, eventName, handler)` 更通用。

**问题**：两个体系之间没有桥接机制，`EventBindingSystem` 只硬编码了 `click` 事件，switch 的 default 分支仅记录日志。

### 1.5 `CompositeValueWriter` 的 RegisterAdapter 和 ClearAdapters 行为不一致

**文件**：`ControlInteraction/CompositeValueWriter.cs`

```csharp
// RegisterAdapter (L100): 只注册到最后一个 writer
_writers[_writers.Count - 1].RegisterAdapter(controlType, getter, setter);

// ClearAdapters (L106-109): 广播到所有 writer
foreach (var w in _writers) { w.ClearAdapters(); }
```

注册是"单播"，清除是"广播"——语义不一致。

## 二、冗余逻辑 (Redundant Logic)

### 2.1 EcsEntityTreeWalker 缓存机制过度设计

**文件**：`ControlLookup/EcsEntityTreeWalker.cs` (L37-177)

使用三重组件的缓存失效跟踪：
- `_cacheDirty`（bool flag）
- `_cacheVersion`（int 版本号）
- `_lastEntityCount`（Entity 总数）

`EnsureCache()` 的入口判断（L145-153）过于复杂：
```csharp
if (_childrenCache != null && !_cacheDirty)
{
    var currentCount = _entityManager.GetAllEntities().Count();
    if (currentCount == _lastEntityCount && _cacheVersion == 0)
        return;
    _cacheDirty = true;  // 此处设 dirty 但后续重建会覆盖
}
```

**问题**：
- `_cacheDirty` 和 `_cacheVersion` 记录的是同一件事（ParentEntityComponent 变更），二选一即可
- 方法内重建时（L152）设置了 `_cacheDirty = true`，但重建后（L176）立即设为 `false`，中间状态未利用
- `_cacheVersion` 重建后重置为 0，那么 `_cacheDirty` 作为冗余标志变得无用

### 2.2 `Ports.cs` 单文件 890 行，三个非相关类共存

`Ports.cs` 包含了三个不相关的顶级类：
- `CsgEntryPoint`（CSG 状态收集）
- `WinFormsOutputPort`（输出端口）
- `EcsInputPort`（输入端口）

每个类功能独立，应拆分到各自文件。

### 2.3 `ContractBuilder.DockAllowedValues`/`AnchorAllowedValues` 委托链过长

```
FrontEndDrivenConstants.DockAllowedValues → 原始定义
  ContractBuilder.DockAllowedValues → 委托 FrontEndDrivenConstants
```

`ContractBuilder` 的私有属性（L22-26）就是一行委托，可直接引用常量消除此间接层。

### 2.4 `EventSubscriptionManager` 三个公开方法 + 一个私有泛型方法

三个泛型重载（Subscribe\<TEventArgs\>、Subscribe\<T\>、Subscribe）都委托到 `SubscribeInternal`。其实可以通过单一泛型方法 + 委托转换简化。

### 2.5 `RenderAuditPort` 中的 SafeCollect 包装

6 个审计步骤每个都被 `SafeCollect` 包装（L59-74），但 `SafeCollect` 只是 try-catch + 日志。若需要步骤隔离，可考虑 `List<Action>` 统一遍历而非 6 次显式调用。

## 三、错误逻辑 (Erroneous Logic)

### 3.1 ❌ `EventBindingSystem.Update()` → ClearBoundHandlers 导致 handler 泄漏

**文件**：`ControlInteraction/EventBinding/EventBindingSystem.cs`

```csharp
// Line 42: 清空字典，但不移除已注册的事件处理器
public void ClearBoundHandlers() => _boundHandlers.Clear();

// Line 73-98: Update 时在注册新 handler 前移除旧 handler
if (_boundHandlers.TryGetValue(entity.Id, out var existingHandlers))
    foreach (var h in existingHandlers)
        control.Click -= h;
```

**问题**：`ClearBoundHandlers()` **只清空字典但不 -= 事件处理器**。调用 `ClearBoundHandlers()` 后，下次 `Update()` 认为没有旧 handler，不会执行 -=，导致旧 handler 泄漏，新 handler 叠加，点击事件被触发多次。

**触发条件**：在两次 Update 之间调用 `ClearBoundHandlers()`（如重新绑定事件流）。

### 3.2 ❌ `EcsEntityTreeWalker.Dispose()` 接口不可见

**文件**：`ControlLookup/EcsEntityTreeWalker.cs`

```csharp
public void Dispose()  // 实现类有 Dispose
{
    _entityManager.ComponentUpdated -= OnComponentUpdated;
}
```

但 `IEntityTreeWalker` 接口（L25-46）**没有继承 IDisposable**，调用方通过接口引用无法调用 `Dispose()`，导致事件订阅泄漏。

### 3.3 ❌ `SyncControlInfoComponent` 注释与实际代码不符

**文件**：`Ports.cs` (WinFormsOutputPort, L723-737)

```csharp
// 注释说"防止 WinForms 控件 Name 属性被意外修改时覆盖原始配置名称"
// 但实际代码根本没读 Name，只读了 Text/Enabled/Visible
info.Text = _adapter.GetText(control) ?? info.Text;
info.Enabled = _adapter.GetEnabled(control);
info.Visible = _adapter.GetVisible(control);
```

注释误导。另外 `GetText` 使用了 null-coalescing，但 `GetEnabled` 和 `GetVisible` 不区分"默认值 vs 用户设的值"。

### 3.4 ❌ `ControlConfigTarget.HasField()` 值类型判断逻辑有缺陷

**文件**：`Shared/ControlConfigTarget.cs` (L109-114)

```csharp
if (prop.PropertyType.IsValueType)
{
    return _config.ExtensionData?.Keys
        .Any(k => string.Equals(k, fieldName, StringComparison.OrdinalIgnoreCase)) == true;
}
```

**问题**：`bool`、`int` 等值类型字段的"是否存在"完全依赖 `ExtensionData`（JSON 反序列化额外数据）。
- 如果 JSON 序列化器**没有**在 `ExtensionData` 中记录该字段（取决于序列化配置），则 `HasField` 永远返回 `false`
- 对于 `bool` 类型，用户显式设 `"enabled": false` 时 `ExtensionData` 不一定包含 "enabled" 键（某些序列化器会跳过默认值）

这意味着某些值类型字段的校验可能不可靠。

### 3.5 ❌ `ControlConfigTarget.GetFieldValue()` 仅返回 string 类型属性但不提示

**文件**：`Shared/ControlConfigTarget.cs` (L128-154)

```csharp
public string? GetFieldValue(string fieldName)
{
    var prop = typeof(ControlConfig).GetProperty(fieldName, ...);
    if (prop == null || prop.PropertyType != typeof(string))
        return null;  // 对非 string 字段静默返回 null
    ...
    if (_config.ExtensionData == null || !_config.ExtensionData.Keys.Any(...))
        return null;  // 对未在 ExtensionData 中显式设置的字段也返回 null
}
```

**问题**：对非 string 字段（如 `enabled` bool、`width` int）和方法内对 ExtensionData 中无记录的字段**都返回 null**，调用方无法区分"字段不存在" vs "字段值为空" vs "非 string 字段不支持"三种情况。

### 3.6 ❌ `ValidationResult.GetSummary()` 中 `PassedCount` 语义混淆

**文件**：`Validation/EntityValidationResult.cs`

```csharp
public int PassedCount => Math.Max(0, TotalChecked - TotalIssues);
```

`TotalChecked` 是 Entity 数，`TotalIssues` 是 Error+Warning 总数。但一个 Entity 可能有多个问题，`TotalChecked - TotalIssues` 可能为负数。虽然 `Math.Max(0, ...)` 防止了负数，但语义上 `PassedCount` 不再是"通过的 Entity 数"。
