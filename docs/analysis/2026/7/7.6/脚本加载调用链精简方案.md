# 脚本加载调用链精简方案

> **目标**：将 4-5 层嵌套的脚本加载链精简为 2 层，消除冗余包装，提升可调试性
> **日期**：2026-07-05

---

## 1. 现状分析

### 1.1 完整调用链

#### 链路 A：脚本加载（JSON → 命令列表）

```
ScriptLoadSkeleton (FileDriven.Execution)
  └─ 继承 BackEndScriptLoadSkeleton<TContext> (BackEndDriven)        ← 第1层包装
       └─ 委托调用 ScriptConverter.ConvertJsonScriptToCommandFile()  ← 第2层包装
            ├─ JsonPipelineRegistry.Process()                         ← 第3层包装（模板展开管线）
            │    └─ 内部管线：ReferenceExpansionStage 等
            └─ ScriptToCommandConverter.Convert()                    ← 第4层包装
                 └─ ScriptDefinition.ToCommandText()
                      └─ ScriptCommand.ToCommandText()
       └─ File.ReadAllLines()  ← 读取临时文件
            └─ CommandLineFilter.ShouldSkip()  ← 过滤空行/注释
```

**层级统计**：4 层嵌套，跨 4 个项目（Execution → BackEndDriven → Utilities → PlaceholderFramework）

#### 链路 B：命令遍历执行（命令列表 → 逐条执行）

```
PipelineEntry (共享状态)
  └─ ForEachSkeleton<TContext, TItem> (泛型骨架)
       ├─ itemsSelector: ctx => ctx.CommandLines
       ├─ onItemPrepare: (ctx, item) => ctx.CurrentCommand = item    ← 外部注入
       │    └─ 子管线:
       │         ├─ ParseCommandStage
       │         │    └─ CommandParser.Parse(currentCommand)         ← 消费 CurrentCommand
       │         ├─ ExecuteCommandStage
       │         └─ ResultCollectStage
       └─ onItemAfter: 更新统计
```

**问题**：CurrentCommand 的设置（onItemPrepare）和消费（ParseCommandStage）之间隔了一个泛型骨架层

### 1.2 核心问题清单

| 编号 | 问题 | 位置 | 严重程度 |
|------|------|------|----------|
| P1 | **临时文件中间状态** | ScriptConverter 写临时文件 → BackEndScriptLoadSkeleton 再读取 | 高 |
| P2 | **onItemPrepare 外部注入** | CurrentCommand 的设置和消费分离 | 高 |
| P3 | **泛型基类包装过度** | BackEndScriptLoadSkeleton 仅做委托转发 | 中 |
| P4 | **模板展开管线冗余** | JsonPipelineRegistry 的管线只包含一个有效阶段 | 低 |

---

## 2. 目标架构

### 2.1 精简后的调用链

#### 链路 A（目标）：脚本加载

```
ScriptLoadSkeleton (FileDriven.Execution)
  └─ 直接调用 ScriptConverter.ConvertJsonToCommands()  ← 返回 string[]
       └─ 直接调用模板引擎展开模板
       └─ 直接调用 ScriptToCommandConverter.Convert()
```

**层级**：2 层，无中间文件 I/O

#### 链路 B（目标）：命令遍历执行

```
ForEachSkeleton
  └─ itemsSelector: ctx => ctx.CommandLines
       └─ ParseCommandStage 内部从 CommandLines[currentIndex] 读取
```

**改进**：CurrentCommand 不再通过 onItemPrepare 传递，由 ParseCommandStage 自行管理

### 2.2 职责重新划分

| 组件 | 当前职责 | 目标职责 |
|------|----------|----------|
| ScriptLoadSkeleton | 继承基类 + 日志包装 | 直接调用 ScriptConverter + 日志 |
| BackEndScriptLoadSkeleton | 泛型委托转发 + 文件读取 | **废弃** |
| ScriptConverter | 模板展开 + 写临时文件 | 模板展开 + 返回 string[] |
| JsonPipelineRegistry | 管线包装模板展开 | **内联**到 ScriptConverter |
| ParseCommandStage | 从 CurrentCommand 读取 | 从 CommandLines[index] 读取 |

---

## 3. 重构方案

### 3.1 方案 C（P0）：消除临时文件中间状态

**现状**：
```
ScriptConverter.ConvertJsonScriptToCommandFile() → 返回 string? (文件路径)
BackEndScriptLoadSkeleton → File.ReadAllLines(文件路径) → CommandLines
```

**目标**：
```
ScriptConverter.ConvertJsonScriptToCommands() → 返回 string[]? (命令列表)
ScriptLoadSkeleton → 直接赋值给 CommandLines
```

**变更内容**：

1. **ScriptConverter.cs**：新增方法 `ConvertJsonScriptToCommands()`，返回 `string[]?`
   - 保留 `ConvertJsonScriptToCommandFile()` 作为兼容接口（标记 `[Obsolete]`）
   - 内部逻辑：模板展开 → 命令转换 → 按行分割 → 返回数组

2. **ScriptLoadSkeleton.cs**：不再继承 BackEndScriptLoadSkeleton
   - 直接调用 `ScriptConverter.ConvertJsonScriptToCommands()`
   - 直接赋值 `ctx.CommandLines = result`

3. **BackEndScriptLoadSkeleton.cs**：标记为废弃（确认无其他调用方后删除）

**影响范围**：
- `FileDriven/FileDriven.Utilities/CLI/ScriptConverter.cs`
- `FileDriven/FileDriven.Execution/Pipeline/Factory/ScriptLoadSkeleton.cs`
- `CsharpPrj/Operation/BackEndDriven/Pipeline/BackEndScriptLoadSkeleton.cs`

**风险**：低。返回值类型变更，但调用方只有 ScriptLoadSkeleton。

---

### 3.2 方案 D（P1）：onItemPrepare 内联化

**现状**：
```
ForEachSkeleton.ExecuteCore:
  foreach (var item in items)
  {
      _onItemPrepare?.Invoke(input, item);  // 设置 CurrentCommand
      var result = _itemPipeline.Execute(input);  // ParseCommandStage 消费
  }
```

**目标**：
```
ForEachSkeleton.ExecuteCore:
  for (int i = 0; i < items.Count; i++)
  {
      input.CurrentIndex = i;  // 只传递索引
      var result = _itemPipeline.Execute(input);
  }

ParseCommandStage:
  var cmd = context.CommandLines[context.CurrentIndex];  // 自行读取
```

**变更内容**：

1. **ForEachSkeleton.cs**：新增 `CurrentIndex` 属性到上下文，替代 `onItemPrepare`
2. **ParseCommandStage.cs**：从 `context.CommandLines[context.CurrentIndex]` 读取命令
3. **FileDrivenPipelineContext.cs**：新增 `CurrentIndex` 属性

**影响范围**：
- `FileDriven/FileDriven.Execution/Pipeline/Stages/ParseCommandStage.cs`
- `FileDriven/FileDriven.Execution/Context/FileDrivenPipelineContext.cs`
- 泛型骨架 `ForEachSkeleton` 的调用方

**风险**：中。需要确认 ForEachSkeleton 的其他使用场景是否也依赖 onItemPrepare。

---

### 3.3 方案 A（P2）：消除泛型基类包装

**现状**：
```
ScriptLoadSkeleton : BackEndScriptLoadSkeleton<FileDrivenPipelineContext>
  └─ base.ExecuteCore()  →  委托调用 _convertJsonScript(scriptPath)
```

**目标**：
```
ScriptLoadSkeleton : SyncSkeletonBase<FileDrivenPipelineContext, FileDrivenPipelineContext>
  └─ ExecuteCore() 直接调用 ScriptConverter
```

**前提条件**：方案 C 实施后，BackEndScriptLoadSkeleton 不再被需要。

**变更内容**：

1. **ScriptLoadSkeleton.cs**：改为直接继承 `SyncSkeletonBase`
2. **BackEndScriptLoadSkeleton.cs**：标记 `[Obsolete]`，确认无其他调用方后删除

**影响范围**：
- `FileDriven/FileDriven.Execution/Pipeline/Factory/ScriptLoadSkeleton.cs`
- `CsharpPrj/Operation/BackEndDriven/Pipeline/BackEndScriptLoadSkeleton.cs`

**风险**：低。前提是方案 C 已实施。

---

### 3.4 方案 B（P3）：内联模板展开

**现状**：
```
ScriptConverter:
  JsonPipelineRegistry.Process(jsonContent, jsonFilePath)
  └─ 内部管线：多个 Stage，但只有 ReferenceExpansionStage 有效
```

**目标**：
```
ScriptConverter:
  SimpleTemplateEngine.Expand(jsonContent, templateConfig)  // 直接调用
  ScriptToCommandConverter.Convert(expandedJson)
```

**前提条件**：需要确认 JsonPipelineRegistry 是否还有其他调用方。

**变更内容**：

1. **ScriptConverter.cs**：直接调用模板引擎 API
2. **JsonPipelineRegistry.cs**：标记为废弃或保留供其他场景使用

**影响范围**：
- `FileDriven/FileDriven.Utilities/CLI/ScriptConverter.cs`
- `CsharpPrj/Share/PlaceholderFramework/Defaults/JsonPipelineRegistry.cs`

**风险**：高。模板展开逻辑复杂，直接调用引擎 API 可能遗漏某些管线阶段的功能。

## 4. 实施优先级

```
P0 ─── 方案 C：消除临时文件 ─── 立即实施
  │
P1 ─── 方案 D：onItemPrepare 内联化 ─── 方案 C 之后
  │
P2 ─── 方案 A：消除泛型基类 ─── 方案 C 之后
  │
P3 ─── 方案 B：内联模板展开 ─── 待评估
```

### 实施顺序说明

1. **方案 C 优先**：收益最大（消除一次文件 I/O + 一层包装），影响最小（只改 ScriptConverter 和 ScriptLoadSkeleton）
2. **方案 D 其次**：需要方案 C 先稳定，因为涉及上下文结构的变更
3. **方案 A 依赖方案 C**：方案 C 消除了 BackEndScriptLoadSkeleton 的核心功能，之后才能安全删除
4. **方案 B 最后评估**：风险最高，需要充分测试模板展开的兼容性

## 5. 风险评估

### 5.1 方案 C

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 返回值变更导致编译错误 | 低 | 高 | 保留旧方法标记 Obsolete |
| 内存占用增加（不再写文件） | 低 | 低 | 命令列表通常 < 100 条 |

### 5.2 方案 D

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 影响 ForEachSkeleton 其他调用方 | 中 | 高 | 先搜索所有调用方，逐个评估 |
| CurrentIndex 线程安全 | 低 | 中 | 当前为单线程执行 |

### 5.3 方案 A

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 有其他调用方依赖 BackEndScriptLoadSkeleton | 中 | 高 | 先搜索引用，保留 Obsolete 版本 |

### 5.4 方案 B

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 遗漏管线阶段功能 | 中 | 高 | 先分析 JsonPipelineRegistry 所有 Stage 的职责 |
| 模板展开行为不一致 | 低 | 高 | 对比新旧路径的输出 |
