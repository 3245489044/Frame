## 一、背景与动机

### 1.1 事件矩阵备用调用链的删除与遗留缺口

提交 `e239cb4c`（删除事件矩阵备用调用链，obsolete标记逻辑）整体删除了「Entity→Idle→Matrix→Handler」备用链路：

| 删除组件 | 原职责 |
|----------|--------|
| `ExecutionLoopManager` | Idle 轮询驱动请求提交 + `ExecutionResultReadyEvent` Reactor 推送驱动 UI 再渲染 |
| `FunctionExecutionSystem` | 轮询 `ExecutionRequestComponent` 提交 Matrix |
| `EcsGate.ExecuteFunctionAndWaitAsync` | TCS 等待执行结果 |
| Matrix "ExecuteFunction" Handler 注册 | 经 Router 执行工作流 |

**删除动机（历史根因）**：该链路依赖 `Application.Idle` 轮询消费 `ExecutionRequestComponent`；在脚本密集执行（命令循环 + 渲染管线）期间 UI 线程难得空闲，Idle 轮询得不到及时触发 → 函数请求 30 秒超时（测试日志全部按钮函数 + exec 命令超时）。`FunctionCallFacade` 被迫改为直达 `IEventExecutionService`（无 Idle、无 Matrix）。

### 1.2 删除后的遗留缺口（本次重构的核心动机）

备用链被砍掉后重构不彻底，产生了新缺口：

1. **`EventPlatform`（公共事件平台）从未真正接管执行**：`InvokeFunctionAsync` 仅是 `FunctionCallFacade` 的薄委托，未承载约束校验（Fail-Fast/模式路由/超时/审计集中度不足）。
2. **`function.Executed` 事件零订阅者**：备用链曾以结果事件驱动 UI 再渲染，删除后当前主链无任何"结果→UI"触发点（全仓 grep 确认所有 `ExecuteRenderStage()` 调用均来自配置加载/重算路径）。
3. **函数执行入口分散**：按钮反射 Delegate、exec 命令 `ExecSystem`、生命周期钩子 `ConfigurationLifecycleManager`、`EventPlatform` 各自拼 `FunctionCallRequest` 直调静态门面，违反"聚拢点唯一入口"原则。
4. **多层容器事件存在结构化问题**（MainLayout.json）：控件查找靠反射 `Controls.Find` 穿透嵌套容器可能匹配错层级；动态容器（contentContainer/sideContainer）加载后事件绑定依赖每帧轮询 Pending 重试，有状态同步延迟。

### 1.3 用户原始意图与决策演进

- **原始意图**：构建"集中的事件池（多播事件）+ ECS 约束校验"，让事件像矩阵元素那样做代数组合/聚合变换，工作流事件运行用矩阵实现。
- **技术评审结论**（本方案记录）：
  - `MatrixEngine` 当前**不支持**复杂事件代数运算（Router 仅为"单事件→单算子"路由表派发，无事件集合组合/聚合语义）。
  - 未来 Agent 工作流需要的是**编排（DAG/状态机/组合子）**而非矩阵代数；`MatrixEngine` 的 `SchedulerSystem`（依赖 DAG）+ `RouterSystem`（算子路由）+ `RetrySystem`（容错）实为**工作流编排引擎**骨架，被"矩阵"命名误导。
  - **当前 UI 场景 1:1 简单触发，矩阵事件运算无落点**。
- **最终决策**：本次只做**层一**（结构化事件池 + 收编执行 + 结果驱动 UI）；**矩阵事件运算/MatrixEngine 重塑（层二）留待 Agent 工作流立项再做**，避免为猜想的未来过度设计（这正是当初"引入大量包装"的教训）。

## 二、现状分析

### 2.1 当前事件生态：4 个事件/执行载体并存

| 载体 | 语义 | 位置 | 问题 |
|------|------|------|------|
| `EventPlatform` | 统一事件总线 + 函数调用入口（委托 FunctionCallFacade） | `FrontEndDriven/Eventing` | `function.Executed` 零订阅；`InvokeFunctionAsync` 仅薄委托，未承载约束校验 |
| `TConfig.IEventBus` 系（DefaultEventBus/EventBusFacade/WinFormsEventBus） | 控件事件绑定 | `Modules/EventFramework` / `Share` | 多实现共存，绑定链与执行链割裂 |
| `FunctionCallFacade` | 静态门面（Sync/Background/Auto + 超时 + 审计） | `BackEndDriven/Gate` | **静态类**不经任何事件池；被多路直调违反聚拢点 |
| `MatrixEngine` | ECS 任务池（Scheduler/Router/Retry/Monitor） | `ExecutionCenter/Matrix` | 仅被 `DefaultMatrixExecutionService` 消费，未接入统一入口；不支持事件组合代数 |

### 2.2 备用链三阶段演进复盘（教训）

| 阶段 | 提交 | 状态 | 教训 |
|------|------|------|------|
| ① 自包含执行池（最早形态） | 前置版本 `MatrixEngine` | 独立 World + Loop + TCS 等待，自洽 | **意图正确**：集中事件/任务池 + ECS 约束 |
| ② 硬接 UI 渲染管线 | `c3d31f30` 事件绑定执行逻辑集中重构 | MatrixEngine 被阉割（共享 World、Loop 空壳）；FunctionExecutionSystem 在 UI 管线轮询；引入请求/结果双 Component + 双事件 + 多层门面 | **过度包装**：为"绑定统一走矩阵"耦合 UI 管线 |
| ③ 被迫绕开并删除 | `e239cb4c` | Idle 饥饿 → 直达执行服务 → 备用链整体删除 | **重构不彻底**：只砍链，没把"执行统一进事件池"做对 |

**核心结论**：`EventPlatform`（统一事件总线 + InvokeFunction）本应承担集中事件池角色，但从未真正收口执行与约束校验；`MatrixEngine` 被"矩阵"命名误导且曾错误耦合 UI 管线，其真实潜力是工作流编排引擎。

### 2.3 MainLayout.json 多层容器事件结构化问题

```
MainView(Panel)
 └─ toolbarPanel（5 按钮，各自 click→函数）
 └─ mainSplitter(SplitContainer)
     ├─ contentSplitter
     │   ├─ contentContainer（动态容器→加载 ConfigSelector）
     │   └─ terminalPanel → outputTextBox + commandBar → executeButton
     └─ sideContainer（动态容器→加载 Side）
```

| 现象 | 本质问题 |
|------|----------|
| 多层嵌套控件靠反射 `Controls.Find` 穿透查找，可能匹配错层级 | 事件路由无层级/作用域意识 |
| 动态容器加载后事件靠 EventBindingSystem 每帧轮询 Pending 重试 | 绑定延迟 + 状态不同步 |
| `"click": ["LoadConfig"]` 仅为"数组=依次触发"，无聚合/条件/串并联语义 | 事件组合能力缺失（当前 UI 用不到，不本期实现） |

## 三、目标模型

```
 按钮/命令/钩子 ─▶ EventPlatform（唯一事件池 + 执行入口）
                    ├─ Subscribe/Publish（多播事件，异常隔离）
                    ├─ InvokeFunction（唯一执行入口）：
                    │     ├─ Fail-Fast 校验（函数名/依赖）
                    │     ├─ 模式路由（Auto：按调用源判 Sync/Background）
                    │     ├─ 超时控制
                    │     ├─ 审计（Entry/Exit/Error）
                    │     └─ 发布 function.Executed（结果可订阅）
                    └─ 订阅者：渲染桥（结果→UI）、其他业务方
  执行内核：FunctionCallFacade（收编为 EventPlatform 内部实现，不再被多路直调）
```

### 3.1 设计原则（对齐项目既定规范）

1. **聚拢点唯一入口原则**（`docs/analysis/2026/7/7.31/FileDriven_FrontEndDriven_聚拢点重构方案.md`）：函数调用统一经 `EventPlatform.InvokeFunctionAsync`；`FunctionCallFacade` 降为执行内核，不再被按钮/exec/钩子直调。
2. **最简设计**：消除 `EventPlatform.InvokeFunctionAsync` 与 `FunctionCallFacade.ExecuteAsync` 的功能重复（Fail-Fast+路由+超时+审计收敛为一套）。
3. **事件池标准**（`JSON框架重构_加载阶段抽象与公共事件平台设计.md` §6.4/附录 B 迭代 1）：事件绑定委托触发改经 `EventPlatform.InvokeFunction`，使按钮点击结果经 `FunctionExecuted` 事件可观测。
4. **不重蹈 Idle 耦合**：结果→UI 再渲染复用备用链的 Interlocked 事件合并思路，但**不依赖 Application.Idle 轮询**，直接由事件推送驱动。

## 四、决策与边界

### 4.1 已确认决策

| 决策项 | 结论 |
|--------|------|
| 执行内核落点 | **收编但保留类**：`FunctionCallFacade` 保留为 BackEndDriven 执行内核实现，收拢所有调用方经 `EventPlatform` |
| Source/Mode 路由归属 | **收编进 `InvokeFunctionAsync`**：调用方只传 `source` 字符串 + 函数名 + 参数，不再拼 Mode（事件池按调用源判 Sync/Background） |
| 矩阵事件代数运算 | **不实施**：当前 UI 无组合/聚合场景；MatrixEngine 不支持 |
| MatrixEngine 处置 | **不在本期改动**：保持现状（仅 DefaultMatrixExecutionService 消费），事件主链不再碰它 |
| 层二（编排引擎重塑） | 搁置：待 Agent 工作流立项，按"工作流编排（DAG/组合子）"而非"矩阵代数"重塑 |

### 4.2 不在本期范围（避免过度设计）

- ❌ 事件"矩阵代数"组合/聚合算子（seq/parallel/when/aggregate）
- ❌ MatrixEngine 重塑（改名/改定位为 WorkflowOrchestrator）
- ❌ 冗余 EventBus 实现清理（EventBusFacade 适配层等）——除非 B2 引入"事件路径路由"与 TConfig.IEventBus 绑定职责**交叉**，否则不动
- ❌ `initCommands` → `lifecycle.onAfterLoad` 迁移（已完成，无需处理）

## 五、批次计划与文件改动清单

> 实施顺序：B1 → B4 → B2 → B3 → B5，每批独立构建 + 行为回归，可单独回滚。

### 批次 B1：EventPlatform 收口执行（建立唯一入口）

**目标**：`EventPlatform.InvokeFunctionAsync` 成为唯一执行入口，收编 Fail-Fast/模式路由/超时/审计。

**文件**：
- `CsharpPrj/Operation/FrontEndDriven/Eventing/EventPlatform.cs`
  - `InvokeFunctionAsync`：内置 Fail-Fast（函数名非空）、模式路由（Auto：ExecCommand→Sync，其余→Background）、超时（默认 30s）、审计（Entry/Exit/Error）。
  - 执行完成后发布 `function.Executed` 事件（参数对齐既有 `FunctionExecutedPayload`）。
  - `InvokeFunctionAsync` 签名简化为 `(functionName, parameters, source)`，移除 Mode 参数（由内部路由）。
- `CsharpPrj/Operation/BackEndDriven/Gate/FunctionCallFacade.cs`
  - 保留类，作为 EventPlatform 内部执行内核（注释声明"统一经 EventPlatform 调用"）。
  - 模式路由/超时核心逻辑维持（被 EventPlatform 复用或内部委托），避免功能重复。

**验证**：`dotnet build` FrontEndDriven + BackEndDriven 0 错误；`EventPlatform.InvokeFunctionAsync` 直接调用行为正确。

### 批次 B4：收编 FunctionCallFacade 直调（消除多入口）

**目标**：所有调用方改为经 `EventPlatform.InvokeFunctionAsync`。

**文件**：
- `CsharpPrj/Share/EventBindingOrchestrator/`（按钮事件委托终点：`ExecuteFunctionDelegate` / `OnEventResult` 落点）
  - 委托触发改经 `EventPlatform.InvokeFunction`，使按钮点击结果经 `FunctionExecuted` 可观测（对齐蓝图附录 B 迭代 1）。
- `CsharpPrj/Operation/BackEndDriven/CommandExecution/CommandSystems.cs`（`ExecSystem.Execute`）
  - 直调 `FunctionCallFacade.ExecuteSyncRequest` → 改经 `EventPlatform.InvokeFunctionAsync`（注意 BackEndDriven→EventPlatform 引用方向，必要时经接口/适配）。
- `CsharpPrj/Operation/FrontEndDriven/Lifecycle/ConfigurationLifecycleManager.cs`（`ExecuteHooksAsync`）
  - 确认已走 `EventPlatform.InvokeFunctionAsync`，统一 Source=LifecycleHook。

**验证**：`dotnet build FileDriven.sln / MainProj.sln` 0 错误；按钮点击/exec 命令/钩子三路径行为回归。

### 批次 B2：事件作用域/层级路由（解决 MainLayout.json 结构化问题）

**目标**：事件路由具备容器树层级/作用域意识，消除反射 `Controls.Find` 穿透歧义。

**文件**：
- `CsharpPrj/Operation/FrontEndDriven/Eventing/EventPlatform.cs`
  - `IEvent` 补充分层信息（如 `ScopePath`：`toolbarPanel.loadConfigButton`）。
- `CsharpPrj/Share/EventBindingOrchestrator/`（绑定查找）
  - 控件定位按容器树路径（作用域限定）查找，优先于全局反射穿透。
- 配置层（如 `TConfig/Controls/` 或 UI 配置模型）：支持声明事件作用域/容器路径。

**验证**：多层容器嵌套下同名控件能精确命中正确层级；按钮触发路径正确。

### 批次 B3：动态容器生命周期衔接事件（消除轮询延迟）

**目标**：动态容器（contentContainer/sideContainer）加载后事件即时可用，去掉每帧轮询 Pending 重试的状态延迟。

**文件**：
- `CsharpPrj/Operation/FrontEndDriven/Lifecycle/ConfigurationLifecycleManager.cs`
  - dynamic 容器加载经 `ConfigLoaded` 生命周期事件建立作用域事件上下文。
- `CsharpPrj/Operation/FrontEndDriven/Gate/EcsGate.cs`
  - 动态加载路径（`LoadConfigAndRenderAsync`）确保 `ConfigLoaded` 发布后立即触发该作用域的事件绑定。

**验证**：Load Side → ConfigSelector 加载后，`configListView` 等控件的事件即时可用（对照原 InitCommands bug 场景）。

### 批次 B5：function.Executed 驱动 UI 再渲染（恢复结果→UI 能力）

**目标**：函数执行完成后自动触发 UI 再渲染，复用备用链事件驱动思路，无 Idle 依赖。

**文件**：
- 新增渲染桥订阅者（建议位置：`CsharpPrj/Operation/FrontEndDriven/Initial/RenderPipeline/` 或 EventPlatform 装配处）
  - 订阅 `function.Executed`，复用备用链 `Interlocked.Exchange` 事件合并（并发多结果只渲染一次）+ `MaxRerenderCount` 防无限循环。
  - 渲染经 `UiThreadHelper`/`IUIDispatcher` 封送到 UI 线程（跨线程安全）。
  - 渲染入口：`RenderPipelineComposition.ExecuteRenderStage()` 或定向增量刷新（首期全量，后续按需增量）。

**验证**：工作流函数修改 UI 状态（文本/可见性/数据绑定）后界面自动刷新。
