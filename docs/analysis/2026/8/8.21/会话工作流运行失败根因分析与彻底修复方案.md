# 会话工作流「运行失败（未装配函数或步骤异常）」根因分析与彻底修复方案

> 日期：2026-08-21 · 状态：**修复已落地**（M1/M3/M4/M6 ✅；M2 可选未做；M5 部分——RoundSpecLoader 侧已落地并顺带完成 F5 msgId 静态化，ConversationHosting/AgentFrameworkHosting 待核）
> 触发：`AgentRuntimeUI.json` 主对话框（⑦ pageConversation）发送消息后，会话运行返回
> `会话=轮次=1 状态=Completed | 步骤: cline_execute:cline | 诊断: 会话工作流运行失败（未装配函数或步骤异常）`，
> 被误读为「函数未装配」。
> 关联文件：`Agent.Core/Conversation/ConversationPipeline.cs`、`Agent.Axioms/Loops/WorkflowRunner.cs`、
> `Agent.Axioms/Nodes/NodeExecutionService.cs`、`Agent.Axioms/Loops/RoundSpecLoader.cs`、
> `Agent.Launcher/Composition/ConversationHosting.cs`、`Config/workflows/collect-analyze-act.json`

---

## 〇、结论先行

「未装配函数或步骤异常」是**误导性的兜底诊断文本**，不是函数未装配。

- **会话服务已装配**：`AgentFramework.StartAsync`（`AgentFramework.cs:84`）调用 `ConversationHosting.TryAttach(a.TaskPool)`。
- **工作流函数已装配**：`AgentFrameworkHosting.TryBootstrapGuiAsync`（`AgentFrameworkHosting.cs:44-45`）强制 `RegisterStatelessAnswer=true`、`RegisterCline=true`，
  经 `AgentOptionalModules.Register` → `AnswerWorkflowFunction.Register()`（`answer`）与 `ClineExecutorFunction.Register()`（`cline_execute`）。
- **真正的根因**：会话工作流模板 **`collect-analyze-act.json`（3 步）与其兜底 `DefaultConversationSpec`（2 步）都没有产出 `decision`（`RoundKeys.Decision`，即键 `"decision"`）决策词的步骤**。
  `WorkflowRunner.RunRoundAsync` 的「本轮成功」判定强依赖 `decision` 为 `stop/complete/continue`（`WorkflowRunner.cs:193-196`），
  会话模板无任何节点写 `"decision"` → `decision == null` → `ok == false`（且 `Error == null`）→ `ConversationPipeline.cs:117` 落到兜底默认文本。

一句话：**模板缺决策环节，被骨架层恒判为失败，而兜底文本把原因错写成了「未装配函数或步骤异常」。**

> 注：UI 层「⑦ 主对话框不显示」是**另一独立问题**（渲染挂载层），根因与修复见同目录
> `框架挂载误判根因分析与整理优化方案.md`（配置误嵌套 + 挂载假绿，已于 2026-08-21 修复）。
> 本方案仅覆盖「会话工作流执行层」。

## 一、误判链（证据）

| # | 环节 | 事实 | 证据 |
|---|------|------|------|
| 1 | 会话服务装配 | 组合根已调用 `ConversationHosting.TryAttach(a.TaskPool)` | `AgentFramework.cs:84` |
| 2 | 工作流函数装配 | `answer`/`cline_execute` 均已注册（默认/强制 true） | `AgentFrameworkHosting.cs:44-45` → `AgentOptionalModules.cs:50-55,30-36` |
| 3 | 模板缺决策 | `collect-analyze-act.json` 仅 `start→collect(cline_execute)→analyze(answer)→act(cline_execute)`，无任何节点写 `decision` | `collect-analyze-act.json`；`RoundSpecLoader.cs:38-43` 兜底 `DefaultConversationSpec` 同样两步无 `decision` |
| 4 | 成功判定强依赖决策 | `ok = ctx.Error==null && decision!=null && (IsSuccess(decision)||IsContinue(decision))` | `WorkflowRunner.cs:193-196`；`DecisionWordClassifier.cs:29,32`（仅 `stop/complete`→Success、`continue`→Continue） |
| 5 | 诊断兜底误导 | `result.Ok ? null : new[]{ result.Error ?? "会话工作流运行失败（未装配函数或步骤异常）" }` | `ConversationPipeline.cs:115-118` |

**完整链**：发消息 → `AgentUi_ConversationSend` → `ConversationSessionService.SendAsync` → `ConversationPipeline.RunSignalAsync` →
`WorkflowRunner.RunRoundAsync` 沿模板跑完（无异常，`Error==null`）→ 因 `decision==null` 判 `ok=false` → `RunSignalAsync` 用兜底文本「未装配函数或步骤异常」→ UI 回显。

> 根因一句话：**会话模板是「对话驱动、沿链跑完即完成」的语义，却被套用了主循环（agent-loop）强依赖 `decision` 决策词的 `ok` 判定；判定语义与模板语义不匹配，被误判失败，且兜底文本掩盖了真实原因。**

## 二、结构性根因（非单点）

### D1 判定语义耦合错位
`WorkflowRunner.ok` 把「本轮成功」与「产出了决策词（rule_match 语义）」强绑定。
主循环 `agent-loop.json` 有 `rule_match` 节点（`ResultKeys` 含 `decision`，`agent-loop.json:48`），故成立；
会话模板 `collect-analyze-act` 无该环节，语义上「跑完即成功」，却被同一判据判失败。**骨架语义与模板语义未解耦。**

### D2 兜底诊断掩盖根因
`ConversationPipeline.cs:117` 的 `result.Error ?? "未装配函数或步骤异常"` 把「ok=false 且无具体 error」笼统归为「未装配函数或步骤异常」，
既误导排障（用户以为函数没装），又丢失真实原因（模板缺决策 / 模板未加载回退 / 步骤产出错配）。

### D3 结果键提取约定不统一
`ExtractProps` 对 `ClineResult` 做了「按 `ResultKeys` 定向全写」的特殊化，但对 `AgentExecutorResult` 走属性名反射，
导致模板 `ResultKeys` 与返回类型属性名不一致时（`answer` 的 `analyze_result`）结果键静默丢失，stages 分层残缺，进一步制造「执行残缺」观感。

### D4 模板加载回退不可观测
`RoundSpecLoader.LoadWorkflow` 失败静默回退两步 `DefaultConversationSpec`（仅 `onLoaded` 记日志，回退路径无显式失败日志），
运行实际用的模板可能与源码期望的 3 步模板不一致，且无观测入口。

## 三、彻底修复方案

> 目标：**会话语义与骨架判定解耦（根上不再依赖 `decision`）+ 结果键提取约定统一 + 诊断明确可归因 + 装配/加载可观测 + 测试锁定。**

### M1【判定解耦（根治）】会话成功判定不再依赖 `result.Ok`
- 文件：`Projects/Agent/src/Agent.Core/Conversation/ConversationPipeline.cs`
- 改动：`RunSignalAsync` 的成功判定从 `result.Ok` 改为 `result.Error == null`（`Error` 已是骨架「步骤异常」的权威归集，见 `WorkflowRunner.cs:148-150`）；
  `result.Ok` 仅作可选「决策词终态信号」参考，不参与会话成败。
  - 现：`result.Ok ? null : new[] { result.Error ?? "会话工作流运行失败（未装配函数或步骤异常）" }`
  - 改：`var diag = result.Error == null ? null : new[] { result.Error };`（无 error 即成功）
- 理由：会话是「对话驱动、沿链跑完即完成」，非预算驱动主循环；`decision` 是主循环 `rule_match` 的语义，不应强加于会话模板。
  **此改动让任意无决策环节的会话模板（含两步/四步）都正确判成功**，且不改动骨架全局语义（`WorkflowRunner` 不动，零回归风险）。
- 同步：`AgentUiLibraryConversation.cs:36` 的输出模板与文档《Task即对话·对话驱动主循环外置设计.md》的成功口径对齐。

### M2【会话模板补决策（可选增强，非 M1 依赖）】
- 文件：`Projects/Agent/Config/workflows/collect-analyze-act.json`
- 改动：末尾 `act` 之后补一个产出 `decision` 的收尾节点（如复用 `rule_match`，或新增恒返回 `complete` 的完成步骤），
  使模板在骨架判据下也自洽；`RoundSpecLoader.cs:38-43` 兜底 `DefaultConversationSpec` 同步补决策步骤。
- 说明：M1 落地后本项非必需，但保留可保证「模板结构与骨架 `ok` 语义一致」，作为双保险与文档示例对齐。

### M3【结果键提取约定统一】`AgentExecutorResult` 走 `ResultKeys` 定向
- 文件：`Projects/Agent/src/Agent.Axioms/Nodes/NodeExecutionService.cs`（`ExtractProps`，248-260 行）
- 改动：`ExtractProps` 增加 `AgentExecutorResult` 分支——与 `ClineResult` 对称，按 `node.ResultKeys` 全写同一值；
  其余类型维持属性名反射。
- 收益：`answer` 步的 `analyze_result` 键被正确写入 → `collect/analyze/act` 三层都进 stages，UI 分层完整。


### M4【诊断明确可归因】
- 文件：`Projects/Agent/src/Agent.Core/Conversation/ConversationPipeline.cs`
- 改动：`RunSignalAsync` 构造 `Diagnostics` 时按真实原因分类输出，去掉误导性兜底：
  - `result.Error != null` → `"步骤 {step} 异常: {result.Error}"`（尽可能定位出错步骤）；
  - `result.Error == null`（M1 后本分支不再视为失败）→ 无诊断；
  - 若保留 `result.Ok` 参考位 → `"工作流未产出决策判定（模板缺 rule_match/决策节点）"` 而非「未装配函数或步骤异常」。
- 收益：排障时一眼看出是「模板缺决策」还是「某步骤异常」，不再误引向「函数未装配」。

### M5【装配/加载可观测】
- 文件：`Projects/Agent/src/Agent.Launcher/Composition/ConversationHosting.cs`、`Agent.Axioms/Loops/RoundSpecLoader.cs`
- 改动：
  1. `ConversationHosting.TryAttach` 失败（`pool==null` 或装配异常）记录 Warn 日志（含原因），不再静默 `return false`；
  2. `RoundSpecLoader.LoadWorkflow` 回退 `DefaultConversationSpec` 时记录 Warn（含文件路径与回退原因），并暴露「实际加载 steps 数」供诊断；
  3. `AgentFrameworkHosting` 降级路径（RulePoolOnly，未装配会话）在 `BootstrapResult` 摘要中标注「会话未装配」。
- 收益：装配/模板加载失败可观测、可归因，避免「静默回退 + 兜底误导」叠加。

### M6【测试锁定】
- 文件：`CentralTest/AgentTest/Agent.Core.Tests/ConversationPipelineTests.cs`
- 新增用例：
  1. **无决策两步模板（M1 后判成功）**：`FakeRunner` 返回 `Ok=false, Error=null`（模拟骨架无决策）→ 断言 `reply.Diagnostics` 为 null、`Status=Completed`；
  2. **步骤异常归因**：`FakeRunner` 返回 `Error="..."` → 断言 `reply.Diagnostics` 含该错误文本；
  3. **answer 提取定向**：经 `NodeExecutionService.ExtractProps` 对 `AgentExecutorResult` 的 `ResultKeys` 定向产出 `analyze_result`（M3）。
- 回归：`StateHoldDriven.Tests`、`FrontEndDriven.Tests`、GUI `agent_ui_smoke_test.json`、`agent_ui_render_test.json`。

## 五、与既有方案衔接

- **UI 层（已修）**：`框架挂载误判根因分析与整理优化方案.md` 已解决「⑦ 主对话框不显示」（配置误嵌套 + 挂载假绿，M1-M5 落地）。
  本方案解决的是**点发送后的会话工作流执行**，两者互补：前者管「控件挂不挂得上去」，后者管「挂了之后跑不跑得通」。
- **骨架语义**：本方案**不改 `WorkflowRunner.ok` 全局语义**（主循环 agent-loop 依赖 `decision` 判定预算/终止），
  只在会话层 `ConversationPipeline` 定制判定（M1），M2 作模板层双保险——零回归主循环路径。
- **依赖治理**：`ConversationPipeline` 已通过 `runWorkflow` 端口注入 runner，测试用 `FakeRunner` 直测编排，
  本方案 M1/M4 改动均在 `ConversationPipeline` 内，不触碰骨架，测试口径稳定。
