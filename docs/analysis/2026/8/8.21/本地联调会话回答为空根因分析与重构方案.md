# 本地联调「会话回答为空」根因分析与重构方案

> 日期：2026-08-21 · 状态：**待评审（分析完成，未改代码）**
> 触发：运行 `FileDriven/DrivenConfig/Scripts/Agent/agent_local_test_gui_test.json`（GUI 本地联调测试），
> 主对话框发送消息后返回 `会话=default 轮次=1 状态=Completed | 步骤: cline_execute:cline | answer:answer`，`终答:` 为空。
> 脚本 `success=true`，但会话回答为空是真实业务缺陷（本地联调开启下，本地 LLM 一次都未被调用，`CallLog=0`）。
> 关联文件：`Agent.Modules/Answer/AnswerWorkflowFunction.cs`、`Agent.Axioms/Loops/RoundSpecLoader.cs`、
> `Agent.Axioms/Infrastructure/ConfigJson.cs`、`Agent.Launcher/Composition/LlmHosting.cs`、
> `Agent.Runtime/State/Infrastructure/LlmMode.cs`、`Config/workflows/collect-analyze-act.json`、`Config/workflows/agent-loop.json`。

---

## 〇、结论先行

本地联调会话回答为空，由**两个叠加根因**造成，缺一不可：

- **根因 A（模板回退）**：会话工作流模板 `collect-analyze-act.json`（PascalCase 键）与加载器
  `ConfigJson.Options` 的 `SnakeCaseLower` 命名策略不匹配 → 多字属性（`NodeId`/`FuncName`/`ParameterKeys`/`ResultKeys`/`NextNodeConfig`）反序列化全为 null
  → `BuildRoundSpec` 返回 null → 校验失败回退两步 `DefaultConversationSpec`，**act 层丢失**。
- **根因 B（回答为空的直接原因）**：`answer` 端 LLM 客户端 `AnswerWorkflowFunction.SharedAnswer` 用
  `AppServiceProvider.Resolve<ILlmClient>()` 解析，null 回退 `LlmClientFactory.Get("semantic")`——**绕过统一网关路由代理 `LlmMode.Routing`**。
  本地联调开关（`LlmMode.LocalOnly`）只对 `LlmRoutingClient` 生效，对 answer 无效 → answer 走真实配置后端（SemanticKernel）→ 无有效凭据返回空 → 终答空。

> 决定性证据：日志 `CallLog=0`。`LocalLlmClient` 一旦被调用必记录 CallLog，且有非空默认响应
> （`（本地后端）已处理问题：{user}`），只要命中本地必有回答。`CallLog=0` 证明整条会话链路（answer/cline）一次都没流经本地后端。

## 二、根因 A：工作流 JSON 键命名与反序列化命名策略失配

### 2.1 机理

`ConfigJson.Options`（`ConfigJson.cs:12-17`）：
```csharp
public static readonly JsonSerializerOptions Options = new()
{
    PropertyNameCaseInsensitive = true,
    PropertyNamingPolicy = JsonNamingPolicy.SnakeCaseLower,
    Converters = { Infrastructure.KeyMappingConfigJsonConverter.Instance },
};
```

`collect-analyze-act.json` / `agent-loop.json` 的键为 **PascalCase**（`NodeId`/`FuncName`/`ParameterKeys`/`ResultKeys`/`NextNodeConfig`/`WorkflowId`/`InputPorts`...）。

System.Text.Json 反序列化时，按命名策略把 CLR 属性名转为 `snake_case`（如 `node_id`）再去匹配 JSON 键；`PropertyNameCaseInsensitive` 只弥合大小写、**弥合不了下划线差异**。因此：

| JSON 键（PascalCase） | CLR 属性 | snake_case 期望 | 是否匹配 |
|---|---|---|---|
| `Nodes` / `Symbol` / `Name` / `Version` / `Configs` | 单字 | 单字无下划线 | ✅（靠 case-insensitive） |
| `NodeId` / `FuncName` / `ParameterKeys` / `ResultKeys` / `NextNodeConfig` / `WorkflowId` / `InputPorts` ... | 多字 | 含下划线 | ❌ |

结果：`WorkflowDefinition.Nodes` 有值（4 节点），但每个 `WorkflowNode` 的 `NodeId`/`FuncName`/`ParameterKeys`/`ResultKeys`/`NextNodeConfig` 全为 null。

`BuildRoundSpec`（`RoundSpecLoader.cs:109`）在 `start?.NodeId is null` 时返回 null → `ConfigFileLoader` 判"解析无效" → 回退默认模板。

### 2.2 影响范围

- `collect-analyze-act.json` → 回退两步 `DefaultConversationSpec`（act 层丢失）。
- `agent-loop.json` **同样失败**，但被硬编码 `DefaultRoundSpec`（步骤等价）兜底掩盖 → 主循环看似正常，实则其声明从未真实生效。
- 既有 `T7` 测试（`RoundSpecLoaderTests.cs`）断言 `Steps.Count>0` 等，**区分不了"声明加载"还是"回退默认"**，故未暴露。

## 三、根因 B：answer 端 LLM 客户端绕过统一网关路由代理

### 3.1 机理

`AnswerWorkflowFunction.SharedAnswer`（改动前 `AnswerWorkflowFunction.cs:26-31`）：
```csharp
var llm = AppServiceProvider.Resolve<ILlmClient>();
if (llm is null) llm = LlmClientFactory.Instance.Get("semantic");
```

而统一网关路由代理 `LlmRoutingClient` 只在 `LlmHosting.Configure` 注入 `LlmMode.Routing`（`LlmHosting.cs:71`），**并未**：
- 以 `ILlmClient` 注册进 AppServiceProvider；
- 以 `local`/`semantic` 键注册进 `LlmClientFactory`（工厂里 `local`=LocalLlmClient、`semantic`=SemanticKernelLlmClient）。

因此 answer 拿到的 `_llm` 是**配置后端（SemanticKernel）**，`LlmMode.LocalOnly` 开关只对 `LlmRoutingClient` 生效，对 answer **无效** → 走真实 semantic 后端 → 无有效凭据/未配置 → 返回空 → `analyze_result` 文本空 → 终答空，且 `CallLog` 不增。

### 3.2 架构矛盾（SingleImplementation 违例，TH-12）

- `LlmHosting.ResolveStatelessAnswerLlm`（任务池路径，`LlmHosting.cs:119-135`）**正确返回 `LlmMode.Routing`**，使本地开关对 stateless-answer 生效。

## 四、修复方案（仅方案，未改代码）

### 方案 B【核心，直接解决空回答】answer 端收敛到统一网关路由代理

- 文件：`Agent.Modules/Answer/AnswerWorkflowFunction.cs`（`SharedAnswer`，26-31 行）
- 改动：LLM 解析优先级改为
  `LlmMode.Routing`（统一网关路由代理，本地开关对其生效）→ `AppServiceProvider.Resolve<ILlmClient>()` → `LlmClientFactory.Get("semantic")`。
- 语义：与 `LlmHosting.ResolveStatelessAnswerLlm` 收敛（SingleImplementation），消除"绕过网关直连配置后端"的分裂路径。
- 收益：本地联调开启时 answer 走 `LocalLlmClient` → 命中规则/默认响应 → 回答非空、`CallLog` 递增、可审计回放。

### 方案 A【恢复三步模板】工作流 JSON 键与反序列化策略对齐

两个可选子方案，推荐 A1：

- **A1（属性标注，推荐）**：给 `RoundSpecLoader` 的 `WorkflowDefinition`/`WorkflowNode`/`WorkflowNext` 属性加 `[JsonPropertyName("PascalCase")]`，使反序列化按声明名精确匹配 JSON 键，不受 `SnakeCaseLower` 影响。`agent-loop.json` 同步受益（声明真实生效，行为等价、零回归）。
  - 文件：`Agent.Axioms/Loops/RoundSpecLoader.cs`（169-212 行，`WorkflowDefinition`/`WorkflowNode`/`WorkflowNext`），需补 `using System.Text.Json.Serialization;`。
- **A2（改 JSON 为 snake_case）**：把工作流 JSON 键改为 snake_case。改动文件多（`collect-analyze-act.json` + `agent-loop.json`），且与现有文档示例（PascalCase）不一致，不推荐。

> 注意：单字属性（`Nodes`/`Symbol`/`Name`/`Version`/`Configs`）已靠 case-insensitive 命中，无需标注；A1 只需覆盖多字属性。

### 验证

重跑 `agent_local_test_gui_test.json`，应观察到：
1. 不再出现 `collect-analyze-act.json 校验未通过` 警告；
2. 步骤为 `cline_execute:cline | answer:answer | cline_execute:cline`（三步）；
3. `conversationHistoryTextBox` 终答非空；
4. `AgentUi_GetLocalTestStatus` 的 `CallLog>0`（本地 LLM 被调用）。

## 五、与既有方案衔接

- **不触碰 `WorkflowRunner.ok` 全局语义**：会话成功判定已在 `ConversationPipeline` 解耦（M1 已落地），本次不回归主循环路径。
- **方案 B 在 `AnswerWorkflowFunction` 内收敛**，不触碰骨架/调用流程，符合 `StateRootSingleSource` / `TH-12`（单一实现）。
- **方案 A 仅加反序列化标注**，不改 JSON 结构、不改执行语义，`agent-loop.json` 从"回退硬编码"变为"声明真实生效"，与设计文档（声明式工作流）对齐。
- 本地联调基础设施（`LlmMode` / `LlmRoutingClient` / `LocalLlmHttp`）本身无缺陷，问题在消费端是否接入网关。
