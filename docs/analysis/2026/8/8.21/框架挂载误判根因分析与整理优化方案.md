# 框架挂载「误判成功」根因分析与整理优化方案

> 日期：2026-08-21 · 状态：方案（分析结论 + 结构性优化蓝图；部分校验已落地）
> 触发：`agent_ui_render_test.json` 定位「⑦ 主对话框 pageConversation 不显示」——根因是**配置误嵌套**，但框架全程报告「渲染成功」，暴露框架自身缺陷
> 关联：`WinFormsControlAdapter.cs` / `WinFormApplier.cs` / `SplitterPanelHelper.cs` / `Ports.cs` / `RenderPipelineStages.cs` / `ScopeLifecycleAdapter.cs` / `IControlAdapter.cs`

---

## 一、结论先行

「⑦ 主对话框不显示」的直接原因是配置结构错误：`pageConversation`（tabpage）被误写成 `displayTabControl`（tabcontrol）的**同级兄弟**（`views[0].controls[4]`），父节点是 `MainView`（Panel），无 TabControl 宿主。

但比配置错误更严重的是**框架的误判**：在配置非法时，框架仍输出——

```
sideload 渲染成功 — scope=Content, nodeCount=1, hostChildCount=1
ScopeLifecycleAdapter 渲染判据 — renderSucceeded=true, hostActualChildCount=1, mountVisible=true, succeeded=true
EcsGate 渲染挂载统计 — mounted=50, orphan=0, hostActualChildCount=1, succeeded=true
```

即「控件实际没挂进宿主（物理 orphan）」与「框架自报渲染成功」同时成立。**可见性审计在后台虽发现 11 个 `inHost=false`，却只入队"自愈重渲染"空转，不报 Error、不阻断**。这说明框架的"挂载成功"判据是**假绿**——这是框架自身的结构性缺陷。

---

## 二、误判链条（证据）

| # | 环节 | 缺陷 | 证据 |
|---|------|------|------|
| 1 | `IControlAdapter.AddControl` | **`void`，无成败契约** | `IControlAdapter.cs:40` `void AddControl(object parent, object child)` |
| 2 | `WinFormsControlAdapter.AddControl` 分支2（TabPage 容错） | 找不到 TabControl 祖先时**记日志后静默 `return`**，不返回失败 | `WinFormsControlAdapter.cs:130-148` |
| 3 | `SplitterPanelHelper.TryAddControl` | `targetPanel` 为空时直接 `AddControl` 后**恒返回 `true`** | `SplitterPanelHelper.cs:56-59` |
| 4 | `WinFormApplier.ApplyRelations` | `TryAddControl==true` → `RelationsApplied++`，**把"调用"当"挂载事实"** | `WinFormApplier.cs:307-316` |
| 5 | `ApplyResult.AllMounted` | 由 `RelationsSkipped==0 && ControlsSkipped==0` 推导，**不含物理入宿主验证** | `WinFormSnapshot.cs:142` |
| 6 | `ScopeLifecycleAdapter` 渲染判据 | `hostActualChildCount>0` **只验证 root 挂到宿主**，不验证内容控件是否入宿主 | `ScopeLifecycleAdapter.cs` |
| 7 | 可见性自愈 | 发现 `inHost=false` 只 `Enqueue("visibility-self-heal")` **重渲染**，对结构错误空转，`healViolated=11` 造成"已修复"错觉 | `RenderPipelineStages.cs:501-513` |

**完整链**：`MainView→pageConversation` 关系 → `AddControl(MainView, pageConversation)` 走分支2 → `FindTabControlAncestor(MainView)` 返回 null → 静默 `return` → `TryAddControl` 仍返回 true → `RelationsApplied++` → `AllMounted=true`、`orphan=0` → 报表全绿。

> 根因一句话：**挂载失败没有在物理层闭环验证，也没有沿调用链向上传递失败信号，最终在统计层被当成成功。**

## 三、结构性根因（5 条，非单点）

### D1 挂载端口无成败契约
`AddControl` 是 `void`。挂载动作（`TabPages.Add` / `Controls.Add` / `Panel1.Add`）能否成功，只有适配器自己知道，但它不对外声明。失败在适配器内被 `return` 吞掉。上层（Applier/统计/审计）无从得知"这次挂载是否真的发生了"。

### D2 成功判据未在物理层闭环
`AllMounted` / `MountedCount` / `orphan` 统计的是**"调用了几次 AddControl"**，而非**"目标子集合（TabPages/Controls/Panel）是否真的收到了该控件"**。逻辑上的"挂载数"与物理上的"入宿主数"可以完全不一致——这就是假绿的本质。

### D3 宿主判据与结构判据分裂
- 结构层：`ApplyRelations` 用"关系边调用"判定挂载。
- 宿主层：`ScopeLifecycleAdapter` 用 `hostActualChildCount>0`（root 物理收到）判定挂载。
- 两套口径对"已挂载"认知不同（历史 `ContainerConfluence`/`M4` 已多次治理，仍残留）：本次 `sideContainer` 收到 root（hostChildCount=1）即报成功，而内容层 ⑦ 早已 orphan。

### D4 关系边 ≠ 物理挂载
`ApplyRelations` 把"配置关系边"当作挂载事实，但真实挂载机制是"宿主注入"（`MarkMounted` 唯一权威在 `ScopeLifecycleAdapter`）。"配置声明的父子关系"与"物理树里的父子关系"是两个世界，中间没有闭环校验，导致一方成功、一方失败却不报。

### D5 自愈无根因诊断
可见性自愈只做"重渲染"，不区分根因：瞬态（时序/未 realize）重渲染可修；**结构错误（配置误嵌套）重渲染永不可修**。却仍报 `healViolated`，制造"已自愈"的假象，掩盖了需要人工修配置的事实。

## 四、整理优化方案（结构性重构，非补丁）

> 目标：**挂载动作携带成败信号 + 挂载判据在物理层闭环 + 宿主/结构判据合一 + 配置结构前置校验 + 自愈带根因门。** 让"配置错误"在框架里**不可能**被误报为"渲染成功"。

### M1 挂载端口返回成败契约
- `IControlAdapter.AddControl(object parent, object child)` → `bool AddControl(...)`（true=已入目标子集合，false=未入）。
- `WinFormsControlAdapter.AddControl` 所有分支显式返回：
  - TabControl→TabPage 入 `TabPages` → true；幂等已存在 → true；
  - 分支2 容错归属成功 → true；**找不到 TabControl → false（不再静默）**；
  - `Controls.Add` → true；`TryGetControl` 失败 / 防环拦截 → false。
- 删除 `FindTabControlAncestor` 自愈（父链必须来自声明树，不该"猜父修正"）；失败直接上抛。

### M2 挂载判据物理闭环
- `SplitterPanelHelper.TryAddControl` 改为透传 `adapter.AddControl` 的 bool（不再恒 true）。
- `ApplyRelations` 依据真实 bool 计数 `RelationsApplied` / `RelationsSkipped`。
- `ApplyResult` 新增**物理核验**：`AllMounted` 由「关系目标子集合实际包含该控件」判定（经 `IControlAdapter.GetControls(parent)` 或专用 `Contains` 原语二次确认），杜绝"调用即成功"。
- `RenderRunResult.MountedCount/OrphanCount` 直接读该物理核验结果。

### M3 宿主/结构判据合一
- 渲染成功判据改为**双条件且**：`root 物理入宿主 ∧ 全部关系物理入宿主`。
- `ScopeLifecycleAdapter` 渲染判据同时上报 `rootAttached`（hostActualChildCount）与 `contentMounted`（物理核验数），二者任一不满足 → `succeeded=false`。
- `hostActualChildCount>0` 不再单独构成"渲染成功"。

### M4 配置结构前置校验（已部分落地）
- `ConfigDrivenControlFactory.ConvertControl` 已加入：`tabpage` 父类型非 `tabcontrol` → 输出 **Error**（`ConfigDrivenControlFactory_tabpage_misnested`，2026-08-21 落地）。
- 扩展同一校验器覆盖更多结构约束（建议）：
  - `splitterpanel` 必须嵌套于 `splitcontainer`；
  - `tabcontrol` 的直接子控件必须为 `tabpage`；
  - 容器类型不得作为叶子（无 `controls` 却声明容器）等。
- 校验失败可选的硬模式：抛配置加载异常 / 或至少 Error + 在 `ApplyResult` 置位，使渲染必失败。

### M5 自愈带根因门
- `RenderVisibilityCheckStage` 触发自愈前，先**诊断 `inHost=false` 根因分类**：
  - 瞬态类（TabControl 未 realize / 布局未就位）→ 重渲染自愈；
  - **结构类（父链非法，如 tabpage 无 TabControl 宿主）→ 不自愈，升 Error 并标 `config-error`**，提示人工修配置。
- 移除"healViolated 计数即代表已修复"的语义；改为"诊断结果 + 是否实际可自愈"两字段。
