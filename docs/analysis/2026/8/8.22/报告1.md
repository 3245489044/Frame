FrontEndDriven 静态分析报告:重复逻辑与错误逻辑
分析范围:CsharpPrj\Operation\FrontEndDriven(约 140 个 .cs 文件,覆盖 Ports / ControlLookup / ControlRender / ControlInteraction / WinForms / Gate / Lifecycle / State / Validation / Shared / Initial / LoadRender 全部子系统)
方式:只读静态分析,未修改任何代码。
一、错误逻辑(按严重度排序)
🔴 E1. RenderStageRunner.ExecuteRenderStage scope 非空时执行全量布局重算
RenderStageRunner.cs
if (!string.IsNullOrEmpty(scope))
{
    ctx.Scope = scope;
    if (_hostBasisSystem.ResolveBasis(scope))
    {
        _layoutSystem.RecalculateAll();   // ← scope 非空却全量重算
    }
}
方法注释明确声明"S3 作用域感知:显式 scope 时收集器按 ScopeComponent 过滤,仅渲染目标作用域";LayoutSystem 中已存在 RecalculateScope(scope)(其注释专门说明"防止 Content 宿主重排误重算 MainLayout splitter")。
但此处 scope 非空时调用的是 RecalculateAll() 全量重算(删除所有非 root 容器实体的 ContainerSizeComponent 并全部置脏),与作用域感知语义直接矛盾。
后果:增量渲染 Side 作用域时,MainLayout 等其它 scope 的容器尺寸组件被全量清除并重排,存在跨 scope 误伤;也破坏了 IncrementalRender 只渲染区间的性能预期。
修复:RecalculateScope(scope)(或传入 ctx.Scope 的等价限定重算)。
🔴 E2. SplitterDistance 语义混用:配置层按"比例"Clamp,协议/快照层按"像素"处理
ConfigDrivenControlFactory.cs:
Ratio = Math.Clamp(control.SplitterDistance.Value, 0.0, 1.0)   // 当比例(0~1)
而 ControlConfig.SplitterDistance 类型为 double?(Plate\TConfig\Models\ControlConfig.cs),JsonToEntityConverter 用 GetValue<int>() 按像素解析;ControlDescriptor.SplitterDistance 为 int(像素),UIProtocol.Prop_SplitterDistance 也按像素写入物理属性。
后果:配置写像素值(如 300)会被 Math.Clamp 成 1.0(100%)——分割条比例错误且静默无告警。同一配置字段在链路两端(配置→ECS vs ECS→快照→物理)语义不一致。
修复:统一语义——要么配置层改为像素并直接写 SplitterDistanceComponent,要么明确区分 SplitterRatio(0~1)与 SplitterDistance(像素)两个字段,并在 JsonToEntityConverter 与工厂处同步。
🟠 E3. StripBoundsKeys 不剥离 SplitterDistance → 内容 Apply 与布局投影双写同一物理属性
WinFormApplier.cs
private static void StripBoundsKeys(Dictionary<string, object?> dict)
{
    dict.Remove(UIProtocol.Prop_Left);  // 只剥离 4 个 Bounds 键
    dict.Remove(UIProtocol.Prop_Top);
    dict.Remove(UIProtocol.Prop_Width);
    dict.Remove(UIProtocol.Prop_Height);
}
对 ECS 布局托管实体(IsEcsLayoutManaged),代码注释声称"像素 Bounds 不再由内容 Apply 写入,物理 Bounds 唯一由 LayoutProjector 投影";但同文件 BuildPropertyDict 第 399-400 行仍把 desc.SplitterDistance 写入属性字典,而 LayoutProjector 对含 SplitterRatioComponent 的实体也会投影 SplitterDistance。
后果:同一物理属性存在两个写入源,谁后执行谁生效,快照差异判定(AppliedSnapshot)与实际物理值可能漂移;且 SplitterRatioComponent 的 splitcontainer 若被 IsEcsLayoutManaged 命中,内容 Apply 写 SplitterDistance 与 R3 收敛原则冲突。
修复:StripBoundsKeys 增加 dict.Remove(UIProtocol.Prop_SplitterDistance)(并确认 IsEcsLayoutManaged 对 splitcontainer 的判定覆盖)。
🟠 E4. InputCapturePort._subscribed 以控件为 key 永久持有引用,无退订路径
InputCapturePort.cs
ConcurrentDictionary<Control, ...> 记录已挂接输入捕获的控件,但没有任何 Unsubscribe/清理路径(ControlPool 物理移除、scope 销毁时均未调用退订)。
后果:控件 Dispose 后仍被字典强引用,阻止 GC 回收——在"反复 load-config-show / 销毁 scope"场景下构成内存泄漏;且字典永续增长。
修复:随 ControlPool 移除/EntityLifecycleBus.InvalidateScope 订阅做退订,或改用 ConditionalWeakTable。
🟡 E5. EventHelper.StandardEventTypes(50 个)与 EventSubscriptionHelper.TrySubscribe(8 个)词表漂移
EventHelper.cs 声明 50 个"标准事件";EventSubscriptionHelper.cs 实际仅支持 8 个(click / doubleclick / textchanged / checkedchanged / selectedindexchanged / valuechanged / afterselect / selectionchanged)。
后果:配置写 selectedvaluechanged 等能通过标准词表校验,但绑定时必然失败且无编译期提示;而 afterselect / selectionchanged 实际受支持却不在标准词表(反向漏项)。
修复:以 TrySubscribe 实际支持集合为唯一真源,StandardEventTypes 从它派生(或二者合一),避免再次漂移。
🟡 E6. LayoutScheduler.DrainAsync while 循环无重入上限(潜在死循环)
LayoutScheduler.cs
DrainAsync 的 while 循环吞掉执行期新请求;若执行委托内对同一 scope 再次 Schedule,理论上可无限循环(正常路径不会,但缺少防重试上限/迭代次数护栏)。
修复:加最大迭代次数或"空转轮次"检测,超限记日志并退出。

三、修复优先级建议
优先级	项	理由
P0	E1 RecalculateAll 全量重算	与 S3 作用域感知直接冲突,跨 scope 误伤,影响正确性
