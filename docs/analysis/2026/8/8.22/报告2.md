## 二、错误 / 易错逻辑（当前仍存在）

### 1. `ContainerAccessPortAdapter.ResolveHost(ContainerId)` 丢弃 HostKey 🔴
`WinForms\Adapter\ContainerAccessPortAdapter.cs`
```csharp
public ContainerHandle? ResolveHost(ContainerId id)
    => _hostMount.ResolveByScope(id.ScopeId);
```
接收的是 `ContainerId`（含 `HostKey`），却只用 `ScopeId` 解析。若同一 scope 存在不同 hostKey 的绑定注册，会解析到错误宿主。即使当前 scope 是主键，也应先按 `id.HostKey` 精确命中、再回退 scope，避免"接收完整标识却只用一半"的隐患。

### 2. 事件校验词表与物理订阅能力集脱节 🔴
- `Shared\EventHelper.cs` `StandardEventTypes` 声明约 50 个"标准事件"（keydown/mousedown/load/shown/formclosing/resize/…）。
- `Shared\EventSubscriptionHelper.cs` `TrySubscribe` 实际仅能物理订阅约 9 个（click/doubleclick/textchanged/checkedchanged/selectedindexchanged/valuechanged/afterselect/selectionchanged）。
- `Validation\Validators\EventBindingValidator.cs` 用 `StandardEventTypes`（大词表）做校验 → 这些事件校验通过。
- 但 `EventBindingSystem`（`TryBindPhysicalEvent`）对这些事件 `TrySubscribe` 返回 false → 实体被判 `Failed`（"事件不支持物理挂接"）。
**结论**：大量"校验通过"的标准事件在实际物理绑定时必失败，词表口径不一致，`Validator` 的"已知事件名"判断具误导性。应将"可物理订阅能力集"独立成真源，校验器与绑定点共用。

### 3. `UiDispatcherCore.DispatchIfNeededAsync` 无超时（同步版有 5s）🟡
`Shared\Utils\UiDispatcherCore.cs`
- 同步版有 `SyncDispatchTimeoutMs = 5000` 超时兜底，异步版 `DispatchIfNeededAsync` 直接返回 `tcs.Task` **无任何超时**。
- 若 UI 线程被同步阻塞，异步版 TCS 永久挂起（无超时抛错），与同步版的防死锁语义不一致。属于健壮性缺口（尽管 `WinFormsUIDispatcher.InvokeAsync` 同样无超时，属已知权衡，但仍值得统一策略）。

### 4. `EntityTreeService.FindByName<T>` 按名双查可能命中不同实例 🟡
`WinForms\Services\EntityTreeService.cs`
- 先 `_controlPool.GetControl(name)`（按名直查），未命中再 `FindEntityByName(name)` → `_controlPool.GetControl(entity)`（按实体查）。两次查找路径不同（名单查 vs 实体映射），在 8.6 报告已指出 `_nameToControl` 名单查按"最后注册者"的残留风险下，同名字面量控件跨 scope 时两次查询可能返回不同实例，存在潜在不一致（S2 命名隔离已缓解但未根治）。

### 5. `EcsStateAccessor.GetValue`/`GetLiveValue` 两条读链几乎同构（语义标注但冗余）🟡
- 两方法都是"FindEntity → 读 ECS/物理 → 兜底 `ControlInfoComponent.Text`"，仅优先级顺序相反。注释明确这是**有意的双语义**（真源读 vs 实时真值读），不算 bug，但两条链的兜底/异常处理各自维护，仍属结构性重复，可提炼公共读链 + 参数化优先级。
