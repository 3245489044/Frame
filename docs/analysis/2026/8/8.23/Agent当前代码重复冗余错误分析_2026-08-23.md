## 一、重复逻辑（重复实现 / 平行维护 / 多源接线）

### 1.【高】JSON 生成能力三重端口并存，注释互相矛盾
"生成 JSON（json_object）"这一能力当前存在 **3 套接线**：

| 端口 | 位置 | 说明 |
|---|---|---|
| 独立接口 `ILlmJsonGenerator` | `Agent.Contract/Llm/ILlmJsonGenerator.cs:11` | 注释明确写"`GenerateJsonAsync` **不在 `ILlmClient` 接口上**（鸭子类型…）" |
| `ILlmClient.GenerateJsonAsync` 默认接口成员 | `Agent.Contract/Llm/ILlmClient.cs:60-62` | 实际已定义，默认抛 `NotSupportedException`，另有 `GenerateJsonWithToolsAsync`(L69-71) |
| 委托注入 `Func<…, Task<LlmResult>> _llmJsonGenerator` | `Agent.Core/Loops/AgentRunner.cs:70,95,447` | 经 `AgentRunnerAssemblyInput.LlmJsonGenerator` 喂给 `LlmStateDirector` |

- `LlmRoutingClient` 与 `SemanticKernelLlmClient` **同时实现** `ILlmClient` + `ILlmJsonGenerator`。
- `ILlmJsonGenerator.cs:7` 注释与 `ILlmClient.cs:60` 定义**自相矛盾**：前者说"不在接口上"，后者已在接口上。
- 同一能力三种取用方式（`is ILlmJsonGenerator` / 接口默认成员 / 委托字段），新增后端或导演时难以确定走哪条，双源漂移风险高。
- **建议**：以 `ILlmClient.GenerateJsonAsync`（含 `GenerateJsonWithToolsAsync`）为**唯一**端口，删除 `ILlmJsonGenerator` 接口与其鸭子类型判定；`AgentRunner` 的 `_llmJsonGenerator` 委托改为直接经统一网关 `ILlmClient` 取用，或保留委托但明确为"网关代理之上的导演专用快捷"，消除注释矛盾。

### 2.【中】LLM 路由/解析薄门面链三层叠放
对同一"取当前生效 LLM 客户端"的路由点，存在三层门面：

- `LlmMode`（`Agent.Runtime/State/Infrastructure/LlmMode.cs`，静态门面，持有 `Routing`）
- `LlmGateway`（`LlmGateway.cs`）：`Current => LlmMode.Routing ?? throw`、`IsConfigured => LlmMode.IsConfigured`（逐字转发）
- `LlmClientResolver`（`Agent.Modules/Invoke/Resolution/LlmClientResolver.cs`）：`Current => LlmGateway.Current`，`Resolve()` = 网关或 `LlmClientFactory.Instance.Get`

三层均指向同一路由代理，新增消费方需先判断该用哪一层，易再叠一层。`LlmClientResolver.Current` 与 `LlmGateway.Current` 完全等价，属冗余转发。
- **建议**：保留"静态门面（LlmMode）+ 显式 provider 解析（LlmClientFactory）"两层即可，`LlmGateway` 与 `LlmClientResolver` 二选一合并（例如统一由 `LlmClientResolver` 承载网关校验与 factory 例外）。

### 3.【中】LLM 调用观测双记录形态 + 双入口
- `LocalLlmClient._callLog`：`List<LocalLlmCallRecord>`（`LocalLlmClient.cs:59`）
- `LlmRoutingClient._callLog`：`List<LlmCallRecord>`（`LlmRoutingClient.cs:27`，治理层全后端）
- `LlmMode` 同时暴露 `CallLog`（→`Routing.Local.CallLog`）与 `AllCallLog`（→`Routing.CallLog`）

真实调用会**同时**记入 Local 层（`LocalLlmCallRecord`）与治理层（`LlmCallRecord`），两套记录形态 + 两个观测入口，字段重叠（Index/Backend/耗时/成败），数据冗余。
- **建议**：以 `LlmCallRecord`（治理层）为唯一可观测记录，`LocalLlmCallRecord` 若仅本地审计需要可保留但明确为"本地后端内部日志"，`LlmMode` 收敛为只暴露 `AllCallLog`。

### 4.【中】三个提示词解析器各自实现文本扫描原语
- `PromptDslParser.cs`：`ReadFencedBlock`（围栏扫描 + `| slots:` 探测）、行切分 `Split(new[]{“\r\n”,“\n”,“\r”})`
- `FormatSpecParser.cs`：`ReadSchemaBlock`（缩进续行收集）、`FindMatchingBrace`（平衡花括号）
- `AgentReturnSpecParser.cs`：`ExtractCandidates` / `ExtractLastJsonObject`（内联平衡花括号 + JSON 字符串转义感知）

三处重复实现"行切分 / 围栏 / 平衡花括号"等通用文本原语，逻辑大同小异（尤其平衡花括号两处）。
- **建议**：抽一个共享 `TextScan` 工具（`SplitLines` / `FindMatchingBrace(string, open, skipStrings)` / `ExtractFenced`），三解析器复用。

### 5.【低】`RoundStateMapper` 字典/IDataSpace 双过载 + `ApplySessionSeeds` 双实现
`RoundStateMapper.cs` 存在 `Seed(AxiomContext)` / `Seed(ctx,state,lease)` / `SeedFromLease`，以及 `ApplySessionSeeds(IDictionary)` 与 `ApplySessionSeeds(IDataSpace)` 两个同构私有方法（L92-105），复制粘贴式实现。
- **建议**：抽一个内部 `ApplyKeys(IEnumerable<(string,object?)>)` 或让 `IDataSpace` 适配到字典再统一处理。

### 6.【低】`DecisionWordMapper` 双命名外壳
`Agent.Orchestration/StepExecution/DecisionWordMapper.cs` 仅是 `DecisionWordClassifier` 常量转发 + `[BindAxiom]` 公理绑定载体。属"收敛"意图的合理外壳（Axioms 内不引 Operation 的调用方复用词汇常量），但作为第二个命名存在，新增词汇需同步两处常量引用。
- **建议**：保留（有正当理由），但在类注释明确"纯载体，词汇单一真相在 DecisionWordClassifier"，避免未来在壳内再塞逻辑。

### 7.【低】`StorageTemplateStore.JsonToScalar`（L104）仅为 `JsonShim.JsonScalarOrRaw` 一行别名
- **建议**：调用点直接使用 `JsonShim.JsonScalarOrRaw`，删除该私有别名（极低收益，可选）。

## 三、错误逻辑（bug / 误导性注释 / 语义不一致）

### 1.【高】`ILlmJsonGenerator` 注释与 `ILlmClient` 定义严重矛盾（误导 + 双源）
`ILlmJsonGenerator.cs:7-9` 明确声明"`GenerateJsonAsync` **不在 `ILlmClient` 接口上**（鸭子类型…）"，但 `ILlmClient.cs:60-62` 已把 `GenerateJsonAsync` 定义为默认接口成员。
- **后果**：若开发者按接口注释实现，会漏掉 `ILlmClient` 默认成员的覆盖；`is ILlmJsonGenerator` 鸭子类型判定与接口默认成员并存，两套判定路径对"后端是否支持 JSON"结论可能不一致。
- **修复**：删除 `ILlmJsonGenerator`（或改为 `ILlmClient` 的显式能力标记），统一注释与实现。

### 2.【中】`StatelessAnswerExecutor` 文档"纯聊天、零工具"与实际行为不符
`StatelessAnswerExecutor.cs` 类注释与 `_llm` 字段注释（L18/L25）均称"纯聊天、零工具"，但私有 `ChatAsync`(L200-207) 实际调用：
```csharp
await _llm.ChatWithToolsAsync(system, prompt, tools: LocalDbToolFacade.GetLocalDbTools(), ct: ct)
```
且 `DefaultSystemPrompt`(L34-37) 文案宣称"可调用本地数据库工具"。类顶注释与默认提示词**自相矛盾**——读者若按"零工具"理解会误以为 answer 不触网、不读写库。
- **修复**：统一注释为"默认带本地库工具（后端不支持时回退纯聊天）"，或将工具注入改为显式可配置，删除"零工具"描述。

### 3.【中】HFSM 信号派生双分类器，跨枚举映射易漂移
`DecisionPoint.ToAgentSignal`（`Agent.Core/Loops/DecisionPoint.cs:60-69`）优先用 `AgentReturnSignalMapper.ToAgentSignal`（`AgentReturnSignal→AgentSignal`），兜底用 `AgentSignalClassifier.FromEval`（`EvalOutcome→AgentSignal`）。两个枚举映射集合不同（`Done/Retry/Error` vs `Pass/Partial/Fail/ParseError`），新增枚举值需人工在两处对齐，易漏同步。
- **建议**：收敛为单一"信号派生"函数，输入统一为强类型评估结论 + 可选的 ReturnSpec，避免双 switch。

### 4.【低】`LlmClientFactory.Get` 与 `TryGet` 对"provider 返回 null"语义不一致
- `Get`(L29-36)：直接返回 `f()`，**不检查 null**（可能返回 null）。
- `TryGet`(L39-49)：`client = f(); return client is not null;`——返回 null 时返回 false。
同一 provider 注册表对"工厂产出 null"两方法行为分叉。
- **修复**：统一为"`Get` 对 null 结果抛异常 / `TryGet` 对 null 返回 false"，或两处都拒绝 null provider。

### 5.【低】`LlmRoutingClient` 统一 60s 网关超时对 Function Calling / 长任务误杀风险
`GuardAsync`(L76-148) 默认 `DefaultCallTimeout=60s` 作用于 `ChatWithToolsAsync`/`GenerateJsonWithToolsAsync`（S2 自由探索 Function Calling）。而 `RecordExternal`(L157) 又明确"编码代理是分钟级长任务，统一 60s 会误杀"。同一网关对"长任务"的两种处理并存，真实后端工具调用链 >60s 会被误判失败。
- **建议**：核对 S2 自由探索的真实后端是否可能 >60s；若可能，为 Function Calling 类端口提供可配置超时（对齐 Cline daemon 预算单一时钟语义）。

### 6.【低】`LoopDriver` 预算终止兜底依赖 `lastDecision` 终态判定（建议核对）
`Agent.Operation/Loops/LoopDriver.cs:54-60`：`budgetTerminate` 先判 `LoopDecisionConvergence.IsTerminal(lastDecision)`，否则 `budgetTerminateFallback?.Invoke(s) ?? Continue`。当 `budgetTerminateFallback` 为 null 且 `lastDecision` 为非终态（如 `Success` 是否被 `IsTerminal` 归为终态）时，收敛由 `ConvergeFinal`(L63) 兜底。建议核对 `IsTerminal` 对 `Success`/`Continue` 的归类，确保预算耗尽前 `Success` 能正确收敛，避免"规则已判成功却因非终态被继续迭代"。
