# 会话工作流「执行端 / LLM 端 / 节点存储」三管理面重构方案

> **版本**：v0.1（重构设计稿）　**日期**：2026-08-23
> **背景**：本地联调脚本 `agent_local_test_gui_test.json` 三步骨架（cline_execute→answer→cline_execute）全部执行成功（`steps=3`、`CallLog=3`、`ok=true`），
> 但 `conversationHistoryViewer` 最终只有 user 气泡、无 assistant / sub-agent 气泡 —— **终答为空**。
> **定位**：该问题的根因不是单点 bug，而是**执行端、LLM 端、节点存储三个横切面均无通用管理架构**，
> 各模块凭散落约定与魔法字符串协作，约定一旦被破坏（同名节点、键未填、后端未统一）即静默断链。
> **落位**：重构对象为 `Projects/Agent/src`（Agent.Contract / Agent.Orchestration / Agent.Modules / Agent.State）；
> 本文档放 `docs/analysis/2026/8/8.23/`

---

## 〇、结论先行

现状是「功能 + 约定」，重构目标是「管理面 + 契约」。

- **执行端**：现在只是注册为 `workflow function` 的"自治函数"，各自拼提示词、各自选后端、各自映射结果；缺统一执行器注册表与执行生命周期。
- **LLM 端**：现在只有 `ILlmClient` 客户端与路由代理，缺统一"模型网关 = 单一路由 + 能力协商 + 统一观测"管理面。
- **节点存储**：现在有内存态（`_stepNodes`，以 FuncName 为键 → 同名覆盖）与持久态（`ur_nodes`）两套，缺单一数据模型与单端口读写。

三管理面统一后，终答 = 引用链尾节点输出端口（模型定义的一部分），不再依赖启发式兜底与魔法键；同名覆盖、绕过网关、键拼错断链在结构上不可能发生。

---

## 一、现状诊断：三个横切面"没有管理面"

### 1.1 执行端：只有"函数"，没有"执行器管理面"

现状：`cline_execute` / `answer` 经 `WorkflowFunctionRegistrar.RegisterOnce` 注册为 workflow function，被模板以字符串 `FuncName` 命中（`WorkflowFunctionRegistrar`、`AnswerWorkflowFunction.cs`、`ClineExecutorFunction.cs`）。

由此产生的散落：

| 关注点 | cline 侧 | answer 侧 |
|--------|----------|-----------|
| 提示词拼装 | `ClineExecutorFunction.BuildRequest` 拼 L0/L1/L2 | `AnswerWorkflowFunction.ExecuteAnswerAsync` 拼 question/system |
| 后端选择 | `EndpointResolver.ResolveCline`（本地/daemon 分叉） | 直接 `ChatWithToolsAsync`（曾绕过网关直连配置后端） |
| 结果映射 | `ClineResult` / `collect_result` | `AgentExecutorResult` / `analyze_result` |
| 执行器单例 | `ClineExecutorFunction.SharedExecutor`（静态 Lazy） | `AnswerWorkflowFunction.SharedAnswer`（静态 Lazy） |

**缺失**：统一执行器注册表、统一执行上下文契约、统一"输入 → 调用 → 结构化结果"生命周期。执行端是自治函数，框架只在外面套了 for 循环。

### 1.2 LLM 端：只有"客户端"，没有"模型管理面"

现状：`ILlmClient` 接口 + 多个实现（`LocalLlmClient` / `OpenAiCompatibleLlmClient` / `SemanticKernelLlmClient`）+ 路由代理 `LlmRoutingClient`。

由此产生的散落：

- **三层门面重复**：`LlmMode`（静态门面）→ `LlmGateway.Current`（逐字转发）→ `LlmClientResolver.Current`（再转发），8.23 分析已点名"冗余转发"。
- **路由决策不在管理面**，而散在消费端：cline 靠 `EndpointResolver` 判 `LlmMode.LocalOnly`，answer 靠 `LlmGateway.Current`，历史上 answer 曾绕过网关。谁用网关、谁绕过，靠自觉。
- **无统一能力协商**：本地是进程内规则引擎、真实是 HTTP，执行端自行判断"是否有工具支持、是否长任务、超时多少"，能力协商逻辑散在各执行端。

**缺失**：统一"模型网关 = 单一路由 + 能力协商 + 统一观测"管理面。

### 1.3 节点存储：只有"落库"，没有"存储模型"

现状存在两套节点数据：

| 形态 | 位置 | 键 | 问题 |
|------|------|-----|------|
| 内存态 | `RoundPipelineContext._stepNodes/_stepProps/_stepInputs` | `step.FuncName` | collect/act 同为 `cline_execute` → **同名覆盖** |
| 持久态 | `ur_nodes`（`NodeExecutionService.PersistAsync` → `INodeOutputStore`） | `NodeKey` | 与内存态分离 |

结果载体 `NodeExecutionRecord` 又由这两套临时组装；"结果"与"状态"双轨（`Vars/Transient` 存执行瞬态，节点输出存持久态），`RoundStateMapper.Harvest/Seed` 在两轨间搬 `exec_result / act_result / collect_result / analyze_result`。

**缺失**：单一数据模型（节点 = 稳定实例 + 输入溯源 + 输出端口 + 状态 + 元数据），存储与状态统一，读写走单一端口。

1. 模板 `collect-analyze-act.json` 三步加载成功（`steps=3`），`CallLog=3` 说明三步都真实执行、本地 LLM 均返回内容。

3. `WorkflowResultDeriver.ResolveFinalStepIndex` 按链尾（act，索引 2）取 `nodes[2]` 越界 → `ResolveFinalAnswer` 返回 null。
4. 触发五层 `??` 启发式兜底（`safe_output → execResult.Text → ExtractText(exec_result) → TraceLeafText`）；会话模板不写 `exec_result`，前几层落空，最后一层因节点错位失败 → `result.Text` 空。

## 三、目标架构：三管理面统一模型

核心思想：把三个横切面收敛成三个「唯一管理面」，执行端不再自治、模型端不再自选、节点端不再双轨。

```
┌───────────────────────────────────────────────────────────────┐
│                 ExecutionHub（执行管理面）                         │
│  · ExecutorRegistry：按名注册 / 解析执行器（cline/answer/…）         │
│  · 统一执行生命周期：读节点输入 → 协商后端能力 → 调用 → 结构化结果 → 回填 │
│  · 执行器只声明：输入端口 / 输出端口 / 所需 LLM 能力（工具? JSON?）       │
└───────────────┬───────────────────────────────────────────────┘
                │ 唯一执行会话（ExecutionSession，承载本轮上下文）
┌───────────────▼───────────────────────────────────────────────┐
│                 ModelGateway（模型管理面）                         │
│  · 单一实例，单一路由决策点（本地 / 真实由它裁决，消费端不再判）          │
│  · 能力协商：工具 / JSON / 长任务超时 / 通道选择，统一在此              │
│  · 统一观测：所有调用（含 daemon 编码代理）经此记录                    │
└───────────────┬───────────────────────────────────────────────┘
                │ 输出以「端口值」写入
┌───────────────▼───────────────────────────────────────────────┐
│                 NodeStore（节点管理面）                            │
│  · 单一数据模型：Node（稳定 NodeId + 输入溯源 + 输出端口 + 状态）        │
│  · 内存态 = 缓存，持久态 = 唯一真相；读写只走一个端口                   │
│  · 终答 = 引用链尾节点的输出端口（模型定义，无启发式 / 无魔法键）          │
└───────────────────────────────────────────────────────────────┘
```

### 3.1 关键设计决策（每项对应一个现状缺陷）

**① 执行器 = 被管理对象，不是自治函数**
- 执行器不再自己拼提示、自己选后端、自己定义返回类型。
- 它只声明：消费哪些输入端口、产出哪些输出端口、需要什么模型能力。
- `ExecutionHub` 统一做：从节点读输入 → 向 `ModelGateway` 请求能力 → 拿结构化结果 → 写回节点输出端口。
- → 消除：提示词拼装散两端、后端路由散两端、结果映射散两端。

**② 模型网关 = 唯一路由 + 唯一能力协商点**
- 消费端永远只做：`ModelGateway.CallAsync(request)`。
- 路由（本地 / 真实）、通道（进程内 / HTTP / daemon）、能力（工具 / JSON / 超时）全部由网关裁决。
- 网关是唯一观测点（替代 `LlmMode.CallLog` + `LlmRoutingClient._callLog` 双记录）。
- 三层门面收敛为一层（只留 `ModelGateway`）。
- → 消除：answer 曾绕过网关、cline 与 answer 路由分叉、三层转发冗余。

**③ 节点 = 单一数据模型，存储与状态统一**
- 节点有**稳定 NodeId**（模板 `collect` / `act` 天然唯一），不再用 FuncName 做键 → 同名覆盖从根上消失。
- "执行结果、输入溯源、状态"是同一节点对象的字段，不再是 `Vars` + `ur_nodes` 两套。
- 读写只走 `NodeStore` 一个端口，内存态只是缓存。
- 终答 = 链尾节点 `OutputPorts`，无 `??` 链、无魔法键。
- → 消除：双轨状态、同名覆盖、五层启发式。

## 四、为什么是"根治"而非"打补丁"

| 本次症状 | 补丁思维（不推荐） | 管理面思维（根治） |
|----------|--------------------|--------------------|
| collect/act 同名覆盖 | 把字典键改成实例 ID | 节点天然有稳定 NodeId，存储模型不允许同名键 |
| 终答空 | 砍掉几层 `??` | 终答 = 链尾节点输出端口，是模型定义的一部分，不是推断 |
| answer 绕过网关 | 让 answer 也走网关 | 执行器不决策后端，网关是唯一路由，旁路在结构上不可能 |
| 键拼错断链 | 加 linter 校验键名 | 输入/输出端口是节点的声明式契约，非散落字符串 |

一句话：**现在是"功能 + 约定"，优化后是"管理面 + 契约"。** 约定靠人守，契约靠结构保证。

## 五、落地节奏（按管理面逐层重建，非补丁）

| 阶段 | 层 | 内容 | 兼容策略 |
|------|-----|------|----------|
| **M1 先立节点管理面** | NodeStore | 统一 Node 模型 + NodeId 主键 + 单端口读写，内存 = 缓存 | 现有 `ur_nodes` 作持久化后端，先不改 schema |
| **M2 再立模型管理面** | ModelGateway | 收敛三层门面为单一网关，路由 / 能力 / 观测唯一化，执行端不再判 `LocalOnly` | 保留 `ILlmClient` 作为网关后端适配，不清空既有实现 |
| **M3 最后立执行管理面** | ExecutionHub | 执行器声明式注册（端口 / 能力），`cline_execute` / `answer` 变执行器的薄包装 | workflow function 注册表保留为兼容入口，内部转执行器调用 |

**为什么这个顺序**：节点是数据真相（M1），模型是能力真相（M2），执行是编排（M3）。先定数据、再定能力、最后收敛编排，每层都有稳定基座，不互相依赖推进。

### 5.1 各里程碑验收信号

| 阶段 | 验收信号 |
|------|----------|
| M1 | 重跑 `agent_local_test_gui_test.json`：`conversationHistoryViewer` 出现 sub-agent + assistant 气泡，终答非空；`RoundPipelineContext` 不再有 FuncName 键控 |
| M2 | `AgentUi_GetLocalTestStatus` 的 CallLog 唯一来源为 `ModelGateway`；代码库无 `if (LlmMode.LocalOnly)` 消费端路由判断（除网关自身） |
| M3 | `cline_execute` / `answer` 均经 `ExecutorRegistry` 解析；模板以 `NodeId` 而非 `FuncName` 声明执行器 |

## 六、风险与回退策略

| 风险 | 应对 |
|------|------|
| 一次迁移改动面过大 | 三阶段独立可部署、独立可回退；每阶段保持既有行为契约（零回归） |
| 既有 `ILlmClient` 消费方众多 | M2 保留 `ILlmClient` 作网关后端适配，消费方统一改指 `ModelGateway`，逐个切换 |
| workflow function 注册表被外部依赖 | M3 保留注册表为兼容入口，内部委托执行器，不改对外注册面 |
| 测试脚本断言（如 CallLog 格式） | M2 观测统一后同步更新 `AgentUi_GetLocalTestStatus` 输出契约，脚本同步调整 |

## 七、与本仓库既有方案的衔接

- **不推倒重来**：`ur_nodes`（持久态）、`ILlmClient`（后端实现）、`WorkflowFunctionRegistrar`（注册入口）均保留，作为新管理面的后端/兼容层。
- **与「8.21 本地联调会话回答为空」方案**：该方案解决"answer 绕过网关"单点；本方案把网关收敛上升为管理面，杜绝同类问题再发。
- **与「8.23 重复冗余分析」**：其 P2「LLM 观测 / 门面收敛（LlmMode/LlmGateway/LlmClientResolver）」即本方案 M2 的子集。
