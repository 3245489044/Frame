# 节点逻辑收敛方案 —— 收敛到 Agent.Core/Nodes 单一节点管理面

> **版本**：v0.1（收敛设计稿）　**日期**：2026-08-23
> **背景**：「会话工作流三管理面重构方案」把节点管理面（M1）作为第一步；本文进一步把「节点管理面」**落成物理收敛**：
> 把散落在 5 个项目里的节点逻辑，收敛到 `Projects/Agent/src/Agent.Core/Nodes` 单一节点管理面（`NodeStore`），
> 消除「改一处节点问题要摸遍全项目」的认知与改动成本。
> **落位**：重构对象为 `Projects/Agent/src`（Agent.Contract / Agent.Axioms / Agent.Orchestration / Agent.Core / Agent.StorageBridge）+ `CsharpPrj/Operation/DataStoreDriven`（遗留引用层，仅门面封装不物理删）。

---

## 〇、结论先行

「所有节点逻辑物理搬到 `Agent.Core/Nodes`」作为**字面目标并不可行**——数据契约（AgentNode/NodeKeys 等）被全系统各层消费，必须留在低层 `Agent.Contract`。
**可行的收敛 = 物理搬「执行引擎」 + 建立「NodeStore 管理面」**：

- **可物理搬**：`Agent.Orchestration/StepExecution/*`（节点执行引擎）→ `Agent.Core/Nodes/`，前提是**先断开 `Agent.Core → Agent.Orchestration` 依赖**。
- **必须留低层**：`Agent.Contract/Nodes/*`（数据契约），只收敛"逻辑入口"不搬"物理归属"。
- **门面包装**：Operation 的 NodeRelationDeriver（遗留共享库）与 StorageBridge 的节点投影，以门面收敛进 `Agent.Core/Nodes`，不物理删。

收敛后：节点逻辑只有两个面——`Agent.Contract/Nodes`（数据契约）+ `Agent.Core/Nodes`（`NodeStore` 管理面）。

---

## 一、现状：节点逻辑散落在 5 处

| 层 | 位置 | 内容 | 角色 | 能否物理搬进 Core |
|----|------|------|------|-------------------|
| 数据契约 | `Agent.Contract/Nodes` | AgentNode、NodeKeys、NodeOutput、NodeExecutionRecord、INodeOutputStore | 被**所有层**消费（Contract/Launcher/Modules/Orchestration/Axioms） | **否**（搬高会违反分层方向） |
| 存储实现 | `Agent.Axioms/Nodes` | NodeOutputStore、NodeOutputCodec、NodeOutputKeys | 节点落库后端（ur_nodes NodeType=output） | 可（并入 Core 作为 NodeStore 后端） |
| **执行引擎** | `Agent.Orchestration/StepExecution` | WorkflowRunner、RoundSpec、RoundStep、NodeExecutionService、RoundStepInvoker、RoundPipelineContext、WorkflowResultDeriver、WorkflowReferenceStaticizer、RoundSpecLoader、StepContract、RoundStateMapper、NodeInputResolution | 节点构建 / 入参解析 / 执行 / 持久化 / 链尾推导 | **可**（整包搬） |
| 关系/引用 | `CsharpPrj/Operation/DataStoreDriven/Core` | NodeRelationDeriver、NodeRelationFactory、NodeStore、NodeGraphReconciler、ReferenceGrounding、WriteGuardPort | 引用图（遗留共享库） | 门面包装（不物理删，可能被他处使用） |
| 投影/注入 | `Agent.StorageBridge/Discovery` | NodeProjectionService、NodeInjectionService、NodeDiscoveryModels、NodeDiscoveryHelpers | 节点 → UI / 存储投影 | 门面收敛（上收到 Core/Nodes 或只消费 NodeStore） |

**主要消费者**（决定搬动爆炸半径）：

| 消费者 | 所在项目 | 使用 |
|--------|----------|------|
| `AgentRunner` | `Agent.Core/Loops` | 具体 `WorkflowRunner`（接口在 Contract） |
| `ConversationPipeline` | `Agent.Orchestration/SessionWorkflow` | `WorkflowRunner` / `RoundSpec` 等 |
| `AgentFrameworkAssembler` / `ConversationHosting` | `Agent.Launcher/Composition` | `RoundSpecLoader` / `WorkflowRunner` |

## 二、两个硬约束（决定收敛边界）

### 2.1 数据契约必须留在低层，不能搬进 Core

分层方向（单向）：
```
Agent.Contract ← Agent.Axioms ← Agent.Orchestration ← Agent.Core ← Agent.Launcher / Agent.Modules
```

`AgentNode` / `NodeKeys` / `NodeOutput` / `NodeExecutionRecord` / `INodeOutputStore` 被 Launcher、Modules、Orchestration、Axioms 全部消费。
把它们搬进 `Agent.Core`（高层）会制造**向上依赖 / 循环**。因此：

> **数据契约物理归属不可动；只能把「节点逻辑」收敛进 Core，不能把「数据契约」搬进 Core。**

可选的折中：在 `Agent.Core/Nodes` 内提供收敛后的"推荐入口"（对 Contract 类型做 using 别名 / 门面再导出），但物理归属仍在 `Agent.Contract`。

### 2.2 `Agent.Core → Agent.Orchestration` 依赖必须先断开才能搬执行引擎

- `Agent.Core/Loops/AgentRunner.cs` 是 **Core 引用 Orchestration 的唯一入口**（`new WorkflowRunner(...)`）。
- 接口 `IWorkflowRunner` / `WorkflowRoundResult` 在 `Agent.Contract`，**不在 Orchestration**。
- 只要 `Core → Orchestration` 依赖存在，Orchestration 的节点执行类型搬到 Core 后，Orchestration 需反向引用 Core → **成环**。

**断环条件**：把 `WorkflowRunner` + 整个 StepExecution 执行引擎搬进 Core，AgentRunner 改从 Core 本地取 `WorkflowRunner`；随后移除 `Agent.Core → Agent.Orchestration` 引用。而 **Orchestration 不依赖 Core**（其 csproj 无 Core 引用），所以断开后无环。

## 三、收敛方案（分三阶段）

> 目标态：**节点逻辑 = `Agent.Core/Nodes` 单一 `NodeStore` 管理面**（读/写/执行/推导/关系），数据契约留在 `Agent.Contract/Nodes`。

### Phase 0 —— 断 Core→Orchestration（搬执行引擎）

1. 把 `Agent.Orchestration/StepExecution/*`（约 13 个文件）**整包**搬到 `Agent.Core/Nodes/`：
   `WorkflowRunner`、`RoundSpec`、`RoundStep`、`RoundSpecLoader`、`NodeExecutionService`、`RoundStepInvoker`、`RoundPipelineContext`、`WorkflowResultDeriver`、`WorkflowReferenceStaticizer`、`StepContract`、`RoundStateMapper`、`NodeInputResolution`、`DecisionWordMapper`、`LoopDecisionMapper`、`LeaseContextFactory`。
2. `Agent.Core` 移除对 `Agent.Orchestration` 的 ProjectReference；`AgentRunner` 改用 Core 内的 `WorkflowRunner`（命名空间更新）。
3. `Agent.Orchestration` 仅保留 `SessionWorkflow/*`（ConversationPipeline 等），新增对 `Agent.Core` 的引用（WorkflowRunner 从 Core 取）。
4. 验证：`Agent.sln` + `FileDriven.sln` 编译通过。

**断环检查**：搬后 Core 不再引用 Orchestration；Orchestration 引用 Core（新增）；`AgentRunner → WorkflowRunner` 变为 Core 内部引用。无环。

### Phase 1 —— 建立 `NodeStore` 管理面（单一端口）

在 `Agent.Core/Nodes` 定义 `NodeStore` 门面，统一暴露节点全部操作：

| 能力 | 委托实现 | 说明 |
|------|----------|------|
| 节点构建 / 执行 | `NodeExecutionService`（已搬入 Core/Nodes） | BuildNode → ResolveInputs → Execute → Persist |
| 读 / 写端口 | `NodeOutputStore`（Phase 2 并入） | ur_nodes 单一持久化通道 |
| 结果推导 | `WorkflowResultDeriver`（已搬入） | 链尾节点输出端口 = 终答 |
| 控制流关系 | `NodeRelationDeriver`（Phase 3 门面包装） | 引用图 / 链尾推导同源 |

所有消费者（WorkflowRunner / ConversationPipeline / UI）只依赖 `NodeStore`，不再直接引用各层散落类型 → 消除"改一处摸全项目"。


### Phase 2 —— 收纳存储与投影

1. 把 `Agent.Axioms/Nodes`（`NodeOutputStore` / `NodeOutputCodec` / `NodeOutputKeys`）并入 `Agent.Core/Nodes`，作为 `NodeStore` 的存储后端。
2. 把 `Agent.StorageBridge/Discovery` 的节点投影 / 注入（`NodeProjectionService` / `NodeInjectionService` / `NodeDiscoveryModels` / `NodeDiscoveryHelpers`）上收到 `Agent.Core/Nodes`，或改为只消费 `NodeStore` 端口。

### Phase 3 —— 关系逻辑门面收敛

1. 在 `Agent.Core/Nodes` 封装 `NodeRelation` 门面，包住 `CsharpPrj/Operation/DataStoreDriven/Core/NodeRelationDeriver`（遗留共享库）。
2. `WorkflowResultDeriver` / `WorkflowReferenceStaticizer` 不再直接依赖 Operation，统一走 `NodeRelation`。
3. 评估 Operation 其他使用方后再决定是否收敛其内部实现；**默认只门面封装、不物理删**（避免影响 Operation 其他模块）。

## 四、目标态：节点逻辑只两个面

```
Agent.Contract/Nodes        Agent.Core/Nodes
┌───────────────────┐      ┌────────────────────────────────────┐
│  AgentNode        │      │  NodeStore（管理面，单一端口）      │
│  NodeKeys         │      │   · 构建/执行 → NodeExecutionService│
│  NodeOutput       │─────▶│   · 读/写    → NodeOutputStore      │
│  NodeExecutionRec │      │   · 链尾推导 → WorkflowResultDeriver│
│  INodeOutputStore │      │   · 关系     → NodeRelation(门面)   │
└───────────────────┘      │   · 投影     → NodeProjection       │
   （数据契约，仅被引用）   └────────────────────────────────────┘
                             （执行引擎，从 Orchestration 迁入）
```

**消费方（AgentRunner / ConversationPipeline / Launcher）一律只依赖 `NodeStore`。**

---

## 五、收益与风险

### 收益
- **单一管理面**："节点"概念不再横跨 5 个项目；节点类改动只摸 `Agent.Core/Nodes` + `Agent.Contract/Nodes` 两个面。
- **契约收敛**：输入/输出端口、链尾终答、关系推导都在一个管理面内，消除散落约定（对齐三管理面方案 M1）。
- **断环收益**：移除 `Core → Orchestration` 这一层高耦合依赖，分层更干净。

### 风险与边界
| 风险 | 应对 |
|------|------|
| 搬执行引擎影响面大（AgentRunner / ConversationPipeline / Launcher 均消费） | 分阶段 + 每阶段 `Agent.sln` / `FileDriven.sln` 编译 + GUI 本地联调回归 |
| `NodeRelationDeriver` 等 Operation 遗留库可能被他处使用 | 仅门面封装不物理删（Phase 3 先评估引用面） |
| 数据契约物理上留在 `Contract/Nodes`，与"全部收敛到 Core"直觉不符 | 文档明确：契约搬高违反分层方向；Core 内提供收敛推荐入口（别名/再导出） |
| 存储后端（NodeOutputStore）从 Axioms 移入 Core 影响 Axioms 层消费者 | 先确认 Axioms 无独立消费者（当前主要消费方为 Orchestration/RoundStepInvoker，随搬动一并迁移） |

---

## 六、与「三管理面重构方案」的衔接

- **M1 节点管理面**：本方案把 M1 从"逻辑管理面"落成"物理收敛 + NodeStore 单一端口"。
- **不动**：`ur_nodes`（持久化后端 schema）、`AgentNode`/`NodeKeys` 数据契约、`INodeOutputStore` 端口契约均保持。
- **分阶段独立可部署、可回退**：Phase 0/1/2/3 各自可独立编译验证，失败可回退到上一阶段（执行引擎仍在 Orchestration 时仅门面方案，不强制一次搬完）。
