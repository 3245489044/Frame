# Agent 主循环提取为"LLM 无关通用框架"的设计分析

> 作者视角：架构分析
> 日期：2026-08-25
> 覆盖：`Share/TaskStatusPool.Loops`、`Share/AiScheduling`、`Agent.Operation.Loops`、`Agent.Core`、`Agent.Modules`
> 目标落点（随项目演进更新）：**优先在 `Operation/CentralLoopDriven` 构建更通用的循环框架**
> 阅读对象：关心 Agent 循环架构收敛的开发/架构人员

---

## 摘要

本文回答一个问题：**Agent 里的"循环"能否（以及如何）从 LLM 中解耦出来，成为一个通用、可复用的确定性框架？**

结论先行：**"循环"本身早已被提取，而且已经是 LLM-free 的。** 真正与 LLM 纠缠的只有"导演"（Director）与"单轮动作"两个插入点。本文给出证据、画出 LLM/非 LLM 的分界线，并提出把剩余耦合收口为显式通用契约的落地路径。这不是"把散落的循环重新抽出来"，而是"把已经抽出来的循环正式化、并把最后两道耦合门显式化"。

---

## 一、现状：循环是分层的，且底层已经无关 LLM

当前 Agent 主循环由五层堆叠而成，从通用到专用逐层收紧。前三层在 `Share`/`Agent.Operation`，**完全不引用 Agent，也完全不引用 LLM**；后两层在 `Agent.Core`，是 Agent 专属薄壳。

```
┌──────────────────────────────────────────────────────────────┐
│ Agent.Core · RoundLoopDriver     AgentTaskItem 专属薄外观      │   ← 唯一挂 Agent
│   —— 租约派生 / 收割 / 五步包裹 / 结果收敛到 AxiomLoopResult    │
├──────────────────────────────────────────────────────────────┤
│ Agent.Operation · LoopDriver     通用单根循环骨架（TState 解耦）│   ← 通用，LLM-free
│   —— 引擎 + lastDecision 闭包 + 预算终止收敛 + 结果收敛         │
├──────────────────────────────────────────────────────────────┤
│ Share.TaskStatusPool · RoundLifecycle      五步单一载体         │   ← 确定性，LLM-free
│   —— Execute→Collect→Evaluate→Decide→Adjust                   │
├──────────────────────────────────────────────────────────────┤
│ Share.AiScheduling · AiSchedulerStateMachine<T: IStateFacet>   │   ← 通用，LLM 只是插件
│   —— AI 提议 + 计算守卫 + 原子施加；fail-safe 回退确定性默认      │
├──────────────────────────────────────────────────────────────┤
│ Share.TaskStatusPool · SnapshotDrivenLoopEngine<TState,TResult>│   ← 最底层 while，纯通用
│   —— while + 探索终止 + 预算终止（TS/TO/TM）                    │
└──────────────────────────────────────────────────────────────┘
```

关键点：**最底层的 `SnapshotDrivenLoopEngine<TState,TResult>` 是一个不包含任何 Agent/LLM 词的通用 while 循环**——`TState` 是任意快照、`execute` 是任意单轮动作、`next` 是任意状态转移、`budgetTerminate`/`externalTerminate` 是两个终止谓词。它只认识 `LoopDecision`（决策域与引擎同库）。

## 二、为什么"可行"不是口号：一个非 LLM 消费者早已实证

提取的可行性不是推测，而是**已被第二个消费者证明**。`RoundLoopDriver` 的类注释明确写着它收敛了 `AgentRunner`（LLM/混合调度）与 `RuleTaskExecutor`（配置式零 LLM）两套循环脚手架：

- `AgentRunner`：混合调度 + LLM 导演。
- `RuleTaskExecutor`：**配置式、零 LLM**，同样跑同一套 `LoopDriver + RoundLifecycle`。

也就是说：**一套 LLM-free 的循环骨架，已同时支撑"有 LLM"与"无 LLM"两个执行器。** 这直接证明了"把循环做成 LLM 无关通用框架"不是要去新建一个，而是要把这个**事实上的共享骨架**正式化、并把它的接入契约显式化。

## 三、LLM 的"法外之地"到底在哪（真正的耦合点）

LLM 在整个循环里只有**三个**实质存在，其余全是确定性计算：

| 位置 | 性质 | LLM 含量 |
|---|---|---|
| **导演 `IStateDirector`**（`LlmStateDirector`） | 提议"本轮整体状态怎么变"（切换策略/下一执行器） | **真 LLM** |
| **单轮动作 `executeStep`**（`WorkflowRunner.RunRoundAsync`） | 本轮实际干活（骨架：guard→prompt→cline→rule_match） | 内含 LLM 调用 |
| `DecisionPoint` / `DecisionWordClassifier` | 把决策词映射为 `EvalOutcome` / `LoopDecision` | 纯确定性词表映射，**无 LLM** |

结论：LLM 只住在**导演**和**单轮动作**两处。而这两处都已经是**注入点**而非硬编码：

- 导演：`AgentRunner.BuildRunEnvironment` 按 `SchedulingMode` 选 `LlmStateDirector` / `ConfigStateDirector` / `NoopStateDirector`，三者共用同一个 `AiSchedulerStateMachine` 与同一条 fail-safe 回退路径。
- 单轮动作：`AgentRunner` 只是往 `LoopDriver` 的 `executeStep` 回调里塞了一个 `RoundPipeline`；去掉这个回调，引擎照转。

因此"LLM 无关"的边界是清晰的：**框架定义循环如何转（while/五步/终止/裁决），LLM 定义每轮转出什么、往哪转（导演 + 动作），两者经显式端口对接。**

## 四、提取方案：把现状"收口为正式契约"，而非另起炉灶

既然通用骨架已存在，落地就在于三步"正式化"。

### 第 1 步：把 `LoopDriver` 的接入面提升为一等通用契约

以 `SnapshotDrivenLoopEngine` 的签名为基础，在 `Share.TaskStatusPool.Loops`（或单独 `Operation/LoopFramework`）定义通用循环端口，消除 `RoundLoopDriver` 目前"靠闭包参数拼装"的半隐式接入：

```text
interface ILoopPorts<TState> {
    // 单轮动作：本轮实质工作（LLM 可注入，也可纯计算）
    RoundOutcome ExecuteRound(TState s, RoundContext ctx);
    // 状态转移：读快照+本轮产物 → 下一快照（导演可注入，非 LLM 也成立）
    TState Next(TState s, RoundOutcome round);
    // 决策：round 产物 → EvalOutcome（确定性词表映射；LLM 不参与）
    EvalOutcome Evaluate(TState s, RoundOutcome round);
    // 两个终止谓词：预算终止 + 探索终止
    LoopDecision BudgetTerminate(TState s);
    bool ExploreTerminate(TState s);
}
```

这一步**纯重构、零语义变化**：把"传给 `LoopDriver.RunAsync` 的四个 lambda"收敛为一个端口对象，使接入契约可被非 Agent 模块显式实现。

### 第 2 步：把 Agent 专属的"租约派生 / 收割"也通用化

`RoundLoopDriver` 目前是唯一一处 `AgentTaskItem` 耦合。用 `IStateFacet` 已有的思想，把"从 TState 派生出每轮租约 + 把轮内标量收割回 TState"定义为两个泛型端口：

```text
interface ILeaseProvider<in TState, out TLease> { TLease Derive(TState s, int round); }
interface IStateHarvester<in TLease, in TState>  { void Harvest(TState s, TLease lease); }
```

`Agent.Core` 只需提供 `AgentTaskItem → AxiomContext` 的实现；通用循环框架不再引用 `AgentTaskItem`。这正好是 `AiSchedulerStateMachine` 已经做到的（它只认 `IStateFacet`，不认 `AgentTaskItem`）。

### 第 3 步：导演选择进入通用层

把"按模式选导演（LLM/Config/Noop）"从 `AgentRunner.BuildRunEnvironment` 提到通用层，作为配置项传入：

```text
IStateDirector ResolveDirector(SchedulingMode mode, IConfigStore? cfg, Func<...>? llmJson);
```

`ConfigStateDirector`（零 LLM）与 `NoopStateDirector`（纯规则）本就是通用实现，本就不依赖 LLM；`LlmStateDirector` 只是其中一个可插拔分支。这样通用框架自带"零 LLM 也能跑"的确定性默认，LLM 是可选增强。

**迁移纪律**：本轮只做 *structural* 移动与契约显式化，不改变任何行为；用现有 `RuleTaskExecutor`（零 LLM）与 `AgentRunner`（LLM）两套测试做双回归，证明重构后两者行为不变。

## 五、落地步骤 + 验证

1. **Task 1**：在 `Share.TaskStatusPool.Loops` 定义 `ILoopPorts<TState>`/`ILeaseProvider`/`IStateHarvester`（新增接口，无行为）。
2. **Task 2**：把 `LoopDriver.RunAsync` 的 lambda 参数改为接收 `ILoopPorts`（内部保持 while 不变）。
3. **Task 3**：`RoundLoopDriver` 改为实现 `ILoopPorts<AgentTaskItem>` + `ILeaseProvider/AStateHarvester`，删除内联闭包。
4. **Task 4**：导演解析收敛为通用 `ResolveDirector`；`AgentRunner` 只传模式与 LLM 生成器。

每步独立可提交、可回滚，都在共享循环骨架与既有测试的语义圈内。

## 六、收益

- **可测性**：LLM-free 的引擎可用纯确定性假执行器测全部分支（终止/熔断/收敛），不消耗 AI 额度。
- **复用**：任何"轮次式快照循环 + 预算终止"的需求（不只 Agent）可直接复用同一套引擎。
- **可替换**：想换一个"导演"（规则表/LLM/人审）只换 `IStateDirector` 实现，框架零改动。
- **认知清晰**：把事实上的共享骨架从 Agent.Core 的闭包参数里"提"出来，消除散落脚手架的重复。

## 七、风险与边界（诚实声明）

1. **并非从零提取，而是正式化**：若期望是"发现一个全新的、还没散的循环引擎"，结论会失望——它已存在，且合法消费者只有一个（RuleTaskExecutor）。本次价值在"显式契约 + 单一接入面"。
2. **导演接口仍是隐性 LLM 面**：`IStateDirector` 的 `DecideAsync` 可以被 LLM 实现，也可以被纯规则实现；"LLM 无关"指的是**框架不强制 LLM**，而非框架不提供 LLM 能力。这点务必说清。
3. **单轮动作内的 LLM**：`executeStep`（骨架 exec）内部仍会调 LLM；本轮提取只解耦"循环调度"，不移动"节点执行"。把节点执行也做成 executor-agnostic 属另一主题（见前一篇 answer↔cline 契约对齐方案）。
4. **过度抽象的克制**：不要为"假设会有第三个消费者"而过早引入抽象。当前一个通用骨架 + 一个已存在的零 LLM 消费者，已足以证明并支撑"LLM 无关"这一主张。

## 八、与既有框架的分工（定位澄清）

- `HierarchyMethod`：**数据/关系/历史的容器框架**（nodes/task/history，零 LLM）——回答"东西存哪、关系怎么编、历史怎么归"。
- `LoopDriver`/`RoundLifecycle`/`AiSchedulerStateMachine`：**循环调度框架**（通用、LLM-free）——回答"循环怎么转、何时停、状态怎么判"。
- `IStateDirector` + `executeStep`：**LLM 的唯一插入面**——回答"本轮干什么、往哪转"。
- `Agent.Core`：**上述三者的装配组合根**，把通用骨架 + LLM 导演 + Agent 节点执行粘在一起。

清晰的分工本身就是"LLM 无关"的最好证明：替换掉第四层的 LLM 实现，前三层与 Agent.Core 的非 LLM 部分纹丝不动。

## 九、落点裁决（更新）：优先在 `Operation/CentralLoopDriven` 构建

> 本节是对第四、五节"落点"的更新**覆盖**：统一循环框架不在 `Share`/`Agent.Operation` 原地正式化，而是优先在 `CsharpPrj/Operation/CentralLoopDriven`（**新建**）构建一个 Agent 无关、LLM-free 的更通用框架。

### 9.1 为什么优先落在 `CentralLoopDriven`

| 考量 | 结论 |
|---|---|
| 层位 | Operation 层，与 `DataStoreDriven` / `HierarchyMethod` 同层，是"Agent 无关"的舞台 |
| 规范 | 遵循 ModuleRule csproj（`Layer`/`Rules`/`Prompts`），与兄弟模块同构 |
| 承接 | `WorkFlowMethod/LoopFramework` 已有的 `IStateMachine`/`ILoopObserver` 抽象应迁入此处统一 |
| 现状缺口 | 该目录当前为空，正是为此新建 |

### 9.2 新模块边界与职责

`CentralLoopDriven` 只做一件事：**提供 `TState` 任意、单轮动作任意、导演可拔插、LLM-free 的轮次式快照循环框架。** 不认识 `AgentTaskItem`、不认识 `Cline`/`Answer`、不认识任何 LLM。

```
CentralLoopDriven
├─ Loops/       ILoopEngine<TState,TResult>；LoopPorts；终止谓词；轮次计数
├─ State/       IStateFacet<TState>（快照读写）；预算/轮次/收敛快照
├─ Decision/    LoopDecision；DecisionWord 词表；终决（确定性）
├─ Lifecycle/   RoundLifecycle（Execute→Collect→Evaluate→Decide→Adjust 五步）
├─ Director/    IStateDirector（LLM/Config/Noop 三实现；唯一可植 LLM 的缝）
└─ Ports/       ILeaseProvider / IStateHarvester / ILoopObserver（通用观测）
```

通用端口以 `SnapshotDrivenLoopEngine` 签名为准，把"传给 `LoopDriver.RunAsync` 的四个 lambda"收敛为 `LoopPorts<TState>`（`ExecuteRound`/`Evaluate`/`Next`/`BudgetTerminate`/`ExploreTerminate`，结构同第四节 `ILoopPorts`）；`ILeaseProvider`/`IStateHarvester`把租约派生与收割也泛型化，彻底摘除对 `AgentTaskItem` 的依赖。

- [ ] **Task 3 · 接 Agent**：`RoundLoopDriver` 改为实现 `LoopPorts<AgentTaskItem>` + 租约/收割端口，删除内联闭包；`AgentRunner` 只注入 LLM 生成器与导演选择。

### 9.4 边界重申

`CentralLoopDriven` 的"LLM 无关"指**框架不强制 LLM**（Config/Noop 导演可跑），而非不提供 LLM 能力（`LlmStateDirector` 仍可用）；单轮动作内的 LLM（`executeStep`）不迁移，本框架只解耦循环调度，节点执行的 executor-agnostic 属另一主题（answer↔cline 契约对齐）。

## 结语

Agent 的循环提取不是一次推倒重来，而是一次**身份确认与契约化**：确认 `SnapshotDrivenLoopEngine` / `LoopDriver` / `RoundLifecycle` / `AiSchedulerStateMachine` 已经是 LLM-free 的通用骨架，把 `RoundLoopDriver` 里最后一处 `AgentTaskItem` 耦合与闭包式接入收敛为显式端口，并用 RuleTaskExecutor 这个既有零 LLM 消费者守住"无关 LLM"的底线。到那时，"Agent 的循环"与"通用循环框架"是两件可独立演进的东西，LLM 只是后者上一个可拔可插的导演。
