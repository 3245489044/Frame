## 摘要

**结论先行：能引入，且高度契合——但只能直接复用"算子层"，"引擎/轨迹/结论"三层缺口必须在折叠框架侧自建。**

`BasicMethod.Calculus` 的四类算子（`IDifferentiator` / `IIntegrator` / `IEvolver` / `IConverger`）与折叠框架的三个端口（`IFoldOperator` / `ICutoffPolicy` / `IFoldHeadProjector`）概念几乎一一对应；其组合子 `EvolveUntilConverged` 本质上是**同步、无轨迹、无预算版本的折叠循环**，本身就是"折叠"这一范式在基础层的既有实证。

- **现状**：Calculus 是零消费者的孤儿模块（全库无外部引用），引入等于给它一个实际落地场景，符合"增强现有而非新建模块"的项目原则。
- **分层**：依赖方向 Operation → BasicMethod，单向无环，引入动作仅一行 `ProjectReference`，零迁移成本。
- **方案**：推荐**方案 A · 薄适配**——Calculus 原样保留，折叠框架侧写三个适配器补齐 async / 上下文 / 轨迹 / 结论。
- **克制**：只引算子，不让 BasicMethod 承担循环推进 / 预算执法——那仍是 `FoldEngine` 与 `SnapshotDrivenLoopEngine` 的领地。

## 一、背景与定位

### 1.1 Calculus 是什么

`BasicMethod.Calculus` 是 BasicMethod.Map 的并行基础模块，基于微积分理念提供 **T→T 同类型结构变换**框架，四大接口：

| 接口 | 数学语义 | 职责 | 核心方法 |
|------|---------|------|---------|
| `IDifferentiator<T>` | 导数 f'(x) | 分解 T 为局部、逐局部变换、合并回 T | `Differentiate(T)` |
| `IIntegrator<T>` | 积分 ∫f(x)dx | 累积多个 T，聚合为一个 T | `Integrate(T, T)` / `Reset()` |
| `IEvolver<T>` | 微分方程 dx/dt = f(x) | T→T 迭代变换，状态逐步演化 | `Evolve(T)` |
| `IConverger<T>` | 极限 lim xₙ = L | 迭代直到满足收敛条件 | `Converge(T)` / `HasConverged(T, T)` |

内置实现包括：`PropertyDifferentiator` / `TreeDifferentiator` / `GraphDifferentiator`（微分），`MergeIntegrator` / `UnionIntegrator` / `AccumulateIntegrator` / `OverlayIntegrator`（积分），`ConditionalEvolver` / `PipelineEvolver`（演化），`StableConverger` / `RetryConverger` / `ThresholdConverger` / `TimeoutConverger`（收敛）。

### 1.2 现状：孤儿模块

全库检索确认：`BasicMethod.Calculus` 命名空间**无任何外部消费方**（只有模块内部自用）。它是一套完整、零依赖、平台无关、纯确定性的算子库，但没有接入任何引擎。这正是引入的前提——不是"抢别人的活"，而是"补上它缺失的宿主"。

| 考量 | 结论 |

## 三、概念映射（算子 ↔ 框架端口）

折叠框架的端口契约（见 LoopFoldMethod 设计文档）：

```text
interface IFoldOperator<in TState, in TContext, out TNextState, out TVertex> {
    (TNextState next, TVertex vertex) Expand(TState state, TContext ctx, CancellationToken ct);
}
interface IFoldHeadProjector<in TState> { TState Head(IReadOnlyList<TState> trace); }
interface ICutoffPolicy<in TState> { FoldCut Decide(TState head, int coordinate, FoldBudget budget); }
```

| Calculus 算子 | 折叠框架端口 | 映射关系 | 可直接复用 |
|---------------|-------------|----------|-----------|
| `IEvolver<T>.Evolve` | `IFoldOperator.Expand` | 演化即展开——T→T 迭代 = 展开下一状态点 | ✅ |
| `IConverger<T>.HasConverged` | `ICutoffPolicy.Decide` | 收敛检测 = 截断判定的收敛分量 | ⚠️ 需补参数 |
| `IIntegrator<T>.Integrate` | `FoldTrace` / `IFoldHeadProjector.Head` | 二目合并累积 = 只增带折叠成判定点 | ⚠️ 需补轨迹 |
| `IDifferentiator<T>.Differentiate` | `FoldState → FoldVertex` | 分解变换 = 增量状态推导 | ⚠️ 弱对应 |
| `EvolveUntilConverged(...)` | `FoldEngine` 主循环 | 演化-收敛循环 = 折叠循环（同步无轨迹版） | ⚠️ 关键复用点 |

**关键认知**：`EvolveUntilConverged(evolver, converger, maxIterations)` 的循环骨架（`current = evolver.Evolve(current) → converger.Converge(current) → HasConverged 判定 → break`）与 `SnapshotDrivenLoopEngine` 的 `while → execute → next → 终止谓词` 完全同构。这本身就是"LLM 循环 = 状态折叠"论断在基础层的既有实证，支撑设计文档"范式更名而非从头发明"的判断。

## 四、缺口清单（折叠框架侧需自建）

| # | 缺口 | 说明 |
|---|------|------|
| 1 | **异步 + 取消** | Calculus 全同步；折叠引擎需 `async` + `CancellationToken` 作为一等公民 |
| 2 | **FoldTrace 只增带** | `EvolveUntilConverged` 只返回最终 `current`，中间演化轨迹被丢弃 |
| 3 | **FoldHead 折叠头** | 无"前缀 → 当前等效判定点"投影 |
| 4 | **FoldResult 结论封装** | 无 `{ Head, Trace, Coordinate, TotalDuration, Cut }` / `DataID` 结论 |
| 5 | **执法参数** | `HasConverged(current, previous)` 只收两状态；`maxIterations` 是硬编码上限 |
| 6 | **信任反转执法** | 截断/预算/取消不是一等公民；"对不可信外部算子强制执法"需引擎层实现 |

## 五、引入方案

### 方案 A · 薄适配（推荐）

Calculus 原样保留；折叠框架侧建 `Adapters/` 目录，把算子包进框架端口，补齐缺口。

```
Operation/LoopFoldMethod
├─ Fold/        FoldEngine<TState>（引擎自建，不引用 Calculus）
├─ Operator/    IFoldOperator<TState, TContext, TNextState, TVertex>
├─ FoldHead/    IFoldHeadProjector<TState>
├─ Cutoff/      ICutoffPolicy<TState>
└─ Adapters/    EvolverFoldOperator / ConvergerCutoffPolicy / IntegratorFoldHead（→ 引用 BasicMethod.Calculus）
```

**适配器设计**：

```csharp
// Adapters/EvolverFoldOperator.cs —— IEvolver → IFoldOperator
// 演化即展开：next = evolver.Evolve(state)；顶点由 vertexFactory 从当前状态合成
public sealed class EvolverFoldOperator<TState, TVertex>(
    IEvolver<TState> evolver,
    Func<TState, TVertex> vertexFactory)
    : IFoldOperator<TState, FoldContext, TState, TVertex>
{
    public (TState next, TVertex vertex) Expand(TState state, FoldContext ctx, CancellationToken ct)
    {
        ct.ThrowIfCancellationRequested();
        var next = evolver.Evolve(state);
        return (next, vertexFactory(next));
    }
}

// Adapters/ConvergerCutoffPolicy.cs —— IConverger → ICutoffPolicy
// 用 HasConverged 做收敛判定；Decide 无 previous 参数，适配器内部记忆上一轮判定点头
public sealed class ConvergerCutoffPolicy<TState>(
    IConverger<TState> converger)
    : ICutoffPolicy<TState>
{
    private TState? _previous;

    public FoldCut Decide(TState head, int coordinate, FoldBudget budget)
    {
        if (_previous is not null && converger.HasConverged(head, _previous))
            return FoldCut.Success;
        _previous = head;
        return FoldCut.Continue;
    }
}

// Adapters/IntegratorFoldHead.cs —— IIntegrator → IFoldHeadProjector
// 把只增带用二目合并折叠成当前判定点：Head(trace) = fold(trace, Reset, Integrate)
public sealed class IntegratorFoldHead<TState>(
    IIntegrator<TState> integrator)
    : IFoldHeadProjector<TState>
{
    public TState Head(IReadOnlyList<TState> trace)
    {
        var head = integrator.Reset();
        foreach (var point in trace)
            head = integrator.Integrate(head, point);
        return head;
    }
}
```

### 方案 B · 增强 Calculus（不推荐）

直接给 Calculus 补 async / context / trace。缺点：违背"基础层保持简单中性"，且把引擎职责下沉到错误的一层，污染零依赖的基础库。

### 方案 C · 只借鉴语义（不推荐）

不引依赖，折叠框架自建四算子。缺点：丢弃现成实现与内置算子（`ConditionalEvolver` / `StableConverger` 等），重复造轮子。

## 六、落地步骤 + 验证

1. **Task 1 · 引依赖**：`Operation/LoopFoldMethod` csproj 增加 `ProjectReference` → `BasicMethod.Calculus.csproj`。
2. **Task 2 · 建适配器**：落地 `Adapters/` 三个适配器（无引擎行为，纯端口包装）。
3. **Task 3 · 确定性测试**：用内置算子组合验证折叠全分支——`ConditionalEvolver` + `StableConverger` 测收敛、`PipelineEvolver` + `TimeoutConverger` 测截断、`RetryConverger` 测重试上限。
4. **Task 4 · 双回归**：以 `SnapshotDrivenLoopEngine` 行为为基准，验证"同一演化序列经适配器后引擎判定一致"，守住零 AI 额度、纯 CI 底线。

**验收标准**：
- 折叠框架编译不依赖 Calculus 的引擎职责（`EvolveUntilConverged` 不直接充当 `FoldEngine`）。
- 适配器覆盖算子 → 端口的完整映射，`FoldTrace` / `FoldHead` / `FoldResult` 由框架侧产出。
- 确定性假算子测试全部通过，不消耗 AI 额度。

## 七、风险与边界（诚实声明）

1. **只复用算子，不迁移引擎**：`EvolveUntilConverged` 语义上同构，但缺 async/轨迹/结论，不可直接充当折叠引擎；引擎推进仍在 `FoldEngine` / `SnapshotDrivenLoopEngine`。
2. **`Converge` 与 `Decide` 语义不同**：`IConverger.Converge` 是"把状态朝不动点变换"，`ICutoffPolicy.Decide` 是"判定是否截断"——适配器只映射 `HasConverged` 到判定，`Converge` 的变换语义不混入截断。
3. **LLM-free 不变**：Calculus 全同步确定性；算子内若含 LLM 属算子自身行为（`IFoldOperator` 的一种实现），不违背折叠框架不强制 LLM 的原则。
4. **克制**：不为假设的第三个消费者过度抽象；一个折叠骨架 + 三个适配器 + 既有零 LLM 消费者已足以支撑引入主张。

---

## 结语

`BasicMethod.Calculus` 与折叠框架的契合不是巧合，而是同一"状态变化"范式在基础层与 Operation 层的两次表达。引入它 = 给孤儿算子库一个宿主 + 给折叠框架一份现成算子集，中间只隔三个薄适配器。**算子在 BasicMethod，引擎在 Operation，适配器是唯一的接缝**——替换算子实现，引擎纹丝不动；替换引擎，算子照常可用。
