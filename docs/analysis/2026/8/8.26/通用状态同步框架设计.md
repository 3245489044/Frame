# 通用状态同步框架设计（收敛窗口 · 屏障-收敛握手 · 三级 ack）

> **版本**：1.0
> **日期**：2026-08-26
> **范围**：跨异步通道耦合的两方（或多方）参与者，为其"变更-可观测"之间的可见性窗口建立通用同步契约。
> **性质**：框架级通用设计文档（不绑定具体技术栈；HTML/WebView2 仅作为首个落地实例）
> **触发**：WinForm + WebView2 场景中"HTML 已写入但 DOM 未就绪"导致真实点击 `data-cmd` 无效——根因是框架层面的"变更已应用、但尚未可观测"窗口。
> **关联**：
> - 实例化文档：《HTML 传递与 UI 装配框架重构修复方案.md》（同一日，HTML 场景落地）
> - 姊妹框架：《通用状态管理框架_基于InternalStorage扩展设计.md》（8.7，状态存储/管理面）

## 一、问题领域（通用抽象）

### 1.1 一句话问题

> 两个通过**异步通道**耦合的参与者：**A 发起变更**，**B 随即（或其读者 R）读取变更后的状态**，二者之间存在一个"**变更已应用、但尚未可观测**"的窗口。窗口内读取者得到陈旧状态，且该窗口对生产者不可见、不可测量。

### 1.2 参与者模型

```
 Producer(A) ──ChangeCommand──▶ Consumer(B) ──Observable 投影──▶ Reader(R)
        ▲                          │
        └───────── Ack 链 ◀────────┘
```

| 角色 | 职责 | 典型实例（HTML 场景） |
|---|---|---|
| **Producer (A)** | 发起状态变更，关心"变更何时可被消费" | WinForm 侧 `SetHtmlAsync` / 写回端口 |
| **Consumer (B)** | 接收并应用变更；对外暴露可观测投影 | WebView2 渲染 DOM |
| **Reader (R)** | 读取 B 的**可观测**状态 | DOM 自动化 / 脚本桥 / 真实鼠标点击 |

关键区分：R 读取的是 B 的**可观测投影**，不是 B 的**内部模型**。这是本框架与"存储一致性"类问题的分界。

### 1.3 三层状态观

任何经过异步通道的状态，都存在三个层次：

```
Intended   —— A 声明的意图（A 侧知道）
Applied    —— B 已应用到内部模型（B 内部知道）
Observable —— B 的可观测投影已反映（R 能看到）
```

**"写成功" 只保证 Intended→Applied 的推进，不保证 Observable。** 本框架的全部机制，都是为了让 Observable 与 Intended 之间的差距可度量、可断言、可等待。

### 1.4 领域不变量（设计目标，也是验收准绳）

| 编号 | 不变量 | 含义 |
|---|---|---|
| I1 | **可观测无中间态** | R 每次观察要么完整旧态、要么完整新态，绝无撕裂/半成品 |
| I2 | **版本单调** | Observable 投影携带单调递增版本，陈旧可检测、可等待 |
| I3 | **写完成 ⇒ 可观测** | A 的"写完成"返回只有在 Converged 之后（或显式降级）才发生 |
| I4 | **降级可观测** | 收敛无法在界内完成时，A 得到显式 `Degraded` 结果，绝不静默成功 |

## 二、核心机制

### 2.1 收敛窗口（Convergence Window）

**定义**：从 B 完成 `Applied` 到 B 完成 `Converged` 的时间区间。

```
Applied ──────────────▶ Converged
        ├─ 收敛窗口 ─┤
        └ 窗口内 R 读旧态，窗口结束 R 读新态
```

**框架对窗口的三重态度**：

1. **显式化**：窗口不再是隐式时序假设，而是可查询的测量对象（起止、时长、超时）。
2. **封口**：生产者通过握手得知窗口结束的精确时刻，而非猜测。
3. **有界**：窗口有上界（超时策略），超界即降级，不无限挂起。

> 当前缺陷的本质：窗口存在但无人测量、无人等待——生产者以为"写入完成=成功"，实际窗口未闭合时读者读到旧 DOM。

### 2.2 屏障-收敛握手（Barrier–Convergence Handshake）

**屏障（Barrier）**：A 在一次变更上**阻塞等待**，直到收到足够的收敛确认才返回。屏障是"同步点"。

**收敛（Convergence）**：B 在自身 `Observable` 投影真正就绪时，向上游发送带证据的收敛确认。

两者合成一个两阶段握手协议：

```
A                              B
│ ── ChangeCommand{id,key,v} ──▶│
│ ◀─ Ack{id, Accepted} ─────── │  传输已接收
│ ◀─ Ack{id, Applied, av} ──── │  内部模型已应用
│ ◀─ Ack{id, Converged, proof}│  可观测投影已就绪
│   (屏障解除)                   │
```

**屏障策略（写方可选）**：

| 策略 | 行为 | 适用 |
|---|---|---|
| **Strict** | 必须收到 Converged 才返回成功 | 交互依赖可观测（点击、断言、自动化） |
| **Timeout** | 界内未收敛则返回 `Degraded`，由上层决定 | 无法保证收敛证据的运行时 |
| **FireAndForget** | 立即返回，收敛由回调/事件通知 | 非关键路径、写后不立即读 |

### 2.3 三级 ack 语义

| 级别 | 名称 | 保证 | 不可保证 |
|---|---|---|---|
| **1** | **Accepted** | 命令已到达 B 的传输层并被接纳 | 是否被应用 |
| **2** | **Applied** | B 的内部模型已更新 | 可观测投影是否反映 |
| **3** | **Converged** | B 的可观测投影已就绪（含证据） | 无（本框架的最终保证） |

**收敛证据（ConvergedProof）**：第三级 ack 必须携带可校验证据，防止"口头声称收敛"。可选策略（可插拔）：

| 证据策略 | 机制 | 适用运行时 |
|---|---|---|
| **RenderCallback** | B 的渲染框架在渲染完成后回调，框架转发为 Converged | WebView2 NavigationCompleted、WPF 布局完成 |
| **VersionSnapshot** | B 发布带单调版本的可观测快照，A 校验版本推进 | 快照式投影、缓存副本 |
| **Probe** | A 在写入后以收敛查询轮询，直到 R 读到新版本 | 无法获得内部回调的黑盒运行时 |

> 证据策略决定"收敛"是**事实**（回调）还是**逼近**（轮询）；框架两者皆支持，由传输适配器声明。

## 三、四层架构

```
┌───────────────────────────────────────────────────────────────┐
│ 应用层 Application     业务代码；写方用 IConvergenceWriter，    │
│                         读方用 IConvergenceReader；不碰传输    │
├───────────────────────────────────────────────────────────────┤
│ 收敛层 Convergence     核心：收敛窗口/握手状态机/ack 升级/       │
│                         屏障/排序/幂等/超时降级                 │
├───────────────────────────────────────────────────────────────┤
│ 协议层 Protocol        消息格式：ChangeCommand / Ack /          │
│                         ConvergedProof / Snapshot；版本、       │
│                         关联 ID、幂等键、编解码                  │
├───────────────────────────────────────────────────────────────┤
│ 传输层 Transport       ITransport 抽象：Send/Subscribe；         │
│                         WebView2 postMessage / NamedPipe /      │
│                         进程内 Actor / MCP / 消息队列           │
└───────────────────────────────────────────────────────────────┘
```

### 3.1 分层职责与依赖规则

- **应用层**只依赖收敛层接口；不感知消息格式与传输细节。
- **收敛层**只依赖协议层抽象；维护每变更的状态机（Session），不感知具体通道。
- **协议层**只依赖传输层接口；负责编解码与消息语义，无业务逻辑。
- **传输层**是唯一触碰具体通道的点；声明自己的收敛证据策略。

> 依赖单向向下，可整体测试：收敛层可用"内存传输"做单测，不依赖真实 UI/进程。

### 3.2 收敛层内部：会话状态机

每个 `ChangeCommand` 产生一个 **ConvergenceSession**，生命周期状态迁移：

```
Created → Accepted → Applied → Converged   （理想路径）
   │         │         │
   └──▶ Timeout / Retry / Degraded          （异常路径）
```

状态机持有：`id`、`key`、`目标版本`、`最高 ack 级别`、`窗口起止`、`结果`。会话在 Converged 或 Degraded 后终结并回收。

## 四、关键接口草图（C#，收敛层 + 协议层）

```csharp
// ── 收敛层 ──────────────────────────────────────────────

public enum AckLevel { Accepted, Applied, Converged }

public enum ChangeResult { Committed, Degraded, Failed }

public sealed record ChangeOutcome(
    string ChangeId,
    string Key,
    long Version,
    AckLevel HighestAck,
    TimeSpan Window,          // 实测收敛窗口
    ChangeResult Result);     // Committed = 已收敛；Degraded = 显式降级

public enum BarrierMode { Strict, Timeout, FireAndForget }

public sealed record WriteOptions(
    BarrierMode Barrier = BarrierMode.Timeout,
    TimeSpan? WindowTimeout = null,
    int MaxRetries = 0);

public interface IConvergenceCoordinator
{
    Task<ChangeOutcome> WriteAsync<T>(
        string key, T value, WriteOptions? options = null, CancellationToken ct = default);
}

public interface IConvergenceReader<T>
{
    Task<Observed<T>> ReadAsync(string key, long minVersion = 0, CancellationToken ct = default);
}

public sealed record Observed<T>(T Value, long Version, bool IsStale);

// ── 协议层 ──────────────────────────────────────────────

public abstract record Message;                       // 消息基类（含 ChangeId 关联）

public sealed record ChangeCommand<T>(string Key, long Version, T Payload) : Message;
public sealed record Ack(string ChangeId, AckLevel Level, object? Evidence) : Message;
public sealed record Snapshot<T>(string Key, long Version, T Value) : Message;

public interface IProtocolCodec
{
    Message Decode(string wire);
    string Encode(Message message);
}

// ── 传输层 ──────────────────────────────────────────────

public interface ITransport : IDisposable
{
    Task SendAsync(Message message, CancellationToken ct = default);
    IDisposable Subscribe(Func<Message, CancellationToken, Task> handler);
    ConvergenceEvidenceStrategy EvidenceStrategy { get; }   // 声明收敛证据能力
}
```

> 读方等待收敛：`IConvergenceReader.ReadAsync(key, minVersion)` 在传输层不支持推送式证据时，内部退化为 Probe 轮询——同一接口、两套实现。

## 五、典型时序

### 5.1 成功路径（Strict）

```
App        Coordinator        Transport          Consumer(B)
 │ WriteAsync                  │                    │
 │──────────▶│ 建 Session      │                    │
 │           │─ ChangeCommand ─▶│──── 投递 ──────────▶│
 │           │◀── Ack Accepted ─│◀── 回执 ───────────│
 │           │◀── Ack Applied ──│◀── 应用后 ────────│
 │           │◀── Ack Converged─│◀── 可观测就绪 ────│
 │           │ 窗口=ΔT, 屏障解除                      │
 │◀─ Committed ─│                  │                    │
```

### 5.2 超时降级路径（Timeout）

```
App        Coordinator          Transport       Consumer(B)
 │            │─ ChangeCommand ─▶│──────────────▶│
 │            │◀─ Ack Accepted ─ │◀──────────────│
 │            │◀─ Ack Applied ───│◀──────────────│
 │            │  (窗口超时)                       │  (可观测未就绪)
 │◀─ Degraded ─│（显式：未收敛即返回，上层决定）   │
 │            │   重试/轮询/放弃 由上层策略决定     │
```

> 关键差异：现有代码在"Applied 前后"就宣称成功；本框架在"Converged 或 Degraded"才返回。失败是**显式结果**，不是静默成功。

## 六、通用适配点（非 HTML 场景）

本框架不是 HTML 专用方案；核心是"写-读之间的可观测性契约"。可适配：

| 场景 | Producer | Consumer | Observable | 收敛证据策略 |
|---|---|---|---|---|
| **HTML/WebView2** | WinForm 写内容 | WebView2 DOM | 可查询/可点击的 DOM | RenderCallback（NavigationCompleted + 桥注入确认） |
| **UI 自动化/点击** | 自动化脚本发指令 | UI 控件渲染 | 控件树可命中 | RenderCallback / Probe |
| **跨进程/跨线程 UI** | 工作线程写状态 | UI 线程投影 | 控件可见/可交互 | UI 线程封送完成回调 |
| **MCP / Agent 工具** | 编排器调工具 | 工具执行 | 工具副作用可见 | Probe（副作用可观测轮询） |
| **分布式缓存/副本** | 主节点写 | 副本应用 | 副本可读 | VersionSnapshot |
| **消息队列消费** | 生产者投递 | 消费者应用 | 下游可读 | Ack 链（MQ 自带回执） |

> 判定一个场景是否适用：**是否满足"写已成功，但读仍是旧值"的窗口**。满足则套用本框架，否则不需要。

## 八、落地路径

### 阶段 A：HTML 场景实例化（验证框架可行性）
- `HtmlChannel.WriteAsync` 升级为返回 `ChangeOutcome`：`SetHtmlAsync` 后 `await` NavigationCompleted + 桥注入确认 → Converged；超时 → Degraded。
- 脚本桥 / 真实点击统一走"就绪断言"：未 Converged 不派发。
- **验收**：`agent_html_view_switch_test` 全绿；真实点击与脚本点击行为一致。

### 阶段 B：收敛层提取为通用组件
- 新建共享模块（如 `CsharpPrj/Modules/Convergence`），落地 `IConvergenceCoordinator` / `ConvergenceSession` / 状态机。
- 传输适配器：`WebView2Transport` + `InMemoryTransport`（单测用）。
- **验收**：收敛层全部用例可在 InMemory 上单测通过，不依赖 UI。

### 阶段 C：推广到其他参与者
- 脚本执行等待 UI 渲染结果、MCP 工具副作用可见性等，按第六节映射逐个接入。
- **验收**：至少 2 个不同传输均满足 I1–I4 不变量。

## 九、验收标准

1. **写完成即可观测（I3）**：`WriteAsync` 返回 Committed 后，读方必然读到新状态；读旧值只可能出现在 Degraded 结果中。
2. **陈旧可检测（I2）**：任何陈旧读取都能由版本号识别，并可通过 `minVersion` 等待收敛。
3. **降级显式（I4）**：收敛超时返回 `Degraded`，绝无"静默成功"。
4. **可观测无中间态（I1）**：任何观察要么全旧、要么全新。
5. **通用性**：同一收敛层代码，InMemory 与 WebView2 两个传输均满足上述不变量。
6. **回归**：既有 `MainProj.sln` / `FileDriven.sln` 全绿；HTML 场景冒烟通过。

## 十、风险与取舍

| 决策 | 取舍 |
|---|---|
| 写操作阻塞到 Converged（Strict） | 增加写延迟（毫秒级）；换取读确定性。可配置 FireAndForget 缓解非关键路径 |
| 收敛证据策略可插拔 | 传输实现复杂度上升；但保证"收敛"是事实而非猜测 |
| 三级 ack 增加消息量 | 每变更多 2-3 条 ack；换取链路每段可观测、可断言 |
| 与既有"写即成功"语义冲突 | 需迁移现有 `SetHtmlAsync`/写回端口调用点；按 B 级既有方案渐进替换 |
| 黑盒运行时只能 Probe | 收敛是"逼近"而非"事实"，有轮询延迟；文档化该传输的证据等级 |

## 十一、建议执行顺序

先 **阶段 A**（在 HTML 场景证明框架能修复真实缺陷），再 **阶段 B**（把收敛层抽成通用组件并单测化），最后 **阶段 C**（推广到其余参与者）。每个阶段独立可交付、带验收，且不破坏既有功能。
