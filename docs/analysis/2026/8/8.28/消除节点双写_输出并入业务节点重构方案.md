# 消除节点双写 — 输出并入业务节点（删除 NodeType=output 独立记录）

> **版本**：1.0　**日期**：2026-08-28
> **性质**：根本解决方案（分析 + 实施纲领）
> **背景**：主对话框 task 中经 `conversation/send.json` 发送消息后，Task 视图节点面板显示「两个节点」。上一轮已定位：**根因不在渲染键去重，而在写侧对同一逻辑节点产生了双条 ur_nodes 记录**。
> **本方案方向（用户裁定）**：不改渲染侧键去重，而从写侧根本消除重复 —— **删除输出节点逻辑，输出值并入业务节点，业务节点成为唯一记录**。

---

## 一、重复写入的根源（双写点）

`NodeExecutionService` 对同一个 send 节点做两种落库，产生两条不同 `NodeKey` 的 `ur_nodes` 记录：

| 记录 | 写点 | NodeKey | NodeType | 载荷 |
|------|------|---------|----------|------|
| 输出节点 | `WriteNodeOutputsAsync`（→`_store.WriteOutputAsync`→`NodeOutputStore`） | `nodes.{wf}.{node}` | `output` | 各端口值（`NodeOutputDoc.Ports`） |
| 业务节点 | `PersistNodeReferencesAsync`（`_nodes.PutAsync`） | 裸 `{node}` | `node` | `{Symbol}` + `RelationsJson` |

读侧 `StandardContextBuilder` 只从输出节点（`TryGetNodeOutputAsync`）读，`RenderTaskNodesPanelAsync` 节点面板把两来源（cross_db_link 挂载键 + ThreadId 全量枚举）并集、按 `NodeRecord.NodeKey`（存储键）去重 —— 同一逻辑节点的 `nodes.{wf}.{node}` 与裸 `{node}` 两条记录 NodeKey 不同，去重不命中 → **显示两个节点**。

> 本质：**同一个逻辑节点被落库成两行**，任何"按键去重"都是治标；根治 = 业务节点唯一、输出并入其中。

---

## 二、根本方案：输出并入业务节点

### 2.1 目标态

`ur_nodes` 中一个 send 节点**只有一条记录**：

```
NodeKey = 裸 {node}（如 answer）
NodeType = node
ThreadId = wf
PayloadJson = { Symbol, Outputs: { Visibility, Ports: { port → {Type, Value} } } }
RelationsJson = { 关系状态 }
```

业务节点同时承载：标识（`Symbol`）+ 输出端口值（`Outputs`）+ 关系状态（`RelationsJson`）。**删除独立的 `NodeType=output` 记录与 `nodes.{wf}.{node}` 键形态。**

### 2.2 关键设计决策

- **`INodeOutputStore` 接口不变**（`WriteOutputAsync/TryGetNodeOutputAsync/EnumerateOutputsAsync/...`），只改 `NodeOutputStore` 实现的**存储形态**（背靠业务节点而非独立 output 记录）→ 消费方（`StandardContextBuilder`、`NodeExecutionService.ResolveInputsAsync`、`RoundStepInvoker`、`NodeStore`）**零接口改动**。
- **业务节点载荷统一模型**：`NodeOutputCodec` 新增 `BusinessNodePayload { Symbol, Outputs }`（`Outputs` 复用既有 `NodeOutputDoc`）。
- **两个既有业务节点写点协调为读-改-写、互不覆盖**：
  - `NodeOutputStore.WriteOutputAsync`（写输出）：读业务节点 → 更新 `Outputs.Ports[port]` → 写回（保留 `Symbol`/`RelationsJson`）。
  - `PersistNodeReferencesAsync`（写业务标识/关系）：读业务节点 → 更新 `Symbol` + `RelationsJson` → 写回（保留 `Outputs`）。

### 2.3 逐文件改动清单

| # | 文件 | 改动 |
|---|------|------|
| 1 | `Operation/HierarchyMethod/Nodes/NodeOutputCodec.cs` | 新增 `BusinessNodePayload { Symbol, Outputs }` 编解码；`NodeOutputDoc` 复用 |
| 2 | `Operation/HierarchyMethod/Nodes/NodeOutputStore.cs` | `WriteOutputAsync`/`TryGetNodeOutputAsync`/`EnumerateOutputsAsync`/`EnumerateNodeKeysAsync`/`ClearNodeAsync`/`ClearWorkflowAsync` 全部改为读写**业务节点**（裸 `{node}`、`NodeType=node`），不再用 `NodeOutputKeys.NodeKey`/`NodeType=output` |
| 3 | `Operation/HierarchyMethod/Nodes/NodeOutputKeys.cs` | `NodeKey`/`Prefix`（`nodes.{wf}.`）仅供迁移/兼容，`NodeOutputStore` 不再消费；`Normalize` 保留 |
| 4 | `Agent.Core/Nodes/NodeExecutionService.cs` | `PersistNodeReferencesAsync` 写业务节点时读-改-写（保留 `Outputs`）；`WriteNodeOutputsAsync` 仍经 `_store.WriteOutputAsync`（现写业务节点 `Outputs`） |

| 8 | 测试 | `NodeOutputStoreTests` / `StandardContextBuilderTests` / `NodeOutputStoreTests` 期望同步（记录形态改业务节点） |

## 三、协调设计与风险

### 3.1 WriteThroughNodeStore 交互（关键风险）

业务节点写入会经 `WriteThroughNodeStore`（写透白名单 = `NodeType=node`）触发图镜像 + `RelationsJson` 对账。改造后：
- `NodeOutputStore` 写业务节点（`NodeType=node`）同样触发写透 → 需确保其 `RelationsJson` 不被误清（WriteOutputAsync 读-改-写时保留既有 `RelationsJson`）。
- `PersistNodeReferencesAsync` 与 `NodeOutputStore` 同一业务节点读-改-写 → 串行化（单进程 SQLite upsert by key 基本安全；B5 竞态若存在需在写侧加护栏）。

### 3.2 存量数据迁移

既有 `NodeType=output` 记录（`nodes.{wf}.{node}`）在新形态下不再被读（`TryGetNodeOutputAsync` 改读业务节点）。需一次性迁移或确认可接受旧记录残留（只读侧失效、不阻塞）。迁移脚本：把 `nodes.{wf}.{node}` 的 `Outputs` 并入裸 `{node}` 业务节点的 `PayloadJson.Outputs`。

### 3.3 影响面

- AI 上下文投喂（`StandardContextBuilder`）：读输出节点 → 读业务节点 `Outputs`，行为等价。
- MCP `node-project`/`node-select`：`NodeRecordResolver` 双键形解析收敛为业务记录。
- UI 节点面板：只显示业务节点（每个逻辑节点一条）→ **「两个节点」根除**。
- 右侧对话历史（`BuildTaskAsync`）：仍 `TryGetNodeOutputAsync` 读业务节点输出 → 节点气泡正常。

## 五、结论

写侧双写（业务节点 + 输出节点）是「两个节点」的根因；**根本解决 = 删除输出节点独立记录、输出值并入业务节点、业务节点唯一**。`INodeOutputStore` 接口保持，消费方零接口改动，从源头消除重复落库。
