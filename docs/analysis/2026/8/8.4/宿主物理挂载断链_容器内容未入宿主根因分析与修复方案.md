## 一、问题现象（运行实证，21:08~21:25 多次复现）

```
16, FAIL, assert container sideContainer count>0
   → assert-container: 容器 'sideContainer' 子控件数断言失败 — 期望 count>0, 实际 0
17, FAIL, validate-mount titleLabel
   → validate-mount: 未找到宿主 'sideContainer'
```

**核心矛盾**：渲染系统对 Side scope 自判成功，容器侧却真实为空：

```
EcsGate_audit_after: Scope=Side, CollectedCount=19, AppliedCount=19,
                     MountedCount=18, OrphanCount=0, Succeeded=True   ← 渲染自判成功
WinFormApplier 挂载结果: controls=19, relations=18/18 mounted, allMounted=true
--------------------------------------------------------------------------------
assert-container: sideContainer(Panel) children=0                     ← 宿主实际 0 子控件
validate-mount: 未找到宿主 'sideContainer'                            ← titleLabel 不在宿主内
```

> ⚠️ 注意：用户最初贴的 20:58 日志中这两项为 PASS，本次实际运行期间不稳定（PASS↔FAIL 交替），
> 属于**多作用域叠加渲染时序竞态**导致的不确定性，而非“恒失败”或“恒成功”。

## 二、根因分析

### 2.1 四层定位：这不是“执行层”、不是“存储层”的问题

| 目录/层 | 职责 | 与本缺陷关系 |
|---------|------|-------------|
| `CsharpPrj/BasicMethod/Map/Container`（执行容器） | 命令/事件→函数，MediatR 分发 + 熔断/重试/超时 | **无关**：只执行“双击→调用 LoadConfigToTarget”，不触碰渲染/宿主；且 `AddContainer` 无调用方（未接线） |
| `CsharpPrj/Modules/InternalStorage`（状态/存储层） | `StorageCell/Registry/StorageLayer` 底座 + `ContainerStateStore/HostBindingStore` | **不产生/不移动控件**；但其 `ContainerState.{NodeCount,Status,LastError}` 是修「如实暴露失败」的现成落点（§4.1） |
| FrontEndDriven 渲染管线（`EcsGate/ConfigDrivenControlFactory/WinFormApplier`） | 配置→实体→控件→物理挂载 | **缺陷所在地**：内容物理挂错宿主 |

### 2.2 运行期诊断锁定的证据链

为定位，往渲染链临时加了诊断日志（已全部清理，见 §六），逐层取证。Side 渲染（scope=Side，host=sideContainer）：

| # | 证据 | 结论 |
|---|------|------|
| 1 | `RenderLoadStage.Host: scope=Side, rootContainerName=sideContainer` | 宿主 **sideContainer 成功注入** |
| 2 | `RootHostReRegister: rootEntity=Entity(34), hostName=sideContainer, before=sideContainer` | 渲染时 root 实体→sideContainer 映射**已建立** |
| 3 | `CsgCollect.Relation: child=MainView(35), parentId=Entity(34)` | collect 的关系父**逻辑正确**（指向 root 实体） |
| 4 | `WinFormApplier.Relation: parent=root(Panel), child=MainView` | `ApplyRelations` 给 MainView 找父控件，**物理得到 root 面板**而非 sideContainer |
| 5 | `validate-mount: titleLabel 实际宿主: titleLabel→MainView→root(ContainerView)→FileDriven(MainForm)` | 内容最终挂在**全局 root**，不是 sideContainer |
| 6 | `assert-container: host=sideContainer(Panel) children=0 挂接链: sideContainer→mainSplitter_Panel2→mainSplitter→MainView→root→MainForm` | sideContainer 骨架正确但**无子控件** |

### 2.3 根因归纳（D1-D5）

**D1 · 全局共享 composition，每次渲染新建同名 `root` 根实体**
`ConfigDrivenControlFactory.Convert` 对**每次**渲染都 `CreateRootEntity` 新建名字固定为 `"root"` 的面板实体，再 `ConvertView→ConvertControl` 把该配置的 view 挂其下。所有 scope 共用同一 `EntityManager + ControlPool`（`EcsGate` 全局 composition 单例），MainLayout 的 root 与 Side 渲染新建的 root 是**不同实体同名 `"root"`**。`Ports.CreateControl` 以实体原名重注册（`_nameToControl["root"]`），在**多 scope 叠加渲染/事件重渲染**中覆盖 `RegisterRootControl` 建立的 `root实体→sideContainer` 映射（证据 2→4 即由此翻转）。

**D2 · 宿主注入只做“名字映射”，不建立“物理挂载”**
`RenderStageRunner`/`RenderLoadStage` 的 `RegisterRootControl(_controlPool, rootEntity, hostControl)` 仅执行 `_controlPool.Register(entity, host.Name, hostControl)`——把宿主控件塞进 `_nameToControl`，**从不把渲染根视图树物理 `Add` 到宿主控件 `Controls`**。真正决定物理父的是 `BuildChildRelation`(ECS 父子) → `WinFormApplier.ApplyRelations`(AddControl)，而该链以渲染根的父（=新建 root 面板）为准，宿主 `sideContainer` 从未被写入任何子控件（证据 6：children=0）。

**D3 · 两条宿主口径分裂**
- `validate` 走可见树递归（`_findOrdinaryControl`），不看 Registry/ControlPool → 可见即 PASS；
- `assert-container`/`validate-mount` 走 `ContainerRegistry` + `ControlPool.GetControl("sideContainer")` → 宿主空/映射被覆盖 → FAIL。
两条口径对同一容器相反结论，且 `ContainerRegistry.ToHandle` 依赖 `_nameToControl["sideContainer"]` 命中（受 D1 覆盖影响）。

**D4 · 结果契约 `Succeeded` 无法暴露“宿主空”**
`RenderRunResult.Succeeded = RenderExecuted && OrphanCount==0 && ControlsSkippedCount==0`，且 `MountedCount = ApplyResult.RelationsApplied`（关系 AddControl 数）。它**从不校验宿主控件实际子控件数/内容归属** → Side 渲染自判 `Succeeded=True, MountedCount=18` 而 `sideContainer.Controls.Count==0`。这是“日志全绿但宿主空”假绿的直接来源（与 P7 方案 §三 S2 判据一致，S6 回归即此 FAIL）。

**D5 · `EcsContainerCore`（每容器独立 composition）机制未接线**
`EcsContainerCore.LoadConfiguration` + `ContainerView.AttachCore`（容器自身作为 host 渲染内容）在运行路径无调用方，属死代码双轨。状态容器（sideContainer）内容实际全走全局 `EcsGate` composition，加剧 D1。

### 2.4 根因收敛

```
D3(口径分裂) 与 D4(假绿判据) —— 症状
   ↑ 源于
D1(每次新建同名 root + 全局共享 world) 与 D2(宿主注入不建物理挂载) —— 机理
   ↑ 共同指向一个架构决策缺陷
「内容渲染画到『全局 root 树』，宿主(sideContainer)只是注册了个名字，从未被真正当作渲染根承载子控件」
```

## 四、修复方案

> 原则：**最小改动、先堵假绿（D4）、再修根（D1/D2）、统一口径（D3）、清理死轨（D5）**。
> 每步交付后跑 `echo 9 | 交互启动.bat` 验证（命令 16/17 转 PASS），并跑既有 Math/Content 脚本防回归。

### S1 · 结果契约绑定真实挂载（堵假绿，D4）—— 先交付、收益明确

- **`RenderStageRunner.cs`** `BuildResult`：`Succeeded` 判据改为「渲染区间执行 且 宿主（若注入）真实收到子控件」，即显式 scope 渲染时增补 `hostControl.Controls.Count > 0`（或经 `ContainerRegistry` 解析宿主控件数）。无宿主（MainLayout 全量）保持原语义。
- **`ContainerProjector.cs`** `PublishLoadedAsync`：携带宿主实际子控件数（替代/追加 `result.MountedCount`）。
- **`ContainerCommandExecutor.cs`** `LoadToScopeAsync`：渲染后回填 `ContainerState`（`NodeCount = host.Control?.Controls.Count ?? 0`；`NodeCount==0` 时 `Status=Failed, LastError="宿主未收到子控件"`），以 `NodeCount>0` 作为 `result.Succeeded` 之外的**真判据**（触发 `ContainerCommandExecutor_Render_NotSucceeded`）。
- **`UIToolbox.cs`** `FireAndForgetLoadConfigAsync`：保留上一轮已生效的失败异常落盘（`UIToolbox_LoadConfigToScope_error`）；（可选）改由 `ILoadConfigPort` 返回真实布尔而非 fire-and-forget。
- **`fde_log_messages.json`**：`ContainerCommandExecutor_Render_NotSucceeded` 模板已存在，确认字段含 `nodeCount`。

**验证**：宿主空时 `Succeeded=false`、`NodeCount=0`、`Render_NotSucceeded` 出现 → 假绿消失。

### S2 · 作用域根命名隔离（根治 D1 同名 root 覆盖）

- **`ConfigDrivenControlFactory.cs`** `CreateRootEntity`/`ControlTypeComponent.Name`：根实体名由固定 `"root"` 改为 `$"root:{scope}"`（scope 唯一化），`ConvertView` 传入的父实体名同步消歧。
- **`Ports.cs`** `CreateControl`：以实体名注册，天然跟随新命名，杜绝 `_nameToControl["root"]` 跨 scope 覆盖。
- **`ControlPool.cs`**：配合 `RefactorPlan_ScopeIsolation_InternalStorage.md` 的 **S2（scope→Cell 分区）** 落地；本文件不改 ControlPool 签名，仅依赖命名唯一性兜底。
- 收敛点：`EcsInputPort.LoadConfig`、`ConfigDrivenControlFactory.Convert`。
- 验证：跨 scope 重复加载、两 scope 共存时 `_nameToControl` 无同名覆盖；`assert-container` 命中稳定。

### S3 · 宿主注入真正物理挂载（根治 D2 内容未入宿主）

- **`RenderStageRunner.cs`** `ExecuteRenderStage`（或 `EcsGate.DoLoadAndRender` 渲染后）：当 scope 有显式宿主（`ctx.RootContainer != null`）时，把该 scope 渲染根实体对应控件**物理 `Add` 进宿主 `Controls`**（`hostControl.Controls.Add(rootControl)`），确保 `sideContainer.Controls.Count>0`。
- **`RenderLoadStage.cs`** `RegisterRootControl`：保持“名字映射”外，补充“渲染完成后把根视图 Add 到 host”的空实现（由 S3 上面的注入点统一完成，避免双写）。
- 收敛点：`EcsGate.DoLoadAndRender`、`ContainerProjector.RenderOnUIThreadAsync`。
- 验证：`assert container sideContainer count>0` PASS 且 count 与 `layout report` 容器归属行一致；`validate-mount titleLabel parent=sideContainer` PASS。

### S4 · 统一宿主寻址口径（收敛 D3）

- **`ContainerRegistry.cs`** `ToHandle`：`_controlPool.GetControl(hostKey)` 未命中时，回退可见树解析宿主控件（消除 `handle.Control==null` → “未找到宿主”）。
- **`ContainerAssertionService.cs`**：`validate`（可见树）与 `assert-container`/`validate-mount`（Registry+池）共用同一“宿主控件解析”委托。
- 验证：`validate` 与容器断言不再分裂。

### S5 · 清理死轨（可选，D5）

- `EcsContainerCore`/`ContainerView` 这套“每容器独立 composition”机制若确认无调用方，文档标注“未接线/deprecated”，避免误接入成第三条轨。

## 五、实施顺序与风险

| 顺序 | 步骤 | 依赖 | 风险/注意 |
|------|------|------|-----------|
| 1 | S1（真实挂载判据） | 无 | 不改变挂载行为，仅暴露真相；**最先交付**呼应“失败不打日志” |

| 3 | S3（物理挂载入宿主） | S1、S2（否则仍会挂错） | 只对显式宿主 scope 生效，MainLayout 全量不受影响 |
| 4 | S4（口径统一） | 无，可与 1 并行 | 低风险 |
| 5 | S5（死轨清理） | 无 | 纯文档/标记，低优 |

> 必须 S1+S2 先行：S3 的物理挂载若在“同名 root 覆盖”未消除前实施，可能把内容挂到错误宿主/重复挂载。
