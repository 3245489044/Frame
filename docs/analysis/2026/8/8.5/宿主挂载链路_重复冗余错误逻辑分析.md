## 一、错误逻辑（需优先修复）

### E1 · `ControlPool` 跨 scope 同名控件覆盖（已修复，作为基准确认）
- **位置**：`CsharpPrj/BasicMethod/ECS/Bridge/ControlPool.cs`（`_nameToControl`）。
- **现象**：`GetControl(Entity)` 原实现经 `_entityToName[entity] → name → _nameToControl[name]`
  中转。多个 scope 存在同名普通控件（如 MainLayout 与 Side 都有 `MainView`）时，全局
  `_nameToControl[name]` 单槽被后注册者覆盖，导致 `GetControl(实体35)` 命中 MainLayout 的
  `MainView` 控件 → Side 内容被物理挂进 `root:MainLayout`，sideContainer 只剩空壳 `root:Side`
  （`validate-mount titleLabel parent=sideContainer` 因此 `未找到宿主`）。
- **定性**：历史 D1「同名 root 覆盖」的**泛化**（root 名已 scope 化，普通控件名未 scope 化）。
- **修复**：引入 `_entityToControl`（实体→控件直接映射），`GetControl(Entity)` 优先按实体返回
  专属控件，不再经 name 中转；`Unregister` 仅在名字槽仍指向本实体控件时才移除（避免误删同名
  字面另一实体映射）。
- **遗留**：`_nameToControl` 仍按名共享（脚本 `set/click/validate` 按名单查依赖它），名单查
  在跨 scope 同名校验场景仍可能命中"最后注册者"，需在命令层显式 `scope` 限定（见 R2）。

### E2 · `RenderMountStage` 依赖渲染区间不存在的 ctx 信号（已修复，作为回归教训）
- **位置**：`RenderPipelineStages.cs` → `RenderMountStage`。
- **现象**：最初守卫 `ctx.RootContainer != null && ctx.RootEntity.IsValid`，而
  `ExecuteRenderStage` 渲染区间 ctx 的 `RootContainer=null`、`RootEntity=default(0:0)` →
  挂载阶段每次被整体跳过，root 面板从未挂进宿主（无任何 `HostMountService_*` 挂载日志）。
- **教训**：管线阶段不应依赖"调用方在渲染区间填 ctx 挂载信号"，而应在阶段内部自洽解析
  （经 HostMountService 按 scope 解析宿主 + 按 `root:{scope}` 解析根）。当前已改为纯 scope 驱动。

### E3 · `ConfigDrivenControlFactory.CreateRootEntity` 自删 Pending 组件（疑似错误/脆弱点）
- **位置**：`ControlRender/Creation/ConfigDrivenControlFactory.cs` L73-74。
- **现象**：root 实体 `AddPendingComponents(rootEntity)` 后又立即
  `RemoveComponent<PendingCapabilityComponent>(rootEntity)`，导致 root 实体**不再经
  `EcsCapabilityApplier` 创建控件**。当前 root 控件依赖其他路径（`AttachRootToHost` 按名
  `root:{scope}` 解析）兜底才可命中。
- **风险**：这与"普通控件经 CapabilityApplier 创建 + Register(entity,name,control)"的机制
  不一致，是历史 `HostMountService_RootControlFallbackByName` 频繁出现（fallbackHit 分支）
  的直接来源——root 控件按实体未命中、总是退化为按名解析。
- **建议**：澄清 root 创建的唯一路径：要么移除该自删（让 root 也走 CapabilityApplier 统一建树），
  要么在文档/代码注释中显式声明"root 不建实体控件、仅靠宿主注入"，消除双轨歧义。

### E4 · `EcsCapabilityApplier.AddToParent` 期间父控件未就绪即静默 return
- **位置**：`Ports.cs` → `WinFormsOutputPort.AddToParent`（`if (parentControl == null) return;`）。
- **现象**：创建（Creation）阶段按无序遍历实体，子控件可能先于父控件创建/注册，此时
  `GetControl(parentEntity) == null` 静默 return，**不建立父链**。真正的父链依赖后续
  `WinFormApplier.ApplyRelations` 阶段再补。两阶段各持一套父子挂载，存在不一致风险
  （若任一阶段父控件解析失败，控件即"孤儿"——对象存在但未挂可见树）。
- **建议**：统一父子挂载到单一权威阶段（Apply 阶段），或 AddToParent 解析失败时入队列在
  父就绪后补建，避免"创建期静默丢边"。

## 二、重复逻辑（需合并）

### R1 · 宿主寻址"scope 优先 + hostKey 反查"三处重复（已收敛 2 处）
- **收敛前**：
  1. `HostMountService.ResolveHost`（手写 scope→hostKey 反查）
  2. `ContainerAccessPortAdapter.ResolveHostByKeyOrScope`（完全重复上一段反查）
  3. `ContainerProjector.ResolveScopeHost`（又一段 scope 解析）
- **现状**：统一收敛到 `ContainerRegistry.ResolveByScopeOrHostKey(scopeOrHostKey)` 单一实现；
  `HostMountService.ResolveHost` / `ContainerAccessPortAdapter.ResolveHostByKeyOrScope` 均改为转发
  （返回 `ContainerHandle` / `Control` 两个薄适配）。**R1 已基本闭环。**
- **遗留**：`ContainerProjector.ResolveScopeHost` 与 `HostMountService` 的 null 语义仍各持一份
  异常文案，可继续收敛（见 R3）。
### R2 · 控件查找 finder 族群并存（未收敛，重复最严重）
- **现状**：项目存在至少 6 个控件查找实现/接口：
  - `FrameworkAbstractions/Controls/WinFormsControlFinder.cs`（`FindControlByName` 用
    `Controls.Find(name, true)`）
  - `FrontEndDriven/WinForms/Finder/ControlFinder.cs`
  - `FrontEndDriven/WinForms/Adapter/ControlFinderAdapter.cs`
  - `EventBindingOrchestrator/ControlFinderWrapper.cs` + `Invoke/ControlTreeWalker.FindControl`
  - `Modules/EventFramework/.../ReflectionControlFinderStrategy.cs`
  - 多份命名不同的 `IControlFinder` 接口
      （`TConfig.Abstractions` / `FrameworkAbstractions.Controls` /
       `FrameworkAbstractions.WinFormsAbstractions` / `EventBindingOrchestrator.Abstractions`）
- **定性**：同名接口多份 + 实现多份，任一查找语义调整需多处同步（典型
  Anti-SingleImplementation 违规）。历史文档 `7/31 重复冗余错误逻辑分析报告` 已指出
  "适配器→适配器→适配器多层转发"。
- **建议**：以 `FrameworkAbstractions.WinFormsAbstractions.IControlFinder`（被
  `StateServiceCollection` 用做可见树兜底）为唯一面，其余实现收敛为适配或标记 deprecated；
  三者 finder 的递归深搜语义统一为 `Controls.Find(name, true)` 一处实现。

### R3 · 容器/挂载失败文案与判定分散
- **现状**：
  - `ContainerProjector.ResolveScopeHost` 手写 throw 文案；
  - `ContainerAssertionService` 内 `assert-container` / `validate-mount` / `validate` 三套
    失败 reason 文案各自拼装；
  - `ContainerCommandExecutor` 又独立判断 `HostActualChildCount>0` 并编文案。
- **定性**：同类"宿主未挂载 / 未找到宿主 / 宿主空"判定与文案分散，改一处易漏另处（文字漂移）。
- **建议**：把"宿主解析结果 + 挂载判定"收敛为一个返回强类型结果的容器服务原语
  （如 `ContainerResolution { Handle, Reason }`），命令层与断言共用同一文案源。

### R4 · Mounted 判定多处重复（已部分收敛，仍有重复）
- **现状**：`ContainerCommandExecutor`（`HostActualChildCount>0`）、`ContainerAssertionService`
  （`handle.IsMounted && _port.IsMounted`）、`EcsGate.DoLoadAndRender`（`mountVisible`）三处在
  "宿主是否真挂上"上用不同判据。
- **建议**：统一为 `HostMountService.IsMounted(scope)` 单一出口（已存在），三处改调；
  删除 `ContainerAssertionService.AssertMounted` 里的 `handle.IsMounted` 与 `_port.IsMounted`
  双重校验的冗余分支。

### R5 · 挂载阶段与结果回传对 `HostActualChildCount` 的重复计算
- **现状**：`RenderStageRunner.BuildResult` 与 `EcsGate.DoLoadAndRender` 各算一次
  `HostActualChildCount`（BuildResult 在挂载前算=0，EcsGate 挂载后重算覆盖）。
- **定性**：历史为暴露"宿主空"缺陷引入的补测逻辑，属过渡性重复，长期应仅在挂载后计算一次
  （或由 RenderMountStage 在挂载完成后回填单一真值）。

## 三、冗余逻辑（可删除/简化）

### D1 · `EcsGate.DoLoadAndRender` 删掉手调挂载后，`_hostMount` 双分支兜底残留
- 上一轮已删除"手写 `Controls.Add` 兜底"（`else` 分支），`_hostMount` 恒非空；但注释仍冗长，
  且 `GetDirectChildCount` / `SetMounted` 与 `ContainerProjector`/`HostMountService` 语义重叠。
  可精简方法体。

### D2 · `Register(entity, controlName)` 两参重载 / `_entityToName` + forward 双向映射并存
- `ControlPool` 同时维护 `_entityToName`（内存）、`_entityToControl`（内存）与
  `IStorageCell.MapForward`（持久双向映射）；同为"实体↔名/控件"关系，索引口径三套。可作为
  SingleImplementation 清理项评估（历史文档 `ControlPool.GetControl(Entity) 永远返回 null`
  即为旧两参重载长期无人调用所致）。

### D3 · 历史缺陷文档中的"待实施"项与当前代码的偏差
- `hostManager` 相关 `S1-S5`修复文档（8.4）标注"修复待实施"，但部分已实际落库（S2 root 命名、
  S4 统一寻址、S3 RenderMountStage）。需更新文档状态，避免"已实施却标待办"的冗余误导。
