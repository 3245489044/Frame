### 1.2 仍存在

**E-1 · 位置报告对子 scope 控件 ECS_MISMATCH 恒误报（诊断伪影）** 🔴 → ✅ 已修复（2026-08-06）
- **位置**：`ControlRender/Commands/LayoutInspectSystem.cs`（`layout positions` 命令）
- **现象**：Content scope 控件（ConfigSelectorView/configListView/titleLabel 等 11 个）ECS 坐标与物理坐标恒偏移 43（工具栏高度），全部 `← ECS_MISMATCH`。运行实证（08-06 修复后回归日志）。
- **机理**：ECS `ComputedLayoutComponent` 对子 scope 是 **scope 局部基准**（root:Content 内 0,0 起算），而物理对照用 `LayoutCoordinateResolver.ToFormRelativeAccurate`（**form 相对**）——两基准天然相差 root 在 form 中的偏移，非真实布局错误。注释"嵌套容器子控件修复后物理 form 位置 = ECS，不再误报"的预期未覆盖"嵌套 scope"场景。
- **影响**：`← ECS_MISMATCH` 缺陷信号被污染——真实 ECS 差异与 scope 偏移无法从日志区分（诊断可判定性受损）。
- **修复**：采纳"物理对照改用 scope 局部基准"——`ExecutePositions` 对子 scope 控件经 `ResolveScopeRootControl`（EntityQueryService.FindRoot → ControlPool.GetControl(entity)，兜底按 `root:{scope}` 名查，与 DestroyScopeEntities 同口径）解析 scope root 物理控件，物理坐标 = `ToFormRelativeAccurate(control) − ToFormRelativeAccurate(scopeRoot)`，与 ECS 同基准比对；根 scope/无 scope 控件偏移 (0,0) 行为不变；输出列标注基准来源，scope root 解析失败时显式标注 `root未解析,form基准` 防静默。验证：FrontEndDriven 编译 0 警告 0 错误；GUI 回归（layout_validation_test）待 GUI 会话确认。

**E-2 · `LayoutCoordinateResolverTests` 2 个存量失败（测试断言语义漂移）** 🔴 → ✅ 已修复（2026-08-06）
- **位置**：`CentralTest/.../FrontEndDriven.Tests/LayoutCoordinateResolverTests.cs`
- **现象**：`ToParentRelative_ContentSplitter_ReturnsRelativeToPanel1`、`ToParentRelative_TerminalPanel_ReturnsRelativeToPanel2` 恒失败（`git stash` 验证修改前后均失败，非本次改动引入）。
- **机理**：断言期望值手算错误——测试期望 `mainSplitter.Panel1.Location == (0,43)`，但 WinForms `SplitterPanel.Location` 平台语义恒为 (0,0)（由 SplitContainer 管理）；期望 `ToParentRelative(terminalPanel, 626, 43) == (0,43)` 但换算应得 (0,0)（Panel2 form=(626,43)）。**断言值与断言消息（"(0,0)"）自相矛盾**。
- **影响**：`ToParentRelative` 实现实为正确（运行日志物理位置 (626,43) 与换算一致），但 2 个失败测试长期存在 → "测试红着但没人修"的维护负债，且掩盖后续真实回归。
- **修复**：按正确语义修正两条断言期望值为 `(0,0)` 并同步修正注释手算（L68：`SplitterPanel.Location` 平台语义恒 (0,0)；L80-84：Panel2 form=(626,43) 与 ECS 输入差值 = (0,0)）。验证：`dotnet test FrontEndDriven.Tests` 18/18 全绿（此前 2 恒失败消除）。

**E-3 · `EventPlatform.InvokeFunction`（同步入口）sync-over-async 死锁风险（低）** ⚠️
- **位置**：`Lifecycle/EventPlatform.cs:195-201`
- **现象**：`InvokeFunction(...) => InvokeFunctionAsync(...).GetAwaiter().GetResult()`。内部 `ConfigureAwait(false)` 缓解了大部分死锁，但 UI 线程同步阻塞等待仍违背"UI 线程不阻塞"原则。
- **影响**：低（当前调用方均在合理时相调用）；属已知模式（BasicMethod 层同类广泛存在，`CellFramework`/`AsyncSyncOrchestrator`/`ElementCalculate_Script` 等）。
- **建议**：不单独立项；随 M4 生命周期收编时评估是否需异步化。

**D-4 · HostBasisSystem 基准决议时相（渲染前、宿主未挂载）** ⚠️
- **现状**：`RenderStageRunner.ExecuteRenderStage` 中 `ResolveBasis(scope)` 先于管线执行（`RenderStageRunner.cs:114-123`）；宿主 0x0 时回退父面板客户区（已缓解），但严格语义上"挂载后基准"（M4-1）更正确。
- **建议**：并入 D-1 的 M4 立项一并处理。
