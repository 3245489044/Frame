## 二、重构原则：聚拢点 → Pipeline 的收敛模型

### 2.1 核心认知：聚拢点 ≠ 手写循环

聚拢点是**职责收敛的边界**，Pipeline 是**边界内部的编排引擎**。二者是"对外契约"与"内部实现"的关系：

```
聚拢点（对外唯一入口/出口）
  └─ 内部 = Pipeline 编排（StaticPipeline / StagePipeline / 组合子）
       ├─ Step 输入（归一化/校验）      ← 输入聚拢
       ├─ Step 核心（业务处理）         ← 执行统一
       └─ Step 输出（审计/统计）        ← 输出聚拢
```

**判定原则**：凡聚拢点内部存在**手写顺序遍历、手工分支、手工错误收集**的，均应收敛为 Pipeline 的 `Step<TContext>` + `IsFatal` + `PipelineResult` 语义。

### 2.2 重构判定矩阵

| 调用环节 | 是否需聚拢 | Pipeline 承载方式 | 优先级 |
|---------|-----------|------------------|--------|
| 流程1 FunctionStorage 注册 | ❌ 保持（静态声明式注册表） | 无（注册本质非顺序流程） | — |
| 流程2 框架初始化 | 🟡 已由 InitializationOrchestrator 承载 | Pipeline.Initialization（现状保持） | 保持 |
| 流程3/4 渲染 | ✅ 三聚拢点已收敛 | StagePipeline`<RenderContext>` 统一双渲染 | 中 |
| 流程5 函数调用 | 🔴 **需收敛到 EventPlatform 唯一入口** | FunctionCallFacade 降为执行内核 + 组合子增强 | **高** |
| 流程6 命令执行 | 🟡 入口已收敛 | StaticPipeline`<CommandContext>` 编排 | **高** |
| WorkflowExecutionEngine | 🔴 需收敛 | StaticPipeline`<WorkflowContext>` 编排 | **高** |

### 2.3 与公理体系的对应

| 重构语义 | 对应公理/公式 |
|---------|--------------|
| Step 成功/失败判定 | `ExecutionStateTaxonomy`（status∈{success,failure}） |
| 步骤失败不中断（IsFatal=false） | `partial/continue` 语义（§6.1 OnError.shared-branch） |
| 步骤失败即中断（IsFatal=true） | `fail → TM/forcehalt`（TerminationPriority） |
| 管线级审计 | `FormatFidelity`/`StructuralGrounding`（输出结构对齐） |
| 聚拢点唯一入口 | `[AX-CORE] 聚拢点唯一入口原则` |
| 双渲染管线统一 | `AttentionWeighting`（scope 参数化，重算仅在轮次边界） |

### 阶段 A：WorkflowExecutionEngine → StaticPipeline（执行内核聚拢）🔵 已实施

> **实施状态**：✅ 已完成（2026-08-03）| 涉及文件：`WorkflowPipeline.cs`（新增）+ `WorkflowExecutionEngine.cs`（改造）| 编译通过

**现状**（`CsharpPrj/Operation/StateHoldDriven/WorkflowExecution/WorkflowExecutionEngine.cs:88-221`）：

- 手写 `for` 循环遍历 `def.Steps`
- 手写 `failedSteps` 收集、取消令牌逐步检查
- 手写输入 JSON 反序列化 / 输出 JSON 序列化
- 手写 `_stepSelector` 起点跳转

**聚拢点定位**：`WorkflowExecutionLayer.ExecuteWorkflow` 为唯一出口，内部 `ExecuteWorkflowCore` 收拢为管线。

**Pipeline 设计**：

```csharp
// WorkflowContext：管线共享上下文（体系 B 语义）
public sealed class WorkflowContext
{
    public Dictionary<string, object> Params { get; } = new();
    public List<Dictionary<string, object>> FailedSteps { get; } = new();
    public int StartIndex { get; set; }
    public CancellationToken CancellationToken { get; set; }
    public IWorkflowDefinition Definition { get; init; } = null!;
    public StepExecuteDelegate ExecuteFunc { get; init; } = null!;
}

public static class WorkflowPipelineFactory
{
    public static StaticPipeline<WorkflowContext> Create(IWorkflowDefinition def)
    {
        var steps = new List<Step<WorkflowContext>>
        {
            // Step 输入：JSON 参数解析 → context.Params
            new("DeserializeInput", ctx => DeserializeInput(ctx), IsFatal: false),

            // Step 核心：每个 IWorkflowStep 动态生成一个 Step
            //   - CanExecute 处理 _stepSelector 起点跳转（仅当 ctx 已越过起点才执行）
            //   - InputKeys → 从 context 取值 → executeFunc → OutputKey 回写
        };

        foreach (var ws in def.Steps)
        {
            steps.Add(new Step<WorkflowContext>(
                $"Execute_{ws.StepName}",
                ctx => ExecuteStep(ctx, ws),
                IsFatal: true, // 步骤失败即 Failed（映射 fail/parse_error 判定）
                CanExecute: ctx => ctx.SkipTo(ws.StepName)));
        }

        // Step 输出：OutputMapping + _failedSteps 组装
        steps.Add(new Step<WorkflowContext>("BuildOutput", BuildOutput, IsFatal: false));
        return new StaticPipeline<WorkflowContext>(steps);
    }

    private static void ExecuteStep(WorkflowContext ctx, IWorkflowStep ws)
    {
        ctx.CancellationToken.ThrowIfCancellationRequested();

        var stepArgs = new List<object>();
        foreach (var key in ws.InputKeys)
            if (ctx.Params.TryGetValue(key, out var val))
                stepArgs.Add(val);

        var result = ctx.ExecuteFunc(ws.FuncName, stepArgs.ToArray());

        if (result.IsSuccess)
        {
            if (!string.IsNullOrEmpty(ws.OutputKey) && result.Value != null)
                ctx.Params[ws.OutputKey] = result.Value;
        }
        else
        {
            ctx.FailedSteps.Add(new Dictionary<string, object>
            {
                ["stepName"] = ws.StepName,
                ["funcName"] = ws.FuncName,
                ["error"] = result.ErrorMessage ?? "未知错误"
            });
            // IsFatal=true → StaticPipeline 中断，PipelineResult.Failed
        }
    }
}
```

**迁移约束**：

- `ExecuteWorkflowCore` 公开签名**保持不变**，内部实现替换为 `StaticPipeline<WorkflowContext>` + `PipelineResult` 判定。
- `WorkflowExecutionLayer`/`WorkflowCommandCenter` 调用方零改动。
- `_stepSelector` 起点跳转：保留原生语义，通过 `CanExecute` 委托实现（`ctx.StartIndex` 之后的 Step 才执行），作为 `StaticPipeline` 不支持动态起点的边界适配。

**实施偏差记录（2026-08-03 复核）**：

- `IsFatal` 语义：文档设计 `IsFatal: true`（步骤失败即中断），实际 `WorkflowPipeline.cs` 采用 `IsFatal: false`（失败仅记录进 `FailedSteps` 不中断后续步骤）——**与重构前 `ExecuteStepsCore` 的 `failedSteps` 收集语义一致**，为实施的语义修正而非偏差遗漏，维持现状。
- 取消语义：原 `ThrowIfCancellationRequested` 保留为 `WorkflowContext.ThrowIfCancellationRequested` 委托，每步骤执行前调用，与重构前逐轮检查等价。

**验证断言**：

| 断言 | 现行为 | 重构后 |
|------|--------|--------|
| 工作流缓存 | count=15 | 不变 |
| 单步骤失败 | 记录 failedSteps 继续 | `IsFatal=true` 中断 + `PipelineResult.Failed`（等价） |
| 取消 | throw OperationCanceledException → `_cancelled` 输出 | `CanExecute` 检查 + 同输出 |
| 输出映射 | OutputMapping 组装 | BuildOutput Step 组装（一致） |

**对齐公理**：`ExecutionStateTaxonomy`（status∈{success,failure}） ↔ `PipelineResult`（Success/Failed/PartialSuccess）。

### 阶段 B：命令编排 → StaticPipeline（命令聚拢入口内核化）🔵 已实施

> **实施状态**：✅ 已完成（2026-08-03）| 涉及文件：`CommandPipeline.cs`（新增）+ `CommandCoordinator.cs`（改造）| 编译通过

**现状**（日志 `14:39:38.678` 起）：

- `CommandInputPort` 加载 73 条元命令 → `CommandExecutionService` 逐条 `FunctionCallFacade.ExecuteSyncRequest`
- 命令执行是**顺序 for 循环 + 手工判断 continue/halt**

**聚拢点定位**：`CommandInputPort.LoadScript / ExecuteAll / ExecuteNext` 为唯一加载口（`CommandECS重构方案` 愿景），内部逐条循环收敛为管线。

**Pipeline 设计**：

```csharp
public sealed class CommandContext
{
    public IReadOnlyList<MetaCommand> Commands { get; init; } = null!;
    public int CurrentIndex { get; set; }
    public bool StopRequested { get; set; }
}

public static class CommandPipelineFactory
{
    public static StaticPipeline<CommandContext> Create(IEnumerable<MetaCommand> commands)
    {
        var steps = commands.Select(cmd => new Step<CommandContext>(
            $"Command_{cmd.Name}",
            ctx => ExecuteCommand(ctx, cmd),
            IsFatal: cmd.IsCritical,               // Echo/加载 → false；执行/校验 → true
            CanExecute: ctx => !ctx.StopRequested  // halt/forcehalt → 后续步骤跳过
        )).ToList();

        return new StaticPipeline<CommandContext>(steps);
    }

    private static void ExecuteCommand(CommandContext ctx, MetaCommand cmd)
    {
        // 经 FunctionCallFacade.ExecuteSyncRequest 或（阶段C后）EventPlatform.InvokeFunctionAsync 执行
        var result = ExecuteCommandCore(cmd);
        if (!result.IsSuccess && cmd.IsCritical)
            ctx.StopRequested = true; // 触发后续 CanExecute=false → 中断语义
    }
}
```

**语义映射**：

| 现有命令语义 | StaticPipeline 映射 |
|-------------|---------------------|
| `continue` | `IsFatal=false` + 非致命失败仅记录 |
| `halt` | `IsFatal=true` → `PipelineResult.Failed` |
| `forcehalt` | `IsFatal=true` + `CanExecute` 后续全 false |
| `halt+persist` | onStepError 钩子内 `persist_reasoning`（公式 §七 ErrorHandler） |
| 无终止风险 | 管线天然有界（步骤数=命令数），对齐 `ANTI-NO-TERMINATION` |

**验证断言**：73 条元命令（`totalCommands=73`）执行顺序与结果一致；`ForceHalt` 语义正确；`CommandInputPort` 对外加载接口不变。

**实施偏差记录（2026-08-03 复核）**：

- 文档设计"每条命令一个 Step"，实际 `CommandPipeline.cs` 采用**单个序列 Step + 内部 for 循环**（注释说明：实体运行时才装载，编译期无法为每条命令生成独立 Step）——`StaticPipeline` 承载编排与中止（`CanExecute`→`StopRequested` 短路）语义，为运行时装载约束下的合理折中，维持现状。
- 每个 `MetaCommand` 的 `IsFatal`/`CanExecute` 映射不在 Step 粒度体现（文档预期逐命令映射），改由 `CommandSystemCoordinator.ProcessEntity` 内部失败标记 + `ctx.StopRequested` 局部短路承载，语义等价。

### 阶段 C：函数调用收敛到 EventPlatform 唯一入口（核心聚拢点重构）

**现状**（日志 `14:39:38.460~38.521`）：

- `FunctionCallFacade` 是静态门面，被**按钮反射 Delegate、exec 命令、生命周期钩子、EventPlatform** 多路直调
- 违反"聚拢点唯一入口原则"——`EventPlatform.InvokeFunctionAsync` 与 `FunctionCallFacade.ExecuteAsync` 功能重复（Fail-Fast + 路由 + 超时 + 审计收敛为一套）

**聚拢点定位**（落实 `事件池聚拢与结构化事件路由重构方案`）：

```
统一聚拢点 = EventPlatform.InvokeFunctionAsync
    ↓ 内部
FunctionCallFacade（降为执行内核，仅被 EventPlatform 调用）
    ↓
WorkflowMethodExecutionService → FunctionStorageRegistry → 函数委托
```

**Pipeline 设计**（FunctionCallFacade 内核增强为组合管线）：

```csharp
// FunctionCallFacade 内部：基础调用管线 + 组合子增强
var basePipeline = Create(
    "FunctionCall",
    (FunctionCallRequest req) => executionService.ExecuteFunctionAsync(req.FunctionName, req.Parameters ?? new()));

// 内核 = 基础管线 + 横切增强
var enhanced = basePipeline
    .WithTimeout(TimeSpan.FromMilliseconds(request.TimeoutMs > 0 ? request.TimeoutMs : 30_000))
    .WithLogging(msg => BackEndLog.Log("FunctionCallFacade_trace", new { message = msg }))
    .WithRetry(maxRetries: 判断 FirstCallTransient 适配, delayMs: 0);
    // WithCache 可预留给 RepeatedCallStable 语义
```

**横切映射**：

| 组合子 | 现有手写逻辑 | 语义来源 |
|--------|-------------|---------|
| `WithTimeout(30s)` | `ExecuteWithTimeout` + `Task.WhenAny` | Formula §5.2 超时熔断 |
| `WithLogging` | `ExecuteWithAudit`（entry/exit） | 审计日志 |
| `WithRetry` | `TransientRetryNoCost`（total=0→retry） | FirstCallTransient / RepeatedCallStable |
| `WithCache`（可选） | 无 | repeated-call 结果稳定化 |

**验证断言**：

- 全仓 grep：`FunctionCallFacade.ExecuteAsync/ExecuteSyncRequest` 调用点**仅存在于 `EventPlatform`**（或经其转发的 `CommandInputPort` 命令执行）
- 收敛度从"低（<50%）"提升到"完全收敛（100%）"
- 日志 `FunctionCallFacade_entry/exit`、`mode=Background`、超时告警行为不变

### 阶段 D：渲染三聚拢点 → StagePipeline 统一（双渲染管线收敛）

**现状**（日志 `14:39:37.965` / `14:39:38.400`）：

- MainLayout 与 ConfigSelector 两条渲染管线**手动重复**四步：`EcsInputPort → CsgEntryPoint → WinFormsOutputPort → EventBindingSystem`
- 差异仅：scope 名、rootEntityId（1 / 23）、控件数（18 / 29）、事件数（6 / 2）
- 日志 `SyncActualContainerSizes` 告警为审计步骤，当前散落在管线尾部

**聚拢点定位**：维持三聚拢点不变，将两条渲染管线统一为**同一 StagePipeline 实例**（scope 参数化）。

**Pipeline 设计**：

```csharp
public sealed class RenderContext
{
    public string Scope { get; init; } = null!;       // "MainLayout" / "Content"
    public bool HasRootContainer { get; init; }
    public int RootEntityId { get; set; }
    public int CollectedCount { get; set; }
    public int AppliedCount { get; set; }
    public int BoundCount { get; set; }
}

public sealed class RenderPipeline : StagePipeline<RenderContext>
{
    public RenderPipeline()
        : base("RenderPipeline")
    {
        Register(new RenderLoadStage());      // EcsInputPort.LoadConfig
        Register(new RenderCollectStage());   // CsgEntryPoint.Collect（WinFormSnapshot）
        Register(new RenderApplyStage());     // WinFormsOutputPort.Apply（WinFormApplier）
        Register(new RenderAuditStage());     // SyncActualContainerSizes（ExternalConsistency 审计，OnAfterStep）
        Register(new RenderBindStage());      // EventBindingSystem（聚拢点 ①输入Gate→②执行→③输出Gate）
    }
}
```

**收益**：

| 现状 | 重构后 |
|------|--------|
| 两条渲染管线手动重复 | 同一 `RenderPipeline` 实例，scope 参数化 |
| `collectedCount=0`（MainLayout 首次）异常静默 | `ConditionalPipeline` / `PipelineTryCatch` 显式降级 |
| `SyncActualContainerSizes` 告警散落 | `RenderAuditStage` 统一审计（对齐 `RenderAuditPort` 聚合点） |
| 事件绑定三聚拢点与渲染管线脱节 | `RenderBindStage` 内嵌输入/执行/输出三聚拢点 |

**验证断言**：

| 断言 | 重构前（日志） | 重构后 |
|------|---------------|--------|
| MainLayout 控件/关系 | controlCount=18, relationCount=17 | 一致 |
| Content 控件/关系 | controlCount=29, relationCount=27 | 一致 |
| 事件绑定 | boundCount=6（MainLayout）+ 2（Content） | 一致 |
| 容器尺寸告警 | entityId=1, ecsWidth=1200 vs actual 1384 | `RenderAuditStage` 输出一致 |

### 4.1 各聚拢点收敛度目标

| 聚拢点 | 重构前收敛度 | 重构后目标 | 度量方式 |

## 五、实施顺序与依赖

```
阶段 B（命令管线化）        ← 低风险、无跨层依赖、投资回报最高
   ↓
阶段 A（工作流引擎管线化）  ← 依赖 StaticPipeline 模式成熟
   ↓
阶段 C（函数调用唯一入口）  ← 依赖阶段 A/B 的执行内核稳定（收敛后再统一入口）
   ↓
阶段 D（渲染统一管线）      ← 影响面最大（UI 回归），最后做
```

**依赖说明**：

- 阶段 B 为阶段 C 的前置：命令执行是 `FunctionCallFacade` 的主要调用方之一，先管线化命令层，再收敛函数入口，可降低阶段 C 的回归面。
- 阶段 A 为独立重构，可与 B 并行。
- 阶段 D 依赖前三阶段稳定后，统一 `EventPlatform` 作为渲染完成后的函数执行出口。

**每阶段独立可验证**：以日志关键断言为准（`count=15` / `controlCount=18,29` / `boundCount=6,2` / `totalCommands=73`）。

## 六、风险与回滚

### 6.1 风险登记

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 阶段 A：`_stepSelector` 动态起点丢失 | 中 | `CanExecute` 委托保留语义；单元测试覆盖 `_stepSelector` 场景 |
| 阶段 B：命令 halt 语义偏差 | 中 | `IsFatal` + `CanExecute` 组合严格映射；对比测试 73 命令序列 |
| 阶段 C：收敛后调用路径变更引发时序问题 | 高 | 保持 `FunctionCallFacade` 全部日志 msgId 不变；逐步迁移调用方（先 exec 命令，再按钮，最后钩子） |
| 阶段 D：渲染结果回归 | 高 | 管线各 Stage 保留三聚拢点原实现；以日志断言做回归基线 |

### 6.2 回滚策略

- 每阶段以"对外签名不变 + 内部实现替换"为原则，单阶段独立可回滚。
- 保留原实现（`WorkflowExecutionEngine` / `CommandInputPort` / `FunctionCallFacade`）源码直至新实现稳定运行 N 个周期，再置 `[Obsolete]`——遵循聚合架构"提取 → 迁移 → 废弃 → 删除"四步法。
