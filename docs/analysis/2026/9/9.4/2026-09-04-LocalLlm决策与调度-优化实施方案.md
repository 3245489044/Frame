## 〇、TL;DR

- **两条收敛主线**取代上一轮 R1–R7 的"逐缺陷补丁"：
  1. **工具调用做内/外二分**：外部能力一律经 **MCP**（`MCPBridge`）、内部能力一律**直接走工作流/节点执行**（`NodeExecutor + WorkflowContext`，复用 `WorkFlowMethod` RGE 内核）；二者统一建模为 `LlmTool`，经**装配期校验的单一工具注册表**收敛，消灭"手工塞 tools / 同名 answer 能力漂移"。
  2. **规则框架 × 决策引擎通用架构下沉 `LoopFoldMethod`**：把散在 `Agent.Contract/Llm` 与 `Agent.Core/Loops` 的"规则→决策→动作"消费逻辑抽成通用能力；Agent 只留薄适配层，规则文件为唯一真源。
- 端点命题：**LLM 决策不再"产出文本命中→预置工具注入"**，而是"规则/LLM 决策→产出结构化意图（`DecisionOutcome.Next(D′)`）→决策引擎映射到工作流节点→统一执行",执行失败必须可见归因。

## 一、两条主线与实现红线

| # | 红线 | 说明 |
|---|------|------|
| L1 | **内/外工具二分显式契约** | 外部=跨进程/跨网（文件系统、终端、代码库、web、外部服务）→`MCPBridge`；内部=平台自身能力（建任务/写图/查询/决策函数）→工作流节点。二者都是 `LlmTool`，只差 `ExecuteAsync` 的路由（内部进程内直调度 / 外部 MCP invoke） |
| L2 | **工具可用性单一注册、装配期校验** | 禁止在调用点手工拼 tools；`ToolRegistry` 声明即校验（名/参数 schema/路由存在性），缺失即显式告警，不回退 |
| L3 | **规则框架 + 决策引擎唯一权威在 `LoopFoldMethod`** | 通用规则模型 / 求值 / 决策引擎宿主下沉；`Strategy.DecisionRules` 作为模型源可被抽入或保持、但**消费决策语义只此一处**（防双份，对齐 StateHoldDriven R7） |
| L4 | **决策→执行不可静默回退** | 规则排除 / 工具缺失 / 导演解析失败的每次降级必须产出可观测归因（结构化 `DecisionRecord` + 告警），与脚本断言闭环 |
| L5 | **会话唯一执行内核（折叠）** | 消除"折叠 / 骨架 / WorkflowRunner"多内核并存的选路不确定性；answer 能力=装配契约而非组合偶然 |

## 二、主线 A：工具调用的内/外二分（化解缺陷 1/3/4/5/6/8）

### 2.1 问题还原（一段即可）

上一轮根因：`LocalLlmRule.Mode=tool_call` 由 `ToolName + ToolArguments` 组成，参数**静态预置**（`agent-config.json:33` 硬编码 `tp_llm_mcp_demo` 完整请求），触发退化为"一段子串是否命中 `regex`"（`local-llm.rules.json:22`）。工具与参数完全不由模型/规则决策产出；可用性跨 3 层手工透传，同名 answer 能力随装配漂移。

### 2.2 目标：统一 `LlmTool` 契约上的内/外路由二分

不新增第三套工具抽象。保留 `LlmTool(Name, Description, ExecuteAsync, InputSchema)` 作为**唯一工具契约**，在 `InputSchema`/元数据上标注来源域，`ExecuteAsync` 内部分派：

```
LlmTool
├─ kind = internal    │ 内部能力 → ExecuteAsync = 工作流节点执行（NodeExecutor + WorkflowContext）
│                     │   · int 目标注册为工作流定义（WorkflowMethodExecutionService，RGE 内核）
│                     │   · 入参 = 决策引擎产出的意图参数 JSON；返回 = 结构化结果/决策词
│                     │   · 令牌/上下文经 FunctionContext 通道（对齐项目硬约束）
└─ kind = external    │ 外部能力 → ExecuteAsync = MCP invoke（MCPBridge）
                      │   · 经 MCP 桥把工具名 + 参数 JSON 发往外部
                      │   · 失败/超时返回结构错误（不抛、不外溢）
```

- **触发不再依赖文本指纹**：decision 引擎产出结构化意图 `{intent/target_workflow, params}`（可来自规则或 LLM），再映射到 `LlmTool.Name`。规则命中但对应工具未注册 → **显式告警**，绝不再 `excluded→continue` 静默回退（修缺陷 1/3/4）。
- **`create_node_reference` 类内部能力**降级为普通内部工具：不再在规则里预置整包 JSON 参数，而是由规则/决策产出"意图 + 必要字段"，工具执行层落在工作流节点（走 `TaskGraphService` 原子写图，含既有 Path B fallback，不触网）。

### 2.3 主要构件（落地于 `LoopFoldMethod` + Agent 薄适配）

| 构件 | 承载 | 职责 |
|------|------|------|
| `ToolRegistry` | `Operation.LoopFoldMethod.Tool`（通用） | 声明即校验：工具名 / 参数 schema / 路由存在性（内/外）在装配期对准，缺失即告警 |
| `NodeToolBridge ↔ LlmTool` | Agent 适配层 | 内部工具→工作流节点（NodeExecutor/WorkflowContext）；外部工具→MCPBridge |
| `ToolExecution` | 通用 | 单一执行 / 去重 / 回喂实现（承接 `LlmToolExecutor` 收敛，修缺陷 8） |
| 声明式配置 | `rules/*.rules.json` | 工具只声明 `{name, description, inputSchema}`，不再夹带预置参数 |

> 装配期校验准则（对齐 `TryRegister*` 反射模式）：工具注册经 `TryRegisterTool` 接口，单模块缺失不崩、告警即 fail-fast 于调测脚本。

## 三、主线 B：规则框架 × 决策引擎通用架构下沉 `LoopFoldMethod`（化解缺陷 2/7/9 + 承接 StateHoldDriven R9）

### 3.1 三层归属（复用 StateHoldDriven 的分层哲学）

| 承载对象 | 放哪层 | 依据 |
|---------|--------|------|
| 规则**模型 / 匹配策略 / 输出形态**（`RuleSet/DecisionRule/MatchClause/OutputClause/MatchStrategy`） | `Strategy.DecisionRules`（保持，既通用且无 Agent 依赖） | 顶层通用，已无环 |
| 规则**求值 + 决策→动作映射**（`RuleEngine` 语义、决策词→`FoldDecision`、`tool_call → LlmTool` 映射） | **`Operation.LoopFoldMethod`（新增 `Rule/` 子目录）** | 通用架构目标；`Agent.Core/Loops/{RuleDecisionEvaluator, RuleMatchFunction, DecisionPoint}` 的消费逻辑收进此处 |
| 决策引擎（确定性终止 + 规则/LLM skill + 动作产出） | **`Operation.LoopFoldMethod/Decision`（既有，扩展）** | `DecisionFoldEngine` 已承载决策折叠；扩展"决策产物绑定动作/工具意图" |
| 应用适配（`LocalLlmClient` / answer / 导演 / 骨架） | `Projects/Agent`（薄，只消费上述） | 上层依赖下层单向，防环 |

### 3.2 规则框架（`LoopFoldMethod.Rule/` 目标形态）

- 把 "规则命中 → 决策信号" 收敛为通用 `IRuleDecider<TState, TVertex>`（LLM-free）：
  - 输入：状态 + 驱动信号 + 折叠上下文；
  - 求值：复用 `Strategy.DecisionRules.DecisionRulesEngine` 语义（规则文件为唯一真源，R2）；
  - 产出：`DecisionOutcome` —— `Next`（软推进，绑定 `FoldDecision.Continue`/动作意图）或 `Terminate`（`stop/error`）。
- 规则**求值对象去 Agent 化**：`RuleMatchFunction`/`RuleDecisionEvaluator` 依赖的 `DecisionWordClassifier`（Agent.Operation 词表）经 P3 前置剥离 `Operation.LoopFoldMethod.FoldDecision` 依赖后，词表唯一映射落到低层，Agent 只留薄 Adapter（对齐 StateHoldDriven R9）。
- **配置真源收敛（R2）**：删除 `agent-config.json:30` 内联 `Rules` 重复条目（`LocalLlmRule` 已 `[Obsolete]`），`RulesFile` 唯一生效；`rules.schema.json` 的 `tool_calls/structured/delegate` 与执行能力对其（schema 不再超前执行层）。

### 3.3 决策引擎（`LoopFoldMethod/Decision` 扩展）

- 现有 `DecisionFoldEngine(RunAsync)` 已是"确定性终止（`IDeterministicTermination`）+ LLM skill（`IDecisionSkill`）"双路折叠。**让规则决策器成为 `IDecisionSkill` 的确定性实现**（LLM 用户侧可替换成真 LLM skill，LocalLlm 侧替换成规则决策器），从而"规则 / 文本 / JSON 调度"共用同一决策折叠内核（化解缺陷 9 的多导演 / 多格式）。
- 决策产物从"纯折叠链标识符 D′"扩展为携带**动作意图** `DecisionOutcome.Next(D′)` + `Action{session,kind,params}`：`kind ∈ {continue|stop|error|tool_call|schedule}`，`tool_call` 经 `ToolRegistry` 校验后才产出（缺工具=中止动作 + 告警，修缺陷 4/7）。
- fail-safe 显式化（缺陷 7）：`DecisionOutcome` 增加 `Abort(reason, context)` 结果域，喂给既有审计（`LocalLlmCallRecord` / `DecisionRecord`），降级不再等价成功。

## 五、验收与回归判据

- **架构判据**：
  - 工具可用性无一处"调用点手工塞 tools"（grep 置零），均出自 `ToolRegistry`；`LlmTool.ExecuteAsync` 路由只分 internal/external 两分支。
  - 规则消费决策语义（`DecisionRulesEngine` 求值 → `DecisionOutcome` 映射）仅 `LoopFoldMethod/Rule` 一处；`Agent.Core/Loops` 不再独立实现规则求值。
  - `DecisionWordClassifier` 词表全库唯一（无第二套）。
- **行为判据**：`tp_llm_mcp_demo` 决策 Success 且必有可见工具执行记录或 `Abort(缺工具)`，二者必居其一——再无可复现的"Success 却无工具落库"假阳性。
- **单测判据**：`Agent.Core.Tests` / `DecisionRules` / `LoopFoldMethod` / `HybridSchedulerCheck` 全绿；新增"内/外路由二分"、"未注册工具装配期告警"、"缺工具→Abort 而非静默回退"、"同名 answer 两条路径能力等价"用例。

## 六、风险与开放问题
