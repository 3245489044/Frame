# 从 LocalLLM 到决策与调度的架构缺陷分析

> **状态**：分析（纯静态，未改代码） | **日期**：2026-09-04
> **关联**：`2026-09-04-AgentPathA-create_node_reference-激活根因分析.md`（Path A 单点根因）· `agent_mcpinvoke_create_task_test.json`（脚本 10）
> **范围**：`Agent.Contract/Llm`（LocalLlmClient / LlmToolExecutor / LocalLlmRule）· `Agent.State`（LlmRoutingClient / LlmMode / LlmGateway）·
> `Agent.Modules/LocalLlmHttp` · `Agent.Axioms/Scheduling`（LlmStateDirector / ConfigStateDirector）·
> `Agent.Core/Signal`（SkConversationFoldOperator）· `Agent.Modules/Answer`（StatelessAnswerExecutor / AnswerWorkflowFunction）·
> 配置（`agent-config.json` / `rules/*.rules.json`）· 执行端（TaskGraphService / ConversationHosting）
> **触发**：Path A 任务 `tp_llm_mcp_demo` 在会话折叠链路中未被创建（LocalLlm 决策 Success 却无工具落库），经排查确认单点修复只能救当例，
> 故对整条 "LocalLLM → 决策 → 调度" 链做结构缺陷梳理，为重构提供依据。

---

## 〇、结论

链路每一层都有合理的收敛意图（统一网关 `LlmGateway.Current`、SingleImplementation、规则文件优先），但存在**三类系统性断点**，
使 "LLM 决策 → 工具执行 → 任务调度" 的组合不可靠：

1. **工具调用是「文本指纹触发的预置注入」而非真 function-calling** —— 触发条件（一段子串是否出现在某个特定 user 槽位）脆弱且不可组合；
2. **同一概念（answer / 规则 / 决策 / 工具可用性）存在多套分裂实现与重复配置** —— 能力随装配漂移，无单源真值；
3. **决策 / 执行的失败被「静默回退」吞掉** —— fail-safe 被当成功，产生"决策 Success 但任务未建"的假阳性。

## 二、架构缺陷清单

### 缺陷 1【高危】`tool_call` 是"子串→预置工具调用"的注入，非工具决策
- **证据**：`LocalLlmRule.Mode=tool_call` 由 `ToolName` + `ToolArguments` 组成，参数为**静态预置**（`agent-config.json:33` 硬编码 `tp_llm_mcp_demo` 完整 CreateTaskGraphRequest）。工具与参数完全不由模型产出。
- **后果**：模型无工具决策能力；触发退化为"一段文本是否命中 `regex:LLM_MCP_DEMO|请用create_node_reference创建任务`"（`local-llm.rules.json:22`）。触发词一旦被会话分步 / 投影移出被匹配的 user 槽位即静默不命中。本次 `tp_llm_mcp_demo` 未创建即此形态。能力本质是 mock，却被当"真实 Function Calling 端到端"验收。

### 缺陷 2【高危】规则配置双轨真源分裂（SingleImplementation 违反）
- **证据**：`agent-config.json LocalLlm` 同时含 `RulesFile:"rules/local-llm.rules.json"`（优先）与 `Rules:[…]`（标 `[Obsolete] 兼容降级`，`LocalLlmRule.cs:11`），且两处逐条重复 r-intro / r-schedule / r-create-task。`LocalLlmClient.ResolveRuleSets`(L228-237) 优先 RulesFile → **内联 Rules 形同虚设却仍在配置中**。
- **后果**：规则真源分裂，改一处另一处误导；Schema 新增能力（tool_calls / structured / delegate，`rules.schema.json:62`）与 LocalLlm 消费能力不完全对齐，扩展在 schema 层超前于执行层。

### 缺陷 3【高危】"喂给规则引擎的 user"经多层投影漂移，匹配不稳定
- **证据**：进程内调用经 `LlmRoutingClient._local`（OpenAI 兼容 client → 8787）→ `LocalLlmHttpHost.BackendAsync` 收到消息后**再 `ConversationLlmProjector.Partition` 一次**（`LocalLlmHttpHost.cs:78`）抽 system/user/history 才送规则引擎。
- **后果**：规则 `Match` 作用的是**服务端再分区的 user**，与调用方（SkConversationFoldOperator 折叠 step 拼的 `[步骤 …] Payload`）可能不一致；同一段语义在调用方 / 传输 / 服务端三重投影中槽位漂移，`r-create-task` 对哪段文本匹配不可预测，且无日志可查。

### 缺陷 4【高危】工具"可用性"跨 3 层手工透传，任一层丢名即静默失效
- **证据**：`LlmRoutingClient.ChatWithToolsAsync`(L190) 把 tools 交给 `_local`；HTTP 传输把 **tool 名**发服务端；`LocalLlmHttpHost.BuildPlaceholderTools`(L83) 造**空 executor 占位**；`LocalLlmClient`(L196-221) 中 `!ToolProvided(name, tools)` 时把该规则 `excluded` 后 `continue`，静默回退文本。
- **后果**：工具可用性判定散布 3 层、靠手工把工具名塞进各调用点 tools。create 工具在折叠 `ChatStepAsync` 有（`hasCreate=true`）但在别处没有 → 行为随装配漂移，且失败无任何提示（无 toolExec 日志、无错误）。单源工具注册 / 校验缺失。

### 缺陷 5【中危】同名 "answer" 两个执行器能力不一致（TH-12 运行时背离）
- **证据**：`AnswerWorkflowFunction.SharedAnswer = new StatelessAnswerExecutor(LlmGateway.Current)`（**无** extraTools，纯聊天）vs ConversationHosting 折叠 `AnswerFoldExecutor(new StatelessAnswerExecutor(llm, extraToolsProvider: …create))`（**有** create，`ConversationHosting.cs:218-223`）。
- **后果**：同一个"answer 步"，走哪个内核 / 哪个组合根就决定它能否工具调用。能力不是类型契约而是**装配偶然**，是"会不会创建任务"的不稳定根因之一。

### 缺陷 6【中危】两套执行内核并存，内核选择决定能力面
- **证据**：任务消费走 `agent-round` 骨架（guard_input / provide_prompt / cline_execute / rule_match，TaskPool 驱动）；会话走折叠 `SkConversationFoldOperator`；默认 GUI 又曾用 `WorkflowRunner`（`EndToEndConversationLocalTests` 注"与 GUI 一致"），而 ConversationHosting 又注入 fold runnerFactory。
- **后果**：会话语义路径存在多内核候选，`create` 工具 / 决策触发是否有效取决于到底哪套在跑，长期并存、文档自认双内核。工具暴露与规则触发强耦合于"选中哪个内核 + 该内核如何拼 user/tools"。

### 缺陷 7【高危】fail-safe 静默成"成功"：决策/执行失败不可观测，假阳性
- **证据**：`LlmStateDirector`(L58-63) LLM 不可用 / 解析失败 / 空响应 → `null(stay)`；日志实见"LLM 状态导演决策解析失败（空响应或无法解析）"仍 `decision=Success, 轮次=1`。`LocalLlmClient` 规则排除 / 回退全程无错误。
- **后果**：核心决策失败被吞成 continue/success，叠加"answer 决策 Success"让**执行没发生也显示绿**——正是脚本 V1 断言要防的假阳性，架构上却系统性支持了它。

### 缺陷 8【中危】工具执行模型三套并存、逻辑分散
- **证据**：进程内 `LlmToolExecutor.ExecuteToolCallsAsync`（LlmToolExecutor.cs）与 LocalLlmClient 内嵌的"去重/排除"多轮循环(L194-224)及 HTTP wire 的 tools 往返各自实现一套执行/去重语义，`excluded` 隐式状态埋在规则引擎。
- **后果**：同一"返回工具调用 → 执行 → 喂回"在多处用不同规则实现，易出现"进程内一致、wire 不一致"的分叉（TH-3 确定性前提被稀释）。

### 缺陷 9【低中危】调度导演语义与文本规则引擎语义超载
- **证据**：`SchedulingMode{Hybrid=LLM导演, Config=ur_config, Deterministic=纯规则}` 三导演并存；而 LocalLlm 的 `r-schedule`(json) 与 `ConfigStateDirector`(ur_config) 是两套 JSON 决策源，`DecisionRulesEngine` 同一引擎同时服务"文本回答 / 调度 JSON / 工具调用"。LLM 导演 JSON 的 `action` 词汇与 TaskPool 调度导演 action 重叠但来源不同。
- **后果**：决策语义多入口、多格式，职责边界靠各导演自约束 + `TransitionGuard` 事后守卫，缺统一的决策请求 / 裁决契约。

---

## 三、叠回本次缺陷（因果链）

`tp_llm_mcp_demo` 不创建的完整因果链 =
**缺陷 1 + 3**（user 槽位漂移 → 规则未命中） × **缺陷 4 / 5 / 6**（create 工具在所选内核 / 执行器是否可用不确定） × **缺陷 7**（未命中被静默回退，仍判 Success）。
单点补丁只能救当前用例，改不了这三类结构性脆弱。

## 四、修复方向建议（架构级，供后续规划）

| # | 缺陷 | 方向建议 |
|---|---|---|
| R1 | 1/3/4 | 把工具调用从"子串注入"升级为真契约：`tool_call` 规则以结构化意图（如 role / 工具名 / 槽位显式绑定）触发；规则命中但无对应可用工具时**显式告警**而非静默 `excluded` |
| R2 | 2 | 删除 agent-config 内联 `Rules` 与重复条目，`RulesFile` 为唯一真源，schema 与执行能力对齐 |
| R3 | 4/5 | 把 create / 本地工具集可用性从"各调用点手工塞 tools"收敛为统一声明 + 装配期校验，消除同名 answer 能力漂移 |
| R4 | 6 | 明确会话唯一执行内核（折叠 or 骨架），消除双内核选择不确定性 |
| R5 | 7 | `LocalLlmClient` 规则排除 / 回退、`LlmStateDirector` 解析失败须产生可见归因（非静默 stay/continue），与脚本断言闭环 |
| R6 | 8 | 收敛"返回工具调用 → 执行 → 喂回"为单一执行/去重实现，消除 wire/进程内分叉 |
| R7 | 9 | 收敛调度决策为统一请求 / 裁决契约，导演仅作来源，守卫/施加集中 |

> 备注：本文档为纯分析产物；涉及的具体落地（R1-R7）可按项拆分为独立重构方案与实施步骤。
