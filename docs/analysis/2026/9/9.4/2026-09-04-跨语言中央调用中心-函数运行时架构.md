# 跨语言中央调用中心 —— CSG 驱动的语言无关工具调用平台

> 理念：把"全量 MCP 化 LLM 调用"升维为**集成的跨语言函数运行时**，并用 **CSG 协议（Configuration–StateMachine–Graph 统一中间表示）**
> 作为 **语言无关的数据面**，构建一个类似**中转站**的中央调用中心（CallCenter / 工具调用平台）。
> 统一整合 C#、TypeScript、PowerShell、外部 MCP 的调用（LLM 调用属 Agent 侧、收拢于 Agent 内单点，D7），采取**热加载 + 编译缓存多轨制**，最终以**统一的 MCP 工具面**暴露给上层。
> CSG 只定义数据，CallCenter 只解释数据 —— **任何语言只要能读写 CSG CanonicalForm，就能接入平台**。

---

## §〇 TL;DR

- **为什么**：C#（FunctionLibraryLoader + FileDriven.Business）、TS（MCPBridge）、PowerShell、外部 MCP 是多套平行机制，各管线缆格式、调用协议、加载缓存，缺一个**语言无关**的中枢；LLM 调用属 Agent 侧，收拢于 Agent 内单点（不进中枢）。
- **用什么**：用 **CSG 协议**（已是 C# 标准文档 + TS 运行时实现）作为数据面：把**工具、调用请求/响应、执行状态、调用流图**全部建模为 CSG CanonicalForm（节点-边图）。中枢**只操作 CanonicalForm**，彻底与语言解耦。
- **做什么**：建一个 **CSG 工具调用平台（CallCenter）** = 数据面(CSG) + 控制面(路由/缓存/可观测) + 终端面(各语言 Adapter = CSG↔native 变换器)；LLM 门控留 Agent 收拢点。
- **怎么落**：P0 确立 CSG 数据面/路由表 → P1 收敛 Agent 工具面（外部 MCP + 确定性工具入 CallCenter）→ P2 FileDriven 接入 → P3 TS/PS 接入 → P4 编译缓存多轨 + 热加载版本切换。LLM 不入中枢，在 Agent 内收拢。

## §二 设计理念

1. **CSG 是数据面，不是另一种语言**：CSG 定位即"统一中间表示、语言/传输/运行时中立"。工具调用平台把**工具契约、调用、状态、编排**都落到 CSG CanonicalForm，天然语言无关。
2. **工具调用 = CSG 图**：一次调用 = 构建一张"调用子图"（节点=工具/参数/结果，边=数据依赖/调用序，metadata=工具 schema，state=调用态）。CSG 三投影正好覆盖平台三需求：Configuration(契约/配置)、StateMachine(调用生命周期/多轨状态)、Graph(依赖/编排拓扑)。
3. **中枢只懂 CanonicalForm**：控制面（路由/缓存/可观测）只读 CanonicalForm，不出现任何语言类型；**语言能力全部在终端面 Adapter**，Adapter = 实现 CSG 操作规范（C↔IR / S↔IR / G↔IR 变换）的**变换器**。
4. **LLM 收拢于 Agent**：LLM 调用属 Agent 侧功能，收拢于 `LlmRoutingClient`/`GlobalLlmGate`/`LlmMode` 单点，**不进 CallCenter**；`guard_input`/`answer`/`cline` 等 LLM 驱动或控制端随 LLM 同侧保留（D7，框架直用位）。
5. **多轨 + 热加载**：同名多实现/多版本在 CSG 图上以 metadata(fingerprint/version) 区分并存；fingerprint 变 → 重构该工具子图 → 版本切换。
6. **跨平台**：平台与语言无关，只依赖能读写 CSG JSON 的终端；各轨用自身 runtime（C# 进程内 / Node / pwsh）。
7. **内部工具双态（调用链不同环节）**：同一内部工具既可在框架内部**直用**，也可**注册进 CallCenter 包装**为统一工具面；二者不冲突，是调用链的不同环节（见下）。

### 内部工具与 CallCenter：调用链的两个环节

- **调用链四环节**：`能力实现`（叶子，单一来源）→ `框架直用`（进程内直接调用实现）→ `CallCenter 注册`（登记进 CsgToolCatalog，生成 CSG 描述符 / Adapter 包装）→ `跨边界调用面`（LLM Function calling / 工作流 / 其他语言经 Router→Adapter 按名调用）。
- **双态不冲突**：同一工具可同时处于"框架直用"与"CallCenter 包装"两个位置 —— 直用不经过 CallCenter，包装则经 `Router→Adapter` 到达**同一份实现**。是否注册取决于是否需要**跨边界可寻址**（被模型/工作流/异语言按名调用）；不注册则仅框架内部可见。
- **单一实现原则**：无论直用还是包装，底层都是同一份能力实现（C# 函数 / TS 工具 / PS 脚本 / Agent 执行端）；CallCenter 的 Adapter 只是变换器，不复制实现。框架直用（如折叠算子直调 guard/answer/cline）与 CallCenter 包装（如 `McpServerTools` 已暴露 answer/cline 为 MCP 工具）可并行存在。

## §三 目标架构（CSG 数据面三层模型）

```
 上层：工作流 / 折叠算子 / Agent / UI        （只认 MCP 工具面）
              │  提交 CSG CanonicalForm（调用子图） / 读回图态
              ▼
┌────────────────────────────────────────────────────────────────┐
│             CallCenter —— CSG 工具调用平台                        │
│                                                                │
│  ┌─ 数据面（契约层 · CSG CanonicalForm）────────────────────┐    │
│  │  工具编目(配置) │ 调用生命周期(状态机) │ 依赖编排(图)      │    │
│  │  schema/fingerprint/version → metadata + state            │    │
│  └─────────────────────────────┬───────────────────────────┘    │
│                                │ 只操作 CanonicalForm           │
│  ┌─ 控制面（路由/缓存/可观测）────────────────────────────┐    │
│  │  Router: csg://tool/{name} → Track                       │    │
│  │  Health / Audit / VersionTable                           │    │
│  └─────────────────────────────┬───────────────────────────┘    │
│                                ▼                                │
│  ┌─ 终端面（适配层 · CSG↔native 变换器）─────────────────┐        │
│  │ C#Track │ TSTrack │ PSTrack │ ExternalMCP           │        │
│  └─────────────────────────────────────────────────────────┘     │
└────────────────────────────────────────────────────────────────┘
     C#(ALC/Roslyn)   Node/MCPBridge  pwsh    MCP server
```

三层：
- **数据面（CSG）**：统一中间表示。与 `CsharpPrj/Protocol/CSG` 标准 / TS `Protocol/CSG` 实现对齐，是平台唯一共享语言。
- **控制面**：操作 CanonicalForm 的确定性调度（路由/多轨/版本/缓存/可观测）；LLM 门控留 Agent 收拢点（D7）。
- **终端面**：每语言 Adapter 把 `CanonicalForm ↔ 本语言可执行形态` 互转（实现 CSG 变换操作），平台不感知语言。

## §四 数据面：用 CSG 建模工具调用

### 4.1 工具 = CanonicalForm 的一个节点（或调用子图）
```
csg://tool/{name}
CanonicalNode{
  id: "tool:cline:ask",
  type: "tool",                       // 或 "call" | "param" | "result"
  props: { backend:"For" | ..., version, fingerprint },
  metadata: {                          // = 工具 schema/签名（给模型可派生 Function schema）
     signature: {inputs[], outputs[], description},
     flags: {deterministic, externalized, hotReloadable, notExposedToModel}
  }
}
```
- **配置投影**：工具编目、签名、fingerprint → 序列化为 CanonicalForm JSON（语言无关线缆）。
- **状态机投影**：一次调用会历经 `pending→(source→build→runtime)→done|failed`，state 落在节点；多轨 Source/Build/Runtime 即一段状态机，符合 CSG `IStateMachine` 投影。
- **图投影**：工具间调用流（A 的结果是 B 的输入）用 `CanonicalEdge` 表达 —— 与「工作流/折叠链」同构，平台可直接执行 CSG 描述的调用流图。

### 4.2 调用协议（请求/响应 = CanonicalForm）
- 请求：`csg://node/{callId}` 一个待执行节点/子图 + `state=ready`。
- 执行：控制面沿 `csg://edges` 依数据依赖调度各 Track。
- 响应：同一图回填 `state=done`、结果写入 `csg://node/{callId}/state/result`；失败回填 `state=failed` + 归类错误。
- 版本/热载：`csg://metadata` 载 fingerprint/version，作为版本路由与缓存 key。

### 4.3 schema 规范
- input/output 用统一 JSON Schema（与 CSG 类型注册表一致：Core 类型 + Domain 扩展）。
- `FileDrivenFunctionRegistryProvider`（函数名+参数类型）升级为 C# 轨的 schema → CanonicalForm metadata 映射源。

## §五 控制面：Router（只操作 CanonicalForm）

- 输入 `CanonicalForm`（含目标节点）→ `Lookup(csg://tool/{name})` → 定位 Track 与版本子图。
- 管线：**健康检查 → 命中编译缓存 ? 直接执行 : 走 Build 轨 → 执行 → 回填图态 → 可观测/审计**（LLM 门控不在 CallCenter，留 Agent 收拢点）。
- 熔断/降级：某 Track 连续失败 → 健康标记降级；同名多实现（C# 版 + TS 版）按版本/优先级在 CSG metadata 上灰度切换。
- 一致性：沿用 CSG 校验规则（节点覆盖、边覆盖、可达性、无死锁、类型一致）在入库/重载时校验工具子图。

## §六 编译缓存多轨制（Source / Build / Runtime 三轨）

| 轨 | 职责 | 每语言形态 |
|---|---|---|
| **Source 轨（发现）** | 扫描函数源，产出 CSG 工具子图 + fingerprint | C# 程序集反射 / TS `tools-definitions/*.json`+namespace / PS `.psm1` 导出 / 外部 MCP `list_tools` |
| **Build 轨（编译）** | 把源编译为可执行产物，写入编译缓存（key=fingerprint） | C# Roslyn IL / TS `tsc` bundle / PS 语法+模块元数据预分析 |
| **Runtime 轨（执行）** | 命中最优产物执行，回填 CanonicalForm state | C# `AssemblyLoadContext` / TS `dynamic import` / PS `pwsh` / external `client.callTool` |

- **缓存 key = fingerprint**：`source+build+api` 哈希（存于 metadata）。
- **多路径并存**：同工具可同时有"编译产物"与"源直译"两条执行路径，按健康/版本/性能命中最优。
- **C# 轨**：复用 `FunctionLibraryLoader` 的 `AssemblyLoadContext`/`ExtensionAssemblyHost.ResolveType`；需源码→IL 走 Roslyn 内存编译。

## §七 热加载与版本切换（图的版本化重构）

- **触发**：文件/程序集/project 变更 → 重算 fingerprint（存于 `csg://metadata`）。
- **流程**：digest 变 → 重构该工具子图（新版本）→ 通过 CSG 一致性校验 → Build 轨重编译 → **新旧版本 CanonicalForm 并存**（旧引用计数保留在途调用）→ 路由瞬切新版本 → 旧计数归零回收。
- **灰度**：`cli:stable` → `cli:next` 由 metadata 上的 version 标签路由。
- **约束**：热加载只对 `hotReloadable` 工具生效；外部 MCP / 触网轨不做函数级热载。

## §八 终端面：Track Adapter = CSG↔native 变换器

每个 Adapter 实现 CSG 变换操作（进入位移 / 结果位移），互操作即读写 CanonicalForm：

| 轨 | 变换（CanonicalForm ↔ 本地可执行） | 复用件 |
|---|---|---|
| **C#Track** | 工具子图 → 描述符/委托（`TryGetDelegate`）→ 执行 → 结果回填 CanonicalForm | `FunctionLibraryLoader`、`FileDrivenFunctionRegistryProvider`、`FunctionExecutor`、`McpServerTools` |
| **TSTrack** | 工具子图 → MCPBridge 路由 → `client.callTool` → 结果回填 | `MCPBridge`（`RequestRouter`/`ToolAggregator`/`registry.ts`） |
| **PSTrack** | 工具子图 → `pwsh` 命令（参数→JSON→执行→JSON）→ 回填 | `invoke-ps-script` |
| **ExternalMCPTrack** | 工具子图 → 外部 MCP server 只读引用转发 | `McpClientManager`/`RegistryMcpHosting` HTTP |

外部生态（如 C# MCP Registry HTTP `/mcp`）可**作为 ExternalMCPTrack 子源反向接入**，形成"平台既聚合外部、也能被 TS 聚合"的对偶。**LlmTrack 不存在**：LLM 属 Agent 侧，收拢于 `LlmRoutingClient`/`GlobalLlmGate`/`LlmMode` 单点（D7）。

## §九 LLM 收拢于 Agent（不在 CallCenter）

- **决策（D7）**：LLM 调用属 Agent 侧功能，收拢于 Agent 内单点（`LlmRoutingClient` + `GlobalLlmGate` + `LlmMode`），**不进 CallCenter**；CallCenter 定位为纯跨语言工具平台（C#/TS/PS/外部 MCP 四轨）。
- 原《LLM经MCP唯一交互-架构收敛设计.md》即该收拢点的载体文档，负责门控下沉、防递归（LLM 不暴露为模型可自调 function）、内/外二分；与本文互不重叠：**CallCenter 管工具面，Agent 管 LLM 面**。
- `guard_input`/`rule_match`/`provide_prompt`（控制/提示词函数）与 `answer`/`cline`（LLM 驱动执行端）同为 Agent 侧能力，随 LLM 同侧保留，**框架直用为主**；按双态原则（§二）需要跨边界寻址时可额外包装进 CallCenter，二者不冲突。
- `notExposedToModel` 语义保留：供未来 CallCenter 托管、但不暴露给模型的 Agent 内部控制工具使用（防递归）。

## §十二 收益 / 风险

**收益**
- 语言无关由 **CSG 标准**保障（非自造 IR）：任何语言读写 CanonicalForm 即可接入。
- 工具契约、调用、状态、编排统一为一种数据模型；工作流/折叠链与工具调用同构，可互相套嵌。
- 新增语言 = 新增一个变换 Adapter，不动数据面/控制面。
- 跨语言工具与外部 MCP 平级；可观测收敛于控制面单点；LLM 收拢于 Agent 内单点（门控不属 CallCenter）。

**风险 / 代价**
- ~~C# 侧暂无 CSG 运行时实现~~ → **已消解（D1）**：直接复用 `CSG.Unified`（CanonicalForm/TransformEngine/ValidationEngine 已具）。
- 不能退化为"把 CSG 塞进加热路径的语言逻辑"：控制面必须只读 CanonicalForm，语言细节禁入。
- TS/PS 跨进程，统一 I/O（CSG JSON / MCP）一致性与序列化开销需测微基准。
- 热加载多版本并存带来内存/句柄管理复杂度；限定 `hotReloadable` 范围。
- CSG 校验（可达性/无死锁/类型一致）在重载入档时须与调用面解耦，避免热路径阻塞。
