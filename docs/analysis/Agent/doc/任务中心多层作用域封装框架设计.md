## 一、背景与问题

### 1.1 现状痛点（为什么"创建任务/加节点/查节点/删节点"麻烦）

在 `FileDriven/DrivenConfig/Scripts/Agent/db_localdb_answer_test.json` 这类脚本里，每个语义操作都要手敲一长串 `requestJson=`。根因是**框架把"一个任务及其节点"拆散在 4 类 action（`task`/`node`/`relations`/`graph`）上**，每一类都要完整 JSON，且节点命名与"节点属于哪个任务"要靠人肉维护：

| 你要做的事 | 现在的写法 | 痛点 |
|---|---|---|
| 建任务 | `task op=enqueue` + `mode/executorId/maxRounds/roundPromptPlan/relatedNodes` 一长串 | 参数极多 |
| 给任务加一个节点 | ① `node` 写 ur_nodes（手拼 `nodeKey=nodes.{wf}.{name}` + 手填 `threadId`）② `addResource` 建图端点 ③ `relations.declare` 或 `enqueue relatedNodes` 建 task→node 边 | **3 个独立 JSON 才能让节点"属于"任务** |
| 查任务的节点 | 没有"按任务查节点"入口，只能 `query outputs(threadId)` 或 `listReferences(task)` 各看一半 | 两条路都不完整 |
| 删节点 | `node delete` + `removeResource`，可能还要清边 | 又 2 步 |

### 1.2 关键事实（代码核实）

- 节点命名依赖手写 `nodes.{workflowId}.{nodeKey}`（`node/output.json`）、`relations.{workflowId}.{relationId}`（`relations/README.md`）；workflowId 常硬编码为 `agent-round`。
- "节点属于任务"存在**两条互不相通的途径**：① 约定共享 `threadId`（命名空间）；② 图边（`ReferenceGrounding.ReconcileTaskAsync` 建的 task→node 边）。没有统一入口。
- 已存在 `TaskGraphService`（`Agent.Core.TaskPool`），它实现了"建图引用边 → 入队任务"的复合逻辑，但**未注册成任何 `AgentUi_*` 函数 / RunJson action**，外部不可达；且 `GetTaskGraphAsync` 返回的是边端点而非节点载荷。

## 二、设计原则（三层封装，逐层不越界，通用逻辑优先下沉 Share）

> 类比"C# 封装 C++、C++ 封装机械码"：上层只依赖紧邻下一层，调用方永远只接触最高层。
> **通用逻辑优先在 `CsharpPrj/Share` 构建为通用组件**，Agent 层只做组装接线（对齐框架既有分工：ProgressUpdater/TerminationDecider 在 Share 为纯裁决器、AgentRunner 注入消费）。

| 层 | 对应物 | 职责 | 谁用 |
|---|---|---|---|
| **机械码** | 存储/引擎原语：`ur_tasks`/`ur_nodes`/图库、`AgentTaskPoolAdapter`、`INodeStore`、`IResourceReferenceStore`、`ReferenceGrounding` | 真实落库、写图、任务池状态机 | 只被 C++ 层碰，**上层禁止直调** |
| **C++** | 协议面：`AgentUi_RunJson` 的 action 分发（`task`/`node`/`relations`/`graph`/`query`…） | 把机械码包装成"动作"；参数校验、诊断、单点入口 | 被 C# 层封装；也直接服务外部脚本/MCP |
| **C# 通用核心（Share 层）** | 本方案新增的 `ScopeCommandTranslator` + `IStep` 步骤链 + `IScopeNamingRule` 命名规则，放 `CsharpPrj/Share`（纯逻辑、零 Agent 依赖、可单测） | 高层命令 → 步骤单 JSON 序列的**纯函数式步骤链展开**；命名/归属派生；前置条件短路裁决 | 被 L3 组装层引用；被 CentralTest 直测 |
| **C# 组装层（Agent.Launcher）** | `AgentUi_TaskScope*` 注册函数（组装 Share 翻译器 + 注入 `RunJsonAsync` 执行端口 + Agent 命名规则实例） | 把 Share 通用核心接线到 Agent 协议面；诊断聚合回传 | 最终调用方：人 / 脚本 / 外部智能体 |

**核心约束**：
- C# 通用核心（Share）**纯逻辑、零 Agent 依赖**：只产出步骤描述（JSON 序列），不执行；执行端口 `Func<string, Task<string>>` 由组装层注入。
- C# 组装层（Agent）**只产出并调用既有 action 的单 JSON（走 `RunJsonAsync`）**，绝不 `new AgentTaskPoolAdapter`/`INodeStore` 去碰机械码。
- 这样天然获得 C++ 层已有的参数校验、诊断文本、装配降级（未装配返回诊断、不消耗额度，语义权威见 §4.3 诊断契约）、单点入口，且**不复制任何落库逻辑**（SingleImplementation、不双真源）。
- **复用范式**：Share 通用核心对齐 `ScopeLifecycleStateMachine`（纯逻辑 + 副作用委托给注入 Func）和 `TaskStateMachine`（自包含状态机原语 `TryTransitionTo(condition)`）的既有 canonical 写法，不另造轮子。

## 三、核心设计：多层作用域（Scope）限制框架

### 3.1 一句话概括

> 保持 `AgentUi_RunJson` 单 JSON 协议不变，在其上做**多层作用域限制**：不选作用域 = L0 原样单 JSON（最灵活、向后兼容）；选中某个 task 作作用域后，后续命令只表达高层意图，封装层用**短路步骤链**自动展开为**一条或多条既有 action 的单 JSON**。

"多层 UI 限制"= **逐步收窄用户要输入的参数 + 逐步自动填充被收窄掉的多步操作**。每一层都叠在前一层之上：

| 层 | 作用域 | 你还需敲什么 | 封装层自动补什么 |
|---|---|---|---|
| **L0 无作用域** | — | 全字段（action/op/taskKey/nodeKey/threadId/…） | 无（直通原样 JSON） |
| **L1 task 作用域** | `scope:{taskKey}` | `name + payload`（+可选 nodeType） | 自动填 `taskKey`、`threadId=wf`、`nodeKey=nodes.{wf}.{name}`，并展开"写节点 + 建图端点 + 建边"多步 |
| **L2 task+类型作用域** | 上面 + `nodeType=output` | `name + payload` | 连 nodeType 也省了，按默认类型建 |
| **L3 全自动** | 上面 + 命名规则固定 | 一句意图 | 封装层全权推导（供外部智能体 / MCP） |

> **"一次限制"语义**：作用域约束是**每条命令自带的**（一次性、命令内生效），不是跨命令的会话状态。选 `scope:{taskKey}` 只对当前这条高层命令生效；下一条命令若不带 scope，回到 L0 原样。这与现有 `RunJson` 的无状态风格一致，可并发、可重放、无副作用。

### 3.2 作用域承载：命令自带（无可变状态）

不引入任何"当前选中任务"的可变槽位（不存 session state）。作用域约束以命令输入形式显式携带：

```
高层命令 =  { cmd: "addNode", scope: {taskKey:"tp_xxx"}, name:"source", nodeType:"output", payload:{...} }
                 └──────── 作用域约束（本命令内生效）────────┘
```

封装层根据 `cmd` + `scope` 进行步骤链展开（见 §四）。无 scope → 展开为"仅当前字段"的直通（L0，见 §4.4 的 `S0 PassThrough`）。

> **与 `StateManager` 持久分区的区别**：`IStateManager.CreateScope` 创建的是**跨命令持久存储分区**（落 `StorageEngine.CreateSession`，有状态、需显式 `ReleaseScope`）。本方案的作用域是**一次性命名空间**（命令内生效、用完即弃），不创建持久分区、不调用 `CreateScope`。二者概念同名但语义不同，实现上完全独立，不得混用。

### 3.3 命名 / 归属派生规则（`IScopeNamingRule` 接口化）

命名/归属派生是**纯逻辑**，下沉为 Share 层单一实现（对齐 TH-12 SingleImplementation），不复制：

```csharp
// CsharpPrj/Share —— 纯接口，零 Agent 依赖
public interface IScopeNamingRule
{
    /// <summary>派生 workflowId：scope.workflowId ?? taskKey（任务隔离，杜绝共享 agent-round 串任务）。</summary>
    string ResolveWorkflowId(ScopeContext scope);

    /// <summary>派生 nodeKey：按 nodeType 选择命名空间前缀（nodes/events/keymapping/config）。</summary>
    string ResolveNodeKey(ScopeContext scope, string nodeType, string name);

    /// <summary>派生 ThreadId：自动填 workflowId。</summary>
    string ResolveThreadId(ScopeContext scope);
}
```

| 事项 | 默认规则（`DefaultScopeNamingRule` 实现） |
|---|---|
| workflowId | `scope.workflowId ?? taskKey`（任务隔离，杜绝共享 `agent-round` 串任务；可在 scope 显式覆盖） |
| nodeKey | `output/resource/node → nodes.{wf}.{name}`；`event → events.{wf}.{name}`；`keymapping → keymapping.{wf}.{name}`；`config → config.{key}`（全局键值，不按任务命名空间） |
| ThreadId | 自动填 `workflowId` |
| 图边 | task→node（`node_to_node`），经既有 `relations.declare` / `task.relatedNodes` 路径建 |

> **nodeKey 与图端点 id 的对应**：节点实体标识 `nodeKey = nodes.{wf}.{name}`（带 `nodes.` 前缀），而图资源镜像端点 id 采用 `{wf}.{name}`（既有 `EnsureNodeMirrorAsync` 语义，Id=wf.node，无前缀）——二者以同一 `(wf, name)` 归属对关联：`S2 addResource` 以 `{wf}.{name}` 建端点，`S3 relations.declare` 建边时以 nodeKey 解析回同一归属对后关联，避免前缀不一致导致建边错位。


> Agent 组装层注入 `DefaultScopeNamingRule` 实例；如有自定义命名需求（如多租户前缀），只需实现 `IScopeNamingRule` 替换注入即可，翻译器逻辑不变。

## 四、核心机制：`ScopeCommandTranslator` 短路步骤链翻译器（Share 层，零 Agent 依赖）

### 4.1 为什么用短路步骤链、且不需要"状态"

"多步操作"（写节点→建图端点→建边→查询聚合）天然是一个**确定性步骤链**，每一步是否执行取决于**输入自带的前置条件**（节点是否已存在、守卫是否装配、图端点是否需手动建、是否要建边）。它不需要完整状态机的转移表（无状态变量、无跨调用持久状态），只需"步骤 + 前置条件短路"即可表达：

- **无跨调用持久状态**：不保存"当前任务/当前步骤进度"；每次调用从 `Idle` 出发，喂入一条高层命令（含 scope 约束），走完到 `Done` 即返回。单次调用内部有步骤游标和诊断累积，但调用结束后即丢弃。
- **前置条件裁决 = 短路**：某步的前置条件不满足 → 短路跳过；满足 → 产出一步（或多步）既有 action 的单 JSON 并进入下一步。
- **可重放 / 可并发 / 无副作用残留**：因不落状态，同一命令可安全重复调用（底层各 action 本就幂等），可并发执行不同任务。

> **复用既有范式**：本设计的"纯逻辑 + 执行端口注入"写法对齐既有 canonical（`ScopeLifecycleStateMachine` 纯逻辑 + 副作用委托注入 `Func`、`TaskStateMachine` 的 `TryTransitionTo(condition)` 守卫转移），不另造轮子（见 §二）。

### 4.2 组件契约（Share 层新增）

```csharp
// CsharpPrj/Share —— 纯逻辑，零 Agent 依赖，CentralTest 可直测

/// <summary>步骤链原语：一个可短路、由实现类静态定义的步骤节点（步骤路径由命令类型硬编码确定，无动态注册）。</summary>
public interface IStep
{
    /// <summary>步骤标识（S0=直通，S1~S7）。</summary>
    string Id { get; }

    /// <summary>前置条件判定：返回 false 则短路跳过。</summary>
    bool CanExecute(ScopeContext scope);

    /// <summary>产出一步或多步既有 action 的单 JSON（不执行，只产出描述；S5/S6 级联会产多条）。</summary>
    IReadOnlyList<string> ProduceActionJson(ScopeContext scope, IScopeNamingRule naming);
}
```

> 注：`IStep` 成员为**实现类静态提供的逻辑**（接口方法），非可注入委托——因为步骤路径由命令类型静态确定（§4.7），无需运行期替换步骤，故不设步骤级注入；唯一注入点是 `ScopeCommandTranslator` 的 `_executePort`（测试桩 / `RunJsonAsync` 可替换）。

```csharp
/// <summary>高层命令 → 步骤单 JSON 序列的纯函数翻译器。</summary>
public sealed class ScopeCommandTranslator
{
    private readonly IScopeNamingRule _naming;
    // 执行端口由组装层注入（Agent 侧注入 RunJsonAsync；测试侧注入桩）
    private readonly Func<string, Task<string>> _executePort;

    public ScopeCommandTranslator(IScopeNamingRule naming, Func<string, Task<string>> executePort)
    {
        _naming = naming;
        _executePort = executePort;
    }

    /// <summary>展开一条高层命令为步骤序列并逐条执行，返回聚合诊断。</summary>
    public async Task<ScopeCommandResult> ExecuteAsync(ScopeCommand command)
    {
        var steps = ResolvePath(command);              // §4.4 转移表
        var diagnostics = new List<string>();
        var results = new List<string>();
        foreach (var step in steps)
        {
            if (!step.CanExecute(command.Scope))       // 前置条件短路
            {
                diagnostics.Add($"[skip] {step.Id}: 前置条件不满足");
                continue;
            }
            foreach (var json in step.ProduceActionJson(command.Scope, _naming))  // 一步可产多条 JSON（如 S5/S6 级联）
            {
                var result = await _executePort(json); // 经注入端口执行（RunJsonAsync）
                results.Add(result);
                diagnostics.Add($"[ok] {step.Id}: {Truncate(result)}");
            }
        }
        return new ScopeCommandResult(command.Cmd, results, diagnostics);
    }

    /// <summary>dry-run：只展开步骤序列不执行（供 UI 预览 / select 命令）。</summary>
    public IReadOnlyList<IStep> Preview(ScopeCommand command) => ResolvePath(command);

    private static IReadOnlyList<IStep> ResolvePath(ScopeCommand command) => /* §4.4 转移表 */ ...;
}
```

### 4.3 可复用的原语步（`IStep` 实现）

| 步 | 执行前提（不满足则短路跳过） | 产出（既有 action 单 JSON） | 落库 |
|---|---|---|---|
| `S1 EnsureNodeWrite` | `payload` 非空或需覆盖 | `{action:"node", op:"write", nodeKey, nodeType, threadId, payload}` | ur_nodes |
| `S2 EnsureGraphEndpoint` | 需手动建图端点：`nodeType≠node`（`nodeType=node` 经 `WriteGuardPort` Put 时自动调 `EnsureNodeMirrorAsync` 建端点）∨ 守卫未装配 | `{action:"addResource", resourceType:"node", id:{wf}.{name}, name}` | 图端点 |
| `S3 EnsureTaskNodeEdge` | 需要 task→node 边（addNode/linkNode/createTask 带 `relatedNodes`） | `{action:"relations", op:"declare", threadId:{wf}, declarations:[...]}` | ur_nodes(relation)+图边（守卫未装配则图边子项跳过并记诊断） |
| `S4 QueryAggregate` | 需按任务查节点 | `{action:"query", target:"nodesByTask", key:{taskKey}, threadId:{wf}}` | 读 ur_nodes（结构化） |
| `S5 DeleteNode` | 节点存在 | 主删除 `{action:"node", op:"delete", nodeKey}` + 级联清边（`relations.undeclare`/`removeResource`） | ur_nodes |
| `S6 DeleteTask` | 任务存在 | 主删除 `{action:"task", op:"delete", taskKey}` + 级联清引用（`relations.undeclare`） | ur_tasks |
| `S7 Enqueue` | 入队激活 | `{action:"task", op:"enqueue", taskKey, input, mode, ...}` | ur_tasks |

> **诊断聚合与短路契约（权威）**：每步 `CanExecute` 返回 false → 短路跳过并记诊断到 `Diagnostics` 列表（对齐 `TaskGraphService` 的 diagnostics 模式）；守卫/任务池未装配时，依赖其的**子项**（如图边写入）返回诊断文本而非抛错、不阻断其余步骤——即"未装配返回诊断、不消耗额度"。该语义在本节唯一定义，§二/§七/§八 引用之。
>
> **短路示例**：`addNode` 若 nodeType=node 且守卫已装配 → `WriteGuardPort` Put 自动建图端点 → S2 跳过（无需手动 addResource）；守卫未装配（无论 nodeType）→ S2 走 addResource 补建（安全降级）。S3 仅以"需要边"为前提，守卫未装配时声明关系仍写入 ur_nodes（保证节点归属），仅图边子项跳过并记诊断。**用户只需表达高层意图，是否执行某步由步骤链按输入执行前提裁决。**

### 4.4 高层命令 → 步骤路径（转移表，`ResolvePath` 实现）

> **L0 直通**：命令不带 scope → `ResolvePath` 返回单步直通节点 `S0 PassThrough`（`CanExecute` 恒真、`ProduceActionJson` 原样回显该命令的原始 JSON 字段、不派生命名），走同一执行循环但产物即原样单 JSON——保持 L0 最灵活、向后兼容。

| 高层命令 | 步骤路径（顺序） | 说明 |
|---|---|---|
| `createTask` | `S3 → S7`（带 `relatedNodes` 时先建边后入队；无则仅 `S7`；`taskKey` 由命令自带并作为归属命名空间） | 建任务（+关联节点）并激活 |
| `addNode` | `S1 → S2 → S3`（S2/S3 按执行前提短路） | 加节点并挂到任务 |
| `getNodes` | `S4 QueryAggregate` | 返回 `[{nodeKey,nodeType,status,payload}]` |
| `findNode` | `S4 QueryAggregate` + 客户端按 `name` 过滤 | 找单个节点 |
| `removeNode` | `S5 DeleteNode`（scope 内自动派生 nodeKey + 级联清边） | 删节点 |
| `linkNode` | `S2 → S3`（不写内容，仅挂边） | 把既有节点挂到任务 |
| `deleteTask` | `S6 DeleteTask`（scope 内自动级联清节点/引用） | 删任务 |
| `select` | 仅校验 scope 合法并回显 `Preview()` 结果 | 供 UI 预览"将展开哪些步" |

### 4.5 参考实现：`TaskGraphService` 步骤链

现有 `Agent.Core.TaskPool.TaskGraphService.CreateTaskWithRelationsAsync`（`TaskGraphService.cs`）已实现了 "建图引用边 → 入队任务" 的步骤链（不写 ur_nodes 实体内容），且 Agent 无关。其步骤顺序与 `S3→S7` 等价、诊断模式一致，可作为 `IStep` 实现中 `S3`/`S7` 的**参考范本**（收敛路径见 §七）。

### 4.6 与 GraphKey 框架的同构分析及复用策略

本方案的"高层命令 → 步骤展开 → 线性 JSON 序列"管线，与 `CsharpPrj/Share/GraphFramework/GraphKey.cs` 中的 `ChainTemplate → ChainTemplateExpander → List<object>` 管线在结构上**同构**。本质都是"模板定义 → 实例化展开 → 线性可执行序列"。

#### 同构映射

| GraphKey 概念 | 任务中心封装概念 | 关系 |
|---|---|---|
| `ChainTemplate<TNode>`（模板定义 + 节点列表 + NodeBuilder） | `ScopeCommand`（高层命令 + scope 约束 + 参数） | **同构**：定义→实例化→线性序列 |
| `ChainTemplateExpander.ExpandToWorkflowNodes()` | `ScopeCommandTranslator.Preview()` | **同构**：两者都只展开产出线性序列、不执行 |
| `ChainTemplateRegistry` | 高层命令注册表 | **同构**：注册多个模板/命令 |
| `DataFlowGraph` + 拓扑排序 | `ResolvePath`（确定性线性链） | **不复用**：步骤链是线性的，不需要图拓扑排序 |
| `PlaceholderResolver`（@input/@prev/@node 跨节点引用） | `IScopeNamingRule`（命名空间派生） | **不复用**：语义不同——Placeholder 解析跨节点数据流引用，NamingRule 派生命名归属 |
| `List<object>`（工作流节点） | `List<string>`（action 单 JSON） | **同构**：都是线性可执行序列，但产物类型不同 |

#### 三种复用策略

| 策略 | 做法 | 优 | 劣 | 评估 |
|---|---|---|---|---|
| **A. 直接引用** | `ScopeCommandTranslator` 继承 `ChainTemplate`，引用 GraphKey 程序集 | 模板/展开管线统一 | 引入 DataFlowGraph 拓扑排序（不需要）、Placeholder 语义不匹配（硬塞）、2000+行重依赖 | ❌ 不推荐 |
| **B. 复用模式不复用代码** | 独立实现 `IStep`/`ScopeCommandTranslator`，借鉴 ChainTemplate 的模式但不引用 | 轻量、零依赖、CentralTest 直测 | 两套展开管线并存（GraphKey 一套、ScopeCmd 一套），设计模式重复 | ✅ 短期方案（P0 采用） |
| **C. 抽取通用模板展开抽象** | 在 Share 层定义 `ITemplateExpander<TTemplate,TStep,TResult>` 通用接口，GraphKey 和 ScopeCmd 各实现一份 | 模式统一、消除重复、两个消费者共享接口 | 需重构 GraphKey 适配接口，改动面大 | ⭐ 长期演进目标 |

#### 采用路径：B → C 渐进

1. **短期（P0）**：按策略 B，`ScopeCommandTranslator` 独立实现，借鉴 GraphKey 的模板/展开模式但不引用。快速落地、CentralTest 可测。
2. **长期（P0 后演进）**：按策略 C，在 Share 层抽取 `ITemplateExpander<TTemplate, TStep, TResult>` 通用接口，让 `ChainTemplateExpander`（GraphKey）和 `ScopeCommandTranslator`（任务中心）都实现它。消除两套展开管线的设计重复，同时保持各自不需要对方的领域模型。

#### 不复用的部分（有明确理由）

- **`DataFlowGraph` + 拓扑排序**：任务步骤是确定性线性链（S1→S2→S3），不需要图拓扑排序——引入 DataFlowGraph 是杀鸡用牛刀。
- **`PlaceholderResolver`**：语义是跨节点数据流引用解析（`@input`/`@prev`/`@node`），与命名空间派生（`IScopeNamingRule`）不同——硬塞占位符到命名规则会导致语义混淆。
- **`WorkflowValidator`**：后置验证（Build 时校验全部节点参数），与前置条件短路（`IStep.CanExecute` 逐步裁决）机制不同——合并会破坏短路语义。

### 4.7 与 Pipeline 框架的同构分析及复用策略

本方案的 `IStep` → `ScopeCommandTranslator` → `ScopeCommandResult` 管线，与 `CsharpPrj/Share/GraphFramework/Pipeline/` 中的 `IGraphPipelineStep` → `GraphPipeline` → `IGraph` 管线在结构上**同构**。两者都遵循"步骤接口 → 步骤容器 → 串行执行"模式。

#### 同构映射

| Pipeline 概念 | 任务中心封装概念 | 关系 |
|---|---|---|
| `IGraphPipelineStep`（Name + Execute(IGraph, IPipelineContext) → IGraph） | `IStep`（Name + CanExecute + ProduceActionJson(ScopeContext) → string[]） | **同构**：步骤接口，都有 Name + Execute；差异：IStep 多了 CanExecute 短路谓词、产出为 JSON 列表 |
| `GraphPipeline`（`_steps` + AddStep/RemoveStep/InsertStep + Execute 循环） | `ScopeCommandTranslator`（`_steps` + ResolvePath + ExecuteAsync） | **部分同构**：步骤管理 API 一致；执行模型不同（见下） |
| `IPipelineContext`（SharedData 字典） | `ScopeContext`（强类型字段） | **不复用**：Pipeline 用弱类型字典传共享数据，ScopeContext 用强类型字段（ScopeConstraint/TaskKey/NodeKey），套字典会弱化类型安全 |
| `GraphPipelineOrchestrator`（RegisterStage/Step/Pipeline + order + isFatal） | `ScopeCommandTranslator.ResolvePath`（固定路径，无 order） | **不复用**：编排器按 order 排序+isFatal 熔断，任务中心按命令类型选固定路径+CanExecute 短路——机制不同 |
| `PipelineBase`（fixed+dynamic stages + dirty-rebuild + InsertBefore/After） | `ScopeCommandTranslator`（静态路径，无动态插入） | **不复用**：任务中心步骤路径由命令类型确定，不需要动态注册/排序 |

#### 关键差异：数据流模型

这是**不能直接继承 GraphPipeline** 的根本原因：

| 维度 | GraphPipeline（链式） | ScopeCommandTranslator（扇出式） |
|---|---|---|
| step 间数据传递 | `step.Execute(graph) → IGraph`，**输出作为下一步输入** | `step.ProduceActionJson(ctx) → string[]`，**输出收集到列表，不传递给下一步** |
| 共享数据 | `IPipelineContext.SharedData`（弱类型字典） | `ScopeContext`（强类型字段，所有 step 共享只读） |
| 执行循环 | `foreach: current = step.Execute(current)` | `foreach: if CanExecute: results.AddRange(step.ProduceActionJson(ctx))` |

GraphPipeline 的 Execute 循环是 `current = step.Execute(current, _context)`——每步的输出成为下一步的输入。而 ScopeCommandTranslator 是 `results.AddRange(step.ProduceActionJson(ctx))`——每步独立产出 JSON（列表）、收集到列表。**数据流模型不同，不能直接复用 Execute 循环。**

#### 复用策略（与 §4.6 同构，仅抽取目标不同）

复用策略与 §4.6 GraphKey 分析**同构**：策略 A（直接继承/引用 `GraphPipeline`）被否——Execute 循环语义冲突（链式 vs 扇出）+ 泛型 `<string,string,string>` 不是图、语义不匹配；策略 B（复用模式不复用代码）为短期（P0）；策略 C（抽取通用接口）为长期演进。与 §4.6 的唯一差异是把抽取目标换成 `IStep<TContext,TResult>` 通用接口 + `StepCollection<TStep>` 通用容器（`AddStep/RemoveStep/InsertStep/GetStepNames`）。采用路径同为 **B → C 渐进**，且策略 C 的 `IStep` 抽取可与 §4.6 的 `ITemplateExpander` 抽取合并为同一次 Share 层重构（详见 §4.6 三策略表模板）。

> **关于"设计模式重复"与 SingleImplementation**：短期（P0）策略 B 会同时存在 GraphKey 与 ScopeCommandTranslator 两套展开/步骤管线，这是**有意的临时重复**——P0 阶段各自只有一份实现、不构成运行期双权威，故不违反"不双真源"原则；它属于 SingleImplementation 演进的中间态（先落地、C 阶段收敛为单一通用接口），而非永久并存。

#### 可复用的部分（有明确理由）

- **步骤管理 API 模式**：`AddStep/RemoveStep/InsertStep/ClearSteps/GetStepNames` 的管理 API 模式可直接借鉴，P0 用独立实现（~20 行），C 阶段收敛为 `StepCollection<T>` 共享。
- **步骤接口模式**：`IGraphPipelineStep` 的 `Name + Execute(context)` 签名模式，IStep 借鉴为 `Name + CanExecute + ProduceActionJson(ScopeContext)`。

#### 不复用的部分（有明确理由）

- **Execute 循环**：链式 `current = step.Execute(current)` vs 扇出 `results.AddRange(step.ProduceActionJson(ctx))`——数据流模型根本不同，强行复用需 override 等于重写。
- **IPipelineContext**：弱类型 `SharedData` 字典 vs 强类型 `ScopeContext` 字段——套字典会丢失编译期类型安全。
- **GraphPipelineOrchestrator**：order 排序 + isFatal 熔断 vs 固定路径 + CanExecute 短路——编排机制不同。
- **PipelineBase 动态 stage**：fixed+dynamic+dirty-rebuild+InsertBefore/After vs 静态路径——任务中心步骤路径由命令类型确定，不需要动态注册。

## 五、单 JSON 协议不变

### 5.1 产物 = 既有 action 的单 JSON

封装层**不新增 action 类型**。所有高层命令最终展开为 `task`/`node`/`relations`/`query` 等**既有 action 的单 JSON**，逐条经 `RunJsonAsync` 执行。老的 `db_localdb_answer_test.json`、模板库、MCP 方案全部兼容，零破坏。

### 5.2 唯一最小扩展：`query` 增补 `nodesByTask` target（利用已有 `INodeStore.ListAsync`）

"按任务查节点要拿结构化载荷"这个缺口，现有 `query outputs(threadId)` 只返回文本、`listReferences(task)` 只返回边。但 **`INodeStore.ListAsync(nodeType:null, threadId:wf)`**（`NodeStore.cs`）已经能返回结构化 `NodeRecord` 列表——按 threadId 过滤即可实现"按任务查节点"。

> **过滤键必须是 `wf`（workflowId）而非 `taskKey`**：节点以 `threadId=wf`（`ResolveThreadId` = `scope.workflowId ?? taskKey`，§3.3）写入，查询侧必须用同一 `wf` 过滤才一致；当 scope 显式覆盖 workflowId（§3.3）时，`taskKey ≠ wf`，按 taskKey 会查不到刚写入的节点。默认 `wf=taskKey` 时两者相同，故默认场景不受影响。

因此 `query` 增补 `nodesByTask` target **不需要新建存储路径**，只需在 `QueryDataTextAsync`（`AgentUiLibraryData.cs`）加一个 case 走 `INodeStore.ListAsync` 并序列化为 JSON：

```
{ "action":"query", "target":"nodesByTask", "key":"tp_xxx", "threadId":"{wf}" }   // wf = scope.workflowId ?? taskKey（与 S1 写入侧一致）
 [{ "nodeKey":"nodes.{wf}.source", "nodeType":"output", "status":null, "payload":{...} }]
```

这是对既有 `query` 的最小扩展（一个 switch case + 已有存储端口），不破坏既有 `outputs`/`inputs`/… target，也不改变单 JSON 形态。

## 八、权衡

| 决策点 | 方案 | 取舍 |
|---|---|---|
| 归属键 | `scope.workflowId ?? taskKey`（任务隔离，可覆盖） | 默认隔离更安全；老脚本共享 `agent-round` 不受影响 |

| 与既有服务 | 复用 `RunJsonAsync`/`ReferenceGrounding`，不复制落库 | SingleImplementation、不双真源 |
| **通用逻辑下沉位置** | 翻译器/命名规则/步骤链放 `CsharpPrj/Share`，Agent 只组装 | CentralTest 可直测纯逻辑（无 UI/DB）；代价是 Share 多一个组件块，但远小于"逻辑嵌在 Agent 里、测试要拉全套装配"的成本。对齐框架既有分工（ProgressUpdater/TerminationDecider 在 Share、AgentRunner 注入消费） |
| **执行端口注入 vs 直调** | `Func<string, Task<string>>` 注入（测试桩/RunJsonAsync 均可） | 翻译器不耦合 Agent 协议面；代价是多一层间接调用，但换来可测试性与可替换性 |
| **S2 短路依赖 WriteGuardPort** | nodeType=node 且守卫已装配时 `WriteGuardPort.Put` 自动镜像图端点 → S2 跳过；否则 S2 走 addResource 补建 | 依赖既有 WriteGuardPort 行为（已核实：写透镜像白名单=仅 `node`）；守卫未装配时自动降级补建，不丢图端点 |
| **TaskGraphService 收敛** | P0 以其为参考范本，P1 后评估迁入 Share | 消除 Agent.Core 重复步骤链；代价是迁移需调整依赖方向（只引 Operation 抽象端口），但符合 SingleImplementation 收敛方向 |
| **GraphKey 复用策略** | 短期策略 B（复用模式不复用代码），长期策略 C（抽取 `ITemplateExpander<T>` 通用接口） | 短期避免引入图模型重依赖（DataFlowGraph/Placeholder 语义不匹配）；长期消除两套展开管线的设计重复。详见 §4.6 |
| **Pipeline 复用策略** | 短期策略 B（借鉴 IGraphPipelineStep 模式 + GraphPipeline 管理 API），长期策略 C（抽取 `IStep<TCtx,TResult>` + `StepCollection<T>`） | 短期数据流模型正确（扇出 vs 链式，不继承 GraphPipeline）；长期消除两套步骤容器+管理 API 重复。详见 §4.7 |

## 十、一句话总结

> **任务中心多层作用域封装框架 = 在既有 `AgentUi_RunJson` 单 JSON 协议面上，用短路步骤链（无内部可变状态）把"选中 task 作作用域"的高层命令自动展开为既有 action 的多步单 JSON**——不选作用域则 L0 原样直通（保持灵活），选中任务则一条命令自动封装多步（保持方便），三层封装逐层不越界、协议零破坏。
