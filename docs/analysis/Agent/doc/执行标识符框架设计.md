# 通用执行标识符框架设计（Execution Flag）

> **版本**：0.1（设计稿）
> **日期**：2026-08-27
> **范围**：把「`Hybrid`→LLM / `Config`/`Deterministic`→零 LLM」这种**任务级调度模式**提升为 **history / node / task 三层共用**的「执行标识符（Execution Flag）」框架：标识符反应式驱动、沿 LiteDB 引用关系传导、全局层级状态统一由标识符系统管理。
> **性质**：设计文档（本文只定方向与契约，落地见 §10 分阶段）。

---

## 0. 一句话总览

> 每个层级实体（History / Task / Node）都挂一个**执行标识符**（`ExecutionFlag`），声明它该用什么方式运行（LLM / 规则 / 确定性）。标识符是**反应式**的：一旦被设置/切换，就自动触发「解析 → 路由到已适配框架 → 运行 → 回切标准标识符」的闭环；标识符状态**落在 LiteDB 引用图资源元数据**上，并**沿 `history_owns_task` / `cross_db_link` 引用边向下传导**（history 切 → 其 tasks → 其 nodes）。从而用**一套标识符体系**统一管理所有层级的运行与状态。

---

## 1. 背景与现状（为什么需要通用化）

### 1.1 当前机制（task 级调度模式）
```
AgentTaskItem.SchedulingMode（Hybrid / Config / Deterministic，仅 task 级）
  → SchedulingModeAutonomy.RequiresLlm（仅 Hybrid=true）
  → TaskRouter.Route(item, autonomy, ruleBackend)
  → ExecutionDisposition（LlmDriven / RuleDriven）
  → ITaskExecutor（LlmTaskExecutor / RuleTaskExecutor）执行
```
依据文件：
- `CsharpPrj/Share/HierarchySupport/SchedulingMode.cs`（枚举定义，注释明确 Hybrid=LLM 导演 / Config=ur_config / Deterministic=纯规则）
- `Projects/Agent/src/Agent.Operation/Routing/SchedulingModeAutonomy.cs`（`RequiresLlm => _mode == Hybrid`）
- `CsharpPrj/Share/TaskStatusPool/Routing/TaskRouter.cs`、`ExecutionDisposition.cs`、`ITaskAutonomy.cs`
- `Projects/Agent/src/Agent.Core/TaskPool/AgentTaskPool.cs`（`Resolve()` 按 Disposition 选执行器）、`ITaskExecutor.cs`

### 1.2 现状的局限（本文要解决的问题）
| # | 局限 | 后果 |
|---|------|------|
| 1 | `SchedulingMode` **只附着在 task**（`AgentTaskItem`） | history / node 层没有执行模式概念，无法在容器/节点级声明"用 LLM 还是规则" |
| 2 | 切换 `SchedulingMode` 只是**改字段**，**非反应式** | 没有"切标识符 → 自动触发解析→路由→运行→回切"闭环 |
| 3 | 状态存在 SQL `ur_tasks` 的 `SnapshotJson`（task 载荷） | **不随 LiteDB 引用图传导**，无法"history 切 → 全部 task/node 跟着切" |
| 4 | 无**层级/批量**操作 | task 无法"选指定 nodes 或全部 nodes 改标志"；history 无法"切指定 task/nodes 状态" |
| 5 | 全局各层状态（lifecycle + mode + result）**分散管理** | 无单一标识符系统统一承载 |

---

## 2. 目标

1. **三层共用一套执行标识符**：history / node / task 都用同一 `ExecutionFlag` 词汇声明运行方式。
2. **反应式驱动**：设置/切换标识符即自动触发「后台解析 → 路由到已适配框架 → 运行 → 完成后回切标准标识符」。
3. **状态落图并传导**：标识符状态写入 **LiteDB 引用图资源元数据**，沿 `history_owns_task` / `cross_db_link` 引用边向下传导（父层标志默认作用于子层，子层可覆盖）。
4. **层级批量操作**：task 可对"指定 nodes 或全部 nodes"批量改标志；history 可对"指定 tasks / 其 nodes"切换状态。
5. **全局层级状态统一管理**：所有层级实体的生命周期（Idle/Running/Completed/Faulted）+ 运行模式（Llm/Rule/Deterministic）+ 结果，统一由标识符系统管理。

## 3. 核心概念：执行标识符（ExecutionFlag）

### 3.1 定义
**执行标识符** = 附着在 history / node / task 任一**层级实体**上、声明"该实体应如何运行"的受控词汇值。它是当前 `SchedulingMode` 的**泛化**：不再只属于 task，而是三层共用的统一概念。

```csharp
public enum ExecutionFlag
{
    Auto,          // 未显式声明 → 沿引用边继承父层（history→task→node 逐层收窄）
    Llm,           // LLM 反应式调用（自主生成 / 工具）—— 对应原 Hybrid
    Rule,          // 规则表驱动（ur_config）—— 对应原 Config
    Deterministic, // 纯规则迭代（零 LLM）—— 对应原 Deterministic
    Std,           // 标准状态 / 回切目标（运行完成后的默认落点）
}
```

> **关键**：`Llm` 把"LLM 反应式调用"本身当作一种标识符值。切到 `Llm` = 声明"该实体要接 LLM"；切到 `Rule`/`Deterministic` = 声明"零 LLM"。

### 3.2 与现有 `SchedulingMode` 的映射
| `ExecutionFlag` | `SchedulingMode` | 路由走向 |
|-----------------|------------------|----------|
| `Llm` | `Hybrid` | `LlmDriven` → `LlmTaskExecutor`（启动 LLM） |
| `Rule` | `Config` | `RuleDriven` → `RuleTaskExecutor`（零 LLM） |
| `Deterministic` | `Deterministic` | `RuleDriven` → `RuleTaskExecutor`（零 LLM） |
| `Auto` / `Std` | 未指定 | 沿引用边解析到最近的非 `Auto` 父层标志 |

映射落点：新增 `ExecutionFlagAutonomy : ITaskAutonomy`（`RequiresLlm => flag == ExecutionFlag.Llm`），与既有 `SchedulingModeAutonomy` 并存，二者都喂给同一个 `TaskRouter`。

### 3.3 实体定位（EntityRef）
三层实体统一用 `EntityRef` 定位，消除 taskKey/sessionName/historyId 混叠：

```csharp
public readonly record struct EntityRef(EntityKind Kind, string Id, string? WorkflowId = null);
// EntityKind.History | EntityKind.Task | EntityKind.Node
//   History → history.{historyId}（图资源 Id）
//   Task    → {taskKey}
//   Node    → {workflowId}.{nodeKey}
```

## 4. 三层统一标识符体系

### 4.1 层级结构（History → Task → Node）
```
History（上层容器，ExecutionFlag 默认下放）
  ├─ history_owns_task 边 ─→ Task（ExecutionFlag 可覆盖或继承）
  │     └─ cross_db_link 边 ─→ Node（ExecutionFlag 最细粒度）
  └─ 全部 Task → 全部 Node 的并集 = 该 History 的节点集（派生视图）
```

- **`Auto` 语义**：子层未显式声明时，沿引用边向上找到最近的非 `Auto` 标志作为生效值（`Node` 没声明看 `Task`，`Task` 没声明看 `History`，都没有则回退 `Deterministic` 零 LLM）。
- **覆盖语义**：`Node`/`Task` 显式声明（`Llm`/`Rule`/`Deterministic`）即覆盖父层默认，与"继承"互补。
- 复用现有层级抽象：`Operation.LoopFoldMethod.Reference.Model.IHierarchyContainer<T>`（`Children` 逐层收窄）+ `ReferenceTypes.HistoryOwnsTask` / `CrossDbLink`。

### 4.2 落库（LiteDB 引用图资源元数据）
标识符状态写入图资源 `Resource.Metadata`（`Dictionary<string, object>`，已具备）：

| 元数据键 | 值示例 | 语义 |
|---------|--------|------|
| `exec.flag` | `"Auto"`/`"Llm"`/`"Rule"`/`"Deterministic"`/`"Std"` | 声明/生效的执行标识符 |
| `exec.lifecycle` | `"idle"`/`"running"`/`"completed"`/`"faulted"` | 该实体生命周期 |
| `exec.result` | 摘要 / 引用 | 运行结果（可选） |
| `exec.parent` | `"history:demo"` / `"task:x"` | `Auto` 时解析到的父层（归因/观测） |

依据：`CsharpPrj/Share/UniversalReference/Core/Models/Resource.cs`（`Resource : ResourceData`）、`Reference/Models/ReferenceModels.cs`（`ResourceData.Metadata`）、`StorageFramework/Abstractions/IResourceReferenceStore.cs`（`UpdateResourceAsync(resourceId, metadata, ...)`）。

## 5. 反应式解析生命周期（FlagLifecycle）

核心：**设置标识符 = 触发一次"解析→路由→运行→回切"的自动闭环**（无需调用方手写各步）。这就是"标识符反应式"的落地。

```
设置/切换标识符（SetFlag）
  │  写 Resource.Metadata["exec.flag"] + ["exec.lifecycle"]="flagged"
  ▼
① 解析 Resolve(entity)
  │  沿引用边向上找最近的非 Auto 标志 → 得实际执行模式（Llm/Rule/Deterministic）
  ▼
② 路由 Route(flag)
  │  ExecutionFlagAutonomy → TaskRouter → ExecutionDisposition（LlmDriven / RuleDriven）
  ▼
③ 运行 Run()（适配框架）
  │  经 IExecutorRegistry 解析 ITaskExecutor（LlmTaskExecutor / RuleTaskExecutor）执行
  │  期间 lifecycle=running；结果写 exec.result
  ▼
④ 回切 Reset()
  │  完成后把标识符回切 Std（标准状态），lifecycle=completed/faulted
  ▼
  标准状态标识符（Idle/Std）—— 等待下一次 SetFlag
```

对应状态机（`ExecutionFlagLifecycle`）：
```
Idle ──SetFlag──▶ Flagged ──Resolve──▶ Routed ──Run──▶ Running ──完成──▶ Completed ──Reset──▶ Idle(Std)
                                    （Route 失败 → Faulted；取消 → Cancelled）
```
- **反应式触发点**：`SetFlag` / `SetFlagScope` 写入图元数据后，向后台 `FlagConductor` 发信号，自动执行 ①→④；无需调用方 await 编排。
- **运行完回切**：`Reset` 无条件把 `exec.flag` 置为 `Std`、`exec.lifecycle` 置 `idle`（或 `completed`），使实体回到"标准状态"，下次用再设标识符。

## 6. 沿 LiteDB 引用边的状态传导

### 6.1 读传导（生效标志解析）
`ResolveFlag(EntityRef)`：若自身 `exec.flag` 是 `Auto`/`Std`，沿引用边**向上游**找最近的非 `Auto` 标志：
```
Node   (Auto) → cross_db_link 入边 → Task   (Auto) → history_owns_task 入边 → History (Llm) → 生效=Llm
```
实现：`IResourceReferenceStore.GetReferencesAsync(entityId, includeIncoming: true)` 取入边 → 沿 `history_owns_task`/`cross_db_link` 逐级读 `exec.flag`；都 `Auto` → 回退 `Deterministic`（零 LLM）。

### 6.2 写传导（批量 / 层级下发）
`SetFlagScope(scope, flag)` 沿引用边**向下游**批量写 `exec.flag`：

| 作用域 | 语义 | 传导方式（沿边枚举） |
|--------|------|---------------------|
| `taskKey + nodeKeys[]` | **task 选指定 nodes 改标志** | 对每个 nodeKey 写 `cross_db_link` 下游邻接资源的 metadata |
| `taskKey`（全部 nodes） | **task 改全部 nodes 标志** | `GetReferencesAsync(task, incoming:false)` 过滤 `cross_db_link` → 全部下游 Node |
| `historyId + taskKeys[]` | **history 切指定 tasks（及其 nodes）** | 对每个 task 写 `history_owns_task` 下游；并递归其 `cross_db_link` 下游 Node |
| `historyId`（全部） | **history 切全部 tasks / nodes** | `GetTaskKeysAsync(historyId)` → 全部 task + 递归全部 node |

> 复用现有读侧枚举：`IHistoryRelationManager.GetTaskKeysAsync(historyId)`（历史归拢任务）+ `GetHistoryNodeKeysAsync(historyId, wf)`（派生节点集）+ `IResourceReferenceStore.GetReferencesAsync`（邻接遍历）。写统一走 `UpdateResourceAsync(metadata)`（唯一守卫，SingleImplementation / TH-12）。

## 7. 路由与适配框架（复用现有，不重造）

标识符"路由到已适配框架"**完全复用**现有 `TaskRouter` / `ExecutionDisposition` / `ITaskExecutor` / `IExecutorRegistry` 链路，只在其上游加一个"标识符→自主性"的适配器：

```
ExecutionFlag → ExecutionFlagAutonomy(ITaskAutonomy)      [新增，1 个适配器]
  → TaskRouter.Route(item, autonomy, ruleBackend)         [复用，不动]
  → ExecutionDisposition(LlmDriven / RuleDriven)          [复用，不动]
  → IExecutorRegistry.Resolve(handle) → ITaskExecutor     [复用，不动]
  → LlmTaskExecutor / RuleTaskExecutor / StatelessAnswer  [复用，不动]
```

- **关键**：`ExecutionFlag.Llm` 复用原 `Hybrid` 的 LLM 走法（`LlmTaskExecutor` → `AgentRunner` → `LlmStateDirector` → `LlmRoutingClient` 调 LLM）；`Rule`/`Deterministic` 走零 LLM（`RuleTaskExecutor`）。
- 对 **node / history 层**的"路由到已适配框架"：node 本身是产出单元，其"运行"是所在 task 的运行（沿 `cross_db_link` 归属到 task）；history 本身是容器，其"运行"是其 tasks 的并集。因此三层标识符最终都在**归属的 task** 处统一路由执行（标识符系统负责沿边把标志解析到 task），执行仍走既有 `ITaskExecutor`，**不新增执行引擎**。

## 8. 全局层级状态管理（由标识符系统统一承载）

所有层级实体的状态统一由标识符系统管理，单一端口 `IExecutionFlagService`：

```csharp
public interface IExecutionFlagService
{
    // 读
    ExecutionFlag? GetFlag(EntityRef entity);                 // 读自身声明标志
    Task<ExecutionFlag> ResolveFlagAsync(EntityRef entity, CancellationToken ct); // 沿边解析生效标志

    // 写（反应式）
    Task SetFlagAsync(EntityRef entity, ExecutionFlag flag, CancellationToken ct);      // 单实体 → 触发 FlagLifecycle
    Task SetFlagScopeAsync(FlagScope scope, ExecutionFlag flag, CancellationToken ct);  // 层级/批量（task选nodes / history切tasks）

    // 生命周期（FlagLifecycle 状态机）
    Task<FlagLifecycleState> StartAsync(EntityRef entity, CancellationToken ct);
    Task<FlagLifecycleState> CompleteAsync(EntityRef entity, CancellationToken ct);
    Task ResetAsync(EntityRef entity, CancellationToken ct);  // 回切 Std

    // 查询
    Task<IReadOnlyList<EntityRef>> ListFlaggedAsync(CancellationToken ct);  // 全局被标识符管理的实体
}
```

- **统一管理范围**：`exec.flag`（运行模式）+ `exec.lifecycle`（Idle/Running/Completed/Faulted）+ `exec.result`（结果）三层一起，全部存 `Resource.Metadata`、经 `FlagConductor` 驱动。
- **与既有任务池关系**：标识符系统是"声明/编排层"，最终把 `Llm`/`Rule` 落到 task 的 `SchedulingMode`（或直接喂 `ITaskAutonomy`）后，仍由既有 `TaskPool` 消费循环执行——标识符系统不替代任务池，只统一"谁用什么方式运行 + 生命周期状态"的声明与管理。
- **落位**：新增 `IExecutionFlagService` + `ExecutionFlagService`（编排，写边委托 `IResourceReferenceStore`/`IReferenceMaintenance`，SingleImplementation）+ `FlagConductor`（后台反应式驱动）+ `ExecutionFlagLifecycle`（状态机）。

## 10. 分阶段落地

| 阶段 | 内容 | 验收 |
|------|------|------|
| **P1 词汇 + 存取** | `ExecutionFlag`/`EntityRef` + 读写 `Resource.Metadata["exec.*"]` | `ExecutionFlagService.GetFlag/SetFlag` 单测；图元数据读写 OK |
| **P2 解析传导** | `ResolveFlagAsync` 沿边向上找非 Auto | node/task/history 三级继承单测（含覆盖） |
| **P3 反应式生命周期** | `FlagConductor` + `ExecutionFlagLifecycle`：Set→Resolve→Route→Run→Reset | 切换 Llm → 自动路由到 LlmTaskExecutor 并回切 Std 的集成测试 |
| **P4 层级批量** | `SetFlagScopeAsync`：task 选指定/全部 nodes；history 切指定/全部 tasks(+nodes) | 沿边批量更新断言；含 history→tasks→nodes 传导 |
| **P5 三层共用 + UI** | `AgentUi_Flag*` + `action=flag` + 模板 + 三视图联动 | 主对话框切 history/node/task 标识符即生效 |

> 每一阶段保持向后兼容：P1-P5 全程不破坏既有 `SchedulingMode`/`TaskPool` 路径（标识符系统仅在装配后作为**增强声明层**叠加，未装配则零影响、回退既有行为）。

## 附：与现有 `Hybrid/Config/Deterministic` 的衔接（不破坏）
- 标识符系统装配后，`ExecutionFlag.Llm` 落到 task 的 `SchedulingMode=Hybrid`（或直接喂 `ExecutionFlagAutonomy`），执行仍走既有 `LlmTaskExecutor`。
- 未装配标识符系统时，`SetFlagScopeAsync`/`FlagConductor` 为 no-op，既有 `SchedulingMode` 路径零回归。
- history/node 层标识符是"声明/继承"，最终收敛到归属 task 执行，**不新增执行引擎**，符合"先路由到已适配框架，再运行"。
