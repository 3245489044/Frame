> 版本：0.1（实施计划·待评审后开工）
> 上游设计：`docs/analysis/Agent/doc/线程自卫式卡死取证框架设计.md`（本节补全其“进程侧资源级取证”的实施细化）
> 关联前置（已就绪）：
> - **M1** 取证内核：`CsharpPrj/Modules/Threading/Hang/*`（`HangProbe`/`HangProbeSlot`/`StepWatchdog`/`RingBuffer`/`HangEvidenceAssembler` + 单测；`TimingDefaults.HangStall=30s`）
> - **M2** 命令级实时遥测：`CsharpPrj/Operation/BackEndDriven/CommandExecution/CommandTelemetry.cs` + `CommandCoordinator` 慢/卡死监视（15s/30s，同步+异步双路径；实时 Console + `backend_log_messages.json`；可选自动 dump）
>
> 目标验收一句话：**让“被卡线程在卡死前自己报出 phase/resource/owner”**，使 DB 读 UI 函数 vs Outbox 写者这类锁竞争，**无需离线 dump 也能给出“在等什么资源/谁持锁”线索**（dump 仍作兜底）。

## 1. 现状与差距（为什么需要 S3）

真机复现已证明 M1+M2 能实时指出“**卡在哪条命令**”：
```
[运行期诊断·卡死] 命令 #46 已停滞 30s 仍未返回: exec AgentUi_DbReadTableMarkdown
  ── 进程证据 ─────────── (命令轨迹/线程/线程池/内存) ──────────
```
但它给不出“**为什么卡 / 谁持锁**”。理由（设计稿 §4.2/§10）：托管进程内无法在 A 线程安全读取 B 线程的托管栈，当前只能靠“哪条命令 + 事后 dump”。

**S3 的目标**：引入“被卡慢路径自报告”机制 —— 每段慢路径执行时把只读 `HangProbe` 槽更新为“我在 stage X、等资源 R、持锁/Owner 是谁、自 T 起”；看门狗据此在卡死时直接给出 `probe.resource`/`owner`，从而**当场判 A(锁竞争，写者=Outbox) / B(UI 互锁) / C(其它)**，把 dump 从“必需”降为“兜底确认”。

## 2. 分层纪律与前置决策（开工前必须先定）

本仓库存在两棵树：`CsharpPrj/`（模块/Operation/读源）与 `Projects/Agent/`（Agent 运行时）。S3 的核心难点是**谁是槽类型的承载方**。

### 2.1 考察项 D1：Agent 能否编译期 `using Modules.Threading`
- `Modules.Threading` 是叶子、零外部依赖（`CsharpPrj/Modules/Threading`，net10.0）。
- 若 Agent.Core 的现有依赖链（→ StorageBridge / Operation.HierarchyMethod → `Modules.csproj` 聚合）已传递引入 `Threading`，则 Agent 侧可直接 `using Modules.Threading` 用 `HangProbeSlot`。
- **待验证命令**：在任一 Agent 编译项目里写一行引用后 `dotnet build`；或查 `dotnet msbuild … -getItem:ProjectReference` 闭包是否含 `Threading.csproj`。
- **结论 A（可引）**：Agent/读源侧直接用 `HangProbeSlot`/`HangProbe`/`TimingDefaults`，最省事。
- **结论 B（不可引 / 或遵循“Agent 不反向依赖 CsharpPrj”既定决策）**：走**中立槽/接口**——槽的类型下沉为“中立 object/接口 + 约定字段”，Agent 侧填充、读源/框架侧读取（**与既有 `RunScopeSlot` 同决策路径**，设计稿 §8/§10）。`Modules.Threading.HangProbe` 作为“框架原生实现”，Agent 侧经一个小适配器填充中立槽，或把 `HangProbe` 抽到更中立位置。
- **建议默认**：优先验证 **D1-结论 A**；A 不成立才落 B（避免造第二套取证类型）。

> **【实施快照 S3-0】D1 已验证并定为「结论 A」，无需改 csproj。** 依据：
> - Agent 全工程经 `Projects/Agent/Directory.Build.props` 的 `CsharpPrjBinaryRefs` **集中二进制清单**消费 CsharpPrj dll（方案 B，`Agent 不把 CsharpPrj 拉进自身构建图`），其中已含 `<Reference Include="Threading" HintPath="$(CsharpBuildOutputDir)\Threading.dll" Private="true" />` → `Agent.Core` 可直接 `using Modules.Threading` 用 `HangProbeSlot/HangProbe/StepWatchdog/HangEvidenceAssembler/IHangEvidenceSource`。
> - 前提：`Threading.dll` 需含 M1 `Hang/*`——已强制重编 `CsharpPrj\Modules\Threading\Threading.csproj` 烘焙（`BuildOutput\Debug\Threading.dll`），反射确认 `HangProbeSlot/HangProbe/StepWatchdog/RingBuffer/HangEvidenceAssembler/IHangEvidenceSource/HangEvidence` 等类型在位。**注意**：Agent 经 HintPath 消费，`EnsureCsharpBaked` 只在哨兵 dll 缺失时才自动重编 MainProj，不感知 Threading 内容陈旧 → 新增 CsharpPrj/Threading 类型后须先单独重编烘焙再编 Agent。
> - 落地：`RoundStepInvoker` 新增 `public HangProbeSlot? HangProbe { get; set; }`（null=no-op），`ExecuteStepAsync` 读源 `try/finally` 内 `Enter("ResolveInputs", resource:"sqlite:ur_nodes")`/`Exit`；`Agent.Core` 编译 0 错 0 警（S3-1 自报告层）。

> **【实施快照 方案甲 · 架构转向】取证收敛为框架横切，回退 Agent 侧散装。**
> - **采纳**：宿主放 `Modules.Threading.Hang`；可空 `IHangReporter` 注入 `Modules.Threading.BoundedExecution`（最底层，Agent/Produce/FileDriven 全覆盖）。
> - 已回退散装到干净基线：`RoundStepInvoker`（删 `HangProbe` 槽 + 读源手写 Enter/Exit）、`WorkflowRunner`（删 `RunObservedRoundAsync`/env 门散装）、`Agent.Core/Diagnostics/HangMonitor.cs`（删，Agent 侧散装观察器）。保留 `NodePersistOutbox` 的 `EvidenceSource` **provider**（供宿主注册）。
> - 已落框架内核（`Threading.csproj` 源码编译通过，C# 0 错；仅因本会话加载占用 DLL 未能重新烘焙落盘）：
>   - `Modules.Threading.Hang/HangForensics.cs`：`IHangReporter` + `HangForensics`（单一归口：共享槽 + 相位栈 + `StepWatchdog` + 低频采样 + `HangEvidenceAssembler` + 证据源注册 + 确证回调；只报不打断/不转 TO）。
>   - `Modules.Threading/Bounded/BoundedExecution.cs`：`CreateRoot(..., hang: IHangReporter?)` / `Derive` 传播；每个 `Run*` 进入即 `Enter(subject)`、离开 `using` 恢复/清槽；`null`=零热路径开销。
> - **待新会话完成（本会话 Debug\Threading.dll 被 LoadFrom 占用无法烘焙，依赖新符号的跨树接线无法编译验证）**：
>   1. 重新烘焙 `Threading.csproj`（落盘新 dll）；2. `ExecutionScope.CreateRoot` 转发 `hang` 到 `BoundedExecution.CreateRoot`；3. `NodeGraphOrchestrator.RunRoundAsync(..., hang)` 传入根 scope；4. Agent per-round（`WorkflowRunner`）建 `HangForensics`、注册 outbox provider、Start→run→Dispose。接线后 Agent 业务执行器/框架内不再出现任何 Hang 类型散落。

### 2.2 纪律对齐（不新增公理，不违反确定性核心）
- 只新增“读 HangProbe + 确证时写诊断/转 TO”的报告，**不触碰/不双写** `FailureBudget/ProgressToken/ControlFlag` 之外的确定性写路径（`SEP.DeterministicCoreDisjoint`；终止仍经既有引擎 `TerminationPriority` 裁决，非本框架自建写门）。
- 槽内禁放可写句柄（对齐 `AmbientSlot`/`HangProbe` 纪律）。
- 本层为工程实现，**不新增 clinerules 符号**，`references.md` 无需重编。

## 5. 配置 / 开关 / 出口（与 M2 一致的习惯）

- 阈值单源：沿用 `TimingDefaults`（`HangStall` 已有）；S3 的 LLM/暂停豁免相位建议登记为配置集合。
- 开关/调参建议沿用 env 约定：`FILEDRIVEN_HANG_DUMP`、`FILEDRIVEN_CMD_SLOW_MS/HANG_MS` 已是命令级；S3 步级阈值可独立（建议默认 ≤ 命令级，因步更细）。
  - **S3 自报告开关（本实施新增）**：`FILEDRIVEN_AGENT_HANG_PROBE=1`（Agent.Core `WorkflowRunner` 读取；默认关 = 常态零开销）。阈值沿用 `TimingDefaults.HangStall`（30s），`HangMonitor` 内置采样间隔 500ms。
- 出口双通道：实时行 Console（FileDriven 管道下即终端）+ `ur_events`/AgentLog 只增归档；自动 dump 仍为兜底开关。

## 6. 验证方法（真机 runbook）

```powershell
# 1) 复现 A 类(锁竞争) —— 用此前实际卡死的 agent_mcpinvoke_create_task_test.json；先开启 S3 自报告
$env:FILEDRIVEN_AGENT_HANG_PROBE = "1"
.\运行测试GUI模式.ps1 agent_mcpinvoke_create_task_test.json
# 期望：卡死时当场出现(不再只到“命令 #N”级)：
#   [HangDiagnostics_captured]
#     taskKey=tp_mcpinvoke_ctrl round=1 step=rule_match
#     phase=ResolveInputs resource=sqlite:ur_nodes stallMs=31200 sources=outbox={"owner":"outbox-writer:42","flushing":true,...}
#     decision=TO
# 注：read-source 若已被 _stepTimeout 有界包住，则单步超时先触发（StepTimeoutException，槽 finally Exit）→ S3 reader 判健康；
#     S3 观察器覆盖的是 `_stepTimeout`/`StallDetector` 之间的**静默区**（handler/next、未设步超时读源）——该处卡死才走上述取证。
# 2) 可选：设 FILEDRIVEN_HANG_DUMP=1，卡死后拿 dump 用 syncblk/clrstack 复核 owner 与上述一致
```

- 单元/本地可测性：`Modules.Threading` 已有单测覆盖槽/看门狗/环/装配语义（FakeClock 驱动）；S3 在 Agent 侧的改动是“薄接线”，判定逻辑仍走内核单测，Agent 侧只验证接线正确与编译。

## 7. 风险与明确不做

- **不做**：自动修复卡死 / 自动 switch；不引进程内抓他线程托管栈（保持 dump 兜底）。
- **误杀治理**：LLM/暂停门/daemon 预热相位显式豁免；WATCH 二次确认防一过性慢（`StepWatchdog` 已支持 confirmWindow）。
- **依赖方向**：D1 未定前不动 `Agent.Core` 引用；结论 B 时优先“中立槽”而非把类型下沉成重复实现（`SingleImplementation`/`RedundancyElimination`）。
- **范围**：只覆盖设计稿 A/B/C 三类已知慢路径；不做通用 UI 线程/线程池 profiler。
