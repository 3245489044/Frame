# 线程自卫式卡死取证框架设计（Thread-Self-Defensive Hang Diagnostics）

> 版本：1.0（草稿）
> 定位：跨 Agent.Core / FileDriven / BackEndDriven 的**通用运行时自卫式 debug 基建**。
> 触发场景：实测中 `tp_mcpinvoke_ctrl` 任务在 `rule_match` 步骤**静默挂死 >120s 且全程无日志**（无异常、无步超时 `StepTimeoutException`、无任何输出），由外部测试看门狗强制终止——表现为"编译全绿、运行哑挂"，根因需人工抓 dump 才能定位。
> 本框架目标：**被卡线程在卡死时能自动交出可定位的证据**，把"无声 120s"变成"一次性的结构化卡死诊断"。

---

## 1. 背景与问题定义

### 1.1 本次卡死现象的定性（锚定设计需求）

| 现象 | 推断 | 暴露的基建缺口 |
|---|---|---|
| `rule_match` 步骤仅打 `步骤开始`，随后 **120s 零输出** | 卡在某**无超时保护**的资源获取上（读源 DB 写锁竞争 / UI 封送互锁） | 无"慢路径自我报告" |
| 全程无 `StepTimeoutException` | `_stepTimeout` 未覆盖该步，或卡点在受限区间之外 | 看门狗覆盖面不全 |
| 无异常、任务状态停在 `Running` | 阻塞型（等锁/等事件），非异常型 | 无超时即无证据 |
| 需人工抓 dump 才能定性 | 进程内缺通用取证通道 | 缺自动证据装配 |

### 1.2 缺口清单（设计必须覆盖）

1. **静默卡死的自报告**：被卡线程不能只"等"，要在超过阈值时把"我卡在哪、等了多久、在等什么"写出来。
2. **跨层覆盖**：不能只护 Agent 步执行，要覆盖读源(DB)、Outbox 后台持久化、UI 封送这几条已知线程交汇带。
3. **有界但不误杀**：卡死阈值应触发**取证 + 预算终止**（转 TO 带证据），而非无限等；但要区分"真卡死"与"合法的长 LLM/暂停等待"。
4. **零健康成本**：系统健康时不产生日志/开销；取证只在慢路径触发。
5. **证据可读**：产出结构化诊断（哪个 step、哪个阶段、卡在什么资源、持锁方、最近 N 条日志、可选的线程栈近似），能直接判 A(锁竞争)/B(UI互锁)。

## 3. 现状基座（复用以对齐，不重复造）

| 现成基座 | 位置 | 可复用点 |
|---|---|---|
| `StallDetector` | `AgentRunner`（每轮 `Heartbeat`，默认 30s / 2×RoundTimeout 产卡死诊断 + `ur_events`） | 循环级心跳范式、诊断事件出口 |
| `RoundStepInvoker.RunBoundedAsync` + `StepTimeoutException` | `RoundStepInvoker.cs` | 步级有界执行范式（但当 `_stepTimeout=0`/未覆盖时不生效） |
| `OutboxWriter` / `NodePersistOutbox` 后台消费 | `RoundStepInvoker`、`NodePersistOutbox` | 后台持久化线程（已知与主读源共享存储的写者） |
| `FailureBudget` / `ProgressToken` / `TerminationPriority`（TO） | axioms/formula | 卡死归入预算终止（引擎内可判定） |
| 任务池 `WaitIfPausedAsync` 合作式暂停 | `AgentTaskPool` | "合法长等待"与"卡死"的判别参照 |

设计原则：**把"看门狗超时 → 取证 → 预算终止"做成一层横切，叠加在既有循环/步执行之上**，不侵入每段业务逻辑。

## 4. 总体设计

### 4.1 核心思想：慢路径"自我报告"，看门狗"超时取证"

- 被监控的**每段慢路径**在执行期间，把一个**只读共享的 `HangProbe` 槽**（无锁、`volatile`/不可变快照字段）更新为"我此刻在阶段 X、等待资源 R、自 T 起"。这是廉价的**进度心跳**（健康时不打日志）。
- 一个**单线程看门狗**（per-run，周期性巡检或 per-step 计时）检测"心跳停更超过阈值"。
- 停更即触发 **`EvidenceAssembler`**：读取 `HangProbe` + 最近 N 条日志环形缓冲 + DB/Outbox/UI 状态探针 → 组装证据包 → 写诊断 + `ur_events` → 按策略转 TO（预算终止）或继续等（合法长等待则重置）。

```
慢路径 (ResolveInputs / Outbox flush / UI marshal / step body)
   │ 每阶段更新 HangProbe 槽（进度心跳，零日志）
   ▼
看门狗 (per-run 单线程巡检)
   │ 心跳停更 > HangThreshold ?
   ├─ 是 → EvidenceAssembler → 证据包(结构化) → 日志 + ur_events → 转 TO / 继续等
   └─ 否 → 空闲（无开销）
```

### 4.2 为什么不用"进程内抓他线程栈"做主通道

.NET 托管进程内没有安全的方式在 A 线程读取 B 线程的托管栈（`Thread.Suspend`/栈遍历已废弃且危险）。因此**主证据 = 被卡慢路径自己的进度自报告**（它在挂起前最后更新的 `HangProbe` 就是"卡死瞬间的位置近似"）。只有当这不足以定位锁归属时，才旁路触发**离线全量 dump**（§10）作为兜底。


### 2.1 目标（In scope）
- 步骤/读源/Outbox/UI 封送四条慢路径的**进度心跳**与**超时触发取证**。
- 卡死时自动装配**结构化证据包**并写入诊断（日志 + `ur_events` 事件，符合 InformationMonotonicity 只增归档）。
- 与引擎**预算终止语义衔接**：确证卡死 → 转 TO（Budgetary，引擎内可判定），不再外部强制终止。
- 提供可选**离线全量转储**兜底（`dotnet-dump` / `SOS`），当进程内近似不足以定位锁归属时用。

### 2.2 非目标（Out of scope）
- 不承诺"在托管进程内拿到**他线程**的原始原生栈"（.NET 进程内无安全跨线程栈读取；用**进度相位近似** + 离线 dump 兜底，见 §10）。
- 不做 UI 线程/线程池的通用 profiler；只做 Agent 主循环相关慢路径。
- 不自动修复卡死（只取证 + 终止 + 归因），修复属于各慢路径自身的锁/WAL/busy_timeout 治理。

## 5. 组件清单

### 5.1 `HangProbe`（共享取证槽，只读快照，无锁）
```
public sealed record HangProbe(
    long Tick,              // 心跳时间戳（Environment.TickCount64）
    string? Phase,          // 慢路径当前阶段（如 ResolveInputs/ur_nodes 图读/Outbox flush/UI marshal）
    string? Resource,       // 等待资源（如 sqlite:ur_nodes / outbox-flush / ui-marshal:pageConversation）
    string? Owner);         // 声称持锁/进行中的写者标识（Outbox 后台线程 / UI 命令线程）
```
- 挂载点：`NodeRoundContext`（本框架作为**挂点注入每步**，与既有 `RunScopeSlot` 平行）或 step 级局部。
- 无锁：被卡线程在进入/离开慢阶段时**原子替换整个 record**（`volatile` 引用写），读者拿到的是某一瞬间的一致快照。
- **纪律**：`HangProbe` 只能承载只读/不可变快照，禁放可写句柄（对齐 `AmbientSlot` 纪律：禁放可写状态句柄防双写）。

### 5.2 `StepWatchdog`（per-run 单线程巡检 / per-step 计时）
- 复用 `StallDetector` 的心跳范式，但下沉到**步骤粒度**：每步开始时启动计时器，检测"`HangProbe.Tick` 停更 > `HangThreshold`（默认如 30s，可配）且无合法长等待标记"。
- 合法长等待豁免：任务池合作式暂停（`WaitIfPausedAsync` 阻塞期）、真实 LLM 调用（`cline_execute` 过 LLM 门）——这些是**合法等待**，看门狗应识别暂停/LLM 相位并在其内**不计**卡死（仅在暂停标记消失后仍停更才算）。
- 判别表：
  | HangProbe.Phase | 是否合法长等待 | 超时处理 |
  |---|---|---|
  | ResolveInputs（ur_nodes 读） | 否 | 卡死 → 取证 + TO |
  | Outbox flush（写者持锁） | 否（>阈值即异常写锁） | 取证（标记持锁写者）+ TO |
  | UI marshal（`UiThreadHelper`） | 否（超 5s 即异常） | 取证（标记 UI 线程忙）+ 预算终止 |
  | LLM / 暂停门 | 是 | 不计；恢复后若仍停更才算 |

### 5.3 `ProgressReporter`（横切注入，慢路径自我报告）
- 封装 `HangProbe` 槽更新：`Enter(phase, resource)` / `Update(...)` / `Exit()`。
- 注入点（不侵入业务）：
  - `NodeExecutionService.ResolveInputsAsync`（读源阶段内、ur_nodes 枚举处）

## 6. 触发与判定流程

```
StepWatchdog tick:
  stall = now - HangProbe.Tick
  if probe.Phase in {LLM, PauseGate}: reset（合法等待，不计）
  else if stall > HangThreshold:
      EvidenceAssembler.Capture()            // 取证（一次）
      → decision = Policy(stall, probe)
         TO  → 终止本轮/任务，带证据
         WATCH → 再给一个宽限窗口后二次取证（防一过性慢）
```

- **一次取证 + 二次确认**：首超取证即出证据；是否立即终止由策略定（默认转 TO，可配 WATCH 二次确认防误杀长但仍在推进的慢路径）。
- **与既有超时分层**：
  - `_stepTimeout`（RunBoundedAsync，确定性步超时，已有）——覆盖读源、抛 `StepTimeoutException`；
  - `StallDetector`（循环级心跳，已有）——覆盖整条 run 停滞；
  - **本框架 StepWatchdog（新增，带取证）**——填补二者之间的"静默无超时区"，并在任一层触发时都给**证据**而不是裸终止。

---

## 7. 取证载荷与"卡死原因"判别

设计目标是让证据包能直接判 A/B 类根因：

| 根因类 | 证据特征 |
|---|---|
| **A. DB/存储写锁竞争** | `probe.resource = sqlite:ur_nodes`、`probe.owner = outbox-writer:<id>` 或 UI 写者、`db.busy=true`；日志环显示前序 Outbox 落库/UI 批量写仍在途 |
| **B. UI 封送互锁** | `probe.phase = UI marshal`、`ui.marshalPendingMs` 持续增长、`ui.uiBusy=true`；前序日志有 UI/WebView2 线程活动 |
| **C. 合法长等待误判** | `probe.phase ∈ {LLM,PauseGate}`（框架主动豁免，不会误报） |
| **D. 静默死循环/空轮询** | `probe.phase` 快速跳变但 round 无进展 → 结合 `ProgressToken`/轮次停滞判定 |

## 8. 接入点（落地清单）

| 位置 | 接入 | 目的 |
|---|---|---|
| `RoundStepInvoker.ExecuteStepAsync` | 步边界设/清 `HangProbe`（phase=step body）；绑定 `StepWatchdog` 计时 | 步级卡死取证 |
| `NodeExecutionService.ResolveInputsAsync` | `ProgressReporter.Enter("ResolveInputs", resource)` | 读源锁竞争取证（本次 rule_match 疑点） |
| `RoundStepInvoker.OnAfterStepAsync` / `OutboxWriter` 落库 | 写者侧 `Enter("Outbox flush", owner=writerId)` | 定位后台写者持锁 |
| `UiThreadHelper.DispatchIfNeeded` | `Enter("UI marshal")` + UI 忙探针 | UI 互锁取证 |
| `NodeRoundContext` | 挂 `HangProbe` 槽 + `RunScopeSlot` 平行 | 每步共享取证槽载体 |
| `AgentRunner` 循环 | 装配 per-run `StepWatchdog`；复用 `ur_events` 出口 | 触发 + 归档 |

> 注：`HangProbe` 挂 `NodeRoundContext` 时与已加的中立 `RunScopeSlot` 平行——均只当不透明/不可变承载，不引入 Agent→CsharpPrj 反依赖（若读源侧在 CsharpPrj，则 HangProbe 类型也走"中立槽/接口"模式，见 §10 局限）。

## 9. 线程封闭与成本

- **看门狗单线程**：per-run 一个巡检线程（或复用循环内已有计时点做同步检查，优先，免新线程）。
- **进度心跳无锁**：`HangProbe` 用 `volatile` 引用原子替换；健康路径每阶段 O(1) 引用写、**零日志零分配**（除阶段边界一次 record）。
- **日志环形缓冲**：仅在取证瞬间读取；健康时只追加、不落盘。
- **不误杀**：LLM/暂停门相位显式豁免；WATCH 二次确认防一过性慢。
- **确定性核心守则**：本框架只读 `HangProbe`/诊断出口、只在确认卡死时写诊断 + 触发 TO，**不触碰/不双写 Budget/Token/Flag 之外的确定性写路径**（对齐 `SEP.DeterministicCoreDisjoint`：写诊断/终止经既有引擎裁决，非框架自建写门）。

---

## 10. 局限与兜底

1. **进程内取他线程原生栈不可行** → 主通道用进度相位自报告；若锁归属仍不定，旁路触发离线 `dotnet-dump`/`SOS` 全量转储（在超时瞬间 `dotnet-dump collect`），由诊断侧读取原生栈定性。
2. **HangProbe 挂 CsharpPrj 读源侧** → 若读源（ur_nodes 读）实现在 CsharpPrj 而 Agent 只能注入，则 `HangProbe` 用既有透明槽模式（中立 object/接口），Agent 侧填充、框架侧读取，避免反依赖（同 `RunScopeSlot` 决策路径）。

---

## 11. 与既有规范的对齐（clinerules）

- **FailureBudget / TerminationPriority（TO）**：确证卡死归入 Budgetary 预算终止，引擎内裁决、阈值到达即触发、不外置（不再依赖外部强制终止）。
- **InformationMonotonicity**：诊断事件只增归档（ur_events），证据包不覆盖旧条目。
- **StallDetector / RunBoundedAsync**：本框架在其上补"证据型"卡死终止，不替换、不重复裸终止。
- **反模式**：针对 `ANTI-NO-TERMINATION`（无终止条件循环）；不误伤 `ANTI-EXCESSIVE-SWITCH`——看门狗只产终止证据，不擅自 switch。
- **写侧单一**：证据/诊断写入口收敛到 `EvidenceAssembler` 单一出口，避免各慢路径各自写诊断漂移。

## 12. 分阶段实施建议

| 阶段 | 内容 | 验收 |
|---|---|---|
| **S1 最小取证** | `HangProbe` 槽 + `RoundStepInvoker` 步级看门狗 + `ResolveInputs` 进度报告 + 日志环 + 取证落 ur_events + 转 TO | 复现 rule_match 场景 → 自动产出含 `probe.resource=sqlite`/`owner` 的证据包并 TO 终止（不再外部强制） |
| **S2 覆盖面** | Outbox 写者自报告、UI 封送探针、LLM/暂停门豁免 | 覆盖 A/B/C 三类 |
| **S3 兜底** | 超时自动触发 `dotnet-dump` 离线转储旁路 | 锁归属可原生栈定性 |
| **S4 收敛** | 阈值配置化、WATCH 二次确认、ur_events 事件 schema 定稿 | 稳定不误杀、成本量化 |

## 13. 验收示例（期望输出）

在本次 `tp_mcpinvoke_ctrl` 复现时，期望不再是外部"120s 无输出强制终止"，而是 ~30s 内自动产出：
```
[HangDiagnostics_captured]
  taskKey=tp_mcpinvoke_ctrl round=1 step=rule_match
  probe.phase=ResolveInputs resource=sqlite:ur_nodes owner=outbox-writer:42 stallMs=31200
  db.busy=true lastLogs=[...前序 Outbox flush 在途...]
  decision=TO
```
据此可直接判 **A（DB 写锁竞争，写者=Outbox 后台线程）** 并转入各慢路径自身的锁/WAL/busy_timeout 治理，而非再次盲查。

  - `RoundStepInvoker.OnAfterStepAsync` / `OutboxWriter` 落库后台消费
  - `UiThreadHelper.DispatchIfNeeded`（UI 封送）——此处加"UI 线程忙"探针
  - `RoundStepInvoker.ExecuteStepAsync` 步边界（phase=step body）
- 健康时只做 `volatile` 引用写，**不打日志**（零健康成本）。

### 5.4 `EvidenceAssembler`（卡死证据装配）
输入：
1. `HangProbe`（当前快照 = 位置近似 + 等谁 + 多久）
2. **最近 N 条日志环形缓冲**（`RingBuffer<LogLine>`，容量如 200；只增、健康时零日志无负担；跨线程写用 `ConcurrentQueue` + 丢最旧）
3. DB 探针：`sqlite`/`INodeStore` 的 busy 状态、`busy_timeout`、当前连接是否在写（如 `IStorageCell`/存储层暴露）
4. Outbox 探针：`OutboxWriter` 当前 flush 是否在途、写者线程 id
5. UI 探针：`IUIDispatcher`/`UiThreadHelper` 是否 UI 忙、是否在 `Invoke` 等待

输出：结构化证据包（JSON 落 `ur_events` + 摘要日志）：
```
hang_evidence = {
  time, runId, taskKey, round, step,
  probe: { phase, resource, owner, stallSeconds },
  lastLogs: [ 最近 200 条 ],
  db: { busy, writerId },
  outbox: { flushing, writerId },
  ui: { marshalPendingMs, uiBusy },
  decision: TO | WATCH
}
```

### 5.5 出口与归档
- 摘要日志（一条可 grep）：`HangDiagnostics_captured` + 关键字段。
- 证据包写 `ur_events`（复用现有事件出口），符合 InformationMonotonicity 只增不丢。
- 按策略转 **TO（预算终止）**：`FailureBudget`/`TerminationPriority` 语义下，确证卡死属 Budgetary 终止，引擎内裁决、不外置（不再依赖外部 120s 强制终止）。
