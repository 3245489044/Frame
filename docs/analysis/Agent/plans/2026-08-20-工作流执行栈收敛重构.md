# 工作流执行栈收敛重构方案

> 适用范围：范围 A —— 工作流模型 / 执行栈多真源收敛。
> 产出形态：设计级方案（现状 → 目标 → 分阶段任务 → 验证 → 风险）。文档约 500 行。

## 1. 背景与动机

当前代码库中存在**两套工作流执行引擎、三处重复的工作流 DTO**，且 UI 点击一条地图在实际执行时发生了"双重跳转"。这与项目的公理（SingleImplementation / RedundancyElimination）相冲突，并带来三处可量化的成本：

1. **同一份 `WorkFlow/*.json`（如 `AgentRuntimeWorkflow.json`）存在两种不相干的消费者**，改动工作流语义时无法确定会影响哪条链路。
2. **工作流定义 DTO 三处重复**（`TConfig`、`Modules.EventFramework`、`FileDriven`），字段几乎一致，改一处另一处漂移，反序列化点分散。
3. **UI 点击经历 RGE→栈B 两次跳转**，`_stepSelector` 起点、`inputKeys`、`failedSteps`、`outputMapping`、取消等核心语义散落在栈B，栈A 只承载了一个无业务含义的"单节点壳"。

本文档给出**单一执行内核 + 单一 DTO 真源**的收敛目标，并拆解为可独立落地、每步可验证的阶段。

## 2. 现状盘点（已核实）

### 2.1 两条并行执行栈

**栈 A —— RGE / 事件绑定栈（"壳"）**

- DTO：`TConfig.WorkflowDefinitionEntry` + `WorkflowNodeEntry.ToStepDefinition()` → `StepDefinition`（RGE 可执行单元）。
  文件：`CsharpPrj/Plate/TConfig/Models/WorkflowDefinitionEntry.cs`
- 注册：`Operation/FrontEndDriven/Ports.cs:848 RegisterDeclaredWorkflows` 递归收集 UI 配置 `events.bindings.workflows` → `IEventExecutionService.RegisterWorkflows` → `FunctionHub._workflows`。
- 解析：`Share/EventBindingOrchestrator/FunctionHub/FunctionHub.cs:49 Resolve` 先查 `_workflows` 字典，再查 `ITrConfigRegistry`（找不到则 `AutoWrapAsWorkflow` 自动包装为单节点）。
- 执行：`Operation/WorkFlowMethod/WorkflowMethodExecutionService.cs:74 ExecuteWorkflowAsync` 把 `WorkflowDefinitionEntry.Nodes` → `TConfig.ExecutionPlan.Steps` → RGE 编排器 `_rgeOrchestrator.OrchestrateAsync`。

**栈 B —— StateHoldDriven 业务工作流引擎（"实"）**

- DTO：`FunctionStorage.Models.WorkflowDefinition` / `WorkflowStep`（load 用）+ StateHoldDriven 自带的 `IWorkflowDefinition` / `IWorkflowStep`（execute 用）。
- 加载：`FileDriven.Business/Workflow/WorkflowExecutionLayer.cs:53` 扫描 `WorkFlow/*.json` 反序列化为 `FunctionStorage.Models.WorkflowDefinition`，缓存。
- 执行：`WorkflowExecutionEngine.ExecuteWorkflowCore`（`StateHoldDriven/WorkflowExecution/WorkflowExecutionEngine.cs:88`）+ `WorkflowPipelineFactory`（`WorkflowPipeline.cs:33`）。
- 能力：`_stepSelector` 起点跳转、`inputKeys` 过滤、`failedSteps` 收集、失败不中断、`outputMapping` 聚合、取消贯穿。
- 外层封装：`WorkflowLibrary.cs:108 RegisterWorkflowCore` 把 `def.WorkflowName` 注册成 `Func<string,string>` 委托（调用 `WorkflowExecutionLayer.ExecuteWorkflow`）。

### 2.2 点击 `AgentRuntimeWorkflow` 的真实路径（双重跳转）

```
点击 → EventTriggerService/InvocationKernel（栈A内核）
  → FunctionHub.Resolve("AgentRuntimeWorkflow")
      → _workflows 字典? 无（UI 配置未声明 bindings.workflows）
      → _registry.Find("AgentRuntimeWorkflow")? 有（WorkflowLibrary 注册的 Func<string,string>）
      → AutoWrapAsWorkflow → 生成 1 节点工作流（FunctionName="AgentRuntimeWorkflow"）
  → WorkflowMethodExecutionService.ExecuteWorkflowAsync → RGE 编排
  → 执行节点 → 调用注册的 Func<string,string>
  → WorkflowExecutionLayer.ExecuteWorkflow(def, input)   ← 跳到栈B
  → WorkflowExecutionEngine.ExecuteWorkflowCore           ← 真正按 steps 执行
```

结论：**栈 A 只承载无业务含义的"单节点壳"，所有工作流语义都在栈 B**。这是最应消除的冗余。

### 2.3 DTO 重复清单

| 类型 | 位置 | 状态 |
|---|---|---|
| `TConfig.WorkflowDefinitionEntry` / `WorkflowNodeEntry` | `Plate/TConfig/Models/WorkflowDefinitionEntry.cs` | **保留为唯一真源** |
| `Modules.EventFramework.Models.WorkflowDefinitionEntry` | `Modules/EventFramework/Models/WorkflowDefinitionEntry.cs` | 与 TConfig 版逐字段重复（除 `ToStepDefinition` 少 `OutputTarget`），**删除候选**，需先核查引用 |
| `SharedWorkflowDefinition`（实现 `FrontEndDriven.Abstractions.IWorkflowDefinition`） | `FileDriven/FileDriven.Utilities/WorkflowExecution.cs` | grep 显示未被 `new` 实例化，**疑似死代码，核查后删除** |
| `FunctionStorage.Models.WorkflowDefinition` / `WorkflowStep` | `FunctionStorage`（FileDriven） | 栈B 执行真源，**收敛为适配到 TConfig 版** |

## 3. 目标架构（单一真源）

最终收敛为：**一套 DTO（`TConfig.WorkflowDefinitionEntry`）+ 一个执行内核（RGE 栈）**，UI 点击直接命中内核，消除双重跳转。

取舍理由——以 **RGE 栈为唯一执行内核**，而非反向：

1. RGE 直接消费 `TConfig.ExecutionPlan` / `StepDefinition`，与现代调用内核（`InvocationKernel` / `FunctionCallFacade` / 观测 / 分类）同构，长期收益最高。
2. `WorkflowDefinitionEntry` 内建 `ToExecutionPlan()` / `ToStepDefinition()`，天然可执行，不必再包 `Func<string,string>` 委托。
3. 栈B 的独立能力（`_stepSelector` 起点、`inputKeys`、`failedSteps`、失败不中断、`outputMapping`、取消）**多数已由 TConfig 的 `ExecutionPlan`/`ExecutionContext`/RGE 承担**，只需把 `_stepSelector` 起点从输入参数抽离为显式语义，做一次等价迁移即可退役栈B。

### 3.1 目标用例图（收敛后）

```
点击(AgentRuntimeWorkflow)
  → InvocationKernel / FunctionCallFacade
  → FunctionHub.Resolve
      → TConfig.WorkflowDefinitionEntry(唯一真源，由 WorkFlow/*.json 加载后注册)
  → WorkflowMethodExecutionService.ExecuteWorkflowAsync → RGE
      → 直接执行 steps（_stepSelector 由 StartStep 显式参数控制，不再包委托）
```

### 3.2 关键决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| DTO 真源 | `TConfig.WorkflowDefinitionEntry` | 内建可执行转换；与现代内核同构 |
| 唯一执行内核 | RGE 栈 | 统一观测 / 取消 / 分类；消除壳 |
| `_stepSelector` | 从 input 抽离为显式 `StartIndex` 参数 | 语义显式化，消除隐晦控制参数 |
| 栈B 引擎 | 迁移能力后退役 `WorkflowExecutionEngine` / `WorkflowPipeline` | 消除双真源 |
| WorkFlow json 加载 | 统一一个 `WorkflowLoader`（→ TConfig 版）替代 `WorkflowExecutionLayer.LoadWorkflowDefinition` | 消除分散反序列化点 |

## 6. Phase 2 —— 执行层收敛（核心）

**目标**：UI 点击直接走 RGE 内核执行步骤，退役栈B 引擎。

- [ ] **步骤 2.1 注册方式改为"注册为工作流"而非"注册委托"**
      文件：`FileDriven/FileDriven.Business/Registrations/Workflow/WorkflowLibrary.cs:108 RegisterWorkflowCore`。
      从"注册 `Func<string,string>` 委托"改为"将 `WorkflowLoader` 产出的 `TConfig.WorkflowDefinitionEntry` 注册进 FunctionHub 工作流集"（走 `IEventExecutionService.RegisterWorkflows`），删除对 `WorkflowExecutionLayer.ExecuteWorkflow` 的间接调用。
      验证：点击 `AgentRuntimeWorkflow` 不再触发 `AutoWrapAsWorkflow`（日志可见 `resolved-from-dictionary` 而非 `auto-wrapped`）；行为与栈B 等价。

- [ ] **步骤 2.2 迁移 `_stepSelector` 起点语义**
      文件：`CsharpPrj/Operation/WorkFlowMethod/WorkflowMethodExecutionService.cs:74` + TConfig 侧 `ExecutionContext` / Step 元数据。
      把 `input` 中的 `_stepSelector` 解析为 `StartIndex`，转为 `StepDefinition.Metadata["StartGreaterEqual"]`（参考栈B `WorkflowPipeline.CanExecute: index >= StartIndex` 语义在目标内核上的等价实现）。
      验证：`AgentRuntimeUI` "② 实时运行态" 组合框选择不同 step 查询，结果与原栈B 一致。

- [ ] **步骤 2.3 退役栈B 引擎**
      文件：删除或停用 `StateHoldDriven/WorkflowExecution/WorkflowExecutionEngine.cs`、`WorkflowPipeline.cs`、其中自带的 `IWorkflowDefinition`/`IWorkflowStep`/`ExecutionResult`。
      迁移取消令牌与 `failedSteps` 收集到 TConfig 执行路径。
      验证：`WorkflowExecutionLayer` 不再引用 `WorkflowExecutionEngine`（改经 `WorkflowLoader` + RGE）。

- [ ] **步骤 2.4 清理 `WorkflowExecutionLayer` 双面职责**
      文件：`FileDriven.Business/Workflow/WorkflowExecutionLayer.cs`。
      上下拆分：加载归 `WorkflowLoader`（栈A 唯一入口），执行归 RGE；删除 `_engine` 静态实例与取消令牌转发。
      验证：`WorkflowCommandCenter` / `UIToolbox` 调用 `WorkflowExecutionLayer.ExecuteWorkflow` 的入口全部改为走 RGE 路径。

1. `AgentRuntimeUI.json` 五个 tab 全部可用：

## 9. 风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| `_stepSelector`/`failedSteps` 在 RGE 栈等价物缺失 → 迁移后功能沉没 | 高 | Phase 0 能力矩阵先行；Phase 2.2 单独验证再进入 2.3 |
| `FunctionStorage.Models.WorkflowDefinition` 反向被 `RoundSpecLoader`/`StorageMigrationService` 依赖，删不动 | 中 | Phase 1.3 统一加载器先建适配层，不强制删 FileDriven 模型 |
| 两套模型并存期 `using` 冲突 | 低 | 类型别名隔离，单阶段内只改一类引用 |
| 构建连锁失败（引用未被一次性替换） | 中 | 每阶段先 `dotnet build` 红绿校验；先改文件后编译 |

**回滚策略**：迁移以"纯加法适配层 + 视觉等价"推进，删除旧引擎放在 Phase 2.3 之后；若某阶段验证不通过，保留适配层，旧引擎仍可切回（临时改回 `WorkflowLibrary` 注册委托即可）。
