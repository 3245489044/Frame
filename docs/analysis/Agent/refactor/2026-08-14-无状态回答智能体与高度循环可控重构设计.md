# 无状态回答智能体 与 高度循环可控重构 设计文档

> 日期：2026-08-14 ｜ 范围：Agent 循环引擎（Agent.Core / Agent.Axioms / Agent.Contract）+ 新智能体模块（Agent.Modules）
> 状态：设计稿（未实施）
> 关键词：无状态回答、不调用工具、支持迭代、非自主迭代、高度循环可控、循环重构

---

## 1. 背景与目标

### 1.1 需求界定

需要在 `Agent.Modules` 中构建一个**无状态回答智能体**（Stateless Answering Agent），其核心特征为：

| 特征 | 含义 | 对本设计的影响 |
|------|------|----------------|
| **无状态** | 每次回答自包含；不持久化、不建会话（无 `SessionId`）、不依赖边界框架/任务池/数据驱动层 | 循环须可"无状态装配"（关闭持久化/边界/任务池等状态特性） |
| **不调用工具** | 纯文本问答，结构上不可能触发任何工具面 | 传输走 `ILlmClient.ChatAsync`（纯聊天），**不走** `ClineAgentExecutor`/`ClineClient`（工具型编码代理） |
| **支持迭代** | 允许多轮精化（问→评→改→下一问） | 复用现有循环引擎的多轮机制 |
| **非自主迭代** | 迭代由**外部确定性规则 + 预算**控制，**不由 LLM 自主决定**继续/切换 | 循环采用确定性调度模式，禁用 LLM 导演（自主迭代源） |
| **高度循环可控** | 循环行为全部由配置/规则收敛控制，可预测、可复现 | 循环控制参数收敛为单一可控面；终止=规则命中 ∨ 预算耗尽 |

**一句话**：这是一个**零工具、无状态、但复用（并受益于）重构后确定性循环引擎**的回答型智能体——迭代由规则与预算驱动，而非 LLM 自主判断。

### 1.2 关键判断：为何不直接用一个 `AskAsync` 门面

当前 `ClineClient.AskAsync` 已能"单次提问"。但需求明确要求"**支持迭代**且**非自主迭代**"，且要"**复用现有循环**"。这决定了：

- 不能退回一个无循环的单次门面（丢迭代）；
- 也不能引入 Cline 编码代理（丢"不调用工具"）；
- 必须**复用 `AgentRunner`/`RoundLoopDriver` 确定性循环**，把"迭代"交给既有循环引擎承载，把"回答"交给纯聊天通道承载。

## 2. 现有循环架构与"自主迭代"来源

### 2.1 循环骨架

主循环唯一路径为 `AgentRunner` → `RoundLoopDriver.RunSingleRootAsync` → `SnapshotDrivenLoopEngine<AgentTaskItem, AxiomRound>`：

```
循环头 budgetTerminate（TerminationDecider 裁决）
   ↓
execute：每轮派生 AxiomContext 租约 → RoundLifecycle.RunAsync（Execute→Collect→Evaluate→Decide→Adjust）
   ↓
next：单根收割（Round/LastEval/Scope/ContinuousFailures）→ 轮后钩子（混合调度 + 运行时发布 + 边界持久化）
```

决策与终止的权威来源：
- **轮内决策**：`rule_match`（`RuleEngine`，零 LLM 规则 → continue/stop/error）+ `DecisionPoint.EvaluateRound`（`LoopDecisionMapper`）。
- **预算终止**：`TerminationDecider`（`ProgressToken`/`FailureBudget`/`ControlFlag` + `LoopDecisionConvergence`），阈值到达即触发，不外置。
- **策略/整体状态变更**：`AiSchedulerStateMachine`，导演二选一（见 2.2）。

### 2.2 "自主迭代"的精确来源

| 调度模式 | 导演 | 是否"自主" | 依赖 |
|----------|------|-----------|------|
| `SchedulingMode.Hybrid`（默认） | `LlmStateDirector`（LLM 提议自由探索 + 计算守卫） | **是（自主迭代源）** | LLM 客户端 |
| `SchedulingMode.Config` | `ConfigStateDirector`（ur_config 规则集表驱动） | 否（确定性） | `ur_config` 数据行 + 规则键 |

> 出处：`Agent.Contract/Scheduling/SchedulingMode.cs`；`AgentRunner` 在运行方法内据 `item.SchedulingMode` 构造 `AiSchedulerStateMachine` 并选导演（`LlmStateDirector` 或 `ConfigStateDirector`）。

**结论**：实现"非自主迭代 + 高度可控"的充分条件 = **循环进入非 `Hybrid` 调度模式**，使 `LlmStateDirector` 完全不被实例化；迭代只由 `rule_match` 确定性规则 + `MaxProgress`/`max_steps`/`RequestTimeout` 预算控制。

### 2.3 传输通道确认

- `ILlmClient.ChatAsync(system, user, history) → LlmResult`（`Agent.Contract/Llm`）为**纯聊天无工具**通道，唯一内置实现 `SemanticKernelLlmClient`（`Agent.Axioms/SemanticKernel`），由组合根 `LlmHosting.Configure` 装配并经 `Agent.State.LlmClientFactory.Instance` 注册（provider=`semantic`）。
- `ClineAgentExecutor`/`ClineClient` 为**工具型编码代理**通道，本智能体**不采用**。

## 3. 现有循环问题分析（为何需先重构）

在接入"高度循环可控"智能体前，循环引擎存在以下结构性障碍：

### 3.1 决策路径纠缠（自主 vs 受控未正交）

`AiSchedulerStateMachine` 把 `LlmStateDirector`（自主）与 `ConfigStateDirector`（受控）耦合在同一状态机；`SchedulingMode` 只有 `Hybrid`/`Config` 两值。无状态回答**不需要任何"策略调度"**，但当前没有"纯规则迭代、禁调度器自主变更"的干净模式——`Config` 导演还强制依赖 `ur_config` 数据行（较重、需落库）。

### 3.2 循环控制参数分散

控制迭代的开关散落在多个载体：`IAgentLoopConfig`（`MaxProgress`/`RequestTimeout`/`RetryLimit`/`LoopScope`）、`RuleSet.Guards.MaxSteps`、`agent-config.json`、任务级 `AgentTaskItem.SchedulingMode`。对"高度可控"目标，缺乏**单一可控面**统一表达"一轮做什么、何时停、最多几轮、失败如何"。

### 3.3 规则集面向编程任务，不适用于回答质量

`rule_match` 默认 `RuleSet.Default` 内嵌规则基于**文本关键词**（"完成"/"DONE"/"尚未完成"等），面向编程/工具型任务；对"回答是否达标"（质量/完整度/是否需精化）的判断无现成规则，且规则集**硬绑单一默认**，无法按智能体类型注入。

### 3.4 无"无状态便捷装配"

`AgentRunnerAssemblyInput` 虽已使 persistence/boundary/taskpool 可空，但没有一条**显式的"无状态回答装配"**路径——当前只存在完整的重装配（StateCenter + 边界 + 持久化 + 运行时 + 调度器 + 节点存储），对新智能体是心智与资源负担。

### 3.5 终止与"未达标"的语义鸿沟

预算终止（`MaxProgress` 耗尽）当前收敛为 `TO`；但回答型场景"未在预算内给出满意答案"与"确已达成答案"需结构化区分，供调用方判定是否应返回部分结果。

## 4. Phase 1 — 循环整体优化重构（前置）

> 目标：把循环引擎抽象成**"自主迭代"与"确定性受控"两条正交路径**，并收敛循环控制为单一可控面。本次重构**只改造现有循环的抽象与装配，不改变既有默认行为**（`Hybrid` 仍为默认，向后兼容）。

### 4.1 重构点 R1：扩展调度模式为三态，新增"确定性规则驱动"模式

**现状**：`SchedulingMode { Hybrid, Config }`；`Config` 依赖 `ur_config` 数据行。

**改动**：新增 `SchedulingMode.Deterministic`：

```csharp
public enum SchedulingMode
{
    Hybrid,       // LLM 导演（自主迭代源）—— 现状默认，保留
    Config,       // 配置式导演（ur_config 规则表驱动，零 LLM）—— 保留
    Deterministic // 纯规则迭代：无 LLM 导演、无 ur_config 依赖；迭代仅由 rule_match + 预算驱动
}
```

- `AiSchedulerStateMachine` 对 `Deterministic` 注入 `NoopStateDirector`（**不实例化任何 `IStateDirector`**），即"不做整体状态变更/策略切换"——消除 LLM 自主迭代与策略自主切换。
- `Config` 语义不变（面向需要"配置式导演"调整策略的场景）。
- 兼容：`CreateItem(userInput, taskKey, schedulingMode, schedulerRulesKey)` 缺省仍 `Hybrid`；存量 `SchedulingMode` 序列化值不受影响（新增枚举值不破坏旧值）。

**为何不直接用 `Config`**：`Config` 的导演语义是"**调整整体状态/策略**"，且依赖 `ur_config` 数据行（需落库）。无状态回答**不需要任何策略调度**，只需"规则驱动 continue/stop + 预算终止"。`Deterministic` 用 `NoopStateDirector` 明确表达"禁调度器自主变更"，规则职责完全交给 `rule_match`，且零落库依赖。

### 4.2 重构点 R2：循环控制收敛为单一可控面

**现状**：控制分散于 `IAgentLoopConfig` / `RuleSet.Guards` / `agent-config.json` / `AgentTaskItem.SchedulingMode`。

**改动**：扩展 `IAgentLoopConfig` 增加"无状态回答型"控制字段（均缺省保默认）：

```csharp
public interface IAgentLoopConfig
{
    int MaxProgress { get; }          // 已有：迭代轮次上限（ProgressToken）
    TimeSpan RequestTimeout { get; }  // 已有：整轮绝对超时
    Scope LoopScope { get; }          // 已有：错误动作作用域
    int RetryLimit { get; }           // 已有：重试上限

    // 新增（可选，缺省 null/默认值）
    SchedulingMode SchedulingMode { get; }        // 缺省 Hybrid（向后兼容）；无状态回答=Deterministic
    string? StopRuleSetKey { get; }               // rule_match 规则集引用；null=RuleSet.Default
}
```

- `AgentLoopConfig`（`Agent.Axioms/Loops`）实现上述字段，供 Profile / `agent-config.json` 统一覆写。
- **单一可控面原则**：一轮做什么（骨架步骤，声明式）＋何时停（规则集）＋最多几轮（`MaxProgress`）＋整体预算（`RequestTimeout`/`RetryLimit`）全部经一个配置对象表达。

### 4.3 重构点 R3：rule_match 规则集可注入，支持"回答质量"规则

**现状**：`RuleEngine.Evaluate` 硬绑 `RuleSet.Default`（内嵌文本规则，面向编程任务）。

**改动**：
- `RuleMatchFunction` / `RuleEngine` 支持按 `StopRuleSetKey` 加载具名规则集（`RuleSet.Load(name)`，缺省 `RuleSet.Default`）。
- 新增内置**回答型规则集模板**（`stop_rule_quality`），判断依据不限于关键词，可组合结构化字段（如 `exec_result.ok`、`result.meta.answerAccepted`、`round`），示例：

```jsonc
{
  "version": "1.0.0",
  "guards": { "max_steps": 3 },
  "rules": [
    { "name": "answer_accepted", "condition": { "field": "result.meta.answerAccepted", "op": "==", "value": true }, "action": "stop", "reason": "答案已达标" },
    { "name": "answer_failed",   "condition": { "field": "exec_result.ok", "op": "==", "value": false }, "action": "error", "reason": "回答失败" },
    { "name": "max_reached",     "condition": { "field": "round", "op": ">=", "value": 3 }, "action": "stop", "reason": "已达迭代上限，返回部分结果" },
    { "name": "default",         "condition": "true", "action": "continue", "reason": "未达标，继续精化" }
  ]
}
```

> 说明：`answerAccepted` 等结构化标记由**回答执行器**在每轮产出（见 §5），`rule_match` 据此确定性判定，**不依赖 LLM 自主判断是否继续**。

### 4.4 重构点 R4：提供"无状态回答"便捷装配路径

**现状**：仅有完整重装配（`AgentRunnerAssemblyInput` 全量 + StateCenter + 边界 + 持久化 + 调度器 + 节点存储）。

**改动**：新增轻量装配工厂（如 `StatelessLoopAssembly`），仅装配无状态回答所需的最小依赖：

- `IAgentLoopConfig`（`SchedulingMode=Deterministic`、`StopRuleSetKey=stop_rule_quality`、紧 `RequestTimeout`）
- 共享 `ILlmClient`（复用 `LlmClientFactory.Instance.Get("semantic")` 或注入实例）
- `StateCenter` 用**内存 StorageCell 兜底**（每轮派生租约用，不落盘）
- **显式关闭**：`Boundary=null`、`PersistenceStore=null`、`TaskPool=null`、`Reactive=null`、`RuntimeState=null`、`NodeStores=null`

即：无会话、无持久化、无边界、无任务池、无节点关系——"无状态"在此得到装配层保证。

### 4.5 重构点 R5：终止结果区分"已达成"与"预算耗尽但未达标"

**现状**：预算耗尽统一 `TO`，无"部分结果"结构化载体。

**改动**：`AxiomLoopResult`/结果模型补充结构化终止信息——`StopReason`（`AnswerAccepted` / `BudgetExhausted` / `Failed` / `Cancelled`）＋每轮 `round` 产出（含最终文本），供调用方在预算耗尽时决定"返回部分答案还是报失败"。**不改变** `TerminationPriority` 的裁决语义（阈值到达即触发、不外置），仅新增可观测归因。

### 4.6 重构范围与兼容性

- 改动面：`Agent.Contract`（`SchedulingMode`、`IAgentLoopConfig`）、`Agent.Axioms`（`AgentLoopConfig`、`RuleEngine`/`RuleSet`）、`Agent.Core`（`AgentRunner` 导演选择、`RuleMatchFunction`）、`Agent.State`（`NoopStateDirector`，或放 `Agent.Axioms/Scheduling`）。
- **向后兼容**：`Hybrid` 缺省不变；`Config` 语义不变；新增枚举值/字段全为可选扩展；既有装配路径不触碰。
- **回归**：`Agent.sln` 全量构建；既有 `cline_smoke_test`/`cline_browser_test` 回归；无状态回答冒烟（§6）。

## 5. Phase 2 — 无状态回答智能体设计（复用重构后循环）

### 5.1 总体形态

```
调用方 → StatelessAnswerAgent.AnswerAsync(question, options, ct)
            │
            ▼
   StatelessAnswerExecutor（IAgentExecutor，Name="stateless-answer"）
            │  单轮：拼纯文本提示 → ILlmClient.ChatAsync（零工具）→ 结构化结果
            ▼
   RoundLoopDriver.RunSingleRootAsync（复用现有循环）
            │  五步 RoundLifecycle（Execute→Collect→Evaluate→Decide→Adjust）
            │  调度模式 = Deterministic（NoopStateDirector，禁 LLM 自主迭代）
            │  终止 = rule_match(stop_rule_quality) ∨ MaxProgress/RequestTimeout 预算
            ▼
   StatelessAnswerResult（FinalText、Rounds、StopReason、Token 用量）
```

**三个正交保证**：
1. **不调用工具**：单轮执行器只调 `ILlmClient.ChatAsync`，无任何工具/插件面；不实例化 Cline。
2. **支持迭代**：多轮精化由循环引擎承载；每轮把"上轮回答 + 精化指令"拼入下一轮 user 提示。
3. **非自主迭代**：调度模式 `Deterministic`（无 LLM 导演）；continue/stop 全由 `rule_match` 规则 + 预算裁决，LLM 不参与"是否继续"决策。

### 5.2 文件布局（`Agent.Modules/StatelessAnswer/`）

| 文件 | 职责 |
|------|------|
| `StatelessAnswerModels.cs` | `StatelessAnswerRequest`（question、System、MaxRounds、RequestTimeout、Model/Provider、StopRuleSetKey）、`StatelessAnswerRound`（round、prompt、answer、answerAccepted、tokens）、`StatelessAnswerResult`（FinalText、Rounds、StopReason、IsAccepted、Error）、`StatelessAnswerStopReason`（`AnswerAccepted/BudgetExhausted/Failed/Cancelled`）。 |
| `StatelessAnswerExecutor.cs` | `StatelessAnswerExecutor : IAgentExecutor`（`Name="stateless-answer"`）。单轮动作：把 `AgentExecutorRequest`（或纯问题）合成单条纯文本提示 → 经共享 `ILlmClient.ChatAsync` 执行 → 从 `LlmResult` 产出结构化结果，并回写 `answerAccepted`/`round` 等字段供 `rule_match` 判定。**零工具**。 |
| `StatelessAnswerLoop.cs` | 复用 `RoundLoopDriver.RunSingleRootAsync` 的封装：注入 `executeStep=StatelessAnswerExecutor`、`evaluate=DecisionPoint.EvaluateRound`、`onRoundCompleted`（轮后把本轮回答并入下轮提示的"精化指令"）。 |
| `StatelessAnswerAgent.cs` | 对外门面 `AnswerAsync(question, options, ct)`：构造最小无状态装配（§4.4）→ 驱动 `StatelessAnswerLoop` → 返回 `StatelessAnswerResult`。每次调用自包含，无会话延续。 |
| `StatelessAnswerModule.cs` | 显式装配入口（镜像 `ClineModule`）：解析共享 `ILlmClient` → 注册命名执行器（供调度器按名选中）。 |

### 5.3 单轮执行器语义（无工具、可评估）

```csharp
public sealed class StatelessAnswerExecutor : IAgentExecutor
{
    private readonly ILlmClient _llm;   // ChatAsync 纯聊天通道
    public string Name => "stateless-answer";

    public async Task<ClineResult> ExecuteAsync(AgentExecutorRequest request, CancellationToken ct)
    {
        var prompt = ComposeAnswerPrompt(request);          // System + 逐条 user（含上轮回答+精化指令）
        var r = await _llm.ChatAsync(request.System, prompt, ct: ct);
        if (!r.IsSuccess) return ClineResult.Fail(r.Error ?? "回答调用失败");
        // 产出结构化结果 + 供 rule_match 判定是否达标的标记
        //   answerAccepted：可由调用方显式置位（options.AcceptWhen），或经规则集/阈值确定性推断（见下）
        return new ClineResult(Ok: true, Text: r.Content, MessageCount: 1);
    }
}
```

> **answerAccepted 的确定性来源（非 LLM 自主）**：规则判定不依赖 LLM 打分。可选任一：
> - **配置式接受条件**：调用方在 `StatelessAnswerRequest` 指定（如"首个非空回答即接受"，或"答案达到 minLength/包含某标记"），由 `rule_match` 结构字段判定；
> - **外部质量评估器（可选）**：接入 `StateValidity`/护栏做确定性质检，产出 `answerAccepted`；
> - **纯预算**：不做接受判定，仅 `MaxRounds` 到达即返回部分结果（`BudgetExhausted`）。
> 三者的共同点：**都不让 LLM 自主决定"要不要继续"**，只让 LLM 产文本。

### 5.4 迭代精化（问→评→改→下一问）

`StatelessAnswerLoop` 在每轮结束后，把 `上一轮回答` 与 `精化指令` 追加为下一轮 user 内容：

```
Round 1: user = question                       → answer1
Round 2: user = question + "[上轮回答]..." + "请复核并改进不足" → answer2
Round 3: ...（最多 MaxRounds 轮；规则命中 answerAccepted 即提前 stop）
```

迭代轮次**由 `rule_match` 规则（continue/stop）与 `MaxProgress`/`max_steps` 预算共同决定**，确定性、可复现。

### 5.5 配置接线（Agent.Launcher）

- `AgentConfig` 增开关 `RegisterStatelessAnswer`（默认 true）＋ `StatelessAnswer` 节：`MaxRounds`（≤ `MaxProgress`）、`RequestTimeout`、`SystemPromptTemplate`、`StopRuleSetKey="stop_rule_quality"`、`Model/Provider`（复用 `AgentLlmConfig` 凭据兜底）。
- `AgentOptionalModules.Register` 中调用 `StatelessAnswerModule.Register(orchestrator, config)`：经 `LlmHosting.Configure`/`LlmClientFactory` 解析 `ILlmClient` → 注册 `StatelessAnswerExecutor`（`Name="stateless-answer"`）→ 可按 `AgentConfig.Agents` 表多实例装配（每实例独立 LLM 参数）。
- 可选：暴露 `Stateless_Answer` 工作流函数供脚本/UI 调用（复用 `WorkflowAsyncFunctionHelper` 注册，镜像 `Cline_Ask`）。

| 4 | 迭代受控 | 复杂问题在多轮下返回精化结果；`MaxRounds=1` 时单轮即止；`stop_rule_quality` 命中 `answerAccepted` 提前 stop |

| 7 | 预算终止归因 | 预算耗尽返回 `BudgetExhausted` 且携带最终文本（调用方可决定返回部分结果） |

## 7. 里程碑与依赖

| 里程碑 | 内容 | 依赖 |
|--------|------|------|
| M1（Phase 1 前置） | R1 `SchedulingMode.Deterministic` + `NoopStateDirector`；R2 `IAgentLoopConfig` 扩展 | 循环引擎回归 |
| M2（Phase 1 前置） | R3 规则集可注入 + `stop_rule_quality`；R5 终止归因 | M1 |
| M3（Phase 1 前置） | R4 无状态便捷装配路径 | M1/M2 |
| M4（Phase 2） | `StatelessAnswer/` 模块（执行器 + 循环封装 + 门面 + 装配） | M3 |
| M5 | Launcher 接线（`RegisterStatelessAnswer` 配置 + `AgentOptionalModules`） | M4 |
| M6 | 验证（§6）+ 文档补全 | M5 |

**关键依赖/风险**：
- `SchedulingMode.Deterministic` 需在 `AgentRunner` 导演选择点扩展（R1），是 M1 的硬前置；`NoopStateDirector` 必须确保**完全不触发** `AiSchedulerStateMachine.AdvanceAsync` 的 LLM 调用。
- `rule_match` 规则集按键注入（R3）需保持 `RuleSet.Default` 语义不变，避免影响既有编程任务路径。
- "无状态"的装配层保证（R4）依赖既有端口可空设计，已具备，只需收敛为显式便捷路径。

## 8. 附录：与既有智能体形态的对照

| 维度 | Cline 编码代理 | 无状态回答智能体 |
|------|---------------|------------------|
| 传输 | `ClineClient`/`ClineAgentExecutor`（工具型） | `ILlmClient.ChatAsync`（纯聊天，零工具） |

| 状态 | 会话续跑（`SessionId`）、持久化、边界、任务池 | 无状态：无会话/无持久化/无边界/无任务池 |
| 迭代 | LLM 自主决策 + 规则 + 预算 | 纯规则 + 预算（LLM 仅产文本） |
| 结果 | `ClineResult`（失败阶段/空结果归因） | `StatelessAnswerResult`（轮次/达标/终止归因） |
