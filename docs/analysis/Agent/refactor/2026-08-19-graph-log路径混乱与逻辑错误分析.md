# 图库（graph-log.db）路径混乱与逻辑错误分析

> **日期**：2026-08-19
> **范围**：排查「LiteDB 引用关系为什么同时落在 `Agent/data/graph-log.db` 与 `Agent/data/graph-log-log.db` 两个库，且 AgentRuntimeUI 加载不出数据库」。
> **结论先行**：Agent 运行时装配出**两个独立的 `ReferenceGraphCoordinator` 实例**（各自开一个 LiteDB 图库文件），图库路径又依赖**相对路径 + 当前工作目录**解析，导致两条装配路径落到不同文件；UI 读路径与写路径指向不同 coordinator，进而「UI 读不到测试写的引用」。`graph-log-log.db` 现已是损坏文件（LiteDB 无法打开），存在并发双写损坏风险。
> **依据**：`DatabaseBootstrapper.cs`、`AgentFrameworkAssembler.cs`（`FrameworkResourceGraphStage`）、`AgentUiHost.cs`、`AgentUiLibraryDb.cs`、`AgentUiLibraryData.cs`、`ReferenceGraphCoordinator.cs`、`PersistenceHelper.cs`、`SqliteConnectionFactory.cs`、`AgentConfig.cs`、`agent-config.json`，以及 `Agent/data/` 三个 `.db` 文件实测。

---

## 一、现状（已实测）

`Agent/data/` 目录当前有三个数据库文件：

| 文件 | 大小 | 上次写入 | 观察 |
|------|------|---------|------|
| `agent.db` | 40 KB | 2026-08-18 23:22 | SQLite 骨干（`ur_tasks`/`ur_nodes`，正常） |
| `graph-log.db` | 90 KB | 2026-08-19 00:03 | LiteDB，**被运行中的 GUI 进程占用（文件锁）**；只读可打开：`ur_references`/`ur_resources`/`ur_endpoints` |
| `graph-log-log.db` | 376 KB | 2026-08-19 00:09 | **LiteDB 打开失败：`Ticks must be between DateTime.MinValue.Ticks and DateTime.MaxValue.Ticks`（损坏）**；本次引用测试实际写入的库 |

关键事实：

1. **两个 LiteDB 图库并存**，且都在持续各自写入（`graph-log.db` 在 00:03 更新、`graph-log-log.db` 在 00:09 更新——正是本次引用测试运行时刻）。
2. **`graph-log-log.db` 损坏**：用 LiteDB 5.0.21 以只读模式打开即抛 `Ticks` 越界异常——典型的多写者碰撞/半写文件症状。
3. **测试引用写进了 `graph-log-log.db`**（mtime 00:09 与测试时刻吻合），而 AgentRuntimeUI 的图读取走的是 `graph-log.db` → 因而「UI 读不到引用」。

---

## 二、根因（逻辑错误清单）

### 错误 1：两个装配路径各自创建独立的图协调器（两个库）
`DatabaseBootstrapper.TryBootstrapAsync`（DB-only）与 `AgentFrameworkAssembler.FrameworkResourceGraphStage`（框架路径）**各自调用 `DatabaseBootstrapper.CreateGraphStoreAsync`，各自 `new` 一个 `ReferenceGraphCoordinator`，各自打开一个 `LiteDatabase`**：

- DB-only → `AgentUiHost.Database.Resources`（coordinator A）→ `graph-log.db`
- 框架 → `AgentUiHost.ReferenceGrounding.Graph`（coordinator B）→ 另一图库

这与「唯一 owner = ReferenceGraphCoordinator、只在一处读写 LiteDB」的**设计原则矛盾**——原则约束的是“类实现单一”，**接线层面却产生了两个实例/两个文件**。`AgentUiHost` 提供 `Database` 与 `ReferenceGrounding` 两个正交槽位，但没有保证两者持有**同一个** coordinator。

### 错误 2：图库路径基于「相对 SQLite 路径 + 当前工作目录」解析，随装配路径漂移
`DatabaseBootstrapper.ResolveGraphLogPath`：

```csharp
var sqlitePath = new SqliteConnectionFactory(config.Persistence).DatabasePath; // = "Agent/data/agent.db"（相对）
return Path.Combine(Path.GetDirectoryName(Path.GetFullPath(sqlitePath))!, "graph-log.db");
```

- `agent-config.json` 里 `Persistence.DatabasePath = "Agent/data/agent.db"` 是**相对路径**；`SqliteConnectionFactory.DatabasePath` 原样返回相对路径。
- `Path.GetFullPath(sqlitePath)` 按**当前工作目录（CWD）**解析。两条装配路径若起始 CWD 或 `configDirectory` 不同（DB-only 用 `ResolveConfigDirectory`，框架用 `cfg.ConfigDirectory`），`GetFullPath` 结果就不同，图库目录随之漂移。
- `graph-log` 作为字符串**在全部源码中无字面量**（grep 仅命中文档），图库文件名完全由上述动态拼接产出——**拼错一个环节就产生 `graph-log-log.db` 这类乖张文件名**。`ResolveGraphLogPath` 本身只能产出 `<目录>\graph-log.db`（恒为 `graph-log.db`），因此 `graph-log-log.db` 来自另一条/旧路径或二次拼接，属于路径逻辑混乱的游离产物。

### 错误 3：UI 读路径与写路径指向不同 coordinator（读不到）
- **写/测试路径**：`AgentUiLibraryData.WriteStore(db) = AgentUiHost.ReferenceGrounding?.Graph ?? db.Resources`。框架装配了守卫时一律走 `ReferenceGrounding.Graph`（coordinator B，`graph-log-log.db`）。
- **UI 读路径**：`AgentUiLibraryDb.GraphCoordinator() = AgentUiHost.Database?.Resources`（coordinator A，`graph-log.db`）。

读写分属两个库，故「测试写入引用 → UI 查 `graph` 看不到」。

### 错误 4：无单实例/单文件守护，存在并发双写损坏
`graph-log-log.db` 已损坏（LiteDB 打开报 `Ticks` 越界），典型是**两个 `LiteDatabase` 写者打开同一文件碰撞**或半写文件。LiteDB 5 默认独占打开，若 DB-only 与框架曾尝试开同一个 `graph-log.db`，第二个会锁冲突——于是「吞异常 / 另起一个文件」导致文件分裂与损坏。`DatabaseBootstrapper.TryBootstrapAsync` 对图库打开失败仅 `catch` 返回 null（降级为“数据库未装配”），**不暴露“图库文件损坏/路径分裂”的真实原因**，进一步掩盖问题。

## 三、证据链

| # | 证据 | 结论 |
|---|------|------|
| 1 | `Agent/data/` 三个 `.db`，`graph-log.db` 被 GUI 进程锁 | 两个 coordinator 各占一个 LiteDB 文件 |
| 2 | `graph-log-log.db` mtime 00:09 与引用测试时刻吻合；`graph-log.db` mtime 00:03（早于测试） | 测试写进 `graph-log-log.db` |
| 3 | LiteDB 只读打开 `graph-log-log.db` 抛 `Ticks` 越界 | `graph-log-log.db` 已损坏 |
| 4 | `FrameworkResourceGraphStage` 与 `TryBootstrapAsync` 均调 `CreateGraphStoreAsync` | 两个独立 coordinator 实例 |
| 5 | `AgentUiLibraryData.WriteStore=ReferenceGrounding.Graph` vs `AgentUiLibraryDb.GraphCoordinator=Database.Resources` | 读写分属不同 coordinator/库 |
| 6 | `Persistence.DatabasePath="Agent/data/agent.db"`（相对）+ `ResolveGraphLogPath` 用 `Path.GetFullPath` | 图库路径随 CWD/配置目录漂移 |
| 7 | 全源码无 `graph-log` 字面量；`ResolveGraphLogPath` 恒产出 `<dir>\graph-log.db` | `graph-log-log.db` 为路径逻辑混乱的游离/损坏产物 |

## 四、影响

- **数据分裂**：DB-only 与框架各写一个图库，引用关系无法汇总，图算法/影响链检索按 coordinator 分叉。
- **UI 读不到**：AgentRuntimeUI 的「载入表 graph」读 `graph-log.db`（多为空/旧数据），看不到框架侧 `graph-log-log.db` 的引用。
- **损坏风险**：`graph-log-log.db` 已无法打开；若继续双写可能再次损坏。
- **不可复现/难诊断**：路径依赖 CWD，换启动方式就换库，问题表象漂移；图库打开失败被静默吞掉。

---

## 五、修复建议（P0 收敛）

1. **图库路径改为显式绝对 + 单点解析**：不再用 `Path.GetFullPath(相对)`，从仓库根或 `configDirectory` 解析出绝对 SQLite 路径，再据此**唯一**生成 `graph-log.db` 绝对路径；`ResolveGraphLogPath` 收敛为单一入口，禁止二次拼接。
2. **消除双 coordinator**：`AgentUiHost.Database.Resources` 与 `AgentUiHost.ReferenceGrounding.Graph` 必须指向**同一个** `ReferenceGraphCoordinator` 实例（`AttachDatabase` 复用框架装配的 coordinator，不再各自 `CreateGraphStoreAsync`）。
3. **装配期单实例断言**：框架装配后校验 `Database.Resources == ReferenceGrounding.Graph`（引用相等），不等则 fail-fast，防再次分裂。
4. **现库修复/迁移**：以 `graph-log.db` 为权威，图库可重建——清空后 `graph.rebuild`（`ReferenceGrounding.RebuildAllAsync`）从 SQL 权威收敛；删除损坏/游离的 `graph-log-log.db`（迁移前先备份）。
5. **暴露失败语义**：图库打开/损坏不静默降级，输出明确诊断（路径 + 文件 + 异常），便于定位。
