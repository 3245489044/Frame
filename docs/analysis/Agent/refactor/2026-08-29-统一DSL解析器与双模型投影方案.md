# 统一 DSL 解析器与双模型投影方案（L0 对齐 L1/L2）

> **日期**：2026-08-29　**状态**：方案（待评审）
> **范围**：`CsharpPrj/Plate/DslMethod` + `Projects/Agent/src/Agent.Operation/Prompts` + `Projects/Agent/src/Agent.Axioms/Prompts` + `Projects/Agent/src/Agent.Core/Prompts`
> **关联**：`Projects/Agent/doc/Agent框架-Skill-Prompt-DSL综合机制.md`（现状梳理）· `docs/analysis/Agent/refactor/2026-08-09-提示词管理整理优化方案.md` · `docs/analysis/Agent/refactor/2026-08-09-dsl-axiom-modularization.md`
> **目标**：把 clinerules 声明 DSL 与提示词协议 DSL 合并为**一套文法 + 一个解析器**（`Plate.DslMethod.DslParser` 为唯一解析器）；`PromptProtocol` / `PromptFormatSpec` 降级为统一中间模型（`DslDocument`）的**投影**；**L0 各段对齐 L1/L2**，也经同一解析器获得**运行期结构化模型**。

---

## 一、背景与问题

当前系统存在**两套 DSL**（同源前缀记号、但三个独立解析器、三套独立模型）：

| | ① clinerules 声明 DSL | ② 提示词协议 DSL |
|---|---|---|
| 用途 | 声明逻辑/公理/契约/类型/门/状态机/算子/策略/Schema/引用 | 声明提示词分层协议（L1/L2 模板/slots/生成配置/replan/输出 Schema） |
| 解析器 | `Plate.DslMethod.Parsing.DslParser` | `Agent.Operation.Prompts.PromptDslParser` + `FormatSpecParser` |
| 产出模型 | `DslDocument` | `PromptProtocol` / `PromptFormatSpec` |
| 运行期/构建期 | **构建期**（AxiomCodeGenerator 生成公理）+ `.clinerules` 校验 | **运行期**（provide_prompt 装配/生成/校验） |
| 所在文本 | `.clinerules/*.md` + Agent L0 段 + `rare/boundaries` | `internal/l1l2` + `l0-format`（`[Schema]`） |

**根因**：两套 DSL 的前缀记号都源自 `Plate.DslMethod.DslConstants` 注册表（`[AX]/[Gate]/[SM]/[Def]/[Schema]/%` 等），但 Agent 侧 `PromptDslParser`/`FormatSpecParser` **未复用** `DslParser`，而是各自手写轻量解析器（只依赖 `Modules.Parsing.TextScan`），聚焦运行期提示词协议语义。形成"**一套记号、双解析实现、双模型**"，三处维护。

**由此带来的问题**：
1. **L0 未对齐 L1/L2**：L1/L2 运行期解析出 `PromptProtocol`（模板/slots/replan 被代码消费）；而 **L0 各段（l0-system/l0-loop/l0-logic）运行期完全不解析**，`PromptCatalog.LoadL0` 仅 `ReadSkillBody → AppendLine` 拼成纯文本给模型读，引擎得不到任何 L0 结构化视图（仅 format 段 `[Schema]` 被 `FormatSpecParser` 解析）。
2. **解析器三处并存**：同一批前缀记号有三套解析逻辑（`DslParser`/`PromptDslParser`/`FormatSpecParser`），语义易漂移（如 `[SM]` 在 DslParser 是通用状态机声明、在 PromptDslParser 是模板块；`[Schema]` 已在 DslConstants 注册但运行期未走 Plate 管线）。
3. **无统一治理**：L0 的 `[AX]/[Gate]/[SM]` 运行期不可见，无法做运行期校验（未引用声明/漂移/装配一致性）。

## 二、目标与非目标

### 目标（Go）
- **一套 DSL 文法**：clinerules 声明 DSL 与提示词协议 DSL 合并为单一文法，前缀/`|`/`→`/`[CR]`/fenced/slots/`%`/`[Schema]` 统一规则。
- **一个解析器**：`Plate.DslMethod.DslParser` 成为唯一解析器，吸收 fenced 模板、slots、Gate 条件、`[Schema]` 通道；`PromptDslParser`/`FormatSpecParser` 移除或降为薄委托。
- **双（多）模型投影**：`DslParser` 保持通用，产出统一中间模型（增强 `DslDocument`）；各消费模型（`PromptProtocol`/`PromptFormatSpec`/新增 `L0Protocol`）由**投影器（Projector）**从中间模型映射得到。
- **L0 对齐 L1/L2**：L0 各段经同一解析器获得运行期结构化模型 `L0Protocol`（公理/门/状态机/类型/定义/Schema 集合），引擎可消费；模型文本仍拼入（保持"模型读"）。

### 非目标（No-Go）
- **不改 DSL 原文书写语法**：`skills/**/SKILL.md` 与 `.clinerules/*.md` 正文一字不改（零迁移，解析器兼容）。
- **不动运行期行为契约**：`PromptProtocol`/`PromptFormatSpec` 的字段与消费方（`PromptCatalog`/`PromptFrameworkFunction`/`PromptValidator`）不变，仅改变**生产方**。
- **不动公理生成**：`AxiomCodeGenerator` 继续消费 `DslParser`（公理通道），公理集/层级/轴不因本方案改变。
- 不做 DSL→可执行引擎绑定：仍以"声明+模型"为准，不引入新运行时。

## 四、核心设计：单解析器 + 中间模型 + 多投影器

### 4.1 总体架构

```
skill 正文（dsl: format / l0-system / l0-loop / l0-logic / protocol）
        │  PromptDslSource.ReadSkillBody(dsl)
        ▼
┌──────────────────────────────────┐
│  Plate.DslMethod.DslParser        │ ← 唯一解析器（新增通道：模板/slots/Gate 条件/Schema）
└──────────────┬───────────────────┘
               ▼
   UnifiedDslDocument（增强 DslDocument：+ Templates / Conditions / Params / Schemas）
               │  投影器 Projector（位置即语义，各模型各自投影）
     ┌─────────┼──────────┬──────────┐
     ▼         ▼          ▼          ▼
 L1L2Projector FormatProj L0Projector  Axiom 通道
     │         │          │          （AxiomCodeGenerator 不变）
     ▼         ▼          ▼
 PromptProtocol PromptFormatSpec  L0Protocol（新增）
```

关键点：**解析器保持通用、不感知消费模型**；各消费模型由投影器映射，新增模型只增投影器、不动解析器。

### 4.2 统一 DSL 文法（合并后）

| 语法元素 | 规则 | 吸收自 |
|---|---|---|
| 声明头 `[前缀] Name: Value` | 前缀来自 `DslConstants` 注册表；Name 至首个 `:`；Value 取首个 `\|` 之前 | 两套已有 |
| `\|` 分句 | 合取/注释/字段分隔（`k=v`、`field∈{...}`、`required:{...}`） | 两套已有 |
| `[CR: ...]` 引用 | `CrReferenceParser` 解析结构化引用 | clinerules DSL |
| 缩进续行 | `[Gate]/[SM]/[Schema]` 后缩进并入 Continuation | 两套已有 |
| fenced 模板块 ` ```text ... ``` ` | 紧随 `[SM]/[Template]` 头后的代码块捕获为模板内容 | 协议 DSL |
| `\| slots: a, b` | fenced 块后紧跟行声明槽位 | 协议 DSL |
| `[Gate]` 条件行 | 缩进行 `field=…, op=…, value=[…]` 解析为条件对象 | 协议 DSL |
| `% NAME=type:value` | 配置参数 | 两套已有 |
| `[Schema]` 声明 | 字段/必填/枚举（吸收 FormatSpecParser 规则） | 协议 DSL |

**统一原则**：一条声明（含 fenced/slots/续行）解析为一个统一节点；节点带**前缀族 + 名 + 值 + 字段 + 引用 + 模板 + 条件 + 位置（节/行）**。文法合并后，同一文本无论走公理、协议、格式、L0 投影，都能被解析。

### 4.3 `DslParser` 能力扩展（新增 4 通道，均在现 `DslParser` 基础上增量）

1. **Fenced 模板通道**：`[SM]`/`[Template]` 头后紧跟 ` ``` ` 块 → 捕获块内内容 + 探测紧随 `| slots:` 行 → 挂到节点 `Template`/`Slots`（复用 `TextScan.ExtractFenced` 原语，吸收 `PromptDslParser.ReadFencedBlock`）。
2. **Gate 条件通道**：`[Gate]` 后缩进行按 `field=…, op=…, value=[…]` 解析为条件（吸收 `PromptDslParser.ParseGate`），挂到节点 `Conditions`。
3. **`[Schema]` 通道**：吸收 `FormatSpecParser` 的字段/必填/枚举解析，产出 `SchemaNode`（注册表已含 `[Schema]`，补齐运行期解析）。
4. **`%` 参数通道**：已有，规范化挂到 `Params`。

> 设计取舍：**不**让 `DslParser` 直接产出 `PromptProtocol` 等具体模型——保持解析器通用（Kernel/Strategy 定位），具体模型由投影器承担（Domain 定位），符合"解析器唯一、模型可扩展"。

### 4.4 统一中间模型（增强 `DslDocument`）

在现有 `DslDocument`（`Sections`/`Declarations`）上扩展：

```csharp
public sealed class UnifiedDslNode   // 替代原 DslDeclaration 的增强节点
{
    string Prefix, Name; string Value;          // 既有
    List<KeyValue> Fields; List<string> Refs;   // 既有（[CR]）
    string? Template; List<string> Slots;       // 新增：fenced 模板 + 槽位
    List<Condition> Conditions;                 // 新增：[Gate] replan 条件
    bool IsAxiomSymbol;                         // 沿用 IsAxiomSymbol 判断
    int LineNumber; string Section;             // 位置（供层级/投影）
}
public sealed class Condition { string? Field; string Op; object[] Value; }
```

`DslDocument` 增补集合：`Templates`、`Conditions`、`Params`、`Schemas`；`Declarations` 升级为 `UnifiedDslNode` 列表。**向后兼容**：`AxiomCodeGenerator` 消费的字段（`Kind/Name/RawLine/LineNumber/SourceFile/Fields/References`）保持存在，零改动。

### 4.5 投影器（Projector，各模型独立）

| 投影器 | 输入 | 输出 | 职责 |
|---|---|---|---|
| `L1L2Projector` | UnifiedDslDocument | `PromptProtocol` | `[SM]` 模板→`L1.Template/L1.Generator.UserTemplate/L2.ContinueTemplate/...`；`[AX]`→生成器 system 提示；`%`→生成配置；`[Gate]`→`L2.ReplanConditions`；`required` 由 Schema 投影 |
| `FormatProjector` | UnifiedDslDocument | `PromptFormatSpec` | `[Schema]`→`Schemas`（字段/必填/枚举）；`InstructionsText`=原始文本 |
| `L0Projector`（新增） | UnifiedDslDocument | `L0Protocol` | `[AX]/[Gate]/[SM]/[Type]/[Def]/[Schema]`→结构化集合 |

投影器放在 `Agent.Operation.Prompts`（沿用现有模型命名空间），只消费 `DslParser` 产出，不反向依赖解析细节。

### 4.6 L0 对齐：`L0Protocol` 与 `L0Projector`

新增运行期模型，使 L0 各段获得与 L1/L2 同等的结构化视图：

```csharp
public sealed class L0Protocol
{
    string InstructionsText;                       // 模型读文本（保持"模型读"）
    List<L0Axiom> Axioms;                          // [AX]/[BAX]/[Strategy]
    List<L0Gate> Gates;                            // [Gate] + 分支/续行
    List<L0StateMachine> StateMachines;            // [SM]
    List<L0Type> Types;                            // [Type]/[Def]
    Dictionary<string, FormatSchema> Schemas;      // [Schema]（复用 FormatSchema）
}
```

- `PromptCatalog` 加载 L0 时：`ReadSkillBody(dsl) → DslParser.Parse → L0Projector.Project`，既产出 `InstructionsText`（拼入模型），又产出 `L0Protocol`（供运行期校验/装配/治理）。
- 引擎获得 L0 结构化视图后，可做：声明未引用检测、L0↔L1/L2 对齐校验、装配一致性治理（对齐 `DslIndex`/`ModuleAxisMatrix` 的既有治理思路）。
- **对现有行为零回归**：`InstructionsText` 与当前拼接文本逐字一致；`AxiomCodeGenerator` 仍用同一 `DslParser` 的公理通道，不受投影影响。

## 五、运行期装配链（改造后）

改造前后 `provide_prompt` 的装配链对比：

```
改造前（现状）
  PromptCatalog
    LoadL0      → ReadSkillBody(dsl) 拼接纯文本（不解析）
    LoadProtocol → ReadSkillBody("protocol") → PromptDslParser.Parse → PromptProtocol
    LoadFormatSpec→ ReadSkillBody("format")  → FormatSpecParser.Parse → PromptFormatSpec

改造后
  PromptCatalog
    LoadL0      → ReadSkillBody(dsl) → DslParser.Parse → L0Projector.Project
                 → InstructionsText（拼入 L0）+ L0Protocol
    LoadProtocol → ReadSkillBody("protocol") → DslParser.Parse → L1L2Projector.Project → PromptProtocol
    LoadFormatSpec→ ReadSkillBody("format")  → DslParser.Parse → FormatProjector.Project → PromptFormatSpec
```

三个入口都收敛到 `DslParser.Parse` 唯一解析，再由各投影器产出目标模型；`AxiomCodeGenerator`（构建期）与 `.clinerules` 校验继续复用同一 `DslParser`（公理/引用通道），一条解析器覆盖全部消费方。

## 八、分阶段迁移计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0（现状基线）** | 记录当前 `PromptProtocol`/`PromptFormatSpec` 的解析产物快照 | 基准备份 |
| **P1（解析器扩展）** | `DslParser` 增 4 通道 + `UnifiedDslNode`；实现 `L1L2Projector`/`FormatProjector` | **双跑对比**：给定全部 skill 正文，新解析+投影 输出 == 旧 `PromptDslParser`/`FormatSpecParser` 输出（逐字段断言） |
| **P2（L0 对齐）** | 新增 `L0Protocol` + `L0Projector`；`PromptCatalog.LoadL0` 走统一解析 | L0 运行期产出 `L0Protocol`；`InstructionsText` == 现拼接文本 |
| **P3（切流+清理）** | `PromptCatalog` 三入口切到统一解析；`PromptDslParser`/`FormatSpecParser` 降为薄壳或移除；更新文档与注释 | 全量回归 + 构建通过 + 无残留引用 |

每阶段独立可合并，P1/P2 可并行；P3 前旧解析器保留以做双跑对照，风险收敛。

## 九、兼容性与风险

| 风险 | 缓解 |
|---|---|
| 解析语义差异（如 `[SM]` 双义：状态机 vs 模板块） | 以**统一节点**承载双通道（`Template`+`Conditions` 并存），投影器按需取；P1 双跑断言兜底 |
| `AxiomCodeGenerator` 依赖 `DslDeclaration` 字段 | `UnifiedDslNode` 向后兼容保留 `Kind/Name/RawLine/LineNumber/SourceFile/Fields/References` |
| `InstructionsText` 文本漂移（L0 模型读） | P2 用逐字断言锁定 |
| 旧解析器遗留引用（测试/文档） | P3 统一清理，扫描 `PromptDslParser`/`FormatSpecParser` 引用并迁移 |
| 单点解析器过度耦合 | 保持解析器通用、投影器可插拔（新增模型=新增投影器，不动解析器） |
| DSL 原文改动 | **本方案不改原文**：`skills/**` 与 `.clinerules/*` 零迁移 |

## 十、验收标准

1. **单测**：对 `skills/**/SKILL.md` 全部正文，`DslParser + L1L2Projector` 输出与旧 `PromptDslParser` 逐字段一致；`DslParser + FormatProjector` 与旧 `FormatSpecParser` 一致（P1）。
2. **L0 结构化**：`PromptCatalog.L0Protocol` 非空且含预期 `Axioms/Gates/StateMachines/Types/Schemas`；`InstructionsText` == 现 `L0SystemPrompt` 文本（P2）。
3. **零回归**：`Agent.sln` 构建通过；`AxiomCodeGenerator` 生成公理集 == 现 mapping-report 16 条（不变）。
4. **无残留**：`PromptDslParser`/`FormatSpecParser` 不再被运行期消费（或已移除）。
5. **依赖**：`Agent.Operation` 仅依赖 `Plate.DslMethod` 一个 DSL 解析入口。
