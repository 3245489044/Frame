## 1. 本文档目的

回答两个问题：

1. **这条链路为什么存在**——从数据库任务到 Agent 执行的闭环，解决了「写任务即自动执行、可控暂停、失败可重放」的自动化诉求。
2. **链路每一跳如何衔接**——任务池消费循环、混合调度主循环、单轮骨架执行三层的职责边界与桥接点。

> 目标读者：接手该链路的开发者，需在 10 分钟内建立「任务怎么进来、循环怎么转、代码怎么执行」的整体心智模型。

## 2. 总体链路图

```
【外部入口层】EnableMent\交互启动.bat（管道 JSON → FILEDRIVEN_INSTANT_BODY → 运行测试GUI模式.ps1 Raw-Body 判别
     → AgentUi_RunJson 合成单命令）→ TaskPoolEnqueueAsync 写 ur_tasks（§3.1.0）
     ▼
【任务池层】ur_tasks → TaskPool 消费循环（Share 层状态机）
     │  写即激活、按 Priority 出队、TaskKey 幂等
     ▼
【接线层】AgentTaskPoolAdapter.handler：TaskRouter 路由裁决（任务自主标记 × 后台规则驱动）→ 选执行器
     │  Hybrid→LlmTaskExecutor(LLM) / Config·Deterministic→RuleTaskExecutor(零LLM)；cline_execute 在 LLM 调用前挂暂停门
     ▼
【调度循环层】AgentRunner.RunHybridInternalAsync → SnapshotDrivenLoopEngine
     │  while 未终止：budgetTerminate → execute(五步管线) → next(确定性+混合调度)
     │  导演按路由：需LLM→LlmStateDirector / Config→ConfigStateDirector / Deterministic→NoopStateDirector(零LLM)
     ▼
【执行层】RunRound → PlanRound 解析执行器 → 骨架五步
     guard_input → provide_prompt → cline_execute → rule_match → guard_output
     │                │
     │                └─ 确定性文件操作：Invoke-AgentStep -Action <verb.object>（PsRuntimeBinding，§3.4）
     ▼
【回写】结果写回 ur_outputs；失败保留错误行可重放
     └ 分析/文件节点经存储桥（单一 C# 写入口）→ ur_resources（标准存储，§3.4）
```
> **旁路防阻塞（§3.5）**：管道投喂无 TTY → `Test-PipeMode` 强制 `Get-RunMode=auto`、跳过所有 `Read-Host`；`Write-LauncherLog` 行级日志全程落盘；函数库加载失败写 fallback + 抛异常，杜绝"无错误无日志卡死"。

## 3. 各层目的与逻辑链

### 3.1 任务池层（目的：持久化排队 + 写即激活 + 可重放）

**目的**：把「创建 Agent 任务」与「执行任务」解耦，让任务在数据库中长期存活、可排队、可重启回填、可全局暂停，而不是一次函数调用。

```
写 ur_tasks（EnqueueAsync，TaskKey 幂等）      // 创建任务
   │ 状态 NotStarted + 唤醒消费循环（写即激活）
   ▼
TaskPool 消费循环（Share 层状态机，MaxConcurrency 默认 1）
   │ 按 Priority 出队 → Running → UpdateStatus
   ▼
AgentTaskPoolAdapter.handler = TaskRouter 路由选执行器 → 执行（Hybrid→LlmTaskExecutor→AgentOrchestrator.RunAsync / 零LLM→RuleTaskExecutor）
```

| 组件 | 位置 | 职责 |
|------|------|------|
| `SqliteTaskPoolStore<TItem>` | `CsharpPrj/Operation/DataStoreDriven/Sqlite/` | `ur_tasks` 表持久化，实现 `Share.TaskStatusPool.TaskPool.ITaskPoolPersistence`；TaskKey 幂等 / Status 镜像 / PayloadJson 载荷，重启回填 |
| `AgentTaskItem` | `Agent.Core/TaskPool/` | 任务载荷（TaskKey/Priority/MaxRetries + UserInput/ThreadId/InputKey/SchedulingMode/SchedulerRulesKey）；实现 `ILoopState`+`IAgentLoopState`（任务=快照） |
| `AgentRuleBackend` | `Agent.Core/TaskPool/` | 后台规则驱动（`IRuleBackend<AgentTaskItem>`）：Hybrid→null(需LLM) / Config·Deterministic→规则解析(零LLM)；供 `TaskRouter` 路由 |
| `AgentTaskPoolAdapter` | `Agent.Core/TaskPool/` | 通用 `TaskPool` ⇄ 执行器接线；`Resolve` 按 `TaskRouter` 路由选执行器（LlmDriven→LlmTaskExecutor / RuleDriven→RuleTaskExecutor）；`EnqueueAndWaitAsync` 入队即自动启动并取回 `AxiomLoopResult`；对外门面（Enqueue/EnqueueAndWait/Pause/Resume/PauseAll/ResumeAll/Status） |

> 任务池**默认启用**（`AgentConfig.EnableTaskPool=true`），`AgentHost.RunAsync` 直跑也统一走任务池（`EnqueueAndWaitAsync`：入队即自动启动消费循环 + 取回 `AxiomLoopResult`）；显式关闭时回退编排器直跑。依赖方向单向无环：`Share.TaskStatusPool` → `Operation.DataStoreDriven`（`ur_tasks`）→ `Agent.Core`（adapter/AgentRuleBackend）→ `Agent.Launcher`（装配）。

### 3.1.1 任务路由（明确"需 LLM vs 零 LLM"，Agent.Operation 纯判定）

**目的**：让任务池在消费时按代码逻辑明确区分"该任务要不要接入 LLM"，而非一律假设 LLM。由「任务自主标记」与「后台规则驱动」**结合**裁决（`Agent.Operation/Routing/TaskRouter`）。

```
路由（按代码逻辑转换，规则优先）：
  ① 后台规则驱动命中（AgentRuleBackend：Config/Deterministic）→ RuleDriven（零 LLM）
  ② 否则按任务自主标记回退（SchedulingModeAutonomy：Hybrid=需LLM / Config·Deterministic=非自主）→ LlmDriven / RuleDriven(纯确定性)
```

| 组件 | 位置 | 职责 |
|------|------|------|
| `ExecutionDisposition` / `TaskRoutingDecision` | `Agent.Operation/Routing/` | 执行走向枚举（RuleDriven/LlmDriven）+ 裁决载体 |
| `ITaskAutonomy` | `Agent.Operation/Routing/` | 任务自主标记：`RequiresLlm` |
| `IRuleBackend<TItem>` | `Agent.Operation/Routing/` | 后台规则驱动端口：`RuleResolution? TryResolve(TItem)` |
| `TaskRouter` | `Agent.Operation/Routing/` | 结合裁决核心（纯函数） |
| `SchedulingModeAutonomy` | `Agent.Operation/Routing/` | 把 `SchedulingMode` 适配成自主标记（Hybrid=需LLM） |
| `AgentRuleBackend` | `Agent.Core/TaskPool/` | 具体规则后端（AgentTaskItem）：Hybrid→null / Config·Deterministic→规则解析 |

**接线**：`AgentTaskPoolAdapter.Resolve` 与 `AgentRunner` 导演选择均按 `TaskRouter.Route(item, SchedulingMode, AgentRuleBackend)` 的 `Disposition` 分流——需 LLM 走 `LlmTaskExecutor`/`LlmStateDirector`；零 LLM 走 `RuleTaskExecutor`/（`ConfigStateDirector` 或 `NoopStateDirector`）。`Deterministic`（非自主）此前无执行器可解析、导演误落 LLM，现归零 LLM 规则/非自主路径。

### 3.2 调度循环层（目的：快照驱动 + 混合调度 + 终止二分）

**目的**：以 `SchedulerState` 为唯一持久根驱动非限定循环，用「LLM 自由探索 + 计算守卫策略完全实施」的混合调度来推进整体状态，并把终止裁决收敛到可判定/不可判定两条边界。

```
AgentOrchestrator.RunAsyncCore → AgentRunner.RunAsync
   → RunInternalAsync（唯一路径，直接调混合调度循环）
   → RunHybridInternalAsync
       │[1] RestoreSchedulerStateAsync            // 恢复/新建 SchedulerState（无快照播种默认策略集）
       │[2] new DecisionPoint(...)                // 唯一决策枢纽，绑定初始租约
       │[3] new HybridSchedulerStateMachine(director, new TransitionGuard(), state)   // director 按 TaskRouter 路由选：需LLM→Llm / Config→Config / Deterministic→Noop
       │[6] engine.RunAsync(SnapshotDrivenLoopEngine<SchedulerState, AxiomActionResult>)
       │      while (外部未终止):
       │        [A] budgetTerminate(state)        // 预算终止（TO/TM/TS，引擎内可判定）
       │        [B] execute(state) = ExecuteHybridRoundAsync（五步编排管线）
       │        [C] next(state, result) = NextHybridRoundAsync（确定性+收割+混合调度+回写策略）
```

**每轮状态转移（`NextHybridRoundAsync`）四步**：
1. **确定性计算**：错误分类 → 评估 → 进度/熔断 → halt → 轮次 +1 → TS 判定；
2. **单根收割**：`HarvestDeterministicCore` 把确定性核心从租约回写根 `SchedulerState`；
3. **混合调度**：`scheduler.AdvanceAsync` = `LlmStateDirector`（LLM 提议）+ `TransitionGuard`（计算守卫）→ 原子施加（Held/Changed/Reject）；失败 → fail-safe stay/continue；
4. **回写策略**：SwitchStrategy 且 Applied 时回写 `state.Data[ActiveStrategy]`。

**路由单一裁决**：决策点不再产出路由动作；"整体状态怎么变"由 `HybridSchedulerStateMachine` + `TransitionGuard` 裁决；预算终止由引擎内 `budgetTerminate` 裁决。

**与任务池的桥接点**：暂停门已下沉到 **LLM 调用点**——`cline_execute` 在真实 LLM 调用前经 `AgentLoopFunction.CheckLlmGateAsync`（= `taskPool.WaitIfPausedAsync(taskKey)`，合作式暂停，Running ⇄ Paused 非终止）挂起；`guard_input/provide_prompt` 等确定性前置步骤照常执行并可观测，仅在 LLM 调用前阻塞。任务键经 `AgentRunCancellation.SetTaskKey/GetTaskKey` Functor 透传。调度导演按 `TaskRouter` 路由的 `Disposition` 选择：需LLM→`LlmStateDirector`（默认）/ Config→`ConfigStateDirector`（读 ur_config 规则集，零 LLM）/ Deterministic→`NoopStateDirector`（非自主、零 LLM）。

### 3.3 执行层（目的：声明式骨架 + 快照消费驱动执行器 + 可扩展）

**目的**：把每轮工作拆成声明式骨架五步，按当前策略**动态解析执行器**（executor-agnostic，Cline 只是其中一种状态），使执行后端可替换、无需改骨架。

```
[run_round] _runtime.PlanRound(activeStrategy) → RoundPlan(Executor)   // 快照消费驱动：执行器解析
   → ctx.State.Data[RoundKeys.Executor] = plan.Executor
   → _runner.RunRoundAsync(…)
       → StateContextAdapter（状态外置 StateCenter 三层）
       → RoundStateMapper.Seed + DataContainerBinder.BindSeedPhase
       → _pipeline.ExecuteAsync(ctx)  // 骨架步骤链：
           [Step 1] guard_input        → 输入安全过滤
           [Step 2] provide_prompt     → L0+L1+L2 提示词装配（首步生成/继续步重规划）
           [Step 3] cline_execute      → ResolveExecutor → executor.ExecuteAsync(request)
           [Step 4] rule_match         → 结构化信号优先 + 文本规则兜底（零 LLM）
           [Step 5] guard_output       → （条件：DecisionWordMapper.IsSuccess，stop 终态脱敏）
       → RoundStateMapper.Harvest + BindHarvestPhase + ClearTransient  // 轮结束隔离
```

**工作流拓扑**（`agent-loop.json` 声明式主路径）：

```
start → guard_input → provide_prompt → cline_execute → rule_match
                                                        ├── stop → guard_output → end
                                                        └── continue →（引擎继续下一轮，回到 provide_prompt）
```

### 3.4 确定性动作层（PsRuntimeBinding）与标准存储（ur_resources）

**目的**：把执行器（Cline 等）在骨架执行内的**确定性文件操作与落库**收敛到统一标准化动作层——一律 `Invoke-AgentStep -Action <verb.object> -Params @{}`，返回 `{status,message,data,errors}` 信封；读到的有价值文件 / 分析结论经**单一 C# 写入口**写入标准存储 `ur_resources`（SQLite 真源），PowerShell 不复制 schema（SingleImplementation，无双真源）。

```
执行器（Cline）确定性操作
   │ 统一调用：Invoke-AgentStep -Action <verb.object> -Params @{}
   ▼
PsRuntimeBinding（PowerShellScript/PsRuntime/Binding/Invoke-AgentStep.ps1 薄绑定）
   │ 加载 PsRuntime + Config/ps1-runtime.json；注入存储桥配置；组合 read→store
   ▼
标准化动作集（BasicMethod 契约，零 LLM，确定性）
   read.file / write.file / replace.file.batch / resolve.path（已有）
   list.dir / store.resource / read.file(-Persist)（新增）
   ▼
存储桥（单一 C# 写入口）
   store.resource 与 read.file-Persist 委托 Agent.StorageBridge.exe
   → IResourceReferenceStore.AddResourceAsync → ur_resources（SQLite 真源）
```

| 组件 | 位置 | 职责 |
|------|------|------|
| `Invoke-AgentStep`（薄绑定） | `PowerShellScript/PsRuntime/Binding/` | 加载 PsRuntime + 配置，暴露统一动作入口；注入存储桥配置、组合 read→store |
| 动作契约 + 实现 | `PowerShellScript/BasicMethod/`（FileOps/Storage/Core） | `list.dir`/`store.resource`/`read.file(-Persist)` 等确定性动作，返回信封 |
| 存储桥 | `Agent/src/Agent.StorageBridge/`（`store-resource`/`get-resource`） | 复用 `DatabaseBootstrapper` 打开 `agent.db`，写/查 `ur_resources`（单一 C# 入口） |
| 流程 skill | `Agent/skills/analyze-folder/SKILL.md` | 指导 Cline：resolve.path → list.dir → read.file(-Persist) → store.resource → 返回节点引用 |

> **与主循环结果（ur_outputs）分工**：标准存储 `ur_resources` 存**确定性产物**（分析结论 `analysis:<folder>`、读到的有价值文件 `file:<path>`），是"写即持久化"的引用图真源；`ur_outputs` 为主循环每轮执行结果（decision/rounds/duration）。两者不混用（storage-template.dsl.md `resource` 模板 → `ur_resources`）。

### 3.5 错误处理与可观测性（目的：管道模式防阻塞 + 卡死可定位）

**目的**：外部入口经管道投喂时无 TTY（stdin 被重定向），任何 `Read-Host` 等待按键都会**无限阻塞**且不抛错；且 Launcher 以 WinExe 静默运行，函数库缺失/执行异常无回显。本节收敛该入口的三类防阻塞/可观测手段，使"无错误无日志卡死"变为"可诊断 + 自动防阻塞"。

```
管道模式防阻塞（PS 层）
   Test-PipeMode（FILEDRIVEN_INSTANT_BODY 非空 ∨ stdin 被重定向）
     ├─ Get-RunMode 强制返回 auto（覆盖 manual 的 Read-Host）
     ├─ ScriptRunner.Invoke 手动暂停块跳过（-and -not (Test-PipeMode)）
     └─ ShowInteractive 直接跳过（交互菜单依赖 Read-Host，管道下不可用）
   ↓
行级诊断日志（PS 层）
   Write-LauncherLog → %TEMP%\fileDriven_launcher.log（启动/Raw-Body 判别/合成脚本/Launcher PID/管道连接/卡死强杀/退出码）
   ↓
函数库加载失败显式化（C# 层）
   FrameworkInitializer → FunctionLibraryLoader.Load 结果 failed.Count>0
     ├─ 写 %TEMP%\FileDriven_FunctionLibFallback_<时间>.log（失败库名/错误/DLL 检查指引）
     └─ 抛 InitializationException（阻断启动，输出 fallback 路径）
```

| 手段 | 位置 | 职责 |
|------|------|------|
| `Test-PipeMode` | `PowerShellScript/Modules/FileDriven/FileDrivenTestUtils.ps1` | 管道模式统一判定（环境变量 + `[Console]::IsInputRedirected` 双信号） |
| `Get-RunMode` 管道强制 auto | 同上 | manual 的 `Read-Host` 在管道下无 TTY → 强制 auto 跳过所有手动暂停 |
| `Write-LauncherLog` | `运行测试GUI模式.ps1` | 行级诊断日志（带时间戳追加，共享 `%TEMP%\fileDriven_launcher.log`），卡死时保留最后轨迹 |
| 管道空闲超时收紧（30s，管道模式） | 同上 | 管道模式无 TTY 无法人工干预，长时间无输出按卡死处理（120s→30s）；卡死时写日志并强杀 Launcher |
| 函数库失败 fallback + 抛异常 | `FileDriven/FileDriven.Execution/Initial/FrameworkInitializer.cs` | `AgentUiLibrary` 等加载失败不再静默：写 `%TEMP%\FileDriven_FunctionLibFallback_*.log` + 抛 `InitializationException`（含 `Agent.Launcher.dll` 缺失指引） |

> **设计要点（SEP 对齐）**：错误处理属引擎执行侧可判定动作（`FailureBudgetEscalation` / `ErrorHandler`），不触碰确定性核心（`SEP.DeterministicCoreDisjoint`）；管道模式防阻塞为**入口层适配**（引擎循环本身无变化），符合 `handle(error, Scope)` 的 Scope 注入思想——管道输入作用域 `single_call` 下仅允许确定性重试，禁止交互等待。

## 4. 生命周期与回写

```
每轮 → cline_execute 在 LLM 调用前 → AgentLoopFunction.CheckLlmGateAsync = taskPool.WaitIfPausedAsync(taskKey)   // 全局暂停合作式挂起（仅 LLM 调用点阻塞）
结果写回 ur_outputs（decision/rounds/duration）；失败保留错误行可重放
```

| 能力 | API | 语义 |
|------|-----|------|
| 队列级全局暂停 | `PauseAllAsync / ResumeAllAsync` | 暂停全部活动任务（在途 + 排队），Running ⇄ Paused 非终止 |
| 单任务暂停 | `PauseAsync / ResumeAsync` | 在途（Running→Paused，合作式挂起）与排队（NotStarted→Paused） |
| 重启回填 | `ProcessPendingAsync` | 死 `Running` → `NotStarted` 重放续跑；`Paused` 保持挂起 |

## 5. 贯穿公理与设计要点

| 公理 / 要点 | 落点 |
|------|------|
| 单根架构（AX.StateRootSingleSource） | `SchedulerState` 为唯一持久根，`AxiomContext` 为每轮派生租约；确定性核心经播种/收割单向流转 |
| 终止二分（AX.TerminationBipartition） | 预算终止（可判定，TO/TM/TS）引擎内裁决；探索终止（不可判定）外置为取消令牌 |
| 混合调度只改状态、不触碰确定性核心（SEP.DeterministicCoreDisjoint） | `ApplyGuarded` 防御性断言；确定性核心由 `ProgressUpdater`/`BudgetEscalator` 写入租约 |
| 快照消费驱动执行器（executor-agnostic） | `AgentRuntimeManager.PlanRound` + `cline_execute.ResolveExecutor`，Cline 只是其中一种执行器状态 |
| 状态外置 + 映射引擎唯一 | `StateContextAdapter` → `StateCenter` 三层；`DataContainerBinder` 四阶段经 `KeyProcessor.Mapper.MapBatch` |
| 需 LLM vs 零 LLM 明确区分（任务自主标记 × 后台规则驱动） | `Agent.Operation/Routing/TaskRouter` 结合裁决；`AgentTaskPoolAdapter.Resolve` 与导演选择按 `Disposition` 分流（Hybrid→LLM / Config·Deterministic→零LLM） |
| 直跑统一走任务池（TaskPoolAgent 自动化） | `AgentHost.RunAsync → fw.TaskPool.EnqueueAndWaitAsync`：入队自动启动、状态自动流转、取回 `AxiomLoopResult`；默认 `EnableTaskPool=true` |
| 外部投喂统一入口（即时指令，§3.1.0） | `AgentUi_RunJson` 单一 JSON 入口：`action` 判别式分发（runLoop/task/resource 系/reference 系）；`task` 内 `op` 分流（enqueue/status/delete/submit）；enqueue 写 `ur_tasks` 即激活消费 |
| 管道模式防阻塞（§3.5） | `Test-PipeMode` 统一判定 → `Get-RunMode` 强制 auto、跳过所有 `Read-Host`；`Write-LauncherLog` 行级日志；函数库失败 fallback + 抛 `InitializationException` |

## 6. 一句话总结

**任务池 = 写 `ur_tasks` 即激活的持久化队列消费循环**（`AgentHost.RunAsync` 直跑也经 `EnqueueAndWaitAsync` 统一走任务池：入队自动启动、状态自动流转、取回 `AxiomLoopResult`）→ **`AgentTaskPoolAdapter` 按 `TaskRouter` 路由裁决选执行器**（任务自主标记 × 后台规则驱动：Hybrid→`LlmTaskExecutor`(LLM) / Config·Deterministic→`RuleTaskExecutor`(零LLM)）→ **进入唯一的 `SnapshotDrivenLoopEngine` 混合调度循环**（每轮 execute 五步管线 + next 确定性计算/收割/调度导演施加状态变更；导演按路由选 Llm/Config/Noop）→ **`RunRound` 按当前策略解析执行器并跑骨架五步** → **`cline_execute` 在真实 LLM 调用前以 `CheckLlmGateAsync`（`WaitIfPausedAsync`）支持合作式暂停**（确定性前置步骤照常执行并可观测，仅 LLM 调用点阻塞）→ **结果写回 `ur_outputs`**；**执行器确定性文件操作经 `Invoke-AgentStep`（PsRuntimeBinding）标准化动作执行**（§3.4），**读到的有价值文件/分析结论经存储桥单一 C# 写入口写入标准存储 `ur_resources`**（与 `ur_outputs` 分工、不混用）。
