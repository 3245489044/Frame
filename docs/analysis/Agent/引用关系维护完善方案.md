# 引用关系维护逻辑完善方案（从被动派生走向声明式构建与可重建）

> **版本**：1.0
> **日期**：2026-08-18
> **范围**：分析当前引用关系维护逻辑的「分散 / 脆弱 / 不支持主动写入构建」三类问题，给出完善方案：守卫入口收敛（SingleImplementation）、消除重复对账、声明式关系构建（主动声明 + 全量重建）、端点符号落盘、跨介质 outbox 补强（P2）、图健康检查。
> **依据**：`CsharpPrj/Operation/DataStoreDriven/Core/{ReferenceGrounding, NodeRelationDeriver, WriteThroughNodeStore, WriteThroughTaskPoolStore, NodeGraphReconciler}.cs`、`CsharpPrj/Operation/DataStoreDriven/Graph/ReferenceGraphCoordinator.cs`、`Agent.Axioms/Nodes/NodeExecutionService.cs`、`Agent.Launcher/Modules/AgentUiLibraryData.cs`（`db.Resources` 直写入口）、`Agent/节点即存储单元：Agent三线存储架构介绍.md`。

---

## 一、现状问题分析

### 1.1 维护逻辑分散（7 个组件各管一段，互不知晓）

当前"图关系维护"的职责散落在多个组件，且存在**双实现 / 双写入口**：

| 组件 | 职责 | 边界问题 |
|------|------|----------|
| `WriteThroughNodeStore` | 业务节点（NodeType=node）写透镜像 | 白名单仅 `{node}`，zone/config/checkpoint 不建资源 |
| `WriteThroughTaskPoolStore` | task 写透镜像（Enqueue/Update/Delete） | 状态/载荷变化只同步不重建边（防图抖动，但无显式更新关系入口） |
| `ReferenceGrounding` | 镜像维护 + 单节点对账 `ReconcileNodeRelationsAsync` | **与协调器重复实现对账 diff** |
| `ReferenceGraphCoordinator` | 写边（幂等）+ 内存端点注册表 + `ReconcileNodeRelationsAsync` | **第二个对账实现**；`_endpoints` 不落盘 |
| `NodeRelationDeriver` | 唯一边推导（映射 + 溯源） | 只服务"执行后"推导，无预声明来源 |
| `NodeExecutionService.PersistNodeReferencesAsync` | 调用方：写业务节点 + 推导边 + 对账 | **含 `is not WriteThroughNodeStore` 运行时类型判断兜底分支** |
| `AgentUiLibraryData`（`db.Resources`） | UI/存储桥直写 `IResourceReferenceStore` | **绕过守卫直接调协调器**，与守卫形成双写入口 |

> **双写入口（最核心的分散问题）**：`db.Resources.AddResourceAsync/AddReferenceAsync`（`AgentUiLibraryData.MutateResourceAsync/MutateReferenceAsync`）直调 `ReferenceGraphCoordinator`，而写透路径（`WriteThrough*` + `ReferenceGrounding`）也写同一协调器——两条通道互不知晓，任一通道遗漏同步都无法被发现，只能靠对账兜底。

### 1.2 脆弱点

1. **时序软约束**：协调器注释明言"端点存在性按 SQL 写透时序保证（SQL 先写、本协调器随后同步边）"——这是**调用顺序约束**，任一写路径漏调同步即产生悬空端点/过期边；
2. **镜像不落盘**：`_endpoints` 字典是会话内存（注释"不落盘"），重启后端点 `Symbol/Metadata` 丢失，`Initialize()` 只能从边文档造裸资源（`EnsureNodeInMemory` 用 `KeyToIdentifier` 兜底），图的"可读性"（符号名）随重启退化；
3. **跨介质无原子**：SQLite（单库原子）与 LiteDB 图库之间无事务，当前仅靠"逐条幂等写透 + 最终一致 + 对账兜底"——而对账（`NodeGraphReconciler.ReconcileAllAsync`）**只覆盖节点侧**（NodeType=node + RelationsJson），task 镜像 / keymapping 资源 / 声明关系不在对账范围；
4. **失败静默**：`EnsureResourceAsync` 命中"唯一键/资源已存在"类异常**容错吞掉**；镜像同步失败无补偿、无重试、无告警（无 outbox / 无失败日志）；
5. **悬空资源只报告不删除**：`ListDanglingGraphNodeResourcesAsync` 仅列出，长期累积脏数据（I3 兜底不越权的代价）；
6. **运行时类型判断**：`NodeExecutionService` 的 `_nodes is not WriteThroughNodeStore` 依赖具体装饰器类型，装配顺序一变（额外包一层装饰器）判断即失效。

### 1.3 不支持主动写入构建

1. **关系只能被动派生**：NodeToNode 边靠**执行后溯源**、KeyMappingToNode 靠**映射存在性**——节点执行前、或纯声明场景（无执行）下**无法建立任何组合关系**；
2. **task 关联一次性**：`RunRequest.RelatedNodes` 只在 `enqueue` 时经 `ReconcileTaskAsync` 生效一次，之后无法增量维护"任务关联哪些节点"；
3. **无全量重建入口**：`NodeGraphReconciler.ReconcileAllAsync` 存在但**未接入任何可见入口**（UI/命令/MCP 均不可调），且只重建节点侧；"投影可重建、幂等可重放"停留在设计愿景，不可作为能力使用；
4. **无声明 DSL**：没有"一次声明构建一批关系"的输入面（当前只有逐条 `addResource`/`addReference` 手动操作）。

## 二、完善目标（不变式）

| # | 目标 | 对齐原则 |
|---|------|----------|
| G1 | **单一守卫入口**：所有关系写入（含 UI/存储桥/声明）经唯一守卫，协调器降级为纯执行者 | SingleImplementation / TH-12 |
| G2 | **权威在 SQL、图可重建**：任意关系状态可从 ur_nodes / ur_tasks + 声明数据幂等重建 | DerivedDataAutoMaintenance / 投影可重建 |
| G3 | **声明式构建**：支持主动声明（预声明组合、增量维护任务关联、全量重建入口） | 主动不被动 |
| G4 | **跨介质不丢**（P2）：outbox 模式补强，崩溃可回放 | 最终一致 + 至少一次投递 |
| G5 | **可观测**：图健康检查 + 对账审计事件 | 数据即真相 / IObservabilitySink |

## 三、方案设计

### 3.1 收敛守卫入口（G1）

把分散的维护逻辑收敛到**唯一守卫** `ReferenceMaintenanceCoordinator`（可由现有 `ReferenceGrounding` 演进，或新增门面包裹它）：

```
业务/执行/UI/声明/存储桥
  → ReferenceMaintenanceCoordinator（唯一守卫，持有权威推导 + 对账 + 重建）
      → ReferenceGraphCoordinator（纯执行：幂等写边/删边，不再暴露 Reconcile/Ensure 决策面）
      → LiteDB graph-log.db
```

守卫统一端口（业务代码只依赖此接口）：

| 端口 | 语义 |
|------|------|
| `MirrorAsync(entity)` / `UnmirrorAsync(entity)` | 镜像维护（node/task/keymapping/声明关系） |
| `WriteRelationsAsync(wf, nodeKey, edges)` | 权威边集写入（内部经 `NodeRelationDeriver` 推导 + 协调器幂等写边） |
| `DeclareRelationsAsync(declarations)` / `UndeclareRelationsAsync(ids)` | 主动声明（§3.3） |
| `ReconcileAsync(scope)` | 对账（单节点 / 全图两级） |
| `RebuildAllAsync()` | 全量重建（§3.3.2） |

**收敛动作**：
- `AgentUiLibraryData.MutateResourceAsync / MutateReferenceAsync` 改走守卫（不再直调 `db.Resources`）；`IResourceReferenceStore` 直写入口标记废弃或内部化；
- `NodeExecutionService.PersistNodeReferencesAsync` 删除兜底分支，只依赖守卫接口（§3.7）。

### 3.2 消除重复对账（G1/G2）

现状 `ReferenceGrounding.ReconcileNodeRelationsAsync` 与 `ReferenceGraphCoordinator.ReconcileNodeRelationsAsync` 是**近乎相同的 diff 逻辑双实现**。收敛为：

- **推导与权威集**：只保留守卫侧（`NodeRelationDeriver` + 持久化 `RelationsJson`/声明记录）——守卫是唯一"知道权威边集"的地方；
- **执行与写入**：协调器只提供原子原语 `ApplyRelationEdgesAsync(targetNodeId, authoritative)`（内部删残留 + 补缺失，无决策逻辑），`Reconcile`/`Rebuild` 全部由守卫编排；
- **回归护栏**：保留现状双实现对账的等价性测试（重构前快照 diff 测试），确保收敛后行为不变。

### 3.3 声明式关系构建（G3，核心新增）

#### 3.3.1 关系声明持久化（权威在 SQL）

新增节点类型 `NodeType=relation`（ur_nodes，随 `SqliteNodeStore` 幂等建表，纯「键名 + 一个 JSON」），声明记录结构：

```
NodeKey = "relations.{workflowId}.{relationId}"   // 幂等 upsert 依据
PayloadJson = {
  "Source":    { "ResourceType": "node|task|keymapping", "Id": "...", "Port": "?" },
  "Target":    { "ResourceType": "node|task|keymapping", "Id": "...", "Port": "?" },
  "RefType":   "keymapping_to_node | node_to_node | 自定义",
  "KeyMappingRef": "?",
  "Status":    "active | revoked"
}
```

> 声明即权威：撤销 = 更新 `Status=revoked`（或删除节点），守卫据此级联清边；对账/重建以声明记录为来源之一——**图库永不比 SQL 多出任何未声明的关系**。

#### 3.3.2 主动声明 API（新 action）

| 动作 | 入参 | 行为 |
|------|------|------|
| `relations.declare` | `relations[]`（JSON 数组 DSL，见 3.3.3） | 批量声明 → 写 ur_nodes（NodeType=relation，SQL 事务）→ 守卫同步图（幂等） |
| `relations.undeclare` | `relationIds[]` | 撤销声明 → 更新 Status / 删节点 → 级联清边 |
| `relations.list` | `workflowId?` | 列出全部声明（含状态） |
| `task.updateRelations` | `taskKey` + `nodeKeys[]` | **增量维护**任务关联（替代 enqueue 一次性 `relatedNodes`，内部复用 `ReconcileTaskAsync` 语义） |
| `graph.rebuild` | — | **全量重建入口**：清空图库 → 从 SQL 重建（业务节点镜像 + task 镜像 + keymapping 资源 + 声明关系边 + 执行推导边），幂等可重复 |

> `graph.rebuild` 把"投影可重建"从愿景变成可调用能力：崩溃/脏数据/版本迁移后，一键让图收敛到 SQL 权威状态（对齐 §4.3 一致性策略"投影重建幂等（可全量可增量）"）。

#### 3.3.3 预声明组合（解决"执行前无法组合"）

声明 DSL 允许**不依赖执行溯源**直接建立节点组合（跨轮复用）：

```jsonc
{
  "workflowId": "agent-round",
  "relations": [
    // 显式声明：节点 B 消费节点 A 的 output 端口（执行前即可建边、可查询）
    { "from": { "node": "A", "port": "summary" },
      "to":   { "node": "B", "port": "input" },
      "refType": "node_to_node" },
    // 显式声明：keymapping 逻辑绑定节点（替代"有映射才建边"的隐式推导）
    { "from": { "type": "keymapping", "id": "NodeInput.agent-round.B" },
      "to":   { "node": "B" },
      "refType": "keymapping_to_node" }
  ]
}
```

**冲突裁决规则**：对账/重建时权威边集 = **声明边 ∪ 推导边**（声明优先，推导不覆盖声明）；节点执行后若溯源推导出与声明冲突的边，以声明为准并记录审计事件。

### 3.4 端点符号落盘 + 启动回填（修复"重启丢符号"）

- **落盘**：LiteDB 新增 `ur_endpoints` 集合（`{Key, ResourceType, Id, Symbol, Metadata, UpdatedAt}`），守卫 `MirrorAsync` 时同步写；或退而求其次把 `Symbol/Metadata` 并入边文档（最小改动）；
- **启动回填**：`Initialize()` 从 `ur_endpoints` + 边重建内存邻接（替代 `EnsureNodeInMemory` 造裸资源）；`RebuildAllAsync` 从 SQL 回填 symbol/metadata；
- 保持"端点镜像非权威"语义不变：`ur_endpoints` 只是可重建缓存，权威仍在 SQL。

### 3.5 跨介质 outbox 补强（G4，P2）

现状"幂等写透 + 对账兜底"在镜像同步失败时会**静默丢失**。升级为 outbox 模式：

```
SQL 事务内：写 ur_nodes/ur_tasks/声明  + 写 ur_relation_outbox(action, relationId, state=Pending)
  → 后台同步器（同进程 Task / 独立宿主）消费 outbox
      → ReferenceGraphCoordinator 幂等应用（Add/Remove）
      → 标记 Done（失败保留 Pending + 指数退避重试）
启动：回放未完成 outbox → 图不丢（至少一次投递 + 幂等应用 = 恰好一次效果）
```

> 保留对账兜底作为最终防线（对账是"校正"、outbox 是"不丢"），两者互补不互斥。

### 3.6 图健康检查与诊断（G5）

| 检查 | 内容 |
|------|------|
| `graph.status` | 端点数 / 边数 / 孤立端点 / 悬空资源（复用 `ListDanglingGraphNodeResourcesAsync` 基础） |
| `graph.diff` | SQL 权威边集 vs 图边集差异报告（声明∪推导 vs 实际边） |
| 对账审计 | 每次 `ReconcileAsync` / `RebuildAllAsync` 的运行结果写 `ur_events`（对齐 `IObservabilitySink`） |

### 3.7 移除运行时类型判断（G1）

`NodeExecutionService.PersistNodeReferencesAsync` 不再做 `is not WriteThroughNodeStore` 判断：装配期把"图维护者"（守卫）显式注入节点执行服务，**有守卫走守卫、无守卫跳过**（二态由注入决定，不依赖具体装饰器类型），删除兜底分支。

## 四、数据模型变更

| 介质 | 现状 | 变更 |
|------|------|------|
| SQLite `ur_nodes` | NodeType ∈ {node, input, output, event, config, checkpoint, keymapping, resource} | **+ `relation`**（声明关系节点，PayloadJson=声明记录） |
| SQLite `ur_tasks` | 任务=状态根 | 不变（task 关联经 `task.updateRelations` 增量维护） |
| SQLite | — | **+ `ur_relation_outbox`**（P2，关系同步日志） |
| LiteDB `graph-log.db` | `ur_references`（边）+ 内存端点 | **+ `ur_endpoints`**（端点符号落盘，可重建缓存） |

> 迁移兼容：旧数据无 `relation` 节点、无 outbox → `graph.rebuild` 走"纯推导"路径，行为与现状一致（向后兼容）。

## 五、实施步骤

| 阶段 | 内容 | 验收 |
|------|------|------|
| **P0 收敛** | 守卫统一端口；`AgentUiLibraryData`/存储桥改走守卫；协调器 Reconcile 内部化；删 `is not` 判断 | 现有测试不回归（StateManagement 47/47、Agent.Persistence 52/52）；无重复对账实现 |
| **P1 声明式构建** | `relations.declare/undeclare/list`、`task.updateRelations`、`graph.rebuild`、`NodeType=relation`、`ur_endpoints` 落盘 + 启动回填 | 声明→图可见、撤销→边清；rebuild 后 diff=0；重启符号保留 |
| **P2 补强** | outbox 同步器 + 崩溃回放；`graph.status/diff`；对账审计事件 | 模拟镜像同步失败后重启，图不丢（outbox 回放）；diff 报告可读 |

> 每阶段纯增量、可回退（P0 收敛后 P1 未做时行为与现状等价）。

## 六、风险与权衡

| 风险 | 权衡 |
|------|------|
| 新节点类型/集合迁移成本 | `graph.rebuild` 一键重建兜底；P0/P1 不引入 outbox，先解"分散/主动构建"主矛盾 |
| outbox 复杂度 | 小规模部署可只做 P0+P1（对账兜底够用）；outbox 为"不丢"保障，按需启用 |
| 声明与推导冲突 | 明确裁决规则（声明优先 + 审计事件），对账权威集 = 声明 ∪ 推导 |
| 守卫变胖风险 | 守卫只做"决策/编排"，写边原语仍在协调器（职责分层不合并） |

---

## 七、一句话总结

> **引用关系维护的完善 = 单一守卫入口收敛分散逻辑（消除双实现/双写入口）+ 声明式关系构建补上"主动写入"能力（relations.declare / task.updateRelations / graph.rebuild 全量重建）+ 端点落盘与 outbox 补强可靠性**——让图库从"被动派生的脆弱投影"演进为"声明可建、重建可跑、崩溃不丢、状态可查"的一等公民，权威始终在 SQL。
