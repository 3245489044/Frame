# 转接层集中重构方案（Relay Layer Consolidation）

> **位置**：本文为「转接层」的集中重构方案——把散布在四个程序集、三个命名空间间、约 16 个桥接组件的转接逻辑收敛为分层清晰、单一守卫、单一适配器的形态。回答「怎么做、按什么顺序、如何验证、可否回退」。
> **现状依据**：与 2026-08-19 代码同步（`Helpers/FacadeDataStore`、`WriteThroughNodeStore`、`ReferenceGrounding`、`NodeZoneStore`、`ReactiveZoneBridge`、`DataStoreEngine`、`StorageBridgeCommands` 等）。
> **对齐公理**：SingleImplementation / RedundancyElimination / LogicCorrectness / 单写入口 + 可重建投影 / 失败不阻断。
> **前置**：本方案为增量、可回退重构；每阶段独立可验证；不新增业务模块。

---

## 〇、优先级原则：先构建完善通用转接逻辑

**本方案的最高优先项是「先把通用的转接逻辑做对、做完整」，而不是先给某个具体业务路径打补丁。**

- **通用逻辑 = 转接层自身的基础设施**，指所有消费方共同依赖的机制：
  1. **单一写守卫端口**（`WriteGuardPort`）——"写完联动图+边"的唯一入口；
  2. **单一节点区适配器**（`ZoneNodeAdapter`）——"业务语义→NodeRecord"的唯一构造点；
  3. **整库写面统一经守卫**（`FacadeDataStore` 装配顺序修正）——守卫覆盖所有写径的结构保证；
  4. **节点分层契约**（zone/config/checkpoint/keymapping/relation 与业务节点的判别语义统一）。
- **为什么先做通用逻辑**：
  - 它们是转接层的**地基**。地基不完善，任何架在其上的流程（包括此前讨论的 **Cline→Answer→Cline 纯转接流水线**）都会持续踩同样的坑（如"写径绕过守卫""NodeRecord 构造分散"）。
  - 通用逻辑完善后，具体业务路径只是「按单一适配器/守卫接口声明节点引用与转接」，改造成本直线下降、且不再为个案引入重复逻辑。
  - 符合公理 **SingleImplementation / RedundancyElimination**：先消灭重复的横切结构，再谈业务扩展。
- **执行准则**：分阶段迁移（§四）以此原则排序——**先落地通用构件（Phase 1 `WriteGuardPort`、Phase 2 `ZoneNodeAdapter` 与装配修正），再处理转发链与读侧等外围收敛（Phase 3/4）**；在通用构件全部就绪前，不开展依赖具体路径的扩展。
- **验收锚点**：Phase 1-2 完成即证明"通用转接逻辑已完善"（构造单点 / 联动单点 / 守卫全覆盖均可验证），其后一切消费方（含 Cline↔Answer↔Cline）建立在该通用基座上。

## 一、现状盘点：转接层为什么散

### 1.1 组件全景（16 个桥接组件，散在 4 程序集）

| 程序集/命名空间 | 组件 | 职责 | 层 |
|----------------|------|------|----|
| `Agent.Runtime/Persistence` | `DataStoreEngine` | 内存⇄IDataStore 落盘桥 | 运行层 |
| `Operation.DataStoreDriven/Core` | `FacadeDataStore` | IDataStore 唯一门面 | 使用层 |
| `Operation.DataStoreDriven/Core` | `NodeZoneStore` | 三区逻辑名→节点文档 | 使用层 |
| `Operation.DataStoreDriven/Core` | `NodeConfigStore`/`NodeCheckpointStore`/`NodeExecutionService` | config/checkpoint 数行化、节点执行服务 | 使用层 |
| `Operation.DataStoreDriven/Core` | `WriteThroughNodeStore` | 业务节点写透图镜像/关系 | 使用层 |
| `Operation.DataStoreDriven/Core` | `ReferenceGrounding`/`NodeRelationDeriver` | 关系写守卫/边推导 | 使用层 |
| `Operation.DataStoreDriven/Graph` | `ReferenceGraphCoordinator` | LiteDB 唯一读写者 | 使用层 |
| `Agent.Core/DataStream` | `ReactiveZoneBridge`/`ZoneSignalPublisher`/`EventSink`/`ReactiveTrigger` | 写即触发、事件批写 | 核心 |
| `Agent.Core` | `OutputZoneWriter`/`RoundStateMapper`/`StateContextAdapter`/`DataContainerBinder` | 结果物化、状态外置、容器绑定 | 核心 |
| `Agent.StorageBridge/Storage` | `StorageBridgeCommands`/`PsRuntimeBinding` | Invoke-AgentStep 路由 | 存储桥 |

### 1.2 写给 `ur_nodes` 的门面就有 6 个

`NodeZoneStore`（三区）、`WriteThroughNodeStore`（业务节点+镜像）、`NodeConfigStore`、`NodeCheckpointStore`、`NodeExecutionService`、`StorageBridgeCommands`（resource/snapshot/checkpoint/config/zone/node 模板）——它们**各自包着同一个 `SqliteNodeStore.PutAsync`**，只是按 NodeType/用途套不同壳。

### 1.3 关键缺陷（LogicCorrectness，现成风险）

**写透守卫只对 `FacadeDataStore.Nodes` 生效，Zone/Config/Checkpoint 写径绕过守卫。**

- 组合根经 `FacadeDataStore.ReplaceNodeStore(WriteThroughNodeStore)` 把 `_nodes` 换成守卫包装（[FacadeDataStore#L62-L67](file:///d:/Project/Program/WorkFlowPrj/CsharpPrj/Operation/DataStoreDriven/Core/FacadeDataStore.cs#L62-L67)）。
- 但装配期**已先以原始 `SqliteNodeStore` 实例**构造了 `NodeZoneStore`/`NodeConfigStore`/`NodeCheckpointStore`/`SnapshotGraph`（`DataStoreProviderFactory` 映射），这些组件仍持原实例。
- 语义约束：节点库只对**业务节点**（NodeType=node）做图镜像/关系对账，zone/config/checkpoint 写不建镜像（`WriteThroughNodeStore.IsBusinessNode` 白名单）。**当前恰好不冲突，但暴露了两点**：
  1. 守卫的"单写入口"语义依赖"Zone/Config 恰好不需镜像"这一巧合，而非结构保证——任何人给 zone 配了关系或改了白名单即漂移。
  2. 转发链存在"同一守卫、多个装配形态"：业务节点写透单独走守卫，zone/config 各自直写底层，无统一归宿。

### 1.4 分散的三个轴

1. **同类职责重复**：`ReactiveZoneBridge`(写+发布)、`WriteThroughNodeStore`(写+镜像)、`ReferenceGrounding`(写+推导) 都是"写完再联动"，却分在不同组件。
2. **节点文档映射分散**：NodeZoneStore/NodeConfigStore/NodeCheckpointStore 各自构造 `NodeRecord`（键、payload、类型），缺单一"NodeType→业务语义"判别点。
3. **转发链偶有双层**：调用方→`AgentUiLibraryData`→Guard 的双层转发（§4.4）已去重，但 `AgentUiHost.ReferenceGrounding` 仍要做"装配期注入守卫"的显式接线（二态选择），未彻底内聚。

## 二、目标设计：收敛后的转接层形态

### 2.1 架构图

```
【业务方】LLM 回写 / 反应式触发 / 任务池 / 声明 / 确定性动作 / UI
   │  （调用方，不再内置节点文档构造）
   ▼
【节点区适配器 ZoneNodeAdapter】     ← 唯一"业务语义 → NodeRecord"映射点（按 NodeType 判别，含节点键/载荷/状态）
   │  ListInput/AppendOutput/AppendEvent/Config/Checkpoint → 生成 NodeRecord
   ▼
【写透守卫端口 WriteGuardPort】        ← 唯一"写完联动"入口（图镜像 + 边推导，替代分散的三处联动）
   │  幂等写底层
   ▼
【底层单真源】SqliteNodeStore.PutAsync / SqliteTaskPoolStore / ReferenceGraphCoordinator
```

收敛目标三条：
1. **单一节点区适配器**：`NodeRecord` 构造统一到一个适配器，按 `NodeType` 判别而非按用途各写一壳。
2. **单一写守卫端口**："写完联动图+边"收敛为守卫的唯一端口；三个原生 `INodeStore` 壳统一从该端口进底层。
3. **单层转发**：调用方 → 守卫 → 底层，删除中间门面转发与"装配期注入守卫的二态选择"。

### 2.2 不变式

| # | 不变式 | 说明 |
|---|--------|------|
| R1 | 物理单写源不变 | ur_nodes → `SqliteNodeStore.PutAsync`；ur_tasks → `SqliteTaskPoolStore`；LiteDB → `ReferenceGraphCoordinator` |
| R2 | 守卫对"所有业务写"统一生效 | 不依赖"zone 恰不需镜像"的巧合，而由结构保证 |
| R3 | 判别类型（zone/config/checkpoint/keymapping/relation）仍直写底层、不建镜像 | 语义不变；仅构造点收敛 |
| R4 | 失败不阻断 | 现有 try/catch 兜底语义保留 |
| R5 | 可回退 | 每阶段独立可开关，不改变存量数据/表结构 |

## 四、分阶段迁移（增量、每阶段可验证、可回退）

> 每阶段遵循：**先立回归护栏 → 改 → 验证 → 提交**；不改表结构、不改存量数据。用现有测试（`ReferenceGroundingWriteThroughTests` 等）作护栏。
> 阶段**排序严格执行 §〇 的优先级原则**：Phase 1/2 落通用构件（写守卫端口 + 节点区适配器），Phase 3/4 做外围收敛；通用构件就绪前，不切片到依赖具体路径的扩展。

### Phase 0：基线护栏（前置，不改业务）

- **目标**：确保改动前有可回归基线。
- **动作**：
  1. 全量跑 `DataStoreDriven` 相关测试，记录通过集合。
  2. 补一条"写透守卫覆盖面"测试：断言 `FacadeDataStore.Nodes`、`Zones`、`Config` 生产出的底层 UUID 都落 `SqliteNodeStore`（暴露 1.3 的装配漂移）。
- **验证**：测试绿；无行为变更。
- **回退**：仅新增测试，删即可回退。

### Phase 1：单一写守卫端口（收敛"写完联动"）

- **目标**：把"写完联动图+边"从三个组件收敛为 `WriteGuardPort` 一个端口。
- **动作**：
  1. 新建 `WriteGuardPort`，暴露 `WriteAsync(NodeRecord, bool deriveGraph)`；内部封装 `ReferenceGrounding.MirrorNodeAsync` + `NodeRelationDeriver` + `WriteRelationsAsync`。
  2. `WriteThroughNodeStore.PutAsync` 改调 `WriteGuardPort`，`IsBusinessNode` 白名单移入守卫。
  3. `NodeZoneStore`/`NodeConfigStore`/`NodeCheckpointStore` 底层由守卫构建（见 Phase 2 装配），使"判别类型"也经守卫直写底层（镜像与否由守卫白名单决定，不再依赖外壳）。
- **验证**：
  - 写业务节点 → LiteDB 镜像/边照旧。
  - 写 zone/config/checkpoint → 仅落 `ur_nodes`，不建镜像（回归 `ReferenceGroundingWriteThroughTests`）。
- **回退**：移除 `WriteGuardPort`，还原既有调用。

### Phase 2：单一节点区适配器（收敛 NodeRecord 构造）

- **目标**：`NodeZoneStore`/`NodeConfigStore`/`NodeCheckpointStore` 各自重复的 `NodeRecord` 构造收敛为 `ZoneNodeAdapter`。
- **动作**：
  1. 新建 `ZoneNodeAdapter`：单一入口 `Build(`nodeType, threadId, key, status, payload, relJson) → NodeRecord`，内含 `BuildNodeKey` 与空值归一化（迁移现有 `NodeZoneStore.BuildNodeKey`/`Normalize`）。
  2. 三个 Store 改为调用 `ZoneNodeAdapter.Build`，删除各自构造逻辑。
  3. `DataStoreProviderFactory`/`DataStoreHosting`：调整装配顺序——**先建 `WriteGuardPort`，再以守卫为底层**构造 Zone/Config/Checkpoint/SnapshotGraph，消除"绕组装漂移"（修复 1.3）。
- **验证**：
  - NodeKey 格式与空值归一化不变（`output:\<thread>:\<key>:\<guid>`）。
  - zone/config/checkpoint 读写回归通过。
- **回退**：可单独回退第一阶段或此阶段，二者无硬依赖。

### Phase 3：转发链单层化

- **目标**：删中间门面转发，保留"调用方 → 守卫"一层；去除"装配期注入守卫的二态选择"。
- **动作**：
  1. 审计 `AgentUiLibraryData` ↔ `AgentUiHost.ReferenceGrounding` ↔ Runtime 的转发路径，确认无第二层转发残留。
  2. 把守卫以单一注册方式注入节点执行服务（`NodeExecutionService` 注入 `WriteGuardPort`），删除 `is not WriteThroughNodeStore` 判断。
- **验证**：relations/graph 动作直通守卫；`NodeExecutionService` 无运行时类型分支。
- **回退**：还原转发注入点。

### Phase 4：读侧统一出口与冗余清删（可选）

- **目标**：读侧统一，清删已确认为冗余的转发方法。
- **动作**：
  1. 读侧统一收敛到单一出口（对齐现有 `GetNodeOutputsAsync`/`StorageBridgeCommands` 读路径，不新增重复读门面）。
  2. 依前置断言删除确认冗余的转发方法（如`宿己确认的 `WriteRelationsAsync` 转发包装）。
- **验证**：`graph.rebuild` 后 diff=0；读接口行为不变。
- **回退**：仅删除确认冗余者，其余保留。

## 七、总结

转接层分散的根因是**"写完联动"与"节点文档构造"两个横切职责在 6 个写门面里重复且装配顺序使守卫只覆盖部分写径**。本方案以 **`ZoneNodeAdapter`（构造单点）+ `WriteGuardPort`（联动单点）+ 装配顺序修正（守卫覆盖整库写面）** 三件事收敛，全程增量、可回退、保持"物理单写源"不变。核心顺序遵循 §〇：**先把这些通用转接逻辑做对、做完整，再言业务扩展**——对用户此前关心的 Cline→Answer→Cline 纯转接流水线而言，完善的通用转接基座（单一适配器/守卫、整库写面统一）正是它"复用节点、只转引用"所依赖的地基，地基落稳后该流程只是一次声明的串联。
