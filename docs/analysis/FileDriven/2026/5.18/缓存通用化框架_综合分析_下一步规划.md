## 三、已发现的遗留问题

### 3.1 WrokFlow_Script.cs 中的 `ConcurrentDictionary` 残留

**位置**：`WorkFlowMethod/WrokFlow_Script.cs`

虽然 `ReflectionHelper` 已改造为 `MemoryCache`，但文件中仍存在大量 `ConcurrentDictionary` 的 `using` 引用。需要检查是否还有其他地方使用了 `ConcurrentDictionary` 但未被改造。

**建议**：全局搜索 `ConcurrentDictionary` 在 `WorkFlowMethod` 中的使用，确认是否全部已替换。

### 3.2 MemoryCache 的 `GetOrAdd` 命名不一致

**问题**：`MemoryCache` 的方法名为 `GetOrAdd`，而 `WeakStateManager` 的方法名为 `GetOrCreate`。在 WdUI 改造中，`CacheConfigStage` 和 `ApplySplitterStage` 从 `GetOrCreateValue` 改为 `GetOrCreate`（对应 `WeakStateManager`），但 `RenderPipeline` 使用的是 `GetOrAdd`（对应 `MemoryCache`）。

**建议**：统一命名风格，建议 `MemoryCache` 也提供 `GetOrCreate` 别名方法，或者统一使用 `GetOrAdd`。

### 3.3 TreeCache 未被实际使用

**问题**：`TreeCache` 已创建但未被任何模块使用。`CacheConfigStage` 仍然使用手动递归 + `WeakStateManager.GetOrCreate` 的方式，没有使用 `TreeCache`。

**建议**：评估是否将 `CacheConfigStage` 的递归缓存逻辑迁移到 `TreeCache`。

## 七、架构原则总结

### 7.1 缓存选型决策树

```
需要为对象附加运行时状态？
├── 是 → 对象生命周期由 GC 管理？
│   ├── 是 → WeakStateManager<TKey, TState>
│   └── 否 → MemoryCache<TKey, TValue>
└── 否 → 需要防止重复操作？
    ├── 是 → DedupFlags<TKey>
    └── 否 → 需要树结构递归缓存？
        ├── 是 → TreeCache<TNode, TData>
        └── 否 → 使用普通 Dictionary/ConcurrentDictionary
```

### 7.2 使用规范

1. **优先使用通用缓存**：任何新的缓存需求，优先考虑 `WeakStateManager`、`DedupFlags`、`MemoryCache`、`TreeCache`
2. **避免直接使用 `ConcurrentDictionary`**：除非有特殊性能要求，否则使用 `MemoryCache` 包装
3. **避免直接使用 `ConditionalWeakTable`**：使用 `WeakStateManager` 或 `DedupFlags` 包装
4. **避免布尔标志去重**：使用 `DedupFlags` 替代 `IsXXXSubscribed` 等布尔字段
5. **命名统一**：`GetOrCreate`（WeakStateManager）、`GetOrAdd`（MemoryCache）— 后续考虑统一

## 八、风险与注意事项

1. **ConditionalWeakTable 的线程安全**：`GetOrCreateValue` 是线程安全的，但 `Add` 不是。`DedupFlags` 已通过 `lock` 解决。
2. **MemoryCache 的过期时间**：当前实现使用 `DateTime.UtcNow` 比较，需要注意系统时间调整的影响。
3. **TreeCache 的 CopyProperties**：使用反射复制属性，性能敏感场景需优化。
4. **向后兼容**：所有改造保持公共 API 不变，WdUI 和 FileDriven.UI 构建验证通过。
