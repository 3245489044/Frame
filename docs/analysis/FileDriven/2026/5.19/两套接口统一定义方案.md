# 两套接口统一定义方案

## 背景

当前存在两套接口定义：

| 项目 | 命名空间 | 用途 |
|------|---------|------|
| `FileDrivenFramework.Abstractions` | `FileDrivenFramework.Abstractions` | 旧接口，与 FileDriven 紧耦合 |
| `WorkFlowEngine.Abstractions` | `WorkFlowEngine.Abstractions` | 新接口，通用执行框架 |

两套接口存在大量重复定义（ICommandEngine、IWorkflowEngine、IFunctionRegistry 等），导致：
- 适配器需要做类型转换
- 新功能需要在两处同步修改
- 代码可读性下降

## 统一原则

以 **MetaCommandAdapter 中的通用逻辑** 为基准进行统一：

1. **MetaCommand.ICommandRouter** 是底层命令路由标准，`WorkFlowEngine.Abstractions.ICommandEngine` 应与之对齐
2. **异步优先**：所有执行方法统一为 `Task<T>` 异步签名
3. **最小接口**：接口只定义核心契约，实现细节由具体类完成
4. **向后兼容**：旧接口标记为 `[Obsolete]`，逐步迁移

## 一、ICommandEngine 统一方案

### 当前对比

| 方法 | FileDrivenFramework.Abstractions | WorkFlowEngine.Abstractions | MetaCommand.ICommandRouter |
|------|----------------------------------|---------------------------|---------------------------|
| 同步执行 | `Execute(string)` | ❌ 无 | ❌ 无 |
| 异步执行 | `ExecuteAsync(string)` | `ExecuteAsync(string)` | `ExecuteCommandAsync(string)` |
| 文件执行 | `ExecuteFileAsync(string)` | ❌ 无 | ❌ 无 |
| 注册处理器 | `RegisterHandler(string, Func<...>)` | `RegisterHandler(string, Func<...>)` | `RegisterAdapter(string, IEnvironmentAdapter)` |
| 注册异步处理器 | `RegisterAsyncHandler(string, Func<...>)` | ❌ 无 | ❌ 无 |
| 获取已注册命令 | `GetRegisteredCommands()` | `GetRegisteredCommands()` | `GetRegisteredAdapters()` |

### 统一后接口（以 WorkFlowEngine.Abstractions 为准）

```csharp
namespace WorkFlowEngine.Abstractions;

/// <summary>
/// 通用命令引擎 - 命令注册、解析、执行
/// 以 MetaCommand.ICommandRouter 为底层标准，通过适配器模式扩展
/// </summary>
public interface ICommandEngine
{
    /// <summary>异步执行命令</summary>
    Task<ICommandExecutionResult> ExecuteAsync(string command);

    /// <summary>从文件异步执行命令</summary>
    Task<ICommandBatchResult> ExecuteFileAsync(string filePath);

    /// <summary>注册命令处理器（异步）</summary>
    void RegisterHandler(string commandName, Func<string[], Task<ICommandExecutionResult>> handler);

    /// <summary>获取已注册命令列表</summary>
    IEnumerable<string> GetRegisteredCommands();
}

/// <summary>命令执行结果</summary>
public interface ICommandExecutionResult
{
    bool Success { get; }
    string Command { get; }
    object? Value { get; }
    string? Error { get; }
    TimeSpan Elapsed { get; }
}

/// <summary>批量命令执行结果</summary>
public interface ICommandBatchResult
{
    int TotalCount { get; }
    int SuccessCount { get; }
    int FailCount { get; }
    bool IsAllSuccess { get; }
    bool Success { get; }
    string? Error { get; }
    IReadOnlyList<ICommandExecutionResult> Results { get; }
}
```

### 变更说明

| 变更项 | 说明 |
|--------|------|
| ❌ 移除 `Execute(string)` 同步方法 | 统一使用异步，同步调用方自行 `.GetAwaiter().GetResult()` |
| ❌ 移除 `RegisterAsyncHandler` | 统一使用 `RegisterHandler`（全部异步） |
| ✅ 保留 `ExecuteFileAsync` | 从 FileDrivenFramework 合并过来，通用功能 |
| ✅ 保留 `ICommandBatchResult` | 从 FileDrivenFramework 合并过来 |
| 🔄 `ICommandExecutionResult.Value` 改为 `object?` | 与 MetaCommand.OperationResult.Data 对齐 |

## 二、IWorkflowEngine 统一方案

### 当前对比

| 方法 | FileDrivenFramework.Abstractions | WorkFlowEngine.Abstractions |
|------|----------------------------------|---------------------------|
| 执行工作流（按名称） | `ExecuteWorkflowAsync(string, string)` | `ExecuteWorkflowAsync(string, string)` |
| 执行工作流（按定义） | `ExecuteWorkflowAsync(IWorkflowDefinition, string)` | `ExecuteWorkflowAsync(IWorkflowDefinition, string)` |
| 加载工作流 | `LoadWorkflow(string)` | `LoadWorkflow(string)` |
| 获取工作流 | `GetWorkflow(string)` | `GetWorkflow(string)` |
| 获取所有名称 | `GetAllWorkflowNames()` | `GetAllWorkflowNames()` |
| 注册工作流 | `RegisterWorkflow(IWorkflowDefinition)` | `RegisterWorkflow(IWorkflowDefinition)` |
| 清空缓存 | `ClearCache()` | ❌ 无 |
| 设置配置路径 | ❌ 无 | `SetConfigBasePath(string)` |

### 统一后接口（以 WorkFlowEngine.Abstractions 为准）

```csharp
namespace WorkFlowEngine.Abstractions;

/// <summary>
/// 通用工作流引擎 - 加载并执行工作流定义
/// 支持线性执行和图结构执行两种模式
/// </summary>
public interface IWorkflowEngine
{
    /// <summary>从文件加载工作流定义</summary>
    IWorkflowDefinition? LoadWorkflow(string filePath);

    /// <summary>按名称获取工作流定义</summary>
    IWorkflowDefinition? GetWorkflow(string workflowName);

    /// <summary>执行工作流（按名称）</summary>
    Task<string> ExecuteWorkflowAsync(string workflowName, string input);

    /// <summary>执行工作流定义</summary>
    Task<string> ExecuteWorkflowAsync(IWorkflowDefinition definition, string input);

    /// <summary>注册工作流定义</summary>
    void RegisterWorkflow(IWorkflowDefinition definition);

    /// <summary>获取所有工作流名称</summary>
    IEnumerable<string> GetAllWorkflowNames();

    /// <summary>设置工作流配置文件路径</summary>
    void SetConfigBasePath(string basePath);

    /// <summary>清空工作流缓存</summary>
    void ClearCache();
}
```

### 变更说明

| 变更项 | 说明 |
|--------|------|
| ✅ 保留 `ClearCache()` | 从 FileDrivenFramework 合并过来 |
| ✅ 保留 `SetConfigBasePath(string)` | 从 WorkFlowEngine 保留 |

## 三、IWorkflowDefinition / IWorkflowStep 统一方案

### 当前对比

两个项目的接口定义完全一致，无需修改：

```csharp
public interface IWorkflowDefinition
{
    string WorkflowName { get; }
    string DisplayName { get; }
    string Description { get; }
    string Version { get; }
    IReadOnlyList<IWorkflowStep> Steps { get; }
    IReadOnlyDictionary<string, string> OutputMapping { get; }
}

public interface IWorkflowStep
{
    string StepName { get; }
    string FuncName { get; }
    IReadOnlyList<string> InputKeys { get; }
    string OutputKey { get; }
    IReadOnlyList<string> Parameters { get; }
}
```

### 实现类

`WorkFlowEngine.Abstractions.Models` 中已有完整实现：

- `WorkflowDefinition` - 带 `[JsonPropertyName]` 属性，支持 JSON 反序列化
- `WorkflowStep` - 同上

**FileDrivenFramework.Core 中的实现应废弃**，统一使用 `WorkFlowEngine.Abstractions.Models`。

## 四、IFunctionRegistry 统一方案

### 当前对比

| 方法 | FileDrivenFramework.Abstractions | WorkFlowEngine.Abstractions |
|------|----------------------------------|---------------------------|
| 注册函数 | `Register(string, Delegate, string?)` | `Register(string, Delegate, string?)` |
| 注册异步函数 | ❌ 无 | `RegisterAsync(string, Func<WorkflowContext, Task<object>>)` |
| 注册工作流函数 | ❌ 无 | `RegisterFunction(string, Func<WorkflowContext, object>)` |
| 执行函数 | ❌ 无 | `ExecuteAsync(string, object?)` |
| 注销函数 | `Unregister(string)` | ❌ 无 |
| 获取描述符 | `TryGetDescriptor(string, out IFunctionDescriptor)` | ❌ 无 |
| 获取已注册名称 | `GetRegisteredNames()` | `GetRegisteredNames()` |
| 检查是否存在 | `Contains(string)` | `Contains(string)` |
| 清空 | `Clear()` | ❌ 无 |

### 统一后接口（以 WorkFlowEngine.Abstractions 为准）

```csharp
namespace WorkFlowEngine.Abstractions;

/// <summary>
/// 通用函数注册表 - 统一管理函数的注册、查找与执行
/// </summary>
public interface IFunctionRegistry
{
    /// <summary>注册函数（委托方式）</summary>
    void Register(string name, Delegate function, string? description = null);

    /// <summary>注册异步函数</summary>
    void RegisterAsync(string name, Func<WorkflowContext, Task<object>> func);

    /// <summary>注册工作流函数</summary>
    void RegisterFunction(string name, Func<WorkflowContext, object> func);

    /// <summary>执行函数</summary>
    Task<IFunctionExecutionResult> ExecuteAsync(string functionName, object? parameters = null);

    /// <summary>注销函数</summary>
    void Unregister(string name);

    /// <summary>获取已注册函数名称</summary>
    IEnumerable<string> GetRegisteredNames();

    /// <summary>检查函数是否存在</summary>
    bool Contains(string name);

    /// <summary>清空所有注册</summary>
    void Clear();
}

public interface IFunctionExecutionResult
{
    bool IsSuccess { get; }
    object? Value { get; }
    string? ErrorMessage { get; }
    TimeSpan ExecutionTime { get; }
}
```

### 变更说明

| 变更项 | 说明 |
|--------|------|
| ✅ 保留 `Unregister(string)` | 从 FileDrivenFramework 合并过来 |
| ✅ 保留 `Clear()` | 从 FileDrivenFramework 合并过来 |
| ✅ 保留 `RegisterAsync` / `RegisterFunction` | 从 WorkFlowEngine 保留 |
| ✅ 保留 `ExecuteAsync` | 从 WorkFlowEngine 保留 |
| ❌ 移除 `TryGetDescriptor` | 过于具体，非核心契约 |
| ❌ 移除 `IFunctionDescriptor` / `IParameterDescriptor` | 非核心契约 |

## 九、迁移计划

### 阶段一：接口定义更新（当前任务）

1. 在 `WorkFlowEngine.Abstractions` 中补充缺失的接口：
   - `ICommandBatchResult`
   - `IFunctionRegistry.Unregister()`
   - `IFunctionRegistry.Clear()`
   - `IWorkflowEngine.ClearCache()`

2. 在 `FileDrivenFramework.Abstractions` 中标记废弃：
   - 所有接口添加 `[Obsolete]` 属性
   - 注释中指明替代接口

### 阶段二：实现类迁移

1. `FileDrivenFramework.Core.CommandEngine` → 改为实现 `WorkFlowEngine.Abstractions.ICommandEngine`
2. `FileDrivenFramework.Core.WorkflowEngine` → 改为实现 `WorkFlowEngine.Abstractions.IWorkflowEngine`
3. `FileDrivenFramework.Core.FunctionRegistry` → 改为实现 `WorkFlowEngine.Abstractions.IFunctionRegistry`
4. `PipelineAdapter` / `MetaCommandAdapter` → 改为引用 `WorkFlowEngine.Abstractions` 接口

### 阶段三：引用方更新

1. `FileDriven.UI` / `FileDriven.CLI` / `FileDriven.Launcher` → 改用新接口
2. 移除对 `FileDrivenFramework.Abstractions` 的引用

### 阶段四：清理

1. 删除 `FileDrivenFramework.Abstractions` 项目
2. 删除 `FileDrivenFramework.Core` 中的冗余实现类

## 十、与 MetaCommand 的对应关系

以 MetaCommandAdapter 为基准，`WorkFlowEngine.Abstractions.ICommandEngine` 与 `MetaCommand.ICommandRouter` 的对应关系：

| WorkFlowEngine.Abstractions | MetaCommand.ICommandRouter | 说明 |
|---------------------------|---------------------------|------|
| `ExecuteAsync(string)` | `ExecuteCommandAsync(string)` | 直接委托 |
| `RegisterHandler(string, Func<...>)` | `RegisterAdapter(string, IEnvironmentAdapter)` | 适配器模式，ICommandRouter 通过 IEnvironmentAdapter 扩展 |
| `GetRegisteredCommands()` | `GetRegisteredAdapters()` | 返回已注册的适配器 ID 列表 |
| `ICommandExecutionResult` | `OperationResult<object>` | MetaCommand 的通用结果类型 |

**核心思想**：`WorkFlowEngine.Abstractions.ICommandEngine` 是面向业务的高级抽象，`MetaCommand.ICommandRouter` 是面向底层的基础设施。两者通过 `MetaCommandAdapter` 桥接。
