# 事件体系分析与集中整理方案

## 一、事件逻辑现状分析

经过深入阅读所有相关文件，梳理出当前事件体系的全貌。

### 1.1 当前事件体系存在 3 条独立的事件处理路径

#### 路径 A：WinForms 原生事件绑定（MainForm 手动绑定）

| 方法 | 绑定的控件/事件 |
|------|----------------|
| `BindToolbarButtons()` | loadConfigButton.Click、loadWorkflowButton.Click、clearButton.Click、helpButton.Click、loadSideButton.Click |
| `BindCommandEvents()` | commandTextBox.KeyPress、executeButton.Click |
| `OnConfigSelectorLoaded()` | searchTextBox.TextChanged、configListView.SelectedIndexChanged/DoubleClick、loadSelButton.Click、browseButton.Click、enableProcessingCheckBox.CheckedChanged |

**特点：** 硬编码、手动 `FindControl` + 注册事件处理器

#### 路径 B：CLI 命令驱动的事件触发（EventTriggerService）

| 组件 | 说明 |
|------|------|
| `BackendCommandAdapter` | 通过 EventTriggerService 触发 click 事件 |
| `GuiCommandAdapter` | 通过 EventTriggerService 触发 click 事件 |

**特点：** 通过配置驱动，但 GUI/Backend 两条路径实现不同

#### 路径 C：事件触发服务层

| 组件 | 说明 |
|------|------|
| `EventTriggerService` | 统一处理控件事件触发，ComboBox 走专用管线 |
| `EventBindingResolver` | 从 ControlConfig.Events 中提取事件绑定的函数名 |

**特点：** 通用抽象层

### 1.2 核心问题

1. **MainForm 中的事件绑定是硬编码的**，与 JSON 配置中的事件绑定（ControlConfig.Events）是两套独立体系
2. **GUI 模式下 click 走 `btn.PerformClick()`**，触发的是 WinForms 原生事件；**Backend 模式下 click 走 `EventTriggerService`**，触发的是配置中绑定的函数——两条路径语义不同
3. **事件绑定逻辑散布在 4 个层**：UI 层（MainForm）、命令层（UICommandManager）、适配器层（GuiCommandAdapter/BackendCommandAdapter）、服务层（EventTriggerService/EventBindingResolver）

## 二、BasicMethod.Framework 与 Share.EventTriggerFramework 功能重叠分析

### 2.1 关键发现

**`FileDriven.CLI` 实际使用的是 `Share\EventTriggerFramework`，而非 `BasicMethod\Framework`**

从 `FileDriven.CLI/Services/EventTriggerService.cs` 和 `EventBindingResolver.cs` 的 using 语句可以确认：
```csharp
using EventTriggerFramework.Abstractions;  // ← Share 版本
using EventTriggerFramework.Core;          // ← Share 版本
```

### 2.2 两者是"同源分支"关系

| 对比维度 | `BasicMethod\Framework` | `Share\EventTriggerFramework` |
|---------|----------------------|------------------------------|
| 命名空间 | `BasicMethod.Framework` | `EventTriggerFramework` |
| EventBindingResolverBase | 只有模式 B（两步走） | 模式 A + 模式 B 双支持 |
| EventTriggerServiceBase | 简单版，参数 `IReadOnlyList<object?>` | 增强版，参数 `Dictionary<string, string?>`，支持输入值提取 |
| IEventTriggerResult | 独立接口 | 基于统一 `Result<T>` |
| WinForms 支持 | 无 | 有 `WinForms/` 子目录 |
| Pipeline 支持 | 无 | 有 `Pipeline/` 子目录 |
| 额外功能 | EventBus（事件总线） | EventBus + EventPipeline + ResolverRegistry + Skeletons |

### 2.3 结论

**`BasicMethod\Framework` 中的事件相关文件是过时的旧版本，已全部删除。**

## 三、最终架构（改造后现状）

### 3.1 核心思路

**将 JSON 配置 events 与 WinFormsEventRegistrar 两套体系打通，以 JSON 配置为主。**

即：UI 点击和 CLI click 在 `EventTriggerService.TriggerEventAsync` 处完全统一，`DefaultEventBindingService` 负责将 JSON 配置中的事件绑定到 WinForms 原生事件，并委托给 `EventTriggerService` 执行。

### 3.2 架构分层

```
Share/EventTriggerFramework/          ← 纯抽象框架层，不依赖任何 UI 技术
  ├── Abstractions/                   ← 接口定义（IEventBindingService, IEventTriggerService 等）
  ├── Core/                           ← 抽象基类（EventTriggerServiceBase 等）
  ├── Models/                         ← 数据模型
  ├── DefaultEventBindingService.cs   ← IEventBindingService 默认实现
  └── EventBus.cs                     ← 事件总线（纯抽象）

FileDriven.CLI/Services/              ← CLI 服务层
  ├── EventTriggerService.cs          ← IEventTriggerService 实现（统一触发管线）
  └── EventBindingResolver.cs         ← IEventBindingResolver 实现（绑定解析）

FileDriven.UI/                        ← WinForms UI 层
  ├── Utils/
  │    └── WinFormsEventRegistrar.cs  ← 代码驱动的事件注册工具类
  ├── Core/
  │    └── MainForm.cs                ← 使用 WinFormsEventRegistrar
  └── Commands/
       └── UICommandManager.cs        ← 使用 WinFormsEventRegistrar
```

### 3.3 统一执行路径

```
┌─────────────────────────────────────────────────────────────────┐
│                    JSON 配置 (events 字段)                        │
│  { "events": { "click": "functionName", "textchanged": "..." } } │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 解析
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                    EventBindingResolver                          │
│  (直接实现 IEventBindingResolver，无模式 A/B 分支)                │
│  FindEventBinding(controlName, eventType) → IEventBindingInfo    │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 查找结果
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                    EventTriggerService                           │
│  (接口注入: IEventBindingResolver + IValueExtractor)              │
│  TriggerEventAsync(controlName, eventType, value)                │
│    ├─ 查找绑定 → 执行函数 → 写入输出                               │
│    └─ ComboBox 复用主管线查找结果                                  │
└──────┬───────────────────────────────────────┬──────────────────┘
       │                                       │
       ▼                                       ▼
┌──────────────┐                    ┌──────────────────────┐
│ GUI 模式     │                    │ CLI 模式              │
│ GuiCommand   │                    │ BackendCommand       │
│ Adapter      │                    │ Adapter              │
│ (真实控件)   │                    │ (虚拟控件)            │
└──────────────┘                    └──────────────────────┘
       │                                       │
       ▼                                       ▼
┌──────────────────────────────────────────────────────────────────┐
│                    WinForms 原生事件绑定                          │
│  DefaultEventBindingService (switch 替代反射，支持 CustomEvents)  │
│    ├─ 命名方法事件处理器（支持 -= 取消绑定）                       │
│    ├─ 传递实际事件类型（非硬编码 "click"）                         │
│    └─ 提取控件实际值（Text/Checked/Value 等）                     │
│  WinFormsEventRegistrar (仅代码驱动，无 RegisterFromConfig)       │
└──────────────────────────────────────────────────────────────────┘
```

### 3.4 关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 事件绑定方式 | JSON 配置驱动为主，代码驱动为辅 | 配置驱动可动态修改，无需重新编译 |
| 事件触发管线 | 统一走 EventTriggerService | UI 点击和 CLI click 行为一致 |
| 事件类型传递 | 传递实际事件类型 | EventBindingResolver 能正确查找对应绑定 |
| 事件处理器 | 命名方法（非匿名委托） | 支持 -= 取消绑定，与 UICommandManager 事件抑制兼容 |
| 事件解析方式 | switch（非反射） | 与 EventBindingResolver 一致，性能更好 |
| CustomEvents | 支持 | 兼容自定义事件类型 |
| 依赖注入 | 接口注入（非构造函数直接 new） | 支持单元测试 mock |
| 僵尸基类 | 删除 | 消除维护者困惑 |
| IEventTriggerService 注入 | 延迟注入（SetXxx 模式） | 组件创建顺序不同，启动器负责桥接 |

### 3.5 组件依赖关系

```
FrameworkInitializer.Initialize()
  └─ RegisterComponents()
       └─ new DefaultEventBindingService()  ← _eventTriggerService = null (安全)
                                              ↓
GuiModeRunner.Run()
  ├─ new GuiCommandAdapter(uiManager)
  │    └─ new EventTriggerService(resolver, extractor)
  ├─ ComponentRegistry.Resolve<IEventBindingService>()
  │    └─ defaultBinding.SetEventTriggerService(guiAdapter.EventTriggerService)
  │         └─ _eventTriggerService = eventTriggerService  ← 注入完成
  └─ mainForm.LoadConfigAsync(configPath)
       └─ DefaultEventBindingService.BindEvents()
            └─ FireAndForgetTriggerAsync()
                 └─ _eventTriggerService.TriggerEventAsync()  ← 正常调用
```

## 四、已完成的改造工作

### 4.1 阶段一：新增 WinFormsEventRegistrar（统一注册入口）

**初始位置：** `Share/EventTriggerFramework/WinForms/WinFormsEventRegistrar.cs`
**最终位置：** `FileDriven.UI/Utils/WinFormsEventRegistrar.cs`

提供一组静态泛型方法，统一 WinForms 控件的事件注册风格。使用纯 WinForms 的 `Controls.Find` 进行递归查找，不依赖任何外部框架。

### 4.2 阶段二：改造 MainForm.cs 中的事件绑定

`BindToolbarButtons()`、`BindCommandEvents()`、`OnConfigSelectorLoaded()` 中的硬编码事件注册已替换为 `WinFormsEventRegistrar.RegisterXxx()` 调用。

### 4.3 阶段三：统一 Click 命令执行路径

**`GuiCommandAdapter.DoClickAsync()`** — 统一走 `EventTriggerService`：
- 不再委托 `UICommandManager.ClickControlAsync()`（走 `btn.PerformClick()`）
- 改为调用 `_eventTriggerService.TriggerEventAsync(target, "click", "")`
- 与 `BackendCommandAdapter.DoClickAsync()` 完全一致

**统一后的 click 路径：**
```
GuiCommandAdapter.DoClickAsync() ──→ EventTriggerService.TriggerEventAsync()
BackendCommandAdapter.DoClickAsync() ──→ EventTriggerService.TriggerEventAsync()
```

### 4.4 阶段四：将按钮事件迁移到 JSON 配置

`MainLayout.json` 和 `ConfigSelector.json` 中已补充按钮的 `Events` 配置：

| 配置文件 | 按钮名 | 事件 | 函数名 |
|---------|--------|------|--------|
| MainLayout.json | loadConfigButton | click | `LoadConfigButton_Click` |
| MainLayout.json | loadWorkflowButton | click | `LoadWorkflowButton_Click` |
| MainLayout.json | clearButton | click | `ClearOutput` |
| MainLayout.json | helpButton | click | `ShowHelp` |
| MainLayout.json | loadSideButton | click | `LoadSidePanel` |
| ConfigSelector.json | loadSelButton | click | `LoadSelectedConfig` |
| ConfigSelector.json | browseButton | click | `BrowseConfigFile` |

### 4.5 阶段五：修正 WinFormsEventRegistrar 位置

将 `WinFormsEventRegistrar` 从 `Share/EventTriggerFramework/WinForms/` 迁移到 `FileDriven.UI/Utils/`，保持 `EventTriggerFramework` 纯抽象。

### 4.6 第一轮框架级重构：DefaultEventBindingService 直接绑定 WinForms 原生事件

**核心思路：** `DefaultEventBindingService` 不再直接调用 `FunctionExecutionFramework.ExecuteAsync`，而是通过 `IEventTriggerService`（即 `EventTriggerService`）的统一管线来执行。

**改造内容：**
1. `DefaultEventBindingService` 构造函数接受 `IEventTriggerService` + `WinFormsEventBus`（可选）
2. 标准事件直接使用 `+=` 绑定，在 UI 线程上同步触发
3. 事件处理器内部委托给 `IEventTriggerService.TriggerEventAsync`，走统一管线
4. `EventTriggerService.WriteOutputAsync` 支持 GUI 模式：当 `TargetForm` 不为 null 时，将结果写入真实控件

### 4.7 第二轮框架级重构：消除 6 个架构级缺陷

| # | 缺陷 | 改造内容 | 状态 |
|---|------|---------|------|
| 10.1 | FireAndForgetTriggerAsync 硬编码 "click" | 传递实际事件类型 | ✅ |
| 10.2 | GuiCommandAdapter 双重写入 | 移除手动写入，完全依赖 EventTriggerService.WriteOutputAsync | ✅ |
| 10.3 | EventBindingResolver 模式 A 返回 null | 直接实现 IEventBindingResolver，移除 EventBindingResolverBase 继承 | ✅ |
| 10.4 | WinFormsEventRegistrar 功能重叠 | 移除 RegisterFromConfig 死代码 | ✅ |
| 10.5 | ComboBox 专用管线重复查找 | 优化管线流程，复用主管线查找结果 | ✅ |
| 10.6 | 构造函数直接 new 依赖项 | 改为接口注入（IEventBindingResolver + IValueExtractor） | ✅ |

### 4.8 第三轮框架级重构：消除 7 个不完全重构与缺陷

| # | 缺陷 | 改造内容 | 状态 |
|---|------|---------|------|
| 1 | EventBindingResolverBase 成为僵尸基类 | 删除整个文件 | ✅ |
| 2 | FireAndForgetTriggerAsync 参数顺序不一致 | 调整为 (controlName, eventType, value) | ✅ |
| 3 | BindControlEvents 用反射 vs GetEventFunction 用 switch | 改用 switch 替代反射 | ✅ |
| 4 | BindControlEvents 未处理 CustomEvents 字典 | 增加 CustomEvents 处理 | ✅ |
| 5 | GuiCommandAdapter 缺少注释说明 | 添加 VirtualControlStore 设计意图注释 | ✅ |
| 6 | 匿名委托与事件抑制逻辑冲突 | 改为命名方法，支持 -= 取消绑定 | ✅ |
| 7 | WinFormsEventRegistrar 注释过时 | 更新注释，移除 RegisterFromConfig 说明 | ✅ |

### 4.9 第五轮修复：DefaultEventBindingService 延迟注入 IEventTriggerService

**问题：** `FrameworkInitializer.RegisterComponents()` 创建 `DefaultEventBindingService` 时，`EventTriggerService` 尚未创建。

**解决方案：**
1. `DefaultEventBindingService` 构造函数改为可选参数 `IEventTriggerService? = null`
2. 增加 `SetEventTriggerService()` 方法支持延迟注入
3. `FireAndForgetTriggerAsync()` 增加 null 检查，安全跳过
4. `GuiModeRunner.Run()` 负责从 `ComponentRegistry` 获取 `IEventBindingService` 并注入

**架构原则：**
- `DefaultEventBindingService` 不引用 `FrameworkAbstractions`，保持 `Share` 项目独立性
- `GuiModeRunner` 作为启动器负责桥接组件间的依赖注入
- 防御性编程：`_eventTriggerService` 为 null 时安全跳过，不抛出异常

## 七、仍存在的待改进项

以下问题经分析确认存在，但尚未实施改造：

### 7.1 GuiCommandAdapter.DoLoadAsync 重复解析配置 ⚠️

**问题：** GuiCommandAdapter 的 load 命令委托给 `MainForm.LoadSideContainerAsync` 完成加载后，又**重复调用** `WdUIComposer.LoadConfigAsync` 解析配置（GuiCommandAdapter.cs L243）。同一个配置文件被解析了两次。

**改进建议：** 让 `MainForm.LoadSideContainerAsync` 返回加载后的配置元信息，或通过回调/事件将配置信息传递给 GuiCommandAdapter。

### 7.2 OnConfigSelectorLoaded 中仍有硬编码事件注册 ⚠️

**问题：** `MainForm.cs` 的 `OnConfigSelectorLoaded` 方法中，`configListView.SelectedIndexChanged`、`configListView.DoubleClick`、`enableProcessingCheckBox.CheckedChanged` 三个事件注册**没有使用 WinFormsEventRegistrar**，仍然是直接 `+=` 绑定。

**改进建议：** 将这三个事件注册也改为 WinFormsEventRegistrar 调用，保持代码风格一致。

### 7.3 executeButton 的 JSON 配置函数名与实际不一致 ⚠️

**问题：**
- `MainLayout.json` 中：`"events": { "click": "ExecuteCommand" }`
- `MainForm.cs` 中：`WinFormsEventRegistrar.RegisterClick(_rootContainer, "executeButton", ExecuteButton_Click);`

JSON 配置中声明的函数名是 `"ExecuteCommand"`，但实际注册的处理器是 `ExecuteButton_Click`。如果通过 CLI `click executeButton` 命令触发，EventTriggerService 会查找名为 `"ExecuteCommand"` 的函数，而实际 MainForm 中注册的是 `ExecuteButton_Click`。

**改进建议：** 统一命名，将 JSON 配置改为 `"click": "ExecuteButton_Click"`，或将 MainForm 中的处理器重命名为 `ExecuteCommand`。

### 7.4 后续优化建议

1. **单元测试覆盖：** 接口注入改造后，EventTriggerService 可轻松注入 mock 的 IEventBindingResolver 和 IValueExtractor 进行单元测试
2. **EventBindingResolver 单元测试：** 直接实现 IEventBindingResolver 后，可独立测试绑定解析逻辑
3. **DefaultEventBindingService 集成测试：** 验证 WinForms 原生事件触发后能正确委托给 EventTriggerService
4. **ComboBox 事件抑制：** 当前 ComboBox 的 SelectedIndexChanged 事件抑制逻辑在 UICommandManager 中，建议后续统一到 EventTriggerService 中管理
