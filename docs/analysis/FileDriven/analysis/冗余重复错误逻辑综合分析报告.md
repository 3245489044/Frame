## 一、错误逻辑（Bugs）

### B1（P0）: `FileDrivenLogManager.Shutdown()` 中 Console/Database 模式的摘要输出重复

- **位置**: `FileDriven.Logging/FileDrivenLogManager.cs` 第 130-183 行
- **问题**: Console 模式（第 130-149 行）和 Database 模式（第 153-184 行）各自独立实现了几乎相同的摘要输出逻辑：

  **Console 模式（第 144-148 行）：**
  ```csharp
  Console.WriteLine($"\n===== 批次日志摘要 =====");
  Console.WriteLine($"  批次: {targetBatchId ?? "(无批次)"}");
  Console.WriteLine($"  日志数: {logCount}");
  Console.WriteLine($"  所有批次:");
  Console.WriteLine(BatchManager.Instance.GetSummary());
  ```

  **Database 模式（第 179-183 行）：**
  ```csharp
  Console.WriteLine($"\n===== 批次日志摘要 =====");
  Console.WriteLine($"  批次: {targetBatchId}");
  Console.WriteLine($"  日志数: {logCount}");
  Console.WriteLine($"  所有批次:");
  Console.WriteLine(BatchManager.Instance.GetSummary());
  ```

  两段代码几乎完全一致，修改一处忘记同步另一处会导致行为不一致。

- **严重度**: P0 — 代码重复，维护风险高
- **建议修复**: 提取为共享方法 `PrintSummary(string batchId, int logCount)`

### B2（P0）: Console 模式直接使用 `Console.WriteLine` 而非日志系统

- **位置**: `FileDriven.Logging/FileDrivenLogManager.cs` 第 130-149 行
- **问题**: Console 模式使用 `Console.WriteLine` 直接输出摘要，而 Database 模式使用 `LogPipeline.ExecuteWithExceptionHandling()` 通过 `LogSummarySkeleton` 输出。两种模式输出路径不一致，Console 模式的摘要不受 `LogController` 控制。
- **严重度**: P0 — 日志输出路径不统一
- **建议修复**: Console 模式也应通过 `LogSummarySkeleton` 或至少通过 `FileDrivenLogPlaceholderHandler.Log()` 输出

### B3（P1）: `FileDrivenPipelineContext` 使用 `new` 覆盖父类属性破坏多态性

- **位置**: `FileDriven.Pipeline/FileDrivenPipelineContext.cs` 第 358-365 行
- **问题**: 使用 `new` 关键字覆盖父类 `CommandContext` 的同名属性 `IsGuiMode` 和 `IsCliMode`：

  ```csharp
  public new bool IsGuiMode => TargetForm != null;
  public new bool IsCliMode => VirtualStore != null && TargetForm == null;
  ```

  父类 `CommandContext` 的 `IsGuiMode` 检查的是 `Mode == "GUI"`（第 321 行设置了 `context.Mode = "GUI"`）。但：
  - 通过 `CommandContext` 引用访问 → 得到父类实现（检查 Mode 字符串）
  - 通过 `FileDrivenPipelineContext` 引用访问 → 得到子类实现（检查 TargetForm）
  - **多态性被破坏**，行为取决于引用类型而非实际类型

- **严重度**: P1 — 可能导致 GUI/CLI 模式判断不一致
- **建议修复**: 移除 `new` 关键字，改为在构造函数中正确设置 `Mode` 属性，或重写（override）父类的虚方法

### B4（P1）: `NonEventCommandHandler` 中 action 获取逻辑可能产生误导性错误

- **位置**: `FileDriven.Pipeline/Skeletons/NonEventCommandHandler.cs` 第 58-68 行
- **问题**: 当 `ParsedAction` 为 null 时回退到 `ParsedVerb.ToString().ToLowerInvariant()`，但 `ParsedVerb` 的默认值是 `MetaVerb.Do`。虽然第 63 行有 `action == "do"` 的检查，但错误信息 "Non-event command action is required" 不够明确，没有说明实际收到的值是什么。
- **严重度**: P1 — 错误信息不够清晰，不利于调试
- **建议修复**: 改进错误信息，包含实际收到的 action 值

### B5（P1）: `PipelineEntry.CreateContext()` 中 `LoadedConfigs` 浅拷贝非真正快照

- **位置**: `FileDriven.Pipeline/PipelineEntry.cs` 第 302 行
- **问题**: 注释说"浅拷贝确保创建时刻的配置快照"，但 `_loadedConfigs` 中存储的是 `LoadedConfigInfo` 包装对象（引用类型）。浅拷贝只复制了字典结构，**内部对象仍然是同一引用**：

  ```csharp
  LoadedConfigs = new Dictionary<string, object>(_loadedConfigs, StringComparer.OrdinalIgnoreCase),
  ```

  如果后续修改了 `LoadedConfigInfo` 内部的 `Config` 属性，上下文中的配置也会被影响。这不是真正的"快照"。

- **严重度**: P1 — 文档与实现不一致
- **建议修复**: 要么实现深拷贝，要么更新注释说明这是"引用共享"而非"快照"

### B6（P2）: `LogPipelineContext` 中 `EnabledCategories` 类型不一致

- **位置**: 
  - `FileDriven.Logging/LogPipeline.cs` 第 100 行：`LogCategory EnabledCategories`
  - `FileDriven.Logging/BatchContextData.cs` 第 41 行：`string EnabledCategories`
- **问题**: `LogPipelineContext.EnabledCategories` 是 `LogCategory` 枚举类型，而 `BatchContextData.EnabledCategories` 是 `string` 类型。`FileDrivenPipelineContext` 通过 `BatchData` 委托访问的是 `string` 类型。在 `FileDrivenBootstrapper.cs` 第 726 行：

  ```csharp
  context.EnabledCategories = options.LogCategories.ToString();
  ```

  这里设置的是 `BatchData.EnabledCategories`（string），而 `LogPipelineContext` 的 `EnabledCategories` 属性（LogCategory 枚举）**不会被设置**。

- **严重度**: P2 — 可能导致日志分类过滤失效
- **建议修复**: 统一类型，或确保两个属性同步

### B7（P2）: `LoggingSkeletonWrapper` 同步/异步方法体完全重复

- **位置**: `FileDriven.Logging/Wrappers.cs` 第 101-150 行
- **问题**: `ExecuteInternal` 和 `ExecuteInternalAsync` 两个方法的 try-catch-finally 结构、日志调用、统计收集逻辑完全一致，唯一的区别是同步/异步执行：

  **同步版本（第 101-123 行）：**
  ```csharp
  private FileDriven.Logging.Pipeline.LogPipelineContext ExecuteInternal(
      SkeletonContext ctx,
      Func<FileDriven.Logging.Pipeline.LogPipelineContext> executeFunc)
  {
      var stats = CreateStats();
      try { LogStart(); var result = executeFunc(); LogSuccess(stats); return result; }
      catch (Exception ex) { LogFailure(stats, ex); throw; }
      finally { SaveStats(ctx, stats); }
  }
  ```

  **异步版本（第 128-150 行）：**
  ```csharp
  private async Task<FileDriven.Logging.Pipeline.LogPipelineContext> ExecuteInternalAsync(
      SkeletonContext ctx,
      Func<Task<FileDriven.Logging.Pipeline.LogPipelineContext>> executeFunc)
  {
      var stats = CreateStats();
      try { LogStart(); var result = await executeFunc(); LogSuccess(stats); return result; }
      catch (Exception ex) { LogFailure(stats, ex); throw; }
      finally { SaveStats(ctx, stats); }
  }
  ```

- **严重度**: P2 — 代码重复，维护成本高
- **建议修复**: 使用模板方法模式或委托提取公共逻辑

### B8（P3）: `CommandEngine` 与 `NonEventCommandHandler` 命令重复

- **位置**: 
  - `FileDriven.Utilities/CommandExecution.cs` 第 66-88 行（`CommandEngine.RegisterBuiltInCommands()`）
  - `FileDriven.Pipeline/Skeletons/NonEventCommandHandler.cs` 第 72-115 行（switch 分支）
- **问题**: `CommandEngine` 注册了 `sleep`/`echo`/`exit` 三个命令，`NonEventCommandHandler` 的 switch 分支也处理了同样的命令。两个地方维护相同的命令处理逻辑，新增命令需同步修改两处。
- **严重度**: P3 — 低风险但长期维护负担
- **建议修复**: 统一命令处理入口，或让 `CommandEngine` 委托给 `NonEventCommandHandler`

## 二、重复逻辑（Duplications）

### D1（P1）: `FileDrivenLogManager.Shutdown()` 中 Console/Database 模式的摘要输出重复

- 同 B1，两段几乎相同的摘要输出代码
- **建议修复**: 提取共享方法 `PrintLogSummary(string batchId, int logCount)`

### D2（P1）: `LogTryExecuteSkeleton` 同步/异步方法体重复

- **位置**: `FileDriven.Logging/LogPipeline.cs` 第 363-399 行
- **问题**: `ExecuteCore` 和 `ExecuteCoreAsync` 的 try-catch-fallback 逻辑完全一致：

  **同步（第 363-382 行）：**
  ```csharp
  protected override LogPipelineContext ExecuteCore(LogPipelineContext input, SkeletonContext ctx)
  {
      try { return _main.Execute(input, ctx); }
      catch (Exception ex)
      {
          ctx.SetData(new LogPipelineException(ex) { StepName = _main.Name }, "LastException");
          PlaceholderLogHelper.Log("ERROR", "Batch_Routing", _logger.ModuleName, 
              $"Pipeline main path '{_main.Name}' failed: {ex.Message}, switching to emergency fallback");
          return _fallback.Execute(input, ctx);
      }
  }
  ```

  **异步（第 384-399 行）：**
  ```csharp
  protected override async Task<LogPipelineContext> ExecuteCoreAsync(LogPipelineContext input, SkeletonContext ctx)
  {
      try { return await _main.ExecuteAsync(input, ctx); }
      catch (Exception ex)
      {
          ctx.SetData(new LogPipelineException(ex) { StepName = _main.Name }, "LastException");
          PlaceholderLogHelper.Log("ERROR", "Batch_Routing", _logger.ModuleName, 
              $"Pipeline main path '{_main.Name}' failed: {ex.Message}, switching to emergency fallback");
          return await _fallback.ExecuteAsync(input, ctx);
      }
  }
  ```

- **建议修复**: 提取共享的异常处理逻辑

### D3（P2）: `LogPipeline` 管线构建方法骨架创建重复

- **位置**: `FileDriven.Logging/LogPipeline.cs` 第 439-513 行
- **问题**: 虽然已提取 `CreateBaseSkeletons()` 共享方法，但 `BuildDefaultPipeline()`、`BuildMinimalPipeline()`、`CreateWithLogCollect()`、`CreateWithLogCollectAndExceptionHandling()` 四个方法各自独立调用 `CreateBaseSkeletons()` 并构建相似的管线链。每个方法都解构元组并重新组合骨架。
- **建议修复**: 进一步抽象管线构建模式，减少重复组合逻辑

### D4（P2）: `PipelineEntry.ShowFormInternal()` 中 UI 线程调度逻辑重复

- **位置**: `FileDriven.Pipeline/PipelineEntry.cs` 第 189-242 行
- **问题**: `mainForm.BeginInvoke` 分支（第 203-218 行）和 `Task.Run` 分支（第 222-230 行）都执行了相同的 `uiManager.LoadFormConfigAsync(configPath, windowName)` 调用，且都有相同的异常处理和 `done.Set()` 逻辑。
- **建议修复**: 提取共享的异步加载逻辑

### D5（P2）: `Skeletons.cs` 中多个日志 Skeleton 的 Input/Output DTO 模式重复

- **位置**: `FileDriven.Logging/Skeletons.cs` 全篇
- **问题**: 以下每个 Skeleton 都定义了几乎相同的 Input/Output DTO 类，每个都有 `Success` 属性和类似的日志记录模式：
  - `RouterAdapterLogInput/Output`
  - `RouterNormalizeLogInput/Output`
  - `RouterLogCommandLogInput/Output`
  - `ExecutionReportLogInput/Output`
  - `ScriptConverterLogInput/Output`
  - `ValueExtractionLogInput/Output`

  每个 Skeleton 的 `ExecuteCore` 方法都遵循相同的模式：记录开始日志 → 处理输入 → 记录结果日志 → 返回 Output。

- **建议修复**: 抽象泛型基类 `LogSkeletonBase<TInput, TOutput>`，封装通用的日志记录模式

### D6（P3）: `FrameworkInitInput` 与 `FrameworkInitOutput` 字段重复

- **位置**: `FileDriven.Logging/Skeletons.cs` 第 68-86 行
- **问题**: `FrameworkInitInput` 和 `FrameworkInitOutput` 各自声明了相同的 4 个布尔字段（`WdUIInitialized`, `BuiltInFunctionsInitialized`, `TemplateEngineInitialized`, `PathAliasesLoaded`），Input 和 Output 的字段完全一致。
- **建议修复**: 让 Output 继承 Input，或使用同一个类

## 三、冗余逻辑（Redundancies）

### R1（P1）: `LoggingManager` 完全退化为空壳

- **位置**: `FileDriven.Logging/LoggingManager.cs` 第 11-39 行
- **问题**: `Setup()` 和 `Shutdown()` 仅委托给 `FileDrivenLogManager`，无任何额外逻辑：

  ```csharp
  public static void Setup(CliOptions options)
  {
      FileDrivenLogManager.Initialize(options);
  }
  
  public static void Shutdown()
  {
      FileDrivenLogManager.Shutdown();
  }
  ```

  `LoggingManager` 已成为纯转发层，可以完全移除。

- **调用链**: `Bootstrapper.SetupLogging()` → `LoggingManager.Setup()` → `FileDrivenLogManager.Initialize()`
- **建议修复**: 移除 `LoggingManager`，调用方直接使用 `FileDrivenLogManager`

### R2（P1）: `Usage.LoadConfig()` 的静态 `_sharedEntry` 缓存导致内存泄漏

- **位置**: `FileDriven.Launcher/Usage.cs` 第 190-202 行
- **问题**: `_sharedEntry` 静态字段 + 双重检查锁的模式引入了隐式状态，且 `_sharedEntry` 从未被释放（`Dispose` 从未被调用），导致 `ConfigCache` 和 `LoadedConfigs` 内存泄漏：

  ```csharp
  private static PipelineEntry? _sharedEntry;
  private static readonly object _entryLock = new();
  public static LoadResult LoadConfig(string configPath, bool showForm = false)
  {
      if (_sharedEntry == null)
      {
          lock (_entryLock)
          {
              _sharedEntry ??= CreatePipelineEntry();
          }
      }
      return _sharedEntry.LoadConfig(configPath, showForm, showForm ? CommandManager : null);
  }
  ```

- **建议修复**: 实现 `_sharedEntry` 的生命周期管理，或在应用程序退出时释放

### R3（P2）: `PipelineEntry.EnsureSharedLoadedConfigs()` 使用反射访问私有字段

- **位置**: `FileDriven.Pipeline/PipelineEntry.cs` 第 446-470 行
- **问题**: 使用反射访问 `EventBindingResolver` 的私有字段 `_loadedConfigs`：

  ```csharp
  var dictField = typeof(EventBindingResolver).GetField("_loadedConfigs",
      System.Reflection.BindingFlags.NonPublic | System.Reflection.BindingFlags.Instance);
  ```

  这是脆弱的实现，如果 `EventBindingResolver` 的字段名更改，编译时不会报错，但运行时将静默失败。

- **建议修复**: 通过公开接口或 `internal` 可见性来避免反射

### R4（P2）: `Bootstrapper` → `LoggingManager` → `FileDrivenLogManager` 三层委托链

- **位置**: 
  - `FileDrivenBootstrapper.cs` 第 256-259 行（`SetupLogging()`）
  - `FileDrivenBootstrapper.cs` 第 769-772 行（`ShutdownLogging()`）
  - `LoggingManager.cs` 第 21-24 行（`Setup()`）
  - `LoggingManager.cs` 第 35-38 行（`Shutdown()`）
- **问题**: 形成了 **Bootstrapper → LoggingManager → FileDrivenLogManager** 的三层委托链：

  ```
  Bootstrapper.SetupLogging()
    → LoggingManager.Setup()
      → FileDrivenLogManager.Initialize()
  ```

  每一层都没有增加任何价值，只是简单转发。

- **建议修复**: 移除 `LoggingManager`，`Bootstrapper` 直接调用 `FileDrivenLogManager`

### R5（P2）: `PipelineEntry` 静态方法委托给 `PipelineFactory` 形成多层委托链

- **位置**: `FileDriven.Pipeline/PipelineEntry.cs` 第 544-561 行
- **问题**: 实例方法 `CreatePipeline()`（第 337-340 行）委托给静态方法 `CreateFileDrivenPipeline()`，静态方法又委托给 `PipelineFactory.CreateFileDrivenPipeline()`：

  ```
  entry.CreatePipeline(options)
    → PipelineEntry.CreateFileDrivenPipeline(options, ...)
      → PipelineFactory.CreateFileDrivenPipeline(options, ...)
  ```

- **建议修复**: 实例方法直接调用 `PipelineFactory`，移除静态委托方法

### R6（P3）: `AutoInitializeLogging()` 的空 catch 块

- **位置**: `FileDriven.Launcher/FileDrivenBootstrapper.cs` 第 781-796 行
- **问题**: catch 块完全为空：

  ```csharp
  private static void AutoInitializeLogging()
  {
      try
      {
          var projectRoot = ProjectPathManager.FindProjectRoot();
          var projectPath = System.IO.Path.Combine(projectRoot, "FileDriven", "filedriven_log_messages.json");
  ```

  如果日志初始化失败，后续的日志调用会静默失败，难以排查问题。

- **建议修复**: 至少记录一条调试输出，或使用条件编译符号控制详细程度

### R7（P3）: `LogPipeline.ExecuteWithExceptionHandling()` 的空 catch 块

- **位置**: `FileDriven.Logging/LogPipeline.cs` 第 544-551 行
- **问题**: catch 块完全为空：

### 核心问题总结

1. **最严重的错误**：`FileDrivenLogManager.Shutdown()` 中 Console 和 Database 模式的摘要输出代码几乎完全重复（B1/B2），且 Console 模式绕过日志系统直接使用 `Console.WriteLine`
2. **最隐蔽的错误**：`FileDrivenPipelineContext` 使用 `new` 覆盖父类属性（B3），破坏了多态性，行为取决于引用类型而非实际类型
3. **最普遍的重复模式**：同步/异步方法体几乎完全一致（B7、D2），在 `LoggingSkeletonWrapper`、`LogTryExecuteSkeleton` 等多个类中出现
4. **最严重的冗余**：`LoggingManager` → `FileDrivenLogManager` 的双层外观（R1），加上 `Bootstrapper` 的委托，形成三层委托链（R4）
5. **最危险的空捕获**：`AutoInitializeLogging()` 和 `ExecuteWithExceptionHandling()` 中的空 catch 块（R6、R7），静默吞掉所有异常
