# 函数注册与命令执行链路重构方案

> **日期**：2026-07-30 | **版本**：1.0 | **状态**：提案
>
> **问题源**：mainlayout_function_test.json 测试中 `Layout_*` 系列函数未注册导致 FAIL
> **根因**：函数注册链路过度抽象，ECS 命令层与业务函数注册层不恰当耦合

---

## 一、现状分析

### 1.1 问题表现

测试脚本 `mainlayout_function_test.json` 中 template 展开为 `exec Layout_*` 命令后，全部因"函数未在函数注册表中注册"而 FAIL：

| 命令 | 展开来源 | 结果 |
|------|---------|------|
| `exec Layout_GetAllPositions` | `validate-positions` 模板 | FAIL |
| `exec Layout_GenerateReport` | `validate-report` 模板 | FAIL |
| `exec Layout_GenerateJsonReport` | `validate-json-report` 模板 | FAIL |
| `exec Layout_DetectOverlaps` | `validate-overlaps` 模板 | FAIL |
| `exec Layout_ValidateText` × 8 | `validate-text` 模板 | FAIL × 8 |
| `exec Layout_ValidatePosition` × 1 | `validate-position` 模板 | FAIL × 1 |

### 1.2 执行全链路

```
JSON 脚本 (mainlayout_function_test.json)
  ↓ 反序列化
ScriptCommand[] (43 条)
  ↓ ScriptTemplateExpander.Expand()
    template="validate-text" → Action="exec", Target="Layout_ValidateText"
    template="validate-positions" → Action="exec", Target="Layout_GetAllPositions"
  ↓ MetaCommandExtensions.ToMetaCommand()
    构建参数字典: {output, controlName, expectedText}
  ↓ ParseCommandSystem.ParseAndCreateEntity()
    创建 ECS Entity, 写入 CommandMetaComponent
  ↓ CommandSystemCoordinator.Update()
    路由到 ExecSystem (action="exec")
  ↓ ExecSystem.Execute()                              ← Layer 1: ECS
    ↓ AppServiceProvider.Resolve<IFunctionExecutor>()  ← Layer 2: DI
    ↓ FunctionExecutor.HasFunction("Layout_ValidateText")
      → FunctionStorageRegistry.Registry.Contains()   ← Layer 3: 静态门面
        → ITrConfigRegistry 实现                        ← Layer 4: 接口
      → false (从未注册)
    ↓ SetFailure("函数未在函数注册表中注册")
```

### 1.3 函数注册接口冗余

| 接口 | 所在项目 | 角色 | 别名使用处 |
|------|---------|------|-----------|
| `TConfig.IFunctionExecutor` | CsharpPrj/Plate/TConfig | **主线** | ExecSystem, PipelineEntry, Core.cs |
| `Container.Abstractions.IFunctionExecutor` | CsharpPrj/BasicMethod | 旧版(退化) | ExecuteCommandHandler.cs |
| `Modules.EventFramework.Services.IFunctionExecutor` | CsharpPrj/Modules | 事件框架层 | EventTriggerService.cs |

代码中通过 using 别名消歧：
```csharp
using IFunctionExecutor = TConfig.IFunctionExecutor;                        // PipelineEntry.cs
using RegistryIFunctionExecutor = TConfig.IFunctionExecutor;                // Core.cs
using ExecutorIFunctionExecutor = Modules.EventFramework.Services.IFunctionExecutor; // EventTriggerService.cs
using IFunctionExecutor = Container.Abstractions.IFunctionExecutor;         // ExecuteCommandHandler.cs
```

### 1.4 当前架构缺陷总结

| 缺陷 | 严重度 | 说明 |
|------|--------|------|
| **ECS 跨界调用** | 高 | ExecSystem 内部硬编码调用 `IFunctionExecutor`。ECS 命令层与业务函数层不恰当地耦合。 |
| **接口三重定义** | 中 | 3 套 IFunctionExecutor 接口，4 处 using 别名。维护者需追踪多层命名空间。 |
| **参数传递冗余** | 中 | 参数字典经过 3~4 次格式转换才到达目标方法。 |
| **静态门面空转** | 低 | FunctionStorageRegistry 是完全委托的静态门面，无额外逻辑，仅增加抽象层。 |
| **测试操作误入函数层** | 高 | UI 布局验证（纯 WinForms 控件操作）本应走 ECS 命令层，却被路由到业务函数注册表。 |

---

## 二、重构目标

1. **ECS 命令层与业务函数层分离** — ECS System 不直接调用 `IFunctionExecutor`
2. **消除函数注册表与 UI 测试操作的错误绑定** — UI 控件操做走 ECS 命令层，业务函数走 PipelineEntry 管线
3. **减少参数传递层级** — 无参/单参函数跳过 `ParameterBuilder`
4. **清理接口冗余** — 逐步淘汰两套非主线 `IFunctionExecutor` 接口

---

## 三、重构方案（四阶段）

### Phase 1 — 修复测试（应急修复）

**目标**：解决 Layout_* 测试 FAIL，不改现有架构。

**修改方式**：改 `ScriptTemplateExpander.cs`，将 template 展开为 ECS 命令而非 `exec`。

| 模板 | 当前展开（FAIL） | 改为（PASS） |
|------|----------------|-------------|
| `validate-text` | `exec Layout_ValidateText` | `validate {controlName} expectedText={text}` |
| `validate-position` | `exec Layout_ValidatePosition` | `validate {controlName} expectedX={x} expectedY={y}` |
| `validate-positions` | `exec Layout_GetAllPositions` | `layout positions` |
| `validate-report` | `exec Layout_GenerateReport` | `layout report` |
| `validate-json-report` | `exec Layout_GenerateJsonReport` | `layout json-report` |
| `validate-overlaps` | `exec Layout_DetectOverlaps` | `layout overlaps` |

**涉及文件**：

| 文件 | 变更 |
|------|------|
| `FileDriven.Utilities/ScriptRunner/Core/Models/ScriptTemplateExpander.cs` | 修改 6 个 case 的展开逻辑 |
| `FrontEndDriven/CommandExecution/ECS/CommandSystems.cs` | RegisterDefaultSystems 中新增 `LayoutInspectSystem` 注册 |

**新增代码**：`LayoutInspectSystem.cs`（ECS System，约 120 行），支持：

| 命令 | target | 功能 |
|------|--------|------|
| `layout positions` | `positions` | 列出所有控件位置 |
| `layout report` | `report` | 生成布局文本报告 |
| `layout json-report` | `json-report` | 生成布局 JSON 报告 |
| `layout overlaps` | `overlaps` | 检测控件重叠 |

**预估工时**：约 1 小时。

### Phase 2 — ECS 与 FunctionExecutor 解耦

**目标**：消除 ExecSystem 对 IFunctionExecutor 的硬编码依赖。

**当前调用链**：
```
ExecSystem (ECS层) → AppServiceProvider.Resolve<IFunctionExecutor> → FunctionExecutor.Core
```

**改为 Component 桥接**：

```csharp
// ExecSystem — 不再直接调用 IFunctionExecutor
public class ExecSystem : CommandSystemBase
{
    public ExecSystem(EntityManager entityManager) : base(entityManager, "exec") { }

    public override void Execute(Entity entity, CommandMetaComponent meta)
    {
        var target = meta.Target;
        if (string.IsNullOrWhiteSpace(target))
        {
            SetFailure(entity, "exec: 缺少目标函数名");
            return;
        }

        // 改为写入 ExecuteFunctionComponent → 由 PipelineEntry 在管线层消费
        EntityManager.AddOrSetComponent(entity, new ExecuteFunctionComponent
        {
            FunctionName = target,
            Parameters = meta.Parameters != null
                ? new Dictionary<string, object?>(meta.Parameters)
                : new Dictionary<string, object?>(),
            ExecutionState = FunctionExecutionState.Pending
        });
        // 状态保留为 Pending，管线层消费后更新 Success/Failed
    }
}
```

```csharp
// [新增] CommandExecution.Components/ExecuteFunctionComponent.cs
public enum FunctionExecutionState { Pending, Executing, Success, Failed }

public class ExecuteFunctionComponent
{
    public string FunctionName { get; set; } = "";
    public Dictionary<string, object?> Parameters { get; set; } = new();
    public FunctionExecutionState State { get; set; } = FunctionExecutionState.Pending;
    public string? ErrorMessage { get; set; }
    public object? ResultValue { get; set; }
}
```

```csharp
// PipelineEntry 管线层新增 FunctionExecutionStage
// 在管线迭代中消费 ExecuteFunctionComponent
// 调用 IFunctionExecutor 的代码集中在这里，ECS 层不再感知 IFunctionExecutor
```

**涉及文件**：

| 文件 | 变更 |
|------|------|
| `FrontEndDriven/CommandExecution/ECS/CommandSystems.cs (ExecSystem)` | 改为写入 Component |
| `FrontEndDriven/CommandExecution/Components/` (新增) | `ExecuteFunctionComponent.cs` |
| `FileDriven.Pipeline/PipelineEntry.cs` | 新增 `FunctionExecutionStage` 消费逻辑 |
| `FrontEndDriven/Ports.cs` (CommandInputPort) | 确保管线含 FunctionExecutionStage |

**架构变化**：

```
前:  ExecSystem → IFunctionExecutor (直连耦合)
后:  ExecSystem → [ExecuteFunctionComponent] → PipelineEntry → IFunctionExecutor (Component桥接)
                                    ↑
                              ECS Entity 通信
```

**预估工时**：约 2~3 小时。

### Phase 3 — FunctionExecutor 参数传递优化

**目标**：减少无参/单参函数的参数构建开销。

**当前**：所有函数都经过 `ParameterBuilder.Build()` → `MethodInfo.Invoke()`。

**优化**：根据参数数量短路。

```csharp
// Core.cs → ExecuteByNameInternal
private async Task<object?> ExecuteByNameInternal(string functionName, Delegate del, object? parameters)
{
    var paramInfos = del.Method.GetParameters();
    var paramCount = paramInfos.Length;

    // 短路 1: 无参函数
    if (paramCount == 0)
    {
        return await AwaitTaskResult(del.Method.Invoke(del.Target, null));
    }

    // 短路 2: 单参函数，且参数不是命名参数字典 → 直接传
    if (paramCount == 1 && parameters is not IDictionary<string, object?>)
    {
        return await AwaitTaskResult(del.Method.Invoke(del.Target, new[] { parameters }));
    }

    // 常规路径: ParameterBuilder 解包参数
    var descriptors = paramInfos.Select(p => new ParamConfigAdapter(...)).ToList();
    var buildResult = new ParameterBuilder().Build(descriptors, parameters);
    var args = buildResult.IsSuccess ? buildResult.Args : new[] { parameters };
    return await AwaitTaskResult(del.Method.Invoke(del.Target, args));
}
```

**涉及文件**：

| 文件 | 变更 |
|------|------|
| `CsharpPrj/Operation/StateHoldDriven/FunctionStorage/Framework/Core.cs` | ExecuteByNameInternal 增加短路分支 |

**预估工时**：约 1 小时。

### Phase 4 — 接口归一化（长期清理）

**目标**：消除 3 套 IFunctionExecutor 接口的冗余。

**步骤**：

| 步骤 | 操作 | 影响范围 |
|------|------|---------|
| 1 | `Container.Abstractions.IFunctionExecutor` 标记 `[Obsolete]`，注释指向 TConfig | 仅接口定义文件 |
| 2 | `Modules.EventFramework.Services.IFunctionExecutor` 标记 `[Obsolete("...")]` | 仅接口定义文件 |
| 3 | 移除 `ExecuteCommandHandler.cs` 中 `using IFunctionExecutor = Container.Abstractions.IFunctionExecutor` | 1 个文件 |
| 4 | `EventTriggerService.cs` 中 `using ExecutorIFunctionExecutor` → 改直接引用 TConfig | 1 个文件 |
| 5 | 统一 using 为 `using IFunctionExecutor = TConfig.IFunctionExecutor` | ~5 个文件 |

**预估工时**：约半天（含回归验证）。

## 四、整体时间线

| Phase | 内容 | 预估工时 | 前置依赖 | 收益 |
|-------|------|---------|---------|------|
| **Phase 1** | 修复测试（模板走 ECS） | 1h | 无 | ✅ 测试立刻 PASS |
| **Phase 2** | ExecSystem 解耦 | 2~3h | 无 | ✅ ECS 与 FunctionExecutor 解耦 |
| **Phase 3** | 参数传递优化 | 1h | 无 | ✅ 减少 ~60% 反射开销 |
| **Phase 4** | 接口归一化 | 0.5d | Phase 2 | ✅ 接口数量 3→1 |

**建议执行顺序**：Phase 1 → Phase 3 → Phase 2 → Phase 4

> 理由：Phase 1 解决最紧迫的测试问题。Phase 3 改动最小立即受益。Phase 2 架构改动较大，可放在 Phase 1 测试通过并合入主干后。Phase 4 是清理收尾，可延后。

## 五、风险与兼容性

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| Phase 2 变更 ExecSystem 行为影响现有功能 | 中 | ExecSystem 输出不变（Success/Failed 状态仍在 CommandStatusComponent），仅调用路径改为 Component 桥接。保持 SetSuccess/SetFailure 不变。 |
| Phase 3 短路分支遗漏某些参数传递场景 | 低 | 短路条件严格检查 `paramCount == 0` 或 `paramCount == 1 && parameters is not Dictionary`。不符合条件的走原路径。 |
| Phase 4 废弃接口后仍有引用 | 低 | 编译期产生警告。清理依赖后再删除。 |
